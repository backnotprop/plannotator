## Plannotator Inbox

One long-lived local server per machine. Agents leave messages, `:::question` blocks, files and guided reviews there for the person, and the person answers when they can. Nothing holds an agent session open on it. A reply wakes the session that asked, through the Claude Code, Pi or OpenCode connection, or reaches any other agent through `wait_for_reply`. The window's design of record and the owner's decisions are kept privately (not in this repo); this section carries what a build here needs from them. Not built: the Mac notification helper (only a spike so far). Where it is documented for users and agents: `plannotator --help` (`apps/hook/server/cli.ts`) and the agent guide `plannotator inbox --help` (`apps/hook/server/inbox-help.ts`, see "The command"), the `## plannotator inbox` section of the `plannotator` skill (`apps/skills/core/plannotator/SKILL.md`; deliberately short: the usage lines, when to use the Inbox, tool-or-MCP, and a pointer to read `plannotator inbox --help` first, so details live in the guide, not the skill), and the marketing reference page `apps/marketing/src/content/docs/reference/inbox.md` (`/docs/reference/inbox/`). A change to the command, the MCP tool list or the knob updates the guide and the reference page, and the skill only when its usage lines or its when-to-use rule change.

**The command** (`apps/hook/server/inbox-command.ts`, usage in `cli.ts`, the agent guide in `inbox-help.ts`).
- `plannotator inbox` starts the Inbox in the foreground and opens it in the browser, or opens the running one.
- `plannotator inbox --background` starts it detached (its own session, output in `inbox/inbox.log`), prints the URL and exits 0. It never opens a browser, so an on-demand start never pops a tab mid-work.
- `plannotator inbox --no-open` runs it here without a browser.
- `--tailscale` (with any of the three) also publishes it over the tailnet for this run (see "Over your tailnet"); with an Inbox already running, the command asks it to publish through the token-guarded `POST /api/inbox/control/tailscale`. Stdout stays the local URL alone; the tailnet URL (with a QR on a TTY) or the reason it is not published goes to stderr, and the exit code never depends on Tailscale. A restart to update of a run published only by the flag passes `--tailscale` on.
- `plannotator inbox mcp` is the stdio MCP entry (`apps/hook/server/inbox-mcp-shim.ts`), a thin JSON-RPC proxy:
  - It POSTs each stdin message to the Inbox's `/mcp` and writes every answer to stdout.
  - It re-reads `inbox/inbox.json` on every message and starts a stopped Inbox through the `--background` path (no tab).
  - When the agent leaves them out, it fills `project_path` (its working folder, or `PLANNOTATOR_CWD`) and `agent_session`.
  - The session is the agent host's own when the shim runs inside one (`inboxHostSessionFromEnv`): a well-formed `PLANNOTATOR_SESSION_TAG` (`<host>:<id>`, host `claude-code`, `pi` or `opencode`, id `[A-Za-z0-9][A-Za-z0-9._-]{0,127}`; anything else is ignored), else Pi's own `PI_SESSION_ID` (Pi sets it on each bash tool call). The host session is adopted only when the agent named no `agent_host` or that same host; an agent that names another host gets the shim's own `ses_` id, so a reply to it never wakes the session. On `send_message`, `submit_guide` and `record_decision` it then also fills `agent_host` and `agent_name` (`Claude Code`, `Pi`, `OpenCode`; the name only when the agent gave none), so the author is byte for byte what that host's `plannotator_inbox` tool writes. A script or command a Claude Code or Pi session runs therefore sends as that session: the same default thread, `asked_by: "me"` and `wait_for_reply` see the tool's threads, and the person's reply wakes the session through its connection (`pendingReplies` matches on `author.session`). An `agent_session` the agent passes always wins. A tag inherited by a long-lived process started from an agent's shell (tmux, nohup) keeps naming that session; pass `agent_session` explicitly to override.
  - Otherwise it is one `ses_` id per shim process, so an MCP client's identity ends with its MCP server process; a client that wants its threads across restarts passes `agent_session` itself. Replies to a session that ended are never handed to another session.
  - OpenCode exports no session variable to the commands it runs (OpenCode 2's `shell.create.before` hook carries no session id; OpenCode 1's `shell.env` does but OpenCode 1 has no wake), so there a command still gets a fresh id.
- Any other argument exits 1 with a usage line.
- Starts are serialized by `inbox/start.lock` (mkdir, stale after 30 s), so two agents that find the Inbox stopped at once start one. The detached child runs under its starter's lock (`PLANNOTATOR_INBOX_LOCK_HELD`, internal, scrubbed at start).
- The Inbox never registers in `sessions/` and never arms auto-update, so it never holds an update back.
- `plannotator inbox --help` (and `inbox mcp --help`) prints the **agent guide**, a markdown document an agent with no skill can read once to use the Inbox: what it is, when to use it, how to reach it, one section per MCP tool, thread routing, where replies go, the question syntax, connecting other agents, commands and flags, data and removal. `formatInboxHelp` in `apps/hook/server/inbox-help.ts` builds it from the code it describes: the tool list `INBOX_MCP_TOOLS` (its per-tool `TOOL_GUIDE` is typed by it, so a new tool does not compile without a section), `QUESTION_AUTHORING_GUIDE` verbatim, `INBOX_SECTIONS`, `INBOX_TOOL_NAME` / `INBOX_FILLED_ARGUMENTS` / `INBOX_TOOL_DEFAULTS`, the window's per-harness setup (`HARNESSES` / `harnessPanel`, `packages/inbox/harnesses.ts`, reached through the `@plannotator/inbox/harnesses` export) and the commands block `INBOX_COMMAND_USAGE` (`cli.ts`, also the `SUBCOMMAND_HELP.inbox` entry the skill freshness test reads). It names this CLI's absolute command (`selfCommand()`: the binary, or bun plus the entry script) and the resolved data dir. `index.ts` prints it for `helpSubcommand === "inbox"`; the top-level help points agents at it. `inbox-help.test.ts` keeps it true: every tool a real Inbox serves has its section and every argument it names is in that tool's served schema, the question guide is byte for byte, every harness is listed with its setup line, every flag and subcommand the parser in `inbox-command.ts` accepts appears, and the CLI as a process prints it (exit 0, empty stderr, no Inbox started). A new tool, tool argument, harness or flag updates the guide.

**Local only by default; each wider path is a switch.**
- It always binds `127.0.0.1` and ignores `PLANNOTATOR_REMOTE` and `PLANNOTATOR_PORT`, because it holds tokens and everything agents sent. To reach the window from your other devices, turn on "Over your tailnet" (below).
- Port: the last one (from the registry) comes first, so the browser's notification permission holds. When something else holds that port, the Inbox takes a random port and shows a one-time notice (stderr and the list model's `notice`). It never uses 19432, nor 8443 (Phones' tailnet port; the window's own tailnet mapping uses the Inbox's port, so the two never collide).
- "Over your tailnet" (off by default; `packages/server/inbox-tailscale.ts`, pure checks in `packages/shared/inbox/tailnet.ts`): `plannotator inbox --tailscale` (this run), `PLANNOTATOR_INBOX_TAILSCALE`, or config.json `inboxTailscale` (Settings' switch) publishes the window with `tailscale serve --bg --https=<the Inbox's port> http://127.0.0.1:<proxy port>`, serve and never funnel.
  - The socket decides, as for Phones: serve picks its handler by TLS SNI and passes the client's own Host through (`r.Out.Host = r.In.Host`, `ipn/ipnlocal/serve.go`), so a peer could claim `Host: 127.0.0.1:<port>`. The mapping therefore points at a second loopback listener that only serve is pointed at; the window's port is unchanged and never learns the tailnet name. That listener hands requests to the window's handler marked `via: "tailnet"`.
  - Owner only: every request on that listener must carry `Tailscale-User-Login` equal to the login that owns this machine (`tailscale status --json`: `Self.UserID` -> `User[id].LoginName`, read at each publish; `parseTailscaleSelfIdentity`) or one in config.json `inboxTailscaleAllow`, compared case-insensitively after RFC 2047 Q-decoding (`decodeTailscaleHeaderValue`; serve Q-encodes non-ASCII logins). Serve deletes incoming `Tailscale-User-*`, `Tailscale-Funnel-Request` and `Tailscale-Headers-Info` before setting its own, so a client cannot forge them through serve. A tagged peer gets no identity headers (`403 tailnet_identity_required`), another login `403 tailnet_identity_refused`, a funnel request (`Tailscale-Funnel-Request`) `403 tailnet_funnel_refused`. A tagged machine has no owner: publishing is refused, with the reason, until `inboxTailscaleAllow` names someone.
  - Also on that listener: Host must be the served MagicDNS name with the HTTPS port (`403 forbidden_host`), and `Sec-Fetch-Site: cross-site` / `same-site` is refused (`403 cross_site`) except a top-level GET navigation to `/` and GETs of `/api/html-assets/` (an attached page's sandboxed srcdoc frame is cross-site by construction): the identity is ambient, like a cookie, and every `*.ts.net` machine of the tailnet is same-site.
  - Through the tailnet (`via: "tailnet"`, whatever Host is claimed): `/mcp`, `/api/inbox/bridge/*`, `/api/inbox/control/*` and the device door answer `403 local_only`; so do pairing a phone, Phones' tailnet and Wi-Fi switches, and turning the window's tailnet switch on (off is allowed). Read routes (the list, threads, settings, attachments, guides, a message's images `GET /api/inbox/messages/:id/image`) answer the owner as on loopback, behind the listener's checks. Every non-GET request runs `isSameOriginOrNoOrigin` (the page's origin is `https://<MagicDNS name>:<port>`), then the `serverSession` guard. `/mcp` also refuses any non-loopback Host on the window's port, so `PLANNOTATOR_ALLOWED_HOSTS` cannot widen it.
  - Lifecycle: the mapping is recorded in `inbox.json` (`tailscale.https_port`, `proxy_port`) BEFORE it is made, so a crash always leaves a record. Every start first removes a recorded mapping whose proxy port is not this run's (a dead ephemeral port any later local server could bind; see "The crash window" under "Tailnet sessions"), switch on or off, then publishes when on. A take-down that fails keeps the record (never forgotten, retried at the next start and by `uninstall --purge`) and nothing is published over it that run. Taken down at every clean stop (quit, SIGINT/SIGTERM, the stop route, a restart to update before the new binary starts) and by `uninstall --purge` (`takeDownInboxTailscale`, by the ports `inbox.json` kept). While a mapping exists an `exit` handler and a SIGHUP route (the Inbox's clean stop, then exit 129) are installed, never otherwise; so while published, `nohup plannotator inbox --tailscale &` ends with the terminal (start it with `--background` instead). A mapping on the port that the Inbox did not make is never replaced or taken down: Settings says how to clear it. A take-down that fails keeps the switch on (`409 tailscale_unavailable`) and the ports in `inbox.json`.
  - A hand-made mapping onto the window's own port (`tailscale serve --https=<P> http://127.0.0.1:<P>`, the old workaround) hands the tailnet the whole Inbox, `/mcp` included, since serve passes a peer's Host through. The window's port therefore refuses (`403 local_only`) every request carrying `Tailscale-Headers-Info`, `Tailscale-User-Login` or `X-Forwarded-For` (serve always sets X-Forwarded-For; a local client never sends these). The first such request reads `serve status` and names the mapping (`tailscale.exposed: [{ https_port, target }]`, from `serveStatusRoutes` + `serveTargetIsLoopbackPort`, web handlers and TCP forwards); each publish reads it too. Stderr and Settings say plainly that it exposes the whole Inbox and its agent tools to the tailnet, and Settings offers "Replace it with the owner-only address" (`POST /api/inbox/settings` `{ tailscale: { on: true, replace_exposed: true } }`: removes each serve port whose route still lands on the window's port, then publishes). Without that request the switch never takes it over: publishing on its port is refused with the same words. A raw TCP forward carries no headers, so only the serve-status read catches it.
  - What a login let in can do: everything the window does, and a reply, and above all a New message, becomes a turn in a live agent session on this machine. So any allowed login, or anyone holding the owner's unlocked, signed-in phone, can drive agents that run commands here. Let in only logins you would let sit at this computer.
  - Never fatal: Tailscale missing, stopped or signed out leaves the Inbox running on loopback; the reason goes to Settings (`tailscale.error`), `inbox.json` and stderr.
  - Settings' "Over your tailnet" block: the switch (saved to config.json and applied at once; locked while the env var decides; shows on with the error while publishing fails, so one click turns it off), the address, who may open it, "Keep it on at every start" for a run published by the flag, and the exposure warning with "Replace it with the owner-only address". Turning it off through the tailnet answers first and closes the listener a moment later. A page opened over the tailnet (`via: "tailnet"` on `GET /api/inbox/settings`) cannot turn it on.
  - Notifications are per origin, so the tailnet address is a separate permission; the one-time line says "moved" only for a port change under the same name (both loopback counts as the same), and a different name gets the plain ask.
- A paired phone reaches it only through the device door (see "Phones"), and only over a path the person switched on in Settings:
  - "Reach from my tailnet" (off by default): a second loopback listener that serves the device door and nothing else, published with `tailscale serve --bg --https=8443 http://127.0.0.1:<door port>`, serve and never funnel. The window's port is never published: `tailscale serve` passes the client's own Host header through, so only the socket can keep tailnet requests on the door. The switch is kept in `inbox.json` as `tailnet: { https_port: 8443, door_port }`; each start publishes again. The listener and the mapping go when the switch goes off and at every clean stop (quit, the stop route, and a restart to update, before it starts the new binary). A mapping a crash left (kill -9) is re-pointed by the next start before anything else, or taken down when it cannot publish; SIGHUP runs the clean stop while a mapping exists (installed only then, as `--tailscale` does, so `nohup` keeps its meaning otherwise); `uninstall --purge` takes a leftover down by `door_port`. A take-down that fails changes nothing (switching off answers `409 tailnet_unavailable`, `door_port` is kept). The window's port never adds the tailnet name to its Host allowlist. A mapping on 8443 that the Inbox did not make (its target is not this run's or the last run's door listener) is never overwritten or taken down: the switch stays off and Settings says so.
  - "Reach from this Wi-Fi" (off by default; `packages/server/inbox-lan.ts`, contract section 3): a TLS listener on every interface (`0.0.0.0`) that serves the same door-only handler as the tailnet's listener, on a port chosen free the first time and kept in `inbox.json` as `lan: { port, on }` (kept when switched off, so on again reuses it). It stays on all interfaces, not the Wi-Fi address alone: a socket bound to one address dies with a new DHCP lease, and `Bun.serve` cannot bind to an interface. The certificate is self-signed ECDSA P-256 (`CN=Plannotator Inbox`, never rotated), made with two `openssl` child processes the first time and kept in `inbox/tls/` (files 0600 in a 0700 folder); its SHA-256 (of the DER) rides the QR as `fp` and the phone pins it. A `_plannotator-inbox._tcp` Bonjour record (instance `computer.name`, TXT `v=1`, `fp=`) goes out through `dns-sd -R` (macOS) or `avahi-publish -s` (Linux) as a child process under `sh`, which ends the publisher when its stdin closes, so a kill -9 leaves no record; with neither, the listener still answers at the QR's address and Settings says phones will not list it. Pairing over the Wi-Fi is by the QR's secret only: the LAN listener's `pair` refuses six digits with `400 code_not_accepted_here` (a Bonjour record anyone on the Wi-Fi can publish must never become the pin), while the window's port and the tailnet's listener take both; the record's `fp` only lets a phone already paired by QR follow the computer to a new address. The QR's `lan` is the first private IPv4 address that is not loopback, link-local or Tailscale's, read when the offer is made. Off closes the listener and the record and keeps the port with `on: false`; a listener that cannot open at start shows the switch on with the reason, and off works; a clean stop closes both and keeps the switch, and the next start opens the same port with the same certificate. `openssl` missing answers `409 lan_unavailable` and the switch stays off.
  - The relay (R1; `packages/server/inbox-relay.ts`, `apps/relay`, contract section 4): not a listener. The Inbox makes an outbound mailbox at the first pairing and holds one WebSocket to it while a phone is paired; the relay holds only hashes, each phone's relay switch, its APNs token and envelopes it cannot open. Through it (R2) a phone reads and answers the Inbox from anywhere: store lines down, commands up, each sealed under keys made at pairing.

**Connecting the agents on this computer** (`packages/server/inbox-agents.ts`; approved design record "inbox-agent-awareness", not in this repo; decisions 1, 2, 3, 7).
- When: a person's `plannotator inbox` (with or without `--no-open`), never `--background`, the shim, a connection that starts a stopped Inbox, or the window's Restart (`spawnDetachedInbox` marks those `PLANNOTATOR_INBOX_DETACHED=1`, scrubbed at start; `PLANNOTATOR_INBOX_LOCK_HELD=1` alone counts as detached too, because an Inbox of 0.28.17 or older spawns its Restart into an updated binary, and every other detached start, with only that marker). Starting the Inbox: `inbox.connectAgents()` once it listens, off the request path, its lines on stderr when done. An Inbox already running (an agent started it): the command opens the window, then `POST /api/inbox/control/connect` (connection-route guards: loopback Host, no Origin, the registry token; an older Inbox answers 404 and nothing happens); the step then runs in that Inbox's process, with the environment (PATH, home) the agent started it with. `PLANNOTATOR_INBOX_CONNECT=0` in either environment skips it. One run at a time (`connectAgents` is single-flight); stdout is unchanged.
- What: every agent found (the install script's rules: its command on PATH, or its folder; Cursor also by `cursor` / `cursor-agent`, Kiro by `kiro-cli`, Codex by `$CODEX_HOME` holding config, a relative one resolved against the working folder as Codex does) with no record in `inbox/agents.json` gets a `plannotator-inbox` MCP server running `<selfCommand> inbox mcp`, through its own `mcp add` where it has one (Codex `codex mcp add … --`, Gemini `gemini mcp add -s user` (`$GEMINI_CLI_HOME` honored), Windsurf/Devin `devin mcp add -s user … --`, Amp, Pi 0.99+ without the extension `pi mcp add`), each only after its `--version` line has that CLI's own shape (`VERSION_SHAPES`: a program that merely shares the name, cln's `pi`, amp.rs, is never handed it; a build older than its `mcp add` is left to the person: Pi before 0.99, which would read the words as a chat prompt, Codex CLI before 0.35.0 and Gemini CLI before 0.1.19), else one key in a plain-JSON file (`mcpServers` in `~/.cursor/mcp.json`, `~/.kiro/settings/mcp.json`, the Claude desktop app's `claude_desktop_config.json`; created when missing). JSON edits are lossless (`packages/server/json-edit.ts`: only that member's text is inserted or cut, in the file's own style and dominant line ending, BOM kept; a file that is not strict JSON or has a duplicate key on the path is refused with the reason). Add then remove gives the file back byte for byte: the record keeps the add's exact text change (`undo: { before, after }` on the agent's record in `agents.json`), and removal puts `before` back while `after` is still in the file untouched, so an empty file stays empty, a final newline or its absence stays, and a container Plannotator made goes; a file Plannotator created (`created`) is deleted once only the empty containers are left; an entry the person edited is cut alone; written at a symlink's target, atomic, a no-op when nothing changes (agent-files.ts). Codex's config.toml is read with `Bun.TOML.parse` (every TOML form). Pi with Plannotator's extension (Pi's `settings.json` `packages`) and OpenCode with its plugin (the global `opencode.json(c)` `plugin`, or `plugins` strings or `{ package }`): `inboxTool.<host> = true` in config.json, unless config.json already decides it (false is recorded `off`) or `PLANNOTATOR_INBOX_TOOL` does (nothing written). Claude Code: nothing (said "already on" when the plugin is enabled). Left to the person (`manual`): Codex or Gemini found without its CLI, Pi before 0.99, a CLI whose version line is not its own, Cline (its `mcp add` is not verified), OpenCode without the plugin. Editors (VS Code, Zed, JetBrains, Goose) are never written. The agent CLIs run with no stdin in their own process group; the time limit kills the group, and the answer comes at exit even if a grandchild keeps the output open.
- Rules: an agent with a record is never added again by itself (turned off, removed outside Plannotator: `removed_outside_at`, checked read-only each run; foreign). An entry is ours when it runs exactly this CLI's command or the one its record says Plannotator wrote; for "already connected", also any `plannotator` binary or checkout running `inbox mcp` (`isPlannotatorInboxCommand`: the program's name is exactly `plannotator`, not `my-plannotator-proxy`). Anything else named `plannotator-inbox` is never replaced and is recorded `foreign`. A refused file or a failing or hung `mcp add` is tried again next run and said again only when its reason changes (`failures` in agents.json). Limits: 10 s per agent, 30 s in all (agents still going are `unfinished`). A test run (PLANNOTATOR_TEST_SANDBOX) whose home is not a scratch folder connects nothing (`agentHomeAllowed`).
- Said once: the first run "Connected Codex, Gemini CLI and Cursor to the Inbox (Claude Code was already on)." plus "Agents use it from their next session. PLANNOTATOR_INBOX_CONNECT=0 skips this step; plannotator uninstall removes what it added."; a later run "Connected Amp to the Inbox (new on this computer)."; failures and foreign entries name the file and reason (`formatConnectReport`); an agent only a person can connect (no CLI on PATH, Pi before 0.99, Cline) is named with its reason ("Pi needs connecting by hand: …"), once per reason (`manual_said` in `agents.json`, `manual_why` on the report); time limits are said as they are (`formatSeconds`: "1.5 s"). The run's report is kept in `agents.json` (`last_report`, `seen: false` when it has news) and served at `GET /api/inbox/agents` (local only; records with `~` paths). Uninstall removes only entries Plannotator recorded as `added` that still run the command it wrote; with no record at all (`agents.json` lost) nothing is removed, and an entry that runs exactly the binary being uninstalled is named in a warning with how to remove it, since the person may have added it by hand; one the person added (`found`) is left.
- Tests: `packages/server/inbox-agents.test.ts` (fake agent CLIs on a scratch PATH and HOME, `tests/helpers/fake-agents.ts`; the real CLIs are never run), `packages/server/inbox-connect-route.test.ts`, `apps/hook/server/inbox-connect-cli.test.ts` (the CLI as processes), the uninstall block in `packages/server/uninstall.test.ts`. The guard test also fails on a path from the real home to an agent's folder and on connecting agents with no agent environment (`agentHomeFindings`, `agentConnectFindings`).

**The note in each agent's instructions** (`packages/server/inbox-agent-notes.ts`; decision 5).
- Written only with the person's yes: the note dialog's Add, a Settings → Agents switch, or `plannotator inbox --notes <ids>` (the install prompt runs it with only the agents the person agreed to in chat; it starts nothing, refuses an agent not found on this computer, and marks the question answered only when a note is there now). Never by a start, the shim or a connection. `PLANNOTATOR_INBOX_NOTES=0` hides the offer, refuses new notes, and lists a note row only for a note already written, so it can be switched off; notes already written stay until switched off or uninstalled.
- Where: Claude Code `~/.claude/rules/plannotator-inbox.md` (a file Plannotator owns; `CLAUDE_CONFIG_DIR`), Codex `AGENTS.override.md` when it exists else `AGENTS.md` (`CODEX_HOME`; created only without an override), OpenCode `$OPENCODE_CONFIG_DIR` / `$XDG_CONFIG_HOME/opencode/AGENTS.md` ONLY when it exists (creating it would stop OpenCode 1 reading `~/.claude/CLAUDE.md`; state `unavailable` otherwise), Pi the first that exists of `AGENTS.override.md`, `AGENTS.md`, `AGENTS.MD`, `CLAUDE.md`, `CLAUDE.MD` in `PI_CODING_AGENT_DIR` (Pi reads only one; `AGENTS.md` created only when none does), Gemini CLI `~/.gemini/<context.fileName>` (default `GEMINI.md`). Copilot CLI and Mistral Vibe are not offered (their MCP connection is out of scope; Copilot's file is not verified). Kiro and Cursor have no file.
- Edits work on the file's own text: every byte outside the block stays, new lines take the file's dominant line ending (more CRLF than lone LF: CRLF), a UTF-8 BOM is kept, and a re-add that finds the block unchanged never rewrites the file. Records hold the RESOLVED path (a symlinked file, or a symlinked folder such as `~/.claude` -> dotfiles), so switching off and uninstall find the very file a note created. A file two agents share (Pi's `AGENTS.md` a link to Codex's) holds one section, recorded for both; turning one off keeps it while the other is on (`shared_with` on the status, said on the card and in Settings).
- The block: `INBOX_NOTE_START` (`<!-- plannotator-inbox:start v1 · added by Plannotator. Remove it in the Inbox's Settings or with \`plannotator uninstall\` -->`), the DESIGN.md §2.3 note, `<!-- plannotator-inbox:end -->`, appended at the END after one blank line. The file's last byte decides how the block ends, so removal gives the file back byte for byte with or without the record: a file that ended with a line break gets the block plus one; a file that ended without (`abc`) gets the two line breaks before the block and none after, so the block is its last bytes; whitespace-only text is kept, with the block after it (an empty file, or one ending in a line break, gets the block plus a line break; one like " " that does not end in a line break gets one line break first, so the start marker begins its own line, and none after the block). Exactly one start before exactly one end is ours; none appends; anything else is `damaged` and nothing is written. `inbox/agent-notes.json` keeps each block's SHA-256: a newer version is written only over an untouched block, a block the person edited (`edited`) is never overwritten, and switching it off removes it as they left it (plus the blank line the writer added). A file Plannotator created is deleted when the note was all it held; a file the person had never is. Line endings and mode kept, symlinks written at their target, atomic, no write when nothing changes (agent-files.ts).
- Switching a note off removes the block from the file its record names AND from every file that agent could read it in, when they differ (Codex: the note went into `AGENTS.md`, then `AGENTS.override.md` appeared). Until then the status reads the recorded file, so the switch shows on with a line naming where the note is (`noteStatus`).
- Plain `uninstall` and `--purge` remove every recorded note, then any of the known files that still holds the markers (`planInboxNoteRemoval`; Claude Code's own rules file is deleted when the note is all it holds, record or not); `--dry-run` lists them ("you edited it" when so), and a damaged section is named and left. `--purge` removes `inbox/agent-notes.json` with `inbox/`.
- `plannotator inbox --help` lists every note file on this computer and how `--notes` adds it ("A note in each agent's instructions").

**The agent-note dialog and Settings → Agents** (`packages/inbox/components/AgentNoteDialog.tsx`, `AgentsSettings.tsx`, pure helpers `packages/inbox/agents.ts`; read from `GET /api/inbox/agents`, local only). **Registry** `${dataDir}/inbox/inbox.json` (`packages/shared/inbox/registry.ts`).
- Shape: `{ v, pid, port, url, version, token, serverSession, startedAt, tailnet?, lan?, tailscale? }` (`tailnet: { https_port, door_port }` while "Reach from my tailnet" is on, `lan: { port, on }` once "Reach from this Wi-Fi" was switched on, `tailscale: { url, error, https_port?, proxy_port? }` while "Over your tailnet" is on, the ports naming the mapping this Inbox made), mode 0600, written atomically at every start and kept after exit. "Found" means the file exists. The token rotates every start.
- Running: `GET /api/inbox/health` on that port answers with this entry's `serverSession`.
- Stopped: a dead pid with no answer, a port answering for another Inbox, or a live pid with nothing listening (a reused pid).
- Busy: a live pid whose port takes the health request but does not answer in time. Callers wait for a busy Inbox (up to 20 s, then an error) and never replace it, because a second process would be a second writer on the store.
- Callers re-read the registry on every call.
- An Inbox whose data is gone exits: every 5 s (`INBOX_DATA_CHECK_MS`) it reads `inbox.json` (`probeInboxData`). It is a miss ONLY when the file or its folder does not exist (ENOENT, ENOTDIR) or the file names another `serverSession`; any other error (EACCES, EIO, ESTALE, a file that does not parse) is unknown and leaves the count alone, and the folder's device and inode are not looked at (a remount or a moved copy must not end it). Two misses in a row stop it cleanly, then it says why on stderr (plus the manual `tailscale serve --https=<port> off` when the tailnet take-down failed) and the process exits 0 (`onDataGone`). Nothing could reach it (agents find an Inbox through the file) and it has no store, so it must not run on headless (an e2e once removed its temp folder under a live `--tailscale` Inbox, which ran for two days at 100% CPU, cause unknown). It is a timer, so it cannot end an Inbox stuck in a synchronous loop. After it starts, the Inbox rewrites `inbox.json` only while the file names its own `serverSession` (`updateOwnInboxRegistry`, used by the tailnet and Wi-Fi saves; read then write, so a start overlapping a stop can still lose its entry, and then exits by the same check), so a stopping Inbox never rewrites its successor's entry and never makes a removed data folder again.
- The detached Inbox runs with `inbox/` as its working directory and `windowsHide`.
- The update control (`packages/server/inbox-updates.ts`; design record, not in this repo): health, the list model and the event stream's `status` carry `update: { available: true, state, version, current, action, releaseUrl, publishedAt? } | null` (`InboxUpdate` in `packages/core/inbox-types.ts`; `available` and `version` keep the older shape). `ready`: on the health tick (60 s, every 2 s while `update.lock` is held), a compiled Inbox stats the binary on disk and, only when the file's identity (device, inode, size, mtime) changed, runs it with `--version`; a different version is ready (the old restart-to-update signal). `updating`: `update.lock` is held. `failed`: `update-result.json` records a non-zero exit for an install the PERSON started (`pending.by: "person"`; a background auto-update failure stays out of the sidebar). `available`: a release build (X.Y.Z, so never `dev` or `0.0.0-dev`) runs the shared daily release check on start and on each tick (it answers from the 24h cache, so it asks GitHub at most once a day, 6 h after a failure, never while `PLANNOTATOR_UPDATE_CHECK` is off) and shows a newer stable release at once, before anything is downloaded (owner's answer 2), unless "Remind me tomorrow" snoozed that version (`update-state.json` `snooze: { version, until }`, 24 h, shared by every tab; a newer release clears it). `action`: `script` when the running binary is the install script's (`isManagedBinary`), else `copy`. The list model also carries `updated`: the version this run started on when it is newer than the one the Inbox ran before (`inboxVersion` in `update-state.json`), for the sidebar's quiet "What's new in X" link this run only. The daily check saves notes only for the `releases/latest` it fetched, so a version installed outside the Inbox (the install script run by hand) before a check saw it has none: `fetchReleaseNotesFor` (`packages/shared/update-check.ts`) then asks for that release by its tag (`releases/tags/vX`, `releaseTagApiUrl`, the same client rules: the `plannotator-update-check` user agent, nothing while `PLANNOTATOR_UPDATE_CHECK` is off, claimed in `update-state.json` `notesFetch[<version>]` before the request, then 6 h after a failure and 24 h after an answer with no "What's New" part, never a loop) and saves `update-notes/<version>.json`. A stored file with an empty "What's New" part (saved before the release body was edited) counts as missing and is fetched again under the same throttle. The Inbox runs it on its tick for `updated` and from `GET /api/inbox/whats-new`, only for a version it has reason to show (the one it runs, the newest known release, the binary on disk, an install in progress); the route waits up to 3 s (`WHATS_NEW_WAIT_MS`), then answers `503 { code: "notes_loading" }` with `Retry-After: 1` and the page asks again (up to 15 times). `updated` is null while its notes are neither saved nor fetchable (checks off, or a fetch in its back-off), so no link points at a page with nothing on it; the event stream's `status` carries `updated` too, so the link appears or goes once the fetch settles. Update now is `POST /api/inbox/update` (`startManualUpdate`: the same wrapper, lock, log, pinned tag and remembered flags as auto-update, without its 24 h window or its open-sessions gate; a second press while it runs is `409 update_locked`); the page that pressed it restarts the Inbox itself once `ready` arrives. A tailnet page reaches none of the update routes.
- Plain `uninstall` and `--purge` both remove the `plannotator-inbox` MCP entries the connect step added (see "Connecting the agents on this computer"; `removeInboxAgentConnections` in `packages/server/uninstall.ts`): with the binary gone, an entry would fail to start at every agent launch. A plain uninstall then forgets those records, so a reinstall connects them again.
- `uninstall --purge` stops a running Inbox first (its token-guarded stop route, then SIGTERM only while the port still answers with that `serverSession` and pid) and removes `inbox/` (`inbox` is in `PURGE_OWNED_TOP_LEVEL`, `packages/server/uninstall.ts`). An Inbox that is still running after that blocks the data purge: uninstall says to quit it and run `uninstall --purge` again. It also takes down a tailnet mapping a crashed Inbox left (`takeDownInboxTailnet`, only when `inbox.json` has `tailnet`; `takeDownInboxTailscale` for the window's, only when `tailscale` keeps its ports). `--dry-run` lists the stop and the take-down. A plain uninstall keeps the data.

**Store** (`packages/shared/inbox/`, one writer: the server process).
- Layout under `inbox/`:
  - `projects/<key>/` holds `project.json`, `messages.jsonl`, `questions.jsonl`, `decisions.jsonl` and `annotations.jsonl`. `<key>` is the project name plus 6 hex of the root's hash. A key that collides takes more of the hash.
  - `blobs/<sha256>` holds sent attachment versions and guided-review snapshots.
  - `seq.json` holds the highest seq across deletions.
  - The Pi and OpenCode connections keep `claims/<reply id>/` (delivery claims), `connection-tools.json` (the last tool list) and `leases/<host>-<session>.json` (which process of a session delivers).
  - The Claude Code mod keeps its claims and lease under `claude-code-mod/<session>/inbox/`.
- A project is the repository (the git toplevel of the path an agent names) or the folder.
- A project's `name` on every read (rows, threads, the project list, Storage, the event stream, the MCP tools, a push) is the real name of its folder, read from its stored `root` (`inboxProjectLabels`, `packages/shared/inbox/project-name.ts`); when two folders share a name each also names its parent ("api · work"). The stored `name` and the folder `key` stay the `sanitizeTag` slug, which also names plan history and the feedback archive, so nothing on disk is rewritten.
- Every line is a full snapshot `{ v, seq, at, kind, id, record }`. The last line per id is current. Nothing is rewritten in place, and fields are only added.
- `seq` is one counter across the Inbox. The union of lines by seq is the event log that the window's stream and `wait_for_reply`'s cursor read.
- A torn last line is skipped on read, and a newline is appended before the next write to that file.
- No storage caps.
- Records are snake_case with `msg_`, `prj_`, `ses_`, `att_` and `dec_` ULIDs.
- Questions:
  - A question record keeps Workspaces' `Question` wire fields beside Plannotator's `QuestionAnswer` v1 (`packages/core/inbox-types.ts`).
  - State (`open | picked | sent | closed | superseded`) is derived, never stored. `superseded` (the question record's additive `superseded_by: { message_id, key | null }`) wins over `closed`; see "Replaced questions".
  - `Stopped:` and `Holds up:` lines are read as Workspaces reads them (`packages/core/inbox-questions.ts`, over core's `findQuestionBlocks` and `parseQuestionBlock`, so keys equal the card's), with one guard Workspaces' parser is to add as well: a `Stopped:` value or `Holds up:` entry that is only a negative word (no, none, n/a, na, nothing, false, nil, null, a dash; any case, trailing punctuation allowed) is no stop and holds nothing up (`isNegativeWaitValue`). Anything else still stops, an empty `Stopped:` and `No; I need the DB password first` included. Records keep the value read at send time.
- Idempotency:
  - An agent's send is idempotent on its `idempotency_key`. The key is checked before routing. Another body, `reply_to` or thread name under the same key is `409 idempotency_key_reused`.
  - A person's Send is idempotent on its own key.

**Threads and the project filter** (the row model, owner ruling 2026-10-07). A row is a thread. The project is a label on the row and a filter (the sidebar's folders), never the row. `send_message` routes in `InboxStore.sendMessage`, and the first match wins:
1. `reply_to`: that message's thread, as a reply.
2. `thread`, a name:
   - Validation: trimmed, 1 to 120 characters, with no control characters, line breaks or bidi controls, and something visible. Anything else is `validation_error: thread: …`.
   - It joins the newest OPEN thread of that name in the project, across sessions. With none open, it starts a new thread under the name.
   - Names compare by `inboxThreadNameKey` (NFKC, default-ignorable code points dropped, whitespace runs as one space, case folded), so look-alike spellings are one thread. The stored name keeps the first sender's spelling.
3. Otherwise, the sender session's default thread: the newest UNNAMED thread that `agent_session` started in the project while it is open, else a new thread. A sender with no `agent_session` starts a thread with each message.

More rules:
- Resolved means done: the next message starts a new thread. A resolved thread still takes `reply_to` replies.
- A thread keeps its first message's subject, except that a subject derived from a question (the agent gave none) follows that question's replacement, down the `superseded_by` chain (`InboxStore.threadSubject`; the root's additive `subject_question` names the question, and a root older than it counts as derived when its subject is its first question's prompt). An agent-given subject never changes, and a question withdrawn with nothing in its place keeps the subject it gave.
- Routing reads only the log: two indexes (`sessionThreads`, `namedThreads`) are rebuilt from each root's first line in seq order. A replay therefore routes exactly as the live store did, and an older store with no `thread_name` replays unchanged.
- Routing is synchronous inside the server process, so racing sends land in one thread.
- `read_thread`'s list mode lists the threads the session sent in (`asked_by: "me"`), and `wait_for_reply` with no id waits on those threads.
- Without a cursor, a reply counts when it comes after the caller's last message in the thread.

**The list** (`packages/shared/inbox/list.ts`, pure; labels in `INBOX_SECTIONS`, `packages/core/inbox-types.ts`). The sections, in order: Stopped on you, Holding up work, Waiting on you, New since you looked, Sent, Quiet. Sent sits below New because it waits on the agent, not on the person (owner ruling 2026-10-11). The strongest reason wins:
1. Archived (resolved) and not come back: Quiet. The window leaves archived threads out of the list altogether (see "Archived" below); the list model places them in Quiet only for callers that do not ask for them apart. A thread that came back (an agent wrote after the archive and something there still waits, `back_from_archive`) is placed by the rules below like an open thread.
2. Marked read (Mark read) and no message since but its set-aside note: Quiet.
3. An open question with `Stopped:`: Stopped on you.
4. One with `Holds up:`: Holding up work.
5. Any other open question: Waiting on you.
6. Picks saved but not sent: New since you looked ("Answered, not sent").
7. The person's reply is the last message and no agent has read it: Sent. The Inbox's own notes (the set-aside and reopened notes below) are read past here and everywhere the list derives from the person's messages: they are neither a reply nor a look (`isInboxNote`).
8. Agent messages after the person's last look: New since you looked.
9. Anything else: Quiet.

Sorting and the rest:
- Every section sorts newest first by the thread's latest message (`last_at`, the time the row shows); ties on the thread id (owner ruling 2026-10-08).
- `unread` (bold) means Stopped, Holding, Waiting or New.
- "Looked" is `POST /api/inbox/threads/:id/seen`, sent when a thread opens (capped with `through_seq` at the newest agent message the window read, so one that lands before the server takes the look stays new) and again when a message that arrived while the thread was open has been seen on sight (see "Seen on sight"). The person's own reply also counts; the Inbox's notes do not.
- "The agent read it" is recorded when `wait_for_reply` returns the person's reply or `read_thread` reads the thread, which moves a Sent row to Quiet. Any agent's read counts.
- `?project=prj_…` keeps the sections and drops other projects' rows.
- The list is linear in the store: about 10 ms for 4,000 threads.

**The thread-state model**: `adr/implementation/inbox-thread-state.md` (sections, events, the transition table, invariants, the violations it found and their fixes), checked by `packages/shared/inbox/store.test.ts`, with trace fixtures for the phones in `packages/shared/inbox/fixtures/thread-state/v1/`.

**Archived** (owner ruling 2026-10-12: "Archived messages should move out of the Quiet list … only visible within a panel on the Settings page … the ability to unarchive them").
- **Came back** (mail apps' rule). An agent's `reply_to` reply into an archived thread lands after its archive line. Messages after that line behave as an open thread's; messages before it stay as the archive left them; the thread stays resolved (`resolved_at` kept) until the person acts, and nothing unarchives it implicitly (not even a Send: that would reopen the archive-closed questions and change the agent's default-thread routing).
  - The line: the store keeps, per root, the seq of the root line that set its current `resolved_at` (`resolvedSeq`, rebuilt in seq order by every replay and cleared by `reload`; a look or any other root rewrite with the same `resolved_at` does not move it). `closedByArchive(message)` = the thread is resolved and the message's first line is before that seq. Derived, never written.
  - One question state everywhere: `InboxStore.questionWire(record)` / `questionsOf` read a question as `closed` only when the archive closed its message. The window's thread, the event stream (`eventPayload`, so notifications and the question sound fire), the Decisions page and `decisions_waiting` (`inbox-decisions.ts`), and the relay push (`pushFor`, so the lock-screen answer is offered) all use it. Writes follow the same rule (`messageAnswerable`): picks, Send, the decision switch, and annotations on a message's attachments or guided review are taken for a message after the line and refused (`409 thread_resolved`) for one before it. New message stays refused on an archived thread (the window hides it). The agent side: `read_thread`'s list and `wait_for_reply` treat a thread with an agent message after the line (`agent_after_archive`) as open, so the person's answer reaches the waiting agent, and a seen-line rewrite no longer ends a wait as "resolved".
  - The row: `agent_after_archive` (an agent wrote after the line) and `back_from_archive` (that, and something still waits: an agent message after the line the person has not looked at, a live question open or picked, or the person's reply after the line the agent has not read). While `back_from_archive` the thread is in the list, placed as an open thread would be (New since you looked; Waiting, Holding or Stopped when it asks; Sent after the person replies) and out of the Archived block; once handled it returns to the archive by itself. Questions the archive closed stay closed, so a plain update comes back as New, not Waiting.
  - The window (`Thread.tsx`, from the thread read's additive `archive_seq`): cards, Reply and comments on files and guides are live for messages after the line; the foot carries "Archived · <agent> wrote after you archived it. Your reply goes to it; the thread stays archived." with **Unarchive** above the reply actions (`data-came-back`). Mark read works on what came back (`canToggleRead` / `offersRowMarkRead` accept `agent_after_archive` / `back_from_archive`): it sets aside the post-archive questions (the agent is told once, as for any Mark read), the thread goes back to the archive, the toast says "went back to Archived", and Undo brings it back.
  - Archiving again after the reply (Unarchive, then Archive) writes a new archive line after it: archived again. Unarchive drops a Mark read made while the thread was archived (`person_read_seq` after the archive line, cleared in the same root line, so a replay agrees): it covered only what came back and must not hold the reopened thread in Quiet over the questions the archive had closed. A Mark read made before the archive is kept.
  - The "person reply the agent has not read" that keeps a thread back ignores the Inbox's own notes (Mark read's set-aside note and its Undo's reopened note), as `readAt` does, so Mark read on what came back leaves it in the archive.
- The window's list holds no archived (resolved) thread in any section, Quiet included. It asks `GET /api/inbox/threads?archived=exclude`, which drops them from the sections. Without the parameter (`archived=include`, the default) the list model is unchanged: archived threads stay in Quiet. That default is for the phone: the door forwards `GET threads` to this route as it is, and an iPhone app that draws the sections natively keeps every thread it had, with no new release needed; an older window keeps working too. The sidebar's folder counts never counted archived threads (they count rows waiting on the person) and are the same either way.
- `GET /api/inbox/threads/archived` (`?project=`, `?offset=`, `?limit=` 1 to 200, default 50, `INBOX_ARCHIVED_PAGE`) lists them newest archived first (`resolved_at`, ties on the thread id; `inboxArchivedRows` in `list.ts`), with `total` in the filtered scope and `projects: [{ id, name, archived }]` (every project with archived threads). The door has an explicit allowlist row for it (`GET threads/archived`, read only, before `threads/:id`), so a phone can read it too.
- Settings' **Archived** block (`packages/inbox/components/Archived.tsx`, above "Stored on this machine"): "N archived threads", then one Settings row per archived thread (the agent's mark, the thread chip, the subject; then the agent, "Archived <day>", the message count) with **Unarchive**. When more than one project has archived threads the rows sit under a small header per project with its count ("billing · 2"), the projects in the order of their newest archived thread; there is no dropdown (the owner asked for no native select). 50 rows across the whole list, then "Showing 50 of N" and "Show 50 more"; "Nothing archived." when empty. It reads again whenever the store's cursor moves. Unarchive is the thread's resolve `false`; the window then opens the thread in the main list (`#thread=`, in whatever section its state puts it) with the toast "Back in your Inbox · “subject”" and Undo (archive again).
- Archiving from a thread keeps its toast and Undo. While that thread stays open its row keeps its place in the list, shown archived ("Archived", not bold: `markHeldRowArchived` in `held.ts`), and leaves the list when the person leaves the thread (the held-order rule). A deep link `#thread=` to an archived thread still opens it, with "Archived … · Unarchive" in its foot; its row, which the list no longer carries, comes from the thread read's additive `row`.

**Mark read and the Send that skips** (design record "inbox-mark-read", not in this repo; approved 2026-10-11, with the owner's later rulings that Mark read closes the questions it leaves and that Sent sits below New). Two ways to get a thread out of the top without answering every question.
- **A Send that answers skips what it leaves unanswered.** The reply box (and the foot while picks or annotations wait) shows the chip "↷ N unanswered questions will be skipped · Keep open"; Keep open turns it into "N unanswered questions stay open · Skip them" for that one Send. Its default follows the Send (approval "inbox-words-only-reply", 2026-10-13, amending this rule): skip once at least one question is answered in it (a saved pick not yet sent, or one being saved), Keep open while it carries no pick (words, annotations, or both), because a person who only writes back ("received, I'll answer later") has not decided to skip anything. A click on the chip wins either way until the Send goes or the thread changes (`SkipChoice` `auto | skip | keep`, with `skipsUnanswered` and `sendAnswersAny`, in `packages/inbox/components/Thread.tsx`; Send reads the choice again once the picks are saved, so a pick still being saved when Send was pressed counts). What the agent gets for a reply with no answers is under "Questions and Send". The window sends `skip_unanswered: true` (false with Keep open) on each reply, and targets every agent message with picks or (skipping) open questions, then the latest agent message last when another session wrote it (`sendTargetsOf`), so the person's words always go to the agent that wrote most recently, never to an older asker; each skip is written on the reply to its own message. When the session of the last pick or skip also wrote the latest agent message, the words and annotations ride that last pick or skip instead, so one Send is one reply (one wake turn) to that session. The ended-session choice and `to` follow that last target's session (`askingSessionOf`). A skip-only target whose questions closed meanwhile answers `{ reply: null, nothing_to_send: true }`, a no-op, so the rest of the Send still goes. The store (`sendReply`) writes each open question without a pick as a sent skip, `answer: { skipped: true, by_reply: true }` (`inboxSkipAnswer`; `by_reply` is additive on `QuestionAnswer`, kept by `parseQuestionAnswer` only beside `skipped`). A Stopped question a Send skipped no longer blocks: the agent has its answer.
- **Mark read** (`POST /api/inbox/threads/:id/read`; Undo `…/unread`). Offered where something waits on the person (Stopped, Holding, Waiting, or New with news or picks; `canToggleRead`, `packages/inbox/markRead.ts`) and never on an archived thread (`409 thread_resolved`). The store (`markRead`) writes the root with `person_read_seq` (the seq of that line) and `person_read_at`, counts it as a look, and closes every question still waiting on the person (open, or picked and not sent): each gets a skip answer and `set_aside: { at, read_seq, previous }` (`InboxQuestionRecord`, additive; `read_seq` is that Mark read's `person_read_seq`), so it reads `state: "closed"` with `set_aside_at` on the wire, records no decision, and refuses a pick (`409 question_set_aside`). The row is Quiet ("Read") while no message but its set-aside note came after the Mark read (`readAt`, derived: an agent's next message, or the person's own reply, ends it with no write; the closed questions stay closed). Undo reopens only the questions that Mark read closed (owner ruling 2026-10-12), exactly as they were, a saved pick included (revision + 1), and clears the root's fields; a question an earlier Mark read closed (and told the agent about) stays closed, so Mark read again then Undo no longer reopens it. A record older than `read_seq` is matched by `set_aside.at` = the root's `person_read_at`. With no Mark read on the root (after an Undo, or an Unarchive that dropped it) Undo writes nothing. On a thread that came back from the archive, a Mark read made after the agent's latest message sends it back to Archived at once, even while the person's earlier reply there waits on the agent (`back_from_archive` reads past that reply while the Mark read stands); a reply the person sends after it brings the thread back as Sent.
- **The agent is told once.** After the Undo window (`INBOX_SET_ASIDE_DELAY_MS`, 10 s: the 7 s toast with 3 s to spare; the server option `setAsideDelayMs`), while the questions are still closed, the server writes one person note per asking message (`tellSetAside`): a reply to that message, `set_aside: [<question ids>]` on it, body "Set aside for now; don't wait on these:" (`INBOX_SET_ASIDE_HEADING`) and the questions as `- Q<n>. <prompt>` (`composeInboxSetAsideBody`). It reaches the agent like any reply (the wake, `wait_for_reply`, `read_thread`), never pushes to a phone (`pushFor` pushes agent messages only), and never ends the read. It is not the person's reply and not a look: the row's `sent`, `unseen`, `waiting_on_person` and "came back", the window's look boundary (`lookBoundary` in `packages/inbox/folding.ts`), its "Saved for / Delivered to" line and the held list's agent activity (the row's additive `last_agent_at`) all read past it, so news the agent wrote inside the Undo window stays New after the note goes. Each question is named once, across Mark reads; an Undo inside the window tells nothing. An Undo after the note went sends one more person note per asking message, for the questions that Undo reopened only, "The person reopened these:" (`INBOX_REOPENED_HEADING`, `composeInboxReopenedBody`, `reopened: [<question ids>]` on it), so the agent does not go on believing it need not wait; a later Mark read may then tell it again. A timer per Mark read, one on Unarchive (an archive holds the note back), and a sweep at start (`setAsideDue`) for a note a stop interrupted.

**Folding a thread** (design record, not in this repo; variant "Land"; `packages/inbox/folding.ts`, drawn by `components/Thread.tsx`).
- What is new: the agent messages after the person's last look or their own last reply, whichever is later (`lookBoundary`, the list's rule). The window reads it from the thread payload BEFORE it records the look: `GET /api/inbox/threads/:id` carries each message's `seq` (its first line's) and, on a person's reply, `sent_annotations` (`InboxStore.windowThread`; additive, absent from an older Inbox, not on the MCP tools). `App.tsx` keeps the boundary per open thread (`look`, from the first read of that thread) and passes it to `ThreadPane` as `lookSeq`, so the "New" marks last until the person leaves the thread. A reply the person sends during the visit is a look too: the pane's effective boundary is the later of `lookSeq` and the highest seq of any person message in the thread now, so what the reply answers stops being new at once (the fold plan is not re-decided). A guided review opens as an overlay (`GuidePane`), so the pane and its fold state stay mounted under it. A payload without seqs folds nothing and marks nothing new.
- When the thread opens, a message is open if it is new, holds a pick not sent, or is the last one (and the last real one, when the Inbox's set-aside or reopened notes trail it: it carries the reply's "Saved for / Delivered to" line, which never sits under a note); every other message, the person's own included, folds to one line (`planFolds`). A message that arrives while the thread is open shows open, new, at the bottom. The fold state is in memory per open thread; nothing is saved.
- A folded line: the sender's mark and name, a snippet, what the message holds (`holdingsOf`: "2 answered" / "1 open question" / "1 pick, not sent", a paperclip with the file count, a guided review, the annotations a reply sent, "Delivered" on a reply the agent read or a connection delivered), and the time. The snippet (`foldSnippet`) of an agent message is the person's answers (`<prompt> → <answer>`) when every live question in it was sent, the prompt plain and cut at a word near 40 characters (`SNIPPET_PROMPT_MAX`) so the answer stays on the line, the whole prompt in the line's `title` and label; else its first words (`firstWords`: question blocks, fences, tables and images out; `cleanInline` drops only paired emphasis marks at word boundaries, so `snake_case` survives, and keeps inline code's text); a message that is only a question block shows its first live question's prompt. A person's reply shows its own words (`replyWords`: without the store's first line ("Answered N questions." and its skip forms) and everything from the "Answers to your questions" heading on); with none, the answers it sent.
- A run of 4 or more folded messages keeps its first and last two; the rest hide behind "N earlier messages" (decided once when the thread opens, so opening a message never makes others appear or disappear).
- The thread opens scrolled to the "New since you looked" divider with the last read line above it; with nothing new (or when the first message is the first new one) it opens at the top. A meta line under the subject says `N messages · <span> · N new since you looked`. The subject moves into the header once it scrolls away, and "↓ N new" floats above the reply foot while new messages the person has not seen are below the view: it counts, and a click goes to the first of, the arrivals below the view not yet seen on sight (`data-arrival`); only when none waits there, the messages that were new when the thread opened and are below the view (`newBelow` in `components/Thread.tsx`; before 2026-10-12 it printed every message new this visit, wherever it was, and went to the first new one below, often an older one). The header subject, the pill and the keep-in-place correction are measured only when the fold, the thread or the file beside it changes, never on a keystroke in the reply box; a `ResizeObserver` on the thread's scroll box re-measures the subject and the pill when the foot grows (the reply box, the stale guard, the New-message composer).
- Opening or folding keeps the message acted on in place and keeps focus on it; "Expand all" / "Fold all" in the header keeps the first message in view in place. Keys in the thread pane (never while typing, never in a dialog or the open file): `j` / `k` between messages and the fold, `n` to the first new one; each line and open header is a button with `aria-expanded`. A jump to a card in a folded message (a replaced question's link, the stale guard) opens the message first.
- A one-message thread looks as before: no fold button, no "New", no meta line, no "Expand all". The phone apps draw their own threads; the surface is unchanged.

**Seen on sight: a new message in the thread you have open** (design record "inbox-new-in-open-thread", variant A, approved 2026-10-12; not in this repo; `packages/inbox/seenOnSight.ts`, wired in `components/Thread.tsx` and `App.tsx`).
- An agent message that arrives while its thread is open (its seq is past what this visit's looks covered, and past the person's own last reply) counts as seen once its first lines (the sender row and 96 px of the body, or the whole message when shorter; `firstLines`) have been wholly inside the thread's view, above the pill's 56 px band while the pill shows, for 1 s without a break (`SEEN_DWELL_MS`), while the tab is visible and the window has focus (`pageInFront`) and nothing covers the thread: a file over it (full screen, a phone, a stacked window; a file beside the thread does not cover it), an open `<dialog>` (the update and sound dialogs), or a guided review (`covered` from `App.tsx`). - At the end of the thread (within 24 px of the bottom, `AT_END_PX`, measured on scroll before the arrival renders) the view scrolls down just far enough to show the arrival's first lines (`followBy`, never upward; smooth, instant under reduced motion); anywhere else nothing moves and the pill counts it. **Replaced questions** (design record, not in this repo; direction A "Quiet"; model agreed with Workspaces).
- An agent supersedes an earlier question of the SAME thread: `supersedes: ["<message id>"]` (every open question of that message) or `["<message id>/<key>"]` on `send_message` (and `submit_guide`, through `SEND_ROUTING_FIELDS`), or a `Replaces: <message id>/<key>` line in a newer block. Core's parser reads that line (`ParsedQuestion.replaces`) only when EVERY token of its value is id-shaped (`msg_` + a 26-character ULID, optionally `/q-` + 8 hex, or a bare `q-` + 8 hex key; one trailing `.` per token dropped), wherever it sits: it is then never the prompt and never context, and it does not change the key. Any other `Replaces:` line is prose (`Replaces: q-learning with PPO`, `Replaces: msg_ queue drain`), so plan review never hides a sentence.
- What replaces it (`superseded_by.key`): the block whose `Replaces:` line named it; through the argument, the new message's only question when it asks exactly one, else null. Null reads "No longer applies"; a key reads "Replaced". Both are `state: "superseded"` on the wire.
- Checked before anything is written (`InboxStore.planSupersede`): every id must name an agent message of the thread the new message lands in (`reply_to`'s, or the routed one) and a question there that is open or picked (not sent, not already superseded, not closed). Two blocks naming the same old question with `Replaces:` is refused too ("named by two questions"). Otherwise the whole send is refused with `invalid_supersedes: …` naming each bad id and listing the thread's open questions (`<message id>/<key> (<prompt>)`, also as `open_questions` in the error's details); a message that would start a new thread can supersede nothing. The message records the argument as given (`InboxMessage.supersedes`, additive), so an idempotent retry with another list is `idempotency_key_reused`. The send's result lists `superseded`.
- Append-only: the message and its questions first, then one more line per superseded question with `superseded_by` (and `decision_draft: null` when it had one). Old stores replay unchanged; routing determinism holds (the generated op model in `store.test.ts` includes supersedes).
- Picks and Send: answering a superseded question (`POST …/picks` or `…/reply` naming its key) and the decision switch are refused `422 question_superseded` (with `superseded_by`). A pick saved on it stays on the record, shown on the card as "Your pick: … Not sent", and is never sent: it is not `picked`, so it never counts as "Answered, not sent", never brings back the "Not sent · Send" foot and never adds to "N picks". A reply's "Answers to your questions" section leaves superseded questions out (neither answered nor "Unanswered"); the others keep their numbers. No decision is recorded from it.
- The list: it leaves Stopped / Holding / Waiting (only open questions count). Replaced by a stopped question, the row stays in Stopped on the new one; withdrawn with nothing open, the superseding agent message makes it "New since you looked" (behind the held "N new", like any agent activity), then Quiet once opened. A supersede raises no browser notification by itself (a new question in the same message does, as any question). The phone push does go for any message that superseded a question, even one that asks nothing new (`question: null`, so no lock-screen answers): pushes collapse per thread, so it replaces the older notification and its answer actions; the push's question is only ever an open one (`pushFor`, `packages/server/inbox-relay-push.test.ts`). **New message** (`packages/server/inbox-sessions.ts`, `packages/inbox/components/NewMessage.tsx`; record 5.1 to 5.3; owner Q4: "just another button next to reply", built as a try, not a chat product).
- The thread's New message button writes the person's words to one LIVE agent session of the thread's project, through the same wake path as a reply.
- A New message belongs only to the session it names. The store keeps it as a person message with `reply_to: null` and `to: { host, session }` (`InboxAddressee`), and `InboxStore.isFor` hands it to that session only:
  - `pendingReplies` gives it to that session's poll (command `type: "message"`), and `recordDelivery` refuses any other session.
  - Another session's `wait_for_reply` never returns it (`forCaller` in `inbox-mcp.ts`).
  - Another agent reading the thread through `read_thread` sees its text but does not settle it. It is settled only by its delivery: the named session's wake, or that session's own `wait_for_reply`, which records the delivery.
- Live sessions are kept in memory only. Every bridge poll can carry `project_path`, `started_at`, `busy` and `idle_since`, and `POST /api/inbox/bridge/event` `{ type: "state", busy }` says when a turn starts or ends.
  - A session is live while it polled within `INBOX_SESSION_LIVE_MS` (30 s, `connection.ts`) or holds a poll now.
  - It is in a project when its `project_path` resolves to the project's root (realpath, then the repository root, cached per path). A connection that sends no `project_path` is in a project when it wrote there.
  - The Claude Code mod sends all four. The Pi and OpenCode polls send none of them, so their sessions count in a project they wrote in.
- Routes: `GET /api/inbox/threads/:id/sessions` and `POST /api/inbox/threads/:id/message` (see "Inbox Server"). A session that is no longer live is `409 session_not_live` and nothing is written. A replayed key answers the message it wrote.
- The wake is `inboxWakeText` with `INBOX_MESSAGE_INSTRUCTION` as its second line: the person wrote to you; answer with `reply_to` the id in the first line. Its subject is the thread's, and there is no MCP tool for it.
- The window:
  - The button reads the live sessions when the thread opens, every 10 s, and on press.
  - None: the button greys but stays pressable and opens "<agent> is not running in <project>" with Reply instead (5.3).
  - One: the box opens addressed to it, "New message to <host> in <project> (live session, idle|working)" (5.1).
  - Several: one row each, with when it started and whether it wrote this thread, is idle or is working (5.2).
  - The thread shows the message "to <host>", then "<host> takes it as its next turn." until delivered, then "Delivered to <host>, <time>".

**Replying when the asking session has ended** (`packages/inbox/components/ReplyRoute.tsx`, `packages/server/inbox-sessions.ts`; design record "replying when the asking agent's session has ended", not in this repo; owner approval 2026-10-11, "build it as mocked"). A reply wakes only the session that asked. When that session is gone, the window says so before the person replies, and at Send the person picks where the reply goes. The choice is always manual; nothing routes on its own.
- The asking session is the session of the message a Send's words answer (the last message with picks waiting, else the last agent message). It is said to have ended only on evidence that it wakes: its message came through a connection that wakes its session (the `INBOX_WAKES_META_KEY` meta on `send_message` / `submit_guide`, `callerWakes`, recorded on the message as `wakes: true`: the Claude Code mod, Pi, OpenCode 2). A message without it (an MCP-only agent, OpenCode 1, the mod off, Windows, an older connection) is never "ended", whatever host it names, because such an agent may be blocked in `wait_for_reply` right now. For a `wakes` message the window asks `GET /api/inbox/threads/:id/sessions?asker=<session>`, which adds `asker: { session, live }`. `live` has a grace (`INBOX_ASKER_GRACE_MS`, 60 s) and counts every sign of the session: it holds a bridge poll or an open MCP `wait_for_reply` (`holdOverMcp`), or it polled or called any MCP tool naming that `agent_session` within 60 s (`seenOverMcp`, read from each `/mcp` POST), or the Inbox itself started less than 60 s ago (all of this is kept in memory only). MCP presence never makes a session live for New message. An older Inbox without `asker` reads as live.
- Ended, before replying: the asking message's sender row reads `to you · session ended`, and the foot carries a note (`role="status"`, the reply box's `aria-describedby`): "The <agent> session that asked has ended. When you send, you can pick a live session in <project> to take your reply." With no other live session: "…has ended, and no agent is running in <project> now. Your reply will wait here until an agent reads this thread." The note is for before replying: once the person's reply is the last message (and nothing waits), its own line says where it went.
- The note lives in one always-mounted `role="status"` region at the top of the foot (`data-asker-note`), whose text changes, so a screen reader announces it.
- At Send, with another live session: Send sends nothing and the actions row is replaced in place by one radio group ("Where should this reply go?"): the project's live sessions in New message's order and rows (the asking session, if it comes back, on top as "the session that asked", selected), then "Leave it for the next agent". Five rows, then "Show N more". The primary button names the result ("Send to <host>" or "Leave it for the next agent"). A selected row past the first five shows in its place, and stays there when "Show N more" opens the rest. A session that leaves the live list while the choice is open greys ("Ended just now.") and cannot be picked.
- Nothing live: Send sends at once (there is one outcome), and the line under the reply reads "Saved for <agent>. The session that asked has ended, so it waits here until an agent reads this thread."
- The server: `POST /api/inbox/messages/:id/reply` takes an optional `to: { host?, session }`. The route checks it against the thread project's live sessions exactly as New message does (`replyTarget`; a host that does not match counts as not live). Not live is `409 session_not_live` and nothing is written (questions stay unsent); a replayed idempotency key answers the reply it wrote. The message's own refusals come first (unknown message 404, resolved thread `thread_resolved`). A Send that answers several messages posts one reply each and puts `to` only on the ended asker's messages; an answer to another session's message still goes to that session. When a later post is refused after an earlier one went, the error says how many went ("Your answers to 1 of 2 messages were sent; the rest was not."), never "Nothing was sent". The reply is stored with `reply_to` AND `to`, so `InboxStore.isFor`, `pendingReplies`, `recordDelivery` and `wait_for_reply`'s `forCaller` treat it like a New message: only that session is handed it, the asking session (back with the same id) never is, and another agent's read does not settle it.
- The wake: the bridge command stays `type: "reply"` and adds `redirected_from`, the asking agent named from its HOST (`Claude Code`; `agent` without one), never from the name the agent gave itself, since the line enters another session's prompt; `inboxWakeText` strips control characters and caps it at `INBOX_REDIRECTED_NAME_MAX` (40). `inboxWakeText` then puts one line under `INBOX_WAKE_INSTRUCTION` (`inboxRedirectedLine`): "This reply was written to another <agent> session that has ended. Read the thread with read_thread to see what it asked, then answer with reply_to <id>." It lives in the connection contract, so the mod's copy (`inbox-contract.ts`), Pi and OpenCode (`agent-link.ts`) all word it the same.
- After delivery: the person's message reads "to <host> (another session)" and its line "Delivered to <host> (another session), <time>". "(another session)" is added only when the host is the asker's own host; otherwise the host alone ("Delivered to Pi, …"). Before delivery: "<host> (another session) takes it as its next turn."

- `send_message` takes `attachments: [path]`: absolute (anywhere the agent's user can read) or relative to `project_path`.
- At send time, `recordInboxAttachments` (`packages/shared/inbox/attachments.ts`) resolves each path to its realpath and checks every file before committing anything, with no size bound. It refuses only:

- Bytes are streamed with async reads (1 MiB chunks, one `O_NOFOLLOW|O_NONBLOCK` handle checked against the stat by dev/ino, so a 3 GB send blocks no other route) through the sha256 into a temp blob, renamed to `inbox/blobs/<sha256>` (the sent version) once every file read, so a file of any size never sits in memory. - The kind (`decideInboxAttachmentKind`): Plannotator's documents keep their viewer by extension while their bytes are text (markdown, text, html, mermaid, graphviz; a document whose bytes are not text is `file`); everything else is read from the bytes: `image` by `sniffImageContentType` (PNG/APNG, JPEG, GIF, WebP, AVIF, BMP, ICO by magic bytes, SVG by its first element; the extension is ignored, so an HTML page named `.svg` is not an image, and an LFS pointer never is), `pdf` by `%PDF-` in the first 1024 bytes, `code` for any other UTF-8 text with no NUL (`.mjs`, `Makefile`, an unknown extension), and `file` for the rest (zip, video, binaries). A text or code file over `INBOX_VIEW_MAX_BYTES` (16 MB, the most the window reads whole) is a `file`, a download; that bounds memory, it is not an attach cap. **Search** (design record "inbox-search", not in this repo; owner approval 2026-10-13, "Approve it as mocked, with your recommendations"). The person searches everything the Inbox holds; agents keep `read_thread` and get no search tool. Server: `packages/shared/inbox/search.ts` (the index, pure over the store), `packages/server/inbox-search.ts` (the routes), the text rules both sides share in `@plannotator/core/inbox-search`.
- What is indexed, one document each: a thread (its current subject, following a replaced question's subject, and its thread name as title fields; its project's name); an agent message (its body as text: question blocks, images and link targets dropped, code kept; each question's prompt, context, choice labels and the person's answer; the agent's name); the person's own reply words (`inboxSearchReplyText`: not the "Answered N questions." line, not the answers section); an attachment's name and the last two path segments; a guided review's title; a decision's text and reason; a project's name and root. Not indexed: attachment contents, guide section text, annotation text, image alt text, the Inbox's own set-aside and reopened notes.
- Text rules (`@plannotator/core/inbox-search`, browser-safe, so the window highlights with the same ones): NFKC, default-ignorable code points dropped, case folded, Latin/Greek/Cyrillic accents dropped (U+0300 to U+036F; Japanese voicing marks stay), for matching only. Tokens: maximal letter and digit runs (an ASCII chunk by a char-code scan; any other chunk as word runs of letters, digits and marks, through `Intl.Segmenter` only when it holds a script written without spaces: Han, Hiragana, Katakana, Hangul, Thai, Lao, Khmer, Myanmar). A token under 2 characters is dropped unless CJK. A query is at most 200 characters and 8 terms; every term must match, the last as a prefix. Snippets cut about 40 characters before the first match at a word start, on grapheme boundaries, with an unbroken run over 48 characters (a URL) shortened unless it holds a match; CJK, Arabic and Hebrew runs are never shortened; a long source is windowed first. Marks are `[start, length]` in UTF-16.
- Ranking inside a group: the match tier (the terms as a phrase, then every term as a whole word, then the last as a prefix; inside a tier, every term in the title fields first), then open before archived, then the project open in the list (`current`, ties only, never a filter), then newest. Groups and first-answer caps: Threads 5, Messages 8, Files 5 (attachments and guided reviews), Decisions 5, Projects 3; `group=` with `offset=` and `limit` (at most 50) is "Show all". A thread is listed under Threads only when its own title fields (or project name) match; a message is listed once, with the snippet from the field that holds every term (the body, else a question: then `question: { key, replaced }`, the "Question" chip). Archived means resolved and not come back (`inboxRowArchived`); archived rows say so. A decision is archived when replaced or retired, whatever its thread, in its label and its rank alike.
- Filters (`project`, `status`, `from`) apply on the server and the totals follow. `status=waiting` is Stopped, Holding and Waiting; `new`, `sent`, `quiet` are those sections of open threads; `archived` the archived. A decision follows its source thread's section; one recorded from no thread (an agent's `record_decision`) is left out by any status. Any status or From hides Projects. `from=me` keeps the person's replies and the decisions recorded from their answers (Files are agents', so hidden); a thread counts for a side that wrote in it. Filters with no words list the matching threads, newest first (20). An empty query with no filters answers `recent` (the 6 threads with the highest `person_seen_seq`: no new storage) and `recent_searches`.
- The index: an inverted index over numbered documents; each document's token ids as varints (0 separates fields, so a phrase never spans two; one pass finds a phrase with a bit run, no look-ahead). The vocabulary and postings (`packages/shared/inbox/search-vocabulary.ts`) are sized for text full of one-off tokens, since a distinct word costs memory however rarely it occurs: word text in one byte pool (ASCII words; others as strings), an FNV-1a open-addressing table that reads ASCII tokens straight from the text and grows incrementally (the old table stays readable while each new word moves 8 of its slots, so no insert pays for a million words), one Int32 of postings per id (a single document inline, more as delta varints in blocks of one shared arena), the last term's prefix through lists keyed by a word's first two characters, and the arrays trimmed when the build ends. About 40 bytes per distinct word. **Identifier-like tokens are not words** (`isIdLikeToken`): 8+ hex characters with digits and letters (commit hashes, UUID parts), more than 8 digits (timestamps), or 16+ letters and digits with 3+ digits switching between letters and digits 3+ times (ULIDs, base32 and base64 ids). Each is posted once under one of 65,536 shared bucket ids, made as first used: an id with a letter by the hash of its first 7 characters, a number by the hash of its whole value (timestamps share their first digits). Beside the bucket id, the document's token stream keeps the id's tail: a number's remaining 16 hash bits, or an id's first 12 characters (whole when it is no longer, else with 21 bits of its whole hash). A query confirms an id from those bytes, so an id query costs about what a word query does however many ids the store holds: an id of up to 12 characters is compared whole, and the text is read only for a number or a longer id whose kept bits all match, to confirm the exact token (`textHasToken`; rare unless the id is there, since a different id must share 32 hash bits, or 12 characters and 21 hash bits). An id with a letter is also found by any start of 7 characters or more (git's short SHA: `9fceb02` and `9fceb02d0ae5` find `9fceb02d0ae598e9…`), compared with the 12 characters kept; a start longer than 12 that is not the whole id is confirmed by reading the text of only the documents whose ids start with those 12 (`textHasPrefix`). Numbers are found by their whole value only, and nothing shorter than 7 characters finds an id. A row is drawn from at most about 8 KB of a long message: the lines around the first token a term matches, case-insensitive (the last term as a token's start, so `re` centres on `retry`, not `there`; `nearFirstHit`, for bodies over 64 KB; the whole body when a term is not plain ASCII). Built lazily on the first search (start stays as fast as before), in slices of 5 ms that yield (`setImmediate`) between messages, so health, the list, the event stream and the bridge keep answering. `store.subscribe` marks what a line touches (a message, its thread's document and facts, a decision, a project); a 50 ms timer, and every search, re-index it. A deletion re-reads the store (`store.reloadCount()` changes), and the next search rebuilds; a build that a deletion interrupts is void. Thread facts (section, archived, last time, who wrote) come from `store.listRow`, cached until a line touches the thread.
- `GET /api/inbox/search` while the index is still building waits up to 250 ms, then answers `indexing: true` with the thread count and no groups; the window asks again. `POST /api/inbox/search/recent` writes the last 6 recent searches to `inbox/recent-searches.json` (0600), only when the window opens a result (`{ q }`) or clears them (`{ clear: true }`).
- Access: the loopback window and the owner over the tailnet listener, like every read route (the listener's identity, Host and `Sec-Fetch-Site` checks first). Both routes refuse another site first (`403 cross_origin`, before anything is searched): `Sec-Fetch-Site: cross-site` or `same-site` (a page on another localhost port is the same site), and an Origin that does not name this server (`isSameOriginOrNoOrigin`), because a page that cannot read the answer could still pick the query and time it (a hit takes longer than a miss); the window's own page and a client without browser headers are answered. The recent-searches POST also takes the `serverSession` guard. Not on the phone's device door (its explicit allowlist; the iPhone app needs its own search design).
- Measured with `bun scripts/inbox-search-bench.ts` (4,000 threads, 30,000 messages, about 65 M characters, 40 projects, written straight into a scratch store, the client in the same process; Apple M-series laptop): first build about 1.1 to 1.4 s (target 1.5 s; 1.5 to 1.9 s with 1% to 15% of words one-off, on a machine at a load average of about 7), longest slice under 8 ms (at most one of about 250 past it), query server time p95 about 21 to 25 ms over a mix that includes queries of only common words (target 25 ms; `the an` alone is about 28 to 30 ms, because every document holding both words is read for the phrase; most queries take under 10 ms). Index memory (JSC live heap plus typed-array memory after full collections, the store loaded first) against the text it covers: 1.0x with no one-off tokens, 1.2x / 1.4x / 2.1x with 1% / 3% / 15% of words replaced by identifiers, paths and timestamps seen once (`--unique N`), 1.1x / 1.3x / 2.4x with random one-off words instead (`--unique N --unique-words`, 1.5 million distinct words at 15%, the case no identifier rule can tell from words). The memory grows with distinct words and ids, not text, so these mixes are the numbers to watch. Id-dense logs (40 MB of lines each holding a timestamp and a 12-character hash, as 200 messages of 0.2 MB or 20 of 2 MB): an id query, a short SHA, a number or an id in no document takes 1 to 5 ms (0.2 MB messages) or 7 to 14 ms (2 MB messages); one 2 MB message is tokenized in one slice of about 25 ms, since slices end between messages. `--keep DIR` keeps the seeded store, for a look in the window.
- The window (`packages/inbox/search/`): a field-shaped **Search** entry at the top of the sidebar, under the Tater mark and above Inbox (`.ib-sp-entry`, 32 px, `aria-haspopup="dialog"`, the ⌘K / Ctrl K hint at its end), and on a phone a search icon in the list header (`.ib-lhead-search`, shown only under `PHONE_QUERY`; decision D3; the desktop header has none, D2). **⌘K on macOS, Ctrl+K elsewhere, opens search**: the Inbox's one keyboard shortcut, an owner exception (approval amendment 2026-10-14) to the rule of no Inbox shortcuts until the centralized shortcut system exists, where ⌘K is its first binding. `search/searchShortcut.ts` defines it as a registry scope (`inboxSearchShortcuts`, `Mod+K`) and holds the window's one capture-phase keydown handler (`onOpenSearchKey`, installed by `App.tsx`): only the platform's own modifier counts (`isModKeyHeld`; on macOS Ctrl+K stays the text fields' delete-to-end-of-line), never with Shift or Alt or while an IME composes; it works from the reply box or any field (a chord eats no typing) and prevents the browser's own Ctrl+K; with the palette open it goes back to its input, the words selected; another modal dialog (`dialog[open]`, `aria-modal`) keeps the keys; keys inside an attached HTML page's frame never reach the window. The Search entry shows the keycaps from the registry's formatter (`⌘K` / `Ctrl K`, `aria-hidden`, hidden on a phone) and names the chord in `aria-keyshortcuts`. No other key opens search. The palette (`search/SearchPalette.tsx`) is lazy: `components/SearchHost.tsx` is its one `lazy(() => import('#search-palette'))`, mounted on the first open with no fallback and kept mounted after (`tests/entry-assets.test.ts` keeps every other import out). It is a native modal `<dialog role="dialog">` pinned at `top: max(16px, 12vh)`, `min(680px, 100vw - 32px)` wide, a full-screen sheet with **Cancel** on a phone (`data-phone`). The input is a `role="combobox"` (`aria-expanded`, `aria-autocomplete="list"`, `aria-controls`, `aria-activedescendant`) over one `role="listbox"` ("Search results") of `role="group"`s labelled by their headings; focus stays in the input (a mouse press on a row, a heading or Show all is `preventDefault`ed, and Show all puts focus back in the input, so the arrows go on). Filter chips **Project** (starting on the project open in the list, removable), **Status**, **From** open `role="menu"` lists of `menuitemradio`; a set chip is primary-tinted with a ×, and **Clear filters** appears. **Notifications** (`packages/inbox/notify.ts`; the open page first, no Web Push, no service worker).
- The page raises a browser `Notification` for each new question that the event stream brings in. News never notifies. Every notification carries one tag (`plannotator-inbox`) and `renotify: true` (`inboxNotificationOptions`), so a new one replaces the last and still alerts; without `renotify` Chrome replaces a notice still holding the tag silently.
- While the tab is away:
  - One thread: "<project>: <agent> stopped on you" or "is waiting on you", with the subject as the body. A click opens the thread.
  - A burst becomes one notice, "3 waiting in 2 projects". A click opens the list.
- Nothing is raised while the tab is visible and focused.
- The one-time ask (`components/NotificationAsk.tsx`) appears above the list when an item arrives and the browser has not decided. It never appears on first paint. "Not now" is remembered.
- After a port change it returns once as "The Inbox moved to a new address. Allow notifications again."
- State lives in config.json as `inboxNotifications` (`{ enabled, dismissed, allowedOrigin }`), through `GET` and `POST /api/inbox/settings`.
- While the question sound can ring (on, and armed by a click in this tab), every notification is raised with `silent: true`, so Windows and Linux do not chime a second time. Otherwise notifications are raised as before.

**The question sound** (`packages/inbox/sound.ts`; design record `.product/approved/inbox-sound/`, not in this repo). A soft two-tone doorbell ("Ding-dong", the owner's pick of twelve), synthesized live with Web Audio (`DING_DONG`, no audio files).
- When it rings: for the same items notifications use (a new question in an agent's message; never a plain message), and only while no Inbox tab is in front (`pageInFront`). It does not depend on notifications being on, allowed or blocked. `notify.ts` calls `onQuestions` after the list read, before any notification rule.
- Once per burst (`decideRing`, pure): the first question rings, a question within 30 s (`RING_BURST_MS`) of the last one stays silent and extends the burst, and a tab coming to the front ends it.
- Several tabs ring once: they share `BroadcastChannel('plannotator-inbox-sound')` (who is in front, repeated every 5 s and trusted for 15 s; who rang, which puts the others in that burst), and a tab rings only while it holds the Web Lock `plannotator-inbox-sound` (`ifAvailable`, held 3 s or until a tab comes to the front; a localStorage timestamp without Web Locks). Another port is another origin, so a tab left on an old port can ring once more.
- Chrome plays sound only after a user activation in the tab. The first pointer, click, touch or key event that the browser counts as one (`navigator.userActivation`; Escape or a modifier alone does not count, and the page keeps listening) makes and resumes the AudioContext ("armed"); before it a ring is skipped. Until then, with the sound on, Settings shows "Click once in this tab to allow sound." under the row and the sidebar shows "Click to turn on sound" above Settings.
- Settings: one row under the notifications switch, "Play a sound · when an agent asks you", the volume (10 to 100 in steps of 10, disabled while off; letting go plays it once at that level), Play (always plays, even in front) and the switch.
- The one-time dialog (`components/SoundIntro.tsx`, on the `Modal` shell of `components/Updates.tsx`): "The Inbox can ring now" with Play, one sentence, a notification line only when something needs fixing (not allowed: Allow; off: Turn on; blocked: where to fix it), and Turn it off · Keep it on. Keep it on has the first focus; Escape and the backdrop keep it on; Tab stays inside; Turn it off saves off and toasts "Sound off". No entrance motion.
- It shows once per machine, for someone who used an earlier Inbox. The server decides at start from evidence that predates that start (`inboxUsedBefore`, read before the store, the update state and the registry are written): a recorded `inboxVersion`, `inbox/inbox.json`, a project under `inbox/projects/`, or `inboxNotifications` / `inboxTool` in config.json. Builds 0.28.7 to 0.28.11 recorded no version, so the version alone is not enough. With such evidence, on a release version other than the one recorded, it writes `inboxSound.dialogDueFor`, which waits in config.json until a page claims it, so a `--background` start that ends before any window opens does not lose it; settings answer `sound.dialog_due`. With none (a fresh install) it writes `dialogShownFor`, so the dialog never shows, and the notification ask line ends with "Sound is on." The page asks `POST /api/inbox/sound/dialog`, a compare-and-set from `dialogDueFor` to `dialogShownFor`: only the first ask ever gets `show: true` (other tabs and reloads get false). It waits for the list, for a reply being typed and for an update dialog; the notification ask line does not show on that load. A page that came through the tailnet is always answered false and leaves it for a page on this computer.
- State lives in config.json as `inboxSound` (`{ enabled, volume, dialogDueFor, dialogShownFor }`), through `GET` and `POST /api/inbox/settings` (`sound: { enabled?, volume? }`); one volume for every device.

**Agent connections and the knob.**
- A connection gives its host one tool, `plannotator_inbox`, whose `action` is one of the Inbox's MCP tools. It also wakes the session that asked when the person sends.
- The contract lives once in `packages/shared/inbox/connection.ts`. The mod keeps a byte-for-byte copy of its CONTRACT section in `apps/hook/hooks/mod/inbox-contract.ts`, pinned by `inbox-contract.test.ts`.
- The tool is built from the running Inbox's own `tools/list` (`inboxAgentTool`). The connection fills `project_path`, `agent_session`, `agent_host` and `agent_name` and keeps them out of the schema, except an OPTIONAL `project_path` (`INBOX_AGENT_PROJECT_PATH`: "The repository or folder this is about; defaults to your working folder."), for a session whose working folder is not the project (a notes subfolder). `inboxToolCall` shape-checks it (a string, no control characters, at most 4096 characters) and returns it as `projectPath`; the connection resolves it against the working folder (absolute as given) to an existing folder's real path (Pi/OpenCode: `inboxProjectDir` in `agent-link.ts`; the mod: `INBOX_PROJECT_DIR_SCRIPT`, `cd` + `pwd -P`) and refuses anything else before the Inbox is reached or started. The Inbox then resolves it to the git toplevel or folder as for any `project_path`, and relative `attachments` resolve against it. No new exposure: any MCP client could already pass any `project_path`. The schema is part of the tool list, so it changes from the next session.
- The wake text (`inboxWakeText`) is `Plannotator Inbox: <subject> (<reply id>)`, the fixed `INBOX_WAKE_INSTRUCTION` line (for a reply the person sent to another session because the asker ended, one more line under it, `inboxRedirectedLine`), a blank line, then the reply verbatim. It never carries the thread and never touches the system prompt.
- A connection whose wake runs sets `_meta["ai.plannotator/inbox-wakes"]: true` on its `tools/call` (`INBOX_WAKES_META_KEY`, `inboxToolCallParams`): the Claude Code mod always, Pi and OpenCode 2 while the session's wake exists, OpenCode 1 never. send_message and submit_guide then end their result with `INBOX_REPLY_ARRIVES_TEXT` (end the turn; the reply arrives by itself) instead of "Call wait_for_reply…", which the stdio shim, raw MCP clients and older connections keep (`callerWakes` in `inbox-mcp.ts`). An older Inbox ignores the key.
- The bridge is two connection routes:
  - `POST /api/inbox/bridge/poll` holds up to 25 s for the person's replies to that session.
  - `POST /api/inbox/bridge/event` `{ type: "delivered" }` writes `delivery` on the reply, which the thread shows as "Delivered to <agent>".
- Pending replies are derived from the store (`InboxStore.pendingReplies`), so a reply is handed out on every poll until it is delivered, survives a restart, and never wakes a session that already read it through the MCP.
- Each host checks the knob and the registry once: the Claude Code mod at the process's first `session.start` (so a change applies when Claude Code restarts; it registers the tool from a bundled list even with no `inbox/inbox.json`, see the mod section), Pi when the extension instance loads (each session and `/reload`) and OpenCode at plugin setup (each OpenCode start), where the tool exists only when `inbox/inbox.json` existed then and the knob allowed it. The tool list never changes during a session.
- The session-start reminder (`INBOX_REMINDER_TEXT`, config-only `inboxReminder`, on by default wherever the tool is, once the Inbox has run here): one fixed line, decided with the tool, in each host's cache-safe place: the mod's `prompt.context` block (the tool's full name), Pi's hidden `before_agent_start` message (`plannotator-inbox-reminder`, once per session, ignored by the Ask-this-session bridge), OpenCode 2's composed system part on requests that offer the tool (primary agents; no-wake wording without `session.prompt`), the end of OpenCode 1's last system part for agents with the tool (no-wake wording). Details in the `inboxReminder` entry under Config-only settings.
- The knob: `PLANNOTATOR_INBOX_TOOL` (`1`, `true`, `on` / `0`, `false`, `off`, `disabled`), then config `inboxTool` (one boolean, or `{ "claude-code", "pi", "opencode" }`, written by Settings), then `INBOX_TOOL_DEFAULTS` (on for Claude Code, off on Pi and OpenCode, which send every tool's full definition with each request) (`packages/shared/config.ts`, `resolveInboxTool`).
- **Claude Code** (the mod, `apps/hook/hooks/mod/inbox.ts`; details in "The Plannotator Inbox" in the mod section):
  - `InboxLink` long-polls on a 1 s tick and submits the wake once the session has been idle for two ticks.
  - It claims each reply once (mkdir) and holds a per-session lease, `watcher.json`: the person's last process wins, and the lease goes stale after 20 s.
  - It needs the mod (Claude Code 2.1.287+, not `claude -p`, not Windows).
- **Pi and OpenCode** (`packages/shared/inbox/agent-link.ts`, vendored into Pi as `generated/inbox/`):
  - `InboxAgentConnection` starts a stopped Inbox with `plannotator inbox --background`, through `PLANNOTATOR_BIN`, `plannotator` on PATH, or `~/.local/bin/plannotator`. With no binary, the first result says to install Plannotator.
  - `InboxWake` long-polls, delivers after two idle ticks, checks the reply once more, and claims it with a mkdir of `inbox/claims/<reply id>`. It never interrupts a turn.
  - Two processes on one session (`pi -c` or `--session` twice; two `opencode2` servers on one database): only the holder of the session's lease, `inbox/leases/<host>-<session>.json` (`{ owner, at, touchedAt }`, `inboxLeaseFileOf` in `agent-link.ts`), polls and delivers. It is the Claude Code mod's rule ported: the process the person used last holds it, renewed every 5 s (`INBOX_LEASE_EVERY_MS`), taken over about 20 s after the holder dies (`INBOX_LEASE_STALE_MS`; released at once on a clean exit), and re-read right before the claim. The claim still keeps a delivery once whatever the lease says.
  - What moves the lease: on Pi, the person typing (an `input` whose source is not `extension`) and a `plannotator_inbox` call, plus a session start. On OpenCode 2 (checked on 2.0.19) typing does NOT move it, only a `plannotator_inbox` tool call does, because the plugin gets no typing events: its event subscription yielded none there. The code would also touch on a user `session.inbox.enqueued` item or a `session.execution.started`, should an OpenCode deliver them. So on OpenCode 2 a process the person only typed into, whose agent never called the tool, has no wake, and the other process still delivers.
  - Pi (`apps/pi-extension/inbox.ts`): the tool is inactive in print and JSON mode. Delivery is `pi.sendUserMessage(text, { deliverAs: "followUp" })`, confirmed by its `message_start`, and the thread reads "Delivered to Pi".
  - OpenCode 2 (`apps/opencode-plugin/inbox.ts`): the wake is per root session, made on its first tool call or run in the process. Delivery is `session.prompt({ delivery: "queue" })`, never steer, and the thread reads "Delivered to OpenCode".
  - OpenCode 1: the tool only, with no wake.
  - Neither package ships `inbox.html`.

**MCP for other agents** (`packages/server/inbox-mcp.ts`, `@modelcontextprotocol/server` 2.2.0, stateless).
- Tools: `send_message`, `read_thread`, `resolve_message`, `wait_for_reply`, `list_decisions`, `record_decision`, `get_guide_brief`, `submit_guide`.
- Transports: stdio through `plannotator inbox mcp` (the harness picker's commands use it), or Streamable HTTP at `http://127.0.0.1:<port>/mcp`. The window says to prefer the command, because the port can change.
- Character limits: server instructions stay under Claude Code's 2,048 characters. The question guide rides `send_message`'s description, and `inbox.test.ts` pins that Claude Code's 2,048-character description cut keeps the guide's working part.
- Answers: success is `structuredContent` plus one line. A refusal is `isError` with `<snake_code>: <message>`.
- `wait_for_reply` returns a reply as soon as it lands, or `{ status: "waiting", cursor }` after 50 s.
- `supersedes` (send_message, submit_guide) is described in its own field (`SUPERSEDES_DESCRIPTION`), which reaches the model whole; send_message's description is cut at 2,048 characters and stays the question guide. `plannotator inbox --help` documents it and the `Replaces:` line ("Only in the Inbox", `INBOX_REPLACES_EXAMPLE`).
- The Inbox-only `Stopped:` / `Holds up:` lines (with the bare-negative rule and an example, `INBOX_STOP_EXAMPLE`) are taught in send_message's `body` field (`SEND_BODY_DESCRIPTION`), which reaches the model whole and rides the `plannotator_inbox` tool's `body`; never in `QUESTION_AUTHORING_GUIDE`, which plan review shares and the skill copies byte for byte.

**Phones** (`packages/server/inbox-devices.ts`, records in `packages/shared/inbox/devices.ts`; contract sections 1, 2 and 6).
- Off unless `PLANNOTATOR_INBOX_PHONES=1` (or config.json `inboxPhones: true`) is set when the Inbox starts: until the iPhone app ships, a released Inbox has no pairing, no door, no reach switches, no relay and no Phones block, and every one of those routes answers the unknown-route 404 (see the env table). Everything below describes the Inbox with the switch on.
- Pairing: Settings' "Pair a phone" calls `POST /api/inbox/pairing`, which opens one offer: a `plannotator://pair` link (drawn as a QR code with `uqr`, `packages/inbox/qr.ts`) carrying the computer's name, the tailnet address when it is on, the LAN address and the certificate's SHA-256 (`lan`, `fp`) when the Wi-Fi is on, a 32-byte secret and six digits. One offer is open at a time, in memory only. It closes when redeemed, when the window makes another, 10 minutes after it was made, or after 5 wrong codes: the two limits pairing needs, and the only ones. The phone redeems the secret or the digits at `POST /api/inbox/device/pair` for its own `tok_` bearer token, returned once.
- Records under `inbox/`: `devices.jsonl` (the store's line rules; `dev_` id, name, platform, the token's SHA-256 and never the token, created, last seen, revoked, `carriage`), `device-secrets/<dev id>` (the pairing secret, 0600 in a 0700 folder, for the relay's keys; deleted on revoke) and `device-commands.jsonl` (the door's answers by key). Last seen is kept in memory on each request and written when its UTC day changes.
- The relay (`packages/server/inbox-relay.ts`; the Worker in `apps/relay`; contract section 4):
  - The first pairing makes the mailbox (`POST /v1/mailboxes` with the SHA-256 of a fresh 32-byte mailbox secret) and keeps it in `inbox/relay.json` (0600): `{ v: 1, url, mailbox_id, secret }`. The redemption's answer carries `relay: { url, mailbox_id }`, or null when the relay cannot be reached (a call waits 10 s at most). Each paired phone is registered by the SHA-256 of its relay secret (HKDF of its pairing secret, `deriveRelayKeys` in `packages/core/crypto.ts`) and removed at the relay when it is revoked.
  - One outbound WebSocket to the mailbox while a phone is paired, reconnecting 1 s to 60 s apart. `hello` writes each phone's relay switch into its record, removes at the relay a phone revoked here, and registers a phone the relay does not list; `carriage` writes the switch a phone flipped. The phone registers its push token at the relay itself, with its relay secret: APNs (iPhone) or FCM (Android, section 10), one per device.
  - The carriage (R2). Frames are handled one at a time in arrival order. Down: after `hello`, each phone with its switch on gets every store line after the cursor the relay holds for it (`changesSince`, as the event stream catches up), then each line as it is written, as an `item` sealed under the phone's key `K` (the event stream's `record` payload plus `v`, `type` and `after`, the seq the previous item reached, so the phone notices a gap); a line past Cloudflare's 32 MiB WebSocket message goes down as a `too_large` placeholder and the cursor moves past it. The push plaintext carries `type: "push"`, so neither can pass for the other. Up: each `command` is opened with the phone's up key `U` (a key per direction, so a down envelope reflected up does not open), applied in-process through the door as that device (`asDevice` in `inbox-devices.ts`: the revocation check, the allowlist and the idempotency log, never a loopback HTTP call), answered with a `result` item under the id sealed inside it (a sealed id that is not the relay's frame id is refused) with status, type and body bytes as base64 (files are GET results; a body over 3/4 of Cloudflare's 32 MiB WebSocket message, base64's growth, becomes a 413 `result_too_large` in its place, refused from its Content-Length before a byte is read, and a body without one read only until it passes that bound, `readRelayBody`), and reported `applied`. `pair` and `events` are not carried. A command no key opens is reported applied with no result. The Inbox stopped, commands wait at the relay and are applied on the next start; a replay answers the stored result and writes nothing.
  - Push: an agent's message landing with a question or a guided review, or one that superseded earlier questions (replaced questions; then `question: null` unless it asks a new one), (its first line in the store) sends one push per paired phone whose switch is on, the summary (thread, subject, project, agent, and one single-choice question with up to four choices) sealed with `encryptWithKey` under that phone's key, collapsed per thread by an HMAC of the thread id under that key (the relay never sees a thread id). Over Apple's 4096 bytes it drops the question's context, then the question, then sends the ids alone.
  - The relay is `https://relay.plannotator.ai` (not yet deployed; until then a pairing answers `relay: null`) unless `PLANNOTATOR_RELAY_URL` names another. Tests never reach the hosted relay: the root preload and the test world point it at a closed loopback port.
  - The Worker (`apps/relay`): one Durable Object per mailbox on SQLite (`mailbox` with the secret's hash; `devices` with the relay secret's hash, the switch, the cursor, the APNs token and environment or the FCM token, the next item number; `items` and `commands`, envelopes kept in parts of 1,000,000 characters because a row may not pass 2 MB). Down items are deleted on the phone's ack (by item number, or by store cursor when it read directly) and when it turns its switch off; commands when the Inbox reports them applied; everything a device held when it is removed. A device holds one push token, APNs or FCM (`PUT .../apns` and `PUT .../fcm` each clear the other; `hello` lists `apns` and `fcm` per device), and a push goes to whichever it holds; with neither it answers `no_push_token` (`no_apns_token` before R3; the Inbox only logs the reason). APNs over HTTP/2 through `connect()` (`src/apns-h2.ts`; a Worker's `fetch` cannot reach APNs; it refuses a frame over 16 KiB and keeps at most 8 KiB of an answer), an ES256 provider token from the `APNS_KEY` secret kept 50 minutes; a 410 deletes the token; without the key a push answers `no_apns_key`. FCM (R3, `src/fcm.ts`): HTTP v1 `messages:send` with plain `fetch`, the body data only (`{ message: { token, data: { e }, android: { priority: "high", collapse_key } } }`), an OAuth access token minted from the `FCM_SERVICE_ACCOUNT` secret (the service account's JSON key file: an RS256 JWT signed with WebCrypto, exchanged at oauth2.googleapis.com) and kept 50 minutes; `UNREGISTERED` deletes the token (`fcm_gone`); any other refusal is `502 fcm_failed` with `fcm_status` and `fcm_reason`; without the secret a push answers `no_fcm_key`. The size ladder stays measured against the APNs body, which is always larger than FCM's data payload around the same envelope. Mailbox creation takes guides.show's rate limit rule (20 a minute per IP); nothing else is braked (pushes are not: a push needs the phone's push token, which only the app and the relay hold); nothing is swept by time. The proof-only host overrides (`APNS_ORIGIN`, `FCM_ORIGIN`, `FCM_OAUTH_ORIGIN`, `src/origin.ts`) are honored only for a loopback host; any other value is ignored with one log line, so no signed token goes elsewhere. Concurrent FCM pushes share one token exchange, and a refused exchange (or an unreadable private key) is answered from memory for a minute.
- The door, `/api/inbox/device/*`, in order: any `Origin` is `403 origin_not_allowed`; `pair` takes no token; then `Authorization: Bearer tok_…` (`401 device_token_missing`, `device_token_invalid`, `device_revoked`); then the explicit allowlist (`ALLOWLIST`: health, threads, projects, the archived threads, a thread, seen, events, picks, reply, resolve, delete thread, attachments, view, the HTML asset route, annotations and remove, the guide and its ticks, the decision switch, decisions, live sessions, New message; anything else `404 device_route_not_found`); then a POST needs `idempotency_key` (`422`). The request then goes to the window's own handler through the server's own `fetch` on loopback, adding and stripping nothing. `/mcp`, the bridge, control, settings, restart, raw attachment bytes, project delete, decision retire and replace, pairing, the device list, the tailnet and Wi-Fi switches and search (until the iPhone app has its own search design) are never on it.
- Idempotency: a POST's status and JSON body are kept per device and key and read at start. The same key on the same route answers them again with `Idempotent-Replayed: true` and writes nothing; on another route it is `409 idempotency_key_reused`; a 5xx is not kept.
- Remove: Settings' Remove (`POST /api/inbox/devices/:id/revoke`) or the phone's own `POST /api/inbox/device/revoke` marks the record revoked, deletes its secret and ends its open event streams. Its next request is `401 device_revoked`.
- Settings → Devices (`packages/inbox/components/Devices.tsx`, design of record `.product/approved/inbox-settings-tabs/`): the paired phones with platform, last seen and Remove (asked twice), and Pair a phone; "How your phone reaches this computer": This Wi-Fi (the LAN address, the certificate's SHA-256 shortened with the whole in its title, where nothing can publish Bonjour a note that phones will not list it but the scan still pairs) and Tailscale (the served address; the phone path, renamed from "Reach from my tailnet"), each a switch named by its title with a "Not working" chip and the reason while on and failing, so one click turns it off.
- Pair a phone, step by step (`components/PairFlow.tsx`, words and gate in `packages/inbox/pairing.ts`), inline in Devices at `#settings/devices/pair`. It always starts at step 1 (owner, decision 3), "How will your phone reach this computer?": the two ways side by side, each with "This computer" (live checks from `GET /api/inbox/pairing/checks`: ✓, ! or × with the fix in one line; Check again reads them again, and again after each switch) and "Your phone needs" (what the computer cannot check: the same Wi-Fi by name, Local Network allowed, the Tailscale app signed in to the same tailnet), Turn on / Turn off in each card, and one line that Plannotator's relay is not available yet. **The no-loop rule** (owner, decision 5): the checks are advisory and never a gate; Turn on stays offered beside Check again whatever a check says; the ONLY gate on the code is a way switched on (`canShowCode`), so with a way on and every check failing "Continue to the code" still shows the code (`settingsSections.test.tsx`, `inbox-phones.spec.ts` prove it). With no way on the button reads "Show the code", `aria-disabled`, and a press only says to turn a way on; with neither way able to work a red line says so. Step 2 (`POST /api/inbox/pairing`): the QR, the six digits only while Tailscale carries an address (over Wi-Fi it pairs by scanning only), the addresses the code carries with Change (back to step 1), "Before you scan, on your phone", the countdown with New code and Cancel, and live notes from `GET /api/inbox/pairing` every 2 s (wrong digits with tries left, digits typed over the Wi-Fi, an older code, a phone after the code closed); on expiry with nothing seen, a numbered troubleshooting list for the ways that were on; a code closed by five wrong tries says so; a code another window replaced (the GET's `expires_at` is not this tab's) reads "This code was replaced", never as this tab's expiry or attempts. A double press makes one code (a ref guards `makeCode`). Step 3: "Paired with <name>", how it reached this computer, and Done (back to `#settings/devices`, focus on Pair a phone). Nothing reads the tailnet's other devices (owner, decision 4). A page opened over the tailnet offers no code: it says pairing and the switches work only from this computer's own screen.

**Security**, on every request:
- The Host allowlist (`createRequestHostGuard({ localOnly: true })`) on the window's port. The tailnet listener ("Over your tailnet") runs its own checks instead: the served Host, the owner's `Tailscale-User-Login`, `Sec-Fetch-Site`.
- `/mcp` refuses any request with an Origin (403 `origin_not_allowed`) and any Host that is not a loopback name with this port (403 `forbidden_host`). Release note: an MCP client that reaches the Inbox through `ssh -L <other port>:127.0.0.1:<port>` sends `Host: localhost:<other port>` and is now refused; forward the same port number, or use `plannotator inbox mcp` on the Inbox's machine.
- The window's port refuses any request carrying `Tailscale-Headers-Info`, `Tailscale-User-Login` or `X-Forwarded-For` (403 `local_only`): it came through a serve mapping pointed straight at this port.
- Connection routes (`/api/inbox/bridge/*`, `/api/inbox/control/*`) take the registry's bearer token, a loopback Host naming this port, and no Origin.
- Nothing that arrives through the tailnet listener reaches `/mcp`, a connection route or the device door (403 `local_only`), whatever Host it claims.
- State-changing window routes run `isSameOriginOrNoOrigin` (403 `cross_origin`), then the `serverSession` stale-tab guard (409 `session_mismatch`).
- No CORS headers on the Inbox's routes. The one exception is annotate's asset route for an attached HTML page's folder.
- The window's CSP: `default-src 'self'`, inline script and style, `'wasm-unsafe-eval'` in `script-src` (the Graphviz engine, `@viz-js/viz`, compiles WebAssembly to render `.dot`/`.gv` attachments; it allows no `eval()` or `new Function()`, and there is no `'unsafe-eval'`), `connect-src 'self'`, `frame-ancestors 'none'`, `base-uri 'self'`, `form-action 'none'`. An attached HTML page's srcdoc frame inherits this policy.
- Agent text reaches the page only through React and Plannotator's markdown renderer.
- The device door (`/api/inbox/device/*`): no Origin, the phone's bearer token, the allowlist (see "Phones"). The tailnet and the Wi-Fi reach only the door, each through its own listener (see "Local only by default").
- DAST (`.github/workflows/dast.yml`) scans a seeded Inbox on port 19435, the door's refusals included.
