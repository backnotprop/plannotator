## Inbox: phones and security

**On a phone**: `adr/implementation/inbox-mobile.md` is the wire contract the iPhone app and its server steps build against: the pairing offer, the device token door `/api/inbox/device/*`, the LAN listener, the relay, the surface bridge and the idempotency rule. Built (P1, P2, R1, R2, R3): pairing, the door, the tailnet path, the LAN listener, and the relay's mailboxes, push (APNs, and FCM for Android: section 10) and carriage. The Plannotator iPhone app lives in the Workspaces repo. The Inbox writes no event when a thread is deleted: a phone learns it at its next read of that thread. Not built: Bonjour discovery in 1.3 (a Wi-Fi address that moves is followed only by scanning the code again).

**Phones** (`packages/server/inbox-devices.ts`, records in `packages/shared/inbox/devices.ts`; contract sections 1, 2 and 6).
- Off unless `PLANNOTATOR_INBOX_PHONES=1` (or config.json `inboxPhones: true`) is set when the Inbox starts: until the iPhone app ships, a released Inbox has no pairing, no door, no reach switches, no relay and no Phones block, and every one of those routes answers the unknown-route 404 (see the env table). Everything below describes the Inbox with the switch on.
- Pairing: Settings' "Pair a phone" calls `POST /api/inbox/pairing`, which opens one offer: a `plannotator://pair` link (drawn as a QR code with `uqr`, `packages/inbox/qr.ts`) carrying the computer's name, the tailnet address when it is on, the LAN address and the certificate's SHA-256 (`lan`, `fp`) when the Wi-Fi is on, a 32-byte secret and six digits. One offer is open at a time, in memory only. It closes when redeemed, when the window makes another, 10 minutes after it was made, or after 5 wrong codes: the two limits pairing needs, and the only ones. The phone redeems the secret or the digits at `POST /api/inbox/device/pair` for its own `tok_` bearer token, returned once.
- Records under `inbox/`: `devices.jsonl` (the store's line rules; `dev_` id, name, platform, the token's SHA-256 and never the token, created, last seen, revoked, `carriage`), `device-secrets/<dev id>` (the pairing secret, 0600 in a 0700 folder, for the relay's keys; deleted on revoke) and `device-commands.jsonl` (the door's answers by key). Last seen is kept in memory on each request and written when its UTC day changes.
- The relay (`packages/server/inbox-relay.ts`; the Worker in `apps/relay`; contract section 4):
  - The first pairing makes the mailbox (`POST /v1/mailboxes` with the SHA-256 of a fresh 32-byte mailbox secret) and keeps it in `inbox/relay.json` (0600): `{ v: 1, url, mailbox_id, secret }`. The redemption's answer carries `relay: { url, mailbox_id }`, or null when the relay cannot be reached (a call waits 10 s at most). Each paired phone is registered by the SHA-256 of its relay secret (HKDF of its pairing secret, `deriveRelayKeys` in `packages/core/crypto.ts`) and removed at the relay when it is revoked.
  - One outbound WebSocket to the mailbox while a phone is paired, reconnecting 1 s to 60 s apart. `hello` writes each phone's relay switch into its record, removes at the relay a phone revoked here, and registers a phone the relay does not list; `carriage` writes the switch a phone flipped. The phone registers its push token at the relay itself, with its relay secret: APNs (iPhone) or FCM (Android, section 10), one per device.
  - The carriage (R2). Frames are handled one at a time in arrival order. Down: after `hello`, each phone with its switch on gets every store line after the cursor the relay holds for it (`changesSince`, as the event stream catches up), then each line as it is written, as an `item` sealed under the phone's key `K` (the event stream's `record` payload plus `v`, `type` and `after`, the seq the previous item reached, so the phone notices a gap); a line past Cloudflare's 32 MiB WebSocket message goes down as a `too_large` placeholder and the cursor moves past it. The push plaintext carries `type: "push"`, so neither can pass for the other. Up: each `command` is opened with the phone's up key `U` (a key per direction, so a down envelope reflected up does not open), applied in-process through the door as that device (`asDevice` in `inbox-devices.ts`: the revocation check, the allowlist and the idempotency log, never a loopback HTTP call), answered with a `result` item under the id sealed inside it (a sealed id that is not the relay's frame id is refused) with status, type and body bytes as base64 (files are GET results; a body over 3/4 of Cloudflare's 32 MiB WebSocket message, base64's growth, becomes a 413 `result_too_large` in its place, refused from its Content-Length before a byte is read, and a body without one read only until it passes that bound, `readRelayBody`), and reported `applied`. `pair` and `events` are not carried. A sealed command carries no headers in v1, so no Range reaches the window through the relay: a video's `video` or `download` answers the whole file, carried when it fits one frame and a `413 result_too_large` otherwise; the phone plays a video over the Wi-Fi or the tailnet (relay ranges of 8 MiB or less are v1.1, contract section 3 of `adr/implementation/inbox-mobile.md`). A command no key opens is reported applied with no result. The Inbox stopped, commands wait at the relay and are applied on the next start; a replay answers the stored result and writes nothing.
  - Push: an agent's message landing with a question or a guided review, or one that superseded earlier questions (replaced questions; then `question: null` unless it asks a new one), (its first line in the store) sends one push per paired phone whose switch is on, the summary (thread, subject, project, agent, and one single-choice question with up to four choices) sealed with `encryptWithKey` under that phone's key, collapsed per thread by an HMAC of the thread id under that key (the relay never sees a thread id). Over Apple's 4096 bytes it drops the question's context, then the question, then sends the ids alone.
  - The relay is `https://relay.plannotator.ai` (not yet deployed; until then a pairing answers `relay: null`) unless `PLANNOTATOR_RELAY_URL` names another. Tests never reach the hosted relay: the root preload and the test world point it at a closed loopback port.
  - The Worker (`apps/relay`): one Durable Object per mailbox on SQLite (`mailbox` with the secret's hash; `devices` with the relay secret's hash, the switch, the cursor, the APNs token and environment or the FCM token, the next item number; `items` and `commands`, envelopes kept in parts of 1,000,000 characters because a row may not pass 2 MB). Down items are deleted on the phone's ack (by item number, or by store cursor when it read directly) and when it turns its switch off; commands when the Inbox reports them applied; everything a device held when it is removed. A device holds one push token, APNs or FCM (`PUT .../apns` and `PUT .../fcm` each clear the other; `hello` lists `apns` and `fcm` per device), and a push goes to whichever it holds; with neither it answers `no_push_token` (`no_apns_token` before R3; the Inbox only logs the reason). APNs over HTTP/2 through `connect()` (`src/apns-h2.ts`; a Worker's `fetch` cannot reach APNs; it refuses a frame over 16 KiB and keeps at most 8 KiB of an answer), an ES256 provider token from the `APNS_KEY` secret kept 50 minutes; a 410 deletes the token; without the key a push answers `no_apns_key`. FCM (R3, `src/fcm.ts`): HTTP v1 `messages:send` with plain `fetch`, the body data only (`{ message: { token, data: { e }, android: { priority: "high", collapse_key } } }`), an OAuth access token minted from the `FCM_SERVICE_ACCOUNT` secret (the service account's JSON key file: an RS256 JWT signed with WebCrypto, exchanged at oauth2.googleapis.com) and kept 50 minutes; `UNREGISTERED` deletes the token (`fcm_gone`); any other refusal is `502 fcm_failed` with `fcm_status` and `fcm_reason`; without the secret a push answers `no_fcm_key`. The size ladder stays measured against the APNs body, which is always larger than FCM's data payload around the same envelope. Mailbox creation takes guides.show's rate limit rule (20 a minute per IP); nothing else is braked (pushes are not: a push needs the phone's push token, which only the app and the relay hold); nothing is swept by time. The proof-only host overrides (`APNS_ORIGIN`, `FCM_ORIGIN`, `FCM_OAUTH_ORIGIN`, `src/origin.ts`) are honored only for a loopback host; any other value is ignored with one log line, so no signed token goes elsewhere. Concurrent FCM pushes share one token exchange, and a refused exchange (or an unreadable private key) is answered from memory for a minute.
- The door, `/api/inbox/device/*`, in order: any `Origin` is `403 origin_not_allowed`; `pair` takes no token; then `Authorization: Bearer tok_…` (`401 device_token_missing`, `device_token_invalid`, `device_revoked`); then the explicit allowlist (`ALLOWLIST`: health, threads, projects, the archived threads, a thread, seen, events, picks, reply, resolve, delete thread, attachments, view, an attachment's `image`, `video` and `download` bytes (the window's `206` returned unchanged), markups, the HTML asset route, a message's images (`messages/:id/image?path=`, the window's route with its rules and headers), annotations and remove, comments on an agent's message's text (7.59), the guide, its ticks and comments on its diff, live sessions, New message, 👍 Looks good (`messages/:id/ack`), and since 2026-10-15 compose (`sessions`, `messages`, `messages/:id/to`), search, the project menu's batches, the skill catalog, and uploads and drawings (`uploads?name=`, `markups`: raw bodies streamed through with their query, the key in `?idempotency_key=`, bounded by the door itself since the window runs in-process (100 MB and 32 MB, declared or counted as they stream: `413 upload_too_large` / `markup_too_large` with `Connection: close`, nothing recorded); after a replay or refusal at most 1 MiB or 2 s of the rest is read and dropped, then `Connection: close`; not carried by the relay: `413 relay_upload_unavailable`; `POST messages` with `draft_id` is `422`, drafts stay on the computer); anything else `404 device_route_not_found`); then a POST needs `idempotency_key` (`422`; in the query on the two raw-body routes). The request then goes to the window's own handler through the server's own `fetch` on loopback, with the route, query and body unchanged; of the phone's headers only `Last-Event-ID`, `If-None-Match` and, on a GET, `Range` and `If-Range` ride along (plus `Content-Type` and `Content-Length` on the raw-body routes). `/mcp`, the bridge, control, settings, restart, raw attachment bytes, project delete, every Decisions route (removed: `decisions`, `messages/:id/decision`, retire and replace; `404 device_route_not_found`), drafts, recent searches, pairing, the device list, the tailnet and Wi-Fi switches and "Open in" (the launch, the app list and the new-tab page) are never on it.
- Idempotency: a POST's status and JSON body are kept per device and key and read at start. The same key on the same route answers them again with `Idempotent-Replayed: true` and writes nothing; on another route it is `409 idempotency_key_reused`; a 5xx is not kept.
- Remove: Settings' Remove (`POST /api/inbox/devices/:id/revoke`) or the phone's own `POST /api/inbox/device/revoke` marks the record revoked, deletes its secret and ends its open event streams. Its next request is `401 device_revoked`.
- Settings → Devices (`packages/inbox/components/Devices.tsx`, design of record `.product/approved/inbox-settings-tabs/`): the paired phones with platform, last seen and Remove (asked twice), and Pair a phone; "How your phone reaches this computer": This Wi-Fi (the LAN address, the certificate's SHA-256 shortened with the whole in its tooltip (`data-fingerprint`), where nothing can publish Bonjour a note that phones will not list it but the scan still pairs) and Tailscale (the served address; the phone path, renamed from "Reach from my tailnet"), each a switch named by its title with a "Not working" chip and the reason while on and failing, so one click turns it off.
- Pair a phone, step by step (`components/PairFlow.tsx`, words and gate in `packages/inbox/pairing.ts`), inline in Devices at `#settings/devices/pair`. It always starts at step 1 (owner, decision 3), "How will your phone reach this computer?": the two ways side by side, each with "This computer" (live checks from `GET /api/inbox/pairing/checks`: ✓, ! or × with the fix in one line; Check again reads them again, and again after each switch) and "Your phone needs" (what the computer cannot check: the same Wi-Fi by name, Local Network allowed, the Tailscale app signed in to the same tailnet), Turn on / Turn off in each card, and one line that Plannotator's relay is not available yet. **The no-loop rule** (owner, decision 5): the checks are advisory and never a gate; Turn on stays offered beside Check again whatever a check says; the ONLY gate on the code is a way switched on (`canShowCode`), so with a way on and every check failing "Continue to the code" still shows the code (`settingsSections.test.tsx`, `inbox-phones.spec.ts` prove it). With no way on the button reads "Show the code", `aria-disabled`, and a press only says to turn a way on; with neither way able to work a red line says so. Step 2 (`POST /api/inbox/pairing`): the QR, the six digits only while Tailscale carries an address (over Wi-Fi it pairs by scanning only), the addresses the code carries with Change (back to step 1), "Before you scan, on your phone", the countdown with New code and Cancel, and live notes from `GET /api/inbox/pairing` every 2 s (wrong digits with tries left, digits typed over the Wi-Fi, an older code, a phone after the code closed); on expiry with nothing seen, a numbered troubleshooting list for the ways that were on; a code closed by five wrong tries says so; a code another window replaced (the GET's `expires_at` is not this tab's) reads "This code was replaced", never as this tab's expiry or attempts. A double press makes one code (a ref guards `makeCode`). Step 3: "Paired with <name>", how it reached this computer, and Done (back to `#settings/devices`, focus on Pair a phone). Nothing reads the tailnet's other devices (owner, decision 4). A page opened over the tailnet offers no code: it says pairing and the switches work only from this computer's own screen.

**The surface** (PLAN step S1; contract section 5). `apps/inbox`'s `build:surface` (`vite.surface.config.ts`, entry `surface.html`) builds `packages/inbox/surface` into one file, which `build:hook` copies to `apps/hook/dist/surface.html`; the iPhone app bundles it.
- It mounts only `Viewer` with the annotation toolstrip, `HtmlViewer` with pins, `DiagramViewer` (lazy) and the guide (`packages/inbox/guide/SurfaceGuideReader.tsx` behind `#surface-guide-reader`, lazy: the sections, then one `GuideSectionCard` per screen).
- No network: CSP `default-src 'none'`, `connect-src 'none'`; an HTML page's folder loads from the shell's asset origin, `plannotator-asset:` on iOS and `https://appassets.androidplatform.net` on Android (both in the one file's policy). The system face on Plannotator's tokens; settings live in memory; diffs unified and wrapped.
- The bridge: `packages/core/inbox-surface-bridge.ts` (re-exported by `inbox-types`), the surface's end in `packages/inbox/surface/bridge.ts`: it posts to `window.webkit.messageHandlers.plannotatorSurface` when `window.webkit` exists, else to the Android shell's `window.plannotatorShell` as a JSON string (contract section 10). The composer is the shell's: the viewers report drafts through ui's `onHostDraft` seams, and `commit_annotation` draws the saved one.
- Proof: `tests/e2e/surface.spec.ts`, Playwright WebKit against the built file and a compiled Inbox (in `inbox-e2e.yml`).
- The iPhone app is the surface's host: one web view loads the bundled file, `plannotator-asset:` serves an open HTML page's folder through the door, and a guided review opens on the same web view (`open_guide`, `reviewed`, `section`, `set_wrap`; contract section 5). The Plannotator iPhone app lives in the Workspaces repo.
- Added for the phone (M2): `comment_selection` (Comment in the system edit menu; on a touch screen a markdown selection stays the system's until then, ui's `ViewerHandle.takeSelection`), `export_feedback` and `feedback` (Send's feedback text, built by `attachmentFeedback` as the window builds it), and ui's `HtmlViewer` `hostNavigates` (a tapped link in an agent's page opens as a new window the shell decides, never a frame message).

**Security**, on every request:
- The Host allowlist (`createRequestHostGuard({ localOnly: true })`) on the window's port. The tailnet listener ("Over your tailnet") runs its own checks instead: the served Host, the owner's `Tailscale-User-Login`, `Sec-Fetch-Site`.
- `/mcp` refuses any request with an Origin (403 `origin_not_allowed`) and any Host that is not a loopback name with this port (403 `forbidden_host`). Release note: an MCP client that reaches the Inbox through `ssh -L <other port>:127.0.0.1:<port>` sends `Host: localhost:<other port>` and is now refused; forward the same port number, or use `plannotator inbox mcp` on the Inbox's machine.
- The window's port refuses any request carrying `Tailscale-Headers-Info`, `Tailscale-User-Login` or `X-Forwarded-For` (403 `local_only`): it came through a serve mapping pointed straight at this port.
- Connection routes (`/api/inbox/bridge/*`, `/api/inbox/control/*`) take the registry's bearer token, a loopback Host naming this port, and no Origin.
- Nothing that arrives through the tailnet listener reaches `/mcp`, a connection route or the device door (403 `local_only`), whatever Host it claims.
- State-changing window routes run `isSameOriginOrNoOrigin` (403 `cross_origin`), then the `serverSession` stale-tab guard (409 `session_mismatch`).
- No CORS headers on the Inbox's routes. The one exception is annotate's asset route for an attached HTML page's folder.
- The window's CSP: `default-src 'self'`, inline script and style, `'wasm-unsafe-eval'` in `script-src` (the Graphviz engine, `@viz-js/viz`, compiles WebAssembly to render `.dot`/`.gv` attachments; it allows no `eval()` or `new Function()`, and there is no `'unsafe-eval'`), `connect-src 'self'`, `frame-ancestors 'none'`, `base-uri 'self'`, `form-action 'none'`. An attached HTML page's srcdoc frame inherits this policy.
- Agent text reaches the page only through React and Plannotator's markdown renderer.
- The device door (`/api/inbox/device/*`): no Origin, the phone's bearer token, the allowlist (see "Phones"). The tailnet and the Wi-Fi reach only the door, each through its own listener (see "Local only by default").
- DAST (`.github/workflows/dast.yml`) scans a seeded Inbox on port 19435, the door's refusals included.

- The thread parity harness (`bun run test:parity:inbox-thread`, `scripts/inbox-thread-parity.ts`; not part of `test:e2e:inbox` or CI): proves that a change to how the thread draws (moving its parts into `@plannotator/ui` or `@plannotator/core`) changes no pixel and no DOM. It builds a dev binary (`__CLI_VERSION__="0.0.0-dev"`, the build order, review then hook) of `--base` (default `origin/main`, in a temporary git worktree, cached in `.local/parity/bin/base-<sha>/plannotator`) as the reference, and one of this checkout as the candidate (`--base-binary` / `--candidate-binary` take a built binary instead; each must be named `plannotator`, as `provenInbox` requires). The reference binary seeds one scratch data dir (`tests/e2e/inbox-thread-parity-seed.ts`: a folding thread with answered questions, an annotated file and a guided review; open, picked and text questions with a reply draft; a replaced question and a Re-ask; image, SVG, markdown, HTML and video files; action items; a 👍 settled and delivered; a reply tagging a second agent; right-to-left and long-token text; a link choice answered beside picture choices). Then `tests/e2e/inbox-thread-parity.config.ts` runs twice. Each project copies the seed and starts its own Inbox on the copy, with `PLANNOTATOR_INBOX_NOTES=0` and a Claude Code plugin registry in its scratch HOME: desktop 1440 by 900 light and dark, the thread pane at 360 px light and dark and at 320 px (a host's sidebar), an iPhone 15 in WebKit light and dark, and a Pixel 7 in Chromium. The page clock is fixed at the seed's `frozenAt`, with `en-US` and `America/New_York`, reduced motion, animations and the caret off, and fonts and images loaded and decoded. It captures the list's rows, then for each thread the landing, every page from the top, its tooltips on a desktop (a time's whole moment, a folded line's time and answers, the 👍 pill), the Files band open, Expand all, the open questions list and the Artifacts view; the list again with the Quiet band open and each delivery tick's tooltip; the list and each thread three days and 400 days later; and a 👍 inside its Undo window. Last, live delivery, which lives in the Inbox's memory and no copy carries: the spec polls the bridge as three seeded sessions (Claude Code busy with Send now: Undelivered and Send now; Claude Code busy on an older plugin: the restart line; Pi busy), reads the Inbox's own wait clock and sets the page clock 90 s after it, so the minutes read the same in both runs. The reference run writes the PNGs; the candidate run compares them at zero pixels (`threshold: 0`). Both write the outerHTML of what each capture shows, normalized for the port, the server session, blob URLs, the HTML asset token and the scratch folder, and each step's page errors and `console.error` lines. The script diffs those files and writes `report.md` and `report.json`, with `dom-diff/` and the candidate's actual, expected and diff PNGs, to `.local/parity/<UTC stamp>/` (or `--out`). It exits 0 only when everything is identical. Known noise: WebKit (the iPhone projects) now and then blends the one pixel row where the thread's scroller clips a picture tile a few colour levels differently, even main against itself; such a capture differs by a dozen to about 130 pixels on that row while its DOM matches, so rerun before reading it as a change. `--keep` keeps the seed folder. It runs under the same sandbox as the specs: a scratch HOME and data dir, `NO_BROWSER`, `PLANNOTATOR_INBOX_CONNECT=0`, `PLANNOTATOR_UPDATE_CHECK=0`, and phones and the relay off.
