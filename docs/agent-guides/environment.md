## Environment Variables

| Variable | Description |
|----------|-------------|
| `PLANNOTATOR_REMOTE` | Set to `1` / `true` for remote mode, `0` / `false` for local mode, or leave unset for SSH auto-detection. Uses a fixed port in remote mode; browser-opening behavior depends on the environment. Remote mode binds `0.0.0.0` and turns off these features: Ask this session (in-process and pull bridge), host control, the agent terminal, open-in, Update now, live app annotation, the strict-gate client lease. Everything else (approve/deny, feedback, agent jobs, `/api/git-add`, `/api/pr-action`, `/api/source/save`, `/api/save-notes`, SDK Ask AI) stays reachable by anyone who can reach the URL. WSL2 does not need it (#1983): local mode binds `127.0.0.1`, WSL2's `localhostForwarding` (default on; mirrored networking too) makes that reachable from Windows at `http://localhost:<port>`, and local mode already opens the Windows browser through `cmd.exe` when neither `BROWSER` nor `PLANNOTATOR_BROWSER` is set and WSL interop is on (`isWSL` in `packages/server/browser.ts`; Pi's `network.ts` likewise), so the guide tells WSL2 users to leave it unset. A "remote but bind loopback" knob was considered and not added: its reachability is exactly local mode's. Remote ready messages also render a terminal QR code of the advertised URL when stderr is a TTY and the advertised host is overridden away from localhost (a QR of a localhost URL scans to nowhere), so another device can join without retyping the URL. |
| `PLANNOTATOR_AGENT_TERMINAL_REMOTE` | Set to `1` / `true` to enable the annotate-mode agent terminal while `PLANNOTATOR_REMOTE` is active or the session is published with `--tailscale`. Off by default in both cases because the session is reachable by network peers and the PTY token is not an auth boundary. |
| `PLANNOTATOR_INBOX_PHONES` | Switch for the Plannotator Inbox's whole phone surface (see "Phones" under "Plannotator Inbox"): pairing, the device door `/api/inbox/device/*`, the tailnet and Wi-Fi listeners, the relay connection, and Phones and Pair a phone in Settings → Devices. **Default: off**, until the iPhone app and the relay ship. Off, the Inbox does nothing phone-related: every pairing, device and reach-switch route answers the unknown-route `404 { code: "not_found" }`, no LAN or door listener opens, nothing connects to the relay, no certificate is made and no `openssl`, `tailscale` or Bonjour process runs, even when `inbox.json`, `relay.json` or `devices.jsonl` hold state from a run that had it on (that state is kept for the next run with it on). `1` / `true` / `on` turn it on, `0` / `false` / `off` / `disabled` off; empty or unrecognized counts as unset. Also `~/.plannotator/config.json` `{ "inboxPhones": true }`; the env var wins (`resolveInboxPhones` in `packages/shared/config.ts`). Read once when the Inbox starts (`startInboxServer`'s `phones` option overrides it); `GET /api/inbox/settings` carries it as `phones`, which is how the window decides to draw the block. The iPhone app's proofs, the relay proof, `tests/e2e/inbox-phones.spec.ts`, the phone server tests (`createInboxWorld(..., { phones: true })`, `phones: true`) and the DAST target set it; `packages/server/inbox-phones-gate.test.ts` proves both states. Not in the public docs. |
| `PLANNOTATOR_EXPERIMENTAL` | Experimental features, each **off by default** (owner, approval "inbox-decision-mode"). A comma list of feature names: a name listed turns that feature on, the name with a leading `-` turns it off (`-decision-mode`); names are trimmed and compared case-insensitively, unknown names are ignored, and a feature the variable does not name follows config.json `experimental` (`{ "experimental": { "decisionMode": true } }`), which the Inbox's Settings → Capabilities → Experimental writes (`POST /api/inbox/settings` `{ experimental: { decision_mode } }`; the switch is locked while the variable decides, and a save then answers `409 experimental_env_decides` and writes nothing, like Over your tailnet's lock). Resolved by `resolveExperimental(config, name, env)` in `packages/shared/config.ts`, whose small `EXPERIMENTAL_FEATURES` table maps each name to its config key (a fuller flag registry is a separate piece of work that wraps these); `saveConfig` merges `experimental` key by key (only when it is a plain object; a hand-edited non-object is replaced), so switching one feature keeps the others. Today one feature: `decision-mode` (see "Decision mode" under "Plannotator Inbox"). Read on every request, so a change applies at once. |
| `PLANNOTATOR_RELAY_URL` | The Inbox relay a new mailbox is made at (`packages/server/inbox-relay.ts`). Default `https://relay.plannotator.ai`. Proofs point it at a `wrangler dev` relay; tests at a closed loopback port. A mailbox, once made, stays at the URL `inbox/relay.json` names. |
| `PLANNOTATOR_PORT` | Fixed port to use. Default: random locally, `19432` for remote sessions. The Plannotator Inbox ignores it (and `PLANNOTATOR_REMOTE`): it always binds `127.0.0.1` on its last port or a random one; to reach it from your other devices use `plannotator inbox --tailscale` / `PLANNOTATOR_INBOX_TAILSCALE`; see "Plannotator Inbox". |
| `PLANNOTATOR_LIVE_PORT` | Live app proxy port or inclusive range, such as `19440-19447` (live app annotation, see "Live app annotation" under the Annotate Flow). Uses the first available port and always binds to `127.0.0.1`. For SSH forwarding, set `PLANNOTATOR_REMOTE=0`, fix the editor's port with `PLANNOTATOR_PORT` (it is random in local mode), and forward both the editor and proxy ports, keeping the same port numbers on each side. A range moves past ports that are in use or that this user may not bind (`EACCES`, a port below 1024 when not root); when none can be used the session fails to start with one line (`LiveProxyPortError` / `LiveProxyPortInUseError` in `packages/shared/live-proxy-port.ts`, vendored to Pi: the CLI exits 1, or 2 under a strict annotate gate, and the annotate server closes its editor listener first). An invalid value warns on stderr and uses a random port. Read by both transports (`packages/server/live-proxy.ts`, `packages/shared/live-proxy-node.ts`); never follows `PLANNOTATOR_PORT` or `PLANNOTATOR_REMOTE`. Default: random. |
| `PLANNOTATOR_URL_HOST` | Display-only hostname for advertised session URLs (issue #657), e.g. a Tailscale MagicDNS name or tailnet IP, so remote-mode links are reachable from another device instead of `http://localhost:<port>`. Host only — bare hostname, IPv4, or bracketed IPv6 (`[fd7a::1]`); the runtime-chosen port is always appended, and anything carrying a scheme, port, path, credentials, or whitespace warns once on stderr and falls back to `localhost`. Strictly display-only and remote-only: binding stays governed by `PLANNOTATOR_REMOTE`; a local session ignores the override (localhost is advertised and opened, since only loopback is bound) with a once-per-process stderr warning to set `PLANNOTATOR_REMOTE=1`, and spawned agent-review jobs keep a pinned `http://127.0.0.1:<port>` API URL so a tailnet-only hostname cannot break local jobs. The sentinel `auto` resolves the host from Tailscale once per process, at first use in a remote session: `tailscale status --json` → `Self.DNSName` (trailing dot stripped), falling back to the single `tailscale ip -4` CGNAT (100.64.0.0/10) address; detection failure warns once on stderr and falls back to `localhost`, and detection never changes binding — `auto` is as display-only as any explicit host. Can also be set via `~/.plannotator/config.json` (`{ "urlHost": "host" }` or `{ "urlHost": "auto" }`); the env var takes precedence, and an empty-but-set env var (`PLANNOTATOR_URL_HOST=`) suppresses a config-file `urlHost`. Default: unset (`localhost`). |
| `PLANNOTATOR_ALLOWED_HOSTS` | Extra hostnames the servers answer on, for the Host allowlist every plan, review, annotate, archive and goal-setup server (and the Plannotator Inbox) applies to every request (see "Host allowlist" under Server API). Comma list of hostnames; a leading dot (`.example.com`) also matches subdomains; `*` turns the check off. For proxies and tunnels that forward their own hostname (a reverse proxy, a Docker service name, a LAN DNS name in remote mode). Not needed for GitHub Codespaces or VS Code dev tunnels (their forwarders present `Host: localhost:<port>`) or for a code-server / Coder port proxy (recognized from `VSCODE_PROXY_URI`). Read once per server start. An entry named explicitly (exact or `.suffix`, never `*`) is also accepted as a page Origin by the cross-origin write guard, for a plain-HTTP reverse proxy that rewrites Host: name the proxy's public hostname here (read on each request; see "Cross-origin write guard" under Server API). Default: unset. |
| `PLANNOTATOR_BROWSER` | Custom browser to open plans in. macOS: app name or path. Linux/Windows: executable path. `--browser <value>` sets it for one run. A "none" value, `none` `false` `0` `off` `no` `true` `1` `:` (trimmed, any case), opens NOTHING, local or remote: no VS Code IPC, no Glimpse, no `BROWSER`, no system opener (`resolveBrowserIntent` in `packages/shared/browser-intent.ts`, vendored to Pi; `none` / `default` / `explicit`), for every caller (sessions, the Inbox, `sessions --open`, `t3 login`). The Bun CLI prints `  Not opening a browser (PLANNOTATOR_BROWSER=<value>).` under the ready line (`openBrowser` prints it itself for direct callers; `handleServerReady` never calls the opener then, and says nothing when the host opens the browser itself, `skipBrowserOpen`); Pi says it in its "opened" message and returns `notOpening` from `openBrowser`. `BROWSER` is different: hosts set it (Claude Code's agent view sets `BROWSER=true`), so its #756 values (`true` `false` `none` `0` `1` `:`) are still read as unset and the default chain runs. Every session prints `  Plannotator session ready: <url>` on stderr before any launch (`SESSION_READY_LINE_PREFIX`, `handleServerReady`), so nothing is lost by opening nothing. |
| `PLANNOTATOR_AI` | Set to `disabled` to disable Ask AI and the Review Agents / Guided Review execution surfaces, including provider and agent-job endpoints. Persisted guide data is retained and its server APIs remain available, but the in-app history browser is hidden while AI is disabled. External agents can still open reviews and submit annotations. The explicit annotate-mode agent terminal is separate and remains controlled by its own settings. Default: enabled. |
| `PLANNOTATOR_SHARE` | Set to `disabled` to turn off URL sharing entirely, including Guided Review share links (the review UI hides "Create share link", `POST /api/guide/:jobId/share` answers `403 { error: "sharing disabled" }`, and `plannotator guide share` refuses with exit 1). Default: enabled. Can also be set via `~/.plannotator/config.json` (`{ "share": "disabled" }`); the env var takes precedence. |
| `PLANNOTATOR_SHARE_URL` | Custom base URL for share links (self-hosted portal). Default: `https://share.plannotator.ai`. |
| `PLANNOTATOR_PASTE_URL` | Base URL of the paste service API for short URL sharing. Default: `https://plannotator-paste.plannotator.workers.dev`. |
| `PLANNOTATOR_CLAUDE_MOD` | Switch for the Claude Code mod (non-blocking plan review, annotate, code review and annotate-last, the `plannotator` tool, the take-over of agent-run Bash `plannotator` commands, plus Ask this session; see "Claude Code mod"). **Default: on** wherever Claude Code runs hooks modules (2.1.287+, interactive CLI sessions; the mod still stands down by itself in `-p` / SDK sessions and where `/bin/sh` is missing, i.e. Windows). Set to `0` / `false` / `off` / `disabled` to turn it off, which leaves the module inert (every hook passes through, no command or tool is registered, no Bash command is taken over, no environment is set) so the classic PermissionRequest hook and `/plannotator-*` skills run exactly as before; `1` / `true` / `on` force it on, and empty or unrecognized counts as unset (on). Can also be turned off via `~/.plannotator/config.json` (`{ "claudeCodeMod": false }`, read from the data dir); the env var takes precedence (`resolveClaudeCodeMod` in `packages/shared/config.ts`, mirrored by `apps/hook/hooks/mod/enabled.ts` because a hooks module can import only its own files; `enabled.test.ts` keeps them in step). Read once when Claude Code starts, so a change applies to the next session start. Set it in the shell that starts Claude Code or in Claude Code's `settings.json` `env`. The plugin installs from the repo and the `plannotator` binary updates separately, so the mod also runs against older binaries; see "Version skew" in the mod section for what degrades. |
| `PLANNOTATOR_AGENT_TOOL` | Switch for the `plannotator` agent tool (`packages/shared/plannotator-tool.ts`) on the hosts that register it. **Default per host** (owner's call, one table: `AGENT_TOOL_DEFAULTS` in `packages/shared/config.ts`): **on for the Claude Code mod** (the tool is deferred behind tool search there, so it costs about its name until used), **on in Oh My Pi** (host key `oh-my-pi`: the Pi extension running inside OMP, which lists an extension tool as one `xd://plannotator` line of its system prompt, measured on OMP 18.10.2 at 212 characters, about 50 tokens, with the tools array unchanged, and loads the schema only when the model reads it; owner's call 2026-10-12, #1814), **off on Pi and OpenCode 2** (a full tool definition in every request: 2,993 bytes, about 800 tokens; 2,901 bytes, about 780 tokens, measured on Pi 0.84.4 before #1907 added review's `gate`, which grew the entry Pi sends by 92 bytes). The Pi extension tells OMP from Pi by its ExtensionAPI object (`detectPiHost` in `apps/pi-extension/pi-host.ts`: OMP's carries `arktype`, its omptype schema builder, and `pi`, its SDK module; Pi's has neither) and resolves with that host; the Inbox tool is not affected (it registers as `pi` in OMP too, `InboxToolHost`). `1` / `true` / `on` turn it on and `0` / `false` / `off` / `disabled` turn it off on every host, overriding the host default in both directions; empty or unrecognized counts as unset. Off removes ONLY the tool: the `/plannotator-*` slash commands, plan review, Ask this session and (Claude Code) the take-over of agent-run Bash `plannotator` commands, which adds nothing to the model's context, are unchanged, and an agent that wants Plannotator runs the CLI. Can also be set via `~/.plannotator/config.json` (`{ "agentTool": true }` / `false`, read from the data dir; allowlisted, boolean only, on `POST /api/config` in both runtimes, which refuses a cross-origin write with `403` on every plan, review and annotate server: `isSameOriginOrNoOrigin` in `packages/shared/request-origin.ts`, the guard every plan, review, annotate and goal-setup server now runs on EVERY `POST` / `PUT` / `PATCH` / `DELETE` before routing (see "Cross-origin write guard" under Server API), and that these routes also run themselves: review progress, guide share links, the CallDiff install, annotate's Edit Mode `/api/source/save`, `/api/open-in` on the annotate and review servers, `/api/save-notes`, `/api/plan/vscode-diff` and the review server's `/api/agents/jobs` launch and kill, since a page on another site can send a preflight-free `text/plain` POST. It passes a request with no Origin, an Origin naming the request host, or the browser's own `Sec-Fetch-Site: same-origin`, and refuses `Origin: null`, and `same-site` or `cross-site` fetch metadata whatever Origin says (a request with no Origin included). The `Sec-Fetch-Site` leg is what lets the VS Code panel write: its cookie proxy serves the page from `http://127.0.0.1:<proxy port>` and rewrites Host to the server, so Origin and Host differ. Before it, `/api/review-progress` and `/api/call-flow/install` were already refused in the VS Code panel (silently: the client ignores the failure); they work there now too. `cookie-proxy.ts` additionally re-anchors an Origin equal to its own origin onto the upstream, for browsers without Fetch Metadata; `vscode-proxy-writes.test.ts` (Bun and Pi) covers both shapes); the env var takes precedence (`resolveAgentTool(config, env, host)` in `packages/shared/config.ts`; the mod's mirror `resolveAgentToolEnabled` lives in `apps/hook/hooks/mod/enabled.ts`, kept equal to the claude-code row by `enabled.test.ts`). `getServerConfig(gitUser, agentToolIntegration)` advertises it for a later Settings toggle / one-time "turn it on" offer, but only where the integration that started the server registers the tool: `agentToolHost` is the session-bridge host, not the agent origin (Bun: `agentToolHostForServer` in `packages/server/ai-runtime.ts`, an in-process bridge's host, else `launchingSessionHost()`, the `PLANNOTATOR_SESSION_BRIDGE_HOST` the Claude Code mod / OpenCode 2 plugin hand the CLI, read once at startup and kept in remote mode, where Ask this session is off but the integration still started the session; Pi: the extension's own host, `pi` or `oh-my-pi` (`currentPiHost()`, recorded by the extension at load), since its servers run inside the extension). With no such integration (the classic Claude Code hook, the mod off, `-p`, Windows, OpenCode 1, a person at a shell) every `agentTool*` field is absent except an `agentTool` config.json sets. Known gap: OpenCode 2's embedded plan review passes its bridge only when the host has `session.generate`, so on an older V2 host that one review advertises nothing. Fields: `agentTool` (the config value, or the host default while unset), `agentToolConfigured` (config.json holds an explicit choice), `agentToolEnv` (present when the env var overrides the file) and `agentToolEnabled` (the effective value, for the NEXT session). **Read once per session start and never mid-session**, because the tool list is part of every request's prompt prefix and changing it would miss the prompt cache: a change applies to the next session (Pi: the next session or `/reload`; Oh My Pi: the next OMP start, the conservative promise the Settings row makes; OpenCode 2: the next OpenCode start; Claude Code: the next Claude Code start). |
| `PLANNOTATOR_INBOX_TOOL` | Switch for the Plannotator Inbox's `plannotator_inbox` agent tool and its reply wake on the hosts that register it (the Claude Code mod, see "The Plannotator Inbox" in the mod section; Pi and OpenCode, see "Agent connections" in "Plannotator Inbox"; OpenCode 1 gets the tool without the wake). **Compressed app page for network sessions (#1617):** remote-mode and `--tailscale` sessions serve the single-file app HTML compressed, negotiated on `Accept-Encoding` (brotli q5, else gzip 6), with `Vary: Accept-Encoding`. Browsers advertise `br` only to HTTPS and localhost origins, so direct plain-http remote mode is served gzip and `--tailscale` (HTTPS) brotli; each server prewarms that likely encoding at start and compresses the other lazily, cached per process (bounded to 4 bodies, which persist for the life of long-lived Pi/OpenCode hosts). Plain local sessions serve the page exactly as before, because on loopback compression only added latency. One shared helper, `packages/shared/app-html.ts` (vendored to Pi), serves every app-HTML route in both runtimes; API responses are never compressed. The single-file builds also drop KaTeX's `woff`/`ttf` fallbacks (`build/katex-woff2-only.ts`); every supported browser loads `woff2`.

**Tailnet sessions (`--tailscale`):** `plannotator review --tailscale` (also `annotate` and `annotate-last`/`last`; other subcommands reject the flag with a clear error; Bun CLI only, not mirrored to Pi) publishes the session over the user's tailnet instead of remote mode: the server stays **loopback-bound** and the CLI orchestrates `tailscale serve --bg --https=<port> http://127.0.0.1:<port>`, so devices on the tailnet reach the session over HTTPS while nothing listens beyond localhost and nothing is ever public (serve, never funnel). The advertised HTTPS URL prints on stderr with a terminal QR code (TTY only), and a publishing failure exits `1` — or `2` under a strict annotate gate (`--require-approval` / `--result-file`), where `1` is reserved for "the reviewer did not approve" and a publish failure is a startup failure like any other — with an actionable message instead of leaving the loopback server hanging (CLI missing, daemon down or logged out, unparsable `serve status` output — which fails closed, or no serve URL matching the session port). A pre-existing serve mapping on the chosen port — background or foreground session, which Tailscale prefers — aborts rather than being stolen, and mappings on other ports are never touched. Mappings the process creates are cleaned up on normal exit and on SIGINT/SIGTERM/SIGHUP (all routed through `process.exit` so exit handlers run; the SIGHUP route is installed by `enableTailscaleServe` only once a mapping exists — an unconditional SIGHUP listener would override the ignored disposition `nohup` depends on, so plain non-tailscale sessions keep no SIGHUP listener and `nohup plannotator review &` survives terminal close); a failed teardown retries once and then warns with the exact manual command, and a hard kill (SIGKILL) or reboot can leave the mapping — `tailscale serve --bg` state persists — so remove it with `tailscale serve --https=<port> off`. Combined with `PLANNOTATOR_REMOTE`/SSH detection, `--tailscale` wins and forces local mode with a stderr notice — the wide `0.0.0.0` bind would only broaden exposure (`urlHost` is also suppressed for the run; the advertised URL comes from serve). `tailscale serve` forwards the browser's own Host header (the MagicDNS name), so the CLI adds the serve hostname to the server's Host allowlist once serve reports it (see "Host allowlist" under Server API). The annotate agent terminal is **off by default** in `--tailscale` sessions, exactly like remote mode, because the session is reachable across the tailnet and the PTY token is not an auth boundary; enable it with `PLANNOTATOR_AGENT_TERMINAL_REMOTE=1`. Open-in (`/api/open-in`, `/api/open-in/apps`) is off outright in `--tailscale` sessions, as in remote mode, with no override: a launch would open an app on this machine for whichever tailnet device sent it. Orchestration lives in `packages/server/tailscale-serve.ts` on shared parsers in `packages/shared/tailscale.ts`.

**"Ask this session" over the tailnet, for the machine's owner (#2166; owner-approved: "tailscale option, Ask this session on, your Tailscale login only, invisible to you").** A `--tailscale` session started by a host with a pull bridge (the Claude Code mod, the OpenCode 2 plugin) KEEPS the bridge token (it used to discard it; `discardEnvPullSessionBridgeConfig` still exists but the CLI no longer calls it), and every review and annotate server started with `tailnetPublished` passes `tailnet: sessionTailnetGate` to `createAIRuntime` (`packages/server/session-tailnet.ts`). Who sent a request is decided per request by `tailnetAudience` (`packages/shared/tailnet-audience.ts`, pure), on the session's own port, by the marks only `tailscale serve` sets (it deletes `Tailscale-User-Login`, `Tailscale-Headers-Info` and `Tailscale-Funnel-Request` from what a client sends, sets its own, and always sets `X-Forwarded-For` to the peer's address, so a request through serve can never read as local; Host is never evidence): `local` (no mark: this machine, the same trust as any local session), `owner` (through serve, not funnel, every `X-Forwarded-For` entry a Tailscale address, 100.64.0.0/10 or fd7a:115c:a1e0::/48, so a local reverse proxy that passes client headers on cannot make a forged login the owner, and the login, RFC 2047 decoded, is the one that owns this machine, the Inbox's `checkTailnetIdentity`), `peer` (anything else through serve: another login, a tagged device, funnel, or an owner nobody could read). With a bridge: `local` and `owner` are served the normal endpoints, where the bridge is the only Ask AI provider (`owner` may create and query a bridge session only with the served MagicDNS name and port as Host, or the bare name when the served port is 443, which a browser omits, `sessionTailnetAskAllowed`; `local` keeps the loopback-Host rule); `peer` is served a SECOND `createAIEndpoints` over the SDK providers only, with its own `SessionManager` and no bridge, i.e. exactly what a `--tailscale` session always gave everyone (chosen over refusing a peer's writes because a teammate on a shared tailnet keeps the review, comments, decisions and SDK Ask AI as before; only the agent session, which runs commands here, is withheld). The bridge's own poll and event routes answer `local` only (a 404 through serve whatever Host is claimed), and the host-control routes (`/api/host/status`, `/api/host/close`, now enabled under `--tailscale` because the token is kept, so the mod's `list` and `close` work there) answer a request through serve as `404 host_control_disabled` (`fromThisMachine` on `handleHostControl`). Writes stay behind the cross-origin write guard (a page on another `*.ts.net` machine is `same-site`). The owner is read once, in `handleTailscaleReady`, only when a bridge exists and AI is on: `tailscale status --json` (`readTailnetOwner`: Self.UserID -> LoginName, none on a tagged machine), before the mapping is made; the served name after it. A plain `--tailscale` run with no bridge asks Tailscale nothing more than before. stderr says `Ask this session: on here, and over your tailnet for <login> only.` or `on this computer only (<reason>)`. The ready line gains `tailnet: { ask }` for every `--tailscale` session (`setServerReadyTailnet`; `ask` true when the owner's tab gets the bridge), which is how a host tells a CLI that keeps the bridge from an older one. A local reverse proxy that sends a non-loopback `X-Forwarded-For` to a `--tailscale` session reads as a peer there. Without `--tailscale` none of this runs (no gate, no second endpoints, no `tailnet` field), with one hardening that applies to EVERY Bun session: a request carrying Tailscale's marks (`cameThroughTailscale`: a serve header, or an `X-Forwarded-For` entry that is a Tailscale address; a LAN proxy's address is not) never asks the agent session, polls the bridge, or reaches host control, since a `--bg` mapping a crashed `--tailscale` session left behind can point at a later local session on the same port. Remote mode is unchanged (still no bridge). The Pi servers do not carry this hardening (they never publish over the tailnet). Tests: `apps/hook/server/tailscale-ask-cli.test.ts` (the CLI as a process with a scripted `tailscale`: the owner asks end to end through serve, a guest and funnel get SDK Ask AI, the bridge and host control refuse serve, the served Host check, a tagged machine, review and annotate, and a local session and a bridge-less `--tailscale` run unchanged), `packages/shared/tailnet-audience.test.ts`.

The Plannotator Inbox has its own `plannotator inbox --tailscale` (owner-only, persistent, a separate listener; see "Over your tailnet" under "Plannotator Inbox"), which this per-session flag never handles (`index.ts` leaves `--tailscale` to the `inbox` subcommand).

**The crash window (both `--tailscale` forms).** A `--bg` serve mapping outlives its process. After a SIGKILL, an OOM kill or a reboot it keeps pointing at a loopback port that nothing holds any more, and any local server that later binds that port is published to the tailnet until the mapping is removed. `review` / `annotate` sessions have no record to recover from: remove it with `tailscale serve --https=<port> off`. The Inbox records its mapping in `inbox.json` before making it, and every Inbox start (and `uninstall --purge`) removes a recorded mapping whose proxy port is not its own, so the window closes at the next start; until then it is open. A loopback-only proxy target that no other process can take (a unix socket) is the follow-up that closes it.
