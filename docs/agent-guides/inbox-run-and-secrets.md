## Run and Secret: commands the person runs, secrets they keep

Two Inbox-only blocks an agent writes in a message (owner's picks, 2026-11-17: "Run here and the Secret box together"; "anywhere I am signed in to my own Inbox"; "never burden me … no unnecessary barriers"). No switch, no confirmation, no Steps list: a card per block, one press. Bun only: the Pi server has no Inbox, so there is nothing to mirror there. Each protection below prevents a named fault; none adds a step for the person.

### The blocks

- `:::run` (`packages/core/inbox-run-blocks.ts`, `parseInboxRunBlocks`): first non-empty line the title, optional `Folder: <path>` (relative to the message's project folder; `~/…` under home; absolute as written), optional `Uses: NAME, OTHER` (saved secrets a program reads from its environment itself), every other line outside the fence the why, and exactly one fenced code block, the command byte for byte. No fence, or two, and it is not a run block: plan review and the window draw it as a callout, each fence with its Copy, which is also how a viewer that does not know the block shows it. Key `r-` + hash8 of the command (`-2`… for a repeat in one message). The title, why and `Where:` lose direction marks and invisible characters before they are drawn (`inboxRunPlainWords`).
- `:::secret`: first line the name (`^[A-Z][A-Z0-9_]{1,63}$`, backticks or a `$` around it dropped), optional `Where: <url or place>` (a URL becomes "Find it on <host>"), other lines the why.
- Names a secret may not have (`INBOX_SECRET_REFUSED_NAMES` and `INBOX_SECRET_REFUSED_PREFIXES`, the one list the parser, the card and the server read): names programs read to decide what runs and how it starts, or that every command needs as they are. A value saved under one could change what a command does (a shell, its startup files, a preloaded library, an interpreter's options, git's helpers) or break every run. Exact: PATH, HOME, SHELL, USER, LOGNAME, PWD, OLDPWD, IFS, CDPATH, ENV, BASH_ENV, ZDOTDIR, PROMPT_COMMAND, PS1, PS2, PS4, TMPDIR, TERM, LANG, TZ, DISPLAY, SSH_AUTH_SOCK, EDITOR, VISUAL, PAGER, MANPAGER, BROWSER, SSH_ASKPASS, SUDO_ASKPASS, NODE_OPTIONS, NODE_PATH, NODE_EXTRA_CA_CERTS, RUBYOPT, RUBYLIB, JAVA_TOOL_OPTIONS, JDK_JAVA_OPTIONS, CLASSPATH, LUA_INIT, LUA_PATH, LUA_CPATH, GEM_HOME, GEM_PATH, BUNDLE_GEMFILE, GOFLAGS, CARGO_HOME, RUSTC_WRAPPER, RUSTFLAGS, CC, CXX, LESSOPEN, LESSCLOSE, COMSPEC, PATHEXT, SYSTEMROOT, WINDIR, PSMODULEPATH, USERPROFILE, APPDATA, LOCALAPPDATA. Prefixes: LD_, DYLD_, PYTHON, PERL, GIT_, NPM_CONFIG_, BASH_FUNC, BUN_, DENO_, LC_, XDG_, PLANNOTATOR_. (Lower-case names such as `npm_config_*` never fit the name rule.) Such a block draws as a card that says "NAME can't hold a secret: programs read it to decide how they start, so a value saved under it could change what every command runs. Ask <agent> for another name." with no field; the route refuses a save (`422 secret_name_refused`).
- Hidden characters (`inboxRunHiddenChar`, `inboxRunBlockHidden`): a command may hold line breaks, tabs and plain spaces; any other control, format (bidi, zero-width, BOM, tag characters), odd space, private-use, unassigned character, variation selector, filler, braille blank (U+2800), Khmer inherent vowel (U+17B4/5) or Mongolian selector (U+180B–F) refuses it, and so does one in its `Folder:`. The card computes this from the block itself (so Copy is never offered before, or without, the computer's answer), shows the command or folder with each one as `⟨U+202E⟩`, says what and where in plain words, and has no Run, no Copy and no Open in terminal. The route refuses it too (`422 run_hidden_char`). Letters from an alphabet with Latin look-alikes (Cyrillic, Greek, Armenian, Cherokee) are said in a quiet line (`inboxRunLookalikes`), not refused.

### What Run does

- The press sends `{ key, op: "start", command }`; the server parses the stored message (never the request's text) and runs that block only when `command` is its exact bytes (`409 run_changed` otherwise: a stale or forged page).
- The run exists from the press on (`packages/server/inbox-run.ts`); then it reads what it needs (`prepare`): the login-shell env and the secrets it names, at once. A Stop during that read ends it before anything starts.
- The program (`packages/server/inbox-run-shell.ts`), chosen from the login env alone, never from a saved value: the login `$SHELL` when it is sh, bash, zsh, dash or ksh, else `/bin/bash`, else `/bin/sh` (a fish or nushell user still gets POSIX meaning), with `-c <command>`. Windows: Git Bash when Git for Windows is installed (found as Claude Code finds it: `CLAUDE_CODE_GIT_BASH_PATH`, beside `cmd\git.exe` on PATH, the install folders), else PowerShell 7 (`pwsh`), else Windows PowerShell, with `-NoProfile -NonInteractive -ExecutionPolicy Bypass -Command` and `$NAME = $env:NAME;` set first for each secret it gets, so the same `$NAME` text reads it. A command written for a Unix shell that would land in PowerShell gets a quiet line on the card (`inboxRunShellNote`: "This is written for a Unix shell, and <computer> has no Git Bash, so it would run in PowerShell, where it may not work. Install Git for Windows, or open it in your terminal."); Run stays.
- The login env is read once and kept (`keptLoginEnv` in `inbox-run-setup.ts`): the first card on screen reads it, a press uses the kept copy at once, and a copy older than five minutes is read again behind it. A sandboxed test Inbox uses its sandbox env.
- Secrets: a run gets only the saved secrets it names, `$NAME`, `${NAME}` or `$env:NAME` in its command, or its `Uses:` line (`inboxRunSecretNames`), and of those only names that are secrets here (saved, asked for in a `:::secret` of the thread, or on `Uses:`). The card shows them in a quiet "Uses NAME" line, and a field ("Needs NAME") for each not saved yet. The values are read from the vault in parallel, each bounded to 10 s; a saved name that cannot be read (a locked or denied Keychain, a keyring that does not answer, a value gone) means the run does not start, and the card and the agent read "Couldn't read NAME from your Keychain. Unlock it if it asks, then run again." with Run again.
- Its own process group (POSIX `detached`; Windows `taskkill /T`, started without waiting), stdin a pipe held open.
- Output: stdout and stderr interleaved as they arrive, ANSI codes stripped, a `\r` progress line kept at its last states, lines capped at 2,000 characters, the last 500 lines kept ("Showing the last N of M lines"). A line with no end is held to its head (`RunLineBuffer`: each piece looked at once, at most 4,000 characters pending), so a binary on stdout or a long `\r` progress bar costs bounded memory and linear time. Hidden as `••••`: the secrets the run gets (a value of 4+ characters wherever it is, a shorter one where it stands as a whole word; the first characters of one that ends the line still being written), and the login env's credential-like values (names with KEY, TOKEN, SECRET, PASSWORD, CREDENTIAL, AUTH…; not paths), since the report goes to the agent. Not in reach of hiding, and accepted: a value the command encodes (base64, hex), splits or writes to a file.
- Waiting for typing: quiet 2 s on a prompt-like last line (ends in `:`/`?`/`>`, or says password, y/n, press enter…) sets `waiting_for_input`; the card says so and makes Open in terminal primary. A run that fails saying it needs a terminal (`no tty present`, `a terminal is required`…) sets `needs_terminal`. No terminal emulator.
- Stop: TERM to the group, KILL after 2 s. When the command exits, what it left in its group is killed (`&`, `nohup`: the guide tells agents a run cannot leave a server going; on Windows, children of a leader that already exited can outlive it). A message gone (thread or project deleted, any path) stops its runs within a second (a sweep while anything runs) and sends nothing. One run per block at a time (`409 run_running`); Run again after it ends.
- The Inbox quitting ends each run as "the Inbox closed": its group killed, the agent told ("The Inbox closed while it ran, after N s, and the command was stopped with it…"), the card "Stopped: the Inbox closed after N s". An Inbox that dies (a crash, a kill) finds the unfinished run in `inbox/runs.json` when it starts again and tells the agent once ("The Inbox stopped while it ran, so its result was not recorded; it may have gone on by itself…"); the card reads "The Inbox stopped while this ran".
- `inbox/runs.json` (0600, `inbox-run-journal.ts`): each block's last run as the card shows it (state, exit code, times, the last 60 lines with values already hidden), so a card is not idle after a restart. Never a value.
- Open in terminal (`op: "terminal"`): Open in's launcher (`openWithApp`) opens the first installed of Ghostty, iTerm2, Warp, Terminal, PowerShell in the folder on the computer that owns the thread, and the server puts the command on that computer's clipboard (pbcopy; PowerShell `Set-Clipboard`; wl-copy, xclip or xsel), the text on stdin. The answer says whether it did (`copied`), and the card says "The command is on its clipboard: paste it there." or "Copy the command from this card and paste it there." Never types into the terminal.
- The result goes to the agent at once: `store.appendPersonNote` writes a person reply to the run's message (`inboxRunReportText`: "Command you asked the person to run: …", how it ended, the last 60 lines in a fence the output cannot close), delivered like any reply (the wake). The thread shows it, so the person sees what the agent got.

### Secrets

- Values: `packages/server/inbox-secret-vault.ts`, one interface (`get`, `set`, `remove`) and a `VaultRun` seam: macOS `security -i` with `add-generic-password -U -s plannotator-inbox -a <project id>:<NAME> -X <hex>` on stdin (read with `find-generic-password -w`, removed with `delete-generic-password`, exit 44 "no such item" counts as removed); Linux `secret-tool store/lookup/clear` with the value on stdin, only with `DBUS_SESSION_BUS_ADDRESS` and `secret-tool` on PATH, falling back to the file when the keyring refuses; Windows DPAPI for the account through PowerShell (value on stdin, the protected blob in `inbox/secrets/<account>.dpapi`); elsewhere `inbox/secrets/<account>` (folder 0700, file 0600, "saved to a file only you can read"). A sandboxed test Inbox always uses the file in its own data dir. No value on a command line; errors are scrubbed of the value (and its hex).
- A value is one line, at most 8,192 characters, with no control character (output loses those before values are hidden in it, so one could show).
- Index: `inbox/secrets.json` (0600), per project id: `{ name, saved_at, store }`. No part of a value (not even its last characters: the read answers any local process without a press). No value is ever in it, in the store, in a note, a log line or a read.
- Save writes a person note "Saved NAME on this computer. A :::run in this project that names $NAME in its command, or has `Uses: NAME`, gets it; its value is never shown to you." (Replace: "Replaced …"); Remove writes none. Remove that the vault refuses answers `500 secret_not_removed` with its words, and the name stays listed.
- A project that is gone: its secrets leave the vault and the index when the Inbox starts (`secrets.prune`).
- The field: `type="password"` outside any `<form>`, no `name`, `autocomplete="off"` and the managers' ignore marks (`data-1p-ignore`, `data-lpignore`, `data-bwignore`, `data-form-type="other"`), so the browser does not offer to save the value as the site's password and sync it; a manager the person calls on can still fill it. Enter saves. Cleared after Save; nothing kept in the window.

### Who may press

`packages/server/inbox-run-routes.ts`, `pressed()`: this computer's window or the owner's over the tailnet (`isWindowRequest`: the page's Origin, this Host, this run's serverSession; the tailnet gate already refused every other account), a paired phone through the device door, a linked machine's press in a window there (`door.window`). An agent's MCP connection, its `plannotator inbox` calls and a bare curl get `403 window_only`. The read refuses another site (`isCrossSiteRequest`). No route answers a value. Both POSTs are rule 8 `now` writes: forwarded to a linked machine at once from a window there or not at all, never held in the outbox (a value is never written to it). The door records a POST's answer, never its body, and these answers are `{ ok: true }` (Open in terminal: also the app's name and `copied`).

### The window

- `packages/inbox/parts/RunBlocks/` (`RunCard`, `SecretCard`, `SecretField`, `RunOutput`, `RunBlock`), CSS `runBlocks.css`. Drawn through MessageBody's `renderRunBlock` (agent messages only), found by the block's opening line.
- State: `packages/inbox/data/runStore.ts` reads `GET …/run` once per message, every 500 ms while a run starts or runs, and on focus; a phone or a linked machine reads the same route on the owning machine, so it sees the same live card.
- The run's state is announced politely to screen readers as it changes (not each second's count); the card's label is its title without markdown marks.
- Desktop, 390 px phone (44 px targets, a 16 px field so the phone does not zoom), dark and light by the theme's tokens. No new keyboard shortcuts.

### What agents are told

`packages/core/inbox-run-guide.ts`. send_message's `body` description (inbox-mcp.ts) carries the short `INBOX_RUN_TOOL_TEXT` (under ~600 characters: every tool listing carries it), which points to `plannotator inbox --help`. The help ("Commands the person runs, and secrets") and `/llms/inbox.md` carry the whole `INBOX_RUN_GUIDE` with `INBOX_RUN_EXAMPLE` and `INBOX_SECRET_EXAMPLE`. The Claude Code mod's bundled tool list (`apps/hook/hooks/mod/inbox-default-tools.ts`) has the short text byte for byte.

### Accepted, not defended

A program running as the person on this computer can read the keychain item or the file as the Inbox does, and can imitate a window (as for every window-only write, see `inbox-launch.md`). An agent with its own shell can run commands without the Inbox; Run is for what it cannot or should not. Any process the person runs with a value in its env can send it anywhere; a run gets only the values its own bytes name, which the person sees before pressing.
