## Run and Secret: commands the person runs, secrets they keep

Two Inbox-only blocks an agent writes in a message (owner's picks, 2026-11-17: "Run here and the Secret box together"; "anywhere I am signed in to my own Inbox"; "never burden me … no unnecessary barriers"). No switch, no confirmation, no Steps list: a card per block, one press. Bun only: the Pi server has no Inbox, so there is nothing to mirror there. Each protection below prevents a named fault; none adds a step for the person.

### The blocks

- `:::run` (`packages/core/inbox-run-blocks.ts`, `parseInboxRunBlocks`): first non-empty line the title, optional `Folder: <path>` (relative to the message's project folder; `~/…` under home; absolute as written), optional `Uses: NAME, OTHER` (saved secrets a program reads from its environment itself; names split on spaces, commas, semicolons and bars, a `$`, `${}`, matching quotes or backticks, or a trailing period dropped, `and`/`or` skipped; a word that is not a name, or a refused one, stays in `uses_unusable` and the card says it gives the run nothing), every other line outside the fence the why, and exactly one fenced code block, the command byte for byte. No fence, or two, and it is not a run block: plan review and the window draw it as a callout, each fence with its Copy, which is also how a viewer that does not know the block shows it. Key `r-` + hash8 of the command (`-2`… for a repeat in one message). The title, why and `Where:` lose direction marks and invisible characters before they are drawn (`inboxRunPlainWords`).
- `:::secret`: first line the name (`^[A-Z][A-Z0-9_]{1,63}$`, backticks or a `$` around it dropped), optional `Where: <url or place>` (a URL becomes "Find it on <host>"), other lines the why.
- Names a secret may not have (`INBOX_SECRET_REFUSED_NAMES` and `INBOX_SECRET_REFUSED_PREFIXES`, the one list the parser, the card and the server read): names programs read to decide what runs and how it starts, which code or certificates they trust, or that every command needs as they are. A value saved under one could change what a command does (a shell, its startup files, a preloaded library, a config that runs a program, an interpreter's options, git's helpers, a CA bundle) or break every run. Exact: PATH, HOME, SHELL, USER, LOGNAME, PWD, OLDPWD, IFS, CDPATH, ENV, BASH_ENV, ZDOTDIR, PROMPT_COMMAND, PS1, PS2, PS4, TMPDIR, TERM, LANG, TZ, DISPLAY, SSH_AUTH_SOCK, EDITOR, VISUAL, PAGER, MANPAGER, BROWSER, SSH_ASKPASS, SUDO_ASKPASS, RSYNC_RSH, NODE_OPTIONS, NODE_PATH, NODE_EXTRA_CA_CERTS, RUBYOPT, RUBYLIB, JAVA_TOOL_OPTIONS, JDK_JAVA_OPTIONS, JAVA_HOME, JAVA_OPTS, MAVEN_OPTS, MAVEN_ARGS, GRADLE_OPTS, GRADLE_USER_HOME, SBT_OPTS, CLASSPATH, LUA_INIT, LUA_PATH, LUA_CPATH, GEM_HOME, GEM_PATH, BUNDLE_GEMFILE, GOFLAGS, GOTOOLCHAIN, RUSTC_WRAPPER, RUSTFLAGS, CC, CXX, LESSOPEN, LESSCLOSE, ELECTRON_RUN_AS_NODE, MAKEFLAGS, MAKEFILES, PHPRC, PHP_INI_SCAN_DIR, OPENSSL_CONF, OPENSSL_ENGINES, OPENSSL_MODULES, GCONV_PATH, KUBECONFIG, DOCKER_HOST, DOCKER_CONFIG, DOCKER_CONTEXT, AWS_CONFIG_FILE, AWS_SHARED_CREDENTIALS_FILE, CURL_HOME, WGETRC, GOSUMDB, GONOSUMDB, GONOSUMCHECK, GOINSECURE, SSL_CERT_FILE, SSL_CERT_DIR, REQUESTS_CA_BUNDLE, CURL_CA_BUNDLE, AWS_CA_BUNDLE, NODE_TLS_REJECT_UNAUTHORIZED, SSLKEYLOGFILE, COMSPEC, PATHEXT, SYSTEMROOT, WINDIR, PSMODULEPATH, USERPROFILE, APPDATA, LOCALAPPDATA. Prefixes: LD_, DYLD_, PYTHON, PERL, GIT_, NPM_CONFIG_, BASH_FUNC, BUN_, DENO_, LC_, XDG_, DOTNET_, COREHOST_, COR_ (not CORS_), CORECLR_, COMPLUS_, CARGO_, RUSTUP_, PLANNOTATOR_. A name caught only by a prefix is a secret's after all when it ends in `_TOKEN`, `_TOKENS`, `_KEY`, `_API_KEY`, `_SECRET` or `_PASSWORD` (GIT_TOKEN, CARGO_REGISTRY_TOKEN, PYTHONANYWHERE_TOKEN; never a PLANNOTATOR_ name). Allowed on purpose: HTTP_PROXY, HTTPS_PROXY, ALL_PROXY, NO_PROXY and package-index URLs (PIP_INDEX_URL, UV_INDEX_URL, GOPROXY), which often carry the credential itself. (Lower-case names such as `npm_config_*` never fit the name rule.) Such a block draws as a card that says "NAME can't hold a secret: programs read it to decide how they start, so a value saved under it could change what every command runs. Ask <agent> for another name." with no field (a name that sets which certificates or checksum servers are trusted, SSL_CERT_FILE and its group, says instead "it changes which servers programs trust, so a value saved under it could change who every command talks to"; a Uses word that is not a name is quoted once, as written); the route refuses a save (`422 secret_name_refused`).
- Hidden characters (`inboxRunHiddenChar`, `inboxRunBlockHidden`): a command may hold line breaks, tabs and plain spaces; any other control, format (bidi, zero-width, BOM, tag characters), odd space, private-use, unassigned character, variation selector, filler, braille blank (U+2800), Khmer inherent vowel (U+17B4/5) or Mongolian selector (U+180B–F) refuses it, and so does one in its `Folder:`. The card computes this from the block itself (so Copy is never offered before, or without, the computer's answer), shows the command or folder with each one as `⟨U+202E⟩`, says what and where in plain words, and has no Run, no Copy and no Open in terminal. The route refuses it too (`422 run_hidden_char`). Letters from an alphabet with Latin look-alikes (Cyrillic, Greek, Armenian, Cherokee) are said in a quiet line (`inboxRunLookalikes`), not refused.

### What Run does

- The press sends `{ key, op: "start", command }`; the server parses the stored message (never the request's text) and runs that block only when `command` is its exact bytes (`409 run_changed` otherwise: a stale or forged page).
- The run exists from the press on (`packages/server/inbox-run.ts`); then it reads what it needs (`prepare`): the login-shell env and the secrets it names, at once. A Stop during that read ends it before anything starts.
- The program (`packages/server/inbox-run-shell.ts`), chosen from the login env alone, never from a saved value: the login `$SHELL` when it is sh, bash, zsh, dash or ksh, else `/bin/bash`, else `/bin/sh` (a fish or nushell user still gets POSIX meaning), with `-c <command>` (a POSIX argv is exact). Windows: Git Bash when Git for Windows is installed (found as Claude Code finds it: `CLAUDE_CODE_GIT_BASH_PATH`, beside `cmd\git.exe` on PATH, the install folders), else PowerShell 7 (`pwsh`), else Windows PowerShell. Windows hands a program one command line that Git Bash (and its `bin\bash.exe` wrapper) and PowerShell parse again, so the agent's text never goes on it: Git Bash runs the fixed `-c 'eval "$PLANNOTATOR_RUN_COMMAND"'` with the command in that variable, and PowerShell gets `-NoProfile -NonInteractive -ExecutionPolicy Bypass -OutputFormat Text -EncodedCommand <base64 of the UTF-16LE script>`, the script setting `$NAME = $env:NAME;` first for each secret it gets (so the same `$NAME` text reads it), except a name that is one of PowerShell's own automatic or preference variables (HOST, INPUT, ERRORACTIONPREFERENCE…), which the card says to read as `$env:NAME` there. A PowerShell run's stdin is closed at once (`closeStdin`: PowerShell spawned with a pipe waits for it to close), so it is not watched for a prompt. A command too long for one Windows command line (about 12,000 characters through -EncodedCommand; Git Bash's variable is capped likewise; `inboxRunTooLong`, or a spawn's ENAMETOOLONG) fails with "This command is too long to run here on Windows. Run it in your terminal." A command written for a Unix shell that would land in PowerShell gets a quiet line on the card (`inboxRunShellNote`: "This is written for a Unix shell, and <computer> has no Git Bash, so it would run in PowerShell, where it may not work. Install Git for Windows, or open it in your terminal."); Run stays.
- The login env is read once and kept (`keptLoginEnv` in `inbox-run-setup.ts`): the first card on screen reads it, a press uses the kept copy at once and reads it again behind itself (a tool installed a moment ago is there next press), and a copy older than five minutes is read again behind any use. A read where the login shell did not answer (`LOGIN_ENV_FALLBACKS`) never replaces a good copy; with none, it stands in for a minute from when it was first taken (presses go at once, each reading again behind), then a press waits for a fresh read once more. A sandboxed test Inbox uses its sandbox env.
- Secrets: a run gets only the saved secrets it names, `$NAME`, `${NAME}` or `$env:NAME` in its command, or its `Uses:` line (`inboxRunSecretNames`), and of those only names that are secrets here (saved, asked for in a `:::secret` of the thread, or on `Uses:`). The card shows them in a quiet "Uses NAME" line. One not saved here but set by the person's login shell is not waited for: the run gets their own value (hidden in output like a secret), and the card says "Uses NAME from your shell" (`from_shell`). One neither saved nor set holds Run back (the button is there but not pressable, the line "Needs NAME" the reason; the route refuses too, `409 run_needs_secret`, so nothing runs with it empty). Each such secret has one field per thread (`fields`): on its `:::secret` card when the thread asks for it, else on the first run card that needs it; the other cards say "Needs NAME" with "Save it above" or "Save it below" (where that field is on the page, its message open or folded to its line; "Save it in its card" when it is not drawn; looked at again whenever the thread changes around the card), which brings that field into view and focus; its message folded, it opens it first (the state's `field_at` names that message). On a run card the field's button is "Save and run" when it is the last one missing. A save refreshes every card on screen. The values are read from the vault in parallel, each bounded to 10 s. A value the store no longer has (removed in Keychain Access) leaves the list, and the run says "NAME is no longer in your Keychain (removed there). Save it again here, then run again"; one it would not give back says "Couldn't read NAME from your Keychain. Unlock it if it asks, then run again" when the store said it is locked or asked the person (or did not answer in 10 s), else its own words. Either way the run does not start.
- Its own process group (POSIX `detached`; Windows `taskkill /T`, started without waiting), stdin a pipe held open.
- Output: stdout and stderr interleaved as they arrive, ANSI codes stripped, a `\r` progress line kept at its last states, lines capped at 2,000 characters, the last 500 lines kept ("Showing the last N of M lines"). A line with no end is held to its head (`RunLineBuffer`: each piece looked at once, at most 4,000 characters pending, a `cut` flag on what it kept), so a binary on stdout or a long `\r` progress bar costs bounded memory and linear time. Whole values are hidden before a line is cut, and a value whose first characters end what is kept (a cut line, the line still being written) loses those too; a cut line always ends in "…". Hidden as `••••`: the secrets the run gets (a value of 4+ characters wherever it is, a shorter one where it stands as a whole word; the first characters of one that ends the line still being written), and the login env's credential-like values (`loginEnvCredentials`: names ending in KEY, TOKEN, SECRET, CREDENTIAL, AUTH, COOKIE, PAT or DSN after an underscore, or in PASSWORD, PASSWD, PASSPHRASE, APIKEY or PWD, so PGPASSWORD and MYSQL_PWD too, never GIT_AUTHOR_EMAIL; not paths; and the password in any value that is a URL with one, DATABASE_URL and friends, as written and decoded, unless it is the URL's user name or shorter than 8 characters), since the report goes to the agent. Not in reach of hiding, and accepted: a value the command encodes (base64, hex), splits or writes to a file.
- Waiting for typing: quiet 2 s on a prompt-like last line (ends in `:`/`?`/`>`, or says password, y/n, press enter…) sets `waiting_for_input` (POSIX and Git Bash; not PowerShell, whose stdin is closed); the card says so and makes Open in terminal primary. A run that fails saying it needs a terminal (`no tty present`, `a terminal is required`…) sets `needs_terminal`. No terminal emulator.
- Stop: TERM to the group, KILL after 2 s. When the command exits, what it left in its group is killed (`&`, `nohup`: the guide tells agents a run cannot leave a server going, on POSIX; on Windows, children of a leader that already exited can outlive it, and the guide says so). A message gone (thread or project deleted, any path) stops its runs within a second (a sweep while anything runs) and sends nothing. One run per block at a time (`409 run_running`); Run again after it ends.
- The Inbox quitting ends each run as "the Inbox closed": its group killed, the agent told ("The Inbox closed while it ran, after N s, and the command was stopped with it…"), the card "Stopped: the Inbox closed after N s". An Inbox that dies (a crash, a kill -9) finds the unfinished run in `inbox/runs.json` when it starts again, with its process id and start time and what it printed (written every 2 s while it prints). It looks whether the command still runs (POSIX: its process group is there and its leader started when the journal says, by `ps -o lstart` in UTC; or the leader is gone and a live process of the group started between the run's start and when the journal last wrote it down, `seen_at`, else unknown; `lostRunStillRunning`), and tells the agent once: still running ("…It is still running on their computer, and its card lets the person stop it…"), ended since, or (Windows, or `ps` cannot tell) "it may have gone on by itself". The card reads "The Inbox stopped while this ran", keeps the output, and says the same; when it still runs, its button is Stop. While a card says it still runs, each read of it looks again (at most every 5 s, `INBOX_RUN_LOST_RECHECK_MS`; `runs.recheck`), so once it definitely ends, or its pid goes to another program (another start time), the card says "It ended while the Inbox was away" with no Stop; one look that cannot tell keeps "still running" as it was (a Stop pressed then signals nothing). Found unknown at the restart, it says "It may still be running on {computer}." with no Stop. One last told "still running" that is found ended by itself (a card read, or the next start) is told once more, the same way: "…it has ended since." Stop (`runs.stopLost`) looks again right before the TERM and again before the KILL 2 s later and signals only a confirmed match; the agent hears "The person stopped it…". A `ps` that fails, or has no `-o lstart` (BusyBox), is unknown, never "still running" (`processStartedAt` asks `ps` about the Inbox's own process before taking silence for "gone").
- `inbox/runs.json` (0600, `inbox-run-journal.ts`): each block's last run as the card shows it (state, exit code, times, the last 60 lines with values already hidden; while it runs, its pid and start time), so a card is not idle after a restart. Never a value. In memory, the newest 20 finished runs keep their whole view; older ones keep only their record, and at most 300 past runs are kept.
- Open in terminal (`op: "terminal"`): Open in's launcher (`openWithApp`) opens the first installed of Ghostty, iTerm2, Warp, Terminal, PowerShell in the folder on the computer that owns the thread, and the server puts the command on that computer's clipboard (pbcopy; PowerShell `Set-Clipboard`; wl-copy, xclip or xsel), the text on stdin. The answer says whether it did (`copied`), and the card says "The command is on its clipboard: paste it there." or "Copy the command from this card and paste it there.", and, when the run uses saved secrets, that they are not set in that terminal (a name from the person's shell is, so it is not named). On Windows the clipboard script (`-EncodedCommand`) reads its stdin as UTF-8. Never types into the terminal. No terminal app, or one that did not open: `409 terminal_failed`, "No terminal app could be opened on {computer}." (the launcher's own words would name an app the person never chose).
- The result goes to the agent at once: `store.appendPersonNote` writes a person reply to the run's message (`inboxRunReportText`: "Command you asked the person to run: …", how it ended, the last 60 lines in a fence the output cannot close), delivered like any reply (the wake). The thread shows it, so the person sees what the agent got.

### Secrets

- Values: `packages/server/inbox-secret-vault.ts`, one interface (`get`: the value, null when the store has none, `InboxSecretReadError` with `locked` when it would not answer; `set`, `remove`) and a `VaultRun` seam: macOS `security -i` with `add-generic-password -U -s plannotator-inbox -a <project id>:<NAME> -X <hex>` on stdin (read with `find-generic-password -w`, removed with `delete-generic-password`, exit 44 "no such item" counts as removed); Linux `secret-tool store/lookup/clear` with the value on stdin, only with `DBUS_SESSION_BUS_ADDRESS` and `secret-tool` on PATH, falling back to the file when the keyring refuses; Windows DPAPI for the account through PowerShell (value on stdin, the protected blob in `inbox/secrets/<account>.dpapi`); elsewhere `inbox/secrets/<account>` (folder 0700, file 0600, "in a file only you can read"). A sandboxed test Inbox always uses the file in its own data dir. No value on a command line; errors are scrubbed of the value (and its hex).
- A value is one line, at most 8,192 characters, with no control character but a tab (output loses the others before values are hidden in it, so one could show; it keeps tabs).
- Index: `inbox/secrets.json` (0600), per project id: `{ name, saved_at, store }`. No part of a value (not even its last characters: the read answers any local process without a press). No value is ever in it, in the store, in a note, a log line or a read.
- Save writes a person note "Saved NAME on this computer. A :::run in this project that names $NAME in its command, or has `Uses: NAME`, gets it; its value is never shown to you." (Replace: "Replaced …"); Remove writes none. Remove that the vault refuses answers `409 secret_not_removed` with its words, and the name stays listed; a save it refuses, `409 secret_not_saved`.
- A project the person deletes takes its secrets with it (`store.onDeletion`, when exactly one project the routes knew is gone; never at start, so a store that loads empty or in part removes nothing).
- The field: `type="password"` outside any `<form>`, no `name`, `autocomplete="off"` and the managers' ignore marks (`data-1p-ignore`, `data-lpignore`, `data-bwignore`, `data-form-type="other"`), so the browser does not offer to save the value as the site's password and sync it; a manager the person calls on can still fill it. Enter saves. Cleared after Save; nothing kept in the window.

### Who may press

`packages/server/inbox-run-routes.ts`, `pressed()`: this computer's window or the owner's over the tailnet (`isWindowRequest`: the page's Origin, this Host, this run's serverSession; the tailnet gate already refused every other account), a paired phone through the device door, a linked machine's press in a window there (`door.window`). An agent's MCP connection, its `plannotator inbox` calls and a bare curl get `403 window_only`. The read refuses another site (`isCrossSiteRequest`). No route answers a value. Both POSTs are rule 8 `now` writes: forwarded to a linked machine at once from a window there or not at all, never held in the outbox (a value is never written to it). The door records a POST's answer, never its body, and these answers are `{ ok: true }` (Open in terminal: also the app's name and `copied`).

### The window

- `packages/inbox/parts/RunBlocks/` (`RunCard`, `SecretCard`, `SecretField`, `RunOutput`, `RunBlock`), CSS `runBlocks.css`. Drawn through MessageBody's `renderRunBlock` (agent messages only), found by the block's opening line.
- State: `packages/inbox/data/runStore.ts`, one entry per message. A card reads its state when it first comes on screen (one IntersectionObserver, 200 px margin; a card scrolled far away reads nothing). After that nothing is read while nothing runs: the Inbox sends windows `event: runs` (`{ message_ids }`, or `{ all: true }` for a secret saved or removed; data/runEvents.ts) when a card's state changed here (any window's press, a phone's, a run ending, a lost run found ended), and those cards read again (on screen now, others when they come on screen). Only a card on screen whose command starts or runs polls, every 500 ms; a linked machine's message (no event reaches this window from there) is read every 5 s while on screen. A hidden window reads nothing; focus, coming back, or the event stream reconnecting (`sharedEvents.ts`, not its first connect) reads the cards on screen. A Save or Remove in this window reads every card once when it lands, and the `runs` event it causes meanwhile is not read again. Measured (runCardLive.test.tsx): a thread of 50 idle run cards read about 17 times a second before (one GET per message every 3 s), and now once per card as it comes on screen, then nothing. React gets a stable `subscribe` per message, and a redraw's unsubscribe-then-subscribe never stops the poll; a tick after the last card of a message is gone (its thread closed) the entry is dropped, so a thread opened again reads fresh state. The run card's Stop is `data-run-card-stop` (not `data-run-stop`, which Rex's run line and the permission card use). A phone or a linked machine reads the same route on the owning machine, so it sees the same live card. Run, Stop and Run again are one button, so keyboard focus stays on it through each change (it is `aria-disabled` while a press is on its way, never `disabled`, and a second press is swallowed); after Save, focus moves to Replace, and after "Save and run" to the run's button. The card says "your Mac" (or "your PC") in this computer's own window and the computer's name on a phone or a linked machine; a folder under /private/tmp on macOS reads as /tmp. A saved Secret card's head says "Saved"; under it, the time and the store ("10:12 AM · in your Keychain"). The storage lines wrap with `text-wrap: pretty`. A long command scrolls inside its box (`max-height`, focusable), and fades at its foot while there is more below (`data-more`, the sidebar project list's hint), so a phone shows it scrolls; not while focused, so its focus ring shows whole. A lost run the person stopped here reads "Stopped" (its hint: "You stopped it…"). An agent message with a run or secret card stays open when the thread folds (`holdsRunCard` in core/inbox-folding.ts), like one with a pick not sent.
- The run's state is announced politely to screen readers as it changes (not each second's count); the card's label is its title without markdown marks.
- Desktop, 390 px phone (44 px targets, a 16 px field so the phone does not zoom), dark and light by the theme's tokens. No new keyboard shortcuts.

### What agents are told

`packages/core/inbox-run-guide.ts`. send_message's `body` description (inbox-mcp.ts) carries the short `INBOX_RUN_TOOL_TEXT` (617 characters: every tool listing carries it), which points to `plannotator inbox --help`. The help ("Commands the person runs, and secrets") and `/llms/inbox.md` carry the whole `INBOX_RUN_GUIDE` with `INBOX_RUN_EXAMPLE` and `INBOX_SECRET_EXAMPLE`. The Claude Code mod's bundled tool list (`apps/hook/hooks/mod/inbox-default-tools.ts`) has the short text byte for byte.

### Accepted, not defended

A program running as the person on this computer can read the keychain item or the file as the Inbox does, and can imitate a window (as for every window-only write, see `inbox-launch.md`). An agent with its own shell can run commands without the Inbox; Run is for what it cannot or should not. Any process the person runs with a value in its env can send it anywhere; a run gets only the values its own bytes name, which the person sees before pressing.
