## Inbox: accounts and usage

Settings → Accounts (`#settings/accounts`) shows this computer's Claude accounts and how much of each is used. It is step 1 of the approved "accounts-page" work (`.product/approved/accounts-page/`, not in this repo): read-only, this machine, Claude only. The sidebar's Usage row, its peek and the phone's sheet show the same read. Switching, linked machines, Codex, OpenCode and Pi are later steps, each with its own review.

The Inbox reads through claude-swap (`cswap`, MIT, installed by the person). Plannotator never reads, stores or moves credentials. `cswap list --json` may: to fetch usage it can refresh an expired login, spending a one-time token and writing the new one back, inside claude-swap, as typing `cswap list` does. There is no flag to skip that. There is no on/off setting: with `cswap` on the Inbox's PATH the page shows the accounts, and without it the page says how to install it. The lookup never goes outside that PATH, because a home lookup could reach a real `cswap` from a test, so a `cswap` installed after the Inbox started takes a restart, and the page says so.

**The read** (`packages/server/inbox-accounts.ts`). `GET /api/inbox/accounts` looks `cswap` up with `AgentEnvironment.which` and runs `cswap list --json` through `runUntilExit` (no shell, an argv array). **Never kill a run for being slow.** A kill between the token being spent and the new one being written loses the login, and `list` has no signal handler, so SIGTERM is no safer. At 20 s the caller is answered `timed_out` and the run goes on. Only a run still going at 2 minutes is killed with its process group, as truly stuck. The Inbox stopping leaves a run to finish, and then nothing enforces that limit. Do not change this to `runWithTimeout`, which is for agent CLIs. The answer is one of:

- `{ state: "not_installed" }`: not on PATH, or a run that exits 127, the shell's "command not found" (a shim whose tool is gone).
- `{ state: "failed", reason }`: `timed_out`, `run_failed` (a non-zero exit), `bad_output` (not the list), or `unknown_schema` (a `schemaVersion` this build does not read; the window says to update).
- `{ state: "accounts", accounts }`.

Rules for the read:

- **Named fields only.** Every value is picked by name in `account()` and `usageWindow()`: `number`, `alias`, `email`, `organizationName`, `isOrganization`, `active`, `usageStatus`, `usageError`, `usageRetryAt`, `usageAgeSeconds`, and `usage`'s `fiveHour`, `sevenDay` and `scoped` (each `pct`, `resetsAt`, `countdown`, `clock`; a scoped window also `name`). Never pass the raw JSON or spread a row: a field a later `cswap` adds must not reach the window. Unknown extra fields are ignored.
- **No `cswap` words.** Its stdout, stderr and error text are never logged, stored or answered. A failure is a fixed code. `usageStatus` and `usageError` pass only as single words, and the window maps them to its own text.
- **An API-key row has no address.** `cswap` gives it a placeholder (`api-key-3@token.local`). The server drops that, for the status `api_key` and for any `@token.local` address.
- **A window `cswap` does not report is null, never 0.** A `pct` that is not a finite number drops its window, and a `usage` with no window left reads as no reading. A window of 0% with no reset time is shown as reported: the mock hides it, and that difference is decided until a real Ultra reading exists. A window past its `resetsAt` reads as not reported: `cswap` serves its last good reading when a fetch fails, so the figure is from before that reset.
- **One run at a time, until it has really ended.** A caller during a run joins it and waits its own 20 s, so a Refresh after a `timed_out` can still get that run's answer, and never starts a second run. A new Inbox process knows nothing of a run the last one left going, so the two can overlap; claude-swap's own locks cover that. Nothing goes on disk and nothing polls: a run starts when a window, the page or the peek opens, or on Refresh.
- **A good answer serves 30 s.** `accounts` answers are kept in memory for `INBOX_ACCOUNTS_CACHE_MS`, so a reloading phone starts no process per load. Failures and `not_installed` are never kept, so a fix shows at once. Refresh sends `fresh=1` and skips it, because someone may have just run `cswap add`. This saves processes, not logins: `cswap` fetches, and so refreshes, at most once per its own 180 s (`SERVE_TTL_S`) however often it runs, and the login's safety rests on that floor. A test that changes the answer between reads passes `cacheMs: 0` or asks with `fresh=1`.

Who may read: the window's read guard (same origin, `403 cross_origin`), and a tailnet login that is not the owner's gets `403 owner_only` before anything runs. The owner reads over the tailnet like any window route. It is not on the device door, so no phone app, linked machine or relay reaches it. The Inbox is Bun-only, so nothing is in the Pi server.

**The window** (`packages/inbox/components/Accounts.tsx`, classes `ib-acct-*`; design of record `.product/approved/accounts-page/mock/`, not in this repo). The section comes after Machines in Settings. Machines comes first on the page: one row, this machine and the account it is using, shown only when an account is active. It is plain text with no control; Switch goes there in a later step. Accounts follow under Claude Code.

A row reads as the alias, else the start of the address, else "API key". Figures show used, as `cswap` reports them. Bars come only from reported windows, in three fixed columns so they line up down the list: week last at the right, the window before it in the middle, a third on the left. On a phone a row with three windows puts them under the name, in columns that still line up. Amber at 90% or more, judged on the rounded figure so a number and its colour never disagree. `usage: null` reads "No reading yet" in the week column with the reason in plain words under the name (`noReadingReason`, which knows `cswap`'s statuses). An API-key account reads "API key" there, unless that is already its name.

The full address, the organization and the reset times stay out of the row until it is opened. A row with none of them opens nothing and is no button. The organization shows on the closed row only when two rows would read the same, and the machine says the same, since one address can be saved under two organizations.

Personal Claude organizations are named after the address, and `isOrganization` is true for them too. So everywhere in the window, an organization containing the row's own address is no organization (`accountOrganization`): it would put the address on a closed row. Rows that then still read alike show `cswap`'s number quietly after the name, `mira #2`, only those rows.

A reading over 10 minutes old (`usageAgeSeconds`; `cswap`'s normal serve age is 3 minutes) means `cswap` could not refresh it, since it serves its last good reading when a fetch fails. The closed row's figures are muted and never amber, and the open row says "Last read 2h ago".

The owner's rule for this page: "Show me only what I need until I want to act. If I want to act take me to settings page. No narrative labels or redundant info." So it has no lede and no side notes, only the accounts and their numbers, and each other state is a few words. Keep it that way.

Not installed shows the mock's line, the first install command of claude-swap's README in a copy block, and "Already installed? Restart the Inbox." No saved accounts shows the same with `cswap add`. Failed shows a short line. A Refresh that fails over a good list keeps the list and shows that line above it; a first read that fails shows only the line. Refresh sits in the Claude Code heading of every state; the first read shows a waiting line, and a Refresh keeps the list up with the button disabled and spinning until it answers.

**One read** (`packages/inbox/useAccounts.tsx`). `AccountsProvider` holds the window's read: the page, the row and the peek show it and never fetch for themselves. A read happens when the window opens, when the page opens, when the peek opens and on Refresh, and a read asked for during another joins it. The read at open is the only one nobody asked for, and it never repeats: the sidebar has to know whether a limit is near. There is no polling, so the row can be behind until the next read. Since `cswap list --json` can refresh a login, this means opening the Inbox can too.

**Usage** (`packages/inbox/components/Usage.tsx`, classes `ib-usage-*`). A row above Settings, at the bottom of the sidebar. Nothing in the foot may arrive late and move the rest (a row landing where Feedback was takes its click), so `/api/inbox/settings` answers `cswap`, a look at PATH that runs nothing and is false for a tailnet guest, and the foot stays hidden (`data-held`) until settings answer, then draws whole. If settings fail or are 1.5 s late it draws anyway. The row shows while `cswap` is on PATH, and the read has the last word once it answers: `accounts` or `failed` keep it, and not installed (a dead shim, a removed `cswap`) or a guest take it away. An Inbox that did not answer leaves it as settings said. It is plain until the account in use reaches 90% on any limit, then shows the logo and that limit's figure, both amber. An old reading or an expired login never goes amber. Other accounts never move it.

The peek is a read-only Base UI popover. Its one block is the account in use, its limits, and a reset time only beside a limit at 90%; the block opens Settings → Accounts, where anything gets done. Beside the name it can say "Login expired", "API key" or "No reading yet". With nothing to show, the block says "No accounts yet", "No account in use" or the read's failure line. Opened before the first read answers, it says "Reading accounts…" and fills in. A failed read over a good list keeps the old figures here, and only the page shows the line. A read that finds `cswap` gone closes it. No address, no switching, no new shortcuts; Codex, OpenCode and Pi are not mentioned, and other machines at 90% wait for the linked machines step.

On a phone the row is in the sidebar's sheet. A tap closes that sheet and opens the same content as the bottom sheet Tidy uses (`.ib-tidy-pos[data-phone]`). The peek's state lives in `App.tsx`, beside the sidebar and not inside it, so closing the sidebar's sheet does not close it. The mock's chip in the phone's list header is not built.

**Proofs.** No test can reach a real claude-swap, which reads and writes the Keychain item "Claude Code-credentials". Every window reads at open, so this covers every test that opens one, not just these. The Accounts tests give the Inbox a PATH of only a fake `cswap`'s folder (`tests/helpers/fake-cswap.ts`, whose script names every program by absolute path). `tests/helpers/inbox-dom-server.ts` reads usage on an empty PATH unless it is in `accounts` mode. A scratch Inbox started by hand or by a dev script keeps the real PATH, so its first window would run a real `cswap`: give it `PLANNOTATOR_TEST_SANDBOX=<its data dir>` (`scripts/inbox-sim.ts` does). In e2e `cswap` is also in `AGENT_CLIS` (`tests/e2e/agent-cli-stubs.ts`): the stub comes first on the runner's PATH and exits 127, so those windows read as not installed. `cswap list --json` is the one stub call that does not fail the run; any other does. The samples in `tests/fixtures/cswap/` are fake output of the real tool.
