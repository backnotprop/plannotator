## Inbox: accounts and usage

Settings → Accounts (`#settings/accounts`) shows the Claude accounts on this computer and on every linked machine, and how much of each is used. It is the read-only part of the approved "accounts-page" work (`.product/approved/accounts-page/`, not in this repo). The sidebar's Usage row, its peek and the phone's sheet show the same read. Switching, Codex, OpenCode and Pi are later steps, each with its own review.

The Inbox reads through claude-swap (`cswap`, MIT, installed by the person). Plannotator never reads, stores or moves credentials. `cswap list --json` may: to fetch usage it can refresh an expired login, spending a one-time token and writing the new one back, inside claude-swap, as typing `cswap list` does. There is no flag to skip that. There is no on/off setting: with `cswap` on the Inbox's PATH the page shows the accounts, and without it the page says how to install it. The lookup never goes outside that PATH, because a home lookup could reach a real `cswap` from a test, so a `cswap` installed after the Inbox started takes a restart, and the page says so.

**The read** (`packages/server/inbox-accounts.ts`). `GET /api/inbox/accounts` looks `cswap` up with `AgentEnvironment.which` and runs `cswap list --json` through `runUntilExit` (no shell, an argv array). **Never kill a run for being slow.** A kill between the token being spent and the new one being written loses the login, and `list` has no signal handler, so SIGTERM is no safer. At 20 s the caller is answered `timed_out` and the run goes on. Only a run still going at 2 minutes is killed with its process group, as truly stuck. The Inbox stopping leaves a run to finish, and then nothing enforces that limit. Do not change this to `runWithTimeout`, which is for agent CLIs. The answer is one of:

- `{ state: "not_installed" }`: not on PATH, or a run that exits 127, the shell's "command not found" (a shim whose tool is gone).
- `{ state: "failed", reason }`: `timed_out`, `run_failed` (a non-zero exit), `bad_output` (not the list), or `unknown_schema` (a `schemaVersion` this build does not read; the window says to update).
- `{ state: "accounts", accounts }`.

Rules for the read:

- **Named fields only.** Every value is picked by name in `account()` and `usageWindow()`: `number`, `alias`, `email`, `organizationName`, `isOrganization`, `active`, `usageStatus`, `usageError`, `usageRetryAt`, `usageAgeSeconds`, and `usage`'s `fiveHour`, `sevenDay` and `scoped` (each `pct`, `resetsAt`, `countdown`, `clock`; a scoped window also `name`). Never pass the raw JSON or spread a row: a field a later `cswap` adds must not reach the window. Unknown extra fields are ignored.
- **No `cswap` words.** Its stdout, stderr and error text are never logged, stored or answered. A failure is a fixed code. `usageStatus` and `usageError` pass only as single words, and the window maps them to its own text.
- **An API-key row has no address.** `cswap` gives it a placeholder (`api-key-3@token.local`). The server drops that, for the status `api_key` and for any `@token.local` address.
- **A window `cswap` does not report is null, never 0.** A `pct` that is not a finite number drops its window, and a `usage` with no window left reads as no reading. A window of 0% with no reset time is shown as reported: the mock hides it, and that difference is decided until a real Ultra reading exists. A window past its `resetsAt` reads as not reported: `cswap` serves its last good reading when a fetch fails, so the figure is from before that reset.
- **One run at a time, until it has really ended.** A caller during a run joins it and waits its own 20 s, so a Refresh after a `timed_out` can still get that run's answer, and never starts a second run. A new Inbox process knows nothing of a run the last one left going, so the two can overlap; claude-swap's own locks cover that. Nothing goes on disk and nothing polls: a run starts when a window, the page or the peek opens, or on Refresh.
- **At most one process per 30 s per Inbox, whoever asks.** Every run's answer, a failure's too, is kept in memory for `INBOX_ACCOUNTS_CACHE_MS`, so a reloading phone starts no process per load and a broken `cswap` runs once however often a window opens. Refresh sends `fresh=1`, from a window here or from a linked machine, and that reads again only once 30 s have passed since the last run started; inside that time it gets the last reading. A kept time ahead of now is a clock set back and counts as passed, so a read never waits for the clock to catch up. `cswap` gone shows at once, since finding that out starts no process. This saves processes, not logins: `cswap` fetches, and so refreshes, at most once per its own 180 s (`SERVE_TTL_S`) however often it runs, and the login's safety rests on that floor. A test that changes the answer between reads passes `cacheMs: 0`; a spec on the compiled binary sets `PLANNOTATOR_TEST_ACCOUNTS_CACHE_MS=0` in its sandbox (`accountsTestOptions`).

Who may read: the window's read guard (same origin, `403 cross_origin`), and a tailnet login that is not the owner's gets `403 owner_only` before anything runs. The owner reads over the tailnet like any window route, which is how a phone's browser reads. The door takes `accounts` from a linked machine's token alone, so no phone app and no relay command reaches it. The Inbox is Bun-only, so nothing is in the Pi server.

**A linked machine's read** (`accountsOf` in `packages/server/inbox-machines.ts`). `GET /api/inbox/accounts/<machine>` asks that machine's door through its `PeerLink`, the way every read between machines goes, and the far Inbox runs its own read, with its own run, 30 s answer and `fresh`. It sits behind the one guard above, and `accounts` is refused by the generic forward, for everyone: a forward has no owner check and passes the far answer as it came. Rules:

- **Only when asked.** A far read happens when a read here happens: a window, the page or the peek opening, or Refresh. Nothing polls, and a machine coming back is not a read. Nothing is kept here, in memory or on disk: GET answers are not stored, so an address never reaches a disk on either side.
- **Named fields only, again.** The far answer is picked by `parsePeerAccounts` with the same `account()` as `cswap`'s, because the other end may be older, newer or hostile. Its failure stays a fixed code. A field over 1,024 characters is dropped, rows past the first 200 are dropped, and a body over `INBOX_MACHINE_ACCOUNTS_MAX_BYTES` (1 MiB, 16 times what a run may print) is read no further and answers `failed`, `bad_output`, whatever its status. `PeerLink.request` also looks into a 401 for a revoked link, through `readCapped` at 64 KiB: no read of a far body is uncapped on this path.
- **One machine at a time.** The window asks each machine in its own request and tracks each one's read, so a slow one holds up only its own row, on Refresh too: a Refresh that finds a machine reading asks it again when that read ends.
- **The wait is 25 s (`INBOX_MACHINE_ACCOUNTS_WAIT_MS`), past the far run's 20 s,** and covers the body too. So a slow far run comes back as its own `timed_out`, whose words are claude-swap's, and the run goes on to serve the next read. `peer.request` gets it as `timeoutMs`: the link's usual 15 s would stop first.
- **`{ state: "offline" }` is a machine that does not answer at all:** a line that is down (at once, without a request), or a read that failed with the line down too. Never an error.
- **`{ state: "unreachable" }` is a machine that is up but gave no answer to this read:** a 401, 403 or 500, a body that is not JSON, a door that hangs through the whole wait with its line still up, or a link it revoked. The wait outlasts the line's 20 s silence limit, so a machine truly asleep has lost its line by then. So is this Inbox not answering the window. The row says "The Inbox did not answer."
- **`{ state: "needs_update" }` is a version apart:** an older door answers `404 device_route_not_found`, and an object this build can't read (a newer `state`, one row it can't pick) came from one too. The link, its threads and its writes carry on. So does a machine too old to link.
- **A door serves only its own Inbox's accounts.** It keeps only `fresh` of the query, and `/api/inbox/accounts/<machine>` is no door route, so no machine can pass on a third's.

**The window** (`packages/inbox/components/Accounts.tsx`, classes `ib-acct-*`; design of record `.product/approved/accounts-page/mock/`, not in this repo). The section comes after Machines in Settings. Machines comes first on the page: this machine, then each linked one, and the account each is using. With nothing linked it is one row, shown only when an account is active. Rows are plain text with no control; Switch goes there in a later step. A row has one line and its words sit where the account would, so an answer never moves the rows under it, which differs from the mock's line under the name: "Reading accounts…" until the first answer, "Asleep" (the mock's word, and Settings → Machines' for `offline`), "Update Plannotator", "No account in use", "No accounts yet", or a read's failure line. A machine without `cswap` says nothing here: its row is its name. An account named here reads as it does in the list below, number and all. Accounts follow under Claude Code.

Every machine's accounts are one list, this machine's always first, and the list waits for this machine's first answer. One login on two machines is one row, by address and organization, with the newer reading, and its open row ends with the machines it is on. An API key has no address to tell it by, so it stays its machine's own row. A machine's figures are not kept once it stops answering: its accounts leave the list unless another machine has them. Without `cswap` here, the page says how to install it under the other machines' list, and the sidebar stays as it is.

A merged row keeps the worst state of its machines (`worstState`): a login that needs a person on one machine ("Sign in again", "No saved login", "Signed in to another account", "Keychain unreadable") says so under the name, beside another machine's bars, and the open row says on which. "Login renewing" and a failed fetch pass by themselves, so they don't.

A late answer moves nothing already showing in the closed rows of the list. The page keeps rows in the order it first saw them (`seen`), so a slow machine's rows land last. A row has one line under its name: what needs a person, else the organization that tells it from a namesake, else why it has no reading. The other waits in the open row, so a row has no third line. With a machine linked every row has room for that line (`[data-linked]`), so a late organization or "Sign in again" pushes nothing. Exceptions: on a phone a row whose third limit arrives late wraps, as such a row always does, and "Signed in to another account" wraps in the name column; an open row can gain a line ("Sign in again on Mini"); this machine's rows land above the others after a first read that failed; rows leaving with a machine move what is under them; and a machines list that arrives after this machine's rows moves the page, which needs a kept answer to beat it, such as a reload inside 30 s.

A row reads as the alias, else the start of the address, else "API key". Figures show used, as `cswap` reports them. Bars come only from reported windows, in three fixed columns so they line up down the list: week last at the right, the window before it in the middle, a third on the left. On a phone a row with three windows puts them under the name, in columns that still line up. Amber at 90% or more, judged on the rounded figure so a number and its colour never disagree. `usage: null` reads "No reading yet" in the week column with the reason in plain words under the name, or in the open row if the organization has that line (`noReadingReason`, which knows `cswap`'s statuses). An API-key account reads "API key" there, unless that is already its name.

The full address, the organization and the reset times stay out of the row until it is opened. A row with none of them opens nothing and is no button. The organization shows on the closed row only when two rows would read the same and nothing there needs a person, and the machine says the same, since one address can be saved under two organizations.

Personal Claude organizations are named after the address, and `isOrganization` is true for them too. So everywhere in the window, an organization containing the row's own address is no organization (`accountOrganization`): it would put the address on a closed row. Rows that then still read alike show `cswap`'s number quietly after the name, `mira #2`, only those rows. That number is unique on one machine only, so the one list keeps its own (`steadyNumbers`, a page-level map beside `seen`). This machine's rows always show the number `cswap` prints here. Any other row keeps the first number it showed for as long as the page is open, through a machine going to sleep and coming back, and a number taken, even by a row not showing, goes past the highest. So while the page is open a number never names two logins. Two limits on that: a far row gives way if this machine's answer lands on its number, which needs a first read that failed, and a new visit to the page numbers again, so a far row's number can differ between visits. A number past `cswap`'s own is one no machine knows: Switch must not take it as `cswap`'s.

A reading over 10 minutes old (`usageAgeSeconds`; `cswap`'s normal serve age is 3 minutes) means `cswap` could not refresh it, since it serves its last good reading when a fetch fails. The closed row's figures are muted and never amber, and the open row says "Last read 2h ago".

The owner's rule for this page: "Show me only what I need until I want to act. If I want to act take me to settings page. No narrative labels or redundant info." So it has no lede and no side notes, only the accounts and their numbers, and each other state is a few words. Keep it that way.

Not installed shows the mock's line, the first install command of claude-swap's README in a copy block, and "Already installed? Restart the Inbox." No saved accounts shows the same with `cswap add`. Failed shows a short line. A Refresh that fails over a good list keeps the list and shows that line above it; a first read that fails shows only the line. Refresh sits in the Claude Code heading of every state; the first read shows a waiting line, and a Refresh keeps the list up with the button disabled and spinning until it answers.

**One read** (`packages/inbox/useAccounts.tsx`). `AccountsProvider` holds the window's read: the page, the row and the peek show it and never fetch for themselves. A read happens when the window opens, when the page opens, when the peek opens and on Refresh, and a read asked for during another joins it. The read at open is the only one nobody asked for, and it never repeats: the sidebar has to know whether a limit is near. There is no polling, so the row can be behind until the next read. Since `cswap list --json` can refresh a login, this means opening the Inbox can too, on this computer and on each linked one. Each read lists the linked machines (`GET /api/inbox/machines`) and asks each one for itself, and a machine keeps its last answer up until the next one arrives; `reading` is this computer's alone. So the machines on the page are as of the last read, not live.

**Usage** (`packages/inbox/components/Usage.tsx`, classes `ib-usage-*`). A row above Settings, at the bottom of the sidebar. Nothing in the foot may arrive late and move the rest (a row landing where Feedback was takes its click), so `/api/inbox/settings` answers `cswap`, a look at PATH that runs nothing and is false for a tailnet guest, and the foot stays hidden (`data-held`) until settings answer, then draws whole. If settings fail or are 1.5 s late it draws anyway. The row shows while `cswap` is on PATH, and the read has the last word once it answers: `accounts` or `failed` keep it, and not installed (a dead shim, a removed `cswap`) or a guest take it away. An Inbox that did not answer leaves it as settings said. It is plain until the account in use reaches 90% on any limit, then shows the logo and that limit's figure, both amber. An old reading or an expired login never goes amber. Other accounts and other machines never move it, and the row is this computer's: `cswap` on a linked machine alone adds none.

The peek is a read-only Base UI popover. Its one block is the account in use, its limits, and a reset time only beside a limit at 90%; the block opens Settings → Accounts, where anything gets done. Beside the name it can say "Login expired", "API key" or "No reading yet". With nothing to show, the block says "No accounts yet", "No account in use" or the read's failure line. Opened before the first read answers, it says "Reading accounts…" and fills in. A failed read over a good list keeps the old figures here, and only the page shows the line. A read that finds `cswap` gone closes it. Under the block, a linked machine shows only while the account it is using is at 90% or more on a limit, by the row's own rule: its name, that limit and its figure in amber, in a block that opens the same place. A machine that does not answer, an old reading, an expired login and that machine's other accounts show nothing here. A far answer that grows an open peek leaves it mounted, with focus where it was: it gets a new position reference, placed at where the row was as it opened, and nothing else changes. Tab past the last block or Shift+Tab past the first, or from the popup itself, closes the peek and leaves focus on the row, since a popover's focus guards would otherwise take it behind the peek; on a phone the sheet holds focus. No address, no switching, no new shortcuts; Codex, OpenCode and Pi are not mentioned.

On a phone the row is in the sidebar's sheet. A tap closes that sheet and opens the same content as the bottom sheet Tidy uses (`.ib-tidy-pos[data-phone]`). The peek's state lives in `App.tsx`, beside the sidebar and not inside it, so closing the sidebar's sheet does not close it. The mock's chip in the phone's list header is not built.
