## Inbox: accounts and usage

Settings → Accounts (`#settings/accounts`) shows the Claude accounts on this computer and on every linked machine, and how much of each is used. It is the approved "accounts-page" work (`.product/approved/accounts-page/`, not in this repo): steps 1 and 2 read, step 3 switches the account on this computer (below), and the page is the approved redesign: one block per machine, every row not in use the switch. The sidebar's Usage row, its peek and the phone's sheet show the same read and never switch. Switching on a linked machine (step 4) is built: every row not in use is the switch, on every machine (below). Codex, OpenCode and Pi are later steps, each with its own review. Real switching waits on a test with two real logins and the owner at the machine; until then it is proven only against a fake `cswap`.

The Inbox reads through claude-swap (`cswap`, MIT, installed by the person). Plannotator never reads, stores or moves credentials. `cswap list --json` may: to fetch usage it can refresh an expired login, spending a one-time token and writing the new one back, inside claude-swap, as typing `cswap list` does. There is no flag to skip that. There is no on/off setting: with `cswap` on the Inbox's PATH the page shows the accounts, and without it the page says how to install it. The lookup never goes outside that PATH, because a home lookup could reach a real `cswap` from a test, so a `cswap` installed after the Inbox started takes a restart, and the page says so.

**The read** (`packages/server/inbox-accounts.ts`). `GET /api/inbox/accounts` looks `cswap` up with `AgentEnvironment.which` and runs `cswap list --json` through `runUntilExit` (no shell, an argv array). **Never kill a run for being slow.** A kill between the token being spent and the new one being written loses the login, and `list` has no signal handler, so SIGTERM is no safer. At 20 s the caller is answered `timed_out` and the run goes on. Only a run still going at 2 minutes is killed with its process group, as truly stuck. The Inbox stopping leaves a run to finish, and then nothing enforces that limit. Do not change this to `runWithTimeout`, which is for agent CLIs. The answer is one of:

- `{ state: "not_installed" }`: not on PATH, or a run that exits 127, the shell's "command not found" (a shim whose tool is gone).
- `{ state: "failed", reason }`: `timed_out`, `run_failed` (a non-zero exit), `bad_output` (not the list), or `unknown_schema` (a `schemaVersion` this build does not read; the window says to update).
- `{ state: "accounts", accounts }`.

Rules for the read:

- **Named fields only.** Every value is picked by name in `account()` and `usageWindow()`: `number`, `alias`, `email`, `organizationName`, `isOrganization`, `active`, `usageStatus`, `usageError`, `usageRetryAt`, `usageAgeSeconds`, and `usage`'s `fiveHour`, `sevenDay` and `scoped` (each `pct`, `resetsAt`, `countdown`, `clock`; a scoped window also `name`). Never pass the raw JSON or spread a row: a field a later `cswap` adds must not reach the window. Unknown extra fields are ignored.
- **No `cswap` words.** Its stdout, stderr and error text are never logged, stored or answered. A failure is a fixed code. `usageStatus` and `usageError` pass only as single words, and the window maps them to its own text.
- **An API-key row has no address.** `cswap` gives it a placeholder (`api-key-3@token.local`). The server drops that, for the status `api_key` and for any `@token.local` address.
- **A window `cswap` does not report is null, never 0.** A `pct` that is not a finite number drops its window, and a `usage` with no window left reads as no reading. A window of 0% with no reset time is shown as reported: the mock hides it, and that difference is decided until a real Ultra reading exists. A window past its `resetsAt` reads as not reported: `cswap` serves its last good reading when a fetch fails, so the figure is from before that reset.
- **One run at a time, until it has really ended.** A caller during a run joins it and waits its own 20 s, so a Refresh after a `timed_out` can still get that run's answer, and never starts a second run. A new Inbox process knows nothing of a run the last one left going, so the two can overlap; claude-swap's own locks cover that. Nothing goes on disk and nothing polls: a run starts when a window, the page or the peek opens, or on Refresh.
- **At most one process per 30 s per Inbox, whoever asks.** Every run's answer, a failure's too, is kept in memory for `INBOX_ACCOUNTS_CACHE_MS`, so a reloading phone starts no process per load and a broken `cswap` runs once however often a window opens. Refresh sends `fresh=1`, from a window here or from a linked machine, and that reads again only once 30 s have passed since the last run started; inside that time it gets the last reading. A kept time ahead of now is a clock set back and counts as passed, so a read never waits for the clock to catch up. `cswap` gone shows at once, since finding that out starts no process. This saves processes, not logins: `cswap` fetches, and so refreshes, at most once per its own 180 s (`SERVE_TTL_S`) however often it runs, and the login's safety rests on that floor. A test that changes the answer between reads passes `cacheMs: 0`; a spec on the compiled binary sets `PLANNOTATOR_TEST_ACCOUNTS_CACHE_MS=0` in its sandbox (`accountsTestOptions`).

Who may read: the window's read guard (same origin, `403 cross_origin`), and a tailnet login that is not the owner's gets `403 owner_only` before anything runs. The owner reads over the tailnet like any window route, which is how a phone's browser reads. The door takes `accounts` from a linked machine's token alone, so no phone app and no relay command reaches it. The Inbox is Bun-only, so nothing is in the Pi server.

**A linked machine's read** (`accountsOf` in `packages/server/inbox-machines.ts`). `GET /api/inbox/accounts/<machine>` asks that machine's door through its `PeerLink`, the way every read between machines goes, and the far Inbox runs its own read, with its own run, 30 s answer and `fresh`. It sits behind the one guard above, and `accounts` is refused by the generic forward, for everyone: a forwarded read has no owner check and passes the far answer as it came. Rules:

- **Only when asked.** A far read happens when a read here happens: a window, the page or the peek opening, or Refresh. Nothing polls, and a machine coming back is not a read. Nothing is kept here, in memory or on disk: GET answers are not stored, so an address never reaches a disk on either side.
- **Named fields only, again.** The far answer is picked by `parsePeerAccounts` with the same `account()` as `cswap`'s, because the other end may be older, newer or hostile. Its failure stays a fixed code. A field over 1,024 characters is dropped, rows past the first 200 are dropped, and a body over `INBOX_MACHINE_ACCOUNTS_MAX_BYTES` (1 MiB, 16 times what a run may print) is read no further and answers `failed`, `bad_output`, whatever its status. `PeerLink.request` also looks into a 401 for a revoked link, through `readCapped` at 64 KiB: no read of a far body is uncapped on this path.
- **One machine at a time.** The window asks each machine in its own request and tracks each one's read, so a slow one holds up only its own row, on Refresh too: a Refresh that finds a machine reading asks it again when that read ends.
- **The wait is 25 s (`INBOX_MACHINE_ACCOUNTS_WAIT_MS`), past the far run's 20 s,** and covers the body too. So a slow far run comes back as its own `timed_out`, whose words are claude-swap's, and the run goes on to serve the next read. `peer.request` gets it as `timeoutMs`: the link's usual 15 s would stop first.
- **`{ state: "offline" }` is a machine that does not answer at all:** a line that is down (at once, without a request), or a read that failed with the line down too. Never an error.
- **`{ state: "unreachable" }` is a machine that is up but gave no answer to this read:** a 401, 403 or 500, a body that is not JSON, a door that hangs through the whole wait with its line still up, or a link it revoked. The wait outlasts the line's 20 s silence limit, so a machine truly asleep has lost its line by then. So is this Inbox not answering the window. The row says "The Inbox did not answer."
- **`{ state: "needs_update" }` is a version apart:** an older door answers `404 device_route_not_found`, and an object this build can't read (a newer `state`, one row it can't pick) came from one too. The link, its threads and its writes carry on. So does a machine too old to link.
- **A door serves only its own Inbox's accounts.** It keeps only `fresh` of the query, and `/api/inbox/accounts/<machine>` is no door route, so no machine can pass on a third's.

**The window** (`packages/inbox/components/Accounts.tsx`, classes `ib-acct-*`; design of record `.product/approved/accounts-page/mock/` and `approval.md`, not in this repo). The section comes after Machines in Settings, with Refresh beside its title. The page is one block per machine: the machine's icon and name over a hairline, this machine first, then each linked one in the order `/api/inbox/machines` gives them. Inside a block, one list per tool: today only Claude Code, with its mark (`CLAUDE_CODE`, an `AccountsTool`: the host, the name, the swap tool, its install and add commands). A Codex list drops in as a second `AccountsTool` under the same machine; nothing on the page assumes one tool.

Each machine's list is its own, as its own `cswap` prints it: nothing is merged across machines, and a slow machine holds up only its own block ("Reading accounts…" in its place). A block that has no list says so in a few words where the rows would be (`Quiet`, `[data-machine-state]`): "Asleep" (the mock's word, and Settings → Machines' for `offline`), "Update Plannotator", "The Inbox did not answer.", or a read's failure line. A machine without `cswap` gets the not-installed block, the same as this machine's. A slow machine's answer moves nothing above its block; the blocks under it move down when its rows land, as in the mock.

A list (`ladder`) is the account in use first, then the others: those with a reading, then those without, then API keys, each by most room left (the lower tightest figure first), then `cswap`'s number. A row is a dot (filled for the account in use, amber when its tightest limit is at 90% or more, red after a failed switch to it), the name, muted notes, and the usage cluster. The cluster is a grid of four fixed columns so it lines up down the page, every machine's rows in one column: the label of the limit nearest to running out (`tightest`: the highest rounded figure, the first on a tie), its bar, its figure, and a detail. The detail is only on the account in use: "resets <time>" at 90% or more, else its other limits ("5h 21% · Fable 33%"). Figures show used, as `cswap` reports them, and are muted on rows not in use. Amber at 90% or more, judged on the rounded figure so a number and its colour never disagree. An API key reads "API key" in the bar's place (blank when that is already its name), and `usage: null` reads "No reading yet" there, with the reason in the notes (`noReadingReason`, which knows `cswap`'s statuses).

The notes beside a name, joined with " · ": the organization when two rows of that list read the same; why a row has no reading, or that it needs a person ("Sign in again" and the rest); "on <machine>" when another machine's list has the same login in use (`usedElsewhere`, by address and organization; an API key has no address, so it is never on another machine); and "most room". "most room" (`mostRoom`) goes on one row only, and only while the account in use has a trusted reading at 90% or more: the trusted row with a login (not an API key, not needing a person) with the lowest tightest figure, if that is below the one in use. A trusted reading is under 10 minutes old and not `relogin_required`.

A row reads as the alias, else the start of the address, else "API key". Personal Claude organizations are named after the address, and `isOrganization` is true for them too. So everywhere in the window, an organization containing the row's own address is no organization (`accountOrganization`): it would put the address on the page. Rows of one list that then still read alike show `cswap`'s number quietly after the name, `mira #2`, only those rows. That number is the machine's own, which Switch sends back. No address shows anywhere on the page.

A reading over 10 minutes old (`usageAgeSeconds`; `cswap`'s normal serve age is 3 minutes) means `cswap` could not refresh it, since it serves its last good reading when a fetch fails. Its figures are muted and never amber, and the account in use's detail says "Last read 2h ago".

The owner's rule for this page: "Show me only what I need until I want to act. If I want to act take me to settings page. No narrative labels or redundant info." So it has no lede and no side notes, only the accounts and their numbers, and each other state is a few words. Keep it that way.

Not installed shows "**claude-swap** isn't installed on <machine>.", the first install command of claude-swap's README in a copy block, and "Already installed? Restart the Inbox there." No saved accounts shows "Sign in to Claude Code, then save the account" with `cswap add`. Failed shows a short line. A Refresh that fails over a good list keeps the list and shows that line above it; a first read that fails shows only the line. The first read shows a waiting line, and a Refresh keeps the lists up with the button disabled and spinning until this machine answers. A guest sees "Owner only." and no Refresh.

**Switch** (step 3; `switchTo` in `packages/server/inbox-accounts.ts`, `POST /api/inbox/accounts/switch`, `AccountRow` and `SwitchConfirm` in `Accounts.tsx`). Every row not in use is the switch, on this machine and on each linked one: a plain button (`button[data-account]`, `aria-expanded`). On a desktop it tints on hover and shows a quiet "Switch" at its right; hover styles sit under `@media (hover: hover)`, so a tap on a phone leaves no tint behind, and a phone row has no "Switch" word and is 44 px or taller. Pressing a row opens the confirm under it (`[data-accounts-confirm]`, focus on Cancel), and pressing it again or Cancel closes it: "Switch Claude Code on <machine> to <name>?", then "Open sessions stay on <current> until you restart them.", plus "<machines> use(s) <name> too, so they share its limits." when another machine has that login in use; an API key's confirm says only "Billed per token." With no account in use and nothing shared, the confirm is its question alone. The confirm holds the login (address, organization, alias), not `cswap`'s number: a read after a `cswap swap` in a terminal keeps it on that login under its new number, and a read without that login, or with it now in use, closes it. On a phone the confirm stacks, its buttons under the words. While a switch runs, its row says "Switching…" with a spinner and every row of that list is disabled until the read after it answers; then, if focus fell to the page, it comes back to the row picked when that is still a switch, else to the list. No new keys: rows and the confirm are plain buttons.

The server's rules, beside the read's:

- **Match first, on a new list.** The body is the account as the window showed it: `cswap`'s number, its address, its organization and its alias (an API key has no address, so its alias is what tells it from another; two API keys with no alias can't be told apart). A list run going ends first, so `cswap list` and `cswap switch` never overlap here. Then a new `cswap list --json` runs, never the kept answer, past the 30 s floor: that floor saves processes, not logins, and `cswap` refreshes a login at most once per its own 3 minutes. It must still have that login under that number, else `changed` and nothing switches: `cswap swap` or `remove` in a terminal can renumber the list under an open page at any time. The account already in use answers `switched` and runs nothing.
- **`cswap switch <number> --json`, never killed.** It writes the login Claude Code uses, so nothing kills it, at any limit, and the Inbox stopping leaves it to finish (`runToExit`). The person waits 20 s, for the list and the switch together, and gets `timed_out`; the switch goes on, and stays the one switch (`busy`) until its process exits. A switch that never exits, one waiting on a Keychain prompt say, holds `busy` until the Inbox restarts, and every read meanwhile waits for it and answers `timed_out`. A switch that throws anywhere answers `run_failed` and frees the next one. `cswap`'s stdout stays a pipe to the Inbox, so after the Inbox exits its final print fails (EPIPE); `cswap` prints only once `switch_to` has returned, so the login is written by then. Windows is unproven (the approval: until someone runs it). There the child is not detached (`spawnRun`), so Ctrl+C or closing the Inbox's console stops a switch too, and the Inbox stopping does not leave it to finish.
- **The answer is a number or a fixed code.** `{ state: "switched", number }` when `cswap` says it switched to the number asked, or that it was already there, and its `to` address is the one the list before gave that number (compared on the server, never passed on: an API key's placeholder counts). The number asked with another address is `renumbered`: the list moved between that list and the switch, which went to another login, and the next read shows which. Any other answer is `run_failed`, unparseable output `bad_output`, another `schemaVersion` `unknown_schema`. Its `from`, `to` addresses, `message` and `warnings` never pass: a door keeps answers on disk, so no address goes in one.
- **The read after it is new.** The switch's end, whatever it was, drops the kept answer and lets go of any run begun before it, and a run begun before it never becomes the kept answer (a generation count). Those last two back up the wait above: while it stands, no list run is going during a switch, so a test can reach them only with the wait removed. A read asked for during a switch waits for it. So the read after a switch is always a new run, started after the switch ended.
- **Who.** The read's guards on the server: same origin, and a tailnet guest gets `403 owner_only` before anything runs, and a page from an earlier Inbox on this address gets `409`, the server-session check of every write. The owner can switch from a phone's browser over the tailnet. A phone's token and the relay never reach it. A linked machine's token reaches it only through the door's `accounts/switch`, which only the owner's forward sends (below).

The window reads this computer again after a switch (never a read that began before it ended, and not the linked machines), and that read has the last word (`switchLine` in `useAccounts.tsx`, which keeps one switch line per machine, `switches`): the account picked in use there is done, whatever the switch answered. Otherwise a line under the row it was for says why, in the page's words, with a red dot on that row: an alert icon, "Couldn't switch to <name>." and a reason, and Try again, which opens the confirm again. "Still switching to <name>. Refresh in a moment." when the switch outlasted the wait and the read after it did too, and "Switched to <name>. Refresh to see it." when it switched and that read failed, have no icon and no Try again. When the login it named is no longer on that number, or is now the one in use, the line sits above the list instead. The list always shows what the last good read said, never the pick. A switch that timed out and a read after it that answered means the switch ended, since that read waited for it: not in the account picked is "claude-swap failed." The line stays until a later read answers with a list (Refresh, the peek, the page opening): then the list shows where the switch ended, and the line goes.

Gaps against the mock, not invented: the confirm's "Compact idle sessions first" is not built, since `cswap` has no such option; Codex lists are a later step; the failed line keeps step 3's wording; "API key" is not repeated where it is already the row's name; the notes can also carry an organization or why a row has no reading, which the mock's data never needed; on a phone the page title is the app's phone Settings title, larger than the mock's.

**A linked machine's switch** (step 4; `switchOn` in `packages/server/inbox-machines.ts`, `POST /api/inbox/m/<machine>/accounts/switch`). The same row, confirm and line, sent through the forward. The forward refuses everything under `accounts/` but this one POST, and only after #2564's guest check: a tailnet guest of this machine gets `403 owner_only` and nothing goes; the owner always switches (here, or over the tailnet; where Tailscale reports no owner, a tagged device or a status that names no login, the logins its allowlist names). Then the same-origin guard, the page-session `409` and `switchTarget`, and the four fields go at once through `peer.request`, never the outbox: a switch held and sent later would change a login long after the person looked. Rule 8's table calls it `now`. The far door (`POST accounts/switch`, a machine's token only, never a phone's or the relay's) hands it to that Inbox's own `POST /api/inbox/accounts/switch`, so the far side re-lists, matches, runs once and never kills, as here. The door does not run it as a `command`: nothing is kept on disk and no key replays it; a second copy re-lists and finds the account in use. The answer comes back picked by name (`parsePeerSwitch`): a number, a known reason, or not installed. A machine asleep is `offline` at once, and so is one the switch never reached (a connection refused before a byte went out, though the line had not yet noticed: `neverReached`); a door without the route is `needs_update`; no answer within 25 s once sent with the line up is `timed_out`, since it may be switching there. The window then reads that machine alone again (its Inbox waits for a switch going, so that read shows where it ended) and the same `switchLine` rules apply; "The machine is asleep." and "Update Plannotator there." are its two extra reasons. When that read has no list, the line stands over the block's own word. A linked switch never holds this machine's rows or reads this machine again.

**One read** (`packages/inbox/useAccounts.tsx`). `AccountsProvider` holds the window's read: the page, the row and the peek show it and never fetch for themselves. A read happens when the window opens, when the page opens, when the peek opens and on Refresh, and a read asked for during another joins it. The read at open is the only one nobody asked for, and it never repeats: the sidebar has to know whether a limit is near. There is no polling, so the row can be behind until the next read. Since `cswap list --json` can refresh a login, this means opening the Inbox can too, on this computer and on each linked one. Each read lists the linked machines (`GET /api/inbox/machines`) and asks each one for itself, and a machine keeps its last answer up until the next one arrives; `reading` is this computer's alone. So the machines on the page are as of the last read, not live.

**Usage** (`packages/inbox/components/Usage.tsx`, classes `ib-usage-*`). A row above Settings, at the bottom of the sidebar. Nothing in the foot may arrive late and move the rest (a row landing where Feedback was takes its click), so `/api/inbox/settings` answers `cswap`, a look at PATH that runs nothing and is false for a tailnet guest, and the foot stays hidden (`data-held`) until settings answer, then draws whole. If settings fail or are 1.5 s late it draws anyway. The row shows while `cswap` is on PATH, and the read has the last word once it answers: `accounts` or `failed` keep it, and not installed (a dead shim, a removed `cswap`) or a guest take it away. An Inbox that did not answer leaves it as settings said. It is plain until the account in use reaches 90% on any limit, then shows the logo and that limit's figure, both amber. An old reading or an expired login never goes amber. Other accounts and other machines never move it, and the row is this computer's: `cswap` on a linked machine alone adds none.

The peek is a read-only Base UI popover. Its one block is the account in use, its limits, and a reset time only beside a limit at 90%; the block opens Settings → Accounts, where anything gets done. Beside the name it can say "Login expired", "API key" or "No reading yet". With nothing to show, the block says "No accounts yet", "No account in use" or the read's failure line. Opened before the first read answers, it says "Reading accounts…" and fills in. A failed read over a good list keeps the old figures here, and only the page shows the line. A read that finds `cswap` gone closes it. Under the block, a linked machine shows only while the account it is using is at 90% or more on a limit, by the row's own rule: its name, that limit and its figure in amber, in a block that opens the same place. A machine that does not answer, an old reading, an expired login and that machine's other accounts show nothing here. A far answer that grows an open peek leaves it mounted, with focus where it was: it gets a new position reference, placed at where the row was as it opened, and nothing else changes. Tab past the last block or Shift+Tab past the first, or from the popup itself, closes the peek and leaves focus on the row, since a popover's focus guards would otherwise take it behind the peek; on a phone the sheet holds focus. No address, no switching, no new shortcuts; Codex, OpenCode and Pi are not mentioned.

On a phone the row is in the sidebar's sheet. A tap closes that sheet and opens the same content as the bottom sheet Tidy uses (`.ib-tidy-pos[data-phone]`). The peek's state lives in `App.tsx`, beside the sidebar and not inside it, so closing the sidebar's sheet does not close it. The mock's chip in the phone's list header is not built.
