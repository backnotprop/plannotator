## Inbox: linked machines

One Inbox across machines, Phase 1: the server engine, then the window (see "The window" below). The design and the formal model live outside the repo (`.ops/multi-machine/PLAN.md`, `model/FINDINGS.md`); this guide is what is built.

**The shape.** Every machine keeps its own Inbox, exactly as before: its agents, files, wakes and offline behavior do not change. There is no home machine and no machine is special. One pairing code links two Inboxes both ways, and each then shows every machine's threads. A thread lives only on the machine whose agent started it; every other Inbox is a view of it and a remote control. No Inbox stores another's threads on disk, and no Inbox passes one machine's data on to a third.

**Files** (`packages/server/`), one job each:
- `inbox-machines.ts`: the coordinator. Linking and unlinking, the merged view, the forward, the window's and the CLI's routes, and the two door routes only a machine calls. Nothing else in the route table knows about links.
- `inbox-links.ts`: the one place linking state lives, `inbox/machines.json` (0600, temp file then rename): `{ v: 1, self: { id }, links: [{ id, name, token, transport, device_id, linked_at }] }`. `self.id` is this Inbox's stable id (`ibx_…`), served by `health`; links key on it, never on an address. Nothing is written until the first offer or link (an Inbox that never links keeps no file, and its id lives in memory until then); a file that cannot be read is moved aside to `machines.json.unreadable-<time>`, never written over. A link to an id already linked replaces it; a link to this Inbox's own id is refused (`link_to_self`). Also the pairing link format.
- `inbox-peer-link.ts`: one live link per machine (`PeerLink`).
- `inbox-outbox.ts`: the outbox and its rules.
- `inbox-transport.ts`: the transport seam, two calls (one request to the door, its event stream). `inbox-transport-tailnet.ts`: the one transport, HTTPS over the tailnet to the other Inbox's door (`https://<MagicDNS name>:<port>/api/inbox/device/*`, Tailscale's real certificate; the port is the one that door took, 8443 to 8450, and travels in the address). Only a `<machine>.<tailnet>.ts.net` name over https is taken, never another host, an IP or `localhost`, so a pasted code, `--address`, `--back` or a linked machine's `link-back` can never send a pairing secret or a token off the tailnet. Plain `http://` to a loopback host is taken only inside a test sandbox (`PLANNOTATOR_TEST_SANDBOX`, two Inboxes on one computer). The event stream's answer has the same 20 s deadline as its silence, so a machine that sleeps between `health` and `events` never hangs the line. A later transport (the relay, or a server reachable only over SSH) is one more file and one more `kind`; SSH between peers is out by design (laptops have no sshd and sit behind NAT).

**The door, with Phones off** (`inbox-devices.ts`). A linked Inbox is a device with platform `machine`, redeemed from a machine offer (its own slots, the same limits as a phone's: 10 minutes, 5 wrong codes). This works with `PLANNOTATOR_INBOX_PHONES` off: the door then answers a machine's token (a revoked one gets `401 device_revoked`), `pair` only while a machine offer is open, and a token it does not know with `401 device_token_invalid` when the request came through the tailnet's listener or a machine is paired here (so a machine whose link was wiped by a reinstall re-pairs, and its held writes end with their notice). To anything else, Origin header or not, it is the unknown-route 404 it always was. The tailnet door (8443, or the next free port up to 8450 at its first publish, then that port for good: a start that finds it held refuses and says why in `machines` (this machine's `reason`) and `link --list`, rather than move; see "Reach from my tailnet" in `inbox-foundation.md`) publishes at start only while a machine is linked or an unlinked machine is still owed its refusal (below; with neither, a start never runs `tailscale`, so a leftover a crash left waits for a link, Phones, or `uninstall --purge`), and comes down (the switch cleared) after the last unlink that reached the other machine, once an unlinked machine's refusal was answered or its week ran out, or when an offer that published it expires unused. With the port held and nothing linked, there is nothing to unlink, so the refusal says the port is let go of once no link code is open (10 minutes; a link that could not publish its way back lets go at once), and the next code takes a free port; phone pairing, the Wi-Fi listener, the relay and the phone routes stay off. With Phones on, machines never pair or connect over the Wi-Fi listener (`403 machine_not_accepted_here`): the tailnet only. A machine device never gets relay carriage or pushes. Two door routes take only a machine: `link-back` and `unlink`. A machine asking for the merged view (`machines=1`, on any route) is `403 machines_view_refused`. On Linux, a failing `tailscale serve` says to run `sudo tailscale set --operator=$USER` once.

**Linking both ways.** On the machine being linked, `plannotator inbox link --offer [--tailscale]` (or `POST /api/inbox/machines/offer`) prints `plannotator://link?v=1&id=&name=&tailnet=&secret=&code=`; `--tailscale` first publishes the door on the tailnet so the code carries its address. On the other machine, `plannotator inbox link <code> [--address <host:port>] [--back <host:port>] [--one-way]`:
1. It redeems the code at the far door as `platform: "machine"` and reads the far `health` with the new token: its `inbox_id` must match the code's `id`, must not be this Inbox's own, and `machine_links` must be at least 1 (else `machine_needs_update`).
2. It opens a machine offer on its own door and hands it to the far Inbox through `link-back`; the far Inbox redeems it the same way and saves its link. The way back is `--back`, else this Inbox's tailnet door address, published now when it is not yet (linking both ways is the person's consent to it). When it cannot be published, the link is refused (`no_way_back`, with Tailscale's words) unless `--one-way`.
3. When the way back fails, the far device is removed (`unlink`), any device the far side made here is revoked, nothing is saved, and a door this link published comes down again.

**Unlink removes both sides** (rule 13). `plannotator inbox unlink <name or id>` (or `POST /api/inbox/machines/:id/unlink`) tells the other Inbox through its door's `unlink` (5 s), then forgets the link here: the PeerLink stops, the other machine's device on this door is revoked, and every write held for it ends with a notice. `told` is the other door's answer (200, or 401 for a token it no longer knows), never whether the connection stayed up after it. On the other side, when that was its last link, its door comes down 1 s after the answer has left (`UNLINKED_DOOR_CLOSE_MS`; at once if the Inbox stops first), never under the request. When the other machine cannot be reached, it learns at its next contact: its link gets `401 device_revoked`, and it forgets this side the same way, revoking this Inbox's token there. That contact needs this Inbox's tailnet door, so with Phones off the door stays published, even after the last link, while that refusal is owed: its revoked device keeps `refusal_owed_until` in `devices.jsonl`, so a restart publishes the door again. The door comes down 1 s after the token was refused once (`REFUSED_DOOR_CLOSE_MS`), after a week (`UNLINKED_REFUSAL_KEPT_MS`: a laptop closed for a trip still hears it; a machine silent longer is likely gone), or when the person turns the tailnet off (Phones on). It serves nothing new meanwhile: that token is revoked, and the door answers as it does while a machine is linked (no token, pairing with no offer open, or a non-door route is the unknown-route 404). A restart past the week after a crash (kill -9, a panic, a dead battery) that left the door published takes it down once, clears the switch and forgets the lapsed refusal; after a clean stop that start runs no `tailscale` at all. The window and `plannotator inbox unlink` say the door stays, only when the other machine could not be reached. Known gap: when the other machine gets the 401 but never processes it (it stops or crashes first), this door still comes down 1 s later, and that machine shows this one offline until it is unlinked there too.

**A link's line** (`PeerLink`). It dials the far door's `health` with its token, then holds the far event stream from its cursor (`Last-Event-ID`). States: `connecting`, `online`, `offline` (since when, and why), `needs_update` (its version), `revoked`. Only `401 device_revoked` or `401 device_token_invalid` stops a link (with Phones off, the far door answers the second through its tailnet listener, or once a machine is paired there); every other failure redials, 250 ms doubling to 30 s, at once when a timer fires far past its time (the computer slept) or the person acts on that machine (a read or a write through the forward). 20 s with no byte on the stream (the door sends a heartbeat every 15 s) is a dead line. The far list is kept in memory only, refreshed after each record with one fetch in flight at a time, and a list older (by cursor) than the one held is dropped. A machine that goes offline keeps its rows in the merged view from that memory; when the viewing Inbox restarts while the other machine is away, its rows come back when that machine does (accepted: no copy on disk). Records at or before the stream's hello cursor are a resync, marked `live: false`, never a notification. The outbox is sent when the stream says hello and after any request that reached the machine.

**Merged data only on request.** Every existing route stays this Inbox's own. The window asks with `machines=1`:
- `GET /api/inbox/threads?machines=1`: the sections computed over this Inbox's rows and every linked machine's, each row with `machine` (its `ibx_` id); `projects` from every machine, each with `machine`; plus `self` and `machines`. `?project=` takes another machine's project id here.
- `GET /api/inbox/events?machines=1`: the local stream unchanged, plus frames that never carry an `id:` (the local seq and `Last-Event-ID` stay this Inbox's): `machines` (`{ machines }`, a snapshot when the stream opens and on every change), `machine` (`{ machine, seq, live, record }`, a far record with that machine's own seq; `live: false` for a resync), `outbox` (an entry, on every change).
- The door refuses `machines=1` to a machine, so two Inboxes linked both ways cannot echo each other: echo is impossible by construction, not by a per-handler check.
- `GET /api/inbox/sessions` carries `machine`.

**The forward**, `/api/inbox/m/<machine>/<door route>`. A GET forwards any route and the far door decides what is allowed (`404 device_route_not_found` otherwise). A POST is decided by its route in rule 8's table (`doorWriteKind`), never by its Content-Type: a write the table has not classified is `404`, so a new door write reaches another machine only once it is classified. `events`, `pair`, `link-back`, `unlink` and `revoke` are not forwarded, nor a route with an empty, `.` or `..` segment or an encoded dot, slash or backslash.
- A GET passes through (of the window's headers only `Range`, `If-Range`, `If-None-Match`; the answer's status, body, content headers and safety headers: `Content-Security-Policy`, `Cross-Origin-Resource-Policy`, `X-Content-Type-Options`, `X-Image-Width`/`-Height`). Every forwarded answer's CSP holds `sandbox`: the far CSP's directives are kept and `sandbox` is added when it lacks one (`sandbox` alone when it sent none), so an SVG or a page from another machine, even an old, buggy or hostile one with a permissive CSP, never runs script on this origin. Cross-site reads are refused. Unreachable: `503 machine_offline` with the machine's state.
- Every write but a file goes through the outbox, online or not: one path. Its body is read as JSON whatever its Content-Type says. This Inbox's `serverSession` is checked here and stripped, and so is a compose's `draft_id` (drafts stay on this computer). It waits up to 4 s (`MACHINE_WRITE_WAIT_MS`) while the machine is online: the far answer, status and body as its door gave them (`X-Plannotator-Outbox: delivered | refused`; `Idempotent-Replayed: true` for a key seen before). Otherwise `202 { outbox, machine }`: "Sending…", or "Will send when … is back" when it is offline.
- A reply (`messages/:id/reply`) must carry `seen_through_seq`, the `cursor` of the thread read the person saw (`422` without it).
- A file (`uploads`, `markups`) is never held: it streams through while the machine is online, `503 machine_offline` otherwise.

**The outbox** (`inbox-outbox.ts`), on the Inbox where the person pressed Send: `inbox/outbox/<machine id>.jsonl`, 0600, append-only, each line a full snapshot of one entry (the last line per key wins, a torn last line is skipped); compaction at start writes a temp file and renames it. One sender loop per machine, oldest first, one request at a time. Entry states: `queued` (never left), `sending` (a request left, no answer yet), `delivered` (2xx), `refused` (4xx), `parked` (5xx five times in a row; a proxy's 502, 503 or 504, which `tailscale serve` answers when the far Inbox is down, counts as unreachable instead), `dropped` (the link went). The folder is made with the first held write. Only small JSON is held (256 KB). Settled entries are kept 7 days so a retried Send answers them; notices nobody dismissed, 30 days, except a `dropped` entry (its words are the only copy), kept until dismissed. When the link goes, its entries keep the machine's name (`machine_name`), those a drain already ended on the other side's `401 device_revoked` included. The rules, each with its code and test:

**The window** (`packages/inbox/`). Any Inbox's window can show every linked machine; "this machine" is only the one whose window it is. While no machine is linked nothing below is drawn: the list asks `machines=1` and gets this machine alone, and `machinesModel` (`machines.ts`) is empty, so there is no label, line, section or menu item, and a `machines` frame reads nothing more (`linkedMachines.test.tsx`, `machines.test.ts`, e2e 1). The one visible change is Settings → Machines, where the first link starts.
- Routing: `inboxUrl(path, query, machine)` (`inboxUrl.ts`) sends a route of another machine's thread through `/api/inbox/m/<machine>/…`. Which machine owns an id is learned from what that machine sent: its list rows and projects (`machine`), the routed id fields of its thread reads (`id`, `thread_id`, `message_id`, `attachment_id` and the like, never any other `*_id`), its `machine` frames (`rememberMachine`, `idsIn` in `api.ts`). Who owns an id, exactly:
  - The server is the authority for this machine's ids. The forward refuses (`409 id_is_local`) any read or write whose route names a thread, message, file or project this store holds, archived and pinned ones included, and any write whose body names such an id in `thread_id`, `message_id` or `reply_to` (a thread or message), `attachment_id` (a file) or `project_id` (a project); a comment route (`annotations/<id>/…`) of a comment this store holds is refused too. Other body fields are not checked. The merged list drops a linked machine's rows and projects that carry such an id. Whatever a window believes, nothing of this machine's goes to a peer (`inbox-machines.test.ts`, "a peer can never take this Inbox's ids").
  - In the window, local ids come only from this Inbox's own records: the list's own rows and projects (with their delivery and message ids; pinned rows included), the archived list, a read of one of its own threads, and its own `record` events. Those ids are local for good (`rememberLocal`, `localIdsIn`). Any other answer (a kept compose draft that names another machine's project, say) teaches nothing. A `409 id_is_local` makes the id local and sends the same read or write to this Inbox.
  - An id two linked machines both claim routes to neither, in either order: the window refuses its reads and writes with "Two linked machines both claim this thread, so it opens on neither." (`machine_conflict`), and the thread's place says so, with Close and no retry (`machines.test.ts`, "thread ids"). No first or last claim wins.
  - Writes: a forwarded write carries an `idempotency_key` and `X-Plannotator-Thread` (the thread it is about, kept on the held entry); a reply carries `seen_through_seq` from the thread read the person saw. A `202` becomes `InboxHeldError`: a reply then resolves with `held` and the thread shows the outbox entry; a new message resolves with `held`; any other held write (Mark read, archive, a pick) says so with a clock, "Waiting for MacBook: this applies when MacBook is back.", never as an error. A held pick stays drawn as picked, and raises the revision the window holds for that question, so a second pick queued behind it applies there in order; if that machine refuses it, or its link goes first, it is unpicked, the revision goes back, and a toast says why. A `202` for a key that already settled says how it ended (delivered: its answer; refused or dropped: an error), not "waiting".
- A fresh load (a reload, `#thread=<id>` in a new tab) reads the thread before the list has named its machine: a `404` from this Inbox waits for the first list (up to 10 s, `FIRST_LIST_WAIT_MS`) and reads again once the list names the owner (e2e 2c). Right after this Inbox starts (a restart, an update) a linked machine's list may not be read yet: while one that can still send its list (not `needs_update` or `revoked`) has `list_cursor: null`, the 404 is not "deleted": the thread says "Waiting for MacBook: this thread may be there." and is read again on the usual schedule, for at most 2 minutes (`UNLISTED_WAIT_MS`); after that it is missing, and a list that names the owner later opens it there (e2e 2d).
- The list: a row from another machine reads its machine where it reads its project, the way a clash reads its parent folder ("billing-svc · MacBook", `machineProjectNames`); names are told apart within each machine, so the same folder on two machines is not a clash. A filtered machine drops the machine from its labels, as one project's list drops the project. A linked machine that is asleep (`offline`) or `needs_update` greys its rows (`data-away`, the ended-option opacity) under one quiet line, "MacBook asleep since 10:42 AM" or "Update Plannotator on MacBook to see its threads here". The list's ⋯ menu has "Hide offline machines" (a checkbox, this browser's cookie `plannotator-inbox-hide-offline-machines`) while a machine is linked, in its own group after the list options (inbox-window.md); unlike them it closes the menu; the line stays while the rows are hidden.
- The sidebar: Machines, a folder section like Projects, before it: this machine first, then each linked one with its waiting count; a click shows that machine's list (`#machine=<id>`); an away machine reads quiet and its tooltip says since when.
- A thread from another machine says "On MacBook" (or its away line) under the subject. A held answer shows as the person's message with "Sending to MacBook…" or "Will send when MacBook is back", never delivered before that machine's Inbox answered (rule 12); when the `outbox` frame says delivered, the thread is read again and the reply shows in it. A write that did not land says why ("Not delivered: …", "May have been delivered. Check on MacBook.") with Dismiss. A thread of an asleep machine that is not on screen yet says the away line, shows the held answers the window tied to it (`thread`), and opens once the machine is back (e2e 4); on a phone or a stacked window this takes the thread's place too. A held line by state: online or connecting "Sending to MacBook…", asleep "Will send when MacBook is back", out of date "Will send when MacBook is updated", removed there "Not sent: MacBook removed the link."
- Events: `machine` frames of the open thread's machine read the thread again; a `machines` frame whose states or `list_cursor`s moved reads the merged list again (a machine linked, its first list read, or unlinked from either side puts that list on screen at once, so an unlinked machine's rows go with it; e2e 7); `outbox` frames update the held writes. Every `machines` frame (the stream sends one on each connect) reads `/outbox` again, so a `delivered` frame lost in a reconnect is caught up, and the open thread is read again when one of its machine's writes settled.
- Settings → Machines (`components/Machines.tsx`, shown while the list names this machine): one card like Devices → Phones, a row per linked machine (its state, version, last seen, "Needs update · runs 0.28.30", writes waiting) with Unlink asked twice (the second ask says what is lost: "Unlink? 2 waiting to send will be lost. Click again"; an Unlink the other machine could not hear says it drops the link at its next contact), "Link a machine" (paste a link code, or an address and six digits; only the Link button sends), and "This machine's link code" (`offer` with `tailscale`; its line says before the click that showing a code puts this Inbox on the tailnet with Tailscale Serve, and the code goes once a new machine links). Linking and Unlink are local only, like Pair a phone. Under the card, "Not sent" keeps what was waiting for a machine that is no longer linked (an Unlink here or on that machine; the outbox keeps the machine's name, `machine_name`): its words to copy, until dismissed. When the window learns of such an unlink, a toast says "Not sent to MacBook: it is no longer linked." Nothing held is dropped silently.
- Stays on this computer: pins, reply drafts (a draft for another machine's thread is not saved), Open in, a linked page.
- `PLANNOTATOR_MACHINE_NAME` names this computer to phones and linked machines (environment.md).

**Known gap (accepted for Phase 1).** A held answer and its later notice exist only on the Inbox that holds it. Another machine's window does not show that an answer is waiting there.

**Routes** (window routes behind the window's guards; linking and unlinking answer only on this computer, `403 local_only` through the tailnet):
- `GET /api/inbox/machines`: `{ self, machines: [{ id, name, self, state, since, reason, version, address, both_ways, waiting, list_cursor }] }`. `list_cursor`: the cursor of that machine's list this Inbox holds (null for this machine); it moves when the far list was read again, so a `machines` frame tells the window its merged list changed.
- `POST /api/inbox/machines/offer` `{ serverSession?, tailscale? }`: `201 { link, code, expires_at, machine, tailnet, tailnet_error }`.
- `POST /api/inbox/machines/link` `{ serverSession?, link | code, address?, back?, one_way? }`: `201 { machine }`; refusals `offer_expired`, `pairing_code_wrong`, `machine_unreachable`, `machine_needs_update`, `machine_mismatch`, `link_to_self`, `no_way_back`.
- `POST /api/inbox/machines/:id/unlink` `{ serverSession? }`: `{ unlinked, told }`.
- `GET /api/inbox/outbox[?machine=]`: `{ waiting, notices }`, each entry with `words` (a held reply's or message's words, cut at 2,000 characters then "…", for the thread to show while it waits) and `thread` (named by the window in `X-Plannotator-Thread`); `POST /api/inbox/outbox/:key/dismiss`.
- `/api/inbox/m/<machine>/<door route>`: the forward.
- The CLI's control routes (the registry's bearer token): `GET /api/inbox/control/machines`, `POST /api/inbox/control/machines/offer | link | unlink` (`unlink` takes `{ machine }`, a name or id).
- `health` adds `inbox_id` and `machine_links` (the protocol, 1).

**Proofs.**
- `packages/server/inbox-machines.test.ts`: three real Inboxes (`plannotator inbox --background`, each its own temp HOME and data dir, Phones off, `PLANNOTATOR_INBOX_CONNECT=0`, `PLANNOTATOR_UPDATE_CHECK=0`, no browser) linked through the real CLI pairing, the tailnet transport pointed at the other Inbox's loopback port. A `tailscale` stand-in on PATH records any call, and the test asserts none happened. An agent on B asks; A's merged list and stream show it; the person answers from A through the forward and B's agent reads it (`read_thread` over MCP). B's Inbox killed: offline, rows kept, the answer held (`202`), B started again, the answer delivered exactly once and the agent reads it. Late words refused (rule 11), a `text/plain` reply included. An SVG on B opened from A keeps B's `sandbox` CSP; in process, a peer sending `default-src *` still gets `; sandbox` added. No echo with C linked to B only, through a resync both ways; a machine token asking `machines=1` is refused. Unlink both up, and with B asleep (B cleans up at its next contact; both tokens revoked).
