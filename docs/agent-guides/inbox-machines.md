## Inbox: linked machines

**The rule: one experience across a person's devices** (the owner, 2026-11-13: "It's all one unified experience for me … No arbitrary rules, this isn't some made-up enterprise scenario, this is an open source tool that needs to work seamlessly across people's devices"). A feature is done only when it works on another linked machine's thread, agent or project the same way it works on this machine's own: the same menu item, the same result, seen from either machine. A thread lives on one machine, so the action goes to that machine (as snooze and Priority do); that is plumbing, never a reason to hide the feature. The one allowed gap is a linked machine that is older or offline: the item is left out for its threads until it updates, with no error and no explanation dialog. Do not add a per-machine rule, switch or warning for any other reason.

- Building a feature: add the far-machine path and its capability check in the same PR, and prove it with two linked Inboxes, both directions.
- Known gaps, each a bug against this rule, to close: the Board's New card makes a card in this machine's projects only (a linked machine's cards are listed and changed there, "The Board" below); a reply draft for another machine's thread is not saved (`inbox-messages.md`); Settings → Accounts switches accounts on this machine only (`inbox-accounts.md`). When you find another, add it here and fix it.

One Inbox across machines, Phase 1: the server engine, then the window (see "The window" below). The design and the formal model live outside the repo (`.ops/multi-machine/PLAN.md`, `model/FINDINGS.md`); this guide is what is built.

**The shape.** Every machine keeps its own Inbox, exactly as before: its agents, files, wakes and offline behavior do not change. There is no home machine and no machine is special. One pairing code links two Inboxes both ways, and each then shows every machine's threads. A thread lives only on the machine whose agent started it; every other Inbox is a view of it and a remote control. No Inbox stores another's threads on disk, and no Inbox passes one machine's data on to a third.

**Files** (`packages/server/`), one job each:
- `inbox-machines.ts`: the coordinator. Linking and unlinking, the merged view, the forward, the window's and the CLI's routes, and the two door routes only a machine calls. Nothing else in the route table knows about links.
- `inbox-links.ts`: the one place linking state lives, `inbox/machines.json` (0600, temp file then rename): `{ v: 1, self: { id }, links: [{ id, name, token, transport, device_id, linked_at }] }`. `self.id` is this Inbox's stable id (`ibx_…`), served by `health`; links key on it, never on an address. Nothing is written until the first offer or link (an Inbox that never links keeps no file, and its id lives in memory until then); a file that cannot be read is moved aside to `machines.json.unreadable-<time>`, never written over. A link to an id already linked replaces it; a link to this Inbox's own id is refused (`link_to_self`). Also the pairing link format.
- `inbox-peer-link.ts`: one live link per machine (`PeerLink`).
- `inbox-outbox.ts`: the outbox and its rules.
- `inbox-transport.ts`: the transport seam, two calls (one request to the door, its event stream). `inbox-transport-tailnet.ts`: the one transport, HTTPS over the tailnet to the other Inbox's door (`https://<MagicDNS name>:<port>/api/inbox/device/*`, Tailscale's real certificate; the port is the one that door took, 8443 to 8450, and travels in the address). Only a `<machine>.<tailnet>.ts.net` name over https is taken, never another host, an IP or `localhost`, so a pasted code, `--address`, `--back` or a linked machine's `link-back` can never send a pairing secret or a token off the tailnet. Plain `http://` to a loopback host is taken only inside a test sandbox (`PLANNOTATOR_TEST_SANDBOX`, two Inboxes on one computer). The event stream's answer has the same 20 s deadline as its silence, so a machine that sleeps between `health` and `events` never hangs the line. A later transport (the relay, or a server reachable only over SSH) is one more file and one more `kind`; SSH between peers is out by design (laptops have no sshd and sit behind NAT).

**The door, with Phones off** (`inbox-devices.ts`). A linked Inbox is a device with platform `machine`, redeemed from a machine offer (its own slots, the same limits as a phone's: 10 minutes, 5 wrong codes). This works with `PLANNOTATOR_INBOX_PHONES` off: the door then answers a machine's token (a revoked one gets `401 device_revoked`), `pair` only while a machine offer is open, and a token it does not know with `401 device_token_invalid` when the request came through the tailnet's listener or a machine is paired here (so a machine whose link was wiped by a reinstall re-pairs, and its held writes end with their notice). To anything else, Origin header or not, it is the unknown-route 404 it always was. The tailnet door (8443, or the next free port up to 8450 at its first publish, then that port for good: a start that finds it held refuses and says why in `machines` (this machine's `reason`) and `link --list`, rather than move; see "Reach from my tailnet" in `inbox-foundation.md`) publishes at start only while a machine is linked or an unlinked machine is still owed its refusal (below; with neither, a start never runs `tailscale`, so a leftover a crash left waits for a link, Phones, or `uninstall --purge`), and comes down (the switch cleared) after the last unlink that reached the other machine, once an unlinked machine's refusal was answered or its week ran out, or when an offer that published it expires unused. With the port held and nothing linked, there is nothing to unlink, so the refusal says the port is let go of once no link code is open (10 minutes; a link that could not publish its way back lets go at once), and the next code takes a free port; phone pairing, the Wi-Fi listener, the relay and the phone routes stay off. With Phones on, machines never pair or connect over the Wi-Fi listener (`403 machine_not_accepted_here`): the tailnet only. A machine device never gets relay carriage or pushes. Three door routes take only a machine: `link-back`, `unlink` and `GET accounts` (this Inbox's own accounts read, of its query only `fresh`; see [`inbox-accounts.md`](inbox-accounts.md)). A machine asking for the merged view (`machines=1`, on any route) is `403 machines_view_refused`. On Linux, a failing `tailscale serve` says to run `sudo tailscale set --operator=$USER` once. An Inbox that started while Tailscale was not running (a restart, the computer just woke) publishes its door once Tailscale runs, and re-points a mapping a crashed or stopped run of its own left on its port, where a connect is refused now; until then the other machine reads it `offline` (`health answered 502` while that dead mapping answers). See "Publishing again by itself" and the door's paragraph in `inbox-foundation.md` (`INBOX_DOOR_REPUBLISH`).

**Linking both ways.** On the machine being linked, `plannotator inbox link --offer [--tailscale]` (or `POST /api/inbox/machines/offer`) prints `plannotator://link?v=1&id=&name=&tailnet=&secret=&code=`; `--tailscale` first publishes the door on the tailnet so the code carries its address. On the other machine, `plannotator inbox link <code> [--address <host:port>] [--back <host:port>] [--one-way]`:
1. It redeems the code at the far door as `platform: "machine"` and reads the far `health` with the new token: its `inbox_id` must match the code's `id`, must not be this Inbox's own, and `machine_links` must be at least 1 (else `machine_needs_update`).
2. It opens a machine offer on its own door and hands it to the far Inbox through `link-back`; the far Inbox redeems it the same way and saves its link. The way back is `--back`, else this Inbox's tailnet door address, published now when it is not yet (linking both ways is the person's consent to it). When it cannot be published, the link is refused (`no_way_back`, with Tailscale's words) unless `--one-way`.
3. When the way back fails, the far device is removed (`unlink`), any device the far side made here is revoked, nothing is saved, and a door this link published comes down again.

**Unlink removes both sides** (rule 13). `plannotator inbox unlink <name or id>` (or `POST /api/inbox/machines/:id/unlink`) tells the other Inbox through its door's `unlink` (5 s), then forgets the link here: the PeerLink stops, the other machine's device on this door is revoked, and every write held for it ends with a notice. `told` is the other door's answer (200, or 401 for a token it no longer knows), never whether the connection stayed up after it. On the other side, when that was its last link, its door comes down 1 s after the answer has left (`UNLINKED_DOOR_CLOSE_MS`; at once if the Inbox stops first), never under the request. When the other machine cannot be reached, it learns at its next contact: its link gets `401 device_revoked`, and it forgets this side the same way, revoking this Inbox's token there. That contact needs this Inbox's tailnet door, so with Phones off the door stays published, even after the last link, while that refusal is owed: its revoked device keeps `refusal_owed_until` in `devices.jsonl`, so a restart publishes the door again. The door comes down 1 s after the token was refused once (`REFUSED_DOOR_CLOSE_MS`), after a week (`UNLINKED_REFUSAL_KEPT_MS`: a laptop closed for a trip still hears it; a machine silent longer is likely gone), or when the person turns the tailnet off (Phones on). It serves nothing new meanwhile: that token is revoked, and the door answers as it does while a machine is linked (no token, pairing with no offer open, or a non-door route is the unknown-route 404). A restart past the week after a crash (kill -9, a panic, a dead battery) that left the door published takes it down once, clears the switch and forgets the lapsed refusal; after a clean stop that start runs no `tailscale` at all. The window and `plannotator inbox unlink` say the door stays, only when the other machine could not be reached. Known gap: when the other machine gets the 401 but never processes it (it stops or crashes first), this door still comes down 1 s later, and that machine shows this one offline until it is unlinked there too.

**A link's line** (`PeerLink`). It dials the far door's `health` with its token, then holds the far event stream from its cursor (`Last-Event-ID`). States: `connecting`, `online`, `offline` (since when, and why), `needs_update` (its version), `revoked`. Only `401 device_revoked` or `401 device_token_invalid` stops a link (with Phones off, the far door answers the second through its tailnet listener, or once a machine is paired there); every other failure redials, 250 ms doubling to 30 s, at once when a timer fires far past its time (the computer slept) or the person acts on that machine (a read or a write through the forward). 20 s with no byte on the stream (the door sends a heartbeat every 15 s) is a dead line. The far list is kept in memory only, refreshed after each record with one fetch in flight at a time, and a list older (by cursor) than the one held is dropped. A machine that goes offline keeps its rows in the merged view from that memory; when the viewing Inbox restarts while the other machine is away, its rows come back when that machine does (accepted: no copy on disk). Records at or before the stream's hello cursor are a resync, marked `live: false`, never a notification. The outbox is sent when the stream says hello and after any request that reached the machine.

**Merged data only on request.** Every existing route stays this Inbox's own. The window asks with `machines=1`:
- `GET /api/inbox/threads?machines=1`: the sections computed over this Inbox's rows and every linked machine's, each row with `machine` (its `ibx_` id); `projects` from every machine, each with `machine`; plus `self` and `machines`. `?project=` takes another machine's project id here.
- `GET /api/inbox/events?machines=1`: the local stream unchanged, plus frames that never carry an `id:` (the local seq and `Last-Event-ID` stay this Inbox's): `machines` (`{ machines }`, a snapshot when the stream opens and on every change), `machine` (`{ machine, seq, live, record }`, a far record with that machine's own seq; `live: false` for a resync), `outbox` (an entry, on every change).
- The door refuses `machines=1` to a machine, so two Inboxes linked both ways cannot echo each other: echo is impossible by construction, not by a per-handler check.
- `GET /api/inbox/sessions` carries `machine`.
- The list's `agents` (the sidebar's Agents section; `server-and-storage.md`, `packages/server/inbox-agents-list.ts`): this Inbox's group first, then each linked machine's, taken from that machine's own list (`PeerLink.acceptList`, capped again here) and named by `machine`. Its `deliveries` frame with `agents` reads its list again and tells this Inbox's windows (`agents: true`); the window reads the list for it only while something draws the agents (`packages/inbox/agentsList.ts`).

**The forward**, `/api/inbox/m/<machine>/<door route>`. A GET forwards any route and the far door decides what is allowed (`404 device_route_not_found` otherwise). A POST is decided by its route in rule 8's table (`doorWriteKind`), never by its Content-Type: a write the table has not classified or calls `local` is `404`, so a new door write reaches another machine only once it is classified as one that can. `events`, `pair`, `link-back`, `unlink`, `revoke` and `accounts` are not forwarded (a linked machine's accounts have their own route, behind the owner's check), nor a route with an empty, `.` or `..` segment or an encoded dot, slash or backslash.
- A GET passes through (of the window's headers only `Range`, `If-Range`, `If-None-Match`; the answer's status, body, content headers and safety headers: `Content-Security-Policy`, `Cross-Origin-Resource-Policy`, `X-Content-Type-Options`, `X-Image-Width`/`-Height`). The far machine's CSP is never trusted (`passAnswer`; `farCsp` and `machineAssetCsp` in `packages/server/inbox-machine-page.ts`). An answer from a far page's folder (`html-assets/…`) gets a local folder's CSP whatever it sent: `INBOX_HTML_DOCUMENT_CSP` for a page, `HTML_ASSET_SUBRESOURCE_CSP` for anything else. Every other forwarded answer (a picture opened in its own tab included) keeps the far directives, but every `sandbox` loses `allow-same-origin`, `allow-top-navigation…` and `allow-popups-to-escape-sandbox`, and `sandbox` is added when there is none. `X-Content-Type-Options: nosniff` is always set. So an SVG or a page from another machine, even an old, buggy or hostile one, never runs as this origin. Cross-site reads are refused. Unreachable: `503 machine_offline` with the machine's state.
- Every write but a file goes through the outbox, online or not: one path. Its body is read as JSON whatever its Content-Type says. This Inbox's `serverSession` is checked here and stripped, and so is a compose's `draft_id` (drafts stay on this computer). It waits up to 4 s (`MACHINE_WRITE_WAIT_MS`) while the machine is online: the far answer, status and body as its door gave them (`X-Plannotator-Outbox: delivered | refused`; `Idempotent-Replayed: true` for a key seen before). Otherwise `202 { outbox, machine }`: "Sending…", or "Will send when … is back" when it is offline.
- A reply (`messages/:id/reply`) must carry `seen_through_seq`, the `cursor` of the thread read the person saw (`422` without it).
- A write that starts, stops or trusts an agent on the other machine (`startsAgentThere`) is taken only from this Inbox's window (`isWindowRequest`), else `403 window_only`. A write from the window is held with `window: true` and sent with `X-Plannotator-Window: 1`, which the far door believes only from a machine's token; there it lets a launch, a launch action and a permission answer through (`inbox-launch.md`, "From another linked machine").
- A file (`uploads`, `markups`) is never held: it streams through while the machine is online, `503 machine_offline` otherwise.
- Reuse ("Reuse a file" in `inbox-files-and-guides.md`) is this Inbox's own: another machine's thread offers no button, and the forward answers `404`: rule 8's table calls `uploads/reuse` `local`. It is useful only as its answer, the new upload's id, so holding it would answer `202` with no id and run it later for nobody. A second copy at this Inbox's own door (a phone's retry the door's log missed) leaves a pending upload nothing names, which the 24-hour sweep takes.

**The outbox** (`inbox-outbox.ts`), on the Inbox where the person pressed Send: `inbox/outbox/<machine id>.jsonl`, 0600, append-only, each line a full snapshot of one entry (the last line per key wins, a torn last line is skipped); compaction at start writes a temp file and renames it. One sender loop per machine, oldest first, one request at a time. Entry states: `queued` (never left), `sending` (a request left, no answer yet), `delivered` (2xx), `refused` (4xx), `parked` (5xx five times in a row; a proxy's 502, 503 or 504, which `tailscale serve` answers when the far Inbox is down, counts as unreachable instead), `dropped` (the link went), `cancelled` (taken back before it left, never sent). The folder is made with the first held write. Only small JSON is held (256 KB). Settled entries are kept 7 days so a retried Send answers them; notices nobody dismissed, 30 days, except a `dropped` entry (its words are the only copy), kept until dismissed. When the link goes, its entries keep the machine's name (`machine_name`), those a drain already ended on the other side's `401 device_revoked` included. The rules, each with its code and test:

**The window** (`packages/inbox/`). Any Inbox's window can show every linked machine; "this machine" is only the one whose window it is. While no machine is linked nothing below is drawn: the list asks `machines=1` and gets this machine alone, and `machinesModel` (`machines.ts`) is empty, so there is no label, line, section or menu item, and a `machines` frame reads nothing more (`linkedMachines.test.tsx`, `machines.test.ts`, e2e 1). The one visible change is Settings → Machines, where the first link starts.
- Routing: `inboxUrl(path, query, machine)` (`inboxUrl.ts`) sends a route of another machine's thread through `/api/inbox/m/<machine>/…`. Which machine owns an id is learned from what that machine sent: its list rows and projects (`machine`), the routed id fields of its thread reads (`id`, `thread_id`, `message_id`, `attachment_id` and the like, never any other `*_id`), its `machine` frames (`rememberMachine`, `idsIn` in `api.ts`). Who owns an id, exactly:
  - The server is the authority for this machine's ids. The forward refuses (`409 id_is_local`) any read or write whose route names a thread, message, file or project this store holds, archived and pinned ones included, and any write whose body names such an id in `thread_id`, `message_id` or `reply_to` (a thread or message), `attachment_id` (a file) or `project_id` (a project); a comment route (`annotations/<id>/…`) of a comment this store holds is refused too. Other body fields are not checked. The merged list drops a linked machine's rows and projects that carry such an id. Whatever a window believes, nothing of this machine's goes to a peer (`inbox-machines.test.ts`, "a peer can never take this Inbox's ids").
  - In the window, local ids come only from this Inbox's own records: the list's own rows and projects (with their delivery and message ids; pinned rows included), the archived list, a read of one of its own threads, and its own `record` events. Those ids are local for good (`rememberLocal`, `localIdsIn`). Any other answer (a kept compose draft that names another machine's project, say) teaches nothing. A `409 id_is_local` makes the id local and sends the same read or write to this Inbox.
  - An id two linked machines both claim routes to neither, in either order: the window refuses its reads and writes with "Two linked machines both claim this thread, so it opens on neither." (`machine_conflict`), and the thread's place says so, with Close and no retry (`machines.test.ts`, "thread ids"). No first or last claim wins.
  - Writes: a forwarded write carries an `idempotency_key` and `X-Plannotator-Thread` (the thread it is about, kept on the held entry); a reply carries `seen_through_seq` from the thread read the person saw. A `202` becomes `InboxHeldError`: a reply then resolves with `held` and the thread shows the outbox entry; a new message resolves with `held`; any other held write (Mark read, archive, a pick) says so with a clock, "Waiting for MacBook: this applies when MacBook is back.", never as an error. A held pick stays drawn as picked, and raises the revision the window holds for that question, so a second pick queued behind it applies there in order; if that machine refuses it, or its link goes first, it is unpicked, the revision goes back, and a toast says why. A `202` for a key that already settled says how it ended (delivered: its answer; refused or dropped: an error), not "waiting".
- A fresh load (a reload, `#thread=<id>` in a new tab) reads the thread before the list has named its machine: a `404` from this Inbox waits for the first list (up to 10 s, `FIRST_LIST_WAIT_MS`) and reads again once the list names the owner (e2e 2c). Right after this Inbox starts (a restart, an update) a linked machine's list may not be read yet: while one that can still send its list (not `needs_update` or `revoked`) has `list_cursor: null`, the 404 is not "deleted": the thread says "Waiting for MacBook: this thread may be there." and is read again on the usual schedule, for at most 2 minutes (`UNLISTED_WAIT_MS`); after that it is missing, and a list that names the owner later opens it there (e2e 2d).
- The list: a row from another machine reads its machine where it reads its project, the way a clash reads its parent folder ("billing-svc · MacBook", `machineProjectNames`); names are told apart within each machine, so the same folder on two machines is not a clash. A filtered machine drops the machine from its labels, as one project's list drops the project. A linked machine that is asleep (`offline`) or `needs_update` greys its rows (`data-away`, the ended-option opacity) under one quiet line, "MacBook asleep since 10:42 AM" or "Update Plannotator on MacBook to see its threads here". The list's ⋯ menu has "Hide offline machines" (a checkbox, this browser's cookie `plannotator-inbox-hide-offline-machines`) while a machine is linked, in its own group after the list options (inbox-window.md); unlike them it closes the menu; the line stays while the rows are hidden.
- The sidebar: the Agents section (`inbox-window.md`, "The Agents section") names each machine above its agents, this machine first, as a small quiet caption with no count; a click on the caption shows that machine's list (`#machine=<id>`), and a click on an agent shows that agent's threads (`#agent=<id>`, in place of the machine's filter); an away machine reads quiet and its tooltip says since when. With no machine linked Agents is one flat list with no caption.
- A thread from another machine says "On MacBook" (or its away line) under the subject. A held answer shows as the person's message with "Sending to MacBook…" or "Will send when MacBook is back", never delivered before that machine's Inbox answered (rule 12); when the `outbox` frame says delivered, the thread is read again and the reply shows in it. A write that did not land says why ("Not delivered: …", "May have been delivered. Check on MacBook.") with Dismiss. A thread of an asleep machine that is not on screen yet says the away line, shows the held answers the window tied to it (`thread`), and opens once the machine is back (e2e 4); on a phone or a stacked window this takes the thread's place too. A held line by state: online or connecting "Sending to MacBook…", asleep "Will send when MacBook is back", out of date "Will send when MacBook is updated", removed there "Not sent: MacBook removed the link."
- Events: `machine` frames of the open thread's machine read the thread again; a `machines` frame whose states or `list_cursor`s moved reads the merged list again (a machine linked, its first list read, or unlinked from either side puts that list on screen at once, so an unlinked machine's rows go with it; e2e 7); `outbox` frames update the held writes. Every `machines` frame (the stream sends one on each connect) reads `/outbox` again, so a `delivered` frame lost in a reconnect is caught up, and the open thread is read again when one of its machine's writes settled. A list or `/machines` read that began before the latest `machines` frame leaves the machines as that frame set them (`data/machineViews.ts`): the frame is newer, and a read in flight at a Try Again would put "Failed" back over "Updating" until the next change.
- Settings → Machines (`components/Machines.tsx`, shown while the list names this machine): one card like Devices → Phones, a row per linked machine (its state, version, last seen, "Needs update · runs 0.28.30", writes waiting) with Unlink asked twice (the second ask says what is lost: "Unlink? 2 waiting to send will be lost. Click again"; an Unlink the other machine could not hear says it drops the link at its next contact), "Link a machine" (paste a link code, or an address and six digits; only the Link button sends), and "This machine's link code" (`offer` with `tailscale`; its line says before the click that showing a code puts this Inbox on the tailnet with Tailscale Serve, and the code goes once a new machine links). Linking and Unlink are the owner's, from this computer or their other devices over the tailnet, like Pair a phone. Under the card, "Not sent" keeps what was waiting for a machine that is no longer linked (an Unlink here or on that machine; the outbox keeps the machine's name, `machine_name`): its words to copy, until dismissed. When the window learns of such an unlink, a toast says "Not sent to MacBook: it is no longer linked." Nothing held is dropped silently.
- A snooze lives on the thread's home machine (`threads/:id/snooze` goes through the forward and the outbox; the stream asks `snoozes=1`); see "Snoozed threads" in `inbox-messages.md`. A list that keeps snoozes says `snoozes: true`, and a machine's view carries it (`snoozes`, true for this machine): the window offers Snooze on a linked machine's rows and threads only when it is true (`rowSnoozes`, `packages/inbox/machines.ts`), so an older Inbox on the other end never gets one: an Inbox before 0.28.46 has no snooze route, and a write to it would answer `404 device_route_not_found` and leave a refused notice. **Update on a linked machine** (approved record `.product/approved/inbox-machine-update/`). A person connected to a machine updates it from here, and the far machine does all the work.
- **The far machine's door.** `GET update` and `POST update` answer a linked machine's token only (the machine-only block in `inbox-devices.ts`, like its accounts): never on the allowlist, so a phone and a relay command get `404`. `POST` never reads its body, so no caller can name a version or a place to download from. It runs exactly Update now (`machineStart` in `inbox-updates.ts`): the same `update.lock`, checksum pin, log and result file, after asking GitHub itself so it installs its own newest answer. A running install (a terminal's `plannotator update`, a second press) is joined (`joined`); a binary already on disk is only a restart (`restarting`).
- **It restarts itself.** The local window drives a local restart; the far machine has no window waiting. Once a press is pending and the lock is gone, a fresh look at the binary decides (`settleMachineUpdate`): a new binary restarts through the same path as the window's Restart, even with someone typing there (their words return as a draft, a file pasted into an unsent reply is lost: the owner's call); a failed install stays on the old version in the `failed` state; anything else is `update_no_change`, said on health and status frames, so an installer that exits 0 with an unchanged binary reads as failed and never as Update again. A new binary nobody pressed Update for never restarts it.
- **What it sends.** `GET update` answers only `{ current, update, platform, log, flags, open_reviews, failure }`. The log is `~/…` (`machinePath`): a username stays on that machine. A review is a count. `flags` are the install flags it remembers, as ids. `failure` is its exit code and the plain reason, with `~` for the home folder and any other temp folder left out. `health` adds `machine_update: 1`, `self_update` and `update_no_change`.
- **This machine.** Nothing is stored: that machine's own state is the truth, heard from its `health` and its `status` frames (`parseFarUpdate` keeps a state, a version that reads as one, and whether the script owns it; no URL and no command). `machineUpdateView` turns that into `MachineView.update`, `{ phase, target, from, can_update, self_update }`, phases `behind`, `updating`, `ready`, `failed`, `restarting`, `not_back` (3 minutes), `updated` (shown 2 minutes). During a press, a far `ready` reads `updating`: the install script runs on after it swaps the binary, and that machine restarts itself when it ends, so only a binary nobody pressed Update for reads `ready`. Latest is the newest of its own check, this machine's version, and the newest release this machine knows of; a machine ahead or level says nothing (null), and a machine older than this one is told by its own Update button. A press that machine answers up to date (this Inbox runs ahead of GitHub's latest) takes the word away (`saidUpToDate`, in memory) until a newer release or that machine's own answer brings it back. A timer sends the `machines` frame when a phase changes by the clock. Press state (`asked`) lives in memory, and a restart here just reads the truth again. `snooze_old` says a list was read and keeps no snoozes; a list not read yet says nothing.
- **The route.** `GET /api/inbox/machines/:id/update` reads the dialog's facts, picked by name (`parseFarDetails`); the install command comes from this Inbox's own table by that machine's platform and remembered flags, and a log that does not read as a path to `update.log` is dropped (`too_old: true` on a door `404`). `POST` always sends that machine `{}`. Refused: another site (`403`, by the guards before this route), a stale tab (`409`), asleep (`503 machine_offline`, nothing sent and nothing held), an Inbox from before the route (`409 machine_too_old`). The forward refuses `update` and the outbox never holds it (an Update that waits days and runs when a machine wakes is not what anyone pressed). `POST update` is on `DOOR_WRITES` only so rule 8 knows it.
- **The window** (`components/MachineUpdate.tsx`, `machineNotice` in `machines.ts`). A machine that is behind has the word Update beside it, beside its caption in the sidebar's Agents and on its Settings → Machines row, whichever way it can be updated; the word is its own target, and the row beside it still filters. Then the row reads Updating, Restart, Restarting, Updated, Failed or Not back. Absent on a page that offers no updates (`pageOffersUpdates`), the Settings row's words included. No keyboard shortcut. Nothing in `packages/ui`.

The agent picked is an idle one before a busy one, then the most recently seen. Then the window tells this Inbox (`POST /api/inbox/machines/:id/update/asked`, `PeerLink.agentAsked`, in memory for 30 minutes, `AGENT_ASK_KEPT_MS`): the view carries `asked: { thread, agent, at }`, the row's word reads Asked, and the dialog says "Asked <agent> on <machine>" with Open the thread (or "Sending to <machine>…" while the outbox holds it). Gone after the ask reads `restarting` for a restart's time (never `not_back`: a machine that sleeps after an ask nobody acted on is only asleep); back on a new version is `updated`, as after a press. No agent running there: it says so, and where an agent can start there (`launch: true`, launch on here) offers "Start an agent on <machine>": New message with the words, To a new agent in a scratch folder there; its Send tells this Inbox the same way. Asleep: it says to wake it, with no request. The three commands stay as the fallback, folded under "Or update it yourself" while an agent can do it, open when nothing here can. **Known gap (accepted for Phase 1).** A held answer and its later notice exist only on the Inbox that holds it. Another machine's window does not show that an answer is waiting there.

**Routes** (window routes behind the window's guards; linking and unlinking answer this computer and its owner's other devices over the tailnet):
- `GET /api/inbox/machines`: `{ self, machines: [{ id, name, self, state, since, reason, version, address, both_ways, waiting, list_cursor, snoozes, launch, message_deletions }] }`, plus `launch_reads: { [id]: { launch, home } }` with `?launch_reads=1` (compose asks): each linked machine's last good launch read, in memory only, so New message lists an asleep machine's projects in a fresh window (`inbox-launch.md`). `message_deletions`: that machine's store takes a Delete on an agent message's words (its health's `message_deletions: 1`; true for this machine, false until the line connected and for an older Inbox). Delete shows on every agent message; when a Delete on a machine that does not say so is refused with 422 (its store's own words), the thread's error line reads "<machine> needs an update to delete words · Update" instead (`saveMessageComment` in Thread.tsx; Update is ThreadPane's `onMachineUpdate`, which opens that machine's `MachineUpdateDialog`, as the sidebar's word does; absent where the page offers no updates, and the line has no Update). Any other failure keeps its own words. `launch`: agents can start there (true), launch is off there (false), or its Inbox is too old to say (null; null for this machine), from its health when the line connected. `list_cursor`: the cursor of that machine's list this Inbox holds (null for this machine); it moves when the far list was read again, so a `machines` frame tells the window its merged list changed.
- `POST /api/inbox/machines/offer` `{ serverSession?, tailscale? }`: `201 { link, code, expires_at, machine, tailnet, tailnet_error }`.
- `POST /api/inbox/machines/link` `{ serverSession?, link | code, address?, back?, one_way? }`: `201 { machine }`; refusals `offer_expired`, `pairing_code_wrong`, `machine_unreachable`, `machine_needs_update`, `machine_mismatch`, `link_to_self`, `no_way_back`.
- `POST /api/inbox/machines/:id/unlink` `{ serverSession? }`: `{ unlinked, told }`.
- `GET /api/inbox/outbox[?machine=]`: `{ waiting, notices }`, each entry with `words` (a held reply's or message's words, cut at 2,000 characters then "…", for the thread to show while it waits) and `thread` (named by the window in `X-Plannotator-Thread`); `POST /api/inbox/outbox/:key/dismiss`; `POST /api/inbox/outbox/:key/cancel` (`{ serverSession? }`): a `queued` write is `cancelled` and never sent, else `409 outbox_already_sent`, `404 not_found`.
- `GET|POST /api/inbox/machines/:id/update`: Update on that machine; see "Update on a linked machine".
- `POST /api/inbox/machines/:id/update/asked`: an agent on that older machine was asked to update it; see "Ask an agent there".
- `/api/inbox/m/<machine>/<door route>`: the forward.
- `GET /api/inbox/accounts/<machine>[?fresh=1]`: that machine's accounts (inbox-accounts.md); 404 `machine_not_linked`.
- The CLI's control routes (the registry's bearer token): `GET /api/inbox/control/machines`, `POST /api/inbox/control/machines/offer | link | unlink` (`unlink` takes `{ machine }`, a name or id).
- `health` adds `inbox_id` and `machine_links` (the protocol, 1), and `launch_from_machines` (1 while launch is on, 0 while it is off).
