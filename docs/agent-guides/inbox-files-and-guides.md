## Inbox: files, annotations, and guided reviews

**Attachments and annotation** (record 2.1 to 2.8; files shown as they are now, versioned; any kind and from anywhere since the owner's 2026-10-10 ruling, design record not in this repo: "make it very accessible and ergonomic for an agent to point out a file so it shows").
- `send_message` takes `attachments: [path]`: absolute (anywhere the agent's user can read) or relative to `project_path`, or to the folder the agent works in when its connection names one (`INBOX_WORKING_FOLDER_META_KEY`, the Claude Code mod after a shell `cd`; see "A session's project" in `inbox-foundation.md`).
- At send time, `recordInboxAttachments` (`packages/shared/inbox/attachments.ts`) resolves each path to its realpath and checks every file before committing anything, with no size bound. It refuses only:
  - a path that is not a regular file (a folder answers "attach the files in it, or a zip of them"; a FIFO or device is refused without blocking)
  - the dotenv family, by the named path's name and by its target's (`inboxAttachmentNameRefusal`, annotate's rule: `.env` and any name ending in `.env` such as `prod.env`, `.envrc`, and any `.env.` name outside the annotatable doc set, so `.env.example` stays)
- Bytes are streamed with async reads (1 MiB chunks, one `O_NOFOLLOW|O_NONBLOCK` handle checked against the stat by dev/ino, so a 3 GB send blocks no other route) through the sha256 into a temp blob, renamed to `inbox/blobs/<sha256>` (the sent version) once every file read, so a file of any size never sits in memory. The send primes the current-file hash cache. A `.send.*.tmp` a crash left is swept at start and on delete once older than 10 minutes.
- The kind (`decideInboxAttachmentKind`): Plannotator's documents keep their viewer by extension while their bytes are text (markdown, text, html, mermaid, graphviz; a document whose bytes are not text is `file`); everything else is read from the bytes: `image` by `sniffImageContentType` (PNG/APNG, JPEG, GIF, WebP, AVIF, BMP, ICO by magic bytes, SVG by its first element; the extension is ignored, so an HTML page named `.svg` is not an image, and an LFS pointer never is), `pdf` by `%PDF-` in the first 1024 bytes, `video` by its container (`sniffInboxVideo`, `packages/shared/inbox/video.ts`, run after the image check so an AVIF stays an image: an MP4/MOV `ftyp` at offset 4 whose major or compatible brand is a video one (`isom`, `iso2`..`iso9`, `mp41`, `mp42`, `avc1`, `M4V `, `qt  `, `dash`, …) and whose MAJOR brand is not an image or audio one (`avif`, `heic`, `mif1`, `M4A `, `M4B `, …); a WebM by its EBML magic and DocType `webm`, while Matroska stays `file`), `code` for any other UTF-8 text with no NUL (`.mjs`, `Makefile`, an unknown extension), and `file` for the rest (zip, Matroska, binaries). A text or code file over `INBOX_VIEW_MAX_BYTES` (16 MB, the most the window reads whole) is a `file`, a download; that bounds memory, it is not an attach cap. The record: `att_` id, realpath, `named_path` for a symlink, `kind`, `sent_sha256`, `size`, `sent_at`, `sent_mtime`, plus additive `media_type` (images, PDF, and video: `video/mp4`, `video/quicktime` when the major brand is `qt  `, `video/webm`), `width` / `height` (images, from the header; an MP4/MOV's first video track) and `duration_ms` (MP4/MOV). An MP4/MOV's length and size come from `readMp4VideoMetadata`, a walk of the top-level boxes by seeking through the send's own descriptor (a few small reads: `moov` may sit after a 461 MB `mdat`; `mvhd` for the length, each `trak`'s `tkhd` + `mdia/hdlr` for the first `vide` track; at most 4,096 boxes, and a box size past the file ends the walk); a `moov` whose tracks hold no video (audio named `.mp4`) keeps the file a `file`, and a header that does not walk records no metadata but stays `video` by its brands. WebM records no metadata.
- Kinds are strictly additive: every reader (window, phone surface, server) reads `kind` through `readInboxAttachmentKind`, so a value it does not know is `file`, a download. The MCP description tells agents the same.
- Access: a file is reached only by its id, and no route takes a path. Reading the current file requires the recorded realpath to still be that path, a regular file, outside the dotenv family (one check, `checkCurrent`, for every route and so for the phone's door), and for `image` / `pdf` / `video` still that kind by its bytes. Otherwise the answer is `409 attachment_changed_type` or `404 attachment_missing`, and the sent version still opens. The current file's hash is cached per (dev, ino, size, mtime, ctime) and read asynchronously; listing a thread (`/threads/:id/attachments`) hashes a changed file only up to 8 MB and judges a larger one by its stat (unchanged when size and mtime are the sent ones), so a growing log is not re-read on every listing.
- Serving (`packages/server/inbox-attachments.ts`; every byte answer carries nosniff and `Cross-Origin-Resource-Policy: same-origin`, and a `Sec-Fetch-Site: cross-site` / `same-site` request is `403` before anything is read):
  - Text kinds: `GET /api/inbox/attachments/:id` as `text/plain` with CSP `sandbox`, and `/view` (JSON). Both answer `415 attachment_not_text` for image, pdf, file and unknown kinds, and check the open handle's size first: a file over 16 MB (one that grew after it was sent) is `413 attachment_too_large`, which the pane shows as its Download card (the phone's `attachments/<id>/view` is the same route).
  - `GET /api/inbox/attachments/:id/image[?version=sent]`: kind `image` only (`415 attachment_not_image` otherwise), `Content-Type` re-sniffed from the bytes served (never the record's or the name's), CSP `sandbox; default-src 'none'; style-src 'unsafe-inline'` (the message-images policy), `inline`, `ETag` = sha256 (`304`), `Cache-Control: private, no-cache`, `X-Image-Width/Height`. The window draws images only by `<img src>`, so an SVG never runs.
  - `GET /api/inbox/attachments/:id/video[?version=sent]` (design record "inbox-video", approved 2026-10-15; not in this repo): kind `video` only (`415 attachment_not_video` otherwise), GET only (`405`), `Content-Type` re-sniffed from the bytes served (`video/mp4`, `video/quicktime`, `video/webm`), `inline`, the message-images CSP, `Cache-Control: private, no-cache`, and HTTP Range (below). The window plays it in `<video src>`; a phone's player streams it through the door.
  - `GET /api/inbox/attachments/:id/download[?version=sent]`: any kind, `Content-Disposition: attachment` with an ASCII `filename` and `filename*=UTF-8''…` (`contentDisposition`), `application/pdf` for a PDF and `application/octet-stream` otherwise, CSP `sandbox`, `Cache-Control: no-store`; streamed from the descriptor, and with HTTP Range (below), so a native player can stream any file.
  - HTTP Range on `video` and `download` (`packages/server/inbox-byte-range.ts`, built by hand from the descriptor the one check opened: `new Response(Bun.file(path))` answers Range by itself but reopens the file by its path, losing the `O_NOFOLLOW` + dev/ino check). Every answer has `Accept-Ranges: bytes` and an `ETag`: the sent version's `"<sent_sha256>"`, the current file's `"<dev>-<ino>-<size>-<mtime µs>"` from the opened descriptor's stat (`inboxStatEtag`; strong, as nginx's stat tag is, because `If-Range` compares strongly; never a hash per request, since every seek is one). One range (`bytes=a-b`, `a-`, `-n`; an end past the file is its last byte) is a `206` with `Content-Range: bytes a-b/size`, never more than `BYTE_RANGE_MAX_ANSWER` (8 MiB): an open-ended or longer range is answered from its start for 8 MiB and the client asks again from where `Content-Range` says it ended (RFC 9110 lets a 206 cover less than was asked; Chromium, AVPlayer and ExoPlayer do ask again). The cap exists because Bun 1.3.14 pulls a streamed body as fast as the file reads, whatever the client's socket takes (every stream form it offers: measured, a client at 400 KB/s on `bytes=0-` of a 200 MB film had all 200 MB read into memory in 0.1 s), so an uncapped range cost the whole range in memory per slow viewer; Bun 1.4.4 waits for the client, and the cap still bounds one answer; no range, a header that is not a byte range we read, or several ranges is the full `200`; a start at or past the end, `-0`, or any range of an empty file is `416` with `Content-Range: bytes */size`; an `If-Range` that is not exactly this version's ETag (a date included) is the full `200`, so a player resuming a film the agent re-rendered starts over. An answer up to `BYTE_RANGE_WHOLE_MAX` (1 MiB: a player's `bytes=0-1` probe, most seeks) is read whole and carries `Content-Length`; a longer one streams in 1 MiB reads, and Bun then sends it chunked and drops `Content-Length` (checked on 1.3.14 and 1.4.4: any stream body over a few hundred bytes loses it), so its size is in `Content-Range` (206) or the record (200). HEAD is answered on `download` (with `Content-Length`), not on `video`. File handles (`handleRangeStream`, also behind the image route and every streamed attachment answer): measured on Bun 1.3.14 with `lsof`, an aborting client does get `cancel`, but a read is usually in flight then and `FileHandle.close()` during a read never closes the descriptor, so a close asked for mid-read is done when that read returns; and a client gone before the answer starts (it closed while the handler was still opening the file) gets a stream Bun neither reads nor cancels, so a body not pulled for `STREAM_IDLE_CLOSE_MS` (5 min) closes its handle and errors (a paused player asks again with a Range). Bun 1.4.4 fixed both (a close mid-read closes; a gone client is cancelled), and the guards stay as a backstop. The watchdog is 5 min, not 30 s, because Bun 1.4 pulls only as fast as the client reads: a player paused with a full buffer leaves a live answer unpulled, and at 30 s 1.4.4 cut it short. `server.timeout` and `idleTimeout` end sockets, not the stream's handle, and the handler is async, so there is no cleaner Bun mechanism. `startInboxServer`'s `streamIdleMs` shortens it for tests; `packages/server/inbox-video.test.ts` counts the process's open descriptors (`/proc/self/fd`, else `lsof -p`) back to baseline after both kinds of disconnect.

**Live pages and pictures in a message** (approval `inbox-inline-html`, 2026-10-28; owner: "inlines look embedded", the page may load "anything, like t3code's pages", and no more strictness than T3 Code). In a message body (an agent's or the person's own) a fence marked `html` draws as a live page in the text, `svg` as an image, and `mermaid` and `dot` as diagrams, as before. Agents are told this in send_message's `body` description and in the `--help` guide. `MessageBody` (`packages/inbox/components/Thread.tsx`) passes ui's `Viewer` the `htmlEmbeds` host (`inboxEmbedUrl`): it POSTs the fence's text to `/api/inbox/embeds` and frames the URL it gets back. `HtmlEmbedBlock` (`packages/ui/components/html-embed/`) owns the frame. It is a sandboxed frame like T3 Code's, nothing more:
- The frame is `sandbox="allow-scripts allow-forms"` (never `allow-same-origin`), `loading="lazy"`, `referrerpolicy="no-referrer"`. The document carries its own sandboxing policy (see "Phones and security"), so the page runs in an opaque origin.
- The page speaks to the window only by message, and only a message whose `event.source` is this frame's window is read (`readEmbedMessage`: a height 0–20,000, an http(s) link, Escape).
- A link the page hands over (the bootstrap posts a click on an `a[href]`) opens in a new tab (`noopener,noreferrer`) only while the frame has focus and the window has the person's activation (`navigator.userActivation.isActive`), as T3 Code does; otherwise it is ignored.
- It looks embedded: no card, border or background of its own; html and body are transparent. The window's theme tokens (`EMBED_THEME_TOKENS`: `--foreground`, `--chart-1`…`--chart-5`, the fonts, …) and `color-scheme` reach it in the URL fragment (`#pn=`) before first paint, and again by message when the theme changes. The frame element's `color-scheme` matches the document's, else the browser paints an opaque backdrop.
- Its height follows its content (the bootstrap's ResizeObserver). Agents are told to let content set the height (no `vh` units or `height:100%` on html or body, as T3 Code tells them): such a page grows on every report until the 20,000 px cap. Above 480 px (`EMBED_CLIP_PX`) it is clipped with a fade and Show more; then Show less.
- Under it, one quiet line: "HTML · sandboxed" (its tooltip names the author), Code (the fence's source, `aria-pressed`), Full screen (ui's `PopoutDialog` with a full-height frame; Escape in the page closes it).
- Loading is gated (`loadGate.ts`): a frame loads only within 400 px of the scroll pane, at most 2 at once, at most 12 alive. Past that, a "Show page" placeholder loads it on a click. A page the Inbox cannot keep (too large, the route refused), or one that never speaks within 10 s (a refused frame), shows its code.
- A page that spins (a long loop) can stall the window where the browser runs the frame in the window's process (the frame is on the window's origin; WebKit always). The load gate bounds how many pages run.
- `svg` (`SvgFenceBlock`) is a `data:image/svg+xml` `<img>`, so no script runs; over 512 KB, or not an `<svg>`, it stays code.
- The phone surface and every other host (plan review, annotate, code review) pass no `htmlEmbeds`, so these fences stay code there.
