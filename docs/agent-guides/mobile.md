# The native app's contract kit

The native iPhone app of the Plannotator Inbox lives in `apps/mobile/`. It is built from one source with the window: `apps/mobile/contract/`. That folder holds data only (JSON, Markdown, generated Swift). Generators in `scripts/mobile/` make it from the product's own TypeScript. `bun scripts/mobile/check.ts` reports when the product changes and the contract does not (a generated file is stale, or the window gained something the phone has no decision for). Only the mobile-contract workflow runs it; no Bun test does, so an Inbox pull request never fails for a mobile reason (see CI).

The Inbox is Bun-only. Nothing here has a Pi twin.

## The standing rules

- Swift never has a hand-written wire type, route string, error code, color or product word. These come from `apps/mobile/contract/generated/`: `Wire.swift`, `Words.swift` and `Tokens.xcassets`.
- Behaviour is taken from the product. The window and the Inbox are the truth. When the app needs a rule, take it from the product's code, and put it in the contract: a type, a door entry, a vector made by running the product's function, or a flow check that cites the code it comes from. Then build the app from that.
- Do not edit a file marked GENERATED. Change its source and run `bun scripts/mobile/all.ts`.

## Reading a newer or an older Inbox

- `VERSION` is the contract number, generated from the door's own `DOOR_CONTRACT` (`packages/server/inbox-door-version.ts`), the number `health.door.contract` answers. It rises only for a breaking wire change, that is, one an app built from the older contract would misread. Adding a route, a field, a record kind or an enum value is not breaking: the app finds an addition in `health.door.routes`. `VERSION` is the only contract data file that holds the number; `Wire.swift` compiles it in as `wireContract`, and `schema/required.json` records which number its baseline began at. A test checks all three equal `DOOR_CONTRACT`.
- An app reads a newer Inbox. Every generated struct keeps the fields it does not know in `unknownFields`, and every generated enum has an `unknown(String)` case.
- A newer app reads an older Inbox. `schema/required.json` records, per struct, the fields that were required when this contract number began. `Wire.swift` decodes only those as required. A field the TypeScript makes required later is optional in `Wire.swift`, so an older Inbox that does not send it still decodes. The file starts again when `VERSION` rises.
- Numbers: a field whose name says it counts or orders is an `integer` in the schema and `Int64` in Swift (`INTEGER_NAME` in `scripts/mobile/schema.ts`: `seq`, `cursor`, `revision`, `rev`, `ms`, `bytes`, `size`, `count`, `position`, `total`, `offset` and `limit`, alone or after `_`). Every other number is a `Double`.
- Doc comments are not copied into the schema or `Wire.swift`. A comment-only edit to a wire type changes no generated byte and starts no iPhone job.

| `generated/swift/Wire.swift` | `scripts/mobile/swift.ts` | The schema, `door.json`, and the error codes of the door (`refuse(…)`) and the window (`ERROR_STATUS` in `packages/server/inbox.ts`). |

| `parity/surface.json` | `scripts/mobile/surface.ts` | Everything the window and its server offer, as `<kind>:<name>` entries: door routes, the Inbox endpoints (paths, read from the server's code by `packages/server/inbox-window-routes.ts`, which is Inbox code; `tests/inbox-api-table.test.ts` holds `server-and-storage.md`'s Inbox table to the same list), stream frames, record kinds, wire enum values, the keys the Settings write takes, capabilities, wire fields, message blocks, `:::` blocks, Settings sections and flow checks. ## Commands

```sh
bun scripts/mobile/all.ts           # every generator, in order
bun scripts/mobile/all.ts --check   # compare with the committed files without writing
```

`--check` fails and names the stale files. Each generator also runs on its own (`bun scripts/mobile/<name>.ts`), but `all.ts` is the one command to remember: the Swift generator reads what the others write.

A word the window shows that is not in `words.json` is written inside a component or a server message. Make it a constant in the product first (that is a product change, in its own pull request), then add its row in `buildWords()`.

To add a fixture:

1. Write the invented input in `fixtures/`. Do not put real data there: no names, keys or tokens.
2. Add a function to `scripts/mobile/vectors.ts` that runs the product's function over the input.
3. Name both paths as literals.
4. Run `bun scripts/mobile/all.ts`.

## The parity ledger

Every entry of `parity/surface.json` needs a row in `parity/ledger.json` that names it in `surface`. The surface is read from the product, never from the docs:

- door routes, from the door itself;
- window endpoints, from the server's code (`packages/server/inbox-window-routes.ts`; a new route module is added to its `ROUTE_FILES` in an Inbox pull request, and `tests/inbox-api-table.test.ts` says so). These are paths without methods, and `<prefix>/*` is a family that a module splits itself;
- stream frames and record kinds;
- the values of every wire enum (`enum:`) and every field of a wire type;
- message blocks and `:::` directives;
- the Settings sections, the keys the Settings write takes (`setting:`, which includes the capability switches), and the capabilities;
- the flows' numbered checks.

A row has:

- `id` and `title`;
- `surface`: the entries it decides;
- `flows`: the flow checks that prove it;
- `mobile`: `v1`, `rethink` (in v1, done the phone's way), `later`, `never`, or `undecided`;
- `why`. `later` and `never` must fill it, starting with a reason code. The codes are SCOPE's (`L-door`, `L-off`, `L-size`, `L-ipad`, `L-ai`, `L-proxy`, `N-desk`, `N-web`, `N-self`), plus `L-nodoor` for a window endpoint that is not on the phone's door;
- `since` (`undecided` only): the day the row was added;
- `decoded: true`: the app reads these entries through `Wire.swift`. That is a fact about reading. The mark says what the phone shows;
- `ios.state`: `not-started`, `building`, `done` or `owed`.

Rules `bun scripts/mobile/check.ts` enforces on the real ledger (`tests/mobile-parity.test.ts` checks the same rules on fixed ledgers):

- **One decision per entry.** `v1` and `rethink` agree. An entry that one row marks `v1` and another `later` or `never` fails. An `undecided` row beside a decided one does not count.
- **An Inbox author runs one command.** `bun scripts/mobile/all.ts` keeps the ledger in step: each new entry gets an `undecided` row dated today, an entry the window lost leaves its row, and a `done` feature the window changed becomes `owed`. A decided row whose every entry is gone (a rename) is left naming nothing: `all.ts` and `check.ts` list it, so an operator moves the decision to the new entry. Rows that never named an entry (a behavior with no entry of its own, the most rows) are not listed. The author never picks a mark. The owner's operators decide `undecided` rows within 14 days.
- **Built features follow the window.** A `done` row records a fingerprint of its entries: a field's schema, a door route's entry, a flow check's line. When the window changes them, the same command marks the row `owed` with today's date.
- **The clock** is a script, `bun scripts/mobile/parity-debts.ts`. An `undecided` row or an `owed` debt older than 14 days fails it. Only the `ledger` job of `.github/workflows/mobile-contract.yml` runs it (see CI). No `bun test` runs it, so the Test workflow, main's full run and a release's checks never fail for a mobile debt. Red there holds back only the app's own release. `tests/mobile-parity-debts.test.ts` checks the rule on fixed dates, never the real ledger, and `scripts/ci-affected-map.test.ts` holds all of this.

The seed (2026-11-18) is the owner's scope inventory: 1,221 rows with their marks and reasons. Entries were joined to rows by the routes, frames and fields each row names, then corrected by review. Rows whose `source` starts with `seed:` cover the entries no scope row names:

- `type-<Type>`: the fields and enum values of one wire type, `decoded`, marked by the feature that reads the type. Update, machine updates, restart, notify reach, cloud wake, agent faces, tag colours and tidy are `later`. The outbox's view is `never`, because the phone keeps its own outbox;
- `window-door` (the door itself, `v1`), `window-web` (the web window's own files, `never`), `window-mcp` (`never`), `window-ask` (`later`), `window-decisions` (`later`), `window-outbox` (`never`);
- `window-door-gap`: v1 features whose route the door does not have yet. This is F5a's work list: drafts, a guide marked viewed, the comment draft's delete, agent icons;
- `window-only-<segment>` (`later`, `L-nodoor`);
- `health` (`v1`), `agent-session-fields` (`v1`), `setting-switches` (`later`, `L-door`);
- the Settings write's other keys, each marked by the SCOPE row for its setting: `setting-keys-look` (`rethink`: theme, text size, notifications, sound, the Mark read warning, rows, voice, the tour), `setting-keys-v1` (the rows' Undo, Show archived, saved emoji), `setting-keys-later` (update checks, the agent tools switch, Tailscale, prompts, the sidebar, diff options and style, chapter diagrams, Experimental, Bro mode, floating drafts), `setting-keys-web` (`never`: the tab icon, the browser's cookie host);
- `capabilities` (`later`, `L-off`: the Plans library is hidden in the product today);
- the flows, blocks, frames and door routes left over.

When you fold such an entry into its feature's row, take it out of the seed row.

`bun scripts/mobile/check.ts` compares the live surface with the committed ledger (see CI). `tests/mobile-parity.test.ts` checks the rules and the one command on fixed ledgers only, so an Inbox pull request never fails for a new entry. When the product gains an entry, check.ts's first line says what to do:

> main is ahead of the mobile contract: run `bun scripts/mobile/all.ts` in a mobile PR

and it lists the new entries. That command records them as `undecided`, dated today. Only the ledger's own rules (a mark, a why, two decisions for one entry) need a person to edit the ledger.

`tests/inbox-api-table.test.ts` ties `docs/agent-guides/server-and-storage.md`'s Inbox API table to the same server-derived route list. An endpoint with no row there fails, whatever the phone decides.

### What parity does not catch

1. Purely visual or interaction changes: layout, gestures, durations, menus, animation.
2. Any word written inside a component or a server message, which is most of the UI. Only the words in `words.json` are entries.
3. A new option inside an existing Settings section that is not a key of the Settings write, and window addresses (`#board`, `#settings/...`). Their only table imports the window's React modules.
4. A new route inside a family (`<prefix>/*`), and a method added to a path that already has one.
5. A changed meaning of an existing field when its type stays the same. A type change only changes the fingerprint of a `done` row.
6. Door answers whose types are not in the schema's roots: cards, pulls, search, sessions, launch, attachments' views and more.
7. A frame sent from a module surface.ts does not read.
8. Server-side changes to a body the kit still declares by hand in `door-shapes.ts`.
9. Rule changes in code that no vector runs: folding, store apply, outbox, push, send, anchors.
10. A window change to a built feature whose entries keep the same fingerprint.
11. A capability that is not on the capability seam.
12. The meaning of a mark: the test checks that each entry has one decision, not that the decision is right. The owner reviews the ledger.

## An Inbox pull request and the contract

An Inbox pull request never fails for a mobile reason, and its author runs nothing for the app. What runs where:

- **The unit lanes** run only tests that an Inbox change cannot redden for a mobile reason. They check rules on fixed inputs and import no product code: `tests/mobile-vectors.test.ts` (the stale check works, colors), `tests/mobile-parity.test.ts` (the ledger's rules and the one command), `tests/mobile-parity-debts.test.ts` (the clock on fixed dates) and `tests/mobile-flows.test.ts` (each check's citation form, in the flow files only). A test may import only `scripts/mobile/lib.ts`, `tokens.ts`, `parity.ts`, `parity-debts.ts` and `flows.ts`, which import nothing but `node:` and each other, and may read no contract file.
- **`bun scripts/mobile/check.ts`** makes every comparison of the live product with a committed contract file: each generator's output, the stream suite, the ledger against the live surface, and whether each flow check's cited file still exists. It also runs the generators' own rules on the live product (`scripts/mobile/rules.ts`): `door.json` is the door, a doc comment changes no generated byte, and each word template prints what the window prints for every value of its part. Those read tables only the mobile scripts keep, so an Inbox change can break them for a phone's reason. It is a script that no test imports. A generator that throws still gets the first line, then the generator and its message.
- `scripts/ci-affected-map.test.ts` asserts that no test imports any other `scripts/mobile/` module, calls a generator or names a contract file; that no mobile test runs for a wire, window or shared UI change; that a pull request touching only the Inbox (a new route module included) starts no mobile job; and that no workflow but `mobile-*.yml` runs a `scripts/mobile/` command.

When main moves ahead of the contract (an Inbox pull request changed a wire type, a route, or a rule the vectors run), the `contract` run on main goes red. Its first line reads "main is ahead of the mobile contract: run `bun scripts/mobile/all.ts` in a mobile PR", followed by the new entries and stale files. The mobile operators run that command in a mobile pull request and decide the new `undecided` rows within 14 days. Until then the committed contract lags main. The app builds and tests against the committed files, so it stays green while it lags.

## CI

- The contract files are data. The test picker reads them like any other data file.
- `.github/workflows/mobile-ios.yml` builds Swift, only when `apps/mobile/ios/**` or `apps/mobile/contract/generated/swift/**` changes. `apps/mobile/ios/ci.sh` typechecks `Wire.swift` and `Words.swift` there. The app's conformance tests will read the committed vectors, not live main.
- `.github/workflows/mobile-contract.yml` (ubuntu, seconds) has two jobs, `contract` (check.ts) and `ledger` (the clock). It runs on a pull request that touches `apps/mobile/contract/**` or `scripts/mobile/**`, on every push to main, nightly and by hand. Both jobs run each time, so an `undecided` row or an `owed` debt past 14 days turns every mobile pull request and every push to main red in `ledger` until an operator decides it. An Inbox pull request touches neither path, so it never starts the workflow. On main its red X is its own workflow's ("Mobile contract"); a reader of main's state filters by workflow name, as the release skill does.
- None of these is a required check.
- A generator never lists a folder of the checkout. Every path it reads or writes is a literal in `scripts/mobile/lib.ts` or in the generator, so the picker can see it.

## The app's look

The native app is the same product as the window, made native: not a web view and not a generic iOS form. Its look lives in two files under `apps/mobile/ios/App/Sources/`: `Look.swift` (the scale, the roles and the pieces every card uses) and `LookKit.swift` (the pieces the next screens are built from). A new screen takes its numbers and its pieces from there. A screen that needs more grows the piece in the kit; it never keeps a copy beside itself. `PairingScreen.swift` is older than the kit and is not yet moved onto it.

The scale and the roles (`Look.swift`):

- `Space` is the room between things and inside them (2, 4, 6, 8, 10, 12, 14, 16, 20, 24, and 44 for a touch). `Size` holds a control's own measure (a button's height, Send's disc, a mark). `Radius` is the corners: a shape inside a card sits 4 points in from its edge and has a radius 4 less, so the two keep one centre. A fraction of a mark's own side is written where the mark is drawn.
- `TextRole` is the type roles. All are system text styles, so each follows the person's text size. A card has one heavy line, its prompt; everything else steps down in size and weight.
- `Role` is what a colour says: the accent is what the person can do or has done, amber is work held up or a caution, red is an agent stopped or a thing destroyed, green is a thing finished. Colour is never decoration. `Role.inkOnTint` and `Role.tint` are a role's words on a tint of itself (a chip, a count): the words keep 4.5:1 on a card, the page and a well, in dark and light.
- `Motion` is the three motions (`settle`, `fade`, `press`); `.motion(_:value:)` applies one and reads Reduce Motion for its timing. A thing that also changes size (a mark filling, a button giving under a touch) reads Reduce Motion where it is drawn and keeps its size then. Motion carries meaning only: a pick settles, Send takes the accent when there is something to send.
- `@MarkSide` is the one size of a choice's mark (22 points, growing with the text to 32); `$side` is the column of the words beside it. Ticks, notices and fields under a row all read it.
- `.touchTarget()` makes a thing 44 points both ways and all of it answer, its padding too. Put it after the padding.
- `.barSized()` is for a line of a bar or of the foot: it grows with the text to `Size.barText` and offers the Large Content Viewer past that. Cards and messages grow all the way.

The pieces (`Look.swift`): `cardSurface()` is the one card (a card that holds an unsent pick has an accent edge); `ChoiceRow` and `PickMark` are a choice and its mark; `CardNotice` is a line about what happened to a pick; `Chip` and `RoleLine` are the small marks (a chip wraps to two lines before it widens its row); `actionGround()` is a button (`filled`, `neutral`, `destructive`, `bare`, `off`); `PressStyle` is how a thing answers a touch; `fieldGround(focused:)` is a field, its hairline in the ring colour while it has the focus; `Hairline` parts two things. A hairline parts things; a ground (a well) is kept for what the person chose.

The thread's foot is one piece (`ThreadFoot.swift`): what still waits is a line across the top of the reply field, and Send (`SendDisc`) keeps the field's own centre.

A thread lands on its newest question and keeps that place while rows above measure themselves again (they are built as they scroll; VoiceOver or a UI test builds them all). The place is the person's to take: any scroll that is not the page's own landing lets it go (a finger, a tap on the status bar, VoiceOver), and so does a touch on a card, a Send or the jump control (`ThreadScreen.swift`: `landingMarks`, `keepPlace`, `ScrollBox.rest`). `testAThreadLandsOnItsQuestionAtTheLargestTextSize` and `testALandedThreadLetsGoWhenThePageIsMoved` guard the two halves. The simulator UI suite runs nowhere in CI yet: it is run by hand before an app pull request.

For the next screens (`LookKit.swift`):

- Rows: `RowStyle(selected:)` gives a row its pressed and selected grounds. `RowAction` (`quiet`, `act`, `destructive`) gives a swipe action its tint and a menu item or confirmation its button role, by what the action does. `selectionRing(_:)` rings a selected thing (an annotation, a thumbnail) in `Token.ring`.
- Raised surfaces: `Surface.sheet`, `Surface.popover`, `Surface.scrim` and the one `Surface.shadow`; `popoverSurface()`; `floatingBar()` for a tool bar. Glass is for what floats over content that moves under it (a tool bar over a file or a picture). A sheet and a popover are solid. The thread's foot is the one exception today: its glass sits on the page's solid ground and shows little; it is kept as the system's look for a reply field.
- Media: `thumbnail(_:)` (`Media.thumb`, `Media.rowThumb`, `Radius.thumb`) and `mediaGround()`, the viewer's ground, dark in both appearances. The viewer's chrome is `floatingBar()` over it.
- `CountBadge` is a count with its mark, tinted by role or quiet.
- States: `Waiting` (loading), `Trouble` (a line about what went wrong, where it happened), `Standing` (a whole-screen state, empty included, with at most one `WideButton`).

Code is drawn in one colour. The window colours code with Shiki grammars and a theme chosen per palette (`packages/ui/utils/syntaxTheme.ts`), which a phone cannot run. The plan: the computer sends each code block already cut into coloured runs with the block tree the app reads from S2 on (`message.blocks`, brief F4), each run naming one of a small fixed set of kinds (keyword, string, number, comment, name, punctuation); the contract carries one colour per kind, dark and light, taken from the theme the window resolves for the default palette (`tokens.ts`); the app draws runs with `TextRole.code()` and those colours. Until then no colours are guessed on the phone: a second highlighter would disagree with the window's.

## What the first app slice (S1) must know

- Use `Wire.swift` and its `Door` routes. Never hand-write a route.
- Match `health.door.routes` against `DoorRoute.name`. `InboxDoorHealth` is in the schema.
- Decode list rows one by one, so one bad row does not blank the list.
- Seqs, cursors and revisions are `Int64`. Other numbers are `Double`.
- The flows are checked against the window and cite it. In the list: left swipe is Archive only, the undo banner stays 7 s, the badge counts threads with unseen agent messages, and a picked card reads "Picked <time> · in your draft".
- About 33 v1 features use door routes that a phone token cannot reach today (`grant: machine`: the Board, pulls, launch, open-in and more), and `window-door-gap` lists v1 features with no door route at all. S1 should use only `grant: phone` routes.
- Time words: the vectors print U+0020 before AM and PM, and iOS's en_US format prints U+202F. Normalise both sides as `vectors/time.json` `normalise.rule` says, and test in each of the fixture's zones: UTC, Asia/Kolkata (+05:30) and America/Los_Angeles (−08:00 in November, −07:00 in summer). Format in the zone the test gives, never in UTC.
- The suites `push` and `decode` do not exist yet (see Fixtures and vectors).
- Skew: a `contract` or `min_app_contract` that is not a whole number from 0 to 2^53 − 1 makes the whole `door` unreadable, so the app treats it as an Inbox from before the handshake. `vectors/skew.json` holds the cases, including a number above 2^53 that `Int64` could hold.
- Only the words in `words.json` (about 30) are generated. Any other window word needs a product constant first, in its own pull request.
- `tokens.json` names the fonts Inter and Geist Mono. Bundling them in the app needs their OFL notices.
- `DoorPicksBody` is the window's own pick body (`inboxPickBody` in `packages/core/inbox-answers.ts`) plus `idempotency_key`, so it has `unsent_only` and `confirm_full`. A pick's `answer: null` takes it back, and `Wire.swift` writes the null. The other bodies in `door-shapes.ts` (pair, seen, reply, the error and the frames) are still written by hand until the product has types for them.
