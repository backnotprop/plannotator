## Starting agents from the Inbox (launch)

The person picks **New Claude Code session** in compose's To, writes, and sends. Claude Code starts in the project with the person's own setup, and the thread is an ordinary thread with one quiet run line under the latest message. This is PR 1 of the launch plan: Claude Code only, project folders only.

**Behind a flag.** `inboxLaunch.enabled` in `~/.plannotator/config.json` (config only, default off; see `environment.md`). Off, every `/api/inbox/launch/*` route answers `404 { code: "launch_off" }`, `GET /api/inbox/sessions` carries no `launch` block, the `to.launch` form of `POST /api/inbox/messages` answers `404 launch_off`, list rows and thread reads carry no `run`, and the window draws nothing new. Existing users' UX is unchanged.

### Who hosts the agent

We start nothing that lives on its own. Claude's own supervisor hosts the session (`claude --bg`, Claude Code 2.1.314 or newer, `CLAUDE_LAUNCH_MIN_VERSION`), and messages move over the mod's existing bridge poll. The code:

- `packages/server/inbox-launch.ts`: the routes, the store glue, availability (cached 30 s, re-checked at once when the last check failed), the host read, respawn on reply, row decoration.
- `packages/server/inbox-launch-claude.ts`: the Claude CLI driver and its pure parsers (`parseBackgrounded`, `parseAgentsJson`, `agentByShort`, `startFailureOf`).
- `packages/server/inbox-launch-env.ts`: the login-shell env, the drop list, the settings-file env and the spawn env.
- `packages/core/inbox-run-line.ts`: `inboxRunOf`, the run line computed on read (never stored).

### The send

1. `prepare`: the project's folder must exist (`422 folder_missing`) and Claude Code must be available (`409 agent_unavailable`). Nothing is written when either fails.
2. Compose writes the thread to a placeholder recipient `{ claude-code, launch:<id> }` with `launch` on the root message (`InboxLaunchRecord`: id, agent, session_ref, folder, scratch, started_at, full_permissions, error, deleted_at). No poll can claim a placeholder, and a replayed idempotency key answers the same thread without a second `--bg`.
3. `begin`, in the background (the Send answers at once with `launch: { id, state }`): write `<dataDir>/inbox/launch/<id>/settings.json` (mode 0600), then run `claude --bg --name <thread name, else subject> --settings <file>` in the folder, adding `--permission-mode bypassPermissions` when the launch has full permissions (`launch.full_permissions`, fixed when the launch is made from the switch; every start and Try again reads the record, never the live switch, so the session and its card always agree). Nothing else goes on argv: no prompt, no secret. On success `store.settleLaunch` readdresses the root to the real session, whose mod takes it as its first turn through the existing new-thread wake. On failure it sets `launch.error` (`untrusted`, `failed`, or `missing`).

**The settings file** carries `env`, `permissions.allow: ["mcp__plannotator__plannotator_inbox"]` (the agent's own Inbox call never prompts) and `hooks.PermissionRequest`: one `*` command hook, `<plannotator> inbox permission-hook`, with the longest timeout Claude allows (see "Permission prompts"). `env` is the person's login-shell `CLAUDE_*` values minus per-session ones and minus `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS`, `PLANNOTATOR_DATA_DIR` when it is not the default, `PLANNOTATOR_LAUNCH` and `PLANNOTATOR_LAUNCH_KEY`; `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS=1` and `PLANNOTATOR_LAUNCH_FULL_PERMISSIONS=1` (the permission hook's leave to switch the session to Full permissions) are added only when the full-permissions switch is on. `model` is set only from `inboxLaunch.model` (config only, a plain model name; the real-CLI smoke sets `haiku`).

**Envs.** One filter (`launchSpawnEnv`) drops every `PLANNOTATOR_*` name, Claude's per-session names (CLAUDECODE, CLAUDE_PID, CLAUDE_CODE_SESSION_*, CLAUDE_CODE_MESSAGING_*, CLAUDE_CODE_CHILD_SESSION, CLAUDE_CODE_ENTRYPOINT, CLAUDE_CODE_EXECPATH, CLAUDE_JOB_DIR, CLAUDE_PROJECT_DIR) and the skip-permissions export; the person's own settings (CLAUDE_CONFIG_DIR, SSH_AUTH_SOCK, proxies, LC_*) stay. The login shell (`$SHELL -ilc`, 5 s at most) is read for a start only, starting from the Inbox's env through that filter. The `--bg` call runs with its result through the filter, plus `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS=1` only when the full-permissions switch is on. Every other call (`--version`, `agents`, stop, respawn, rm, osascript) runs with the Inbox's own env through the filter, its PATH followed by the last start's login PATH and `~/.local/bin`, `~/.claude/local`; availability looks for `claude` there (before any start, without the login PATH). No `claude` call is ever killed with its process group: any of them may start the person's shared supervisor. A sandboxed test Inbox (`PLANNOTATOR_TEST_SANDBOX`) reads no login shell and searches no install folder.

### The run line

`inboxRunOf` maps the launch record, the mod's poll (`runStateOf` in `inbox-sessions.ts`: busy, busy since, poll count) and the host's status to one of:

| State | Line | Row word / tick |
| --- | --- | --- |
| `starting` | Starting Claude Code in <project>… (again… after a respawn) | Starting |
| `working` | Claude Code is working · N min, Stop | Working |
| `waiting_terminal` | Claude Code is waiting on a permission prompt · N min, Open in Terminal, the attach command, Stop (phone: no Open) | the row goes to Stopped on you, unread |
| `waiting_answer` | Claude Code is waiting for your permission · N min, Stop: the header of the permission card itself (no separate line) | the row goes to Stopped on you, unread |
| `stopped` | You stopped Claude Code at <time>. Your reply starts it again. | none |
| `failed` | Claude Code didn't start. <cause> Your message is kept. Try again (Open in Terminal for an untrusted folder) | Not delivered |
| `missing` | Claude Code isn't on this computer any more. … plus Send to another session | Not delivered |
| `null` | no line: the agent rests | none |

`starting` holds from Send until the session polls busy or answers: the mod takes the turn one poll before it reports busy, and the line must not blink out in between (`Memo.busySeen`, reset at each start and respawn). `waiting_terminal` needs the session not to be live and idle: once the person answers in Terminal and the turn ends, the line goes even before the next host read.

After Stop or a respawn, the session's earlier polls would keep it "live"; it counts as live again only once it starts a poll past the count recorded at that moment (`Memo.quietPolls`). A reply to a launched session that is not live runs `claude respawn <short>` once per reply. A respawn that exits non-zero, or never polls within a minute, reads `failed` with Try again (`missing` when the CLI is gone, which a failed respawn re-checks at once); it is never retried by itself. Try again respawns an existing session and runs a new `--bg` only after a failed start.

**When the CLI is read.** Only while a window watches (`sweep(watched)`): availability every 30 s while a launched thread exists, and `claude agents --json --all` at most every 10 s while a launched session works or the host last said it waits on a prompt. With no window open, nothing runs but a respawn a reply asks for.

**Delete and Try again during a start.** Try again is refused while a start or respawn runs. Delete during a start marks the launch deleted; when `--bg` answers, the session it made is stopped and removed and the thread is left as it is. A session `--bg` started but the supervisor never listed is stopped and removed before the start is marked failed.

### Permission prompts

A launched session asks its permission prompts in the thread, not only in Terminal. The code:

- `packages/core/inbox-permission.ts` (pure, browser-safe): the question's body and choices from the hook's event, the choice read from the person's answer, the decision built from the hook's own event, the hook's output.
- `packages/server/inbox-launch-permission.ts`: the long-poll route, the question's lease and its withdrawal.
- `apps/hook/server/inbox-permission-hook.ts`: `plannotator inbox permission-hook`, the hook the settings file names.

**The hook.** Claude runs it for every prompt with the event on stdin. ExitPlanMode and AskUserQuestion print nothing at once (plan review and Claude's own question dialog keep them), and so does a session without `PLANNOTATOR_LAUNCH` and `PLANNOTATOR_LAUNCH_KEY`. Otherwise it posts `{ key, request_id, event }` to `POST /api/inbox/launch/:id/permission` and long-polls (about 25 s a call, each call cut off at 35 s, `message_id` after the first) until the person decides. The Inbox names only the choice (`once`, `session`, `auto`, `full` or `deny`, and a deny's reason); the hook builds the decision from its own event (`inboxPermissionDecisionFor`): Allow once echoes its own `tool_input`, Allow for this session adds its own first suggestion with `destination: "session"`, `auto` allows with `updatedPermissions: [{ type: "setMode", mode: "auto", destination: "session" }]`, `full` the same with `mode: "bypassPermissions"` but only when its own env has `PLANNOTATOR_LAUNCH_FULL_PERMISSIONS=1` (else nothing), anything else prints nothing. So whatever answers on the port can never change the tool's input, grant more than Claude suggested, or pick bypass mode for a session not started with it. Claude Code honours `bypassPermissions` only in a session started with it allowed (`--allow-dangerously-skip-permissions`, or started in bypass mode). It prints nothing when the question is withdrawn or the Inbox refuses it (a line on stderr says why), so Claude's own dialog decides. While the Inbox is down (no `inbox.json`, a refused connection, `5xx`, a timed-out call) it reads `inbox.json` again and retries every 2 s; a `401` retries too, but 15 refusals of the same token end the wait (stderr: answer it in Terminal), and a new token (a restarted Inbox) starts the count again. Printing nothing never blocks the session: the Terminal dialog is always there too.

**The route.** Guarded like the bridge (loopback Host, no Origin, the Inbox's Bearer token), and then the launch's key: it must match `env.PLANNOTATOR_LAUNCH_KEY` in `launch/<id>/settings.json` (`403 wrong_key`; `410 launch_gone` for a deleted launch, `404 launch_off` while launch is off). The first call asks: one `:::question` message in the launch thread, authored by `{ claude-code, perm:<session>, "Claude Code" }` so the person's words never go to it and it wakes no one (`wakes: false`), keyed `perm-<request_id>` so a replayed call finds it. The `perm:` session prefix is reserved: the store refuses it from any other writer (`sendMessage` without `permission: true`), so nothing else can post a card that looks like a permission prompt. Answers: `{ status: "waiting" | "withdrawn", message_id }` or `{ status: "decided", message_id, choice, reason }`. Before it reads an answer the route checks the stored question is this prompt's: the message body exactly as it would write it now (the detail, preview, purpose and folder over the block), one question, its prompt, and exactly its expected labels; anything else is withdrawn with "This one can't be answered here. Answer it in Terminal." (fail closed).

**The question.** "Claude Code wants to run a command" (edit, write or read a file, open a web page, search the web, use a tool from a server). A Write says "create a file" or "overwrite a file" (the route checks the path when it asks, and keeps that word when it checks the question again; "write a file" when it cannot tell). The detail, a Write's content (```` ```new ````, ```` ```overwrite ```` or ```` ```write ````), an Edit's change (```` ```diff ````, or ```` ```diff-all ```` when `replace_all`), a MultiEdit's edits (one ```` ```diff ````, each after `@@ Edit N of M`), a NotebookEdit's new source (```` ```cell ````), all 50,000 characters at most, else not asked; every other key of the input the card does not draw (a notebook cell's id and mode, a WebSearch's domain lists, a key a newer Claude Code adds) as JSON (```` ```input ````, 8,000 at most); "Runs outside the sandbox." over a Bash call with `dangerouslyDisableSandbox: true`; Claude's own purpose (a Bash `description` or a WebFetch `prompt`, one plain line of 300 characters at most, else left out) and "in <folder>" sit over the `:::question` block, never inside it, so no line of a command (a heredoc's `- Deny`, a commit message's bullets, `- [ ] X`) can become a choice. A command, a file's content, a change (or a tool's input as JSON) is fenced with a fence longer than any run of backticks in it, a line starting `:::` is escaped, and every control or invisible character (bidi controls like U+202E, zero-width spaces, the soft hyphen, Hangul fillers, variation selectors, the tag block U+E0000–E007F, a lone CR) is shown as `⟨U+202E⟩`, never hidden. A path (Write, Edit, Read, NotebookEdit), a link (WebFetch) or a query (WebSearch) is one line of inline code; one holding a line break, a control or an invisible character is never asked (it could open a `:::question` of its own over the real choices). The block holds only the prompt and its `- [ ]` choices: Allow once, Allow <Claude's first suggestion> for this session (only when Claude suggests one, never bypass mode, always `destination: "session"`), Deny, "Allow and switch to Auto mode", and "Allow and switch to Full permissions" only when the launch has full permissions (`inboxLaunchFullPermissions(launch)`, `launch.full_permissions`: the same value the start reads for the flag and the hook's env; if every launch starts with `--allow-dangerously-skip-permissions`, both change together). The session label names every rule or folder the suggestion grants, in full (a compound `git add . && git commit` reads "Allow `git add` and `git commit` for this session"); a rule it cannot show exactly, or a label over 200 characters, offers no session choice. The foot says "1 permission waiting". The pick is read by its exact label (`inboxPermissionAnswer`), never by position: one pick that is exactly Allow once, this prompt's session label, the Auto mode label or (with full permissions) the Full permissions label allows; anything else (Deny, Skip, a free answer, two picks, an unknown label) is a deny. Allow returns the tool's input unchanged; Deny tells Claude not to retry, with the person's words as the reason (2,000 characters at most). A detail over 8,000 characters, or a path, link or query that cannot be shown exactly, is never asked: the route answers `withdrawn` at once, writes nothing, and Claude's own dialog decides (never a cut-off or reshaped detail). A permission question is unsent-only in the store: once its answer was sent, no pick reopens it, with or without `unsent_only` (`409 question_already_sent`), so a stale window or phone never rewrites what the thread says Claude was told. The first Full permissions pick of a session needs `confirm_full: true` on the pick (`422 validation_error` without it; not again once a prompt of the same session was answered with it): a consent step the window asks for, not a control. A permission question is never re-asked: the store refuses a Re-ask on a `perm:` message (`422 validation_error`; it would send the person's unsent picks without their Send), and the window offers none. The card draws as a permission card only for a `perm:` author in a launched thread while launch is on; with the flag off nothing renders as one.

**The card** (approval "inbox-permission-prompt", `packages/inbox/components/PermissionCard.tsx`, `permissionCard.css`). Its own frame, 720 px at most. The header is the run line while the session waits: "Claude Code is waiting for your permission · N min" and Stop (no second line under it). Then the action ("Run a command", "Create a file", "Overwrite a file", "Edit a file", "Open a web page", …) and the exact request, read back from the stored body (`readInboxPermissionBody`): "Runs outside the sandbox" first when it does, the command with "<purpose>. Runs in <folder>", a file's path with "New file, N lines", "Replaces the whole file, N lines", "N lines", or "N removed, M added" (", every occurrence") and ten numbered lines (eight on a phone; a MultiEdit's edit headings between) then "Show N more lines", or the link exactly as sent (scheme, host, path and query, wrapped, never cut or cleaned) with its host stressed only when the text starts with it, and "Host: <host>" on its own line when it does not (a host that normalizes to another length, user info), then "Looking for: …"; and "Also in the request:" with the leftover input. The footer: Allow once (the one accent button), Allow <rule> for this session (it wraps, so every rule it grants shows on a desktop and a phone), Deny (plain, never red), and Deny with a reason (a field in place, Enter sends); then "Or allow this and switch the session to Auto mode · Full permissions". Full permissions without full permissions is drawn off (`aria-disabled`, faded) with "Start the session with full permissions allowed to use this" on a line of its own under it on hover, focus or a click, and sends nothing; with them it asks "Switch this session to Full permissions?" the first time in a session (Auto mode never asks). Each button is one pick (`unsent_only`, and `confirm_full` from the confirm) and Send of its exact label (a deny with a reason: no pick, the words as Other). When the card is the thread's newest item and waits, and nothing has focus (the page body), Allow once takes focus without a focus ring (`focusVisible: false`) and the footer is scrolled into view, so Enter answers it; it never takes focus from a control, the thread's own Reply at open included, so a card that is there when the thread opens is answered by a click or after moving to it; no new shortcut. The answers ignore activation for 600 ms (`ARM_MS`) after the card appears or takes focus other than from a pointer, and a repeated keydown never clicks: a second Enter, a double tap or a held key never allows the prompt that arrived right after the last one (`data-perm-armed` marks the armed card). Answered, it shrinks in place to one framed line, the verb then what it was for: "Allowed once", "Allowed <rule> for this session", "Allowed, and asked Claude to switch to Auto mode" (or Full permissions: what was asked, never a claim it switched), "Denied" with "You said: “…”", or the withdrawal ("Answered in Terminal", "No longer waiting"); a click unfolds the request. The reply that carried the answer ("You answered 1 question") and the withdrawal follow-up are not drawn.

**Who can answer.** `picks` and `reply` on a `perm:` question are refused (`403 window_only`, nothing written) unless the request is the person's: a window's (the page's own `Origin`, the same host as its `Host`, and this run's `serverSession`), or a paired phone's through the device door, which checked the device's token and hands its requests in in-process (`fromDeviceDoor` in `inbox.ts`; a plain local call cannot be one). A browser window always sends both; an agent's bare `curl` sends neither. This stops an agent in a launched session from answering its own prompt by accident or by a prompt injection.

**Accepted, not defended.** Any process running as the person on this Mac can already reach the Inbox's local routes. A local program that runs code can forge the `Origin` header and read `serverSession`, and so answer a prompt; browser automation (a browser MCP, Playwright) can click the real window. Both already run with the person's own rights, so the Inbox does not try to stop them.

**The lease.** A question lives while its hook holds a call, and 60 s after the last one ends. It is withdrawn (a follow-up from the same author that `supersedes` it, so the card shrinks to its one line with the reason) with "Answered in Terminal." when the host says the session went on (a fresh `claude agents` read after the question: not waiting, not stopped), or with "No longer waiting." when the lease runs out otherwise. It is never withdrawn as answered in Terminal while the hook holds a call (parallel tool calls can read the session as busy). Stop and Delete withdraw at once, and so does turning launch off: every open question of every launched thread is withdrawn with "No longer waiting.". An Inbox restart adopts open questions and gives them a new lease.

### Window routes

Same origin and `serverSession`, like every window write. Open and the settings route are refused over the tailnet.

- `POST /api/inbox/launch/:id/stop`: `claude stop`.
- `POST /api/inbox/launch/:id/open`: macOS Terminal through `osascript`, running `claude attach <short>` in the folder (plain `claude` in an untrusted folder, so its trust prompt shows).
- `POST /api/inbox/launch/:id/delete`: stop, `claude rm`, and remove `launch/<id>/`. The thread stays. Never `claude purge` on a project folder. Not offered on a phone.
- `POST /api/inbox/launch/:id/retry`: Try again after a failed start (a new `--bg`), a failed respawn (`claude respawn` again), or a start that never connected (`claude respawn`, or a new `--bg` when no session was made).
- `POST /api/inbox/launch/settings`: `{ full_permissions }`, Settings → Agents' "Start new sessions with full permissions" switch.

### The window

- Compose's To picker (`ToPicker.tsx`) lists start rows after the running sessions under the caption "Start a new session in <project>", one per available agent (`startBlock` in `compose/model.ts`). Picking one makes the To sentence "New Claude Code session ▾ in <project> ▾"; the folder button opens `FolderMenu.tsx` (recent projects; a missing folder is struck through). A missing folder shows a note and keeps Send off; Save draft keeps the words and the project.
- The thread header says "You started Claude Code in <project>" (and "Full permissions"). `RunLine.tsx` replaces the delivery line while `run` is not null. The thread ⋯ adds Open in Terminal, Copy attach command, Stop Claude Code, and Delete Claude Code session… (asks first, in the thread). A phone gets Copy attach command and Stop only. A stopped session's reply head reads "Reply to Claude Code in <project> · starts it again".
- No new keyboard shortcuts.
