## Starting agents from the Inbox (launch)

The person picks **New Claude Code session** in compose's To, writes, and sends. Claude Code starts in the project with the person's own setup, and the thread is an ordinary thread with one quiet run line under the latest message. Claude Code, and OpenCode 1 ("OpenCode" below); it starts in a project's folder or in a new scratch folder (PR 3, "Scratch folders" below).

**Behind a flag.** `inboxLaunch.enabled` in `~/.plannotator/config.json` (config only, default off; see `environment.md`). Off, every `/api/inbox/launch/*` route answers `404 { code: "launch_off" }`, `GET /api/inbox/sessions` carries no `launch` block, the `to.launch` form of `POST /api/inbox/messages` answers `404 launch_off`, list rows and thread reads carry no `run`, and the window draws nothing new. Existing users' UX is unchanged.

### Who hosts the agent

Where the agent has a background host of its own, it keeps the session: Claude's own supervisor (`claude --bg`, Claude Code 2.1.314 or newer, `CLAUDE_LAUNCH_MIN_VERSION`), and messages move over the mod's existing bridge poll. OpenCode 1 has none, so its host runs one `opencode serve` per launch and stops it after 30 minutes with no turn and no prompt (a reply continues the session; see "OpenCode"). The code:

- `packages/server/inbox-launch.ts`: the engine, the same for every agent: the routes, the store glue, availability (cached 30 s, re-checked at once when the last check failed), the host read, respawn on reply, row decoration. It holds one `LaunchHost` per agent (`hosts`, by agent id).
- `packages/server/inbox-launch-host.ts`: the `LaunchHost` interface, and what the engine hands a host (`LaunchHostContext`).
- `packages/server/inbox-launch-claude.ts`: Claude Code's host (`createClaudeLaunchHost`: availability, how a launch starts, the settings file, trust, `settingsState`), its CLI driver (`createClaudeHost`) and its pure parsers (`parseBackgrounded`, `parseAgentsJson`, `agentByShort`, `startFailureOf`).
- `packages/server/inbox-launch-opencode.ts` and `inbox-launch-opencode-permission.ts`: OpenCode's host (see "OpenCode").
- `packages/server/inbox-launch-env.ts`: the login-shell env, the drop list, the settings-file env and the spawn env.
- `packages/core/inbox-run-line.ts`: `inboxRunOf`, the run line computed on read (never stored).
- `packages/core/inbox-scratch.ts`: the scratch folder's name (`inboxScratchSlug`, then `-2`, `-3`).

**Adding an agent: one host file.** Write `packages/server/inbox-launch-<agent>.ts`: a factory that takes the `LaunchHostContext` and returns a `LaunchHost` (`available`, `startOf`, `trusts` (compose's `scratch_trusted` for it), `start`, `sessions`, `live`, `resume`, `stop`, `remove`, `purge` (`skipped` when it must not run), `attach`, `terminal`, `permissions`, and the login-shell names it keeps). `start` sends no first turn: the engine moves the root to the session it returns. `live.polls` must rise whenever the session shows new life. `permissions` writes its questions with `createLaunchQuestions` (`inbox-launch-permission.ts`); only an agent that calls in, as Claude's hook does, has `handle`. Add the host on its own line in `ownHosts` in `createInboxLaunch` (keyed by its own `agent`), its own member line in `InboxLaunchAgent`, and its e2e spec's own line in `OWN_FAKES` (`tests/agent-cli-stubs.test.ts`) when the spec builds its own PATH. Nothing else in the engine names an agent: the record's `agent`, `to.host` and a question's author come from the host. A record whose agent has no host (a downgrade) gets no run line, no sweep and `404 launch_not_found`. The engine's test fake is `fakeLaunchHost` in `packages/server/inbox-launch-host.test.ts`, registered through `createInboxLaunch`'s `hosts` option.

**The optional seams.** Claude Code uses only `context.loginEnv()`, and its behavior is the same without the others.

- `context.loginEnv()`: a fresh login-shell read, shared with one under way, never held. `start` gets the login env from the engine already; a host that spawns a process of its own again (in `resume`) reads it here, just before that spawn and for that spawn only.
- `stoppedNote(launch)`: the words after "<name> stopped." on the line of a launch whose session stopped without the person's Stop (why it stopped, what a reply does). It is per launch, so the cause can be right for each one. The engine passes it to `inboxRunOf` as `stoppedNote`, and the stopped line carries it as `cause`. Null, or no `stoppedNote`: the line reads "<name> stopped. Your reply starts it again." The person's own Stop always reads "You stopped <name> at <time>."
- `close()`: the Inbox stops. The engine's `stop()` calls `close` on each host after it stops listening to the store, so the host can let go of what it holds (a connection, the processes it owns).
- A `resume` that throws (or rejects) is a failed restart: the engine writes the error to `start.log` and the line shows Failed, "It did not start again.", with Try again. It is never an unhandled rejection, which would end the Inbox.

The permission card names the agent from its question's author (`agentNameOf` in `PermissionCard.tsx`: the author's name, Claude Code when there is none; "Claude" in the deny field for Claude Code). Still Claude-worded, for the agent that needs it to change: the card's Auto/Full choices, and Settings → Agents' launch row (`settingsState`, read from the Claude host: Claude Code's bypass mode and its settings).

### OpenCode

OpenCode 1 (`opencode` 1.18.0 or newer and older than 2, `OPENCODE_LAUNCH_MIN_VERSION`), with Plannotator's OpenCode plugin in the person's OpenCode config (`openCodePluginInstalled`). Otherwise the row is not offered, and availability gives the reason. OpenCode 2 (an `opencode --version` of 2.x) is refused: "OpenCode X is OpenCode 2, which the Inbox cannot start yet" (a follow-up). `opencode2` is not looked for. `opencode` is found on the Inbox's PATH, else in `~/.opencode/bin` (not under `PLANNOTATOR_TEST_SANDBOX`).

- **The server.** One `opencode serve --hostname 127.0.0.1 --port <port>` per launch, in the launch's folder, detached in its own process group. The host picks a free loopback port itself (never `--port 0`, which takes OpenCode's default 4096 when it is free, and never 4096). Its env (`openCodeServerEnv`) is the login env with the launch filter and no `OPENCODE_SERVER_PASSWORD` or `OPENCODE_SERVER_USERNAME` of another server, plus `PLANNOTATOR_DATA_DIR` (when it is not the default), `PLANNOTATOR_INBOX_TOOL=1`, `PLANNOTATOR_LAUNCH=<id>` and a new random `OPENCODE_SERVER_PASSWORD`. `launch/<id>/server.json` (0600) holds `{"pid","started","url","password"}` (`started`: the process's start time from `ps -o lstart=`, read with `LC_ALL=C` and `TZ=UTC0` so every Inbox reads it the same). It is written right after the spawn, before the wait for the server to answer, so an Inbox that dies then leaves a server the next one can prove and end. Every call to the server uses Basic auth.
- **Start.** `POST /session?directory=<folder>`. With full permissions on, the session gets OpenCode's allow-all ruleset (`[{"permission":"*","pattern":"*","action":"allow"}]`); otherwise one rule, `external_directory` allowed on the Inbox's uploads folder (an attached file sits outside the session's folder), so the person's own OpenCode permissions apply to everything else. The engine moves the root to the session.
- **Secrets.** The password is in `server.json` and in the env of the server and of every process it starts (the session's shell commands, its subagents' tools) and of a terminal's `opencode attach`; the same user can read those (`ps -E`, `/proc/<pid>/environ`). It is never in argv, `start.log`, `server.log` (the server's output), the Inbox log, the page, the run line or the attach command (the shell in Terminal reads it from the file). The session's shell commands also inherit `PLANNOTATOR_LAUNCH`, `PLANNOTATOR_INBOX_TOOL` and `PLANNOTATOR_DATA_DIR` (the plugin reads them in the server's process, so they cannot be dropped there); a Plannotator started from such a command sees this launch's Inbox and launch id.
- **Turns.** OpenCode 1 has no Plannotator wake, so the host runs the shared `InboxWake` (`packages/shared/inbox/agent-link.ts`) in the Inbox. It polls the Inbox's bridge as host `opencode`, and it delivers each turn with `POST /session/:id/prompt_async` (the session counts as busy from just before that call, and its status is read again when the call fails). `live` is the bridge's `runStateOf` while the host is connected to the server, and null at once once it is not (Stop, idle, gone). The agent answers with the plugin's `plannotator_inbox` tool. The plugin says replies come back as turns only when `PLANNOTATOR_LAUNCH` is a launch id (`openCode1LaunchWakes` in `apps/opencode-plugin/inbox.ts`). The host reads busy, idle and a waiting permission from `GET /event` and `GET /session/status`. A dropped event stream counts as a gone server only after 3 health checks a second apart fail (then its cards are withdrawn with "No longer waiting.").
- **An Inbox restart, and proof.** A server running a turn or holding a prompt runs on (one with nothing to do is ended by `close`, below). The Inbox adopts it from `server.json` only when it is proved ours: the pid runs `opencode serve --hostname 127.0.0.1 --port <its port>`, with the recorded start time, as the leader of its own process group (`ps`); it answers `401` with no password and `200` with ours; and `GET /session/<id>` finds the session. A file whose pid is not ours that way, or whose server answers without the password, is dropped and nothing is signalled. A server of ours by its process that does not answer is tried again on later sweeps for 60 s (`UNPROVED_MS`), then ended; one that lost the session is ended at once. A reply meanwhile (`resume`) waits for such a server 20 s at most from the reply on (`REPLY_WAIT_MS`; no call runs past it, so the restart stays inside the engine's 60 s start grace) and continues on it when it answers; still silent, it is ended before a new server starts, so two never run on one session. A reply that comes while a sweep's adoption runs waits for it, and opens a server itself when the adoption found none; when that adoption was cancelled (Stop, Delete, the Inbox's close) nothing opens, so the Stop holds. A server gone (Stop, or it exited) leaves no wait behind it: the next reply starts at once. Adopted again (after a restart or an outage), it reads the open permission requests (`GET /permission`): a request whose card is still open is not asked twice; one whose card was withdrawn meanwhile is asked anew. No signal ever goes to a pid that is not proved ours by `ps` just before it (`endServer`), and Stop never ends a server from `server.json` that answers without the password.
- **Stop, a reply, Delete, idle.** Stop cancels a start or a reply's restart under way and waits for it (a server it made anyway is ended), then sends `POST /session/:id/abort`, SIGTERM to the process group and SIGKILL after 3 s, and removes `server.json`. A start whose launch folder is removed meanwhile (Delete) ends its server and never makes the folder again; the engine writes nothing for a launch deleted while a reply's restart ran, and a host's `resume` that throws is a failed restart (`.catch`), never an unhandled rejection. A reply starts a new server on the same session (`resume`, with a new login-shell read). Delete stops it, then runs `opencode session delete <id> --pure`. `purge` is skipped. A server with no turn, no prompt and no delivery for 30 minutes (`OPENCODE_IDLE_STOP_MS`; checked once more against `GET /session/status` and `GET /permission`) is stopped the same way (on the host's own timer, so with Launch off and with no window open too; no turn is handed over while it reads the server that last time, and one that went meanwhile keeps the server), and the run line says "OpenCode stopped. It was idle for 30 minutes. Your reply continues it." (`stoppedNote`; after an Inbox restart it reads as a plain stop). When the Inbox stops, `close()` ends the event streams, wakes and idle timer, cancels what still opens (nothing opens or starts a server after it), and sends SIGTERM to every server with no turn and no prompt (a reply continues the session on a new one); its `server.json` stays until the process is gone, so one that ignores SIGTERM is proved and adopted by the next Inbox, which ends it. A server running a turn or holding a prompt runs on, and the next Inbox adopts it.
- **Attach.** With a server: `cd <folder> && OPENCODE_SERVER_PASSWORD="$(sed … server.json)" opencode attach <url> --session <id>`. The shell in Terminal reads the password from the file, so the command never holds it. With no server: `cd <folder> && opencode --session <id>`.
- **A turn that ends in an error.** When the provider refuses the turn (a model the login does not allow, an expired key), OpenCode answers nothing in the Inbox: the server's event stream says `session.error` with `{ name, data: { message } }` (the smoke's: `APIError`, "This API key has expired. …", and `UnknownError`, "Token refresh failed: 401"). The host posts one note from the session: "OpenCode's turn ended with an error: <OpenCode's own message, else the error's name>" (one line, controls dropped, Markdown's marks escaped, 300 characters at most), and writes it to `start.log` and the Inbox log. `MessageAbortedError` (Stop) and `ContextOverflowError` (OpenCode compacts and goes on) say nothing, nor does a subagent's own session. The person's OpenCode settings are theirs to fix: no retry, no label, nothing changed.
- **Permission prompts.** `permission.asked` becomes the same card (`openCodePermissionEvent`): bash is Bash, edit is Edit (OpenCode's own unified diff, from its first hunk), and read, webfetch and websearch are Read, WebFetch and WebSearch. Any other permission keeps its own name and shows its input whole. The choices are Allow once, "Allow <OpenCode's `always` patterns> for this session" (`*` reads "every file edit"), Deny, and Deny with a reason. There is no mode switch and no Approve in Terminal (`openCodePermissionTerms`). The reply (`POST /permission/:id/reply`): Allow once is `once`, the session choice is `always` (OpenCode keeps it for this server, so for this session), and a deny is `reject` with `inboxPermissionDenyMessage` (OpenCode gives the reason to the model, which goes on). A subagent's prompt (a child session, `parentID` the session or one of its children; known from `session.created` and `session.updated`, else looked up with `GET /session/<id>`) is asked the same way, with a `Note: ` line under the answers, "From a subagent (<its title>).". A reply the server does not take (no answer, or not 2xx and not 404) is kept and sent again 2 s later. OpenCode answers other prompts itself with a reply (its `permission/index.ts`): a `reject` rejects the session's other pending prompts, and an `always` allows those its patterns now cover; their cards are withdrawn with "Denied with your earlier answer." and "Allowed by your Allow for this session." (a `permission.replied` within 15 s of the same reply of ours in the same session). Any other `permission.replied` the Inbox did not send (answered in `opencode attach`) withdraws the card with "Answered in Terminal.". Stop and Delete withdraw with "No longer waiting.".

### The send

1. `prepare`: the project's folder must exist (`422 folder_missing`) and Claude Code must be available (`409 agent_unavailable`). Nothing is written when either fails. It decides from the last login-shell read and the person's own Claude files (`claudeBypassSetup`, read-only, the sources Claude 2.1.314 reads), and fixes how the launch starts (`launchStartOf`), in this order: Settings → Agents' switch once the person set it, either way; never set (`inboxLaunch.fullPermissions` absent, `resolveInboxLaunch` gives null), the person's own `permissions.defaultMode` when their Claude settings set one (managed, the folder's `.claude/settings.local.json` and `settings.json`, then their user `settings.json`; a folder's `bypassPermissions` is skipped, as Claude ignores it): `bypassPermissions` means full permissions, any other mode is theirs; else the shell's `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS` set to a true value (`1`, `true`, `yes`, `on`) means full permissions (an inference: Claude itself never turns bypass on from that export; it only says the person runs Claude that way); else auto mode. Whenever the launch is not full and the person has their own mode, it starts in it (`own_mode`, no `--permission-mode`), the switch off included: turning Full on then off never widens an ask-every-time person to auto. Full permissions needs the person's own recorded bypass consent: in a `--bg` session Claude ignores `--allow-dangerously-skip-permissions` and a bypass start without `skipDangerousModePermissionPrompt` in their managed or user `settings.json` or `bypassPermissionsModeAccepted` in `~/.claude.json` (consent in `settings.local.json`, a project's or our `--settings` file does not count), and `permissions.disableBypassPermissionsMode: "disable"` (that value only) in the settings Claude merges for the session (managed `managed-settings.json`, the user's `settings.json`, the folder's `.claude/settings.json` and `settings.local.json`; Claude reads `~/.claude/settings.local.json` only for a session in the home folder) turns it off. The Inbox never writes that consent. Without it, or with bypass turned off, a launch that wanted full permissions starts as if the switch were off (`bypass_available` absent), and Settings says why (the bypass notice not accepted, or bypass turned off in Claude Code's settings). Where the Inbox cannot see what Claude sees (managed settings pushed by MDM or a server, `managed-settings.d/` drop-ins), Claude starts the session in another mode (default or auto) instead of bypass; its prompts still come to the card, as every launch has the permission hook. A Send decides from the last finished login-shell read, however old (each start reads the shell again for its own env), and waits only for a read already under way (the composer's read ahead, or another launch's start) or when no read ever finished. The Inbox reads it once at start (`warm`), and the composer's "Start Claude Code" asks `GET /api/inbox/launch/settings?ahead=1`, which reads it every time (while the switch was never set).
2. Compose writes the thread to a placeholder recipient `{ claude-code, launch:<id> }` with `launch` on the root message (`InboxLaunchRecord`: id, agent, session_ref, folder, scratch, started_at, full_permissions, own_mode, bypass_available, error, deleted_at; a launch made before these fields reads as not full and without bypass). No poll can claim a placeholder, and a replayed idempotency key answers the same thread without a second `--bg`.
3. `begin`, in the background (the Send answers at once with `launch: { id, state }`): write `<dataDir>/inbox/launch/<id>/settings.json` (mode 0600), then run `claude --bg --name <thread name, else subject> --settings <file> [--allow-dangerously-skip-permissions] [--permission-mode <mode>]` in the folder. The allow flag goes on only with the person's bypass consent (`launch.bypass_available`), so such a launch may switch to bypass mode later (the card's Full permissions). The mode is `bypassPermissions` when the launch has full permissions (`launch.full_permissions`, the one source, fixed when the launch is made; every start and Try again reads the record, never the live switch, shell or Claude files), none when it starts in the person's own default mode (`launch.own_mode`), else `auto` (the owner's default for a launch; prompts auto mode still raises come to the card). An auto launch's settings file always has `permissions.defaultMode: "default"`: when Claude drops auto mode (its auto killswitch, which falls through to the settings' default mode) the session lands in default mode, never in the person's own `bypassPermissions` default; `--permission-mode auto` wins whenever auto is available. When Claude refuses auto mode outright (a CLI without it: commander's own refusal, `option '--permission-mode <mode>' argument 'auto' is invalid`, `refusedForMode`), the start is made again with no `--permission-mode`; why is written to the launch's start log and the Inbox log. A refused bypass start fails as it is. Nothing else goes on argv: no prompt, no secret. On success `store.settleLaunch` readdresses the root to the real session, whose mod takes it as its first turn through the existing new-thread wake. On failure it sets `launch.error` (`untrusted`, `failed`, or `missing`).

**The settings file** carries `env`, `permissions.allow: ["mcp__plannotator__plannotator_inbox", "Read(/<uploads>/**)"]` (the agent's own Inbox call never prompts, and neither does reading a file the person attached: `<uploads>` is `launchUploadsDir`, outside the session's folder; the leading `//` makes the rule's path absolute) and `hooks.PermissionRequest`, in every launch, full included: one `*` command hook, `<plannotator> inbox permission-hook`, with the longest timeout Claude allows (see "Permission prompts"). A full launch still asks bypass mode's safety checks (a dangerous `rm`, and the checks bypass never skips): Claude's `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS` would waive some of them only when no PermissionRequest hook exists at all, and Plannotator's own plugin, which every launch needs, has one (ExitPlanMode; Claude counts any such hook, matcher ignored). So the Inbox hook carries them to the card, and the export is never set. What goes where: Claude Code 2.1.314 takes a hook's allow only when the ask lets hooks allow it, and its own safety checks do not. For those it awaits the hooks first (read in the 2.1.314 binary), takes a deny, ignores an allow, and only then shows its own dialog, which blocks the call by itself after about 2 minutes. Nothing in the hook's input marks such a check, but the input carries the session's `permission_mode`, and in bypass mode only such checks reach the hook. So a prompt whose input says `bypassPermissions` (the launch record's `full_permissions` only when the input has no mode) gets the bypass card: Deny, Deny with a reason, or Approve in Terminal, which hands it to Claude's own dialog (see "The card"). Every other prompt's card offers the allows, and Approve in Terminal beside them: outside bypass mode a prompt can be person-only too, and nothing in the hook input says so (2.1.314 builds it from the common fields, `tool_name`, `tool_input`, `permission_suggestions` and `mcp_server`, read in the binary). The case seen in the real smoke: a project's `permissions.ask` rule (`Bash(touch:*)`) reached the card with Allow once, and Claude ignored the allow and kept its "Permission rule … requires confirmation" dialog in Terminal; a safety check very likely behaves the same in default and auto mode. Such an allow is stated on the card as the click, and the run line ("waiting on a permission prompt") says Claude still waits; Approve in Terminal is the honest way when Claude wants a person. Limit: a `permissions.ask` rule of the person's own, if Claude asks it in bypass mode, gets the bypass card too, though a hook could allow it. `env` is the person's login-shell `CLAUDE_*` values minus per-session ones and minus `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS`, their login `PATH`, `PLANNOTATOR_DATA_DIR` when it is not the default, `PLANNOTATOR_LAUNCH`, `PLANNOTATOR_LAUNCH_KEY` and, for a launch with bypass allowed that is not full, `PLANNOTATOR_LAUNCH_FULL_PERMISSIONS=1` (the permission hook's leave to switch the session to Full permissions). `model` is set only from `inboxLaunch.model` (config only, a plain model name; the real-CLI smoke sets `haiku`).

**Envs.** One filter (`launchSpawnEnv`) drops every `PLANNOTATOR_*` name, Claude's per-session names (CLAUDECODE, CLAUDE_PID, CLAUDE_CODE_SESSION_*, CLAUDE_CODE_MESSAGING_*, CLAUDE_CODE_CHILD_SESSION, CLAUDE_CODE_ENTRYPOINT, CLAUDE_CODE_EXECPATH, CLAUDE_JOB_DIR, CLAUDE_PROJECT_DIR) and the skip-permissions export; the person's own settings (CLAUDE_CONFIG_DIR, SSH_AUTH_SOCK, proxies, LC_*) stay. The login shell (`$SHELL -ilc`, 5 s at most; the account's own shell when the Inbox has no `SHELL`) is read once when the Inbox starts with launch on, while the switch was never set by the composer's read ahead (every time) and Settings → Agents (`GET /api/inbox/launch/settings`, again only when the last read is over a minute old), by a Send only as above, and by each start or respawn for its own env after the Send answered (one read at a time, shared; the env is never held for a launch), starting from the Inbox's env through that filter. The `--bg` and `respawn` calls run with its result through the filter, and find `claude` in the plain env's folders when that env does not reach it (a failed read). Every other call (`--version`, `agents`, stop, rm, osascript) runs with the Inbox's own env through the filter, its PATH followed by the last start's login PATH and `~/.local/bin`, `~/.claude/local`; availability looks for `claude` there (before any start, without the login PATH), and for the plugin in the Claude folder the login shell names. No `claude` call is ever killed with its process group: any of them may start the person's shared supervisor. **What reaches a session:** a session gets the supervisor's env, not its caller's (`.ops/work/bg-test`), and the supervisor keeps the env of whichever call started it. So the settings file is the only sure way in: `CLAUDE_*` and PATH go through it, and anything else the person exports (a token, `AWS_PROFILE`) reaches a session only when an Inbox start or respawn started the supervisor, or when they started it themselves with it set. That part is theirs: Claude Code has no setting for it, and the Inbox shows no label for it. A sandboxed test Inbox (`PLANNOTATOR_TEST_SANDBOX`) reads no login shell and searches no install folder.

### The run line

`inboxRunOf` maps the launch record, the mod's poll (`runStateOf` in `inbox-sessions.ts`: busy, busy since, poll count) and the host's status to one of:

| State | Line | Row word / tick |
| --- | --- | --- |
| `starting` | Starting Claude Code in <project>… (again… only after a reply's respawn; Try again of a start that never ran is a first start) | Starting |
| `working` | Claude Code is working · N min, Stop | Working |
| `waiting_terminal` | Claude Code is waiting on a permission prompt · N min, Open in Terminal, the attach command, Stop (phone: no Open). Never from a host read made before an answer from the card settled (it still shows that prompt) | the row goes to Stopped on you, unread |
| `waiting_answer` | Claude Code is waiting for your permission · N min, Stop: the header of the permission card itself (no separate line) | the row goes to Stopped on you, unread |

"· N min" shows from the first full minute (never "1 min" a few seconds in).
| `stopped` | You stopped Claude Code at <time>. Your reply starts it again. | none |
| `failed` | Claude Code didn't start. <cause> Your message is kept. Try again (Open in Terminal for an untrusted folder) | Not delivered |
| `missing` | Claude Code isn't on this computer any more. … plus Send to another session | Not delivered |
| `null` | no line: the agent rests | none |

`starting` holds from Send until the session polls busy or answers: the mod takes the turn one poll before it reports busy, and the line must not blink out in between (`Memo.busySeen`, reset at each start and respawn). `waiting_terminal` needs the session not to be live and idle: once the person answers in Terminal and the turn ends, the line goes even before the next host read.

After Stop or a respawn, the session's earlier polls would keep it "live"; it counts as live again only once it starts a poll past the count recorded at that moment (`Memo.quietPolls`). A reply to a launched session that is not live runs `claude respawn <short>` once per reply. A respawn that exits non-zero, or never polls within a minute, reads `failed` with Try again (`missing` when the CLI is gone, which a failed respawn re-checks at once); it is never retried by itself. Try again respawns an existing session and runs a new `--bg` only after a failed start. No reply starts a session again while its Stop or Delete runs (a host's `live` may read null as soon as its stop begins). A reply still waiting when the person pressed Stop does not undo the Stop (`Memo.heldReply`): the person's next reply starts the session again, and the held one goes along.

**When the CLI is read.** Only while a window watches (`sweep(watched)`): availability every 30 s while a launched thread exists, and `claude agents --json --all` at most every 10 s while a launched session works or the host last said it waits on a prompt. With no window open, nothing runs but a respawn a reply asks for.

**Delete and Try again during a start.** Try again is refused while a start or respawn runs. Delete during a start marks the launch deleted; when `--bg` answers, the session it made is stopped and removed and the thread is left as it is. A session `--bg` started but the supervisor never listed is stopped and removed before the start is marked failed.

### Permission prompts

A launched session asks its permission prompts in the thread, not only in Terminal. The code:

- `packages/core/inbox-permission.ts` (pure, browser-safe): the question's body and choices from the hook's event, the choice read from the person's answer, the decision built from the hook's own event, the hook's output.
- `packages/server/inbox-launch-permission.ts` (any agent): the question written in the thread, the answer read back, its withdrawal.
- `packages/server/inbox-launch-claude-permission.ts` (Claude Code's transport and terms): the long-poll route, the key, the question's lease, `claudePermissionTerms`.
- `apps/hook/server/inbox-permission-hook.ts`: `plannotator inbox permission-hook`, the hook the settings file names.

**The hook.** Claude runs it for every prompt with the event on stdin. ExitPlanMode and AskUserQuestion print nothing at once (plan review and Claude's own question dialog keep them), and so does a session without `PLANNOTATOR_LAUNCH` and `PLANNOTATOR_LAUNCH_KEY`. Otherwise it posts `{ key, request_id, event }` to `POST /api/inbox/launch/:id/permission` and long-polls (about 25 s a call, each call cut off at 35 s, `message_id` after the first) until the person decides. The Inbox names only the choice (`once`, `session`, `auto`, `full` or `deny`, and a deny's reason); the hook builds the decision from its own event (`inboxPermissionDecisionFor`): Allow once echoes its own `tool_input`, Allow for this session adds its own first suggestion with `destination: "session"`, `auto` allows with `updatedPermissions: [{ type: "setMode", mode: "auto", destination: "session" }]`, `full` the same with `mode: "bypassPermissions"` but only when its own env has `PLANNOTATOR_LAUNCH_FULL_PERMISSIONS=1` (a launch with the person's bypass consent; any other session gets nothing), anything else prints nothing. So whatever answers on the port can never change the tool's input, grant more than Claude suggested, or pick bypass mode for a session not started with it. Claude Code honours `bypassPermissions` only in a session started with it allowed (`--allow-dangerously-skip-permissions`, or started in bypass mode). It prints nothing when the question is withdrawn or the Inbox refuses it (a line on stderr says why), so Claude's own dialog decides. While the Inbox is down (no `inbox.json`, a refused connection, `5xx`, a timed-out call) it reads `inbox.json` again and retries every 2 s; a `401` retries too, but 15 refusals of the same token end the wait (stderr: answer it in Terminal), and a new token (a restarted Inbox) starts the count again. Printing nothing never blocks the session: the Terminal dialog is always there too.

**The route.** Guarded like the bridge (loopback Host, no Origin, the Inbox's Bearer token), and then the launch's key: it must match `env.PLANNOTATOR_LAUNCH_KEY` in `launch/<id>/settings.json` (`403 wrong_key`; `410 launch_gone` for a deleted launch, `404 launch_off` while launch is off). The first call asks: one `:::question` message in the launch thread, authored by `{ claude-code, perm:<session>, "Claude Code" }` so the person's words never go to it and it wakes no one (`wakes: false`), keyed `perm-<request_id>` so a replayed call finds it. The `perm:` session prefix is reserved: the store refuses it from any other writer (`sendMessage` without `permission: true`), so nothing else can post a card that looks like a permission prompt. Answers: `{ status: "waiting" | "withdrawn", message_id }` or `{ status: "decided", message_id, choice, reason }`. Before it reads an answer the route checks the stored question is this prompt's: the message body exactly as it would write it now (the detail, preview, purpose and folder over the block), one question, its prompt, and exactly its expected labels; anything else is withdrawn with "This one can't be answered here. Answer it in Terminal." (fail closed).

**The question.** "Claude Code wants to run a command" (edit, write or read a file, open a web page, search the web, use a tool from a server). A Write says "create a file" or "overwrite a file" (the route checks the path when it asks, with an async `lstat` given 300 ms (`FILE_CHECK_MS`) so an unreachable network path never holds the Inbox, and keeps that word when it checks the question again; "write a file" on a timeout or an error). When a file tool's path is a symbolic link, a "Links to `<target>`" line under the path says where it points (read back and kept the same way). The detail, a Write's content (```` ```new ````, ```` ```overwrite ```` or ```` ```write ````), an Edit's change (```` ```diff ````, or ```` ```diff-all ```` when `replace_all`), a MultiEdit's edits (one ```` ```diff ````, each after `@@ Edit N of M`), a NotebookEdit's new source (```` ```cell ````), all 50,000 characters at most, else not asked; every other key of the input the card does not draw (a notebook cell's id and mode, a WebSearch's domain lists, a key a newer Claude Code adds) as JSON (```` ```input ````, 8,000 at most); "Runs outside the sandbox." over a Bash call with `dangerouslyDisableSandbox: true`; Claude's own purpose (a Bash `description` or a WebFetch `prompt`, one plain line of 300 characters at most, else left out) and "in <folder>" sit over the `:::question` block, never inside it, so no line of a command (a heredoc's `- Deny`, a commit message's bullets, `- [ ] X`) can become a choice. A command, a file's content, a change (or a tool's input as JSON) is fenced with a fence longer than any run of backticks in it, a line starting `:::` is escaped, and every control or invisible character (bidi controls like U+202E, zero-width spaces, the soft hyphen, Hangul fillers, variation selectors, the tag block U+E0000–E007F, a lone CR) is shown as `⟨U+202E⟩`, never hidden. A path (Write, Edit, Read, NotebookEdit), a link (WebFetch) or a query (WebSearch) is one line of inline code; one holding a line break, a control or an invisible character is never asked (it could open a `:::question` of its own over the real choices). The block holds only the prompt and its `- [ ]` choices: Allow once, Allow <Claude's first suggestion> for this session (only when Claude suggests one, never bypass mode, always `destination: "session"`), Deny, "Allow and switch to Auto mode", and "Allow and switch to Full permissions" only when the launch has full permissions (`inboxLaunchFullPermissions(launch)`, `launch.full_permissions`: the same value the start reads for the flag and the hook's env; if every launch starts with `--allow-dangerously-skip-permissions`, both change together). Every card ends with Approve in Terminal (`terminal` in the host's terms); a prompt in bypass mode has Deny and Approve in Terminal only (see "The card"). The session label names every rule or folder the suggestion grants, in full (a compound `git add . && git commit` reads "Allow `git add` and `git commit` for this session"); a rule it cannot show exactly, or a label over 200 characters, offers no session choice. The foot says "1 permission waiting". The pick is read by its exact label (`inboxPermissionAnswer`), never by position: one pick that is exactly Allow once, this prompt's session label, the Auto mode label or (with full permissions) the Full permissions label allows; anything else (Deny, Skip, a free answer, two picks, an unknown label) is a deny. Allow returns the tool's input unchanged; Deny tells Claude not to retry, with the person's words as the reason (2,000 characters at most). A detail over 8,000 characters, or a path, link or query that cannot be shown exactly, is never asked: the route answers `withdrawn` at once, writes nothing, and Claude's own dialog decides (never a cut-off or reshaped detail). A permission question is unsent-only in the store: once its answer was sent, no pick reopens it, with or without `unsent_only` (`409 question_already_sent`), and a reply that carries its own answer for it posts its words as text and leaves the answer record alone (`409 question_already_sent` when it has nothing else), so a stale window or phone never rewrites what the thread says Claude was told. The first Full permissions pick of a session needs `confirm_full: true` on the pick (`422 validation_error` without it; not again once a prompt of the same session was answered with it): a consent step the window asks for, not a control. A permission question is never re-asked: the store refuses a Re-ask on a `perm:` message (`422 validation_error`; it would send the person's unsent picks without their Send), and the window offers none. The card draws as a permission card only for a `perm:` author in a launched thread while launch is on; with the flag off nothing renders as one.

**The card** (approval "inbox-permission-prompt", `packages/inbox/components/PermissionCard.tsx`, `permissionCard.css`). Its own frame, 720 px at most. The header is the run line while the session waits: "Claude Code is waiting for your permission · N min" ("is waiting on a safety check" on the bypass card; "Claude Code waiting · N min" on a phone, one line) and Stop (no second line under it). An answered record keeps its verdict on one line; the path after it takes only the room left and truncates first. Then the action ("Run a command", "Create a file", "Overwrite a file", "Edit a file", "Open a web page", …) and the exact request, read back from the stored body (`readInboxPermissionBody`): "Runs outside the sandbox" first when it does, the command with "<purpose>. Runs in <folder>", a file's path (and "Links to …" when it is a symbolic link) with "New file, N lines", "Replaces the whole file, N lines", "N lines", or "N removed, M added" (", every occurrence") and ten numbered lines (eight on a phone; a MultiEdit's edit headings between) then "Show N more lines", or the link exactly as sent (scheme, host, path and query, wrapped, never cut or cleaned) with its host stressed only when the text starts with it, and "Host: <host>" on its own line when it does not (a host that normalizes to another length, user info), then "Looking for: …"; and "Also in the request:" with the leftover input. The footer: Allow once (the one accent button), Allow <rule> for this session (it wraps, so every rule it grants shows on a desktop and a phone), Deny (plain, never red), and Deny with a reason (a field in place, Enter sends); then "Or allow this and switch the session to Auto mode · Full permissions" (none in a launch already in Full permissions). A session in bypass mode gets the bypass card: the host's terms (`claudePermissionTerms` in `inbox-launch-claude-permission.ts`, from the hook input's `permission_mode`) give the question `allowHere: false`, so its choices are Deny and Approve in Terminal, with a `Note: ` line ("Claude Code only accepts this approval in Terminal.", under the answers) and a `Then: ` line ("Approve it in Claude Code within 2 minutes.", on the record) over the block. Approve in Terminal is answered `terminal`: the hook prints nothing, so Claude's own dialog comes up (a safety check's with its own 2 minutes), and on a computer the card opens Terminal attached (the thread ⋯ menu's Open in Terminal). Every other card offers it too, as a quiet link under the answers, with the `Then: ` line "Approve it in Claude Code, in Terminal." Any allow label picked on such a card (a card from before) is handed to Terminal the same way, never an allow Claude would ignore. Full permissions shows only for a launch with the person's bypass consent that is not already full (`bypass_available`, so it started with `--allow-dangerously-skip-permissions`; otherwise the question has no such choice and the card shows only Auto mode; a Full pick on a card from before that the session cannot honour is Allow once) and asks "Switch this session to Full permissions?" the first time in a session (Auto mode never asks). Each button is one pick (`unsent_only`, and `confirm_full` from the confirm) and Send of its exact label (a deny with a reason: no pick, the words as Other). When the card is the thread's newest item and waits, and nothing has focus (the page body), Allow once takes focus without a focus ring (`focusVisible: false`) and the footer is scrolled into view, so Enter answers it; it never takes focus from a control, the thread's own Reply at open included, so a card that is there when the thread opens is answered by a click or after moving to it; no new shortcut. The answers ignore activation for 600 ms (`ARM_MS`) after the card appears or takes focus other than from a pointer, and a repeated keydown never clicks: a second Enter, a double tap or a held key never allows the prompt that arrived right after the last one (`data-perm-armed` marks the armed card). Answered, it shrinks in place to one framed line, the person's click as a fact (never a promise about Claude), then what it was for: "You chose Allow once", "You chose Allow <rule> for this session", "You chose Allow and switch to Auto mode" (or Full permissions), "You chose Deny" with "You said: “…”", "You chose Approve in Terminal" with the host's `Then: ` line, or the withdrawal ("Answered in Terminal", "No longer waiting"); a click unfolds the request. The record never says what Claude did with the answer: the run line does (a session still on its dialog after the answer settled reads "waiting on a permission prompt" with Open in Terminal, the attach command and Stop: the one set of Terminal actions). On a phone (no Open in Terminal), a record handed to Terminal shows Copy attach command until that line shows. The reply that carried the answer ("You answered 1 question") and the withdrawal follow-up are not drawn.

**Who can answer.** `picks` and `reply` on a `perm:` question are refused (`403 window_only`, nothing written) unless the request is the person's: a window's (the page's own `Origin`, the same host as its `Host`, and this run's `serverSession`), or a paired phone's through the device door, which checked the device's token and hands its requests in in-process (`fromDeviceDoor` in `inbox.ts`; a plain local call cannot be one). A browser window always sends both; an agent's bare `curl` sends neither. This stops an agent in a launched session from answering its own prompt by accident or by a prompt injection.

**Accepted, not defended.** Any process running as the person on this Mac can already reach the Inbox's local routes. A local program that runs code can forge the `Origin` header and read `serverSession`, and so answer a prompt; browser automation (a browser MCP, Playwright) can click the real window. Both already run with the person's own rights, so the Inbox does not try to stop them.

**The lease.** A question lives while its hook holds a call, and 60 s after the last one ends. It is withdrawn (a follow-up from the same author that `supersedes` it, so the card shrinks to its one line with the reason) with "Answered in Terminal." when the host says the session went on (a fresh `claude agents` read after the question: not waiting, not stopped; a bypass card's question says "No longer waiting." instead), or with "No longer waiting." when the lease runs out otherwise. It is never withdrawn as answered in Terminal while the hook holds a call (parallel tool calls can read the session as busy). Stop and Delete withdraw at once, and so does turning launch off: every open question of every launched thread is withdrawn with "No longer waiting.". An Inbox restart adopts open questions and gives them a new lease.

**After an answer.** A `claude agents` read made before an answer settled (3 s, `ANSWER_SETTLE_MS`) still shows the prompt just answered, so it counts for nothing in the run line ("waiting on a permission prompt" never shows for it), and one read is due once it settled. A bypass card's question whose hook is gone while the session went on is withdrawn as "No longer waiting." (Claude's dialog may have blocked the call by itself), never "Answered in Terminal.". The Claude-only parts (the terms and the two lines in `inbox-launch-claude-permission.ts`, the attach command in `inbox-launch-claude.ts`); the card shows the host's words as given.

### Scratch folders

The folder menu ends, under a line, with **New scratch folder** and the folder a Send would make: `<root>/<slug of the thread's name>` (`inboxScratchSlug`: lowercase ASCII letters, digits and single dashes, 48 at most, `scratch` when nothing is left). Picking it makes To read "New Claude Code session ▾ in New scratch folder ▾" and the status line names that folder; Send sends `to: { launch: { agent, scratch: true } }`.

- **The root.** `inboxLaunch.scratchDir`, default `<dataDir>/scratch` (`~/.plannotator/scratch`). Settings → Agents' "Scratch folders" row (under Claude Code, beside the full-permissions switch) changes it: Change, a path field (`~/` is the home; empty is the default), Save. It applies to new folders only; the ones already made stay where they are. A root in a git repository (a `.git` in it or a folder above it, as typed or through a link: the real path of its nearest existing folder counts too) is refused, in Settings (`422 validation_error`) and at Send (`422 scratch_unavailable`): each folder would join that repository's project and its trust, and `claude purge` of a folder there drops the repository's own entry (below).
- **The send.** `prepare` checks the agent first, then makes the root (`mkdir -p`) and the folder with a plain `mkdir` under the root's real path: the first free name of `<slug>`, `<slug>-2`, … (999 at most). A name already there, as a folder, a file or a symbolic link (dangling too), is taken and never followed, and so is a path any launch record (a deleted one too) was given: one path, one launch. The new folder must then be a real folder with no link on its path (`scratchIntact`); else it is removed and the Send refused. The record keeps its identity (`scratch_inode`, `<dev>:<ino>`). `resolveProject` makes it a project as usual (its name is the slug). If the thread is then not written (an error such as a refused thread name, or a replay that landed meanwhile), `abandon` removes the folder and the project made for it while no thread is in it. Any refusal is `422 scratch_unavailable` with nothing sent.
- **Trust.** Claude Code keys trust on a git repository's root, else on the folder it starts in, and a trusted folder covers its subfolders except any nested git repository (code.claude.com workspace-trust docs; on 2.1.314 the launch's real-CLI runs saw a plain child folder start under a trusted plain parent, and a child that was its own repository refused under one). `--bg` and a restart both check it, and only an interactive `claude` can accept it (the one other way, editing `~/.claude.json`, the Inbox never does). So scratch folders are plain folders, never repositories (the Inbox never runs `git`), and one trust of the root covers them all. Trust is the agent's own, so the compose block carries it per agent: `agents[i].scratch_trusted` (the host's `trusts(root)`; for Claude, `claudeTrustsFolder` in `inbox-launch-claude.ts`: `hasTrustDialogAccepted` for the root or a folder above it in `~/.claude.json` or `$CLAUDE_CONFIG_DIR/.claude.json`, a repository's root only by its own entry; read only, never written, and parsed again only when the file's inode, mtime or size changes). Where a launch's trust is keyed is the host's `trustFolder(launch)`. Making and removing scratch folders in `inbox-launch.ts` stays agent-neutral. Not trusted, the row reads **New scratch folder · trust it once**, shows the root (the folder to trust) rather than the new folder, and says under it that the first Send asks to open the root in Terminal once. A Send still starts: `--bg` fails as untrusted (screen 14), the line names the root ("~/.plannotator/scratch isn't a trusted folder yet…"), and Open in Terminal runs `cd <root> && claude`, so one trust covers every scratch folder after it. Try again then starts it. A scratch folder the agent made a repository (`git init`) needs its own trust: a reply's restart is refused as untrusted, and the line names that folder, with Open in Terminal running `claude` there (a refused restart offers Open in Terminal as a refused start does), then Try again. A root set to the home folder is never remembered as trusted (Claude keeps home-folder trust for one session).
- **Delete.** After stop and `claude rm`, a scratch launch's folder, while it is still the folder the Inbox made (a real folder named as a slug whose real path is the recorded one, so no link swapped in and still inside the root it was made in, and the same `scratch_inode`, so never a folder made at that path since), gets `claude purge --yes <folder>` (that folder's sessions, transcripts and `~/.claude.json` entry; `--yes` because without a terminal its confirmation aborts; only when its purge reaches nothing else, below) and is removed; the folder is checked again right before it is removed. Anything else is left alone and logged, and the toast says "its scratch folder was kept". A launch deleted already answers `{ ok: true }` and does nothing (a stale window's second Delete); a Delete still under way (a double click) is waited for and answered alike, so the folder is purged once. Never for a project folder. During a start, `run` does it once `--bg` answers. The folder menu no longer lists a scratch folder Delete removed.
- **`claude purge`, as run on 2.1.314** (sandboxed `CLAUDE_CONFIG_DIR`, no session): it removes the exact folder's `projects/<path with every non-alphanumeric as ->` folder and its `projects["<folder>"]` entry. Purging `<root>/settings-search` left `<root>/settings-search-2` and the root's trusted entry alone. A folder that is its own repository (a `.git` folder): only its own entry. But a folder below a repository's root also drops `projects["<repository root>"]` (its trust, history and MCP servers; not its transcripts folder), and so does a linked worktree (a `.git` file, `gitdir: <repo>/.git/worktrees/<name>`), for its main repository. So the Claude host's `purge` (`claudePurgeRefusal`) skips a folder with a `.git` above it, or a `.git` in it that is not a folder, then runs `claude purge --dry-run <folder>` and purges only when the plan's `config:` lines name that folder alone and its `dir:` lines under `projects/` are that folder's own; a dry run that fails (exit 1: nothing to purge) or prints nothing it can read is no purge either. Every skip is logged with its reason. The folder itself is still removed as Delete says (a linked worktree's checkout too; its branch stays in the main repository). Nothing left to purge exits 1 (logged, ignored); without `--yes` and no terminal it aborts with exit 1.

### Window routes

Same origin and `serverSession`, like every window write. Open and the settings route are refused over the tailnet.

- `POST /api/inbox/launch/:id/stop`: `claude stop`.
- `POST /api/inbox/launch/:id/open`: macOS Terminal through `osascript`, running `claude attach <short>` in the folder (plain `claude` in an untrusted folder, so its trust prompt shows).
- `POST /api/inbox/launch/:id/delete`: stop, `claude rm`, and remove `launch/<id>/`. The thread stays. Never `claude purge` on a project folder; a scratch folder is purged and removed ("Scratch folders"). Not offered on a phone. The confirm names the scratch folder for a scratch launch.
- `POST /api/inbox/launch/:id/retry`: Try again after a failed start (a new `--bg`), a failed respawn (`claude respawn` again), or a start that never connected (`claude respawn`, or a new `--bg` when no session was made).
- `POST /api/inbox/launch/settings`: `{ full_permissions }`, Settings → Agents' "Start new sessions with full permissions" switch (once set, the person's choice wins over the shell, either way); or `{ scratch_dir }`, the "Scratch folders" path.
- `GET /api/inbox/launch/settings`: how a launch made now would start, `{ launch: { enabled, full_permissions, follows, own_mode, needs_consent, bypass_off } }`. Never set, `full_permissions` is what the person's Claude settings or login shell say, and `follows` names which (`claude`, `shell`, else null); `own_mode` means a launch starts in their own default mode; `needs_consent` means full permissions is wanted but Claude Code's bypass notice was never accepted on this computer; `bypass_off` means it is wanted but the person's Claude Code settings turn bypass mode off (it wins over `needs_consent`). Settings → Agents reads it when shown: the value reads Full permissions, Your default mode or Auto mode, with "Follows your shell's setting until you change it." (or "your Claude Code settings") and "Accept Claude Code's bypass notice once in Terminal to use this. Until then sessions start without it." or "Bypass mode is turned off in your Claude Code settings, so sessions start without it." under the switch. While the switch was never set it reads the login shell again when the last read is over a minute old, or every time with `?ahead=1` (the composer picked "Start Claude Code"); concurrent reads share one shell. Never over the tailnet (`403 owner_only`), never for another site's page (`403 cross_origin`, `isCrossSiteRequest`).
