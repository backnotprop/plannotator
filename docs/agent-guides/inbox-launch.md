## Starting agents from the Inbox (launch)

The person picks **New Claude Code session** in compose's To, writes, and sends. Claude Code starts in the project with the person's own setup, and the thread is an ordinary thread with one quiet run line under the latest message. Claude Code, Pi (**New Pi session**, see "Pi" below) and Codex (**New Codex session**, see "Codex" below); each starts in a project's folder or in a new scratch folder (PR 3, "Scratch folders" below).

**On by default, with a switch (0.29; approval `inbox-launch-default-on`).** `inboxLaunch.enabled` in `~/.plannotator/config.json` (see `environment.md`): absent is on on macOS and Linux, and off on Windows, where launch has no support (Claude Code's mod, which carries the messages, stands down there; an explicit `true` still turns it on). Any false-like value (`false`, `0`, `"false"`, `"0"`, `"off"`, `"no"`), in `enabled` or as `inboxLaunch` itself, is off; a config.json that does not parse reads as the defaults. Settings → Agents' first row, "Start agents from New message" (value "Claude Code, Codex and Pi", sub: "New message can start Claude Code, Codex or Pi in a folder you pick. Turn off to only message sessions that are already running."), is the switch, hidden on Windows (`unsupported`): `POST /api/inbox/launch/settings` `{ enabled }` writes `true` or `false` (only that key: saveConfig merges `inboxLaunch` key by key under its lock, so a change made at once from another window or the phone is kept), and the launch module reads config.json again whenever it changes, so New message offers or drops its New session rows (on its next sessions read, every few seconds while open) with no restart. The row is always shown elsewhere; "Sessions you start" and "Scratch folders" (under Claude Code) show only while it is on. **The switch governs new starts only** (the coordinator's default for the owner): off, `/api/inbox/launch/folders` answers `404 { code: "launch_off" }`, `GET /api/inbox/sessions` carries no `launch` block, and the `to.launch` form of `POST /api/inbox/messages` answers `404 launch_off` ("Starting agents from the Inbox is off. Turn it on in Settings → Agents."; from a linked machine, "Starting agents is off on that computer. Turn it on in its Settings → Agents."); the settings route's GET answers `{ launch: { enabled: false, full_permissions: false } }` and reads no shell, and its POST takes only `{ enabled }`. An agent already started keeps everything: its run line, Stop, Open, Delete, Try again, Trust folder, the respawn on a reply, the permission hook and its open permission questions. `GET /api/inbox/settings` carries `launch` either way, never for a tailnet guest. **The login shell** is read the first time it is needed (New message's sessions read; `warmLogin`), never at Inbox start (hooks start the Inbox often, and the person's rc files may prompt), and never on Windows. Test: `packages/server/inbox-launch-settings.test.ts` (absent on, false off, Windows, the switch's writes and live flip, new starts only, the refusal's words, the lazy shell read), `packages/shared/config.test.ts` (`resolveInboxLaunch`, the key-by-key merge), `packages/inbox/agentsSettings.test.tsx` (the row, the rows it hides, none on Windows). The e2e worlds start with launch off (`launchOff` in `tests/e2e/inbox-scratch.ts`), so New message never runs the runner's `claude` stub; the launch specs turn it on with their fakes on a PATH of their own.

### Who hosts the agent

**The agent's own local setup decides.** A launched agent runs with its own settings (model, permissions, extensions, trust). The Inbox passes a setting only where the agent exposes one, never works around one, and adds no labels or warnings about them.

We start nothing that lives on its own. Claude's own supervisor hosts the session (`claude --bg`, Claude Code 2.1.314 or newer, `CLAUDE_LAUNCH_MIN_VERSION`), and messages move over the mod's existing bridge poll. The code:

- `packages/server/inbox-launch.ts`: the engine, the same for every agent: the routes, the store glue, availability (cached 30 s, re-checked at once when the last check failed), the host read, respawn on reply, row decoration. It holds one `LaunchHost` per agent (`hosts`, by agent id).
- `packages/server/inbox-launch-host.ts`: the `LaunchHost` interface, and what the engine hands a host (`LaunchHostContext`).
- `packages/server/inbox-launch-claude.ts`: Claude Code's host (`createClaudeLaunchHost`: availability, how a launch starts, the settings file, trust, `settingsState`), its CLI driver (`createClaudeHost`) and its pure parsers (`parseBackgrounded`, `parseAgentsJson`, `agentByShort`, `startFailureOf`).
- `packages/server/inbox-launch-claude-trust.ts`: Claude Code's trust key, the write under Claude's own lock, and the one reading of a folder (`claudeTrustReading`) behind Trust and start's facts and Trust folder's warning line.
- `packages/server/inbox-launch-pi.ts`: Pi's host (`createPiLaunchHost`): one `pi --mode rpc` process per session, owned by the Inbox (see "Pi").
- `packages/server/inbox-launch-codex.ts`: Codex's host (`createCodexLaunchHost`): one `codex app-server` per thread, owned by the Inbox; its approvals on the card in `inbox-launch-codex-permission.ts` (see "Codex").
- `packages/server/inbox-launch-env.ts`: the login-shell env, the drop list, the settings-file env and the spawn env.
- `packages/core/inbox-run-line.ts`: `inboxRunOf`, the run line computed on read (never stored).
- `packages/core/inbox-scratch.ts`: the scratch folder's name (`inboxScratchSlug`, then `-2`, `-3`).

**Adding an agent: one host file.** Write `packages/server/inbox-launch-<agent>.ts`: a factory that takes the `LaunchHostContext` and returns a `LaunchHost` (`available`, `startOf`, `trusts` (compose's `scratch_trusted` for it), optional `trustOffer` (New message's Trust and start and the run line's Trust folder), optional `trustCoversHome` (the run line's how-to where trust would cover home), `start`, `sessions`, `live`, `resume`, `stop`, `remove`, `purge` (`skipped` when it must not run), `attach`, `terminal`, `permissions`, and the login-shell names it keeps). `start` sends no first turn: the engine moves the root to the session it returns. `live.polls` must rise whenever the session shows new life. `permissions` writes its questions with `createLaunchQuestions` (`inbox-launch-permission.ts`); only an agent that calls in, as Claude's hook does, has `handle`. Add the host on its own line in `ownHosts` in `createInboxLaunch` (keyed by its own `agent`), its own member line in `InboxLaunchAgent`, and its e2e spec's own line in `OWN_FAKES` (`tests/agent-cli-stubs.test.ts`) when the spec builds its own PATH. Nothing else in the engine names an agent: the record's `agent`, `to.host` and a question's author come from the host. A record whose agent has no host (a downgrade) gets no run line, no sweep and `404 launch_not_found`. The engine's test fake is `fakeLaunchHost` in `tests/helpers/fake-launch-host.ts`, registered through `createInboxLaunch`'s `hosts` option.

**The optional seams.** Claude Code uses only `context.loginEnv()`, and its behavior is the same without the others.

- `context.loginEnv()`: a fresh login-shell read, shared with one under way, never held. `start` gets the login env from the engine already; a host that spawns a process of its own again (in `resume`) reads it here, just before that spawn and for that spawn only.
- `stoppedNote(launch)`: the words after "<name> stopped." on the line of a launch whose session stopped without the person's Stop (why it stopped, what a reply does). It is per launch, so the cause can be right for each one. The engine passes it to `inboxRunOf` as `stoppedNote`, and the stopped line carries it as `cause`. Null, or no `stoppedNote`: the line reads "<name> stopped. Your reply starts it again." The person's own Stop always reads "You stopped <name> at <time>."
- `close()`: the Inbox stops. The engine's `stop()` calls `close` on each host after it stops listening to the store, so the host can let go of what it holds (a connection, the processes it owns).
- `processEnded(ref)`: a host that owns its session's process says no process of its own runs that session now (it ended, or this Inbox never ran one). A reply then starts the session again even when it never connected (no `root.delivery`), so a stopped line that says a reply continues it is true. Without it, a session that never connected is never started again by a reply (Try again is the way). Pi's.
- `terminalFailed(launch, command)`: Open in Terminal's osascript failed for that command, so the host undoes what `terminal` did for it (Pi: the hand-off is withdrawn, and a restart it called off goes on).
- `connector`: what of Plannotator's connects a session, in the never-connected line's words ("Started, but not connected to the Inbox. Is Plannotator's <connector> on in that folder?"): "plugin" by default, Pi's "extension".
- A `resume` that throws (or rejects) is a failed restart: the engine writes the error to `start.log` and the line shows Failed, "It did not start again.", with Try again. It is never an unhandled rejection, which would end the Inbox.

The permission card names the agent from its question's author (`agentNameOf` in `PermissionCard.tsx`: the author's name, Claude Code when there is none; "Claude" in the deny field for Claude Code). Still Claude-worded, for the agent that needs it to change: the card's Auto/Full choices, and Settings → Agents' launch row (`settingsState`, read from the Claude host: Claude Code's bypass mode and its settings).

### The send

1. `prepare`: the project's folder must exist (`422 folder_missing`), Claude Code must be available (`409 agent_unavailable`), and a press of Trust and start must be on the folder as it is now (`409 trust_warning_changed`, "Trusting a folder"). Nothing is written when any fails. It decides from the last login-shell read and the person's own Claude files (`claudeBypassSetup`, read-only, the sources Claude 2.1.314 reads), and fixes how the launch starts (`launchStartOf`), in this order: Settings → Agents' switch once the person set it, either way; never set (`inboxLaunch.fullPermissions` absent, `resolveInboxLaunch` gives null), the person's own `permissions.defaultMode` when their Claude settings set one (managed, the folder's `.claude/settings.local.json` and `settings.json`, then their user `settings.json`; a folder's `bypassPermissions` is skipped, as Claude ignores it): `bypassPermissions` means full permissions, any other mode is theirs; else the shell's `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS` set to a true value (`1`, `true`, `yes`, `on`) means full permissions (an inference: Claude itself never turns bypass on from that export; it only says the person runs Claude that way); else auto mode. Whenever the launch is not full and the person has their own mode, it starts in it (`own_mode`, no `--permission-mode`), the switch off included: turning Full on then off never widens an ask-every-time person to auto. Full permissions needs the person's own recorded bypass consent: in a `--bg` session Claude ignores `--allow-dangerously-skip-permissions` and a bypass start without `skipDangerousModePermissionPrompt` in their managed or user `settings.json` or `bypassPermissionsModeAccepted` in `~/.claude.json` (consent in `settings.local.json`, a project's or our `--settings` file does not count), and `permissions.disableBypassPermissionsMode: "disable"` (that value only) in the settings Claude merges for the session (managed `managed-settings.json`, the user's `settings.json`, the folder's `.claude/settings.json` and `settings.local.json`; Claude reads `~/.claude/settings.local.json` only for a session in the home folder) turns it off. The Inbox never writes that consent. Without it, or with bypass turned off, a launch that wanted full permissions starts as if the switch were off (`bypass_available` absent), and Settings says why (the bypass notice not accepted, or bypass turned off in Claude Code's settings). Where the Inbox cannot see what Claude sees (managed settings pushed by MDM or a server, `managed-settings.d/` drop-ins), Claude starts the session in another mode (default or auto) instead of bypass; its prompts still come to the card, as every launch has the permission hook. A Send decides from the last finished login-shell read, however old (each start reads the shell again for its own env), and waits only for a read already under way (the composer's read ahead, or another launch's start) or when no read ever finished. The Inbox reads it the first time New message asks (`warmLogin`, never at start or on Windows), and the composer's "Start Claude Code" asks `GET /api/inbox/launch/settings?ahead=1`, which reads it every time (while the switch was never set).
2. Trust and start only: every check on the thread passes first (its name, its uploads), then `acceptTrust` saves the trust. `409 trust_failed` sends nothing. Compose writes the thread to a placeholder recipient `{ claude-code, launch:<id> }` with `launch` on the root message (`InboxLaunchRecord`: id, agent, session_ref, folder, scratch, started_at, full_permissions, own_mode, bypass_available, error, deleted_at; a launch made before these fields reads as not full and without bypass). No poll can claim a placeholder, and a replayed idempotency key answers the same thread without a second `--bg`.
3. `begin`, in the background (the Send answers at once with `launch: { id, state }`): write `<dataDir>/inbox/launch/<id>/settings.json` (mode 0600), then run `claude --bg --name <thread name, else subject> --settings <file> [--allow-dangerously-skip-permissions] [--permission-mode <mode>]` in the folder. The allow flag goes on only with the person's bypass consent (`launch.bypass_available`), so such a launch may switch to bypass mode later (the card's Full permissions). The mode is `bypassPermissions` when the launch has full permissions (`launch.full_permissions`, the one source, fixed when the launch is made; every start and Try again reads the record, never the live switch, shell or Claude files), none when it starts in the person's own default mode (`launch.own_mode`), else `auto` (the owner's default for a launch; prompts auto mode still raises come to the card). An auto launch's settings file always has `permissions.defaultMode: "default"`: when Claude drops auto mode (its auto killswitch, which falls through to the settings' default mode) the session lands in default mode, never in the person's own `bypassPermissions` default; `--permission-mode auto` wins whenever auto is available. When Claude refuses auto mode outright (a CLI without it: commander's own refusal, `option '--permission-mode <mode>' argument 'auto' is invalid`, `refusedForMode`), the start is made again with no `--permission-mode`; why is written to the launch's start log and the Inbox log. A refused bypass start fails as it is. Nothing else goes on argv: no prompt, no secret. On success `store.settleLaunch` readdresses the root to the real session, whose mod takes it as its first turn through the existing new-thread wake. On failure it sets `launch.error` (`untrusted`, `failed`, or `missing`).

**The settings file** carries `enableAllProjectMcpServers: true` (see "Startup prompts"), `env`, `permissions.allow: ["mcp__plannotator__plannotator_inbox", "Read(/<uploads>/**)"]` (the agent's own Inbox call never prompts, and neither does reading a file the person attached: `<uploads>` is `launchUploadsDir`, outside the session's folder; the leading `//` makes the rule's path absolute) and `hooks.PermissionRequest`, in every launch, full included: one `*` command hook, `<plannotator> inbox permission-hook`, with the longest timeout Claude allows (see "Permission prompts"). A full launch still asks bypass mode's safety checks (a dangerous `rm`, and the checks bypass never skips): Claude's `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS` would waive some of them only when no PermissionRequest hook exists at all, and Plannotator's own plugin, which every launch needs, has one (ExitPlanMode; Claude counts any such hook, matcher ignored). So the Inbox hook carries them to the card, and the export is never set. What goes where: Claude Code 2.1.314 takes a hook's allow only when the ask lets hooks allow it, and its own safety checks do not. For those it awaits the hooks first (read in the 2.1.314 binary), takes a deny, ignores an allow, and only then shows its own dialog, which blocks the call by itself after about 2 minutes. Nothing in the hook's input marks such a check, but the input carries the session's `permission_mode`, and in bypass mode only such checks reach the hook. So a prompt whose input says `bypassPermissions` (the launch record's `full_permissions` only when the input has no mode) gets the bypass card: Deny, Deny with a reason, or Approve in Terminal, which hands it to Claude's own dialog (see "The card"). Every other prompt's card offers the allows, and Approve in Terminal beside them: outside bypass mode a prompt can be person-only too, and nothing in the hook input says so (2.1.314 builds it from the common fields, `tool_name`, `tool_input`, `permission_suggestions` and `mcp_server`, read in the binary). The case seen in the real smoke: a project's `permissions.ask` rule (`Bash(touch:*)`) reached the card with Allow once, and Claude ignored the allow and kept its "Permission rule … requires confirmation" dialog in Terminal; a safety check very likely behaves the same in default and auto mode. Such an allow is stated on the card as the click, and the run line ("waiting on a permission prompt") says Claude still waits; Approve in Terminal is the honest way when Claude wants a person. Limit: a `permissions.ask` rule of the person's own, if Claude asks it in bypass mode, gets the bypass card too, though a hook could allow it. `env` is the person's login-shell `CLAUDE_*` values minus per-session ones and minus `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS`, their login `PATH`, `PLANNOTATOR_DATA_DIR` when it is not the default, `PLANNOTATOR_LAUNCH`, `PLANNOTATOR_LAUNCH_KEY` and, for a launch with bypass allowed that is not full, `PLANNOTATOR_LAUNCH_FULL_PERMISSIONS=1` (the permission hook's leave to switch the session to Full permissions). `model` is set only from `inboxLaunch.model` (config only, a plain model name; the real-CLI smoke sets `haiku`).

**Envs.** One filter (`launchSpawnEnv`) drops every `PLANNOTATOR_*` name, Claude's per-session names (CLAUDECODE, CLAUDE_PID, CLAUDE_CODE_SESSION_*, CLAUDE_CODE_MESSAGING_*, CLAUDE_CODE_CHILD_SESSION, CLAUDE_CODE_ENTRYPOINT, CLAUDE_CODE_EXECPATH, CLAUDE_JOB_DIR, CLAUDE_PROJECT_DIR) a Pi session's own markers (PI_SESSION_ID, PI_SESSION_FILE, PI_PROVIDER, PI_MODEL, PI_REASONING_LEVEL) and the skip-permissions export; the person's own settings (CLAUDE_CONFIG_DIR, SSH_AUTH_SOCK, proxies, LC_*) stay. The login shell (`$SHELL -ilc`, 5 s at most; the account's own shell when the Inbox has no `SHELL`) is read the first time New message's sessions read asks with launch on (`warmLogin`; never at Inbox start, never on Windows), while the switch was never set by the composer's read ahead (every time) and Settings → Agents (`GET /api/inbox/launch/settings`, again only when the last read is over a minute old), by a Send only as above, and by each start or respawn for its own env after the Send answered (one read at a time, shared; the env is never held for a launch), starting from the Inbox's env through that filter. The `--bg` and `respawn` calls run with its result through the filter, and find `claude` in the plain env's folders when that env does not reach it (a failed read). Every other call (`--version`, `agents`, stop, rm, osascript) runs with the Inbox's own env through the filter, its PATH followed by the last start's login PATH and `~/.local/bin`, `~/.claude/local`; availability looks for `claude` there (before any start, without the login PATH), and for the plugin in the Claude folder the login shell names. No `claude` call is ever killed with its process group: any of them may start the person's shared supervisor. **What reaches a session:** a session gets the supervisor's env, not its caller's (`.ops/work/bg-test`), and the supervisor keeps the env of whichever call started it. So the settings file is the only sure way in: `CLAUDE_*` and PATH go through it, and anything else the person exports (a token, `AWS_PROFILE`) reaches a session only when an Inbox start or respawn started the supervisor, or when they started it themselves with it set. That part is theirs: Claude Code has no setting for it, and the Inbox shows no label for it. Pi's process gets the login env through the same filter, plus `PLANNOTATOR_INBOX_TOOL=1` and `PLANNOTATOR_DATA_DIR` when the data dir is not the default (see "Pi"); its other calls (`--version`) run with the Inbox's own env through the filter. A sandboxed test Inbox (`PLANNOTATOR_TEST_SANDBOX`) reads no login shell and searches no install folder.

### The run line

`inboxRunOf` maps the launch record, the mod's poll (`runStateOf` in `inbox-sessions.ts`: busy, busy since, poll count) and the host's status to one of:

| State | Line | Row word / tick |
| --- | --- | --- |
| `starting` | Starting Claude Code in <project>… (again… only after a reply's respawn; Try again of a start that never ran is a first start) | Starting |
| `working` | Claude Code is working · N min, Stop | Working |
| `waiting_terminal` | Claude Code is waiting on a permission prompt · N min, Open in Terminal, the attach command, Stop (phone or tailnet: no Open). Never from a host read made before an answer from the card settled (it still shows that prompt) | the row goes to Stopped on you, unread |
| `waiting_answer` | Claude Code is waiting for your permission · N min, Stop: the header of the permission card itself (no separate line) | the row goes to Stopped on you, unread |

"· N min" shows from the first full minute (never "1 min" a few seconds in).
| `stopped` | You stopped Claude Code at <time>. Your reply starts it again. | none |
| `failed` | Claude Code didn't start. <cause> Your message is kept. Try again (Open in Terminal for an untrusted folder or a session that exists; phone or tailnet: no Open) | Not delivered |
| `missing` | Claude Code isn't on this computer any more. … plus Send to another session | Not delivered |
| `null` | no line: the agent rests | none |

`starting` holds from Send until the session polls busy or answers: the mod takes the turn one poll before it reports busy, and the line must not blink out in between (`Memo.busySeen`, reset at each start and respawn). `waiting_terminal` needs the session not to be live and idle: once the person answers in Terminal and the turn ends, the line goes even before the next host read.

After Stop or a respawn, the session's earlier polls would keep it "live"; it counts as live again only once it starts a poll past the count recorded at that moment (`Memo.quietPolls`). A reply to a launched session that is not live runs `claude respawn <short>` once per reply. A respawn that exits non-zero, or never polls within a minute, reads `failed` with Try again (`missing` when the CLI is gone, which a failed respawn re-checks at once); it is never retried by itself. Try again respawns an existing session and runs a new `--bg` only after a failed start. No reply starts a session again while its Stop or Delete runs (a host's `live` may read null as soon as its stop begins). A reply still waiting when the person pressed Stop does not undo the Stop (`Memo.heldReply`): the person's next reply starts the session again, and the held one goes along.

**When the CLI is read.** Only while a window watches (`sweep(watched)`): availability every 30 s while a launched thread exists, and `claude agents --json --all` at most every 10 s while a launched session works or the host last said it waits on a prompt. With no window open, nothing runs but a respawn a reply asks for.

**Delete and Try again during a start.** Try again is refused while a start or respawn runs. Delete during a start marks the launch deleted; when `--bg` answers, the session it made is stopped and removed and the thread is left as it is. A session `--bg` started but the supervisor never listed is stopped and removed before the start is marked failed.

### Permission prompts

A launched session asks its permission prompts in the thread, not only in Terminal. The code:

- `packages/core/inbox-permission.ts` (pure, browser-safe): the question's body and choices from the hook's event, the choice read from the person's answer, the decision built from the hook's own event, the hook's output.
- `packages/server/inbox-launch-permission.ts` (any agent): the question written in the thread, the answer read back, its withdrawal.
- `packages/server/inbox-launch-claude-permission.ts` (Claude Code's transport and terms): the long-poll route, the key, the question's lease, `claudePermissionTerms`.
- `apps/hook/server/inbox-permission-hook.ts`: `plannotator inbox permission-hook`, the hook the settings file names.

**The hook.** Claude runs it for every prompt with the event on stdin. ExitPlanMode and AskUserQuestion print nothing at once (plan review and Claude's own question dialog keep them), and so does a session without `PLANNOTATOR_LAUNCH` and `PLANNOTATOR_LAUNCH_KEY`. Otherwise it posts `{ key, request_id, event }` to `POST /api/inbox/launch/:id/permission` and long-polls (about 25 s a call, each call cut off at 35 s, `message_id` after the first) until the person decides. The Inbox names only the choice (`once`, `session`, `auto`, `full` or `deny`, and a deny's reason); the hook builds the decision from its own event (`inboxPermissionDecisionFor`): Allow once echoes its own `tool_input`, Allow for this session adds its own first suggestion with `destination: "session"`, `auto` allows with `updatedPermissions: [{ type: "setMode", mode: "auto", destination: "session" }]`, `full` the same with `mode: "bypassPermissions"` but only when its own env has `PLANNOTATOR_LAUNCH_FULL_PERMISSIONS=1` (a launch with the person's bypass consent; any other session gets nothing), anything else prints nothing. So whatever answers on the port can never change the tool's input, grant more than Claude suggested, or pick bypass mode for a session not started with it. Claude Code honours `bypassPermissions` only in a session started with it allowed (`--allow-dangerously-skip-permissions`, or started in bypass mode). It prints nothing when the question is withdrawn or the Inbox refuses it (a line on stderr says why), so Claude's own dialog decides. While the Inbox is down (no `inbox.json`, a refused connection, `5xx`, a timed-out call) it reads `inbox.json` again and retries every 2 s; a `401` retries too, but 15 refusals of the same token end the wait (stderr: answer it in Terminal), and a new token (a restarted Inbox) starts the count again. Printing nothing never blocks the session: the Terminal dialog is always there too.

**The route.** Guarded like the bridge (loopback Host, no Origin, the Inbox's Bearer token), and then the launch's key: it must match `env.PLANNOTATOR_LAUNCH_KEY` in `launch/<id>/settings.json` (`403 wrong_key`; `410 launch_gone` for a deleted launch, `404 launch_off` while launch is off). The first call asks: one `:::question` message in the launch thread, authored by `{ claude-code, perm:<session>, "Claude Code" }` so the person's words never go to it and it wakes no one (`wakes: false`), keyed `perm-<request_id>` so a replayed call finds it. A new question ends the thread's snooze, since the agent is blocked until it is answered (the owner, 2026-11-03); a replayed call does not. The `perm:` session prefix is reserved: the store refuses it from any other writer (`sendMessage` without `permission: true`), so nothing else can post a card that looks like a permission prompt. Answers: `{ status: "waiting" | "withdrawn", message_id }` or `{ status: "decided", message_id, choice, reason }`. Before it reads an answer the route checks the stored question is this prompt's: the message body exactly as it would write it now (the detail, preview, purpose and folder over the block), one question, its prompt, and exactly its expected labels; anything else is withdrawn with "This one can't be answered here. Answer it in Terminal." (fail closed).

**The question.** "Claude Code wants to run a command" (edit, write or read a file, open a web page, search the web, use a tool from a server). A Write says "create a file" or "overwrite a file" (the route checks the path when it asks, with an async `lstat` given 300 ms (`FILE_CHECK_MS`) so an unreachable network path never holds the Inbox, and keeps that word when it checks the question again; "write a file" on a timeout or an error). When a file tool's path is a symbolic link, a "Links to `<target>`" line under the path says where it points (read back and kept the same way). The detail, a Write's content (```` ```new ````, ```` ```overwrite ```` or ```` ```write ````), an Edit's change (```` ```diff ````, or ```` ```diff-all ```` when `replace_all`), a MultiEdit's edits (one ```` ```diff ````, each after `@@ Edit N of M`), a NotebookEdit's new source (```` ```cell ````), all 50,000 characters at most, else not asked; every other key of the input the card does not draw (a notebook cell's id and mode, a WebSearch's domain lists, a key a newer Claude Code adds) as JSON (```` ```input ````, 8,000 at most); "Runs outside the sandbox." over a Bash call with `dangerouslyDisableSandbox: true`; Claude's own purpose (a Bash `description` or a WebFetch `prompt`, one plain line of 300 characters at most, else left out) and "in <folder>" sit over the `:::question` block, never inside it, so no line of a command (a heredoc's `- Deny`, a commit message's bullets, `- [ ] X`) can become a choice. ### Scratch folders

The folder menu ends, under a line, with **New scratch folder** and the folder a Send would make: `<root>/<slug of the thread's name>` (`inboxScratchSlug`: lowercase ASCII letters, digits and single dashes, 48 at most, `scratch` when nothing is left). Picking it makes To read "New Claude Code session ▾ in New scratch folder ▾"; Send sends `to: { launch: { agent, scratch: true } }`.

- **The root.** `inboxLaunch.scratchDir`, default `<dataDir>/scratch` (`~/.plannotator/scratch`). Settings → Agents' "Scratch folders" row (under Claude Code, beside the full-permissions switch) changes it: Change, a path field (`~/` is the home; empty is the default), Save. It applies to new folders only; the ones already made stay where they are. A root in a git repository (a `.git` in it or a folder above it, as typed or through a link: the real path of its nearest existing folder counts too) is refused, in Settings (`422 validation_error`) and at Send (`422 scratch_unavailable`): each folder would join that repository's project and its trust, and `claude purge` of a folder there drops the repository's own entry (below).
- **The send.** `prepare` checks the agent and a Trust and start press first, then makes the root (`mkdir -p`) and the folder with a plain `mkdir` under the root's real path: the first free name of `<slug>`, `<slug>-2`, … (999 at most). A name already there, as a folder, a file or a symbolic link (dangling too), is taken and never followed, and so is a path any launch record (a deleted one too) was given: one path, one launch. The new folder must then be a real folder with no link on its path (`scratchIntact`); else it is removed and the Send refused. The record keeps its identity (`scratch_inode`, `<dev>:<ino>`). `resolveProject` makes it a project as usual (its name is the slug). If the thread is then not written (an error such as a refused thread name, or a replay that landed meanwhile), `abandon` removes the folder and the project made for it while no thread is in it. Any refusal is `422 scratch_unavailable` with nothing sent.
- **Trust.** Claude Code keys trust on a git repository's root, else on the folder it starts in, and a trusted folder covers its subfolders except any nested git repository (code.claude.com workspace-trust docs; on 2.1.314 the launch's real-CLI runs saw a plain child folder start under a trusted plain parent, and a child that was its own repository refused under one). `--bg` and a restart both check it. An interactive `claude` accepts it, and so does the run line's Trust folder, which edits `~/.claude.json` ("Trusting a folder"). So scratch folders are plain folders, never repositories (the Inbox never runs `git`), and one trust of the root covers them all. Trust is the agent's own, so the compose block carries it per agent: `agents[i].scratch_trusted` (the host's `trusts(root)`; for Claude, `claudeTrustsFolder` in `inbox-launch-claude.ts`: `hasTrustDialogAccepted` for the root or a folder above it in `~/.claude.json` or `$CLAUDE_CONFIG_DIR/.claude.json`, a repository's root only by its own entry; physical paths, and parsed again only when the file's inode, mtime or size changes). Where a launch's trust is keyed is the host's `trustFolder(launch)`. Making and removing scratch folders in `inbox-launch.ts` stays agent-neutral. Not trusted, the owner's window gets the same button as any folder: **Trust and start** trusts the root, so one press covers every scratch folder after it, and the row reads plain. Where no press can (a guest, a root at home), the row reads **New scratch folder · trust it once**, shows the root (the folder to trust) rather than the new folder, and says under it that the first Send asks to trust the root once. Such a Send still starts: `--bg` fails as untrusted (screen 14), the line names the root ("~/.plannotator/scratch isn't a trusted folder yet."), and Trust folder (or Open in Terminal, which runs `cd <root> && claude`, then Try again) trusts it. A scratch folder the agent made a repository (`git init`) needs its own trust: a reply's restart is refused as untrusted, and the line names that folder, with Trust folder for it, or Open in Terminal running `claude` there (a refused restart offers both, as a refused start does) and then Try again. A root set to the home folder is never remembered as trusted (Claude keeps home-folder trust for one session).
- **Delete.** After stop and `claude rm`, a scratch launch's folder, while it is still the folder the Inbox made (a real folder named as a slug whose real path is the recorded one, so no link swapped in and still inside the root it was made in, and the same `scratch_inode`, so never a folder made at that path since), gets `claude purge --yes <folder>` (that folder's sessions, transcripts and `~/.claude.json` entry; `--yes` because without a terminal its confirmation aborts; only when its purge reaches nothing else, below) and is removed; the folder is checked again right before it is removed. Anything else is left alone and logged, and the toast says "its scratch folder was kept". A launch deleted already answers `{ ok: true }` and does nothing (a stale window's second Delete); a Delete still under way (a double click) is waited for and answered alike, so the folder is purged once. Never for a project folder. During a start, `run` does it once `--bg` answers. The folder menu no longer lists a scratch folder Delete removed.
- **`claude purge`, as run on 2.1.314** (sandboxed `CLAUDE_CONFIG_DIR`, no session): it removes the exact folder's `projects/<path with every non-alphanumeric as ->` folder and its `projects["<folder>"]` entry. Purging `<root>/settings-search` left `<root>/settings-search-2` and the root's trusted entry alone. A folder that is its own repository (a `.git` folder): only its own entry. But a folder below a repository's root also drops `projects["<repository root>"]` (its trust, history and MCP servers; not its transcripts folder), and so does a linked worktree (a `.git` file, `gitdir: <repo>/.git/worktrees/<name>`), for its main repository. So the Claude host's `purge` (`claudePurgeRefusal`) skips a folder with a `.git` above it, or a `.git` in it that is not a folder, then runs `claude purge --dry-run <folder>` and purges only when the plan's `config:` lines name that folder alone and its `dir:` lines under `projects/` are that folder's own; a dry run that fails (exit 1: nothing to purge) or prints nothing it can read is no purge either. Every skip is logged with its reason. The folder itself is still removed as Delete says (a linked worktree's checkout too; its branch stays in the main repository). Nothing left to purge exits 1 (logged, ignored); without `--yes` and no terminal it aborts with exit 1.

### From another linked machine

A project file is read only inside its folder (no symlink out), up to 256 KiB, and one that isn't JSON counts as unset (`claudeProjectSettingsDirs`, `claudeCodePluginEnabled(e, project)`).
- **The sign-in check.** Claude Code's `available()` asks `claude auth status` after the plugin check, in the Claude folder a session will use. Only a plain "signed out" counts (JSON `loggedIn: false`, or "not logged in" / "not signed in" on stdout with a failing exit); a timeout, a CLI without the command or an answer it can't read never takes launch away (`claudeAuthState`). A launched session may sign in a way the check, run with the Inbox's env, can't see: the login shell's read records only whether `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`, `CLAUDE_CODE_USE_BEDROCK`, `_VERTEX` or `_FOUNDRY` is set (the host's `shellFlags`, kept as "1", never the value), and with one set (there or in the Inbox's env) a signed-out answer is not believed. An answer is kept 30 s (`CLAUDE_AUTH_TTL_MS`), a signed-out one 5 s (`CLAUDE_AUTH_SIGNED_OUT_TTL_MS`), and checks asked meanwhile share one run, so compose's reads don't run the CLI each time and signing in shows within seconds. A machine's `launch` in A's list is read when the line connects: launch turned on or off later shows in B's launch block (`sessions`) at once, and in the list at the next connect. The exact output of a real `claude auth status` is not pinned yet (SPEC §8); the fake `claude` answers JSON (`signedOut`).
- Test: `packages/server/inbox-remote-launch.test.ts`, two real Inboxes linked both ways with the fake `claude` (both directions: the start, `from`, the run line read through the forward; a bare call and a door call without the mark refused, at A and at B, for a start and a Stop; Open not forwarded; Trust and start writing B's config only; asleep, Cancel, and one start when back; signed out with and without SSH, refused in B's name, and launch off in health). `PLANNOTATOR_INBOX_TEST_BINARY` runs it on a compiled binary.

### Pi

**A Pi session stops when the Inbox stops, and continues when you reply.** Pi has no background host (no `claude --bg`, no daemon), so the Inbox owns the process: one `pi --mode rpc --session-id <uuid> --name <thread name>` per launched session, in its folder, its stdin held open by the Inbox. The uuid is Pi's session id, so it is both the session and `session_ref`. Pi's RPC mode ends when its stdin closes. Stop (`abort`, then stdin closed; SIGTERM only after 5 s), Delete, and the Inbox exiting (the host's `close`: `abort`, then stdin closed) all end it. Pi writes its session file as it goes (from its first answer on; before that there is no file). A reply to a stopped session starts a new process with the same `--session-id`, which reopens that file with the whole conversation, and the waiting reply is delivered. Try again on a Pi that runs but never connected ends that process and starts a new one. We start nothing that lives on its own: a holder process that kept Pi's stdin open past the Inbox would be exactly that.

- **The stopped line** (the host's `stoppedNote`, per launch; the person's own Stop keeps "You stopped Pi at …"):
  - after an Inbox restart: "Pi stopped. A Pi session runs only while the Inbox runs. Your reply continues it.";
  - a Pi that ended on its own: "Pi ended on its own (exit N). Your reply continues it.";
  - both hold for a Pi that ended, or whose Inbox restarted, before it ever connected: the host's `processEnded` lets that reply start it again;
  - during Open in Terminal's hand-off there is no stopped line: the session reads as held (below), so the line is empty, or the Terminal Pi's own while it is connected;
  - after the hand-off: "It was opened in Terminal and is not running there now. Your reply continues it here."
- **Messages.** Plannotator's own Pi extension runs in the process (RPC mode reports `ctx.hasUI`), polls this Inbox's bridge as host `pi`, session `<uuid>`, takes the root as its first turn and answers with `plannotator_inbox`; `live` is that bridge poll, so the Terminal's Pi counts too. The spawn env is the login env through the launch filter plus `PLANNOTATOR_INBOX_TOOL=1` (the Inbox tool is off for Pi by default; set for the launched process only) and `PLANNOTATOR_DATA_DIR` when the Inbox's data dir is not the default (so the extension reaches the launching Inbox). The filter also drops a Pi session's own markers (`PI_SESSION_ID`, `PI_SESSION_FILE`, `PI_PROVIDER`, `PI_MODEL`, `PI_REASONING_LEVEL`), for an Inbox started from inside a Pi session. A restart reads the login shell itself (`context.loginEnv()`), after its checks. Nothing else goes on argv; `inboxLaunch.model` is Claude Code's and is not passed.
- **One writer per session file.**
  - A restart is marked from its first step. Stop, Delete (which stops first) and Open in Terminal cancel it: before its spawn nothing starts, and a process that is coming up is ended once it answers. Both `attach` and `terminal` respect the mark. The engine's own `stopping` and `deleting` keep a new restart off while a Stop or Delete runs; the mark is for a restart already under way.
  - Nothing starts while any other process runs the session. Pi sets `process.title = "pi"`, so ps lists a running Pi as `pi` alone, without its argv. Two signals, either one enough: a command line that names the session (`--session-id <uuid>`, in one `ps -A -ww -o pid=,ppid=,command=` listing shared for 1.5 s: the terminal's shell about to start Pi, a Pi whose title is its argv), or the session's claim. Plannotator's Pi extension, in every Pi on a computer that has run the Inbox (Inbox tool on or off), writes `inbox/pi-sessions/<session>.<pid>.json` (`{ session, pid, rpc, title, owner }`, `packages/shared/inbox/pi-session-claim.ts`) as a session starts and removes it as it ends (`/new`, `/resume`, exit; `owner` keeps a `/reload`'s old instance off the new one's). A claim counts while its pid is in the listing under the title it claimed with (or naming the session), so a pid another program reused is not that Pi; a claim whose pid is gone is removed when read, and one whose pid a later Pi claims (a killed Pi's pid, reused) is removed by that Pi. RPC is `--mode rpc` on argv or Pi's `pi-rpc` entry (its title). A Pi on a Plannotator extension from before the claim writes none: for it only the ps match is left, so a Pi titled `pi` there can still get a second writer beside it. The Inbox's own processes and every process under them are left out, so a `pi` wrapper that does not exec, as Volta's shim, is the Inbox's own. What remains is a terminal's Pi (Open in Terminal's, Copy attach command's, one started by hand), the terminal's shell about to start it, or an RPC Pi an Inbox that ended could not end. It holds across an Inbox restart.
  - When ps does not run, no one can tell what runs the session, so a restart starts nothing: it fails with "The Inbox could not list processes (ps), so it cannot tell whether another Pi runs this session. Pi did not start again.", and the launch's start log says why. Open in Terminal then ends the Inbox's process at once.
  - A terminal's is held: `live` reads the session as held (not busy), so a reply waits for that Pi and the engine starts nothing. A new Inbox lists the processes once, the first time a Pi session is in question, and checks a held one again until it is gone.
  - An RPC one fails the restart: "A Pi process from before (pid N) still runs this session, so it did not start again."
  - `launch/<id>/pi-session.json` keeps the session file Pi named and whether it was on disk when the last process ended. When that file is gone at a restart, Pi starts the session again empty, and one note from the session says so in the thread.
- **The row.** `pi` on the plain env's PATH, `--version` at least 0.79.1 (`PI_LAUNCH_MIN_VERSION`, the extension's floor), and Pi's `settings.json` (`$PI_CODING_AGENT_DIR`, else `~/.pi/agent`) lists Plannotator's Pi extension in `packages` or `extensions`. The settings are read first, so no Pi starts while the extension is missing; `pi --version` goes through the shared version run, which keeps its answer for 60 s. Pi never refuses a folder (in RPC mode its project trust only decides which project resources load), so `trusts` is true and no launch is `untrusted`. No permission modes: nothing on the record, and Settings → Agents' switch is Claude Code's.
- **No permission card.** Pi has no permission prompts of its own. An extension's dialog (`ctx.ui.select`, `confirm`, `input`, `editor`: an `extension_ui_request` on RPC) is a free-form title and the extension's own option strings, with no tool and no allow or deny, so it cannot go on the permission card honestly. The host answers it `cancelled` at once, and Pi gives the extension what a dismissed dialog gives (`undefined` for select, input and editor, `false` for confirm, the same as a dialog's timeout). Whether that blocks is the extension's choice: a gate that allows only on an explicit yes blocks (Pi's permission-gate example did in the smoke). The host then posts one note from the session in the thread: "Pi asked something the Inbox can't show yet (“<title>”); answered Cancel." The title is one line, with controls and invisible characters dropped, Markdown's marks escaped, 80 characters at most. Fire-and-forget UI requests (notify, status, widgets) are ignored.
- **A turn that ends in an error.** When the provider refuses the turn (a model the login does not allow, an expired login), Pi answers nothing through the Inbox: the run's `agent_end` carries the error as its last assistant message's `stopReason: "error"` and `errorMessage`. The host holds it until Pi settles (`agent_settled`; a run Pi retries (`willRetry: true`), or one a compaction continues, starts again and its own end decides; a Pi before 0.80.4 sends no `agent_settled`, so 1.5 s after the run's end), then posts one note from the session: "Pi's turn ended with an error: <Pi's own error text>" (one line, as the dialog title above, 300 characters at most), and writes the error to `start.log` and the Inbox log. The person's agent settings are theirs to fix: no retry, no label, nothing changed.
- **Open in Terminal hands the session over.** A working Pi's way to Terminal is Stop, then Copy attach command. Open in Terminal shows only when a run is stuck, so it reaches a running process on one Pi only: one that started but never connected (`failed`), where Stop is not offered and there is no attach command.
  - The command: `/bin/sh -c 'cd <folder> || exit 1; while kill -0 <pid> …; done; PLANNOTATOR_INBOX_TOOL=1 [PLANNOTATOR_DATA_DIR=<dir>] pi --session-id <uuid>'`. It runs through `/bin/sh -c` so it reads the same in fish or csh. When the folder is gone, nothing runs. It waits for the Inbox's process, then runs Pi with the Inbox tool on. `--session-id` opens the session's file, or starts the session when Pi has written none yet; `--session` would exit on a session with no file.
  - The Inbox's process ends (aborting a running turn) only once the terminal shows: its shell names the session in the process list. When none shows within 30 s (Terminal did not open), the hand-off is withdrawn and the Inbox's Pi keeps the session. A restart under way is cancelled at once.
  - The Terminal's Pi polls this Inbox's bridge and takes the replies. The hand-off holds on every Open in Terminal, a stopped session's included. While it holds, `live` reads the session as held: a reply waits for the Terminal's Pi, with no restart line, and is not used up. Nothing starts here, Copy attach command is not offered, and a second Open in Terminal only prints that the session is open, or opening, in another terminal.
  - It ends only once the bridge saw the Terminal's Pi and then lost it (30 s after its last poll), or, when that Pi never connected, a minute after the Inbox's process was gone. In either case no process may still run the session. Each launch sweep moves it on.
  - Copy attach command (`/bin/sh -c 'cd <folder> && PLANNOTATOR_INBOX_TOOL=1 … pi --session-id <uuid>'`) is offered only when nothing has the session: no process of the Inbox's, no restart, no hand-off, no terminal's Pi, and no Pi live on the bridge as the session (one the person started from this command).
- **Delete.** Ends the process (or cancels a restart under way); `remove` has nothing to do (Pi keeps no session list; the session file stays, like a transcript). A scratch folder's `purge` removes the session files in Pi's default sessions folder for it whose header `cwd` is that folder exactly (as resolved, or through its links), and the folder once empty.
- **Proof.** Unit: `packages/server/inbox-launch-pi.test.ts`, and `packages/server/inbox-launch-pi-engine.test.ts` for the engine's own wiring (To offers Pi only with `pi` and the extension there; a Send starts it in the project's folder with the thread's name as one argument, addressed to that session, which takes the root; the spawn env's names). It runs against the fake `pi` (`tests/helpers/fake-pi/`: `--version`, `--mode rpc --session-id`, its session file, the extension's bridge poll and session claim, and a terminal's `pi --session-id`; on Node and titled `pi`, as Pi is, so ps never lists its argv) and a small bridge in the test's data dir. The Terminal command is run in `/bin/sh` and `/bin/csh`, with spaces, quotes and shell marks in the data dir and the folder, and with its folder gone. Other tests cover a `pi` wrapper that does not exec, a missing ps, Copy attach while that command's Pi runs, that Pi after an Inbox restart (listed as `pi` alone), the claim's stale and reused pids (and the extension's side, `apps/pi-extension/inbox-session-claim.test.ts`), and a turn that ends in a provider error (after retries, and from a Pi with no `agent_settled`; the fake's `turnError`). E2E: `tests/e2e/inbox-launch-pi.spec.ts`; its Stop then Copy attach command test and its never-connected Open in Terminal test run the command against the real Inbox's bridge. The real Pi 0.85.1 was checked by hand (`.ops/work/launch-pi/`): ready in under a second, the session id as given, the extension live in this Inbox in about 2.5 s, stdin's end exits 0 in under 10 ms, a resume reopened the file and delivered the waiting reply, and a permission-gate extension's dialog came over RPC and blocked on Cancel.

### Codex

**Pi's pattern over `codex app-server` (approval `inbox-launch-codex`, 2026-11-09; research and T3 Code notes in the PR).** The Inbox owns one `codex app-server` (JSON-RPC over stdio, as Ask AI, voice and T3 Code use it) per launched thread, in its folder, with the person's login env through the launch filter: their `CODEX_HOME` (from the login shell, never a scratch one), config, login, model, sandbox and approval policy. The filter also drops an outer Codex thread's `CODEX_THREAD_ID` and `CODEX_SANDBOX*`, and `PLANNOTATOR_DATA_DIR` is set when the data dir is not the default. Nothing of the person's goes on argv or on the thread. Draft #2407 built the same on Codex's shared daemon; this one keeps no daemon of the Inbox's making alive.

- **The row.** `codex` on the plain env's PATH (never the desktop apps' copies), the person's Codex config has a `plannotator-inbox` MCP entry (`readCodexEntry`; else `tool_off`), `codex --version` at least the Codex wake's floor (`CODEX_LAUNCH_MIN_VERSION` = 0.149.0), and `codex login status` does not say "Not logged in" (`signed_out`; local only, no network). A linked machine's window says why in its words; on this computer To lists only what can start.
- **Start.** `initialize`, `initialized`, `account/read` (no account and `requiresOpenaiAuth`: the start fails with "Codex isn't signed in. Run codex login in Terminal, then try again." and the app-server ends), `thread/start { cwd, config }`, `thread/name/set` (the thread's name; a refusal is logged, not a failure). `config` carries `mcp_servers.plannotator-inbox.env.PLANNOTATOR_DATA_DIR` for a non-default data dir (Codex starts MCP servers with a clean env, so the process env alone would not reach them) and, only where Codex itself would write `trust_level = "trusted"` into `config.toml` (no trust entry for the folder, its real path or its git trust root, and a `sandbox_mode` that can write), that trust in memory (`config.projects`): a launch never changes the person's `config.toml` (#2407's finding). The thread id is the session and `session_ref`.
- **Turns.** No first turn from the host: the engine moves the root to `{ codex, <thread> }`, and the Codex wake (`inbox-codex-wake.ts`) hands every waiting item to the engine's `deliver` before `codex queue`. A launched thread's host puts the wake text in as `turn/start` (Codex runs one started during a turn after it); when Codex refuses it, `turn/steer` into the running turn. Answered: delivered at once. No answer in time: `uncertain`, never sent again. A launched thread never goes through `codex queue`, and needs no Codex CLI that queues (`launched`). The engine holds an item (`hold`) for a deleted launch, during a Stop or Delete, and for a thread whose app-server is not running unless a reply's restart is under way: only the owner's new reply starts it again (`maybeRespawn`), so a Stop holds across an Inbox restart too. A launched Codex's first turn is the shared wake text, so the launched-agent start note (in progress) reaches it there; the host adds nothing of its own.
- **The run line.** `live` is the host's own process: ready once the thread is loaded, busy from `turn/started` to `turn/completed`, and `polls` counts every message the thread's app-servers wrote (across restarts, so it never goes back). Starting → Working · Stop → no line at rest. Stop: `turn/interrupt { threadId, turnId }` only while a turn runs (5 s at most), then stdin closes (SIGTERM after 5 s, SIGKILL 2 s later); "You stopped Codex at <time>. Your reply starts it again." A reply then starts a new app-server that `thread/resume`s the thread, and the reply goes in on it. The stopped line otherwise: "Codex ended on its own (exit N). Your reply continues it.", after an Inbox restart "The Inbox restarted, which ended it. Your reply continues it.", after Open in Terminal "It was opened in Terminal. Your reply continues it here once Codex there has quit." A resume refused as another Codex's thread ("active writer") fails with "This Codex thread is open in another Codex. Quit it there, then try again."
- **Approvals** (`inbox-launch-codex-permission.ts`, #2407's mapping): `item/commandExecution/requestApproval` as Bash (Codex's session approval as the session choice for a command shown exactly), `item/fileChange/requestApproval` for one added or changed file as Write, Edit or MultiEdit, `item/permissions/requestApproval` as `request_permissions`, on the shared card from `perm:<thread>` authored Codex. Choices: Allow once (`accept`), Allow <command> for this session (`acceptForSession`), Deny (`decline`; a reason follows with `turn/steer`). `modes: false` (no Auto mode or Full permissions) and no Approve in Terminal: the Inbox owns the process. A request the card can't show whole is declined at once with the note "Codex asked for an approval the Inbox can't show yet; declined." A turn's end, Stop or the process ending withdraws open cards ("No longer waiting."), as does the sweep for a card no request is behind (an earlier Inbox's).
- **Other questions.** `item/tool/requestUserInput` (answered with an error) and `mcpServer/elicitation/request` (answered `cancel`): one note, "Codex asked something the Inbox can't show yet (“<title>”); answered Cancel." (#2620 puts them on question cards.)
- **A failed turn.** `turn/completed` with `status: "failed"` (a refused model, an expired login): one note with Codex's own words, "Codex's turn ended with an error: <text>" (one line, 300 characters at most; the turn's `error.message`, else the last `error` notification's that did not retry), and the start log and Inbox log.
- **Terminal.** Copy attach command: `cd <folder> && codex resume <thread>`, only while no app-server of the Inbox's runs the thread. Open in Terminal while one runs ends it (its turn interrupted) and runs `/bin/sh -c 'cd <folder> || exit 1; while kill -0 <pid> …; done; codex resume <thread>'`.
- **Delete** ends the process; `remove` keeps Codex's own thread (its history, `codex resume`); `purge` is skipped (Codex keeps its sessions by date, not by folder). The Inbox exiting closes every app-server's stdin (SIGTERM after 2 s).
- **The account line** (Settings → Agents, the Codex group, read-only; `GET /api/inbox/codex/account`, `packages/server/inbox-codex-account.ts`, words in `packages/inbox/codexAccount.ts`): "Account" with the plan ("ChatGPT Plus", …; the limits read's plan first), "API key", "Signed in" (another provider) or "Not signed in" with "Run `codex login` in Terminal to sign in."; under a plan, the limits used as the Accounts page writes them ("5h 21% · week 40%"), and for a limit at 90% or more "· 5h resets <time>". Asked once when the group shows, and only where New message could start Codex (launch's own check first, so a Codex without the Inbox MCP entry or too old is never run for it); no row while it could not be read. The Inbox never signs in or out for the person.
- **Pi server.** Launch is Inbox-only (Bun); nothing in `apps/pi-extension/server/`.
- **Proof.** `packages/server/inbox-launch-codex.test.ts`: the real engine and Codex wake against the stub (`tests/helpers/fake-codex-launch.ts`: `--version`, `login status`, `queue`, and the app-server subset with turns, a queued second turn or its refusal, steer, interrupt, an approval, a user-input request, a failing turn, a held thread): To offers Codex only with `codex`, a login and the MCP entry (`missing`, `signed_out`, `tool_off` otherwise); a Send starts the app-server in the folder with the person's env, the thread there with the data dir and trust in memory and nothing else, the root as a turn and never `codex queue`, `config.toml` unchanged; a reply is a turn; Stop interrupts and ends it, and the next reply resumes the thread; a refused second turn is steered; no login is the line above; a failed turn is a note; an approval is the card and Allow once answers `accept`. `packages/server/inbox-codex-account.test.ts`, `packages/inbox/codexAccount.test.ts` and a case in `packages/inbox/agentsSettings.test.tsx` cover the account line. The real Codex was not run by tests or by the build's smoke; a real end-to-end run is ops' with the owner.

### Window routes

Same origin and `serverSession`, like every window write (`serverSession` required for Trust folder and a Send with `to.launch.trust`, `403 window_only`). Open is refused over the tailnet. The settings routes (the full-permissions switch, the scratch folder, and how a launch would start) and Trust folder are the owner's, on their phone too; a guest gets `403 owner_only` ("launch settings are the owner's, on their phone too"). Starting an agent is the owner's: a Send with `to.launch` and Try again answer a tailnet login from `inboxTailscaleAllow` `403 owner_only` (as Ask AI does), and the owner over the tailnet as on the computer (`inbox-tailnet-owner.test.ts`, "starting an agent is the owner's"). So are Stop and Delete: a guest gets `403 owner_only` and the session runs on ("stopping or deleting an agent is the owner's"), and a guest's page (`tailnetGuest`) has neither in the thread's ⋯, and its run line has no Stop or Try again (`launchMenuGuest.test.tsx`), nor a permission card's header Stop (`permissionFocus.test.tsx`). A guest's reply, re-ask, tag or new message is kept and delivered, but never starts a stopped session again: the route that writes it marks it `by_guest` (from `isGuest`, once, when it is written, so the owner's is never marked whatever rewrites it later, and the mark survives a restart), and the respawn's pick leaves those out, in any thread and for tags. A guest's stopped run line says "<agent> stopped. Your reply waits for it." Every one of these asks `isOwnerRequest` (through `isGuest` and `isOwner` in `inbox.ts`), so on a tagged machine, which has no owner, the logins `inboxTailscaleAllow` names are the owner here too.

- `POST /api/inbox/launch/:id/stop`: `claude stop`.
- `POST /api/inbox/launch/:id/open`: macOS Terminal through `osascript`, running `claude attach <short>` in the folder (plain `claude` in an untrusted folder, so its trust prompt shows).
- `POST /api/inbox/launch/:id/delete`: stop, `claude rm`, and remove `launch/<id>/`. The thread stays. Never `claude purge` on a project folder; a scratch folder is purged and removed ("Scratch folders"). Not offered on a phone. The confirm names the scratch folder for a scratch launch.
- `POST /api/inbox/launch/:id/retry`: Try again after a failed start (a new `--bg`), a failed respawn (`claude respawn` again), or a start that never connected (`claude respawn`, or a new `--bg` when no session was made).
- `POST /api/inbox/launch/:id/trust`: Trust folder, then Try again ("Trusting a folder"). Owner only.
- `POST /api/inbox/launch/settings`: `{ full_permissions }`, Settings → Agents' "Start new sessions with full permissions" switch (once set, the person's choice wins over the shell, either way); or `{ scratch_dir }`, the "Scratch folders" path.
- `GET /api/inbox/launch/settings`: how a launch made now would start, `{ launch: { enabled, full_permissions, follows, own_mode, needs_consent, bypass_off } }`. Never set, `full_permissions` is what the person's Claude settings or login shell say, and `follows` names which (`claude`, `shell`, else null); `own_mode` means a launch starts in their own default mode; `needs_consent` means full permissions is wanted but Claude Code's bypass notice was never accepted on this computer; `bypass_off` means it is wanted but the person's Claude Code settings turn bypass mode off (it wins over `needs_consent`). Settings → Agents reads it when shown: the value reads Full permissions, Your default mode or Auto mode, with "Uses your shell's setting until you change it." (or "your Claude Code settings") and "Accept Claude Code's bypass notice once in Terminal to use this. Until then sessions start without it." or "Bypass mode is turned off in your Claude Code settings, so sessions start without it." under the switch. While the switch was never set it reads the login shell again when the last read is over a minute old, or every time with `?ahead=1` (the composer picked "Start Claude Code"); concurrent reads share one shell. Never over the tailnet (`403 owner_only`), never for another site's page (`403 cross_origin`, `isCrossSiteRequest`).

### Windows

Launch stays off on Windows by default (the switch above); these make it able to work there, and change nothing on macOS or Linux (`packages/server/inbox-launch-windows.ts`, pure where it can be):

- **PATH.** Windows names the variable in any case (`Path` is usual) and joins folders with `;`. A plain copy of the env (`{ ...process.env, PATH: x }`) holds both spellings, and the child may get the old one. `launchSpawnEnv` folds every spelling into the one key `PATH` (the last copy wins), `launchPlainEnv` splits and joins on the platform's delimiter (`env-path.ts`), and an agent environment's `which` reads PATH by any spelling.
- **A `.cmd` CLI** (npm's `claude.cmd`) starts through cmd.exe as agent jobs do (`windowsShimOf` on `planAgentJobSpawn`); an argument cmd.exe would misread is refused, never passed, so on Windows a session's name drops `"`, `%`, `!`, `^` and line breaks. A run that hits its limit ends cmd.exe's whole tree (`taskkill /t`), except the calls that may start Claude's supervisor (`killGroup: false`), which end cmd.exe alone.
- **Claude's rules and trust.** The Read rule names the drive the way Claude matches it: `Read(//c/Users/me/…/**)`. Trust is read under `C:/…`, `c:/…` and `C:\…`, and written as `C:/…` (forward slashes, the drive letter as the file system gives it).
- **Commands a person copies** (Copy attach command, the trust command) are PowerShell's: `Set-Location -LiteralPath '<folder>'; if ($?) { claude attach <id> }`, with `'` and `‘ ’ ‚ ‛` doubled. The per-launch permission hook sets `"shell": "powershell"` and runs `& '<plannotator.exe>' inbox permission-hook; exit $LASTEXITCODE`, so it works with or without Git Bash (a Claude Code that ignores `shell` runs it in Git Bash, where it fails and Claude asks in its own prompt).
- **Folders.** A typed folder may use backslashes or `/` and either drive-letter case (`windowsTypedUnderHome`); `~\code` works too. A folder with the Hidden or System attribute (`GetFileAttributesW` through `bun:ffi`), or whose attributes can't be read (an access-denied junction such as `Application Data`), counts as hidden, as a dot-folder does. A folder outside home (a junction's real place) is judged by Windows' own rules: `refusedOutside` in `inbox-home-folders.ts` calls `windowsFolderRefusal` (system folders, Program Files, ProgramData, the Users folder and other accounts, hidden by attributes; a drive root may be started in). That file's source, bundled with `inbox-launch-windows.ts`, also runs in the folder-reader child, which gets `SystemRoot`, `ProgramFiles` and `ProgramData` on Windows. A typed path on another drive is still `outside` (the any-folder browser speaks POSIX paths). The scratch-folder setting refuses any drive's root.
- Open in Terminal is still macOS only, and Pi's and Codex's launch on Windows is a later step (their attach commands are still `sh`'s).

Tests: `packages/server/inbox-launch-windows.test.ts` (the pure rules everywhere, with the macOS/Linux forms; on Windows, in the `pi-extension-ai-runtime-windows` job of `windows.yml`: PowerShell commands run for real, `attrib +h` folders, a junction to the Windows folder, a `.cmd` through cmd.exe and its tree kill).
