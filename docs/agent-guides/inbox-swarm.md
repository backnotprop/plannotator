## Swarm

Several agents work on one Inbox thread as one team. Experimental, **off by default**: its row in Settings → Capabilities → Experimental ("Swarm", beside Grid; `data-settings-swarm`), config.json `{ "experimental": { "swarm": true } }`, or `PLANNOTATOR_EXPERIMENTAL=swarm`, which decides over the row and locks it (`resolveExperimental(config, "swarm")`). The row saves `experimental: { swarm }` through the settings route as Grid's does (`saveExperimental`). Swarm is in the one set of capabilities shared by linked computers (`INBOX_CAPABILITY_SET_KEYS`, "One set of capabilities" in `inbox-machines.md`; its key is read inside `experimental`, `INBOX_CAPABILITY_EXPERIMENTAL_KEYS`), so a flip on one computer flips it on the others, and in `plannotator inbox capability` as `swarm` (read from `experimental.swarm`, turned by posting `experimental: { swarm }`; it is not in the door's older-window key list, `INBOX_CAPABILITY_SWITCH_KEYS`). Off, nothing of it shows or answers: no `/swarm` skill in the catalog, no `swarm` on the thread read, `/api/inbox/swarm` answers `409 swarm_off`, `threads/:id/swarm` `404`, and `plannotator inbox --help` has no Swarm section.

Piece 1 (this): several agents in New message, the swarm record, the ghost thread, `plannotator inbox swarm`, the read-only plan card, the Settings row, and adding and removing an agent. Later pieces add the task list (`swarm add`, `take`, `done`, `tasks`; until then the command refuses them with `not_available`) and Change plan.

### Starting a swarm

- The `/swarm` built-in skill (`packages/core/swarm-skill.ts`, the owner's approved text, pinned by `swarm-skill.test.ts`): the Swarm badge puts `/swarm` in the words, and the window pastes the text at Send like any human-only built-in.
- A person's message whose skills block names `swarm` (`inboxMessageStartsSwarm`, `packages/shared/inbox/swarm-start.ts`) starts the swarm of its thread when it is written (inbox.ts, beside the far tags' subscriber): the record and the ghost thread.
- New message to several agents: `to` is the first pick, the others ride `tags` (`startPersonThread`'s `tags`, resolved by the far tags' `targets`, so an agent on a linked computer can be picked). `tags` in a New message is refused while Swarm is off.
- What each agent is handed (`packages/server/inbox-swarm-wake.ts`): the message, then `swarmJoinLine(threadId)`. The stored body is unchanged. The join line is decided from the root itself (it names `/swarm`, and no swarm of it is turned off), never from whether the record is written yet: a held poll and the far tags build the wake inside the very write that starts the swarm. `joinSwarm` starts the swarm of such a root when its record is not there yet, so the join that line asks for always works. A later message of the person's that names `/swarm` in a swarm that is on (Add an agent's, below) carries the join line too.

### Adding and removing an agent

- **Add an agent** (the status view's foot): a list of the agents the thread reaches (`threads/:id/taggable`, the reply's `@` list: this computer's and each linked computer's), less the members (`SwarmAddList.tsx`). A pick posts `threads/:id/swarm/add` (`addSwarmAgent`, `inbox-swarm-route.ts`): the agent is resolved as a reply's tag is (the far tags' `targets`), and `store.writeSwarmAdd` writes the person's message `/swarm` with the approved skill text (`swarmAddBody`, never a skill of the person's own) as a reply to the root, with no `to` and tagged to that agent (`joined: true` for a live agent, the "Add instead" wake; a plain tag for one that reads the Inbox only). So only that agent is handed it, with the join line; the agents in are not woken again. Such a message has no owner (`inboxTagsOnly`, `packages/core/inbox-delivery.ts`; the store's `recipientOf` is null): the thread's head says "to <the agent added>" with no "tagged" and draws only that agent's delivery line, and its list row draws no owner's delivery (never the thread's first agent's "Saved for"). It is a member that has not joined (the thread names it) until it runs join. An agent on a linked computer: its tag carries `machine`, and the far tags send its wake there through the outbox; from another computer's window the route goes through the forward (outbox `append`, written once under its key). A joined member still in writes nothing.
- **Remove** (a member's row: quiet "Remove" on hover and focus; a phone's row swipes left): main's Remove an agent from a thread (`threads/:id/remove-agent`, its toast and Undo; `swarmRemove.ts`). `removeFromThread` takes a swarm member that never wrote in the thread (a sub-agent). While the removal stands (`store.swarmRemoved`), the agent is in neither list of the wire, not in "to everyone" (`saySwarm`), handed no ghost words (`isSwarmMember`), and its `say`, `doing`, `propose` and `join` are refused `removed_from_swarm` with `SWARM_WORDS.removed` ("The person removed you from this swarm, so nothing was written. You are back in it only if the person adds you again.", approved as a CLI refusal line). Its past ghost words stay. Added again (or any message of the person's to it), it is back as it was. Across computers: the remove route is main's (door, outbox `set`); a far member's own computer cannot speak for it there.

### The record and the ghost thread

- One `swarm` record per thread (`InboxSwarmRecord`, `packages/core/inbox-swarm-types.ts`) in the project's `swarm.jsonl`, quiet like `steps` and `thread_pull`: `on`, `ghost_id`, `members` (each `session`, `host`, `name`, `machine?`, `machine_name?`, `for?`, `joined_at`, `doing?`), `person_seen_at`, `plan?` (below).
- The ghost thread is a real thread whose root (written by the Inbox, author `person`, empty body) carries `ghost_of: <thread id>`. The store keeps `ghostParents`; `listRow` answers null for it, so it is never in the list, a section, unread counts, notifications, the Board or Tidy; `threadsOf` skips it; search never indexes it; its messages are never a session's latest or first thread (sidebar, routing) and its person tags are not indexed.
- The wire: `InboxThread.swarm = { on, ghost_id, members, ghost_unread, plan? }` on `GET /api/inbox/threads/:id`. Members are the joined agents, then the agents the thread is addressed to (`to` and every person tag) that have not joined, `joined: false`. A member on a linked computer carries that computer's name (`machine_name`, from `far.nameOf` of its `machine` when the record or the tag has none), so the status view and the plan card never show this computer's name for it. `state` is `working` / `idle` from the live connection (here or on a linked computer), `waiting` when the thread waits on the person after that agent's words, else null.

### The plan

The proposal `/swarm` asks for, as the agent's first reply: `plannotator inbox swarm propose "<plan>"` (`proposeSwarm`, `parseSwarmPlan`, `packages/shared/inbox/swarm.ts`). Its text is one list item per agent, `- <name>: <what it will do>`; an item indented under another is that agent's sub-agent (`for`), one with nothing above it is the proposer's; a line that is not a list item is the plan in one line (`summary`, 200 characters). A bad line refuses the whole proposal (`validation_error`, "Line N: …"), and only a member may propose (`not_in_swarm`).

- The record's `plan`: `{ summary?, parts: [{ who, does, for?, by, at }], message_id, at }`, at most 60 parts (`INBOX_SWARM_PLAN_MAX`). A later proposal, from the same agent or another, adds to it: a line for a name already there (case-insensitive) replaces that line, a new one is added, a summary given replaces the old.
- The first proposal (no plan, or its message is gone) writes one agent message, the proposer's reply to the person's latest message (`reply_to`), with `swarm_plan: true` (server-only, `InboxSendInput.swarm_plan`) and the plan as plain words (`swarmPlanText`), so every reader that does not draw the card (search, notifications, an older window, the phone today, Swarm off) reads it as a message. It wakes as the agent's own reply does (`wakes` from this computer's live connection; a far proposer's comes through its door, `author.machine`). A later proposal writes no message: the record's write goes out as the `swarm` stream line, and the open thread re-reads.
- The wire's `plan` is there only while its message is. Plain prose proposals (an ordinary `send_message`) stay ordinary messages.
- The card (`SwarmPlanCard.tsx`, `swarmPlanModel.ts`, `swarmPlan.css`): drawn in place of the body of the message whose id is `plan.message_id` (`drawMessageBody` → `SwarmPlanSlot`), from the thread's swarm, which `useThreadSwarm` shares by thread id (`swarmThreadShare.ts`), because the message list draws from its data only. Its band: the Swarm gradient and the dots mark, "Swarm plan", one status line ("Started <time>", then "everyone joined", "<name> is joining [on <computer>]", "N agents are joining" or "turned off"), the part count. Then the summary, then each part: what it does, the agent's mark, name and where it runs (project · computer, as the status view words it), "joining" while its agent has not joined, "sub-agent" for a sub-agent not in the swarm, "Added by X" when another agent wrote the line. More than 8 parts fold to 6 and "Show N more". The foot opens the ghost thread. No change controls in this piece (Change plan is a later one), no marks in the band. Narrow (a phone, a narrow pane) the rows stack (a container query).

### Delivery inside a ghost thread

The only place an agent's words reach other agents. `store.isGhostSay(message)`: an agent message in a ghost thread with tags. `pendingReplies`, `pendingRepliesFor`, `pendingFor`, `recordDelivery`, `recordCloudWake`, `wakingSessionsOfHost` and `farSessions` accept it, for a tagged session that is a member of a swarm that is on, and only for a connection that words tags. The person's words from the ghost pane follow the same rule: a member only, while on. With the experimental switch off (`store.setSwarmSwitch`, set by inbox.ts) no ghost words wait for anyone. `store.ghostWaitsFor(message)` names the sessions they still wait for (never the author). Every other thread is exactly as before. A ghost message is handed as a notice (`moved` with its own `notice` line, `SWARM_WORDS.wake`, `swarmNoticeOf`), so it never reads as the person's reply. A far member's tag carries its `machine`; the far tags' `onPersonMessage` sends its wake there.

Only `swarm say` writes there: the store refuses an agent's `send_message` whose `reply_to` is in a ghost thread (`SWARM_GHOST_SEND_REFUSED`, `swarm-start.ts`; `sendProject` refuses it first, before any attachment is kept), and `writeGhostMessage` refuses an agent that is not a member. Turned back on (Turn on, or the experimental switch seen going from off to on), nothing said before is handed out: the record's `on_seq` (the store stamps it when a swarm turns on) and the switch's in-process mark (the store's seq the last time it was seen off, so the first words after it is back are handed even when nothing looked in between) leave older ghost words waiting for nobody. An Inbox restarted while the switch was off does not know it was off.

Delivery receipts stay in the ghost thread: a member's delivery is written on the ghost message's tag, never on the main thread, and the ghost thread is no row, so no unread, no "Delivered to …" line and no notification comes of it (`swarm-wakes.test.ts`).

### Who is woken how

Each member is woken by the channel its host's ordinary reply uses, once per message, by the command `replyCommand` makes (the notice):

|---|---|---|

| Codex | The Codex wake: `codex queue`, or a launched thread's app-server; its subscriber looks at a ghost message's tags as at a person's | store test; the wake read only |
| Qwen Code | The Qwen wake's cross-session frame, same subscriber change | store test; read only |
| T3 Code (no mod) | The T3 wake, same subscriber change | store test; read only |
| Antigravity | The Antigravity wake's `agentapi send-message`, same subscriber change | `inbox-swarm-host-wakes.test.ts` |
| Paired cloud agent with a wake address | The cloud wake's webhook, the notice line first in the item's words; each member's own wake state on its tag (`InboxTag.cloud_wake`, `store.cloudWakeOf`), and its own gap and backoff, so no member's wake overwrites another's and none is woken twice | `inbox-swarm-host-wakes.test.ts` |
| Paired cloud agent that checks by itself | Its relay signal (`agentSignalsFor`): only the members the words wait for | read only |
| A launched session that rests | Started again (`maybeRespawn`), as the person's reply starts it (inbox-launch.ts, its subscriber) | read only |

### The window

Approval `inbox-swarm-thread-ui`; all of it in `packages/inbox/swarm/` (styles `swarm.css`, `swarmBadge.css`), wired into ComposeDialog, Thread and App by single lines. The window learns the switch from `settings.experimental.swarm` (`useSwarmOn` in App, `useSwarmSwitch` anywhere); off, none of it renders and `thread.swarm` is absent anyway.

- New message (`useSwarmPicks`): after the first To, "Add an agent" picks more agents from any computer (`ToPicker` / `PhoneToSheet` with `checked`), each a chip; the Swarm badge at the row's end puts `/swarm` in the words. Send posts the others as `tags` (`machine` only when the pick is not on the thread's computer). The Swarm tip shows once across windows: `POST reveal` `{swarm_tip}` (`swarmTipClaim`, config `inboxReveals.swarm_tip`), refused while Swarm is off. It is "Turn on for", then one line per thing that is true today (`SWARM_TIP_SHOWN` in `useSwarmTip.tsx`: Agents work together, Ghost thread; the shared task list's line is drawn and worded, and comes in by adding `'tasks'` there), and it goes for good when Swarm is turned on (the badge, or `/swarm` typed).
- A swarm thread (`useThreadSwarm`): the Ghost button first in the top bar (the "Glancing" ghost, `GhostGlyph`: assets/ghost/ghost-glance*.svg, a small cut for 16-20 px, `ghost_unread` while above zero, no shortcut); the summary row in the meta line in place of "N sessions", whose chevron opens the status view (each member's computer, state as words, doing line; a sub-agent indented under its `for`; foot: Add an agent, Ghost thread, Turn off / Turn on; below, "Adding and removing an agent").
- The ghost pane (`GhostPane`): local state of the thread pane, beside the thread the way a file is (the list column steps aside), covering it when the room is too narrow and on a phone, where its back button returns. Opening it posts `seen` when there is something unread; its box posts `say` (`GhostTo`: everyone or one joined member). A file opening closes it and opening it closes the file.
- The stream: a `swarm` line, and a ghost thread's message, go out as `{ kind: "swarm", id, thread_id: <swarm thread> }` (`eventPayload`), never as a message, so nothing notifies and the open thread re-reads (`threadOfRecord`, `applyRecord`).
- The window route checks the page's `serverSession` as every window write does (a tab from an earlier run: `409`), then takes it and `idempotency_key` off the body before it reads it. `{ on: true }` is Turn on for a swarm that exists (turned off); on any other thread it answers `409 not_a_swarm`: a swarm starts only from a message that names `/swarm`.
- The settings read always carries `experimental.swarm` (`{ on, env }`), as it does Grid; a settings frame of an experimental change carries it too (`experimentalOfFrame`), so another window's or a linked computer's flip reaches this window. A turn reads the skill catalog again (`adoptSwarmOn`), so `/swarm` comes and goes with the switch.
- Escape: the status view's and the ghost box's lists close on it, never on an Escape pressed inside a modal dialog that does not hold them (New message; `swarm/escape.ts`); the Swarm tip, a note, closes on an Escape that goes on to New message, so one Escape closes that.
- A phone's New message: the other agents' marks, Add an agent's `+` and the badge sit inline after To's pill in the foot's row. With them in it the row's gaps narrow (8 to 4 px, `swarm.css`), so Send stays on a 390 px screen; at 360 px and below the row is still wider than the screen, and what gives way there is not decided yet.
- Deleting a thread deletes its ghost thread with it (`deleteThread`); the swarm record goes with the thread's lines.

### `plannotator inbox swarm`

`apps/hook/server/inbox-swarm-command.ts`, a thin client over `POST /api/inbox/swarm` (`packages/server/inbox-swarm-route.ts`), with the capability command's guards: never through a device door, another site's page refused, a paired cloud agent through the agent door's `route`. `join <thread> [--as] [--for]` (idempotent; a name taken is refused; `--for` must name a member; a name, `--as` or the host's own, is one line of at most 60 characters, so the wake's notice names the agent who wrote and never falls back to the person's line), `propose "<plan>"` (the plan card, above), `doing "<line>"` (control characters out, at most 200 characters), `status [<thread>]`, `say "<text>" [--to <name>]`, `leave`. Without `--thread`, `propose`, `say`, `doing`, `status` and `leave` act in the one swarm the caller is in. The words agents read are `SWARM_WORDS` (`packages/shared/inbox/swarm.ts`), `INBOX_SWARM_USAGE` and `INBOX_SWARM_HELP_SECTION`.

### Linked computers

The swarm lives on the thread's computer. A linked computer's agent runs the command on its own computer; that Inbox finds the thread's computer (`placeOf`: a wake it holds, a listed row, else a read) and asks its door's `POST swarm` (a machine's token only; `farSwarmAnswer`, as the far tags' `asSession`, refuses a session that is not the calling computer's: one live here, a member with no `machine` or another computer's, one a thread here is addressed to (`to` or a tag) with no `machine`, or one `sessionMachine` puts elsewhere, so a join never rewrites another computer's member). `say` to an away computer is held in the outbox as this Inbox's own write, as a far reply is (`packages/server/inbox-swarm-far.ts`, `holdSwarmSay`): the agent reads `FAR_REPLY_WORDS.held` ("Waiting for …"), and it goes once when that computer is back; its key (`swarm-say:<uuid>`) is written on the ghost message there, so a resend after a lost answer writes nothing more (`writeGhostMessage`). `join`, `status`, `doing` and `leave` are answered now; an away computer refuses them with `machine_offline`. A far join is kept in `swarm-far-joins.json` in the Inbox's data (0600; `createSwarmFarJoins`), so `say`, `doing` and `leave` need no `--thread` after a restart; `leave` forgets it. The window's `threads/:id/swarm` is on the door's allowlist, so the phone and a linked computer's window reach it.
