- A New message belongs only to the session it names. The store keeps it as a person message with `reply_to: null` and `to: { host, session }` (`InboxAddressee`), and `InboxStore.isFor` hands it to that session only:

  - Another session's `wait_for_reply` never returns it (`forCaller` in `inbox-mcp.ts`).
  - Another agent reading the thread through `read_thread` sees its text but does not settle it. It is settled only by its delivery: the named session's wake, or that session's own `wait_for_reply`, which records the delivery.
- Live sessions are kept in memory only. Every bridge poll can carry `project_path`, `started_at`, `busy` and `idle_since`, and `POST /api/inbox/bridge/event` `{ type: "state", busy }` says when a turn starts or ends.
  - A session is live while it polled within `INBOX_SESSION_LIVE_MS` (30 s, `connection.ts`) or holds a poll now.
  - It is in a project when its `project_path` resolves to the project's root (the send resolution: realpath, then the repository root, a linked worktree counting as its main repository; the shared project-root cache). A connection that sends no `project_path` is in a project when it wrote there.
  - All three connections send all four: the Claude Code mod, and Pi and OpenCode through the shared `InboxWake` (`project_path` from the target's `projectPath()`: Pi's `ctx.cwd`, OpenCode's session `location.directory`; `started_at` the wake's start in ms; `busy`/`idle_since` from `isBusy()`, asked every tick while a reply waits and every 5 ticks otherwise, with a `state` event when it flips). So every live session is listed under its real project from its first poll, even one that never wrote. On Pi and OpenCode the wake (and so the poll) runs only where the Inbox tool is on.
- Routes: `GET /api/inbox/threads/:id/sessions` and `POST /api/inbox/threads/:id/message` (see "Inbox Server"). A session that is no longer live is `409 session_not_live` and nothing is written. A replayed key answers the message it wrote.

**Sessions the Inbox runs (ACP runner; spec "Inbox replies as real turns for Cursor and Grok", step 1: Grok Build).** Grok Build (and Cursor next) cannot be woken from outside, so the Inbox runs it itself over ACP and every reply in its thread is a real turn. Server: `packages/server/inbox-acp-runner.ts` (the runner and its routes), wire types in `packages/core/inbox-acp.ts`, the ACP client in `packages/acp-client/`. Window: compose's To picker (`compose/ToPicker.tsx`, `startChoices` in `compose/model.ts`), `components/RunLine.tsx` (`RunLine`, `PermissionCard`, `RunFoot`), `components/RunAgentsSettings.tsx`.
- Agents: `INBOX_RUN_AGENTS` (`grok`: `grok agent stdio`, the `GROK` descriptor in `packages/acp-client/agents.ts`); Cursor is one more entry (no `resumeCommand`: its CLI does not open ACP sessions; never `session/set_config_option`, which rewrites Cursor's global defaults). The program is found on the agent environment's PATH and must answer `--version` with the descriptor's `versionShape` (cached a minute).
- Starting: compose's To lists "New Grok Build session" rows (one per installed, enabled agent and Inbox project whose folder exists, the current project first, 4 before typing; a filter searches every folder), To id `start:<agent>:<project id>`. Send posts `POST /api/inbox/acp/start`: the runner makes a session (key `run_<ulid>`, also its agent session id in the Inbox), registers it with the live sessions as a runner session (`registerRunnerSession`: always live, never listed in compose, a thread's project sessions or a reply's `to`), then writes the thread with compose's own `writeThread` addressed `{ host: "grok", session: key }`. A replayed idempotency key answers the thread it wrote.
- Turns: every message the session waits for (`store.pendingReplies`; 👍 and set-aside notes are recorded as delivered without a turn, so the window and the row say a 👍 is saved for the session to read, never "Delivered") becomes ONE turn: `session/new` the first time (cwd the project's folder, MCP server `plannotator-inbox` = `<selfCommand> inbox mcp` with `PLANNOTATOR_SESSION_TAG=grok:<key>`, `PLANNOTATOR_DATA_DIR`, `PLANNOTATOR_CWD` in its own env), `session/load` after (replayed history ignored), the wake text the connections send (`inboxWakeText`, several replies joined), then `session/close`. No system prompt, no mode or model change. Replies are recorded delivered as the prompt goes, so an interrupted turn is never sent again. A `session/load` that fails sends nothing and says why (never a fallback to `session/new`); the failed replies wait for a new message or Try again (`/retry`). The shim (`apps/hook/server/inbox-mcp-shim.ts`, `INBOX_RUNNER_HOSTS`) sends as that session (author `grok`, "Grok Build") and marks its calls as waking, so send_message tells it the reply comes by itself. A turn that ends by itself with no Inbox message from the session posts its final text (after its last tool call) as its message (`acp-final-<reply id>`); a stopped turn posts nothing.
- Permissions: the agent's own settings decide what it asks; every request waits with all its options and no timeout (`permission` on the status; `POST …/permission` `{ permission_id, option_id, approve_rest? }`, "Allow this and the rest of this turn" answers allow-once for the turn). Calls to the Inbox's own MCP tools are allowed once without a prompt (`ownToolAutoAllow` in `packages/acp-client/permission-policy.ts`; Grok titles them `plannotator-inbox__<tool>`). While one waits the list row is in Stopped on you (`decorateRow`, additive `run` on the row: `{ key, agent, label, state, permission_title, permission_id }`), the window raises a notice (`acp:<id>` claim, "<project>: Grok Build needs your OK") and the question sound, and a paired phone gets a push (`relay.pushText`). Stop (`POST …/stop`) reaches only that turn's own process (kept on the turn): it answers a waiting request `cancelled`, sends `session/cancel` for that session, and when the turn has not ended after 10 s it ends the turn as stopped and kills the process group, unless another session's turn runs on the same process, which is left running.
- Processes: one agent process per agent kind (the starting process is recorded before anything is awaited, so turns that start together share it), its own process group, started on demand with the person's environment minus another session's identity (`INBOX_RUN_ENV_DROPPED`: `PLANNOTATOR_SESSION_TAG`, `PI_SESSION_ID`, `CODEX_THREAD_ID`, `CLAUDECODE`, so a `plannotator inbox …` or `card …` from its shell never sends as that session), given `INBOX_RUN_START_TIMEOUT_MS` (2 min; Grok Build updates itself as it starts) to answer `initialize`, else the turn fails ("did not answer within 120 s of starting, so nothing was sent") and its group is stopped. Stop reaches a process still starting: past the grace it gets SIGTERM, then SIGKILL 3 s later (unless another turn waits for that start), and the turn reads Stopped; the next turn starts a new process, never waiting on a hung start. A running prompt has no time limit: Stop ends it (cancel, then the group stopped after the 10 s grace). The process is stopped after 10 min idle (never while a turn or permission runs), killed (a process still starting too) on the Inbox's clean stop and restart, which also SIGKILLs every group still inside its 3 s grace (`killPendingProcessGroups`: a stopped, idle-stopped or exited agent, whose unref'd SIGKILL timer would never fire once the Inbox exits). An agent that exits or crashes by itself has its group stopped too (SIGTERM, then SIGKILL), so a dev server or watcher it started never outlives it. An empty group is never signalled (`processGroupAlive`, `kill(-pid, 0)`, checked before every delayed SIGKILL and in `killPendingProcessGroups`; a stopped agent whose whole group ended cancels its SIGKILL), since its id may already be another group's. A synchronous `process.on("exit")` hook in `packages/acp-client/client.ts` SIGKILLs every live agent group and the pending ones, so an uncaught exception leaves none; a running turn then reads Interrupted (fixed at the next start from `inbox/acp/sessions.json`, 0600, `{ key, agent, acp_session_id, cwd, project_id, thread_id, created_at, turns }`).
- Secrets: Grok's `_x.ai/*` notifications carry the person's MCP server env (API keys). The ACP client hands a host only an extension notification's method name and drops the params; the runner keeps nothing of them and never logs the agent's stderr. Activity (the last 20 tool titles, the last 4000 characters of text) is memory only.
- Who: the window on this computer, the owner's tailnet login (`tailscale.isOwnerRequest`), paired phones (door rows `acp`, `acp/:key`, `acp/start`, `acp/:key/permission|stop|retry`). A tailnet guest (`inboxTailscaleAllow`) gets `403 owner_only` on the runner routes and on writes to a thread a runner session answers.
- The window: under each person message the run line replaces the delivery line ("Queued", "Starting Grok Build…", "Grok Build is working · 0:42 · Stop · Show activity", "Grok Build needs your OK" with the card, "Done · 1:12", "Stopped", "Interrupted…", "Not sent: <why>" with Try again); the thread foot "Open in Grok Build: `grok -r <id>` in <folder> · Copy" and "Close it in Grok Build before you reply here." (folded on a phone); the row reads "Grok Build is working" / "needs your OK". Windows hear `event: runs` (`{ key, thread_ids, permission? }`) and read the run again. Settings → Agents "Run in the Inbox" (config.json `inboxRun`) and the note that Grok Build updates itself when it starts; its model is Grok's own. The section lists only agents installed on this computer and is not drawn when none is: without Grok Build, Settings looks as before (no install command, no switch).

**Compose: a new message to a connected agent** (approval record "inbox-compose-to-agent", 2026-10-14, not in this repo: variant Compose; the owner's answers "close asks Keep draft / Discard", "no send without a live agent", "any file, keep uploads simple"). The person starts a NEW thread with one live agent session in any project. Server: `packages/server/inbox-compose.ts` (routes), `packages/server/inbox-sessions.ts` (`allLive`, `composeTarget`, `isSessionLive`), `packages/shared/inbox/drafts.ts`, `packages/shared/inbox/uploads.ts`, `InboxStore.startPersonThread` / `readdressMessage`.
- The thread: a root PERSON message (`started_by_person: true`, `reply_to: null`, `to: { host, session }`, `subject_question: null`), written by `startPersonThread`. Its subject is a SHORT name, not the first 120 characters of the first line an agent's derived subject is: `derivePersonThreadSubject` (`packages/core/inbox-thread-subject.ts`, re-exported by `@plannotator/core/inbox-questions` beside `deriveInboxSubject`), which compose's subject preview (`subjectPreview` in `packages/inbox/compose/model.ts`, also the Drafts page's rows) calls too, so the preview is what the store writes. The rule: the first line with words, plain (markdown marks, link targets, images, HTML, list/quote/heading marks dropped; fenced code and `:::` blocks skipped); a greeting or filler at its start dropped ("Hey Claude,", "So,", "Okay so", "Um,"; "so" only before a comma, another filler or a request word, so "So many tests…" keeps it; a dash ends one only with spaces around it, so "Right-click", "Hi-DPI", "Well-known" and "So-called" stay whole; an agent's name may follow a greeting without a comma, but "there", "team", "all" and the like only before punctuation, so "Hey there is a bug" keeps "There is a bug"; when dropping would leave only a name or nothing, "Hey Claude" alone, the line is kept as it is) and the next letter capitalized; a URL shortened to its host and last path part, a long path to its last two parts; then the first sentence when it fits 60 columns (`PERSON_THREAD_SUBJECT_COLUMNS`; CJK, Hangul, full-width and emoji count two; a sentence never ends at an abbreviation, a lone initial or single letters with dots such as "U.S."), whole, final "." dropped, "?" and "!" kept, no "…"; else its last clause boundary (comma, semicolon, colon, dash; at least 24 columns) plus "…"; else the last whole word that fits (a dangling "and", "the"… dropped) plus "…", and text without spaces is cut between characters (never inside one). A body with no words is named by its first image's alt text or file name, else the first attached file's name ("spec.md and 2 more files"), else "Image", else its first line of code, else its first question's prompt (a body that is only a `:::question` block), else its first line with anything on it (an unclosed directive), so a body with anything on it always gets a subject. Bidi controls are stripped from the subject. Stored once, at send; threads already written keep their subject. Agents' subjects keep `deriveInboxSubject`. Question blocks in it are text: no question records. It is no session's default thread (`indexRoot` gives only agent roots a session's default thread; a person root is indexed only by a name it has), so only a `reply_to` answer (or a send naming its `thread_name`) lands in it; the session's next message without `reply_to` joins its own thread. It is handed to that session alone (`isFor` by `to`), settled only by delivery, and the list places it by the existing rules: Sent until delivered (the delivery is the agent's read), then Quiet; New once the agent answers. The row carries the additive `addressee` (the root's current `to`), so the window draws the agent's mark and "To <agent>" instead of the person's. Idempotent on its key (`personThreadByKey`); another body under it is `idempotency_key_reused`. Two Sends racing with one key both answer the one message; the one the store replays answers `replayed: true` and its copied files are removed, as they are when the store refuses the message.
- The wake: the bridge command stays `type: "message"` and adds `new_thread: true` for such a root; `inboxWakeText` then takes `INBOX_NEW_THREAD_INSTRUCTION` (a new fixed constant in the connection contract, copied into the mod's `inbox-contract.ts`): the person's own idea or request, possibly unrelated; say how you will handle it before you start; answer with `reply_to`. An older connection ignores `new_thread` and uses `INBOX_MESSAGE_INSTRUCTION`, which stays true. Files the person attached ride the command's `body` as `Attached: <name> (<path>)` lines (`inboxBodyForAgent` in `uploads.ts`, used by `replyCommand` and by `wait_for_reply`'s result alike).
- No live session, no send: `POST /api/inbox/messages` answers `409 session_not_live` and writes nothing (`composeTarget`: live within `INBOX_SESSION_LIVE_MS` or holding a poll, any project; the host, when given, must match). The window saves a draft instead.
- Where the thread goes: the session's root (its `project_path`, resolved through `resolveProject`, which creates a project new to the Inbox; a linked worktree folds into its main repository's project, as a send does), else the project it last wrote in (`lastThreadsBySession`). When git does not answer in time and no existing repository project holds the folder, the Send answers `503 project_unresolved` ("…try the same call again") and writes nothing; the pending uploads stay, so the same Send goes once git answers. `GET /api/inbox/sessions` groups the live sessions the same way (a folder the Inbox has not seen yet has `id: null` and its folder name); a session with neither is not listed.
- Send to another session (`POST /api/inbox/messages/:id/to`): re-addresses a person message that no session took yet (a thread the person started, a New message, a redirected reply, or a reply in a thread the person started) to a live session of its thread's project (`replyTarget`). A new snapshot of the same message (the last line wins); `409 already_delivered` once delivered, `409 thread_resolved` on an archived thread, `422 not_addressed` for anything else. A reply in a thread the person started, moved to a session that has seen nothing of that thread (it never took the root, the root is not addressed to it, and it never wrote there), wakes it with `continues_thread: true`, and `inboxWakeText` adds `inboxContinuesLine` (read the thread first with `read_thread`, then answer with `reply_to`). The window offers it after the asker grace (`GET /api/inbox/sessions?session=<id>` or the thread route's `?asker=`).
- A reply in a thread the person started, written before the agent answered, is stamped with the `to` of the message it answers (the root's current `to`) when it is written (`sendReply`), so like any addressed message it is handed only to that session and settled only by its delivery: another agent's `read_thread` or `wait_for_reply` never settles it.
- The thread's name (its chip, `thread_name`): the person may give one in compose (`thread_name` on `POST /api/inbox/messages`, checked by `checkInboxThreadName`: one line, 1 to 120 visible characters, no control or bidi characters; `422 validation_error` otherwise; refused with `409 thread_name_taken`, nothing written, while another OPEN thread of the project has the name (compared by `inboxThreadNameKey`; a resolved one does not hold it); empty means none; part of the Send's idempotency). Compose sends its own suggestion the same way with `thread_name_auto: true` (the chip the person left following the message): best effort, so one that is not a valid name or that another open thread has is dropped without refusing the Send, and it is stored with `named_by: { kind: "auto", at }`, which still lets the agent name the thread (`threadNamers` ignores it) and is replaced, once, by the agent's name; a retry compares only a name the person typed. Otherwise the agent names it ("Naming a thread the person started" under "Agent connections and the knob"). The root carries `named_by` (`{ kind: "person" | "auto", at }` or `{ kind: "agent", host, session, message_id, at }`); a name the person typed or an agent gave never changes. Routing (review of #1956): a compose name, typed or suggested, routes NOTHING. Another session's `send_message` with that `thread` starts its own thread; only the addressed session's `reply_to` replies land in the person's thread, and only an AGENT's name (given once, never changed after) indexes it in `namedThreads`, from which point named sends join it as for any agent-named thread. Compose names live in `personNamed`, read only by `threadNameTaken` (with the root's current name, since an agent may replace a suggestion), so two open threads never share a name. Proved by an independent model, `packages/shared/inbox/store-routing-model.test.ts` (built from the operations alone, with readdress, delete and reopen; it asserts a named send lands in a person's thread only when an agent named it so), beside the line-walk oracle in `store.test.ts`. A retried agent reply compares its `thread` only when the stored reply kept `thread_naming` (anywhere else `thread` with `reply_to` is ignored, and older stores never recorded `reply_thread`). The bold subject stays the short name above. A thread an AGENT named is indexed under its name (`namedThreads`), so later sends with that `thread` join it; a compose name never is (see "Routing" above).
- Drafts: one file per draft, `inbox/drafts/<drf_id>.json` (0600, folder 0700, temp then rename), `{ v: 1, id, created_at, updated_at, body, to: { host, session, project_root, project_name, started_at } | null, project, files: [upload], thread_name?, card?, board_request? }` (`board_request: true`: the Board chip was on when it was saved, kept as it was left; `thread_name` as the person typed it in the chip, at most 500 characters; absent while the chip follows the message; the Send checks it. `card`: `{ id: crd_…, title }`, the Board card a Create thread compose was for, so sending the draft later still links the thread to it; anything else is `422 validation_error` on `card`). Never in the event log, so never seen by agents, the MCP, phones, the relay or search. A save is a compare-and-set on `updated_at` (`base`: the `updated_at` the writer read, null to create; a mismatch is `409 draft_conflict` with the newer draft); `updated_at` always moves forward. `GET /api/inbox/drafts` adds each draft's chip, `status: live | ended | none` (its session live now, gone, or none chosen). Sending with `draft_id` deletes the draft. A draft never sends itself and is never re-addressed on its own. Storage in Settings counts the drafts' bytes; `uninstall --purge` removes them with `inbox/`.
- Uploads (`POST /api/inbox/uploads?name=<name>&serverSession=<s>`, the raw body): streamed to a temp file in `blobs/` (never whole in memory), refused past `INBOX_UPLOAD_MAX_BYTES` (100 MB, under the 128 MiB request bound; `413 upload_too_large`), hashed and renamed to `blobs/<sha256>`, the kind decided by `decideInboxAttachmentKind`, and recorded as `inbox/uploads/pending/<upl_id>.json`. The name must be a plain file name (no `/` or `\`, none of the thread name's refused characters: C0 and C1 controls, U+2028/U+2029, bidi controls; at most 255 bytes) outside the dotenv family (`422 upload_refused`, "Not attached: .env files often hold secrets."). At send each upload becomes an ordinary `InboxAttachment` (`inboxUploadAttachments`): the blob copied (a clone where the filesystem has them; never a hard link, so an agent writing to its file cannot change the stored blob), read-only outside Windows (where a read-only file could not be swept), at `inbox/uploads/<att_id>/<name>`, its realpath the record's `path`, `named_path` null, so the tiles, viewers, download route and phone door carry it unchanged, and it never reads as changed since sent. The store's blob sweep after a deletion keeps the pending uploads' blobs and removes the `uploads/<att_id>/` files of deleted messages; an hourly sweep (and one at start) forgets pending uploads older than a day that no draft names, and the blobs only they held (`sweepInboxUploads`).

- Who is handed it: the owner, always, and every tagged session (`InboxStore.isFor`). Each records its own delivery: the owner's in `delivery`, each tag's in its own entry (`recordDelivery` by the session). **The bug fix that came with it:** a reply without `to` used to count as read when ANY agent read the thread (`agent_checked_seq`), so a tagged agent told to read the thread first could swallow the owner's wake. A reply with tags is settled for each recipient only by its own delivery or its own `wait_for_reply`, like a message `to` one session (`pendingReplies`); a tagged session's delivery marks nothing for the owner. Proved by `packages/server/inbox-tags.test.ts` (the read before the owner's poll) and the property in `packages/shared/inbox/store.test.ts` ("settled for each recipient only by its own delivery"; the op model sends tagged replies and tagged deliveries, and routing determinism and the round trip hold).
- The wake (`packages/shared/inbox/connection.ts`, the mod's byte copy in `apps/hook/hooks/mod/inbox-contract.ts`): a tagged session's command carries `tagged: { owner }` (the owner's agent named from its host) and `inboxWakeText` gives `INBOX_TAGGED_INSTRUCTION` and `inboxTaggedLine` (read the thread first with read_thread, answer only what is addressed to you, with reply_to). The owner's command carries `also_tagged: [names]` and its wake adds `inboxAlsoTaggedLine` after its instruction. Names are hosts' own names only (they go into another session's prompt, and an MCP agent chooses its own `agent_host`): the server maps each host through `INBOX_HOST_NAMES`, and `inboxWakeText` keeps only a name in `INBOX_WAKE_AGENT_NAMES`; anything else reads "another agent". The tags of one Send (the words' and every comment it carries) ride its LAST reply only, once each (`sendTagsByTarget` in `packages/inbox/tags.ts`), so a tagged agent gets one reply and one wake per Send. An older connection would word a tag as "the person replied to you", which is false, so a session is handed what it was only tagged in only when its poll says `tags: true` (`pendingReplies(session, { tags })`); the Claude Code mod, Pi and OpenCode (`InboxWake`) send it. The window offers an older one as "Update Plannotator to tag this session". On Pi and OpenCode, sessions share `inbox/claims/`: a tagged command's claim is `<reply id>.<session>` (`claimDirOf`), so each session is delivered once.
- MCP-only agents: any MCP agent may be tagged. It is never woken: `wait_for_reply` without a thread also waits on every thread it was tagged in, in any project (`taggedThreadsOf`), and in a thread it never wrote in only what tags it answers; its result says `tagged_you: true` and records that agent's own delivery. `read_thread` shows `tagged: [{ agent, session }]` and `tagged_you` on the message (never the delivery state), lists tagged threads with `tagged_you` and `unread`, and records `read_at` on that agent's own tag (the window: "<agent> read this thread, <time>"). Agents do not tag each other (not built).
- Who can be tagged: `GET /api/inbox/threads/:id/taggable` (`inbox-tags.ts`): every live session in any project, the owner first (the latest agent writer, else a thread the person started's `to`), then the thread's writers, the same project, the rest; then the MCP agents (`kind: "mcp"`). `taggable: false` for a live session without the capability. On the device door (contract 7.60).
- The window: `@` at a word start in the reply box (`InboxComposerField`'s `tags`, ui's `useMentionAutocomplete` with `kinds: ['agent']` and `matchDetail: false`) opens TagPicker: a listbox of `role="group"`s labelled by their headings (the owner's agent first with "Owns this thread", then each agent, "Reads the Inbox, not woken" last with "Not woken"), the skill picker's rules (nothing active until arrowed onto; Enter, Tab and Mod+Enter keep their meaning; Escape closes it before the reply box; no new shortcut; the field's `aria-autocomplete`, `aria-controls`, `aria-activedescendant`). Labels never collide in the text (`tagOptions`): "Claude Code (another session)" in this project, "Claude Code (<project>)" in another, then "(…, another session)". A pick inserts the readable `@Label` (painted as a chip, `TAG_TOKEN_CLASS`) and a polite live region says what it means; an older Plannotator's row inserts nothing and says to update. Under the field, `TagNotes` (described by the field): "Goes to" with the owner's chip ("owns this thread") and each tag's, and one heads-up per tag that does not own the thread, another for one that cannot be woken. Send puts `tags` (with each `label`) on the reply that carries the words, plus the tags of the comments each reply carries; the owner is never sent as a tag. An untagged next reply goes to the agent that wrote last (`sendTargetsOf`, unchanged).
- File comments: `AttachmentPane` passes `mentionSource` to `Viewer` (markdown, text) and `HtmlViewer`; ui's comment composer offers the agents grouped (`MentionPerson.group`) and draws `TagNotes` under the field (`MentionSource.renderNotice`); the ids ride the annotation (`Annotation.mentions`), the Send tags those agents, and the export marks the comment ("Tagged Pi: this comment sends the reply to it too.", `attachmentFeedback`'s `tagNames`). The image, video, code and diagram comment boxes take no tags yet.
