## The canvas (`packages/canvas`)

Plannotator's own canvas: boxes, notes, text, lines drawn by hand, arrows, frames, groups, pictures, sprites, charts, custom HTML and reference cards on a plain board, with **snapshots** (captures of part of the board) that embed in a plan. It is a package with **no product surface yet**: nothing in the apps imports it. Its only consumer is its own development demo (`bun run --cwd packages/canvas demo`, port 3017). This is separate from Shape (the agent's living board in `guides-and-shared-ui.md`).

The owner's rules for it: any colour on any object, set by a person or an agent; no keyboard shortcuts; no dot grid (a plain ground); an agent hears about changes through a hand-over or comments sent in bulk, not live (the seam is `CanvasStore.since`; neither is built).

### Layers

Each layer imports only the ones above it, and `layers.test.ts` fails on any import that goes the other way: `model` < `events` < `view` < `react` < `snapshot`, with `unfurl` (server-side) importing `model` only. No React in `model/`, `events/` or `view/`, and no document change outside `events/`.

| Folder | What it owns |
|---|---|
| `model/` | The document: plain JSON, typed, versioned (`CANVAS_DOCUMENT_VERSION`, `MIGRATIONS`). `types.ts` (objects, `Snapshot`, `ReferenceTarget`), `codec.ts` (fail-closed `parseDocument` / `checkObject`; unknown fields are dropped), `document.ts` (bounds, arrow geometry, groups), `capture.ts` (taking and comparing a snapshot's capture), `color.ts`, `ink.ts` (a drawn line: its stored form, and making it from points), `html-item.ts` (the sandbox contract), `reference.ts`. |

### Events

`command → planCommand → events → applyEvents → document`, and every commit is an `Envelope` (`id`, `actor`, `origin`, `gesture`, the command, the events). A person's drag and an agent's "add image" are the same commands through the same `dispatch`; the actor is the only difference (`by` on a new object is always the actor's kind).

- **Events are field-level.** `object-added` and `object-removed` carry or name a whole object; every change to one is `object-set { id, set, unset }` naming only the fields that changed (`setEvent`, `events/reduce.ts`). The planner still builds and checks the whole next object (`checkObject`, `move` included, so nothing it makes fails to save and load), then emits the difference. This was whole-object events until the review; it was changed before any document or log existed because it decides undo, sync and the size of a hand-over.
- **Drawing order is a key on each object** (`z`, `model/order-key.ts`), not a position in a list. A key never ends in `0`, so there is always a key between any two; asked for one between two neighbours that hold the same key (two people each put something on top at the same moment), `keyBetween` gives one just above both. A caller that reorders between two objects passes the next different key above the pair as the third argument, and the key is then strictly between the pair and that one: no key the board already holds, and it passes nothing else. Without it the key is the pair's with one more digit, which a board can already hold (no command reaches this yet: `reorder` goes to the front or the back). A reorder is `object-set { z }` on the objects moved, so two people reordering different things at once both keep what they did. `doc.order` is worked out from the keys by the reducer and is not saved. The planner gives a new object a key on top.
- **Undo and redo** are the inverse events, committed as an ordinary envelope. Because they are field-level, undoing a move restores `x` and `y` and leaves alone what an agent or a peer did to the same object since. Only the local person's commands go on the stack. Commands sharing a `gesture` id are one step (a drag; one pick in the colour well). `dispatch(…, { gesture, amend: true })` folds a late change into that gesture's step wherever it now is and leaves redo alone (a link's preview arriving); its reversal goes first in the step, so a field the step and the late change both set is undone back to what it was before the step.
- **The log** keeps one entry per gesture (`foldEnvelope`), so a hand-over reads a drag as one `move` with the whole distance.
- **Agents** send JSON through `decodeCommand` and receive envelopes from `onCommit`. For a hand-over they keep `store.cursor()` and later ask `store.since(cursor)`. A cursor names the store (`epoch`) as well as the place, because commit numbers start again with every store; a cursor from another store, ahead of this one, older than the log, or taken in the middle of a gesture answers `{ kind: 'resync', document }`, never "nothing changed".
- **Sync** (seam only; no backend): `SyncPort` + `connectSync` (`events/sync.ts`). The backend puts every envelope for a canvas in one order and hands each to every peer, the sender included, as `{ stream, order, actor, envelope }` (`SyncDelivery`). Each store applies them in that order to the document all peers agree on and shows its own unconfirmed changes on top (`CanvasStore.receive`), so peers converge: different fields of one object both survive, the same field ends on the one ordered last. `connectSync` decodes every delivery (`decodeDelivery`); the reducer checks each changed object (`applyEvents(…, { check: true })`). Presence would travel beside the port.
  - **What whoever wires a backend must hold to** (nothing in the package can check any of it; the header of `events/sync.ts` has the same list):
    1. **The count is the canvas's, durable, and never starts again.** `order` is 1, 2, 3 with no gaps for one canvas, for as long as the canvas exists. The count has a name, `stream`. A backend that has lost its count starts again under a new `stream`; every connected store then stalls (`reason: 'restarted'`) instead of taking the new 1, 2, 3 for old repeats, and the host loads the canvas again. A count that restarts under the same name cannot be told from repeats and is silently ignored.
    2. **The stamp is the store's own actor.** `actor` on a delivery is what the backend knows of the connection, never what the envelope claims, and it must equal the actor the store on that connection was made with (`new CanvasStore(doc, { actor })`): a store knows its own change coming back by the id and that actor. With another name none of its changes is ever confirmed; they are let go of after 1,000 (`PENDING_LIMIT`), so the store does not part from its peers for ever, but until then its own stale changes are laid over later ones. An agent that should be signed as itself has a connection of its own: an agent's change sent over a person's connection is that person's to every peer.
    3. **One connection's envelopes stay in the order they were sent.** A store lets go of an unconfirmed change of its own as soon as a later one of its own is confirmed.
    4. **An envelope is ordered once.** The same id from the same actor, sent again after a reconnect, is not counted twice (a reconnect sends every unconfirmed change again).
    5. **The stamp's shape.** `{ kind: 'person' | 'agent', id }`, the id 1 to 128 characters. A delivery whose stamp is anything else (a `system` actor, a long subject) is counted and skipped by every peer, like an envelope that does not pass the decoder: it changes nothing and stalls nobody, and the change it carried is lost.
  - **A repeat is told by the count, not by remembering ids.** A store knows the count it has reached (`syncedTo`) and ignores anything at or below it, so a backend may deliver again from any point, however far back.
  - **Out of order, lost, reconnected.** A delivery ahead of the count is held (up to `SYNC_HOLD_LIMIT`, the nearest kept) and applied when what is missing arrives. Meanwhile the connection is `stalled`, `SyncPort.resend(after)` is called once per hole if the port has it, and the host hears `onGap`, then `onCaughtUp`, so it can say the board is not live. Deliveries let go of because there was no room are remembered by their highest count: when everything held has been applied the connection stays stalled and asks again from the count it has reached, and it is not called caught up until that count is in. `SyncGap.asked` is false when the port cannot be asked: then nothing brings the board back by itself. `connectSync` returns `{ stalled, stop }`. After `stop()` the store keeps the agreed document, the count and its unconfirmed changes (`unconfirmed`); `connectSync` on the same store resumes after the count and sends those again. `store.endSync()` leaves sync for good. A new store for a loaded document connects with `{ at, stream }`; a count above 0 with no stream is refused (`connectSync` throws, and the type says so), because it could not tell a backend that started again from old repeats.
  - **Who sent it, and who added it, are the backend's word.** The actor inside a peer's envelope is never read. A store takes an envelope for one of its own only when the backend says it is from the same actor, so a peer cannot confirm away someone's unsent change by reusing its id. On an object a peer adds, `by` is the stamped actor whatever the object says; the one exception is an object the store has seen removed, which keeps the name it had when it is put back, so an undo of a delete restores the author and nobody can add something signed as someone else. No `object-set` can set or remove `by`: the wire drops the field (and keeps the rest of the change), `setEvent` never names it, and the reducer skips it. `CanvasStore` keeps only `kind` and `id` of the actor it is given, and the planner stores only those.
- **Comments** (not built) will anchor with `CanvasAnchor`.

**Untrusted ids and references.** Every `objects` and `snapshots` map has no prototype (`idMap`, `model/document.ts`; made by `createDocument`, the reducer, the codec and `CanvasStore`'s constructor), so `doc.objects[id]` is the stored value or undefined even for `constructor`. An arrow's end sticks to a placed object or to a group the arrow is not inside (`bindingFault`); a group is never inside itself (`groupCycle`). The planner and `parseDocument` refuse anything else, the reducer drops a peer's event that would break it, and `resolveArrow` measures a group by its placed members only, so it cannot recurse whatever a document holds. `hostile.test.ts` covers each door.

Add a new object type in `model/types.ts`, `checkObject`, `PATCH_FIELDS` (`events/plan.ts`), `ObjectView` and `snapshot/picture.ts`; the compiler's exhaustive switches name the rest. Add a field to a type in `model/types.ts`, the list of field names in `model/codec.ts` (`FIELD_NAMES`, which is `OBJECT_FIELDS`: a change carries only names listed there, and a field of the types that is missing from it does not compile), `checkObject` and `PATCH_FIELDS`: no event changes. `events/store.test.ts` edits every `PATCH_FIELDS` entry of every type through a peer and an undo.

### The look ("Default")

The owner picked one look (the designer's "Default"): typed shapes and right-angled connectors for the diagram, paper and depth for what people add, and a sketch style on single objects that means "proposed, not decided". The values are closed lists, checked in `checkObject`; an agent never has to set any of them to get a good board.

| Field | Values | Notes |
|---|---|---|
| `shape` (box) | `process` (absent), `decision`, `database`, `document`, `queue`, `actor`, `cloud`, `pill`, `container` | `lanes: string[]` on a container |
| `routing` (arrow) | `elbow` (absent), `straight`, `curve` | `curve`: one arc, see Connectors |
| `size` (text) | `small`, `medium` (absent), `large`, `title`, `display` | 12.5, 15, 22, 40 and 84 units (`TEXT_SIZE_PX`) |
| `face` (text) | `sans` (absent, never stored), `serif`, `mono`, `hand` | no font is bundled |
| `pen` (ink) | `fine`, `marker` (absent, never stored), `highlighter` | 2, 4.5 and 18 units wide (`PEN_WIDTH`) |
| `style.look` | `sketch` | boxes and arrows |
| `style.fill` | `tint`, `solid`, `hachure`, `cross`, `none` | hachure and cross draw in sketch only |
| `style.rough`, `style.seed` | 0, 1, 2; an integer | sketch only; the seed defaults to a hash of the id |
| `style.dash` | `true` | arrows and shape outlines |
| `style.fromSide`, `style.toSide` | `n`, `e`, `s`, `w` | arrows; absent: the sides that face each other |
| `style.labelAt` | 0 to 1 | arrows |
| `style.ends` | `arrow` (absent), `none`, `dot`, `bar`, `bar-arrow` | arrows |
| `stamp` (type) | `kind`: `check`, `thumb`, `ask`; `count` | |
| `by` | `{ kind, id }` | set by the planner from the actor; a host maps it to a face with `PeopleProvider` |

Sizes have defaults per type and shape (`DEFAULT_SIZES`), so `add` may leave `w` and `h` out. A heading (text in the `title` or `display` size) with no size gets a box worked out from its words (`headingSize`, `events/plan.ts`), so `{ type: 'text', text, size: 'display' }` arrives on one line. The width is a count per kind of letter that errs wide (checked against the browser's own measure for 112 headings in the four faces on macOS: the widest filled 93% of its box). It is an estimate: no font can be measured in the model, and text an agent adds does not grow to fit afterwards as typed text does, because a box that followed one device's fonts would be written to the document for everyone. No migration entry was written for any of this: no saved document exists yet (`MIGRATIONS` is ready for the first).

- **Shapes** (`view/shape-outline.ts`): one function gives each shape's outline as segments. The board draws it as a small inline SVG under the box's own HTML words; the sketch renderer feeds the same segments to the rough generator; the still picture of a snapshot draws them too. A plain `process` box stays a CSS box.
- **Connectors** (`view/route.ts`, `view/routes.ts`): an `elbow` connector is routed at right angles round what is in the way by A* over a sparse grid (a line at each side of every nearby obstacle, grown by a clearance, and at each end's stub), with a cost per bend; the same input gives the same route. Frames and containers hold things and are not obstacles; a boxed-in end still gets the plain line. Each end leaves by the side facing the other (kept across small moves), and connectors sharing a side are spread along it in the order their lines go. `Router` (one per store, `routesFor`) keeps every route and, on a commit, marks stale only the connectors stuck to what changed, those sharing a side with them, and those whose line passes where the object was or is. Stale routes are worked out as they are drawn within `ROUTE_BUDGET_MS` a frame; the rest wait a frame with their last shape. Drawn (`view/route-path.ts`) with rounded elbows, an arc where a later line hops over an earlier one (found among the lines on screen), the label on the line, and typed ends. Far out, connectors are straight lines. The still picture of a snapshot draws connectors straight.
- **Curved connectors** (`curveControl` in `model/document.ts`, `curveRoute` in `view/route-path.ts`): `routing: 'curve'` is one quadratic arc between the two ends, bowing to the left of the way it runs by 16% of its length (90 units at most). The same every time; two connectors between one pair, one each way, part. The label, the ends' angles, the pointer, the arrow's bounds (so culling and captures) and the still picture all use that curve. It is not routed: it goes through whatever lies between, and `fromSide` / `toSide` are ignored. A loop back to the same object keeps the loop's shape. The style popover does not offer it yet (new editor UI): an agent sets it.
- **Sketch** (`view/rough.ts`): strokes and hatching are generated from a seed as path strings and kept by what they were made from (seed, shape, size, fill, roughness), so a move reuses them and a pan or zoom costs nothing. Never an SVG filter. Words in a sketched shape use `--pcv-hand`, the device's own handwriting face: no font is bundled.
- **Surfaces**: notes are paper with a tilt worked out from the note's id and place (not stored) and lift while carried; frames are soft panels with the title on a chip that grows as the board shrinks (a rule in the view's own small stylesheet, rewritten when its step changes; not an inherited custom property, which restyled every object); pictures have captions; faces show who added something.
- **Depth costs frames**, so shadows are drawn only at full detail on a board that is not crowded (`data-crowded`: over 500 mounted objects). Far out with more than 4,000 objects mounted each object is one flat element (`FlatView`) and bare text is not drawn; not below that, because swapping markup as the zoom crosses a detail level costs a long frame. Hatching is dropped a level earlier than text.
- **Words** (`TextObject`): five sizes and four faces, closed lists. `title` and `display` are the words a board is read by from far off: at the lowest detail (`data-lod='far'`), where every other word is hidden, they and frame titles stay drawn. On a board so crowded that objects are flat patches (over 4,000 mounted, far out), headings and frames are still drawn as themselves, frames with their titles; everything else is a patch. Faces are lists of fonts a device is likely to have (`--pcv-serif`, `--pcv-mono`, `--pcv-hand`), so they differ between devices.
- **Lines drawn by hand** (`InkObject`, `model/ink.ts`): `{ type: 'ink', x, y, w, h, points, pen?, color? }`. `points` is x then y for each point, each from 0 to 1 across the object's own box, 2 to 1,000 points (`LIMITS.inkPoints`). So `move` changes `x` and `y`, `resize` changes `w` and `h`, and the points are never rewritten or copied: no new command or event. `strokeFromPoints(points)` makes the stored form from points in board coordinates (it simplifies, bounds its own work and drops what is not a number): it is what a pen tool will call, and what an agent with a line in board coordinates calls. Drawn as one SVG path with smooth joins, cached by the points list (`view/ink-path.ts`). Grabbed along the line, as wide as its pen, so a ring does not take clicks from what it circles; a marquee takes it by its box. Its stroke runs half a pen's width past its box, so what it covers (`inkBounds`: the index, culling, captures, `objectBounds`) is the box grown by that much, and the half of a line that lies outside its box is found by the pointer. Not an obstacle for connectors, no ports, a line (not a patch) on the map. **There is no pen tool yet**: a person can move, resize, recolour and delete a line but cannot draw one.
- **Editor**: alignment guides with the distance between the two things and a soft snap while dragging (`view/guides.ts`); a port at the middle of each side of the selected shape, from which a connector is drawn; the selection's bar (colour, style, group, open, delete, Add to plan) with a colour popover (six named, six more, any colour typed or picked) and a style popover; the map (`Minimap`, its own small canvas, never a layer over the board).

### Renderer

DOM, with one SVG layer for arrows. Reasons are in the header of `react/CanvasView.tsx`: text is the content (the browser shapes, wraps and exposes it), pictures and sandboxed iframes are elements already, and theming is CSS variables. What keeps it fast: the camera is one CSS transform written outside React; only objects in the render window are mounted (`view/cull.ts`); objects are placed with `transform`; zoomed out, CSS draws less (`data-lod`).

Do **not** put `will-change: transform` on `.pcv-world`: measured, a promoted layer is rastered at full scale and 2,000 objects at 12% zoom pan at 10 fps instead of the display rate. Do not set a CSS variable on the root per frame either (every object inherits it and restyles): the zoom goes to `.pcv-overlay` only.

Styles are plain CSS in `canvas.css` under the `pcv-` prefix, so a host needs no Tailwind `@source` for this package. Colours fall back from the host theme's variables.

### Snapshots

A snapshot is a **materialized view**: a capture of part of the canvas taken at one moment (the owner's direction: "like a materialized view … this one time snapshot … somebody should be able to update the materialization"). Editing the canvas afterwards does not change it.

- **What is stored.** `Snapshot` (`model/types.ts`) is `id`, `title`, `source` (a frame by id, a set of objects, or a rectangle) and `capture`: the rectangle and a frozen copy of the objects it showed, back to front. It lives in the canvas document, so a plan's block stays two ids and one snapshot can appear any number of times.
- **Who takes it.** Only the planner, with `captureOf` (`model/capture.ts`): on `add-snapshot`, on `edit-snapshot` with a new source, and on `update-snapshot`. A capture sent with a command is ignored, so a person and an agent make and update snapshots the same way and neither can forge one. The new capture travels in the `snapshot-put` event, so undo, redo and a peer all get it.
- **What it costs.** The document never mutates an object, so a capture holds the canvas's own objects, not copies, until one of them is edited. Fifty snapshots of an unchanged canvas are fifty small arrays. An arrow with an end stuck to something outside the capture gets that end fixed in place (one small copy), and group membership is dropped, so a capture draws by itself. Not done: a shared table for large `data:` pictures, which are written once per capture when the document is saved.
- **Behind.** `snapshotStanding` (`snapshot/resolve.ts`) captures the source again and compares (`capturesEqual`, by reference first). No clock or counter is kept, so it is right across peers and after an undo, and it means exactly "taking it again would look different": for a set of objects, one of them changed or was deleted; for a frame, the frame or anything wholly inside it changed, arrived or left; for a region, anything in the rectangle did. A frame's capture is the frame and what is wholly inside it (a neighbour that overlaps the edge is not drawn in slices), and its rectangle leaves the title strip out, because the caption says the name. Changing something back makes it `current` again. When the source is gone (the frame, or every chosen object) it is `detached`: the capture is all that is left, it stays, and `update-snapshot` is refused. Only a figure that is drawing asks; `behindSnapshots` answers for a whole plan ("update all": dispatch the updates with one `gesture` id for one undo step).

In a plan it is a directive block, which the existing parser already makes one block (name approved by the owner):

```
:::canvas-snapshot
canvas: parcel-alerts
snapshot: architecture
title: Architecture
![Orders API feeds two queues](architecture.svg)
:::
```

`canvas` and `snapshot` are ids; `title` and the image line are optional. A `title` here is the plan's own caption and wins over the snapshot's name. The image is the fallback: another Markdown viewer shows it, and `SnapshotFigure` shows it when the canvas is not in the `CanvasRegistry`. `snapshotToSvg` makes one from the capture (self-contained, no script, no outside address).

The plan renderer draws the block through the `directiveRenderer` seam of `@plannotator/ui` (`components/blocks/directiveRenderer.ts`; see `packages/ui/README.md`): `createSnapshotDirectiveRenderer` returns the function a host passes to `configurePlannotatorUI`. Neither package imports the other. No product host passes it yet.

**The figure** (`SnapshotFigure`) is `CanvasView` over a small frozen store (`snapshot/frozen.ts`, the twelve most recent kept), so it is text and vector shapes, sharp at any zoom. It has no box of its own and sits on the page's ground, exactly the shape of what it shows and never larger than life. It draws only within 1,400 px of the screen, measured against the pane the plan scrolls in (`scrollRootOf`), not the window. It always draws in full detail: detail is reduced only for a view holding more than 150 objects (`lodFor`, `view/cull.ts`), never because a view is small. Its caption is the snapshot's name, typed in place (`edit-snapshot`); with no name it shows the item count. Behind, the caption adds "Changed on the canvas" and one action, "Update". The open button carries a spoken description made from the capture's words (`describeCapture`). Naming rule: `defaultSnapshotTitle` in `view/snapshot-source.ts`.

**The portal** (`CanvasStage`, `transition.ts`). Clicking a figure mounts the stage, which draws the live canvas clipped to the figure's box with the camera placed so the snapshot's rectangle does not move, then one critically damped spring (about 0.4 s to nine-tenths) grows the opening and carries the camera.

- The plan is never unmounted or scrolled. It stands back with depth: smaller, softer and dimmer, eased early (`recede`, a host element; `recedeAt`), and is exactly where it was on return.
- The opening keeps the figure's corner radius, easing to square as it reaches the window, with a fine line and a soft shadow that fade as it lands (`rimOpacity`).
- The snapshot's capture is always drawn over the live canvas on the same camera and dissolves between 10% and 62% of the way (`ghostOpacity`). It holds only what the figure shows, so the rest of the board arrives around the picture instead of being cut by the opening's edge, and a capture the canvas has moved on from becomes the canvas as it is now with no swap. Going back it forms again, so the opening closes onto what the figure shows.
- While behind, the open canvas offers "Update snapshot" beside "Back to plan".
- It is a dialog: everything else in the body is `inert` while it is open (which is also the focus trap), focus goes to "Back to plan" (first in the Tab order) and returns to the figure, and Escape leaves (first the words being typed, then the canvas).
- The spring keeps its velocity when turned round, so closing mid-open is continuous; a person who grabs the board takes the camera at once (a wheel still spinning from before the click does not count for 150 ms). Reduced motion: a 140 ms fade, nothing travels.

A host should open from a plan that fills its pane. The demo's "Side by side" view exists for dragging a snapshot into the plan; while the stage is open its side pane stands down so one canvas is on screen.

**Keyboard reach, not shortcuts** (the owner's ruling: these are accessibility basics). In an editor, Tab lands on one object, then walks objects in reading order (`view/reading-order.ts`): from an object to its selection bar, from the bar's last control to the next object. Enter on an object starts typing in it, or opens a card; Escape ends typing. No other keys do anything.

### Reference cards and link previews

`ReferenceObject` is a card for a web page, one of the person's artifacts, or a place in a plan. What it shows is stored on the object as text and picture addresses. Paste is the way in (`CanvasEditor`: a bare address becomes a web card; `resolvePaste` lets a host claim its own artifact and plan references); an agent adds the same object with `add`.

A web card appears at once with its address and fills in from `linkPreview` (a `LinkPreviewPort`, `model/reference.ts`; the browser side is `routeLinkPreview` in `react/link-preview.ts`). The port is called only for an address a person pasted (`addReference` from the paste handler); an agent's `add` of a web card never causes a fetch, which is how the two are told apart.

`unfurl/fetch.ts` is the real fetcher: Open Graph, Twitter card, title, description, icon; http and https only, five redirects, 6 s, the first 512 KB, a small cache (a failure is not cached), and the bare link whenever a site gives nothing. None of that is shown to the person. Addresses:

- Every host name is resolved (the system resolver by default), judged on the address's bytes (`unfurl/address.ts`: IPv4 and IPv6, mapped, NAT64 and its local-use prefix, IPv4-translated, 6to4 and its old relay range, discard-only, benchmarking, loopback, private, link-local, unique-local, carrier NAT, multicast), and then connected to at the address that was checked (`pin`), on every redirect hop. Under Bun the pin is built in (connect by address, `Host` and TLS server name set); under Node (the Pi server) the host must pass a `pin`, for example an undici agent with `connect.lookup`. Not exercised here: the built-in Bun pin against a real TLS site.
- **A preview's picture and icon are checked by name only, and it is the viewer's browser that fetches them.** The server resolves the name once and drops a picture whose name answers with a private address; it cannot pin what a browser later connects to. A name that answers differently for the browser can still make that browser send one blind GET to an address on the viewer's network. A product host that needs that closed serves preview pictures through its own asset route.
- **A fetcher that could not keep to that is refused when it is made** (`unfurlFault`; `createUnfurler`, `createUnfurlHandler` and `unfurlUrl` all throw): with `allowPrivate` false there must be a pin (so not Node without one, and not a custom `fetch` without one) and the lookup must be on (`lookup: false` leaves a name unchecked, and is allowed only with `allowPrivate`).
- The wait for a name to resolve ends with the preview's time limit and with the caller's `signal` (the system resolver cannot be stopped, so the wait is what ends; a `HostLookup` of the host's own is handed the signal). A name that did not answer in time is a failure, not "private", and is asked again next time.
- `allowPrivate` is the host's policy, default false. A local server that one person runs for themselves sets it true, so their own `http://localhost:3000` gets a card; a hosted server leaves it false. With it false, a preview picture or icon that points at a private address is dropped before it reaches a viewer's browser.

`createUnfurlHandler` is a `(Request) => Response`; **only the demo's dev server mounts it** (`demo/vite.config.ts`, with `allowPrivate: true`). The demo's middleware runs before Vite's own check of the `Host` header (tried: a request naming another host got the preview), so it checks it itself (`isLoopbackHost`, `unfurl/route.ts`) and refuses a request that does not name this machine: a page that pointed its own name at 127.0.0.1 cannot read a preview of something on loopback. What is left while the demo runs: any page in the developer's browser can make the browser send a request there, which makes the demo GET a loopback address; it cannot read the answer. Making it a product endpoint means mounting it in both the Bun and the Pi server behind the usual guards (the same `Host` check among them), a concurrency cap, and a line in the API tables.

### Pictures and the asset port

A document, an event and a plan's text never hold a picture's bytes: no `data:` URL, no `blob:` URL (`isPictureRef`, `model/assets.ts`; `checkObject` refuses them). An image, a sprite, a card's picture and icon hold a reference: `asset:<name>`, an http(s) address, or a relative path. The host keeps the bytes behind an `AssetPort` (`put(file) → { ref } | { refused }`, `url(ref)`); the name is best a content hash (`asset:sha256-…`), which is how the Inbox already stores attachments. `pictureResolver(assets, other)` is the one function a view needs (`resolveImageSrc`). `createMemoryAssets` (`react/memory-assets.ts`) is the demo's and the tests' port; nothing in the product implements one yet.

Pasting or picking a picture (`react/pictures.ts`): the file is decoded (anything the browser can decode; a kind it cannot show from a file, such as bmp, is redrawn as PNG), handed to the port, and an image object with the reference is added. Each way that can fail shows a line in the editor (`CANVAS_STRINGS.pictureProblems`): no port, over 25 MB, unreadable (tiff and heic where the system cannot decode them), or the host could not save it. Never silently.

The still fallback of a snapshot (`snapshotToSvg`) is stored by the host as a file or an asset and the plan block names that address. Never write the SVG, or a `data:` URL of it, into the plan: a plan is agent context.

Every `<img>` the package draws has `referrerPolicy="no-referrer"`. A relative `src` is a same-origin request chosen by whoever wrote the object, so a product host passes a resolver that confines it to its artifact route.

### Colour

Any object takes a named colour (the canvas's six, which follow the theme) or any CSS colour: hex, a CSS colour name, `rgb()`, `hsl()`, `hwb()`, `lab()`, `lch()`, `oklab()`, `oklch()`, `color()`. `isCustomColor` (`model/color.ts`) is a closed grammar: nothing that can load, run or end a declaration passes. Any colour stays readable without limiting the choice: `canvas.css` ("Colours") takes the ink for a solid custom fill, and the shade a custom line or text is drawn in on the board, from the colour's own lightness with CSS relative colour syntax (a browser without it draws the colour as chosen).

**A drawn line follows the same rule** (decided when ink was added; the exploration drew a custom ink colour exactly as chosen). On the board, a custom ink colour is the line colour every other custom line gets: kept dark enough on a light board and light enough on a dark one. The reason: the board under a line differs between the two themes, and a black ring must not vanish for the person on the dark theme. The exception is the next paragraph, which is where "exactly as chosen" is right.

**Over a picture** (`react/picture-look.ts`, `data-ground`). Bare text or a drawn line with half or more of its box on a picture, and a connector with both ends on one picture, is read against the picture, which is the same in both themes, not against the board. A custom colour is then drawn exactly as chosen (a yellow highlighter over a screenshot stays yellow), but only once the picture has been looked at: while it is loading, when it failed, or when it cannot be read, the board's own rule holds, so the mark is seen whatever is there. With no colour or a named one, ink and line colours are the light-ground or the dark-ground set (`--pcv-*-l`, `--pcv-*-d`), chosen by how light the picture is under the mark: a 24 by 24 copy of each loaded picture is looked at once (the 2,000 looked at most recently are remembered), and light means a relative luminance above 0.18, the same line as ink on a solid fill. A connector's label gets a halo to match. A picture from another site that cannot be read back gives no answer: there, every mark follows the board's theme as before. Only the marks lying over a picture hear that it has been looked at (`useGround`), gathered once a frame: a board of pictures loading draws nothing else again. Notes, boxes and stamps carry their own ground and do not change.

**Who added it** (`PersonLabel.color`, `react/people.tsx`). A person's mark is a quiet neutral that follows the theme (its initial is read at 4.5 to 1 or better in both) unless the host's `PeopleProvider` gives that person a colour: any colour `isCustomColor` takes, anything else ignored, drawn exactly with white or black ink by its lightness. No fixed hue is in the stylesheet.

### Custom HTML items

`model/html-item.ts` is the contract and the only way `HtmlObject.html` is drawn (`alt` on the object is its text alternative, since the frame is inert): an iframe with an empty `sandbox`, a CSP of `default-src 'none'` with inline styles and `data:` pictures, `inert`. No script, no network, no navigation, no access to the page. `react/HtmlItem.dom.test.tsx` holds the element that is really mounted to it: the attributes on the frame, the policy ahead of the item's first byte, and none of the item in the page itself. Do not add a sandbox token or loosen the policy for convenience; a scripted item is an owner decision with its own review.

- **Zoom.** The frame is laid out at the object's own size in board units and lives inside the board's one transform, so an item scales with the board like every other object (measured: a 344-unit item is 310 px wide at 90%, 190 px at 55%, 37 px at 11%). What does not scale is the item's content when the object is **resized**: the frame is a viewport, so a larger box shows more room, not larger type. An item is written for the size it is given.
- **Low detail.** An item runs no script, so its frame is already a still picture of itself; it stays drawn below full detail (`htmlFramesNext`, `react/CanvasView.tsx`). Until this change every item became an empty dashed box as soon as a view held more than 150 objects and was zoomed under 45%. Frames are kept while few items are **on screen** (not merely mounted round it): dropped when more than 10 are, back when 8 or fewer are, so one item at the edge of the screen does not turn them all over and back. Past that each item shows its `alt` words in a quiet box (with no `alt`: "Embedded content" and its size), all or none so a board never shows a mix. A frame that has been drawn stays mounted, hidden, so going back and forth never loads an item again. Why a cap at all, measured headed while panning 2,000 objects at 12% with moving items on screen: none 119 fps; 6 items 84 fps, 0 of 336 frames slow; 8: 82 fps, 3 of 330; 10: 81 fps, 1 of 324; 12: 83 fps, 2 of 334; 16: 80 fps, 5 of 321 (outside the budget of 1%); 42: 71 fps, 45 of 286. A layer per frame was worse (61 fps). With the board at rest the items cost nothing at any of these counts (120 fps while they animate): the cost is in moving the whole board under them. The count is taken when the view is drawn again (a change, or the view leaving its window), not on every frame of a pan.
- **The host's type** (`HtmlItemFace`, `checkHtmlItemFaces`, `htmlItemFaceCss` in `model/html-item.ts`; `HtmlItemFacesProvider` in `react/objects.tsx`). The policy loads fonts from `data:` only and an item holds 64,000 characters, so an item could not be set in the product's faces. A host lends up to 6 faces, each `{ family, src, weight?, style? }` with `src` a `data:font/woff2;base64,…` URL (woff, ttf and otf too), at most 256,000 characters each and 512,000 together. The package writes the `@font-face` rules into the head of the item's document, in a style block closed before the item's markup begins, and only for families the item's markup names. A family is letters, digits, spaces, `-` and `_`; an address must be one of the font types and pure base64; anything else is left out. Nothing is fetched, the sandbox and the policy are unchanged, and an item cannot add to or change the lent rules. (An item could always write its own `@font-face` with a `data:` font inside its 64,000 characters; that is unchanged.) Each item's document carries the faces it names, so thirty items naming a 70 KB face hold thirty copies: lend small or subset files. The demo lends the repository's Geist and Paper Mono (both SIL OFL 1.1), read from `apps/marketing/public/fonts` by `demo/vite.config.ts`.

### Charts

A chart is an object like any other (`ChartObject`, `model/types.ts`): **a small table and which field goes where**, never a picture and never markup. Whoever adds it sends numbers; the canvas draws them. `?board=charts` in the demo is twelve of them.

```
{ type: 'chart', x, y, w, h,
  mark: 'bar' | 'line' | 'area' | 'dot' | 'cell' | 'span',
  fields: ['week', 'minutes'],              // the table's column names
  rows: [['W31', 11.2], ['W32', 10.8]],     // each row as long as fields
  encode: { x: 'week', y: 'minutes' },      // every value is one of the fields
  stack?, flip?, dash?, rules?, title?, unit? }
```

| Word | What it does | Drawn for |
|---|---|---|
| `encode.x`, `encode.y` | Along the bottom and up the side. `y` may be up to four fields, each a series. | every mark |
| `encode.series` | Rows with the same value are one series. Not together with several `y` fields. | every mark |
| `encode.x2` | Where a span ends. | `span` (needed) |
| `encode.value` | How strong a cell is, in five steps. | `cell` (it or `series` is needed) |
| `encode.size` | How large a dot is. | `dot` |
| `encode.facet` | One small chart for each value, on shared scales. | `bar`, `line`, `area`, `dot` |
| `stack` | Series on top of each other. | `bar`, `area` |
| `flip` | Bars sideways, names down the left. | `bar` (not with `facet`) |
| `dash` | Series drawn dashed, by name. | `line`, and the outline of an `area` that is not stacked |
| `rules` | `{ at, label?, on?: 'x' }`: a dashed line at a value with a word. Across, `at` is a number; upright it may be a name on the x axis. The scale grows to hold it. | every mark but `cell`; `span` draws upright ones only |

- **The codec is the whole defence** (`checkChart`, `model/chart.ts`; limits in `CHART_LIMITS`): 500 rows, 12 fields, 80 characters a cell, numbers finite and at most 1e12 either way, 4 `y` fields, 8 series, 12 facets, 8 rules, 200 names on an axis that gives each one room. A field's name is letters, digits, spaces and `_ - . % /`, at most 32, and never a name every object has (`constructor`, `toString`). What a mark measures must be all numbers: there is **no empty cell**. Everything else is refused with a reason. An option that means nothing for the mark (`stack` on a line) is kept and not drawn, so the mark can be changed without first undoing options.
- **One drawing** (`chartShapes`, `view/chart.ts`): a list of two kinds of shape, paths and words, each naming a ROLE for its paint (`ink`, `muted`, `rule`, `accent`), never a colour. The board turns them into SVG elements (`react/ChartView.tsx`; words are React text, never markup, and `.pcv-ch-*` in `canvas.css` are the roles), the still picture turns the same shapes into SVG text with every word escaped (`chartToSvg`, used by `snapshotToSvg`). So a chart is the same on the board, in a figure and in a file. No library and no dependency.
- **The look is fixed**, so nobody styles a chart to get a good one: a small caps title, the latest value of the first series large on a line or an area, hairline rules with their values in a margin of their own, flat marks. The object's `color` is the accent and marks the first series (`--pcv-chart-accent`: the theme's accent when the chart has no colour; a custom colour is the readable shade the package already works out, `--pcv-stroke`). The other series are quieter steps of ink and of the accent (`SERIES`). A person changes the mark, the colour and the fields. Nothing in a chart moves: no transition, no animation.
- **Cost.** All the marks of one series are one path, however many rows (500 stacked bars of four series are four paths), and a cell chart is at most five. `ChartView` works the shapes out again only when the table, the encoding or the size changed, not on a move. Too small on screen to read (`rich` false: a view of more than 150 objects, below 45%), a chart draws its marks and none of its words; with more than 4,000 mounted it is a flat patch like everything else. The map draws it as a patch.
- **Events.** A chart's fields travel in `object-set` like any others. `fields`, `rows` and `encode` must agree, so an edit sends together what changes together. **A change to one cell sends the whole `rows`** (a few kilobytes for 500 rows of four numbers; about half a megabyte for a table at every limit at once), and two people editing different cells at once end on one of the two tables. That is accepted for a chart that carries its own rows; cell-level changes belong to shared data sets, which are not built.
- **In words** (`describeChart`): what a screen reader is told for a chart, what a snapshot's description holds, and what an agent should read back in place of the rows: `Scan to alert. Line chart of minutes from 11.2 to 1.3 min by week: 3 rows, W1 to W3.`

### Worst-case data

`demo/worst.ts` is the regression fixture for input at its limits: the longest words, every script, colours with no contrast or no opacity, pictures that fail, shapes at their smallest and largest. `demo/marks.ts` (`?data=marks`) is the same for words, drawn lines, curves and colour: every size and face, ink on the board and over a pale and a dark picture, custom-colour notes, solid plain boxes, and a crowd of more than 150 objects. Open the demo with `?data=worst` (also `marks`, `empty`, `one`, `huge`, `max`, `stacked`, `far`; add `&view=canvas` or `&view=split`, `&theme=dark`). In `bun run demo` a switch at the bottom of the page changes the set. When a rule below changes, look at this board in both themes before and after.

What holds, and where:

- **What saves, loads.** Removing a group lets go of whatever is still in it (the reducer, so it holds for a peer's change and for an undo). A change names only fields an object can have (`OBJECT_FIELDS`): `__proto__` and the like are dropped at the wire and never assigned. A snapshot's rectangle, asked for or captured, has one bound (`readArea` in `model/codec.ts`, `LIMITS.area`): anywhere objects can be, as large as all of them. `hostile.test.ts` saves and loads a board at its limits.
- **Words that do not fit are cut at the end, with an ellipsis.** A box's title wraps to the lines its box has room for, three at most (`titleLines` sets `--pcv-lines`); its detail is one line; a lane's name is as long as its lane is tall; a frame's title is one line. A box title, a frame title and an arrow label that were cut show all of themselves on hover (`title`), and are whole in the object's accessible name. An arrow label is 40 characters at most and fewer on a short line (`shortLabel`). A card's file name is cut in the middle (`shortName`). Text objects grow to fit when typing ends.
- **Any colour, always readable.** Ink on a solid fill is white or black by the fill's relative luminance against 0.18, where both pass 4.5 to 1 (`--pcv-on-solid` in `canvas.css`); a see-through colour is weighed with the board behind it (`--pcv-ground-y`). Lines and ink are always opaque. A note in a custom colour is that colour exactly; a plain box takes `style.fill` (`solid`, `none`) and `style.dash` like any shape.
- **An arrow from an object to itself is a loop** (`selfLoop` in `model/document.ts`), for the board, the still picture and hit-testing.
- **A figure can always be seen and pressed**: never smaller than `FIGURE_MIN` (`figureBox`), and never at the wordless lowest detail (`wordsAlways` on `CanvasView`), except that a view of more than 4,000 objects is flat patches.
- **A drop never leaves the page.** The editor takes every drop: a picture is added through the asset port, a link becomes a card, anything else gets a line.
- **Pictures.** One with see-through parts gets a light ground on a dark board (looked at once per address; a picture from another site cannot be looked at and is left alone). With reduced motion every picture that could be animated is its first frame, drawn into a canvas. A sprite whose sheet does not load shows its words.
- **An HTML item with more than its box shows** fades out at its foot. The item runs no script, so the fade is CSS tied to a scroll timeline: browsers without `animation-timeline` show no fade.
- **A link being looked up** dims its title until the answer or the timeout (`previewsPending`, not part of the document).
- **"Fit" uses the room a view has** (`fitPadding`, `view/camera.ts`): 72 px above and below, which clears the editor's bars (less only in a view under 216 px tall); at the sides a twentieth of the width, 72 px at most and 12 at least. A view 1440 px wide or more is as it was; a narrower one gives the board more of its width (36 px a side at 720, 20 px at 390 where it was 72), so on a phone a wide board is drawn about 1.4 times as large. A board much wider than a phone is still small when all of it is in view.
- **An empty board** shows one line; **a board wider than the furthest zoom** (5%) shows a mark on each edge with more beyond it, which goes to the nearest thing that way (`EdgeMarkers`).
- **Opening a snapshot of more than 1,500 objects** does not draw the capture a second time over the canvas (`GHOST_MAX_OBJECTS`).

### Known limits

What is known not to hold yet. Read this before putting the canvas in front of anyone.

Measured (headed benchmark, `bun run --cwd packages/canvas bench --headed`):

- Three rows are not met. A figure on screen with nothing drawn yet while scrolling at 12,000 px/s: 1 of 480 frames. Zooming through every level of detail with a third of the shapes sketched: worst frame 58 ms. Panning 10,000 objects with all of them mounted: worst frame 158 ms.
- Opening a snapshot of a 10,000-object board has a 248 ms worst frame.
- A figure of more than 4,000 objects draws flat patches with no words (the one exception to "a figure always has its words").

Charts:

- No empty cells, no time scale (a date is a name or a number), no log scale, and a `span` runs between numbers only. `facet` charts share one scale; there is none of their own each.
- Words are fitted by counting characters, not by measuring them, so a wide script may be cut later than it should.
- Eight series is the most that can be told apart, and past four they are hard to: the steps are of two colours only.
- A person has no way yet to change a chart's mark or fields by hand (no editor UI); they can move, resize, recolour and delete one. An agent or a host edits the rest.
- No flow chart. Boxes and connectors draw one.
- Looked at in Chromium on a desktop only, like the rest.

Not drawn:

- The still picture of a snapshot (`snapshotToSvg`) draws elbow connectors straight (a curve is drawn as its curve), sketched shapes clean, a plain box's solid fill as a tint, and marks over a picture in the board palette (it draws a picture as its words in a box).
- Curved connectors are not routed round anything, ignore `fromSide` and `toSide`, and two between one pair in the same direction lie on each other.
- There is no pen tool and no "curved" choice in the style popover: only an agent (or a fixture) makes a drawn line or a curved connector.
- Marks over a picture from another site that cannot be read back follow the board's theme (custom colours are still exact). A connector with only its label over a picture is not noticed.
- An HTML item's content does not scale when the object is resized (it does with zoom). More than 10 HTML items on screen in a zoomed-out view of more than 150 objects show their words, not themselves; with any on screen, panning the whole of a 2,000-object board runs near 82 fps instead of 119.
- **Version skew (open, decide before the first product use).** `CANVAS_DOCUMENT_VERSION` is still 1, and a reader from before this change refuses a whole document that holds one `ink` object, a `title` or `display` size or a `face`, with a field error, not "saved by a newer version". A peer on older code refuses an envelope that adds an ink and then drifts. That is acceptable only while no saved document and no backend exist. Before either does: bump the version when the set of objects or values grows, and have a reader say "saved by a newer version".
- On a board so crowded that objects are flat patches (over 4,000 mounted, far out), drawn lines are still drawn in full.
- The fade at the foot of an HTML item that holds more than its box shows depends on `animation-timeline`: a browser without it shows no fade.

Not checked:

- WebKit, Firefox and phones. Everything was looked at and measured in Chromium on a desktop (a 390 px wide window stands in for a phone).
- The serif, mono and handwriting faces on Windows, Android and Linux: only macOS was looked at.
- `strokeFromPoints` with a real hand on a real pointer: tested with made-up points.
- The TLS pin in `unfurl/fetch.ts` has not been tried against a real site.

For whichever product wires the canvas in:

- **SVG assets must be served sandboxed.** A pasted SVG is stored as it is. Inside `<img>` it is inert; opened by itself (open image in new tab) it would run script in the asset route's origin. The product's `AssetPort` must serve SVG with `Content-Security-Policy: sandbox` (or as an attachment, or redraw it as PNG).
- **Unfurl under Node needs a `pin`.** The built-in pin is Bun's. Under Node (the Pi server), or with a custom `fetch`, a fetcher with `allowPrivate: false` and no `pin` now refuses to be made, so the Pi server must pass one before it can mount the route.
- **Sync needs a backend that holds to five rules** (listed under Events, Sync), and none exists: nothing here has run against a real one. The seam trusts `stream`, `order` and `actor` and cannot check them.
- **Who added an object can differ between peers in one case.** A store remembers the author of the last 5,000 objects it saw removed, and only from when it joined. A peer that joined after a delete (or one where that delete has fallen out of the 5,000) signs the object, when an undo puts it back, with the name of whoever put it back; peers that saw the delete keep the original name. For example: Alice deletes Bob's note, P joins, Alice undoes; P shows the note as Alice's, everyone else as Bob's, and their saved files differ in that one field. Only `by` differs. A rule that never differs exists (always the backend's stamp), at the cost that an undone delete shows the person who restored it. Closing it needs the removed authors to travel with the document.
- **A store whose actor is not the backend's stamp is out of step until its stale changes are let go of.** Its own changes reach its peers but never come back as its own, so each is laid over later changes by others until 1,000 newer ones of its own push it out: it sees its own value for a field while everyone else sees the peer's. Nothing tells the host (the port does not say who it is); rule 2 is the only guard.
- **A stalled connection has no reload.** After `reason: 'restarted'`, or a gap the backend never fills, the host must load the canvas again and make a new store; that path is not built. Changes of the person's own that were never confirmed are lost with the old store.
- **Undo across a reconnect** is tested for one step only.

### Measuring

`bun run --cwd packages/canvas bench` builds the demo, opens it in Chromium and prints each budget with what was measured, as it goes (`--headed` for a visible window with GPU raster: use that run as the evidence; headless numbers are flattered by its software frame clock). It is not run in CI. Budgets are stated at 60 fps whatever the display. Besides frame times it measures what a frame rate cannot show: frames in which a figure is on screen with nothing drawn yet, heap and DOM nodes over scroll passes and over 50 open/close cycles, that the plan is where it was after coming back, a drag on the real pointer path at 100%, a board with pictures, HTML items, cards and long notes, the canvas being edited behind 50 figures, 10,000 objects, and the `will-change` finding above (with and without).

`LIMITS.objects` is 10,000 because that is what has been measured: at 10,000 a pan with the whole board in view still drops frames (every object is mounted at that zoom, each as one flat element), while work at 100% holds. The benchmark also has rows for 2,000 typed shapes with 1,500 routed connectors and for a board where a third of the shapes are sketched, and for a board of 200 charts (`?bench=canvas&charts=200`).

Tests are `*.test.ts` beside the code and run in the unit lanes; `hostile.test.ts` and `layers.test.ts` sit at the package root. Three are DOM tests listed in `tests/dom-test-list.txt`: `packages/ui/components/blocks/directiveRenderer.seam.test.tsx`, `packages/canvas/snapshot/CanvasStage.dom.test.tsx` (opening a figure and coming back leaves the plan where it was) and `packages/canvas/react/HtmlItem.dom.test.tsx` (the frame a custom HTML item is really drawn in).
