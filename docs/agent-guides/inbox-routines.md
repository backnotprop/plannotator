## Routines

On screen and to agents this feature is "Routines"; in code (files, types, routes, the record kind, config and wire keys) it is "scheduled".

A routine is a saved prompt with a name, a schedule, a folder, an agent and an on/off switch. Each run starts the agent the way New message does and works in one Inbox thread: every run replies there, and the person replies there to that run. Code: `packages/core/inbox-scheduled.ts` (the pure schedule rules, croner 11.0.0), `packages/server/inbox-scheduled.ts` (records, clock, runs), `inbox-scheduled-routes.ts` (the switch and the window's routes), `inbox-scheduled-login.ts` (start at login), `inbox-mcp-scheduled.ts` (the agents' tool). Types: `packages/core/inbox-scheduled-types.ts`.

A routine is managed on the computer that made it, and its runs' thread works from linked machines like any thread.

### The switch

Settings → Capabilities, config.json `inboxScheduledThreads` (`true`, else off). Not offered on Windows. Off: no timer, no run, no write, no `routine` tool in tools/list, every `/api/inbox/scheduled…` route answers `404 routines_off`, and a tool call from a session that listed it before answers `routines_off` with nothing written. Records on disk are kept. Turning it on starts every routine that is on from the next due time, with no catch-up; so does turning "Start agents" back on. "Start agents from New message" (`inboxLaunch.enabled`) must be on too: a run is a launch.

The one-time Routines intro offers the switch once, after three good days of sends, the queue's gap from any other dialog; its "Turn on" saves this switch and opens `#routines`. Who, when and the dialog: "The Routines intro" under "The schedule of one-time dialogs" in `inbox-window.md`.

On also adds a start-at-login item, removed when it goes off and by `plannotator uninstall` (the file only, on macOS; disabled, not stopped, on Linux: removing it never ends the Inbox it started): on macOS `~/Library/LaunchAgents/ai.plannotator.inbox.plist` (launchd reads it at the next login; it runs `plannotator inbox --no-open` for this data dir, no window); on Linux a systemd user unit `~/.config/systemd/user/plannotator-inbox.service`, enabled, only when `systemctl --user` answers (else none, and the switch reads `login: "unavailable"`).

### The record and the runs

Records live in `<dataDir>/inbox/scheduled.jsonl` (kind `scheduled`, one file for every project, last line per id wins, a delete is a tombstone). A run is a person-authored divider message in the thread (`scheduled_run: { scheduled_id, name, run, due_at, by, late?, missed_before?, failed? }`) whose body is the prompt (plus the late line, "This run was due Mon 9:00 AM and started Mon 11:14 AM."), carrying that run's own `launch` record and `to` its session. The first run (or skip line) starts the thread, named after the routine; later dividers take the thread over (`took_over`), so the person's plain reply goes to the newest run. A skip line is its own message, `scheduled_run` with `skipped` and no `run`: an Inbox note ("Skipped Mon 9:00 AM · this computer was asleep"). The store delivers a skip line, and a divider whose run didn't start, to no session; a divider only to its own run's session (`pendingFor`), so neither wakes or restarts an earlier run. Archiving the thread (its row, a bulk Archive, a swipe, or a Combine that took it) leaves the schedule as it is: the next run writes in the same thread, and its reply brings the thread back as any agent's reply does; a Combine's new thread gets no runs.

The folder is a project (`{ project_id }`), a folder by its real path (`{ path }`: a worktree or a subfolder runs there, not at its project's root, and home, `/`, hidden and system folders are refused as New message refuses a typed folder), or a scratch folder made at the first run.

One session per launched root is unchanged for every other thread: the store indexes each routine's newest later run beside the launched roots (`scheduledRunLaunches`; earlier runs have ended), and the launcher's thread reads (run line, row, respawn, attach) follow it. Starting a run lets go of the previous run's session when it is idle. One start at a time per routine: a second (Run now twice, or Run now as the clock fires) answers `409 routine_running`, and its number and thread are read after the launch is ready. A reply to an earlier run (its divider or its session's message) is refused, `409 routine_run_ended`: "Run 3 has ended, so your reply was not sent. Reply to the latest run (Run 4) instead."

A run that didn't start is a divider with `failed` (the launch's reason, without New message's "Nothing was sent."), shown as "The run didn't start." and the reason; a first run that fails, on the clock as on Run now, writes it in its folder's project (a folder by its path that is there), else in the project of the thread an agent made it from, else in a project for the scratch folders' own folder (as a new scratch folder, or a project that is gone, does). A folder that isn't there never becomes a project. So it always has a thread. A run's outcome is read, never stored: `didnt_start` (no launch, or `failed`), `running`, `replied` (its session wrote after the divider), `didnt_finish`.

### The clock

One check when the switch is on or the Inbox starts, then every 30 seconds. A check that finds more than 2 minutes since the last one reads as the computer having slept (`asleep`); the first check after a start reads as the Inbox not running (`not_running`). Per routine that is on, approved and has a schedule: nothing due, wait; a run still going, skip (`still_running`); due more than 2 minutes ago and the next due time under 15 minutes away, one skip line for all of them (`missed`, or the sleep or start that caused it); the same with `if_missed: "skip"` (`asleep`, `not_running`, or `late` when the Inbox was up and awake); else one run for the newest due time (`late`, `missed_before`). The newest missed time is read back from now, and the ones before it are counted up to 1,000 ("Skipped 1,000 or more times"), so a long sleep costs at most that many steps. The clock counts from the record's `handled_through` (set at turn-on and at a schedule change) or the newest due time it wrote a line for, whichever is later, so nothing is written to the record at a due time. The run key `sch:<id>:<due_at>` is the divider's idempotency key, so a restart in the middle of a check answers the same run and never starts a second. A one-time schedule is Done after its run or skip.

The only limit is the 15-minute rule: a schedule whose runs come closer than 15 minutes apart is refused (`422 schedule_too_frequent`, "Scheduled times are at least 15 minutes apart. This one runs every 5 minutes.", with `every_minutes`; a cron whose runs are not evenly spaced, `*/14`, "This one can run 4 minutes apart."). It spaces the scheduled times only: Run now is never held back by it. Also refused as `schedule_invalid`, in its own words and never the cron library's: a cron it cannot read or a zone it does not know ("That isn't a schedule Plannotator can read." and a hint), a cron that never comes round ("That schedule never runs: no day matches it."), a one-time date the calendar does not have, and a one-time time already passed when it is set ("That time has already passed."; one saved before its time keeps it). Daylight saving: a time that does not exist runs at the next one; a time that happens twice runs once.

### Agents

The `routine` tool (also `plannotator_inbox` action `routine`; the shim fills it like `card`): `op` create, list, get, update, on, off, run, delete. Paired cloud agents (the agent door) do not get it: a call through the door answers `tool_not_allowed: routine: a routine runs an agent on the person's computer, and you run elsewhere…`, true whether Routines are on or off (the person can still pick `/create-routine` in a cloud agent's thread).

| Surface | Form |
| --- | --- |
| MCP tool | `routine`, title "Make or change a routine" |
| `plannotator_inbox` action | `routine` |
| Shell | `plannotator routine <op> [options] [--session <id>]` (below), or `plannotator routine <op> '<json>'` with the tool's fields, both `plannotator inbox call routine '{"op":"<op>",…}'` underneath |
| Link | `#routine=<id>` opens that routine's editor (`&runs` on its Runs tab); `#routines` the list (`#routine=new` a new one) |

- A routine an agent creates arrives off, unless the person asked that agent for it with `/create-routine` (below). Off, the person turns it on the first time, in the Inbox (`approved_at` on the record); before that the agent's `on` and `run` answer `routine_not_approved` and change nothing. After that the agent may update, turn it on or off, run it and delete it.
- `/create-routine` grants (`inbox-routine-grants.ts`; the owner: "If I create a routine, I want it turned on"). The person's own Send of a message carrying the built-in `/create-routine` is their approval of the routine it asks for: it mints ONE grant on that thread (thread id, message id, time). The next `create` whose `thread_id` names that thread, from a session the Send went to, takes it and is made approved and on (`approved_at`, `handled_through` now, its next run computed), and its change line says "It is on, as you asked with /create-routine." Without one, a create is exactly as before.
  - Who mints: only the Send routes (a reply, New message, a new thread), only for the person's own call by the bar a permission prompt's answer has (`noteSend` in `inbox.ts`: the window's Origin, this Host and `serverSession`; a paired phone through the door; a linked machine for a press in a window there), and only when the written message is `author.kind: "person"`, is not a run's divider, and ends in the skills block naming the BUILT-IN (its list line "a Plannotator Inbox skill", instructions included). An agent's message, an agent's bare call to any Send route (no Origin, or the window's Origin without this run's `serverSession`; it writes as the person but mints nothing), a linked machine's call without the window's mark, an MCP tool and a skill of the person's own named `create-routine` never mint. A replayed Send mints nothing more. A press in machine A's window into a thread that lives on machine B is forwarded with the mark, so B mints, and B's agent's create in that thread is on, on B.
  - Who takes it: only a session the Send went to, read from the stored message when the create comes (`sendRecipients`): its owner by the store's rule (`recipientOf`: the session it is addressed to, else the agent whose message it answers), each session it tags, and a launched thread's agent once it started (`launch.session`; the Send is that thread's root, and its session is not known at the Send). Another agent session that names the thread, or a caller that names no session (a shell with no session), gets none and its create arrives off; a Send that went to no session can be taken by nobody (the stricter choice). The session is the caller's word, as everywhere in the Inbox: an Inbox tool call names it (the connection fills `agent_session`, so every agent's tool call matches), a shell call only when its shell names one (Claude Code's `PLANNOTATOR_SESSION_TAG`, Codex, Pi, T3) or it passes `--session`. That is why the skill sends the agent to its tool first.
  - Lifetime: one hour from the Send (`ROUTINE_GRANT_MS`), one routine each, kept in memory only (an Inbox that restarts forgets them, and the create then arrives off). Taken before the create is written, and given back only when the server refuses the create before anything is saved (a field `fieldsOf` refuses, such as a schedule closer than 15 minutes). Once every field passed (`create`'s `checked`), it stays used, even if a later step fails.
  - The result says which: on, `Made sch_… "Name": on, <schedule>, <agent> in <folder>, next <ISO>. It is on: the person asked for it with /create-routine in thread msg_….`; off with `thread_id` and none held there, `… No /create-routine request from the person in thread msg_… that this Inbox still holds (one lasts an hour and makes one routine, and an Inbox restart forgets it), so it is off until the person turns it on in Routines in the Inbox.`; off because the one held there went to another session and the call named a different one, `… The /create-routine request from the person in thread msg_… was for another agent session, not yours, so it is off until the person turns it on in Routines in the Inbox.`; off because the call named no session (the grant stays held for its retry), `… This call names no agent session, so it could not be matched to the person's /create-routine request in thread msg_…, and it is off until the person turns it on in Routines in the Inbox. To have it on, delete it and make it again with your Inbox tool's routine action, or from the shell with --session and your session id.`; off without `thread_id`, `… It is off until the person turns it on in Routines in the Inbox. A create starts on only with thread_id (--thread from a shell) naming the thread where the person asked for it with /create-routine.` The structured result has `asked_with_create_routine` and the row (`enabled`, `approved_at`, `next_run`).
  - Accepted: the person's own Send that ends with text an agent wrote in the exact shape of the built-in's block (pasted in, with no real block after it) would mint. It needs the person's own Send, so it is left as is.
- Each change posts one line, as the agent, in the thread the call names (`thread_id`), else in the routine's own thread, with `scheduled_change: { scheduled_id, name, op, fields?, turned_off? }` and a link `[Name](#routine=<id>)` that opens the editor. An edit says old and new: the schedule and folder in words, the prompt as a `diff` block.
- An agent's change of the folder or the agent turns it off and clears the approval; the line says so. Prompt and schedule edits apply at once.
- Runs start in the person's own permission mode, exactly as New message does.
- `update` changes only the fields passed. A schedule without `tz` takes this computer's zone. `thread_id` is only where the change lines go: runs reply in the routine's own thread, made at its first run. With no `thread_id` the line goes in the routine's own thread (made for it when the routine has none yet); there it is a note, not anyone's words: it wakes no run and takes no reply (`threadOwner`, `wordsMessage`, the run outcome), and the list row says the change (`last_change`, "Changed by Codex") while it is the thread's latest.

### From a shell: `plannotator routine`

`apps/hook/server/routine-command.ts`, for an agent the person asked to make or change one, and the Inbox's `/create-routine` skill that teaches it (below). Sugar over `plannotator inbox call routine` (who is calling, `--session`, the session's project, starting a stopped Inbox, the refusals and the exit codes are that command's), so it is the agent's `routine` tool exactly: one it makes arrives off (on with `--thread` naming the thread of a `/create-routine` grant), `on` and `run` answer `routine_not_approved` until the person turned it on once, and every value is checked by the server's own rules (`fieldsOf` in `inbox-scheduled.ts`: the 15-minute rule, the schedule's words, the folder refusals, the agents a run can start, which leaves out T3 Code). The command only says which field a flag fills; no rule is copied into it.

While routines are on, the routine section of `plannotator inbox --help` names it too, and `plannotator --help` has one line for it.

Every composer reads the one catalog, so New message, the reply box and the comment composers on attached files all list it. A skill of the person's own named `create-routine` wins. ### The editor

`packages/inbox/scheduled/ScheduledEditor.tsx` beside the narrow list (approval "inbox-routine-editor-autosave"). It saves by itself and says so (`useAutosave.ts`): a typed field after a 600 ms pause (`TYPING_PAUSE_MS`), a field when it is left, a pick at once, a schedule once the preview takes it (a refused one is held), and what waits as the page hides or goes (`pagehide`, `visibilitychange` to hidden) with `keepalive` (bodies under 60 KB). Only the fields that differ from what the server has are sent, the same write is never sent twice at once (a tab closing fires `visibilitychange` and `pagehide`), and what the server answers is what the window takes as saved (an answer older than one already in is let go; the store keeps the newer row). A routine that is on runs what is saved, so its typed name and prompt are not saved on the typing pause: only when the field is left, the editor goes, the page hides, or before Run once now or a turn; the header says "Not saved yet" until then (`held`). The saves that come on their own (the typing pause, the schedule preview's, a pick, a retry of one of those, the save on opening) leave its typed name and prompt out, and a new one made on (or turned on) holds the words typed while it was being made the same way. A write with no answer, or a 5xx, 408 or 429, is tried again after 1, 2, 4, 8, 15, then every 30 s while the words stay in the field; a 4xx refusal is said in the alert line under the On switch and waits for the next edit. Leaving the editor (closed, another routine, Back) saves what waits. Run once now (the foot and the ⋯ menu) and Turn on (the foot, the switch, the ⋯ menu) save what waits first; if it did not save they are not taken, and the alert line says "Not run: your last change isn't saved yet." / "Not turned on: …" (Turn off is taken at once, without waiting for a save on its way). A saved routine's edits not saved yet are kept in sessionStorage too (`plannotator-routine-edits:<id>`, with what the server had), so a reload (an Inbox that updated asks for one) brings them back over a field nobody else changed; one over a field changed since is forgotten when the routine opens. The header's status (`SaveStatus.tsx`, `data-scheduled-status`): "Not saved yet" (`new`), "Saving…", "Saved" with a check, "Couldn't save · retrying" in red, "Couldn't save" (a refusal), and on a saved one whose name or prompt was emptied "Not saved · needs a name" / "needs a prompt": an empty required field is never sent and never put back while the person types. The words shown are not a live region; a polite one beside them says only a failure or what is missing.

A new one (`#routine=new`) is made, off, once it has a name and a prompt; until then it is kept in the tab's sessionStorage (`routineDraft.ts`, key `plannotator-routine-draft`, with its create's `idempotency_key`), so a refresh or New routine again brings it back, and a page that went mid-create makes it once when it comes back. It is forgotten once made, when its name and prompt are both emptied, or on Delete (one being made at that moment is deleted when its create answers). When it is made the address turns to its id in place (`replace`) and the editor stays mounted (`editorKey.ts`): focus and the words typed during the create stay. Closed while it is being made, it is made and does not open again.

The foot (`EditorFoot.tsx`): while off, "Off, so it won't run on its own.", a quiet "Run once now" and the filled "Turn on"; while on, "On · next run today at 7:00 PM" (`footNextWords`) and "Run once now", no filled button (on is `routineOn`, the switch's rule too: a one-off run of an off routine leaves it off); Stop in place of Run once now while a run goes. A new one that cannot be made yet: "Saves by itself once it has a name and a prompt." and a dimmed Turn on (Turn on on a new one makes it on). Run once now saves what waits first, then runs (a real run, as the list row's Run). Beside the editor (wider than 760 px) the narrow list hides Runs and gives its room to the name, as the phone layout does; Run stays right of the name.

The tabs (`RoutineTabs.tsx`), under the name and the On switch: Edit (schedule, folder, files, prompt) and Runs (the newest 20 runs the read answers, each opening the thread at its run, then "All N in the thread" or "Open the thread"; a routine with none says "No runs yet." and when it first runs). They are the Inbox's segmented control as a tab list, as Feedback's and Settings → Appearance's: automatic activation, the arrows, Home and End, one tab in the Tab order. Edit opens first; the address keeps Runs (`#routine=<id>&runs`, written in place, not a new history entry), so a reload or a shared link lands on it, and a new one taking its id keeps its tab. Both panels stay mounted, so a switch keeps the words, the focus's field saves as it is left, and the header's status shows on either tab; the foot (Run once now, Turn on, Stop) is under both. The Runs tab's label carries the run count (`ib-n`, heard as "Runs, 12"), the page's running mark while a run goes, and a red dot when the last run didn't start or didn't finish (with the words for a screen reader). The tab keys leave Cmd, Ctrl and Alt alone (Cmd+← is the browser's Back). On Edit, one line beside the tabs says the last run ("Last run Today 9:00 AM · Didn't start", in red when it went wrong; "Running · 0:42" while one goes) and opens Runs; a one-time one that ran says "Done" by its switch, so the time is said once. The editor pane's width, not the window's, puts that line beside the tabs or under them (a container query on `.st-tabsrow`), always on one line (cut with …), so a run ending never changes its height. Beside the tabs it keeps its place unseen on Runs; under them it takes no space on Runs (the runs below say it). The tabs never move on a switch. On a phone the tabs span the screen.

### Routes (Bun only)

`GET /api/inbox/scheduled` → `{ scheduled: InboxScheduledRow[], launch_on }` (a row carries `thread_name`, "Replies in"). `GET /api/inbox/scheduled/:id` → `{ scheduled, runs }` (the newest 20). Writes are the window's only (same origin and `serverSession`; else `403 window_only`, "A routine is changed in the Inbox window; an agent uses the routine tool."): `POST /api/inbox/scheduled` (create, `201`; `enabled: true` turns it on and approves it; one `idempotency_key` (at most 128 characters) makes one routine: a second create with the key, at once, later or after a restart, answers that routine; `inbox-scheduled-once.ts`, the key kept on the record as `create_key`, which no row or tool answer carries), `POST /:id` (update), `/:id/on`, `/:id/off`, `/:id/run` (`202 { scheduled, message_id, failed? }`; `409 routine_running`), `/:id/stop`, `/:id/delete` → `{ deleted: true }` (a run under way is stopped first, and one still starting does not start; its thread and past runs stay), `/:id/restore` (the window's Undo: back as it was, counting from now). `POST /api/inbox/scheduled/preview { schedule }` → `InboxScheduledPreview` (words, zone, next run, or the refusal). The settings read carries `scheduled_threads: { on, login? }` (absent on Windows); `POST /api/inbox/settings { scheduled_threads: { on } }` writes it and sends `event: capabilities` (which carries `scheduled_threads` only while on, and when it turns off). A change to a record sends `event: record` with `{ seq, kind: "scheduled", id }` only.

### Linked machines

The record stays on the computer that made it: no door route and no list field carry it. Its runs' thread is an ordinary thread, so a linked machine shows it, replies in it and stops its run like any launched thread; the reply goes through the forward to this computer, where the same rules apply (the newest run takes it, an earlier one says it ended). Every divider keeps `name` on `scheduled_run`, so a linked machine's list shows the sender.
