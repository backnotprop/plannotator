## Inbox: window and questions

**The window** (`packages/inbox`, built by `apps/inbox` as a Vite single-file app).
- Build and serve: `build:hook` copies its `dist/index.html` to `apps/hook/dist/inbox.html`. The binary embeds it, and `runInboxCommand` hands it to `startInboxServer` as `htmlContent`. Without it, `/` says to run `build:hook`.
- Styling: `packages/inbox/inbox.css` carries the design record's values on Plannotator's theme tokens with an `ib-` prefix. Plannotator's own components draw themselves.
- Server URLs: every `/api/inbox/...` URL the window builds (fetch, EventSource, attachment `src`) goes through `inboxUrl` in `packages/inbox/inboxUrl.ts`; `tests/inbox-url-helper.test.ts` fails on a raw one.
- Routing is the hash: `#thread=msg_…` (the link the MCP tools hand agents), `#project=prj_…`, `#settings` (General; on a phone the list of sections), `#settings/<section>` (`general`, `agents`, `prompts`, `devices`, `capabilities`, `archived`, `storage`, `about`; an unknown one reads as `#settings`; `#settings/experimental`, an old link, becomes `#settings/capabilities` in place and lands on its Experimental group), `#settings/devices/pair` (Pair a phone open), `&file=att_…` (with `&view=full|side`, the file's view; see "Side by side, remembered"), `&guide=msg_…`, `&msg=msg_…` (land on that message: a search result; dropped from the hash once landed) (`packages/inbox/settingsRoute.ts` for the Settings addresses). An old link to the removed Decisions page (`#decisions=…`) opens the list.
- Opening a thread (`#thread=`): the pane shows once `GET /api/inbox/threads/:id` lands. A read that fails (a dropped connection, a 5xx) or has no answer in `THREAD_READ_TIMEOUT_MS` (8 s, an AbortSignal) is read again after `THREAD_READ_RETRY_MS` (250 ms, 1 s, 2 s, 4 s, then every 5 s while the thread stays open; a 404 is not; opening another thread or closing stops it; a read the event stream lands meanwhile ends the wait; `packages/inbox/App.tsx`). Reads are numbered, so an older one never overwrites a newer one that landed. Until it lands the thread's place beside the list says so (`components/ThreadWait.tsx`: nothing for the first 600 ms from the open in any state, then "Opening the thread…" (`aria-busy`), the failure with Try again (said once, not per retry), or for a 404 "not in the Inbox" with Close; focus inside it goes to the thread's subject when the thread lands; a phone and a stacked window keep the list, as before). Before this one failed read left the right side blank until some agent wrote anywhere in the Inbox (the event stream re-reads the open thread). Proof: `packages/inbox/threadReadRetry.test.tsx`.
- Issue refs (#1840): bare `#123` / `@user` in messages and markdown attachments link to the project's git `origin` (GitHub or GitLab, per `forgeRefLinks`, new tab). The server resolves `git remote get-url origin` per project root off the request path (`packages/server/inbox-repos.ts`: for every project once the server is listening and when a project is first seen, at most 4 gits at once, refreshed in the background after 5 min, 3 s git timeout, parsed by `parseRemoteUrl`/`parseRemoteHost`) and `GET /api/inbox/threads/:id` carries it as `thread.project.repo: { display, host } | null` (null for a folder without git or without origin, or until the first resolve lands; a git failure or timeout is cached as null for those 5 min too). The window hands it to `Viewer` as `refRepo`, which links refs without drawing `repoInfo`'s repo badge. A digit-only 6 or 8 digit ref (`#186379`) is an issue ref, not a hex swatch, only in the Inbox (`configurePlannotatorUI({ digitHexIssueRefs: true })`, off for every other host), only when a ref link can be built (a repo on a known forge), and only without a leading zero (#1932). `owner/repo#123` links to that repo on the project's forge host (`matchCrossRepoRef`, see "Hover cards for #refs" in `guides-and-shared-ui.md`), and the agents are told so in both `body` descriptions and `--help` (`INBOX_REF_LINK_RULE`); the opened Board card renders its You band, notes and history through the same `InlineMarkdown` with its own project's repo (`GET /api/inbox/cards/:id` `repo`).
- Hover cards for issue, PR and MR links (owner's call, 2026-10-26: GitHub and GitLab now; the latest comment only; 400 ms; no new key). A link in a message body to an issue, pull request or merge request (a `#123` linked as above, or a pasted `https://github.com/o/r/pull/N`, `…/issues/N`, `https://<gitlab host>/<namespace>/<project>/-/merge_requests/N`, `/-/issues/N`, `/-/work_items/N`) shows a card (its host taken exactly as written: `parseForgeRefUrl` does not fold the SSH aliases `normalizeForgeHost` folds for git remotes, and a host that only starts like `github.com` or `gitlab.com`, such as `github.com-evil.example`, gives no card) after the pointer or keyboard focus rests on it for `REF_CARD_DELAY_MS` (400 ms). Before that nothing is asked: opening a thread runs no CLI and makes no request (`tests/e2e/inbox-ref-cards.spec.ts`).
  - The card (`RefCardView` in `packages/ui/components/RefHoverCard.tsx`, the same in light, dark and on a phone): repo and "opened N ago"; the state icon, title and number (`!7` for a GitLab MR, `forgeRefLabel`); a state pill (Open, Draft, Merged, Closed, Not planned; merged and done in the palette's `--primary`); author, "updated" or "merged/closed N ago"; for a PR or MR `base ← head`, `+adds −dels · N files`, the checks (GitHub: the head commit's check runs and statuses; GitLab: the head pipeline's jobs, "Pipeline running · 2 of 4 jobs left") and the review decision (Approved, Changes requested, Review required; GitLab from `approved` and `detailedMergeStatus`, quiet once the MR is merged or closed); labels and assignee avatars. Then a scroll area: the body (markdown cut at 4,000 characters, "The rest is on GitHub"), "Closes" / "Closed by" (GitHub only), and the latest comment by a person (GitLab system notes skipped), cut at 600; it shows up to 216 px (about eight lines of a description) before it scrolls, 340 px once pinned (the sheet gives it the height). A footer: the comment count and **Open on GitHub / GitLab ↗**, always in view: when the window leaves too little room for the description (a short window), the header and the scroll area scroll together as one (`tight`, `data-ref-card-tight`) instead of squeezing the description to a line or cutting the footer off. Untrusted text renders through `RenderedMarkdown` (DOMPurify on HTML), images are never loaded (their alt text, an empty title), and a link in the body has no `href` once drawn (kept as `data-ref-card-href`, `role="link"`, focusable), raw-HTML and `<details>` links included: a MutationObserver strips every `a` and `area` `href` (and `xlink:href`) after any change to the body, because `HtmlBlock` writes raw HTML in a passive effect after the card's own pass, and native capture-phase `click`, `auxclick`, middle `mousedown` and Enter listeners on the body catch any link, `href` or not, before the renderer's listeners; a local path in the body is inert (`resolveLocalLink` answers unavailable). So a middle-click, a modified click or the context menu opens nothing; a click or Enter only offers "Open · Cancel" with its URL (the host whole and in the text colour, however long a lookalike makes it, the path cut in the middle when long, the whole URL for a screen reader; `confirmUrlParts`), whose Open is the one real link. Failures are a calm card that still offers Open on GitHub: the CLI not installed (`cli_missing`), signed out, not found or no access (`not_found`), rate limited, unavailable; a host this computer does not fetch from (`unsupported`) shows the same quiet card ("Details show for hosts your gh is signed in to…") with nothing fetched.
  - Behaviour (`useRefHoverCards(rootRef)`, event delegation on the region, so `InlineMarkdown` is unchanged): opens on hover or `:focus-visible` focus after the delay; Tab from the focused link moves into the card, Shift+Tab from its first control back; a press inside pins it (`data-ref-card-pinned`: it stays when the pointer leaves, scrolls, shows Close); Escape (used, so the thread's own Escape skips it), Close or a press outside close it, focus back on the link when it was in the card; a page scroll closes an unpinned card and moves a pinned one; one card on the page at a time. On a touch screen (`(hover: none)`, or a touch pointer) a tap shows it as a bottom sheet instead of following the link (44 px targets, its scrim closes on click so the tap never lands underneath). The Inbox's `MessageBody` calls it on each body (`packages/inbox/components/Thread.tsx`).
  - The seam: `configurePlannotatorUI({ refCardTransport })` / `setRefCardTransport` (`packages/ui/utils/refCard.ts`; the client keeps an answer 30 s per ref and shares one request between hovers). Default none: no card and no request, so every `@plannotator/ui` host that installs none is unchanged. Plan review, annotate and code review install one over their own `GET /api/ref` (see "Hover cards for #refs" in `guides-and-shared-ui.md`). The Inbox installs one over `GET /api/inbox/ref?url=` (`packages/inbox/App.tsx`). The link parser and the card's data types are browser-safe in `@plannotator/core/forge-ref-card` (`parseForgeRefUrl`, `forgeRefKey`, `ForgeRefCardData`, `ForgeRefCardResult`).
  - The fetch (`packages/server/ref-cards.ts`, `createRefCards`, reusable by any server): one read-only GraphQL `query` per ref through this computer's own CLI (the module refuses to load a non-query): GitHub `gh api graphql` (`issueOrPullRequest`, both kinds in one call); GitLab `glab api graphql` (`project.issue` or `project.mergeRequest` by the link's kind, since GitLab numbers them apart). Hosts: github.com and gitlab.com, plus the hosts this computer's own gh or glab is signed in to (`readSignedInHosts`: `gh auth status --json hosts`, a host counting only when an account there says `state: "success"`, else its text form, and `glab auth status`, read once per 5 min, `REF_AUTH_HOSTS_MS`; an answer with no host, as from a failed or timed-out `auth status`, only for 30 s, `REF_FAILURE_MS`), which covers GitHub Enterprise and self-managed GitLab; `--hostname <host>` is passed on every call, github.com and gitlab.com too, so `GH_HOST`, `GITLAB_HOST` or the working folder's git remote never pick the host; any other host answers `unsupported` without running anything, so a link or a cloned repo's origin naming `github.evil.example` can never make the CLI send `GH_ENTERPRISE_TOKEN` or `GITLAB_TOKEN` there. Owner and repo go as strings (`-f`; `-F` would turn a repo named `2048`, `true` or `null` into another type). GitHub accounts follow #2157's rule: the active account first; when GitHub refuses it (404/401/403/SAML), each other account signed in on that host is tried through its own token in `GH_TOKEN` (`GH_ENTERPRISE_TOKEN` on GHES) for that child only, and the account that could see a repo is remembered for it (memory only, never logged). Cache per ref: fresh 60 s (`REF_FRESH_MS`), a failure 30 s (`REF_FAILURE_MS`); a stale answer is served at once while one refresh runs, up to 15 min, and a failed refresh keeps it and holds off the next for 30 s; hovers of one ref share one request; at most 2 CLIs at once; a rate-limit answer pauses that host for 60 s (`REF_RATE_LIMIT_MS`); each CLI is killed after 8 s. Memory is bounded for the life of the Inbox: at most 500 refs (`REF_CACHE_MAX`) and 200 remembered repo accounts (`REF_REPO_ACCOUNTS_MAX`), least recently used dropped first; answers past 15 min, failures past 30 s and finished holds are dropped at the next fetch; at most 500 lookups wait for a CLI (`REF_MAX_WAITING`, above a Board request's 200 links), and one more answers `unavailable` at once without being cached. Avatars are fetched once from GitHub's avatar host, the GitLab host itself or Gravatar (64 KB, png/jpeg/gif/webp) and inlined as data URIs, since the window's CSP takes no remote image (at most 500 kept, `AVATAR_CACHE_MAX`, and 8 MB of data URIs in all, `AVATAR_CACHE_MAX_BYTES`).

The box opens behind full screen without taking focus, and the draft saves as it always does (`replyDraft.ts`, `base_body` and all). Typing in either place is the same draft.
- Send is the thread's Send (`send({ stayFull: true })`), with the same rules and refusals. Its error shows in the card (the thread's own `role="alert"` line announces it). A Send that goes clears the words and the draft (`clear_draft`), keeps full screen, keeps focus in the card, and shows "Sent to <agent>" for 4 s (the thread's live region says it). A replaced pick's guard, and the choice of where an ended session's reply goes, need the thread: the Send then takes the person there. Files: the Reply tab's toolbar starts with the reply box's paperclip (`AttachFilesButton`, the card's 30 px button, 36 px on a phone; none on the Comment tab, as a comment takes no files), a paste of files into the field attaches, and files dropped on the card attach (`useFileDrop`, the box's dashed "Drop to attach"). They are the reply box's own files (`replyFiles`; the box opens behind full screen), shown in the card with the box's tiles, and the Send carries them. Send is dimmed when nothing would go (no words, picks, comments, files or action items); Mod+Enter in the field still sends, and an empty Send says "Write a reply or pick an answer first."
- The bottom row (Reply tab) is the reply's toolbar: the paperclip, then what rides the Send (picks, action items, comments, open questions) or "Sent to <agent>" just after a Send, with **Open in thread** at its right. Open in thread takes the device's own route to the thread: beside it where there is room (as Write the reply), else the file closes (a phone's or a stacked window's Back). A comment not saved yet in the file is asked about first. The box keeps its words and focus lands at their end. When another window changed the draft, the row says so; Keep mine and Discard stay in the thread.
- Minimize: the double chevron at the card's top right (the toolbar's 30 px `.ib-fvb`, tooltip "Hide the composer") leaves a 30 px pill at the foot (`[data-fcomp-pill]`) that reads "Reply draft" while words wait, else the tab's label. One click restores the card and focuses its field. Minimizing focuses the pill. It is kept per thread, across files, until the person restores it. No dots and no "Draft saved" line: the words carry the state.
- Hide (») hides the card and the pill with the toolbar and the size chip (`data-tools` on the pane, `tucked` or `revealed`; the card and the pill are `inert` then).
- Phone: the card spans the width (8 px in), the toolbar sits above it (the card is the pane's foot, `data-file-foot`, so `--ib-fvfoot` lifts the toolbar), the tabs read Comment and Reply, and Send is the icon ("Send to <agent>"). Minimized, the pill is a 52 px button left of the toolbar, at its height: the icon, plus "Draft" when words wait. On a phone a film's comment row is in the Comment tab, so its "Comment at" button does not show in full screen. What it did is kept: a tap in the comment field pauses the film and pins that moment, and clearing the words lets go of it (that was Cancel), so another moment can be picked.
- Keys: nothing new. Escape in the reply field is full screen's `field` rung, as in a comment row: focus leaves the field and the words stay ("Left the reply box. Your words are kept."). R from a file in full screen goes back beside the thread first, also when the composer has opened the box; the box keeps its words and caret (before the composer, R with the box open put focus in the box hidden under full screen).
