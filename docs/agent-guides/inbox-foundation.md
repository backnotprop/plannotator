## Plannotator Inbox

One long-lived local server per machine. Agents leave messages, `:::question` blocks, files and guided reviews there for the person, and the person answers when they can. Nothing holds an agent session open on it. A reply wakes the session that asked, through the Claude Code, Pi or OpenCode connection, or reaches any other agent through `wait_for_reply`. The window's design of record and the owner's decisions are kept privately (not in this repo); this section carries what a build here needs from them. Not built: the Mac notification helper (only a spike so far). Where it is documented for users and agents: `plannotator --help` (`apps/hook/server/cli.ts`) and the agent guide `plannotator inbox --help` (`apps/hook/server/inbox-help.ts`, see "The command"), the `## plannotator inbox` section of the `plannotator` skill (`apps/skills/core/plannotator/SKILL.md`; deliberately short: the usage lines, when to use the Inbox, tool-or-MCP, and a pointer to read `plannotator inbox --help` first, so details live in the guide, not the skill), and the marketing reference page `apps/marketing/src/content/docs/reference/inbox.md` (`/docs/reference/inbox/`). A change to the command, the MCP tool list or the knob updates the guide and the reference page, and the skill only when its usage lines or its when-to-use rule change.

**The command** (`apps/hook/server/inbox-command.ts`, usage in `cli.ts`, the agent guide in `inbox-help.ts`).
- `plannotator inbox` starts the Inbox in the foreground and opens it in the browser, or opens the running one.
- `plannotator inbox --background` starts it detached (its own session, output in `inbox/inbox.log`), prints the URL and exits 0. It never opens a browser, so an on-demand start never pops a tab mid-work.
- `plannotator inbox --no-open` runs it here without a browser.
- `plannotator inbox --open` opens the Inbox in the browser and prints its URL on stdout, exit 0: the running one, else one it starts through the `--background` path first (detached, so it never blocks the caller; no agents connected, as for any detached start). The browser opens through `openBrowserDetached` (`packages/server/browser.ts`): the opener runs in its own process group with no stdio and is never waited for, because a browser the opener starts can hold its output open for as long as it runs (`openBrowser` waits for that, which is right for bare `plannotator inbox`, unchanged); the VS Code IPC has a 2 s limit. In a remote session (`isRemoteSession()`) with no browser set, only VS Code's IPC is asked, never the system opener on the remote host, and stderr gets one line on `ssh -L <port>:127.0.0.1:<port>` or `--tailscale` (`inboxRemoteOpenHint`). It refuses `--background` and `--no-open` beside it (exit 1). It is what every `/plannotator-inbox` command runs (the person closed the tab, or asks where the Inbox is), and what the agent guide tells an agent to run when the person asks where their Inbox is.
- `/plannotator-inbox`, one per host that has the other `/plannotator-*` commands: the Claude Code mod answers it itself (`INBOX_COMMAND` in `apps/hook/hooks/mod/launch.ts`: one `$.process.run` of `plannotator inbox --open`, the address as the command's answer, no model turn), else the Claude skill's bang line (`apps/skills/claude/plannotator-inbox`); the core skill (`apps/skills/core/plannotator-inbox`, installed to `~/.agents/skills` for Codex and the rest, and as the Kiro and Vibe copy, since it needs no origin label); Gemini's `apps/gemini/commands/plannotator-inbox.toml`; OpenCode's stub plus the plugin (`handleCliCommand`'s inbox branch over `openInboxInBrowser` in `packages/shared/inbox/agent-link.ts`: OpenCode 2 a transcript notice and no turn, OpenCode 1 a toast and the command's own turn carrying the address; never the embedded runtime); Pi's `pi.registerCommand("plannotator-inbox")` (the same shared helper, a notify); Droid's `commands/plannotator-inbox.js`; Amp's palette command. An older CLI answers `Unknown inbox option: --open`, which the hosts that read it (mod, Pi, OpenCode, Amp) turn into "update Plannotator"; each shows `Plannotator Inbox: <url>` plus the CLI's stderr note. OpenCode 2's notice is its own (`createInboxNotifier` in `v2-client.ts`), dropped from model requests like the failure notice. Droid's spawn has a 30 s limit. Codex spells the skill `$plannotator-inbox`. Like the other core skills it is user-invoked only and not offered in the installer's model-invocation question.
- `--tailscale` (with any of the three) also publishes it over the tailnet for this run (see "Over your tailnet"); with an Inbox already running, the command asks it to publish through the token-guarded `POST /api/inbox/control/tailscale`. Stdout stays the local URL alone; the tailnet URL (with a QR on a TTY) or the reason it is not published goes to stderr, and the exit code never depends on Tailscale. A restart to update of a run published only by the flag passes `--tailscale` on.
- `plannotator inbox mcp` is the stdio MCP entry (`apps/hook/server/inbox-mcp-shim.ts`), a thin JSON-RPC proxy:
  - It POSTs each stdin message to the Inbox's `/mcp` and writes every answer to stdout.
  - It re-reads `inbox/inbox.json` on every message and starts a stopped Inbox through the `--background` path (no tab).
  - When the agent leaves them out, it fills `project_path` (its working folder, or `PLANNOTATOR_CWD`) and `agent_session`.
  - The session is the agent host's own when the shim runs inside one (`inboxHostSessionFromEnv`): a well-formed `PLANNOTATOR_SESSION_TAG` (`<host>:<id>`, host `claude-code`, `pi` or `opencode`, id `[A-Za-z0-9][A-Za-z0-9._-]{0,127}`; anything else is ignored), else Pi's own `PI_SESSION_ID` (Pi sets it on each bash tool call), else Codex's `CODEX_THREAD_ID` (Codex sets it in the commands its shell runs; a UUID, anything else ignored). A tool call from Codex itself is its thread's, whatever the environment says: when the MCP client is Codex (`initialize`'s `clientInfo.name` is `codex-mcp-client`, or the call carries Codex's `x-codex-turn-metadata`) and the call names a thread id (`params._meta.threadId`, which Codex puts on every tool call), the shim sends as `agent_host: "codex"`, `agent_session: <thread id>`, `agent_name: "Codex"` (`codexThreadOfCall`, `packages/core/inbox-codex.ts`), and leaves `_meta` on the call (see "The Codex wake" under "Agent connections and the knob"). The host session is adopted only when the agent named no `agent_host` or that same host; an agent that names another host gets the shim's own `ses_` id, so a reply to it never wakes the session. On `send_message` and `submit_guide` it then also fills `agent_host` and `agent_name` (`Claude Code`, `Pi`, `OpenCode`; the name only when the agent gave none), so the author is byte for byte what that host's `plannotator_inbox` tool writes. A script or command a Claude Code or Pi session runs therefore sends as that session: the same default thread, `asked_by: "me"` and `wait_for_reply` see the tool's threads, and the person's reply wakes the session through its connection (`pendingReplies` matches on `author.session`). An `agent_session` the agent passes always wins. A tag inherited by a long-lived process started from an agent's shell (tmux, nohup) keeps naming that session; pass `agent_session` explicitly to override.
  - Qwen Code (`inboxCallHostSession`, read at every tool call; pure parts in `packages/core/inbox-qwen.ts`, the registry read in `packages/shared/inbox/qwen-sessions.ts`). Qwen sets `QWEN_CODE_SESSION_ID` in the processes it starts, but `/clear` and `/resume` give the session a new id under the same process while the MCP server keeps the old one, so the shim asks Qwen's own session registry each time: `$QWEN_HOME/sessions/<parent pid>.json` (else the parent's single `<pid>-<8 hex>.json`; two or more: only the call can say), checked as Qwen's protocol says (schema version 1, `pid` equal to the file name's, a UUID session id; a `kind` of the wrong shape reads as `tui`, as Qwen reads it), never written. Order: a daemon-run session's own `_meta["qwen-code/invocation"].sessionId` on the call; then, when the caller is Qwen (`clientInfo.name` `qwen-cli-mcp-client-<server name>`, or the older `qwen-code-mcp-client`; or a registry record for the parent), the record's id, else the variable; a variable alone counts only while no other client named itself (an MCP client's process may inherit it from a Qwen shell) and after another host's own variable (`PLANNOTATOR_SESSION_TAG`, `PI_SESSION_ID`, `CODEX_THREAD_ID`). `inboxHostSessionFromEnv` takes the variable last, so a command Qwen's shell runs (`plannotator card`) sends as that session too. The author is `agent_host: "qwen"`, `agent_name: "Qwen Code"`. The person's reply goes into a running Qwen Code session by itself (the Qwen wake, inbox-notifications-and-agents.md); a `PLANNOTATOR_SESSION_TAG` naming `qwen` must carry a Qwen session id.
  - Otherwise it is one `ses_` id per shim process, so an MCP client's identity ends with its MCP server process; a client that wants its threads across restarts passes `agent_session` itself. Replies to a session that ended are never handed to another session.
  - OpenCode exports no session variable to the commands it runs (OpenCode 2's `shell.create.before` hook carries no session id; OpenCode 1's `shell.env` does but OpenCode 1 has no wake), so there a command still gets a fresh id.
- `plannotator inbox status | stop | restart` (`statusCommand`, `stopCommand`, `restartCommand` in `inbox-command.ts`; ported from rmohta's fork, branch feat/plan-library, and rebuilt on today's stop and start paths; owner approval 2026-10-27).
  - `status [--json]` only reads (`inboxStatus`). It prints the URL, the tailnet URL while published, pid, version, start time and data dir; for a stopped Inbox, what the record last named and why it is not running. It exits 0 when running, 1 when not running (never ran, or `stopped`), and 2 when `busy` (a live pid holds the port but does not answer). In `--json`, `state` is `running`, `not_answering`, `stopped` or `never_started`, and `reason` is the stopped reason. `--json` is the CLI's global flag: `index.ts` takes it out of the arguments and passes `json` to `runInboxCommand`. It names a version skew when the running Inbox reports another version: "This plannotator is X", and it points to `restart` only when X is a newer stable release than the Inbox's (`isNewerStableVersion`), since restart runs this binary and would otherwise be a downgrade.
  - `stop` is `stopInbox(dataDir, { escalate: true })` (`packages/shared/inbox/registry.ts`). It asks first over the token-guarded stop route (the clean stop: tailnet mappings come down) and waits 5 s. Then it sends SIGTERM and waits 5 s, then SIGKILL. Before EVERY signal the pid is proven again (`proveInboxProcess`, `packages/shared/inbox/process-proof.ts`), in one of two ways. Health: the port answers with the record's pid AND serverSession. Process, POSIX only: `ps -o etime= -o args=` shows an Inbox server command line (`plannotator inbox`, or `… index.ts inbox`, followed only by `--no-open` / `--tailscale`; never `inbox mcp` or another subcommand) whose start, now minus `etime`, is no later than the record's `startedAt` plus 2 s. The Inbox writes `startedAt` once it listens, so a process that reused the pid started after it. A pid proven neither way is never signalled.
    - A record whose pid exited (`dead_pid`), whose port answers another Inbox (`other_session`), or whose pid is another program now (`no_answer`, the word `status --json` uses too): "No Plannotator Inbox is running: …", exit 0, nothing signalled.
    - A copied data dir (a backup, a sandbox seeded from `~/.plannotator`): its `inbox.json` names the original's Inbox, and both proofs pass for it. So the stop route's body carries `data_dir` (the caller's), and the Inbox answers 409 `not_ours` when its `inbox/` folder is another folder than the caller's (`isOwnDataDir`: refused only when both folders exist, their realpaths differ AND their device and inode differ, so a moved data dir, a bind mount or another mount namespace is never refused). Then nothing is signalled, `stop` exits 0 ("its record names the Inbox of another data dir"), and `restart` exits 1 having started nothing (a start would find the original through the copied record, as every start on a copy already does). An older Inbox ignores the body and stops, as before; the signal fallback (an Inbox that does not answer the route) cannot tell a copy either. `status` reads only health and still reports the original as running.
    - `inbox.json` is never removed: "found" means it exists, and it keeps the port.
    - A `start.lock` older than its stale age is removed and reported on stderr. A fresh one is waited out, so the Inbox that start brings up is the one stopped.
    - Exit 1 (stderr names the pid and `kill <pid>`, or Task Manager on Windows) only while it still runs: `busy` or `unproven` (it could not be proven, so nothing was sent) or `survived`.
    - Uninstall's purge keeps the old behaviour (`escalate` off: health proof only, SIGTERM only), and gets the same `not_ours` refusal on a copied data dir. Then it leaves both tailnet mappings the copied record names ("Reach from my tailnet" and "Over your tailnet") up, since they are the running original's, and warns that the Inbox was left running.
    - `--json` on `stop` or `restart` exits 1 with a pointer to `status --json`: neither prints JSON.
    - Stop is not sticky: an agent's next tool call or shim message starts the Inbox again through `--background`. The wakes never start it.
  - `restart [--tailscale]` takes the start lock (waiting out a starter that holds it), stops as `stop` does, refreshes the lock's mtime, then starts through the one detached start (`startDetachedInbox`, shared with `ensureInboxRunning`). So it starts the CLI that ran `restart`, never a tab. Its URL goes to stdout alone, its notes to stderr. An agent that finds the Inbox stopped in the gap fails to take the lock, waits (up to 20 s) and gets the new Inbox: never two writers. A run published only by the flag is published again: the stop route's answer carries the additive `tailscale_run_only` (`tailscale.runOnly()`, read before the stop), as the window's Restart passes `--tailscale` on. A foreground Inbox's terminal process exits 0; the new Inbox runs detached.
  - Limits kept as they are: `stop` waits up to 60 s (twice the lock's stale age) for a fresh start lock, which a `restart` keeps fresh, and a frozen Inbox makes `restart` take about 15 s, inside an agent's 20 s start wait (`START_TIMEOUT_MS`) but close to it.
  - The process proof reads the wall clock: a clock set back further than the time from the Inbox's start to its pid's reuse can let a reused pid that runs an Inbox server command line pass.
  - Agents across a restart: the token and serverSession rotate. Every caller re-reads `inbox.json`. A wake's poll that the stop cuts short backs off 5 s (`INBOX_RETRY_MS`), then polls the new Inbox. Pending replies come from the store, so a reply held during the restart, and one sent after it, are each delivered once. The Claude Code mod's wake has the same retry.
  - Windows: no `ps`, so only the health proof works. An Inbox that stopped answering is never signalled there, and stop says to end it in Task Manager; SIGTERM there is already a forced end.
  - Tests: `apps/hook/server/inbox-lifecycle-cli.test.ts` (the CLI as processes; a pid that is another program, or an Inbox-shaped one started after the record, left running; a SIGSTOPped Inbox ended by SIGKILL; a stale lock; restart's port, stdout and one-start log; an agent's start in the gap; a Pi wake across a restart), `packages/shared/inbox/registry-stop.test.ts` (stand-ins that ignore the stop route and SIGTERM; a health answer under another pid; the process proof both ways; the classifier; a stop route's `not_ours` refusal signals nothing), and the `tailscale_run_only` case in `packages/server/inbox-tailscale.test.ts`.
- Any other argument exits 1 with a usage line.
- Starts are serialized by `inbox/start.lock` (mkdir, stale after 30 s), so two agents that find the Inbox stopped at once start one. The detached child runs under its starter's lock (`PLANNOTATOR_INBOX_LOCK_HELD`, internal, scrubbed at start).
- The Inbox never registers in `sessions/` and never arms auto-update, so it never holds an update back.
- `plannotator inbox --help` (and `inbox mcp --help`) prints the **agent guide**, a markdown document an agent with no skill can read once to use the Inbox: what it is, when to use it, how to reach it, one section per MCP tool, thread routing, where replies go, the question syntax, connecting other agents, commands and flags, data and removal. `formatInboxHelp` in `apps/hook/server/inbox-help.ts` builds it from the code it describes: the tool list `INBOX_MCP_TOOLS` (its per-tool `TOOL_GUIDE` is typed by it, so a new tool does not compile without a section), `QUESTION_AUTHORING_GUIDE` verbatim, `INBOX_SECTIONS`, `INBOX_TOOL_NAME` / `INBOX_FILLED_ARGUMENTS` / `INBOX_TOOL_DEFAULTS`, the window's per-harness setup (`HARNESSES` / `harnessPanel`, `packages/inbox/harnesses.ts`, reached through the `@plannotator/inbox/harnesses` export) and the commands block `INBOX_COMMAND_USAGE` (`cli.ts`, also the `SUBCOMMAND_HELP.inbox` entry the skill freshness test reads). It names this CLI's absolute command (`selfCommand()`: the binary, or bun plus the entry script) and the resolved data dir. `index.ts` prints it for `helpSubcommand === "inbox"`; the top-level help points agents at it. `inbox-help.test.ts` keeps it true: every tool a real Inbox serves has its section and every argument it names is in that tool's served schema, the question guide is byte for byte, every harness is listed with its setup line, every flag and subcommand the parser in `inbox-command.ts` accepts appears, and the CLI as a process prints it (exit 0, empty stderr, no Inbox started). A new tool, tool argument, harness or flag updates the guide.

**Local only by default; each wider path is a switch.**
- It always binds `127.0.0.1` and ignores `PLANNOTATOR_REMOTE` and `PLANNOTATOR_PORT`, because it holds tokens and everything agents sent. To reach the window from your other devices, turn on "Over your tailnet" (below).
- Port: the last one (from the registry) comes first, so the browser's notification permission holds. When something else holds that port, the Inbox takes a random port and shows a one-time notice (stderr and the list model's `notice`). It never uses 19432, nor 8443 (Phones' tailnet port; the window's own tailnet mapping uses the Inbox's port, so the two never collide).
- "Over your tailnet" (off by default; `packages/server/inbox-tailscale.ts`, pure checks in `packages/shared/inbox/tailnet.ts`): `plannotator inbox --tailscale` (this run), `PLANNOTATOR_INBOX_TAILSCALE`, or config.json `inboxTailscale` (Settings' switch) publishes the window with `tailscale serve --bg --https=<the Inbox's port> http://127.0.0.1:<proxy port>`, serve and never funnel.
  - The socket decides, as for Phones: serve picks its handler by TLS SNI and passes the client's own Host through (`r.Out.Host = r.In.Host`, `ipn/ipnlocal/serve.go`), so a peer could claim `Host: 127.0.0.1:<port>`. The mapping therefore points at a second loopback listener that only serve is pointed at; the window's port is unchanged and never learns the tailnet name. That listener hands requests to the window's handler marked `via: "tailnet"`.
  - Owner only: every request on that listener must carry `Tailscale-User-Login` equal to the login that owns this machine (`tailscale status --json`: `Self.UserID` -> `User[id].LoginName`, read at each publish; `parseTailscaleSelfIdentity`) or one in config.json `inboxTailscaleAllow`, compared case-insensitively after RFC 2047 Q-decoding (`decodeTailscaleHeaderValue`; serve Q-encodes non-ASCII logins). Serve deletes incoming `Tailscale-User-*`, `Tailscale-Funnel-Request` and `Tailscale-Headers-Info` before setting its own, so a client cannot forge them through serve. A tagged peer gets no identity headers (`403 tailnet_identity_required`), another login `403 tailnet_identity_refused`, a funnel request (`Tailscale-Funnel-Request`) `403 tailnet_funnel_refused`. A tagged machine has no owner: publishing is refused, with the reason, until `inboxTailscaleAllow` names someone.
  - Also on that listener: Host must be the served MagicDNS name with the HTTPS port (`403 forbidden_host`), and `Sec-Fetch-Site: cross-site` / `same-site` is refused (`403 cross_site`) except a top-level GET navigation to `/` and GETs of `/api/html-assets/` (an attached page's sandboxed srcdoc frame is cross-site by construction): the identity is ambient, like a cookie, and every `*.ts.net` machine of the tailnet is same-site.
  - Through the tailnet (`via: "tailnet"`, whatever Host is claimed): `/mcp`, `/api/inbox/bridge/*`, `/api/inbox/control/*` and the device door answer `403 local_only`; so do pairing a phone, Phones' tailnet and Wi-Fi switches, "Open in" (`/api/inbox/open-in` and its app list: launching an app changes this computer), and turning the window's tailnet switch on (off is allowed). Read routes (the list, threads, settings, attachments and their new-tab page, guides, a message's images `GET /api/inbox/messages/:id/image`) answer the owner as on loopback, behind the listener's checks. Every non-GET request runs `isSameOriginOrNoOrigin` (the page's origin is `https://<MagicDNS name>:<port>`), then the `serverSession` guard. `/mcp` also refuses any non-loopback Host on the window's port, so `PLANNOTATOR_ALLOWED_HOSTS` cannot widen it.
  - Lifecycle: the mapping is recorded in `inbox.json` (`tailscale.https_port`, `proxy_port`) BEFORE it is made, so a crash always leaves a record. Every start first removes a recorded mapping whose proxy port is not this run's (a dead ephemeral port any later local server could bind; see "The crash window" under "Tailnet sessions"), switch on or off, then publishes when on. A take-down that fails keeps the record (never forgotten, retried at the next start and by `uninstall --purge`) and nothing is published over it that run. Taken down at every clean stop (quit, SIGINT/SIGTERM, the stop route, a restart to update before the new binary starts) and by `uninstall --purge` (`takeDownInboxTailscale`, by the ports `inbox.json` kept). While a mapping exists an `exit` handler and a SIGHUP route (the Inbox's clean stop, then exit 129) are installed, never otherwise; so while published, `nohup plannotator inbox --tailscale &` ends with the terminal (start it with `--background` instead). A mapping on the port that the Inbox did not make is never replaced or taken down: Settings says how to clear it. A take-down that fails keeps the switch on (`409 tailscale_unavailable`) and the ports in `inbox.json`.
  - A hand-made mapping onto the window's own port (`tailscale serve --https=<P> http://127.0.0.1:<P>`, the old workaround) hands the tailnet the whole Inbox, `/mcp` included, since serve passes a peer's Host through. The window's port therefore refuses (`403 local_only`) every request carrying `Tailscale-Headers-Info`, `Tailscale-User-Login` or a non-loopback `X-Forwarded-For` (#1867: a local reverse proxy like nginx/caddy/portless sending loopback addresses in X-Forwarded-For is allowed; serve always sets X-Forwarded-For with the peer's tailnet/remote IP). The first such request reads `serve status` and names the mapping (`tailscale.exposed: [{ https_port, target }]`, from `serveStatusRoutes` + `serveTargetIsLoopbackPort`, web handlers and TCP forwards); each publish reads it too. Stderr and Settings say plainly that it exposes the whole Inbox and its agent tools to the tailnet, and Settings offers "Replace it with the owner-only address" (`POST /api/inbox/settings` `{ tailscale: { on: true, replace_exposed: true } }`: removes each serve port whose route still lands on the window's port, then publishes). Without that request the switch never takes it over: publishing on its port is refused with the same words. A raw TCP forward carries no headers, so only the serve-status read catches it.
  - What a login let in can do: everything the window does, and a reply, and above all a New message, becomes a turn in a live agent session on this machine. So any allowed login, or anyone holding the owner's unlocked, signed-in phone, can drive agents that run commands here. Let in only logins you would let sit at this computer.
  - Never fatal: Tailscale missing, stopped or signed out leaves the Inbox running on loopback; the reason goes to Settings (`tailscale.error`), `inbox.json` and stderr.
  - The window page through the tailnet (#2032, `tailnetWindowPage` in `inbox.ts`): `/` is served through the shared `packages/shared/app-html.ts` helper (brotli q5 / gzip 6 on `Accept-Encoding`, `Vary: Accept-Encoding`, brotli prewarmed when the tailnet listener opens; 21.8 MB → 5.1 MB br, 5.8 MB gzip), with `Cache-Control: private, no-cache` and a weak ETag of the page (`304` on `If-None-Match`), after the listener's checks. The window's loopback port is unchanged (uncompressed, `no-store`), and the data routes stay `no-store`.
  - Settings' "Over your tailnet" block: the switch (saved to config.json and applied at once; locked while the env var decides; shows on with the error while publishing fails, so one click turns it off), the address, who may open it, "Keep it on at every start" for a run published by the flag, and the exposure warning with "Replace it with the owner-only address". Turning it off through the tailnet answers first and closes the listener a moment later. A page opened over the tailnet (`via: "tailnet"` on `GET /api/inbox/settings`) cannot turn it on.
  - Notifications are per origin, so the tailnet address is a separate permission; the one-time line says "moved" only for a port change under the same name (both loopback counts as the same), and a different name gets the plain ask.
- A paired phone reaches it only through the device door (see "Phones"), and only over a path the person switched on in Settings:
  - "Reach from my tailnet" (off by default): a second loopback listener that serves the device door and nothing else, published with `tailscale serve --bg --https=8443 http://127.0.0.1:<door port>`, serve and never funnel. The window's port is never published: `tailscale serve` passes the client's own Host header through, so only the socket can keep tailnet requests on the door. The switch is kept in `inbox.json` as `tailnet: { https_port: 8443, door_port }`; each start publishes again. The listener and the mapping go when the switch goes off and at every clean stop (quit, the stop route, and a restart to update, before it starts the new binary). A mapping a crash left (kill -9) is re-pointed by the next start before anything else, or taken down when it cannot publish; SIGHUP runs the clean stop while a mapping exists (installed only then, as `--tailscale` does, so `nohup` keeps its meaning otherwise); `uninstall --purge` takes a leftover down by `door_port`. A take-down that fails changes nothing (switching off answers `409 tailnet_unavailable`, `door_port` is kept). The window's port never adds the tailnet name to its Host allowlist. A mapping on 8443 that the Inbox did not make (its target is not this run's or the last run's door listener) is never overwritten or taken down: the switch stays off and Settings says so.
  - "Reach from this Wi-Fi" (off by default; `packages/server/inbox-lan.ts`, contract section 3): a TLS listener on every interface (`0.0.0.0`) that serves the same door-only handler as the tailnet's listener, on a port chosen free the first time and kept in `inbox.json` as `lan: { port, on }` (kept when switched off, so on again reuses it). It stays on all interfaces, not the Wi-Fi address alone: a socket bound to one address dies with a new DHCP lease, and `Bun.serve` cannot bind to an interface. The certificate is self-signed ECDSA P-256 (`CN=Plannotator Inbox`, never rotated), made with two `openssl` child processes the first time and kept in `inbox/tls/` (files 0600 in a 0700 folder); its SHA-256 (of the DER) rides the QR as `fp` and the phone pins it. A `_plannotator-inbox._tcp` Bonjour record (instance `computer.name`, TXT `v=1`, `fp=`) goes out through `dns-sd -R` (macOS) or `avahi-publish -s` (Linux) as a child process under `sh`, which ends the publisher when its stdin closes, so a kill -9 leaves no record; with neither, the listener still answers at the QR's address and Settings says phones will not list it. Pairing over the Wi-Fi is by the QR's secret only: the LAN listener's `pair` refuses six digits with `400 code_not_accepted_here` (a Bonjour record anyone on the Wi-Fi can publish must never become the pin), while the window's port and the tailnet's listener take both; the record's `fp` only lets a phone already paired by QR follow the computer to a new address. The QR's `lan` is the first private IPv4 address that is not loopback, link-local or Tailscale's, read when the offer is made. Off closes the listener and the record and keeps the port with `on: false`; a listener that cannot open at start shows the switch on with the reason, and off works; a clean stop closes both and keeps the switch, and the next start opens the same port with the same certificate. `openssl` missing answers `409 lan_unavailable` and the switch stays off.
  - The relay (R1; `packages/server/inbox-relay.ts`, `apps/relay`, contract section 4): not a listener. The Inbox makes an outbound mailbox at the first pairing and holds one WebSocket to it while a phone is paired; the relay holds only hashes, each phone's relay switch, its APNs token and envelopes it cannot open. Through it (R2) a phone reads and answers the Inbox from anywhere: store lines down, commands up, each sealed under keys made at pairing.

- Busy: a live pid whose port takes the health request but does not answer in time. Callers wait for a busy Inbox (up to 20 s, then an error) and never replace it, because a second process would be a second writer on the store.
- Callers re-read the registry on every call.
- An Inbox whose data is gone exits: every 5 s (`INBOX_DATA_CHECK_MS`) it reads `inbox.json` (`probeInboxData`). It is a miss ONLY when the file or its folder does not exist (ENOENT, ENOTDIR) or the file names another `serverSession`; any other error (EACCES, EIO, ESTALE, a file that does not parse) is unknown and leaves the count alone, and the folder's device and inode are not looked at (a remount or a moved copy must not end it). Two misses in a row stop it cleanly, then it says why on stderr (plus the manual `tailscale serve --https=<port> off` when the tailnet take-down failed) and the process exits 0 (`onDataGone`). Nothing could reach it (agents find an Inbox through the file) and it has no store, so it must not run on headless (an e2e once removed its temp folder under a live `--tailscale` Inbox, which ran for two days at 100% CPU, cause unknown). It is a timer, so it cannot end an Inbox stuck in a synchronous loop. After it starts, the Inbox rewrites `inbox.json` only while the file names its own `serverSession` (`updateOwnInboxRegistry`, used by the tailnet and Wi-Fi saves; read then write, so a start overlapping a stop can still lose its entry, and then exits by the same check), so a stopping Inbox never rewrites its successor's entry and never makes a removed data folder again.
- The detached Inbox runs with `inbox/` as its working directory and `windowsHide`.
- The update control (`packages/server/inbox-updates.ts`; design record, not in this repo): health, the list model and the event stream's `status` carry `update: { available: true, state, version, current, action, releaseUrl, publishedAt? } | null` (`InboxUpdate` in `packages/core/inbox-types.ts`; `available` and `version` keep the older shape). `ready`: on the health tick (60 s, every 2 s while `update.lock` is held), a compiled Inbox stats the binary on disk and, only when the file's identity (device, inode, size, mtime) changed, runs it with `--version`; a different version is ready (the old restart-to-update signal). `updating`: `update.lock` is held. `failed`: `update-result.json` records a non-zero exit for an install the PERSON started (`pending.by: "person"`; a background auto-update failure stays out of the sidebar). `available`: a release build (X.Y.Z, so never `dev` or `0.0.0-dev`) runs the shared release check on start and on each page load (when the answer is over a minute old) and on each tick (when it is over 10 minutes old, and 10 minutes after a failure; never while `PLANNOTATOR_UPDATE_CHECK` is off; a new release therefore shows within 10 minutes, at once on a restart or a reload) and shows a newer stable release at once, before anything is downloaded (owner's answer 2), unless "Remind me tomorrow" snoozed that version (`update-state.json` `snooze: { version, until }`, 24 h, shared by every tab; a newer release clears it). `action`: `script` when the running binary is the install script's (`isManagedBinary`), else `copy`. The list model also carries `updated`: the version this run started on when it is newer than the one the Inbox ran before (`inboxVersion` in `update-state.json`), for the sidebar's quiet "What's new in X" link this run only. That start also keeps the version it found as `inboxPreviousVersion` (additive; kept across restarts on the same version, replaced at the next update, removed on a downgrade), so the What's new page of a release this Inbox already runs still lists the releases skipped since the version run before the update (the answer's additive `since`, which `skipped` counts from; a newer release counts from the running version, and `current` stays the running version). The release check saves notes only for the `releases/latest` it fetched, so a version installed outside the Inbox (the install script run by hand) before a check saw it has none: `fetchReleaseNotesFor` (`packages/shared/update-check.ts`) then asks for that release by its tag (`releases/tags/vX`, `releaseTagApiUrl`, the same client rules: the `plannotator-update-check` user agent, nothing while `PLANNOTATOR_UPDATE_CHECK` is off, claimed in `update-state.json` `notesFetch[<version>]` before the request, then 6 h after a failure and 24 h after an answer with no "What's New" part, never a loop) and saves `update-notes/<version>.json`. A stored file with an empty "What's New" part (saved before the release body was edited) counts as missing and is fetched again under the same throttle. The Inbox runs it on its tick for `updated` and from `GET /api/inbox/whats-new`, only for a version it has reason to show (the one it runs, the newest known release, the binary on disk, an install in progress); the route waits up to 3 s (`WHATS_NEW_WAIT_MS`), then answers `503 { code: "notes_loading" }` with `Retry-After: 1` and the page asks again (up to 15 times). `updated` is null while its notes are neither saved nor fetchable (checks off, or a fetch in its back-off), so no link points at a page with nothing on it; the event stream's `status` carries `updated` too, so the link appears or goes once the fetch settles. Update now is `POST /api/inbox/update` (`startManualUpdate`: the same wrapper, lock, log, pinned tag and remembered flags as auto-update, without its 24 h window, its open-sessions gate or its mismatch back-off; a second press while it runs is `409 update_locked`); the page that pressed it restarts the Inbox itself once `ready` arrives. On macOS and Linux that wrapper downloads the install script and checksums with the Inbox binary's own fetch (`update-prepare`, environment.md `PLANNOTATOR_AUTO_UPDATE`). The failure dialog (`FailedDialog` in `packages/inbox/components/Updates.tsx`) reads `failure.exit_code` (codes in `packages/core/update-exit-codes.ts`) and, for `75`, the additive `failure.prepare` (the update was downloaded but the temp folder could not hold it: the plain reason, shown as "Plannotator couldn't prepare the update: …" with the advice for its cause (`updateStagingAdvice`) and `TMPDIR=/another/folder plannotator update`, no install command) and `failure.tls` (`failureDetails`: the last run's lines in `update.log` hold `update-prepare`'s `UPDATE_TLS_HINT`). `113` (the download did not match the checksum Plannotator fetched) and `75` (Plannotator could not download the update) say nothing changed and the old version still works, and show the log and Try Again. `113`, and `75` with `tls: "revoked"` (a blocked eMudhra key), never show the `curl | bash` line: "try again on another network". Any other `75` can be a lasting local condition (a proxy, a network that inspects HTTPS), so it keeps the way out: "If this keeps happening, install it yourself" with the command and the release page, plus `NODE_EXTRA_CA_CERTS=/path/to/its-root.pem plannotator update` for `tls: "untrusted"`; on macOS that case also carries `failure.release_first` and the release page comes before the command (macOS curl still trusts emSign G3). Any other code keeps "Or run the install script yourself". A tailnet page reaches none of the update routes.
- **No one stuck on a version** (owner, 2026-10-26, QA item 30; audit of every shipped generation in the PR that added this). Every path ends with the update shown within a stated bound, or the person told plainly that checking or installing fails, with the command that always works (the install script finds the newest release by itself: the API, else the release page).
  - **Checking that fails for hours.** `releaseCheck.failingSince` in `update-state.json` marks when the current run of failed checks began (kept with its last `failedAt` across the claim of each next attempt and across any gap between checks, cleared only by a success), and `failingFor` how long it has failed as of that last failure, each gap between two failures counted as at most 90 min (`RELEASE_CHECK_FAILURE_RECENT_MS`). `releaseCheckFailing` (`packages/shared/update-check.ts`, vendored to Pi) answers since when and why once that time reaches 3 h (`RELEASE_CHECK_FAILING_AFTER_MS`), its latest failure is under 90 min old (an attempt claimed since, in flight or abandoned by a process that exited mid-request, changes nothing until it answers), and no process succeeded since. So checks hours apart (a review window now and then, a laptop that sleeps a lot) say so by their third failure; a machine that slept, or checks turned back on after weeks, shows nothing until a check fails again; one failure right after a week asleep stays quiet. An API-only setup (`PLANNOTATOR_UPDATE_API_URL`) waiting out the API's back-off keeps its run current. A state file that cannot be written never stops the check: `writeUpdateState` keeps this process's own changes in memory (`unwrittenStates`: the fields that differ from the file as it read when the write failed; one `update.log` line, no temp file left), `readUpdateState` reads the file and lays those over it, and every later write tries the file again, so it still checks every 10 minutes at most, shows what it learns, reaches the failing state if GitHub fails too, and never writes a stale copy over other processes' `pending`, `lastCheckAt`, `snooze` or `latestRelease` once the file can be written. It shows only while update checks are on and nothing better can be offered: the list model and the event stream's `status` carry the additive `update_check_failing: { since, error } | null`; the sidebar draws a quiet row "Can't check for updates" (`CheckFailingRow`, opening Settings → About) where the Update button would be, the toggle's dot is neutral, About's nav has its dot, and Settings → General's update row and About say "Can't check for updates since <time> (<reason>) · last tried <time>" with the install command; the reason is in plain words (`plainCheckError`: "release page didn't answer as expected; GitHub API rate-limited", "couldn't reach the release page", never a status code; `update.log` keeps the raw one), as is `check.error` and Check now's error (`check.failing` on `GET /api/inbox/update`). The plan, review and annotate servers (Bun and Pi) add `updateCheckFailing: { since, error, command }` beside (never with) `updateAvailable`, which the Options menu shows as a quiet line with the command (no dot, no toast); the terminal hint says it once a day; `plannotator update` that cannot check ends with the install command.
  - **Updating… never spins.** The detached POSIX wrapper (auto-update, Update now: `PLANNOTATOR_UPDATE_DETACHED=1`; it leads its own process group) first writes `pid=<pid> group=<pgid> host=<uname -n> boot=<Linux boot id> pidns=<Linux pid namespace>` into `update.lock`. A lock in that form, from this machine (host, boot and pid namespace equal; anything else or unreadable is unknown), whose process group has no process left (`kill(-group, 0)` answers ESRCH; a wrapper killed alone leaves its installer in the group, still held), 5 s after it was written (`UPDATE_LOCK_HANDOFF_MS`), is not held: `reapDeadUpdateLock` (the Inbox's tick, `acquireUpdateLock`) renames it aside, removes it only if it is still the same inode and content (`removeJudgedLock`; a lock another process took in between is put back), and records the install as failed (exit -1), so the Inbox shows Failed with the log and Try again. Any other lock (the taker's bare pid, an older wrapper, the foreground `plannotator update`, Windows) keeps the hour's rule only. A lock more than an hour in the future (the clock moved back) is expired too. The wrapper's download of the install script gives up when it stalls for a minute (`--speed-limit 1 --speed-time 60`).
  - **Clocks and snoozes.** A "Remind me tomorrow" hides a version only while its time is at most a day away (`isSnoozed`), so one stamped while the clock was ahead cannot hide the update until the clock catches up.
  - **Auto-update meeting a failing check** installs the newer release an earlier check already named (it used to give its window back and stay "active", which keeps the review toast away, without ever installing).
  - **The release page's redirect** on github.com is read whatever the case of the owner and repository in its path; a mirror (`PLANNOTATOR_UPDATE_LATEST_URL`) is read exactly.
  - **The words.** Settings → General and About say "Up to date" only after a successful check in the last 24 h with checks on (`checkStatusWords`): otherwise "Update checks are off", "Can't check for updates since … · last tried …", "Last check failed <time>", "Last checked <day>" or "Not checked yet". The terminal hint's failing line names the install script only for the binary it manages; any other copy is told to update the way it was installed.

**Store** (`packages/shared/inbox/`, one writer: the server process).
- Layout under `inbox/`:
  - `projects/<key>/` holds `project.json`, `messages.jsonl`, `questions.jsonl`, `annotations.jsonl` and `cards.jsonl` (the Board's cards; see "The Board") (an older store's `decisions.jsonl` stays there, kept only so sequence numbers are never reused; see "Decisions were removed"). `<key>` is the project name plus 6 hex of the root's hash. A key that collides takes more of the hash.
  - `blobs/<sha256>` holds sent attachment versions, the images messages show (`inline_images`) and guided-review snapshots.
  - `seq.json` holds the highest seq across deletions.
  - The Pi and OpenCode connections keep `claims/<reply id>/` (delivery claims), `connection-tools.json` (the last tool list) and `leases/<host>-<session>.json` (which process of a session delivers).
  - The Claude Code mod keeps its claims and lease under `claude-code-mod/<session>/inbox/`.
  - `pins.json` holds the threads pinned to the sidebar, in order (outside the log; see "Pinned threads").
  - Compose keeps `drafts/<drf_id>.json` (drafts, outside the log), `uploads/pending/<upl_id>.json` (uploads not sent yet) and `uploads/<att_id>/<name>` (sent uploads: read-only copies of their blobs). See "Compose".
- A project is the repository (the git toplevel of the path an agent names) or the folder, with one fold: a LINKED git worktree (`git worktree add`, including Claude Code's `.claude/worktrees/agent-…`) files under its main repository's project, for new messages (owner approval "inbox-project-menu", separate small change, 2026-10-14). One module decides it, `packages/server/inbox-project-root.ts` (`createInboxProjectRoots`, one cache shared by sends and New message's live sessions, so they always agree):
  - The path is taken by its realpath (`folder`); not an existing absolute folder is `validation_error`. Not in a git work tree (no git, not a repository, inside `.git`, a worktree whose main repository was moved or deleted, since git cannot open it): the folder.
  - One `git rev-parse --show-toplevel --git-dir --git-common-dir` in the folder. A linked worktree is git's own layout: its git dir is `<common dir>/worktrees/<id>` (realpaths). Otherwise (a plain checkout, a submodule, whose git dir is its own common dir, a `--separate-git-dir` main checkout) the toplevel is the project, as before.
  - The main worktree of a linked one: `<repo>` for `<repo>/.git`; else a bare repository (`rev-parse --is-bare-repository` in the common dir) is the project itself, or the folder holding it when it is named `.bare` or `.git`; else the work tree git records for the common dir (`core.worktree`, how a submodule's own worktrees point at its checkout). A candidate counts only when git, asked from it, names it as its toplevel and the same common dir; anything else (a separate git dir with no work tree on record, an answer of the wrong shape, a git before 2.5 that echoes `--git-common-dir` back) keeps the worktree's own toplevel.
  - Every path is compared by realpath, both sides (symlinked spellings, macOS `/tmp`). Each git is `inboxGitRunner`: `rev-parse` only, killed at `INBOX_PROJECT_ROOT_GIT_TIMEOUT_MS` (3 s), `GIT_TERMINAL_PROMPT=0`, and `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT` and every `GIT_CONFIG_KEY_<n>` / `GIT_CONFIG_VALUE_<n>` cleared (`INBOX_PROJECT_ROOT_GIT_ENV_CLEARED`), so an Inbox started with them exported still asks each folder's own repository with its own config. Answers are cached per folder (at most 512), used as they are for `INBOX_PROJECT_ROOT_TTL_MS` (60 s) and then once more while a background refresh runs, so only the first sight of a folder waits on git. No git installed is an answer (exit 127: the folder is the project, as before).
  - A git that ran past the time limit gives a guess (the folder, or a worktree's own toplevel), marked `settled: false`, used once and never cached. `resolveProject` (`packages/server/inbox.ts`) never makes a project from a guess, because the store keeps every project forever: it takes an existing project at that root, else the existing REPOSITORY project whose root holds the folder most closely (`nearestProjectHolding` over projects whose root has a `.git`, read from disk without git; a folder project such as one at `~` never takes a guess, or a new worktree under it would be filed there for good), else it refuses with `project_unresolved` ("…git did not answer in time. Nothing was sent or saved; try the same call again.", `503` on a window route). Every MCP tool that takes `project_path` (send_message, submit_guide, read_thread, wait_for_reply) answers it as an `isError` result `project_unresolved: …`, which the stdio shim, the Claude Code mod (`deny`) and the Pi / OpenCode connections hand the agent as it is; nothing was written, so the retry (same idempotency key included) lands once.
  - A message sent from a folded worktree keeps the folder it was sent from as its `base_path` though it lies outside the project's root (`sendBasePath` in `inbox-mcp.ts`, through the context's `projectRootOf`), so relative images and attachment links resolve where the agent works. Attachments were already recorded by absolute realpath, relative to `project_path`.
  - Existing projects keyed by a worktree are never rewritten (the store is append-only): their threads, `reply_to` into them and their routing stay as they were. Routing reads only the `project_id` recorded on each message line, never a path, so a replay routes exactly as before.
  - After the upgrade, for an agent in such a worktree: its next plain send (no `reply_to`) starts a new default thread in the main repository's project, which is created then if no agent wrote from the main checkout yet (the old worktree project stays in the sidebar until it is archived and hidden). An idempotent retry that spans the upgrade lands in the main project (keys are per project). Thread reads still find the old threads: `read_thread`'s list and `wait_for_reply` without ids scope by `threadReadScope` (`inbox-mcp.ts`), the resolved project PLUS the project an older Inbox kept for that very worktree (`store.projectByRoot(<worktree toplevel>)`), so an agent that asked before the upgrade (an MCP-only agent in `~/.codex/worktrees/…`, whose shim always fills `project_path`) still gets the person's reply. Chosen over scoping by session alone, which would change what a session sees when it names another repository's `project_path` and does nothing for `asked_by: "anyone"`; the legacy project joins only for a path inside that worktree, so a read from the main checkout is unchanged.
- A project's `name` on every read (rows, threads, the project list, Storage, the event stream, the MCP tools, a push) is the real name of its folder, read from its stored `root` (`inboxProjectLabels`, `packages/shared/inbox/project-name.ts`); when two folders share a name each also names its parent ("api · work"). The stored `name` and the folder `key` stay the `sanitizeTag` slug, which also names plan history and the feedback archive, so nothing on disk is rewritten.
- Every line is a full snapshot `{ v, seq, at, kind, id, record }`. The last line per id is current. Nothing is rewritten in place, and fields are only added.
- `seq` is one counter across the Inbox. The union of lines by seq is the event log that the window's stream and `wait_for_reply`'s cursor read.
- A torn last line is skipped on read, and a newline is appended before the next write to that file.
- No storage caps.
- Records are snake_case with `msg_`, `prj_`, `ses_`, `att_` and `dec_` ULIDs.
- Questions:
  - A question record keeps Workspaces' `Question` wire fields beside Plannotator's `QuestionAnswer` v1 (`packages/core/inbox-types.ts`).
  - State (`open | picked | sent | closed | superseded`) is derived, never stored. `superseded` (the question record's additive `superseded_by: { message_id, key | null }`) wins over `closed`; see "Replaced questions".
  - `Stopped:` and `Holds up:` lines are read as Workspaces reads them (`packages/core/inbox-questions.ts`, over core's `findQuestionBlocks` and `parseQuestionBlock`, so keys equal the card's), with one guard Workspaces' parser is to add as well: a `Stopped:` value or `Holds up:` entry that is only a negative word (no, none, n/a, na, nothing, false, nil, null, a dash; any case, trailing punctuation allowed) is no stop and holds nothing up (`isNegativeWaitValue`). Anything else still stops, an empty `Stopped:` and `No; I need the DB password first` included. Records keep the value read at send time.
  - The contract lines and picture choices (see "Contract lines and picture choices" under "Question blocks") are read by core's parser at send time and kept on the record as additive `parsed.stakes`, `parsed.shows { kind, label, src }`, `parsed.why`, `parsed.reversible { value: false, why | null }` and `parsed.choices[].image { alt, src }`, each only when present (`contractFacts` in `packages/core/inbox-questions.ts`), and served on the wire question (`InboxQuestionContract`; `toInboxQuestion`). No backfill: older records lack them and the card reads the body anyway. A record from before picture choices that kept `![B](b.png) B` as a label also answers to the card's plain `B` (`storedChoices` through `questionLabelWithoutImage`, the #2139 `Context:` precedent; `STORED_CONTEXT_SPLIT_RE` also splits at a contract label an older build joined onto a bullet). Choice pictures and a `Shows:` picture are ordinary markdown images of the body, so the send-time capture (`inline_images`) and the message image route take them like any other, and send_message / submit_guide name one that will not show (`images_not_shown`). Their result also nudges, never refuses: a question that is Stopped or Holds up with no `Stakes:` line adds `noStakesText` to the text and `no_stakes: [keys]` to `structuredContent`. Likewise a question written with a recommended marker in a choice label (`(Recommended)`, `[Recommended] Foo`; read or, with two on pick one, not; with or without a `Recommended:` line: `ParsedQuestion.recommendedMarker`, `inboxQuestionKeysWithRecommendedMarker`) adds `recommendedInLabelText` and `recommended_in_label: [keys]`. Taught only in send_message's `body` description (`SEND_BODY_DESCRIPTION`, one example `INBOX_CONTRACT_EXAMPLE` and the rule "Most questions need none of these"), the connection's short `body` (`INBOX_AGENT_FIELD_DESCRIPTIONS`) and `plannotator inbox --help` ("Decision lines and picture choices"). In the thread the card's pictures are not the body's image buttons (`img[data-question-picture]` is skipped by `MessageBody`'s image wiring): the tile's picture picks and its zoom button opens the thread's viewer. Tests: `packages/shared/inbox/store-question-contract.test.ts`, `packages/server/inbox-question-contract.test.ts`, `packages/server/inbox-recommended-marker.test.ts`, `tests/e2e/inbox-picture-choices.spec.ts`.
- Idempotency:
  - An agent's send is idempotent on its `idempotency_key`. The key is checked before routing. Another body, `reply_to` or thread name under the same key is `409 idempotency_key_reused`.
  - A person's Send is idempotent on its own key.

**Threads and the project filter** (the row model, owner ruling 2026-10-07). A row is a thread. The project is a label on the row and a filter (the sidebar's folders), never the row. `send_message` routes in `InboxStore.sendMessage`, and the first match wins:
1. `reply_to`: that message's thread, as a reply.
2. `thread`, a name:
   - Validation: trimmed, 1 to 120 characters, with no control characters, line breaks or bidi controls, and something visible. Anything else is `validation_error: thread: …`.
   - It joins the newest OPEN thread of that name in the project, across sessions. With none open, it starts a new thread under the name.
   - Names compare by `inboxThreadNameKey` (NFKC, default-ignorable code points dropped, whitespace runs as one space, case folded), so look-alike spellings are one thread. The stored name keeps the first sender's spelling.
3. Otherwise, the sender session's default thread: the newest UNNAMED thread that `agent_session` started in the project while it is open, else a new thread. A sender with no `agent_session` starts a thread with each message.

More rules:
- Resolved means done: the next message starts a new thread. A resolved thread still takes `reply_to` replies.
- A thread keeps its first message's subject, except that a subject derived from a question (the agent gave none) follows that question's replacement, down the `superseded_by` chain (`InboxStore.threadSubject`; the root's additive `subject_question` names the question, and a root older than it counts as derived when its subject is its first question's prompt). An agent-given subject never changes, and a question withdrawn with nothing in its place keeps the subject it gave.
- A subject is one line of plain text. send_message and submit_guide refuse one with leaked tool-call text (`</subject>`, `</parameter>`, `<parameter name=`, `<invoke name=`, `</invoke>`, `<function_calls>`, `antml:`-prefixed tags), a line break, a control or a bidi character with `validation_error: subject: …` before anything is written, so a corrected retry under the same `idempotency_key` lands once (`checkInboxSubject`, `@plannotator/core/inbox-types`; checked in `sendProject`/`sendAgentMessage` and again in the store; ordinary `<` / `>` in prose stays allowed). Subjects an older Inbox kept verbatim are never rewritten on disk: every read serves them through `displayInboxSubject` (first line, cut where such markup starts, controls and bidi dropped, trimmed) at the one funnel `InboxStore.threadSubject` plus a root's wire record, search's fallback, the event stream's message lines and the relay push, so the window, the phone, notifications and agents (read_thread, wait_for_reply, search) all get the cleaned subject.
- Routing reads only the log: two indexes (`sessionThreads`, `namedThreads`) are rebuilt from each root's first line in seq order. A replay therefore routes exactly as the live store did, and an older store with no `thread_name` replays unchanged.
- Routing is synchronous inside the server process, so racing sends land in one thread.
- `read_thread`'s list mode lists the threads the session sent in (`asked_by: "me"`), and `wait_for_reply` with no id waits on those threads.
- Without a cursor, a reply counts when it comes after the caller's last message in the thread.

**The list** (`packages/shared/inbox/list.ts`, pure; labels in `INBOX_SECTIONS`, `packages/core/inbox-types.ts`). The sections, in order: Stopped on you, Holding up work, Waiting on you, New since you looked, Sent, Quiet. Sent sits below New because it waits on the agent, not on the person (owner ruling 2026-10-11). The strongest reason wins:
1. Archived (resolved) and not come back: Quiet. The window leaves archived threads out of the list altogether (see "Archived" below); the list model places them in Quiet only for callers that do not ask for them apart. A thread that came back (an agent wrote after the archive and something there still waits, `back_from_archive`) is placed by the rules below like an open thread.
2. Marked read (Mark read) and no message since but its set-aside note: Quiet, unless unsent work waits and no Re-ask note waits (rule 9).
   After it, before rule 3 (rule 2a of the thread-state model; owner's rule, approval "inbox-reask"; see "Re-ask"): every open question is listed in a Re-ask note that still waits: Sent, whether or not the agent read the note (`reask_pending` on the row). A note waits until the session it went to (its `to`, else the asker) writes again, and only while a question it lists is still open; another session's new question, or the listed questions answered, superseded or closed by anyone, ends it, so a session that never writes again cannot hold the thread in Sent.
3. An open question with `Stopped:`: Stopped on you.
4. One with `Holds up:`: Holding up work.
5. Any other open question: Waiting on you.
6. Picks saved but not sent: New since you looked ("Answered, not sent").
7. The person's reply is the last message and no agent has read it: Sent. The Inbox's own notes (the set-aside and reopened notes below) are read past here and everywhere the list derives from the person's messages: they are neither a reply nor a look (`isInboxNote`).
8. Agent messages after the person's last look: New since you looked.
9. Unsent work (the row's additive `unsent`, see "Reply drafts and the Draft label"): words typed in the reply box, picks not sent, or comments waiting for a Send: New since you looked. A thread holding any of it never sinks to Quiet unless it is archived (rule 1 wins: archiving is the person's explicit "done", and the draft is kept). A Re-ask note that waits (rule 2a) keeps the row in Sent, after a Mark read in Quiet, as without a draft; the row still shows its Draft label. Agents never see this rule: `read_thread`'s list gives them the section without it.
10. Anything else: Quiet.

Sorting and the rest:
- Every section sorts newest first by the thread's latest message (`last_at`, the time the row shows); ties on the thread id (owner ruling 2026-10-08).
- `unread` (bold) means Stopped, Holding, Waiting or New, except a row in New only for the person's own unsent words or comments (no unseen agent message, not "Answered, not sent"): not bold, and not counted as waiting on the person (the sidebar's Drafts row counts it).
- "Looked" is `POST /api/inbox/threads/:id/seen`, sent when a thread opens (capped with `through_seq` at the newest agent message the window read, so one that lands before the server takes the look stays new) and again when a message that arrived while the thread was open has been seen on sight (see "Seen on sight"). The person's own reply also counts; the Inbox's notes do not.
- "The agent read it" is recorded when `wait_for_reply` returns the person's reply or `read_thread` reads the thread, which moves a Sent row to Quiet. Any agent's read counts.
- `?project=prj_…` keeps the sections and drops other projects' rows.
- The list is linear in the store: about 10 ms for 4,000 threads.

**The thread-state model**: `adr/implementation/inbox-thread-state.md` (sections, events, the transition table, invariants, the violations it found and their fixes), checked by `packages/shared/inbox/store.test.ts`, with trace fixtures for the phones in `packages/shared/inbox/fixtures/thread-state/v1/`.

**Archived** (owner ruling 2026-10-12: "Archived messages should move out of the Quiet list … only visible within a panel on the Settings page … the ability to unarchive them").
- **Came back** (mail apps' rule). An agent's `reply_to` reply into an archived thread lands after its archive line. Messages after that line behave as an open thread's; messages before it stay as the archive left them; the thread stays resolved (`resolved_at` kept) until the person acts, and nothing unarchives it implicitly (not even a Send: that would reopen the archive-closed questions and change the agent's default-thread routing).
  - The line: the store keeps, per root, the seq of the root line that set its current `resolved_at` (`resolvedSeq`, rebuilt in seq order by every replay and cleared by `reload`; a look or any other root rewrite with the same `resolved_at` does not move it). `closedByArchive(message)` = the thread is resolved and the message's first line is before that seq. Derived, never written.
  - One question state everywhere: `InboxStore.questionWire(record)` / `questionsOf` read a question as `closed` only when the archive closed its message. The window's thread, the event stream (`eventPayload`, so notifications and the question sound fire), and the relay push (`pushFor`, so the lock-screen answer is offered) all use it. Writes follow the same rule (`messageAnswerable`): picks, Send, and annotations on a message's attachments or guided review are taken for a message after the line and refused (`409 thread_resolved`) for one before it. New message stays refused on an archived thread (the window hides it). The agent side: `read_thread`'s list and `wait_for_reply` treat a thread with an agent message after the line (`agent_after_archive`) as open, so the person's answer reaches the waiting agent, and a seen-line rewrite no longer ends a wait as "resolved".
  - The row: `agent_after_archive` (an agent wrote after the line) and `back_from_archive` (that, and something still waits: an agent message after the line the person has not looked at, a live question open or picked, or the person's reply after the line the agent has not read). While `back_from_archive` the thread is in the list, placed as an open thread would be (New since you looked; Waiting, Holding or Stopped when it asks; Sent after the person replies) and out of the Archived block; once handled it returns to the archive by itself. Questions the archive closed stay closed, so a plain update comes back as New, not Waiting.
  - The window (`Thread.tsx`, from the thread read's additive `archive_seq`): cards, Reply and comments on files and guides are live for messages after the line; the foot carries "Archived · <agent> wrote after you archived it. Your reply goes to it; the thread stays archived." with **Unarchive** above the reply actions (`data-came-back`). Mark read works on what came back (`canToggleRead` / `offersRowMarkRead` accept `agent_after_archive` / `back_from_archive`): it sets aside the post-archive questions (the agent is told once, as for any Mark read), the thread goes back to the archive, the toast says "went back to Archived", and Undo brings it back.
  - Archiving again after the reply (Unarchive, then Archive) writes a new archive line after it: archived again. Unarchive drops a Mark read made while the thread was archived (`person_read_seq` after the archive line, cleared in the same root line, so a replay agrees): it covered only what came back and must not hold the reopened thread in Quiet over the questions the archive had closed. A Mark read made before the archive is kept.
  - The "person reply the agent has not read" that keeps a thread back ignores the Inbox's own notes (Mark read's set-aside note and its Undo's reopened note), as `readAt` does, so Mark read on what came back leaves it in the archive.
- The window's list holds no archived (resolved) thread in any section, Quiet included. It asks `GET /api/inbox/threads?archived=exclude`, which drops them from the sections. Without the parameter (`archived=include`, the default) the list model is unchanged: archived threads stay in Quiet. That default is for the phone: the door forwards `GET threads` to this route as it is, and an iPhone app that draws the sections natively keeps every thread it had, with no new release needed; an older window keeps working too. The sidebar's folder counts never counted archived threads (they count rows waiting on the person) and are the same either way.
- `GET /api/inbox/threads/archived` (`?project=`, `?offset=`, `?limit=` 1 to 200, default 50, `INBOX_ARCHIVED_PAGE`) lists them newest archived first (`resolved_at`, ties on the thread id; `inboxArchivedRows` in `list.ts`), with `total` in the filtered scope and `projects: [{ id, name, archived }]` (every project with archived threads). The door has an explicit allowlist row for it (`GET threads/archived`, read only, before `threads/:id`), so a phone can read it too.
- Settings' **Archived** block (`packages/inbox/components/Archived.tsx`, above "Stored on this machine"): "N archived threads", then one Settings row per archived thread (the agent's mark, the thread chip, the subject; then the agent, "Archived <day>", the message count) with **Unarchive**. When more than one project has archived threads the rows sit under a small header per project with its count ("billing · 2"), the projects in the order of their newest archived thread; there is no dropdown (the owner asked for no native select). 50 rows across the whole list, then "Showing 50 of N" and "Show 50 more"; "Nothing archived." when empty. It reads again whenever the store's cursor moves. Unarchive is the thread's resolve `false`; the window then opens the thread in the main list (`#thread=`, in whatever section its state puts it) with the toast "Back in your Inbox · “subject”" and Undo (archive again).
- Archiving from a thread keeps its toast and Undo. While that thread stays open its row keeps its place in the list, shown archived ("Archived", not bold: `markHeldRowArchived` in `held.ts`), and leaves the list when the person leaves the thread (the held-order rule). A deep link `#thread=` to an archived thread still opens it, with "Archived … · Unarchive" in its foot; its row, which the list no longer carries, comes from the thread read's additive `row`.
