## Archive Flow

```
User runs plannotator archive (CLI)
        ↓
Server starts in mode:"archive", reads ~/.plannotator/plans/
        ↓
Browser opens read-only archive viewer
        ↓
User browses saved plan decisions with approved/denied badges
        ↓
Done → POST /api/done closes the browser
```

During normal plan review, an Archive sidebar tab provides the same browsing via linked doc overlay without leaving the current session.

## Server API

**The app and its chunks (plan, review, annotate and goal-setup servers; Bun and Pi).** A route no handler claims answers the app page (SPA). Under `/assets/` it answers instead the chunk or asset packed behind the page with exactly that name (`openPackedApp` in `packages/shared/packed-app.ts`; Pi's `serveApp` in `apps/pi-extension/server/helpers.ts`): `GET` / `HEAD` only (else `405`), from memory with no filesystem path, its own `Content-Type`, immutable caching (names carry Vite's content hash), `nosniff`, same-origin CORP; any other name `404`. Remote and `--tailscale` sessions compress text chunks like the page (#1617). Code review's `/assets/diagram-engine/` route answers before it.

### Review Server (`packages/server/review.ts`)

| Endpoint              | Method | Purpose                                    |

| `/api/diff`           | GET    | Returns `{ rawPatch, gitRef, snapshotId, origin, mode?, diffType, base, hideWhitespace, gitContext, agentCwd?, approvalNotesSupported, semanticDiff?, callFlow?, sections?, commitInfo?, generatedFiles?, baseBehindRemote?, title? }`. `title` is the caller's `plannotator review --title` (#2289), absent without one; the page shows it as the whole tab title in place of `<repo> · Code Review`. `snapshotId` identifies this diff snapshot; the client echoes it on `/api/diff/fresh` probes (also returned by the switch/PR endpoints). `approvalNotesSupported` is the approve-with-notes capability advert (echoed on `/api/diff/switch`, `/api/pr-diff-scope`, and `/api/pr-switch` too, so it survives a diff switch); absent reads as false. `sections` is the since-base sidecar (Committed/Changes/Untracked partition); `commitInfo` is the commit-metadata sidecar (subject, markdown body, author + avatar) present only while a `commit:<sha>` (or jj `jj-commit:<commit id>`) diff is active; `generatedFiles` lists the repo-relative paths that count as generated, which the client collapses by default GitHub-style (presentation-only: the patch is never filtered). All servers use random ports locally or fixed port (`19432`) in remote mode.

**Stale-tab guard (`serverSession`).** Because a port can be reused (a fixed `PLANNOTATOR_PORT`, remote mode's `19432`, a rare random-port collision), a tab left open on an old session could post its decision to a NEW server on the same address and approve a document it never showed. Every plan, annotate and review server (Bun and Pi) therefore issues one random `serverSession` nonce per process (`packages/core/server-session.ts`, vendored to Pi) and advertises it on `/api/plan` and on every diff payload (`/api/diff` and the switch/PR endpoints, beside `approvalNotesSupported`). The client (`packages/ui/utils/serverSession.ts`) echoes it on every decision: `serverSession` in the body of plan `/api/approve` + `/api/deny`, annotate `/api/approve` + `/api/feedback`, review `/api/feedback` (the platform status post included), and as `?serverSession=` on `/api/exit` (whose body is empty). A server holding a DIFFERENT nonce answers `409 { code: "session_mismatch", error }` before it claims or settles anything, and the tab shows `ServerSessionReplacedBanner` ("This review was replaced — reload"). A decision WITHOUT the field is accepted, so an older client (and any host posting decisions by hand) keeps working; only a present, different nonce is refused. `/api/pr-action` (which posts the review to GitHub, GitLab or Bitbucket) carries the nonce in its body too and is guarded the same way in both runtimes: a mismatch posts nothing and the tab shows the same banner. So is annotate's `POST /api/source/save` (Edit Mode writing a file, single-file, folder and bundle sessions): the body carries `serverSession` and a mismatch writes nothing. So is `POST /api/open-in` on the annotate and review servers (both runtimes, after its same-origin check): a mismatch launches nothing. That route also requires an `appId` from the open-in catalog: a missing or unknown one is `400`, and there is no fallback to the OS default handler, which could run the file. Open-in is also off in a session published with `--tailscale` (Bun only: `exposed` on `handleOpenIn` / `handleOpenInApps`, from `tailnetPublished`), exactly as in remote mode: the apps list answers `{ available: false }` and a launch is `400`, since other devices reach the session (the update route's `update_exposed` rule). The same nonce guards the other routes that write files or start and stop processes, both runtimes: `POST /api/save-notes` on the plan and annotate servers (writes into an Obsidian vault, opens `bear://` / `octarine://`; body), `POST /api/plan/vscode-diff` (opens an editor; body), and the review server's agent jobs, `POST /api/agents/jobs` (body; `serverSession` is a known launch field) and `DELETE /api/agents/jobs[/:id]` (`?serverSession=`). The clients send it (`ExportModal`'s default notes wire, plan review's auto-save and quick save, `PlanDiffViewer`'s default VS Code wire, `useAgentJobs`; each a no-op for a `@plannotator/ui` host that never adopted a nonce). Each of these handlers also runs `isSameOriginOrNoOrigin` itself, so it is safe wherever it is mounted. `saveToObsidian` refuses a folder setting with a `..` segment (`obsidianFolderEscapesVault` in `packages/shared/integrations-common.ts`), so the note is always written inside the vault; the vault itself must already be an existing directory, as before, and is not restricted further (a custom path that is not a detected vault keeps working).

**A decision that does not land (#1392).** When a decision POST fails (fetch rejects because the server stopped, or it answers a non-2xx that has no screen of its own: not `409 session_mismatch` or plan review's `409 plan_revised`), the page stays exactly as it was and shows one toast, `showSendFailureToast` (`packages/ui/components/SendFailureToast.tsx`): "Feedback not sent" / "Approval not sent", why (`describeSendFailure` in `packages/ui/utils/sendFailure.ts`: not running or not reachable, the status, or already decided), **Retry** (runs the same handler with the same options again, from the page as it is now) and **Copy feedback** (read when clicked, so it copies what Retry would send now, in the form the page's own Copy feedback uses: plan deny and annotate feedback through `wrapCopiedFeedback`, approvals with notes and review feedback as sent; absent for a bare approval or a Done with nothing to send). The annotate and review servers (Bun and Pi) refuse a decision on a review already decided (another window sent first, or the agent closed it) with `409 { code: "already_decided" }`, as Pi's plan server does once the session that opened it ended; the toast then says so and offers no Retry, and plan review no longer reads Pi's closed-session 409 as "The agent revised the plan" (only `code: "plan_revised"` is a revision). Each handler brackets its send with `sendStarted()` / `sendSettled()`: a send starting takes the toast down, Retry does nothing while a send is in flight (the Bun plan server has no already-decided check, so a second deny would run the integrations and the archive twice), and the toast goes when the review is decided. The handlers tag the failure with `.catch(throwUnreachable)` on the fetch and `await assertSendOk(res)`: plan review, annotate and annotate-last (feedback and approve), code review (send feedback and approve). Plan review's approve and deny used to show the Approved / Feedback Sent screen on a 500. Drafts are not involved: annotations already autosaved to the server's draft come back when the same file is opened again, and the open page keeps everything in memory. Client-side apart from the `code` on the refusal, so the Pi extension (which serves the same built HTML) gets it too. Not covered: `/api/exit` (Close, which sends nothing) and the platform status post after a PR review was posted (fire-and-forget by design).

### Cross-origin write guard (every state-changing request)

Every plan, review, annotate and goal-setup server (archive and the servers OpenCode embeds included), Bun and Pi, refuses a `POST`, `PUT`, `PATCH` or `DELETE` that a page on another site sent, right after the Host allowlist and before any route: `403 { ok: false, error, code: "cross_origin" }` (`refuseCrossOriginWrite` in `packages/server/request-origin-guard.ts`, Pi mirror `apps/pi-extension/server/request-origin-guard.ts`, over the shared pure `isSameOriginOrNoOrigin` + `isStateChangingMethod` in `packages/shared/request-origin.ts`). A page on another site can send a preflight-free `text/plain` POST, and every JSON route parses its body whatever the content type, so before this a page that knew the port could reach every route that writes, decides or launches (plan approve without a nonce, review feedback, `/api/git-add`, `/api/pr-action`, Ask AI sessions, external annotations, agent jobs). The rule: refused when the browser marked the request `Sec-Fetch-Site: cross-site` or `same-site` (whatever Origin says, present, absent or matching: another localhost port is `same-site`), or when Origin is `null` or names another host; passed with no Origin and no such fetch metadata (agents' curl, the VS Code extension host, the Claude Code mod's `$.http.fetch`, the pull bridge and host control, which already require no Origin), with an Origin naming the request host, or with `Sec-Fetch-Site: same-origin` (the VS Code panel's cookie proxy, and a reverse proxy that rewrites Host when the page is served over HTTPS or from localhost). Browsers send `Sec-Fetch-Site` only to HTTPS and localhost origins: over plain HTTP to any other address there is none (measured in Chromium, Firefox and WebKit), so behind a plain-HTTP reverse proxy that rewrites Host (nginx's default `proxy_pass http://127.0.0.1:<port>` with no `proxy_set_header Host`) the page's Origin names the proxy and Host names the upstream, and nothing marks the request as the session's own. For that case an Origin whose hostname `PLANNOTATOR_ALLOWED_HOSTS` names EXPLICITLY (an exact entry or a `.suffix` entry) also passes, unless the browser sent fetch metadata (`isOriginNamedInAllowedHosts` in `packages/shared/request-host.ts`, the same allowlist parsing as the Host check; read on each request). `*` never widens it: a `*` that turned the Host check off does not turn this guard off. The route-level checks on `/api/save-notes`, `/api/plan/vscode-diff` and the agent jobs use the same helper (`isSameOriginRequest` in each adapter); the older per-route checks below use `isSameOriginOrNoOrigin` alone, as before, so those routes (config, review progress, guide share links, the CallDiff install, source save, open-in, update) still refuse a plain-HTTP Host-rewriting proxy, which they already did. GET, HEAD and OPTIONS are left to their routes, and so are WebSocket upgrades (GET; the agent terminal's carries a per-session token in its path). The per-route checks that predate it (config, review progress, guide share links, the CallDiff install, source save, open-in, update) stay. Not covered, by design: GET routes that start read-only work (`/api/semantic-diff`, `/api/call-flow`, `/api/agents/capabilities` and `/api/ai/capabilities?activate=` model discovery), which another site can trigger but not read or steer; the Inbox does not run this guard ahead of its routes (it has its own guards, see "Security" under "Plannotator Inbox"), but its window writes use `isSameOriginOrNoOrigin`, so the stricter rule (cross-site or same-site fetch metadata refused even without an Origin) applies there too, harmlessly, since its window is always same-origin; the live-app proxy (its own Host, Origin and WebSocket-origin checks). Tests: `packages/server/state-route-guards.scenarios.ts`, run by `packages/server/state-route-guards.test.ts` (Bun) and `apps/pi-extension/server/state-route-guards.test.ts` (Pi).

### Host allowlist (every request)

Every plan, review, annotate (archive and goal-setup included, and the servers OpenCode embeds) server, and the Plannotator Inbox (always the local rule: `createRequestHostGuard({ localOnly: true })`), checks the request's `Host` header BEFORE any route, in both runtimes: the app HTML, every API and every WebSocket upgrade. The rule is one pure predicate, `isAllowedRequestHost` in `packages/shared/request-host.ts` (vendored to Pi); the adapters are `packages/server/request-host-guard.ts` (Bun, first lines of each `fetch`) and `apps/pi-extension/server/request-host-guard.ts` (node:http, first line of each handler, plus an `upgrade` interception, because node:http hands an upgrade to every `upgrade` listener, such as the annotate agent terminal's). Why: `isSameOriginOrNoOrigin` compares Origin with Host, which cannot tell the session's own page from a page served under another DNS name that resolves to this machine (both carry matching Origin and Host), and most GETs had no check at all. IP literals and loopback names cannot be re-pointed by DNS, so the allowlist is built from them:

- **Every mode:** loopback names: `localhost`, `*.localhost`, `127.0.0.0/8` literals, `[::1]` (`isLoopbackHostname`).
- **Remote mode** (`PLANNOTATOR_REMOTE` / SSH, wide bind): also any IPv4 or IPv6 literal (LAN or container address), the configured urlHost (`auto` resolved through the same cached Tailscale lookup the advertised URL uses), the hostname of the configured public URL (`PLANNOTATOR_PUBLIC_URL`, for a reverse proxy that forwards the browser's Host), and this machine's `os.hostname()` (full name, first label, and `<first label>.local`, the mDNS name another LAN device types, which `os.hostname()` omits on Linux and often on macOS; mDNS answers on the local link only, so it cannot be pointed here from outside the network). These names are resolved lazily, on the first request that is neither loopback nor an IP literal.
- **`--tailscale`** (local mode, Bun CLI only): `tailscale serve` forwards the browser's own Host (the MagicDNS name; for TCP backends it sets `r.Out.Host = r.In.Host`), so `enableTailscaleServe` registers the serve URL's hostname with `allowServedHostname` once serve reports it (not for the Inbox's persisted mapping, which points at a door-only listener that reads no Host).
- **Browser IDE port proxies** (every mode): code-server and Coder set `VSCODE_PROXY_URI`; when its HOSTNAME holds the `{{port}}` template (`https://{{port}}--main--ws--me.coder.example.com/`), the per-port hostname (`<digits>` in the template's place, nothing else) is allowed (`forwardedPortHostPatterns`). Such a proxy reaches the loopback-bound server and forwards its own Host. The value comes from the environment the IDE started and names the IDE's own proxy domain, never a request. A path-based template (`./proxy/{{port}}/`) adds nothing. GitHub Codespaces and VS Code dev tunnels need no rule: their forwarders present `Host: localhost:<port>` (the browser's name rides in `X-Forwarded-Host`, which is never read). No provider domain (`.app.github.dev`, `.gitpod.io`, `.devtunnels.ms`) is built in: the forwarders that matter present loopback, and a blanket suffix would admit every other tenant's forwarded hostname for no gain.
- **`PLANNOTATOR_ALLOWED_HOSTS`**: extra names (a `:port` on an entry is ignored), `.suffix` entries, or `*` (off). See the env table.
- **No Host header** (an HTTP/1.0 non-browser client): allowed; browsers always send one. A malformed Host is refused.
- **The port is never compared.** Forwarded ports legitimately arrive with another port (`ssh -L 8080:localhost:19432`, VS Code / devcontainer auto-forwarding to a loopback-bound server when the local port is taken, `docker -p`), and a foreign name is refused by its hostname alone. The VS Code cookie proxy rewrites Host to the upstream's `localhost:<port>`, a loopback name. The narrower loopback-AND-port checks of the pull bridge and host control stay as they were, behind this one.
- **Refusal:** `403`, `text/plain`, `X-Plannotator-Error: host_not_allowed`, a one-paragraph body naming the hostname (only when it parses as one) and `PLANNOTATOR_ALLOWED_HOSTS`; never a 404, so it cannot be mistaken for the app catch-all.

Not covered, by design: the Inbox's tailnet listener ("Over your tailnet": it answers only the served MagicDNS name and the owner's Tailscale login, and never hands on `/mcp` or a connection route), the live-app proxy (`live-proxy-core.ts` has its own Host, Origin and WebSocket-origin checks), the compiled build's agent-terminal Node sidecar (`agent-terminal-node-sidecar.mjs`: bound to `127.0.0.1` on a port only the Bun server learns, never sent to the browser, and served only under the session's random-token PTY path; the browser's upgrade reaches the guarded annotate server first), the paste service (a public service, not a session) and the guides.show local static dev server (serves build output only). Tests: `packages/shared/request-host.test.ts` (the predicate), `packages/server/request-host.scenarios.ts` run by `packages/server/request-host.test.ts` (Bun, plus goal setup and the tailnet name) and `apps/pi-extension/server/request-host.test.ts` (Pi), and `apps/pi-extension/server/request-host-guard.test.ts` (the upgrade interception).

### File-browser live refresh (`/api/reference/files/stream`)

One engine for both runtimes, `packages/shared/file-browser-watch-core.ts` (vendored to Pi; transports `packages/server/reference-watch.ts` and `apps/pi-extension/server/file-browser-watch.ts`): construction deferred off the request path and a 30 s reconnect grace (#1313), so a reload reuses the warm watcher; an entry whose watching failed (could not start, or its root could not be watched: unreadable, gone, or no watches left; a deep folder hitting the system limit does not count) is rebuilt by the next subscription instead, its open tabs moved over. macOS and Windows use one native recursive `fs.watch`; Linux uses one `fs.watch` per folder (#1439), never per file. The Linux watcher: breadth-first scans, one at a time per subscription (a rename queues one re-list of its folder, plus a deep scan only when the name was a watched folder; the queue is deduplicated by walking up to the root, so a burst of 100k new files costs what #2155 did; Bun on Linux reports a move under one name only, which the re-list covers); symlinked folders are not followed; ignored folders (`isFileBrowserWatchExcludedPath`: the listing's `FILE_BROWSER_EXCLUDED` plus `.jj/`, which only the watcher skips) are never watched and never trigger a refresh; unreadable folders (EACCES) and folders whose watch fails are skipped, never fatal. A registry-wide budget of a quarter of `fs.inotify.max_user_watches`, kept between 1,024 and 8,192 (4,096 when unreadable): past it the folders nearest the root keep their watches (a new shallow folder takes the deepest watch's slot), deeper ones go unwatched, it is logged once per subscription, and a freed watch scans only the shallowest skipped folders, never the whole tree. Exact-file watches (the open document) are outside the budget. Tests: `packages/shared/file-browser-watch-directories.test.ts` (every platform, a fake filesystem and `fs.watch` through the `directories` backend and the `directoryFs` / `nativeWatch` seams) and `packages/shared/file-browser-watch-linux.test.ts` (real inotify, Linux only).

`GET /api/host/status` and `POST /api/host/close` (`packages/shared/host-control.ts`,
vendored to Pi; Bun adapter `packages/server/host-control.ts`, Pi adapter
`apps/pi-extension/server/host-control.ts`) let the agent session that launched a
review ask what it holds and close it. Guarded exactly like the pull bridge: a
loopback Host naming the server's port (`403`), no `Origin` (`403`), and
`Authorization: Bearer <token>` (`401`), the launch's `PLANNOTATOR_SESSION_BRIDGE_TOKEN`
(Bun default; servers also take `hostControlToken`). Without a token the paths answer
`404 { error: "Not found", code: "host_control_disabled" }` (`HOST_CONTROL_DISABLED_CODE`),
which a host reads as "turned off" rather than "an older Plannotator" (an uncoded `404`);
they are off in remote mode, and in a `--tailscale` session a request through `tailscale serve`
gets the same `host_control_disabled` answer (`fromThisMachine`; #2166). Unlike the pull bridge they still answer under
`PLANNOTATOR_AI=disabled` (closing a review is not an AI feature). Once a session is
decided (a host close included), the review servers refuse a late `/api/feedback` or
`/api/exit` with `409` (both runtimes, like annotate), so a tab still open after the
close neither deletes the kept draft nor gets an ok for feedback nobody receives.
Close settles the decision as `exit` with
`closedBy: "agent"` and `unsentAnnotations` (no draft delete, no feedback-archive
record: the reviewer decided nothing), broadcasts `{ type: "session-closed", by:
"agent", unsentAnnotations }` on the external-annotation stream (`broadcast` on both
runtimes' handlers; `useExternalAnnotations`'s `onSessionClosed`), and the CLI's
host result record carries the same `closedBy` / `unsentAnnotations` on its
`dismissed` record. Every server result also exposes `hostControl` (`status()`,
`close?()`) for hosts that run the server in-process (Pi, the OpenCode 2 embedded
plan server). Plan servers implement status only. A host that calls the endpoints
over HTTP reads the answers with `classifyHostCloseAnswer` / `readHostStatusAnswer`
from the same shared module (the OpenCode 2 tool); the Claude Code mod keeps its own
copy of that rule because a hooks module imports only its own folder.

## Plan Version History

Every plan is automatically saved to `~/.plannotator/history/{project}/{slug}/` on arrival, before the user sees the UI. Versions are numbered sequentially (`001.md`, `002.md`, etc.). The history slug is `{sanitized-heading}-YYYY-MM-DD`, scoped by project name (git repo or cwd), and is resolved by `resolveHistorySlug()` (`packages/shared/storage.ts`) so that the date names the day the chain STARTED, not today (#1679): an open server keeps its own slug for revisions whose heading is unchanged (`updatePlan`, Pi's and the Claude Code mod's); otherwise today's `{heading}-{UTC date}` directory is used if it already holds versions; otherwise the most recently written existing `{heading}-YYYY-MM-DD` directory of the project that is not dated after today is continued when its newest version file's mtime is within `PLAN_HISTORY_CONTINUE_WINDOW_MS` (48h); otherwise today's directory starts a new chain. So a plan revised across midnight (UTC or local) or resumed the next day keeps its version diff, every revision refreshes the window, and a same-heading plan after two quiet days starts fresh. Nothing on disk is renamed or migrated. Both plan servers (Bun and Pi) use it. The decision snapshots in `~/.plannotator/plans/` are named separately by `generateSlug()` (heading + the UTC date the plan arrived at the server, or of its latest in-session revision, unchanged), because `parseArchiveFilename` / `listArchivedPlans` read that date back; the feedback archive's `target.slug` names the history directory, matching its `planVersionFile`. Identical resubmissions are deduplicated (no new file if content matches the latest version).

**The project half (#2197).** `{project}` is the basename of the git toplevel (else the folder) that `detectProjectName()` finds. It is read from the CLI's cwd, which a shell `cd` moves between submits, so for Claude Code the session's root is also consulted (a workspace folder holding separate clones would otherwise split one plan into two chains of length 1): the mod reads `$.session.root()` once per session and sends it as `projectRoot` on `claude-mod-plan`'s stdin; the classic PermissionRequest hook uses `CLAUDE_PROJECT_DIR` (only for origin `claude-code`, never Gemini, which sets the same variable as an alias). Both reach the plan server as `ServerOptions.historyRoot` (ignored unless an existing absolute folder). `resolveHistoryChain(projects, slug)` (`packages/shared/storage.ts`) runs `resolveHistorySlug` for the cwd's project first and the root's project second, takes the first whose chain already holds versions, and otherwise starts a new chain under the cwd's project. So a plan started at the root and resubmitted from a nested clone continues its chain, while where a new plan lands does not change: a nested clone keeps its own plans (and their feedback archive records), and same-heading plans from two clones never merge. With no root, or a root equal to the cwd, the list is the cwd's project alone. Not covered: a plan started in a nested clone and resubmitted from the root or another clone (the clone is no candidate then; that needs the host to remember the plan's earlier folder). The root only affects which existing chain is continued (and so the feedback archive record, which names that history version); plan file trust, linked docs, `/api/doc` roots, `projectRoot` on `/api/plan`, `repoInfo` and the `sessions/` registry label keep the process's cwd. Other agents pass no root. Tests: `apps/hook/server/plan-history-root.test.ts` (the CLI as processes, both Claude Code paths), `resolveHistoryChain` in `packages/server/storage.test.ts`, the stdin in the mod's `controller.test.ts`.

This powers the version history API (`/api/plan/version`, `/api/plan/versions`) and the plan diff system.

**Annotate mode** also saves history on open, so the same version diff works when annotating a standalone `.md`/`.txt`/`.html` file (or any other supported plain-text file, e.g. `.yaml`/`.json`/`.toml`). It keys the slug by **file path** — `annotate-{sanitized-basename}-{hash8}` — rather than heading + date, so re-opening the same file groups its versions even as its content (and headings) change. **Note this writes a copy of each annotated file's content** under `~/.plannotator/history/` (or `PLANNOTATOR_DATA_DIR`); disable via `PLANNOTATOR_ANNOTATE_HISTORY=0` or `{ "annotateHistory": false }` in `~/.plannotator/config.json` to keep annotate sessions stateless (the version diff is then unavailable, and the durable submitted-feedback records described in the env-var table are also skipped). Single-local-file annotate sessions additionally write each submitted decision to `history/{project}/{slug}/submissions/{timestamp}.md` BEFORE deleting the annotation draft, so feedback survives an agent-side timeout (#678); a failed record write keeps the draft as the recovery copy. For `--render-html` files the diff is rendered as the real page with inline `<ins>`/`<del>` highlights via `htmlDiff()` (`packages/shared/html-diff.ts`).

**Live versions (#2037).** An open single-file Markdown/text annotate session already reloads the text in place when the file changes on disk (the editor's source-document reconcile over `/api/reference/files/stream`). That reload now also becomes a version, so the `+N/-M` badge and the Version Browser show an agent's edit in the same session instead of only after a reopen. When the session's OWN file's disk text lands on screen (`noteRootDiskText` in App: the watcher reconcile's `clean-updated`, "Reload from disk" after a conflict, and a save that found the file changed and reloaded it; linked and folder documents are not covered), and `/api/plan` advertised `liveVersions`, `useLiveAnnotateVersion` (`packages/editor/hooks/`) waits until the file has held still for `LIVE_VERSION_SETTLE_MS` (750 ms, so a burst of agent writes is one version) and posts `POST /api/plan/versions { serverSession, hash }`. The server (`saveAnnotateLiveVersion` in `packages/shared/annotate-live-version.ts`, vendored to Pi; the Bun and Pi routes only parse the body and answer) reads the file itself, saves it only while its bytes still have the hash the editor showed (`409 stale` otherwise, and the next change asks again), and runs the open-time pipeline (`computeAnnotateHistory`: dedupe against the latest version, then the one before it), keyed by the same resolved path as the open-time save. It also replaces the session's `annotateHistory`, so a tab reload's `/api/plan` names the new version. The client then sets `previousPlan`/`versionInfo` and gives `usePlanDiff` a new identity (`live-version:<n>`), so the diff base becomes the version before the edit (each edit shows on its own; the Version Browser can still pick an older base) and an open diff view stays open on the new comparison. Design choice: save a version (what the issue and the approved card asked), not the lighter "diff against the version at open" HTML Refresh does, because the reviewer wants what changed since they last looked; and never on a GET: the write is an explicit POST from the open editor. Not saved: the reviewer's own Edit Mode saves (the reconcile reads them as `unchanged`), raw HTML (HTML Refresh keeps its open-time diff), folder and bundle files, URL, message and live-app sessions. Eligible means a single local session whose named and real paths are Markdown/text (`isSourceSaveFilePath`, `annotateLiveVersionFilePath`), so data files and diagram sources are left out. A file that was empty at open has no version yet but is still advertised: its first text becomes version 1. A session without history (`PLANNOTATOR_ANNOTATE_HISTORY=0`) gets no `liveVersions` and never posts, and the server answers `409 history_off` without touching the data dir; a file past the 2MB annotate cap answers `413 too_large`. Tests: `packages/server/annotate-live-version.scenarios.ts` (both runtimes) and the DOM test `packages/editor/App.liveVersion.test.tsx`.

History saves independently of the `planSave` user setting (which controls decision snapshots in `~/.plannotator/plans/`). Storage functions live in `packages/shared/storage.ts` (runtime-agnostic, re-exported by `packages/server/storage.ts`). Pi copies the shared files at build time. Slug format (history and archive alike): `{sanitized-heading}-YYYY-MM-DD` (heading first for readability; `plan-…` when the plan has no heading).

## Feedback Archive

Every review submitted through a Plannotator decision is durably archived at
decision-settlement time, so a submission survives an agent-side timeout, a
closed terminal, or a `planSave` setting the user turned off. One deliberate
exception: a review posted straight to GitHub, GitLab or Bitbucket with `POST
/api/pr-action` is delivered to the platform and is **not** archived locally
yet (a named follow-up). Layout, per project (same `{project}` key as
`history/`):

```
${PLANNOTATOR_DATA_DIR}/feedback/{project}/
  index.jsonl                                  # append-only, authoritative, schema v1
  records/2026-08-31T14-22-07-511Z-review-feedback.md   # human-readable sidecar
```

The JSONL line is self-contained (`v`, `ts`, `client`, `clientVersion?`,
`project`, `origin`, `surface`, `decision`, `target`, `feedback`,
`annotations`, `counts`, `recordFile`) so an analyzer never has to open a
sidecar; the markdown sidecar exists because the rest of the data dir is
greppable markdown and is written only for records that carry content. Bare
approvals, LGTMs, and dismissals are decision-only lines with no sidecar.

**This index is shared, not Plannotator-private.** Several tools that share the
data dir append to the SAME `feedback/{project}/index.jsonl`, separated by the
`client` field on each line rather than by separate files. Known writers today:
`plannotator` (this repo) and `plannotator-tui`, the Rust terminal client;
`herdr-annotate` is reserved for a possible future Lite writer. Treat `client`
as an open set, never an enum to validate against. Practical consequences: the
line shape is a cross-tool contract, so fields are **added, never repurposed**;
other clients suffix their id onto their sidecar filenames
(`{stamp}-{surface}-{decision}-plannotator-tui.md`), so the `records/`
directory holds more filename shapes than this repo writes and `recordFile` is
the only valid handle to a sidecar (nothing may parse the name); and unknown
fields must be ignored rather than rejected.

Two optional fields are declared in v1 but not populated here, so their names
are reserved across every client: `target.agent` (`{ host?, session?,
transcript? }`) is the provenance for surfaces whose subject is an agent
session rather than a file or a diff, such as annotate-last, and
`clientVersion` is the writing client's own version where it knows it
(`packages/shared` has no runtime-agnostic version constant, so this repo
leaves it unset rather than reading `package.json` from a vendored module).

Everything is written by one shared module, `packages/shared/feedback-archive.ts`
(vendored to Pi as `apps/pi-extension/generated/feedback-archive.ts`), which
resolves the data dir per call and **never throws**: a failed archive write is
logged, degrades silently for the user, and keeps the annotation draft as the
recovery copy. The append happens BEFORE `deleteDraft`, generalizing the #678
ordering to every surface. Call sites: `packages/server/index.ts`
(`/api/approve`, `/api/deny`), `packages/server/review.ts` (`/api/feedback`,
`/api/exit`), `packages/server/annotate.ts` (`persistSubmittedDecision`,
`/api/exit`), and the three Pi mirrors in `apps/pi-extension/server/`.

Invariants worth keeping: records never contain patch bytes or a second copy of
the plan (identity and a version-file reference instead); repeat decisions
append rather than overwrite (unlike the legacy `plans/` snapshot, which is
keyed by slug and status and is left alone); annotation `source` / `author`
provenance is preserved so external, agent, and WebMCP findings stay
distinguishable from the human's own comments; and `feedback` is listed in
`PURGE_OWNED_TOP_LEVEL` (`packages/server/uninstall.ts`) so uninstall purge
removes it. Controls and the privacy/retention note are in the
`PLANNOTATOR_FEEDBACK_HISTORY` row of the environment table above. The read
path in v1 is the files on disk (`jq` over `index.jsonl`, `grep` over
`records/`); there is no CLI reader or UI surface yet.

Details that surprise people:

- **Index durability is a practical guarantee, not a formal one.** One record
  is always exactly one line, and the whole line is handed to a single
  append-mode write. That write is not one syscall (`appendFileSync` loops
  internally until its buffer is drained); what holds in practice is that an
  `O_APPEND` write of a line-sized buffer completes without interleaving on a
  local filesystem. NFS and SMB do not promise even that, and a genuine
  interleave damages **both** records that raced, not just the later one. The
  backstop is the reader: unparsable lines are skipped, so everything else in
  the file still reads. With several clients writing one index, this caveat is
  worth knowing rather than assuming away.
- **Readers gate on structure, not version.** `parseFeedbackIndex` keeps any
  line that parses and carries a numeric `v`, so a newer writer's lines are
  still returned; an analyzer that depends on v1 semantics should filter
  `v <= 1` itself. Since fields are only added and never repurposed, a `v2`
  would signal a real shape change rather than the arrival of new keys.
- **Folder-session records name the folder, not the open document.** A folder
  annotate session submits one body of feedback for the session, so
  `target.filePath` is the session's folder. The record's `annotations` hold
  every document's comments (not only the open one's), and each comment made
  on a document other than the session's own target carries the additive
  `documentPath` field naming that document (absent means the session's own
  target or message; distinct from `file`, a code annotation's file).
- **Records of a review of several files name every file.** Surface
  `annotate-bundle` (additive), no `target.filePath`, and the additive
  `target.documents: [{ path, annotationCount }]` in review order; every
  comment on a file carries its `documentPath`.
- **A quick label is marked as one** (#2626). Its record carries the additive
  `isQuickLabel: true` and, when the label has one, `quickLabelTip` (the
  instruction the agent got with it). Its `text` is the label itself
  ("🔍 Verify this"), not the person's words.
- **URL-session records store the full URL, query string included**, because
  that is the page that was reviewed. A URL carrying a token in its query is
  therefore written to disk; the opt-out is the control for that.
- **`target.review.cwd` is provenance, not a durable handle.** A PR review
  started with `--local` records a per-PR pool checkout that is cleaned up when
  the session ends; `target.review.pr` plus `gitRef` are the identity that
  survives.
- **Project bucketing prefers the caller's `project` option** (the `project`
  field on `ReviewServerOptions`, mirroring the annotate server), falling back
  to deriving a name from the review cwd. The fallback is wrong in PR mode,
  where there is no `gitContext` and `--local` points `agentCwd` at
  `pool/pr-<n>`, so every CLI entry point passes `detectProjectName()`.
- **The test suite turns the archive off** through the `tests/setup/feedback-archive-off.ts`
  preload in `bunfig.toml`, because most server tests boot a real server
  without redirecting `PLANNOTATOR_DATA_DIR` and would otherwise write into the
  contributor's own data dir. Tests that need the archive opt back in inside
  their own test bodies.

## Daily ping

Once a UTC day per tool, one anonymous ping (`packages/shared/daily-ping.ts`; the Worker is `apps/telemetry`). The only automatic request Plannotator makes to its owner; the feedback service, the Inbox relay and the paste and share services are owner-run too, but run only when someone uses them. On by default with no in-app notice (owner decision): the release notes, the privacy page and the Inbox's Settings → About (the Privacy part, `AboutPrivacy` in `packages/inbox/components/Updates.tsx`) tell people.

- **The request:** `POST https://ping.plannotator.ai/ping`, `content-type: application/json`, `user-agent: plannotator`, body exactly `{"version":"X.Y.Z","age_week":N,"tool":"plan","first":1,"favicon":"glass"}`: the release; the install-age bucket from `firstWeek` (Fedora countme: 1 first week, 2 weeks 2-4, 3 weeks 5-24, 4 older); the tool (`inbox`, `plan`, `review`, `annotate`, `last`); `first`, 1 only on the computer's first ping of the UTC day from any tool, so the server counts daily users without an ID; and `favicon`, the favicon set in Settings, read from `${dataDir}/config.json` `favicon` at send time (`readDailyPingFavicon`: `glass`, `yellow`, `totman` is `face`, unset or anything else, the retired `classic` included, `none`). Every tool's ping carries it, Pi's and OpenCode's too (they run the same check). At most five a computer a day. No ID, no OS, nothing else. 3 s timeout; only a 2xx records the tool as sent, so offline tries again at that tool's next check.
- **Who checks:** the CLI's `registerCliSession` (plan, review, annotate, and every annotate-last command as `last`: `cliDailyPingTool` in `daily-ping.ts`; archive and goal setup send nothing), the Inbox (`inbox`) at start and at most hourly on the update timer (`onTick` in `inbox-updates.ts`), Pi's three servers (`apps/pi-extension/server/daily-ping.ts`, over the vendored module; Pi's annotate-last is `last`, and its archive browser sends nothing), and OpenCode's in-process servers (`apps/opencode-plugin/daily-ping.ts`). Every check is `scheduleDailyPing`: a timer, never awaited.
- **Gates, in order:** a release build: `version` X.Y.Z and a build release CI marked. The binaries are compiled with `--define __PLANNOTATOR_RELEASE__=true` (release.yml only; `isMarkedReleaseBuild`), Pi and OpenCode count only with the `release.json` release CI writes (Pi's beside its package.json, shipped by `files`; OpenCode's in `dist/`) naming the package's own version. `tests/daily-ping-live-guard.test.ts` checks release.yml keeps marking all three. Anything else (a source run, a local build, a test spawning the CLI with any `__CLI_VERSION__` and a replaced env) is a dev build and has no live endpoint. Then the environment (`NO_ANON_PING`, the do-not-track convention, CI: `parseTelemetryEnvOff` in `config.ts`), this tool not sent today, and `ping.lock` (O_EXCL, waited for up to 5 s, stale after 60 s; it holds a random token, the file is read again under it, and a process whose lock was taken over writes nothing and removes nothing). Under `PLANNOTATOR_TEST_SANDBOX` or `NODE_ENV=test` it sends only to a loopback `PLANNOTATOR_TELEMETRY_URL`, never the real host. The test preload and the e2e global setup set `NO_ANON_PING=1`, and `tests/daily-ping-live-guard.test.ts` fails when a test spawns with a release version without the off switch or the sandbox, or makes a release-marked build.
- **No switch:** no config key, no Settings switch, no `/api/config` or `/api/inbox/settings` field. `NO_ANON_PING` is the only off switch user-facing text names.
- **The file:** `${dataDir}/ping.json`, `{"firstWeek","day","sent":[tools]}` (UTC dates; `firstWeek` is a Monday). A new file's `firstWeek` is the week of the oldest time on the data folder or anything directly in it (`firstUseWeek`), so an existing user's first ping is not counted as a new install. Nothing is written while the ping is off. `uninstall --purge` removes it and `ping.lock`.
- **The Worker:** `POST /ping` validates the exact keys (the four-key body older releases send, or the five with `favicon`), upserts `daily(day, version, age_week, tool, n)` and, when `first` is 1, `daily_total(day, version, age_week, n)` and, for a five-key body, `daily_favicon(day, favicon, n)`, kept apart from version, age and tool (`n = n + 1`), `204`; a body over 160 bytes is refused by its Content-Length unread, and never read past the cap. `GET /totals` serves the last 90 days' public sums (users, per age bucket, per version, per tool, per favicon) from the Cache API for 5 minutes, so repeated GETs do not read D1. No per-isolate rate limit (it would bound nothing); a zone rate-limiting rule is the answer if counts are ever inflated. It stores no IP, header or `request.cf` field; logs, observability and Logpush are off. Owner-deployed (see `apps/telemetry/README.md`); a body change ships Worker first; its tests run in the root `bun test` against a fake D1.

## Plan Diff

When a user denies a plan and Claude resubmits, the UI shows what changed between versions. A `+N/-M` badge appears below the document card; clicking it toggles between normal view and diff view.

**Diff engine** (`packages/ui/utils/planDiffEngine.ts`): Uses the `diff` npm package (`diffLines()`) to compute line-level diffs. Groups consecutive remove+add into "modified" blocks. Returns `PlanDiffBlock[]` and `PlanDiffStats`.

**Three view modes** (toggle via `PlanDiffModeSwitcher`; `planDiffMode` in `packages/editor/App.tsx` defaults to `classic`):
- **Classic** (`PlanCleanDiffView`, block-level, old above new): Color-coded left borders — green (added), red (removed/strikethrough), yellow (modified). The default.
- **Rendered** (`PlanCleanDiffView` with `wordLevel`, experimental): the same view with word-level inline highlighting.
- **Raw** (`PlanRawDiffView`): Monospace `+/-` lines, git-style. It takes no annotation props: comments are made in the other two modes.

**Config and data files** (`renderAs: "code"`, see `annotate.md`): App passes `codeDocument={{ language }}` to `PlanDiffViewer`, which hands it to `PlanCleanDiffView`. Each chunk then renders as the file's own monospace text in that language (`CodeChunk`) instead of the markdown parse, unchanged chunks line up with the changed ones, and Rendered word-diffs a modified block's raw text (`computeCodeInlineDiff`; stacked like Classic past `CODE_INLINE_DIFF_LIMIT`, 8 KB). `packages/ui/utils/codeDiffSegments.ts` lays the diff over Shiki's colours (`highlightToRuns`): unchanged and added text take the new side's, removed text the old side's, and struck text never strikes a line's leading whitespace. The language is the one the document's own block resolved, so the 128 KB highlight limit applies here too. Without the prop the view is unchanged. Diagram and AsciiDoc files still diff through the markdown parse.

**State** (`packages/ui/hooks/usePlanDiff.ts`): Manages base version selection, diff computation, and version fetching. The server sends `previousPlan` with the initial `/api/plan` response; the hook auto-diffs against it. Users can select any prior version from the sidebar Version Browser.

**Diff annotations:** The clean diff view supports block-level annotation — hover over added/removed/modified sections to annotate entire blocks. Annotations carry a `diffContext` field (`added`/`removed`/`modified`). Exported feedback includes `[In diff content]` labels. A diff annotation's `blockId` is `diff-block-N` (N indexes the diff against the selected base, not a document block), so the export cannot place it in the document: diff comments print together AFTER the document's other comments, in diff order (`sortAnnotationsInDocumentOrder` in `packages/ui/utils/parser.ts`); a document with no diff comments sorts exactly as before.

**Annotation hook** (`packages/ui/hooks/useAnnotationHighlighter.ts`): Annotation infrastructure used by `Viewer.tsx`. Manages web-highlighter lifecycle, toolbar/popover state, annotation creation, text-based restoration, and scroll-to-selected. The diff view uses its own block-level hover system instead.

**Sidebar** (`packages/ui/hooks/useSidebar.ts`): Shared left sidebar with three tabs — Table of Contents, Version Browser, and Archive. The "Auto-open Sidebar" setting controls whether it opens on load (TOC tab only). In archive mode, the sidebar opens to the Archive tab automatically.
