## Inbox: Plans

Plans keeps every plan plan review handled, with its versions and decisions, in one library on the person's computer. It lives in the Inbox (the same server and window); there is no separate Plans window. This guide covers the records, the library on disk, the import from today's stores, the switch, the routes, the command and the Plans page in the window. Comments on a plan's Markdown pages, Send to the plan's agent (its own Inbox thread once the first Send made one), editing, Restore and Approve are on the plan page (editing and approvals: approval "plans-editing", `.product/approved/plans-editing/approval.md`); an agent tool comes later.

On screen the panel is "Spaces" (approval "plans-home", `.product/approved/plans-home/`): the sidebar row, the page, its crumbs and its messages; its home says "On this computer", and nothing on screen implies another person (no share, link or who-is-here), but for a plan page's Share button while Share this space is on (its own switch, off by default; "Share this space" below). A plan is what an agent puts into a space, so "Start a plan", "plan" in "Search plans" and "All plans", and a version ("v3") keep their words. Every word an agent may read keeps "Plans" and "plan": `plannotator plans`, plan review, the routes (`/api/plans`, `#plans`), the store (`plan-library/`) and the code's names. The words Groups and Loops are never used.

### The switch

- config.json `inboxPlans` (`true` / `false`, unset is off): `plansOn()` / `setPlansSwitch()` in `packages/shared/plans/switch.ts`, read on every request.
- On only by the person: `plannotator plans` (no gate: running it is the opt-in, from any shell), or `POST /api/inbox/settings` `{ plans: { on } }` from the window. No agent tool, agent text, skill or `--help` names it (the subcommand is in `HIDDEN_SUBCOMMANDS`; its help is the usage line only).
- `plannotator plans off` (or the settings switch) turns it off and keeps `plan-library/`.

### Off costs nothing

`packages/server/plans-capability.test.ts` holds all of it:

- Every `/api/plans` path is the Inbox's unknown-route `404`, as if absent (as Shape's).
- The library is not opened, read or imported; no file appears under the data dir.
- `GET /api/inbox/settings` has no `plans` key (it is present only while on, as `plans: { on: true }`; the window draws Plans only when it reads that key, see The Plans page).
- Plan review writes exactly what it wrote before (`history/` stays the source). On, it also writes the session that submitted a version beside it (`NNN.agent.json`, `saveToHistory`'s `agent`; the hook passes one only while `plansOn()`, `planHistoryAgent` in `apps/hook/server/index.ts`).
- The Inbox's agent tools, their text and the served tool list are unchanged; only the capability seam and the command reach Plans' modules (a source scan in the same test).
- `plannotator plans …` other than `plans` and `plans off` prints `PLANS_OFF_TEXT` (one line naming `plannotator plans`) and exits 1, starting nothing.

### The records (`packages/core/plans.ts`)

Browser-safe types, id prefixes, pure checks and the version id; no I/O. Field names are snake_case, as stored.

| Record | Id | Notes |
| --- | --- | --- |
| Plan | `pln_<ulid>` | `name` (the primary document's first heading), `project_name` (the `history/{project}` folder), `project_id` / `project_root` (an Inbox project, later), `primary_doc_id`, `status`, `thread_id` (its Inbox thread: the one the first Send from the plan page started), `created_by`, `legacy` (the chains and snapshots it was built from), `last_approval_cleared` (`{ document_id, cleared_at, version_number, from_version_number, approver_names }`: the last new version that cleared approvals) and `last_approval_moved` (`{ document_id, moved_at, version_number, from_version_number, name }`), both absent until the first, and `agent_told` (per page id, the newest of the person's versions a Direct Edits section carried to the agent) |
| Document | `doc_<ulid>` | `kind` (markdown, html, mermaid, graphviz), `title`, `head_version` |
| Version | the git blob SHA-1 (`gitBlobSha`) | `version_number` 1, 2, 3… with no gaps, `file` (`docs/<doc>/<n>.md`), `committed_at`, `source` (`person` for the person's own edit or Restore), author fields, `legacy` (the file it came from), `restored_from` (a Restore only: the version whose bytes it took) |
| Decision | (inside a `decision` event) | `decision` (approved, approved-with-notes, denied, feedback), `version_number`, `feedback`, `feedback_record`, `snapshot`, `moved_from` (an approval the person's own edit carried from that version); who gave it is the event's actor (`author_label`, else the person on this computer, `PLAN_PERSON`) |
| Event | `actev_<ulid>` | the plan's activity; `legacy` names the line or file an imported one came from |
| Look | (looks.json) | per plan `looked_at`, per document the newest version seen |
| Artifact | (its `asset_path`) | a file kept with the plan as it is, no versions: `asset_path` (relative, `isPlanAssetPath`: plain `/`-separated names every disk can hold, so no `.`/`..`, leading dot, trailing dot or space, `\`, control character, `<>:"|?*` or Windows device name such as `CON` or `com1.txt`), `content_hash` (sha256 hex), `content_type`, `size`, `title`, `created_at`. Read and shown; written only by the store's `addArtifact` (tests and a sandbox seed): no agent or command adds one yet. `addArtifact` refuses a path that differs from a recorded one (or its folders) only by case or Unicode form, since the Mac's and Windows' disks hold them as one file; serving (`artifactPath`) answers only when the file's real path is exactly the recorded one under the plan's `files/` (a symlink anywhere below it, or a name the disk folds, is refused) |
| Comment `anno_` | | the person's comment on a version (`comments.jsonl`): `anchor` the annotation, `sent` (`{ at, message_id, to }`) once a Send carried it |
| Reply `reply_` | | type only: not written yet |

Rules the records keep, so a later copy kept elsewhere stays possible (nothing leaves the computer today):

- A version's author is a display name only (`author_label`, with `author_via` and the agent fields): never an email or a user id. The import writes none.
- Events and Looks are local-only: they never go with a plan; a copy kept elsewhere writes its own.
- Of the decisions, only "approved" (and "approved-with-notes") maps to a document approval at a version. "denied" and "feedback", with the person's notes, stay local-only.
- An approval belongs to the version it was given on, the current one only (approval "plans-editing"; `planApprovalsOn`, `planApprovalState` in `packages/core/plans.ts`, one rule for the store, the index and the window). The store's `addVersion` decides as it writes the version, from the new version's authors: the approvals the version before holds clear (nothing to write: approvals are read on the newest version; `last_approval_cleared` in the plan line it writes says whose), except that the person's own edit (`source: "person"`, `author_via: "person"`, no Restore, no agent field) carries the person's own approval to the new version (a decision event on it with `moved_from`, then `last_approval_moved` in the plan line). Those are separate appends after the version lines, not one write: a crash between them reads as cleared, the safe way, since no approval ever survives a change it was not given on. A Restore, an agent's version or any version with an agent in it clears. Past approvals stay on their own versions (history); an imported decision whose version was never found counts as on the first version (`planDecisionVersion`), so an old approval is history there rather than lost. The index line carries `approval` (`planApprovalState` of the main page), so the list never shows an older version's approval as current, and, for the Spaces home's facts, `primary_kind` (the main page's kind), `head_source` (who made the newest version: `person` for the person's own) and `decided_versions` (the main page's versions that hold one of the person's decisions, sorted). An index line written before them is repaired at start (its JSON differs), and the window reads an absent `decided_versions` as the newest decision's version.

### The library on disk (`packages/shared/plans/store.ts`)

```
<dataDir>/plan-library/
  index.jsonl              one line per plan change (the last line per id wins), for a fast list
  looks.json               the person's looks (written whole)
  pins.json                the person's pinned plans in their order, `{ v: 1, ids }` (written whole; a plan that is gone is
                           left out when read)
  legacy-map.json          what the import took from where (written whole)
  <pln_id>/
    plan.jsonl             the plan record, one snapshot per change (a new version that clears or moves approvals adds one)
    docs.jsonl             documents and versions ({ kind: "document" | "version", record })
    docs/<doc_id>/<n>.md   each version as a plain file, readable without Plannotator
    events.jsonl           decisions and activity
    artifacts.jsonl        artifact records (the last line per asset_path wins)
    files/<asset_path>     each artifact's bytes (written before its line)
    comments.jsonl         the person's comments ({ kind: "comment", record } with the annotation in `anchor`, the last line per
                           annotation id wins; { kind: "removed", annotation_id, at } takes one away)
```

Not under `plans/`, which holds decision snapshots (and may be a person's custom folder). The Inbox store's rules (`packages/shared/inbox/store-log/jsonl-log.ts`): one writer (the Inbox server; `plans list` only reads), one line per change in one append-mode write, a torn line skipped on read and never glued to the next one, whole files through a temp file and a rename, folders 0700 and files 0600. A version's file is written before the line naming it; the head is the newest version line, so a crash between lines never reuses a number; `repairIndex()` writes again an index line a crash left behind. Opening the store reads and writes nothing.

### The import (`packages/shared/plans/import.ts`)

Read-only: it reads `history/`, `plans/` and `feedback/` and writes only under `plan-library/`; it calls no writer of those stores (`getPlanDir` creates its folder). It runs as often as asked and never takes anything twice: each record it writes names its source (`legacy`), checked before every add; `legacy-map.json` only makes a second run fast and is rebuilt from the records when lost. The odd cases:

- A `history/{project}/{slug}/` folder with `NNN.md` files is one plan: its files in number order are versions 1, 2, 3…, dated by each file's modified time; the plan's name is the newest version's first heading.
- Chains are never joined. A heading change (a new slug) or the same heading after two quiet days (a new dated slug) is a second plan; two projects with the same slug are two plans. Joining is the person's later merge.
- Missing numbers (001, 002, 004): imported in order and numbered without a gap; each keeps its file name; the chain is listed in the report's `gaps`.
- A file plan review may still be writing (it truncates, then writes: modified less than `PLAN_IMPORT_SETTLE_MS`, 2 s, ago, or a different size or time after the read than before) is not read yet: its chain stops there (`unsettled`), is not marked read, and a later run takes the whole file. The same for a snapshot. An empty `NNN.md` is no version (`empty_files`). The newest file empty: its chain waits there and is not marked read (plan review fills a truncated file in place, which does not change the folder's time, so a mark would skip it for good). An empty file with later files after it: that write is over, the later files are imported. `legacy-map.json` is written only when a chain's entry changed, so a chain waiting on an empty file writes nothing on each pickup.
- Version order is file order, never arrival: a version is never placed before one already imported. A file whose number is below the newest one imported (an empty `002.md` filled after `003.md` was taken) is not imported: it is listed in `late_files`.
- An unreadable file stops its chain there (`unreadable`); the next run goes on from it, in order.
- A folder with no `NNN.md` is no plan yet; annotate's chains (`annotate-…-<8 hex>`), `submissions/` and other files are left out.
- A feedback line of plan review (`surface: "plan"`) is a decision on the version it names (`target.slug`, `target.planVersion`), with the person's notes. A line with nothing to land on yet (its chain is not in the library, or the version it names is on disk but not imported yet) waits, counted in `orphan_feedback`; the map keeps the file's size, the offset after its last whole line read and the waiting lines' byte ranges, so the file is not read again until it grows (then only its new lines), and the waiting lines are tried again only after a run that added versions. A line still being appended (no newline yet) waits for the next run. Other surfaces and torn lines are skipped.
- A decision snapshot is matched by its text (the version's text, or it followed by `\n\n---\n\n` and the notes) to a version of a chain with the same heading. If a feedback line already gave that decision on that version, it is not kept twice (`duplicate_snapshots`); otherwise it is a decision. A snapshot written over by a later decision is a new decision. Feedback lines are read before snapshots; plan review writes the snapshot a moment before its line, so a pickup landing exactly between the two would keep both.
- A snapshot with no matching history (a decision without history) is a plan of its own: the snapshot file as its one version (the plan text and the notes cannot be told apart), its decision, no project. The plan's `legacy.snapshots` names the snapshot (`plans/<file>#<blob sha>`) from its first record, and it counts as done only once it holds its decision: a run after a crash between its steps finishes that plan rather than making a second one.
- Snapshots saved to a custom folder (a browser setting the server never keeps) are not found.
- New versions plan review writes while Plans is on are picked up by the same function: the Inbox runs it in the background once it is up and when the switch turns on, and a request to `/api/plans` runs it again at most every 2 seconds (`packages/server/plans-capability.ts`). The list says `importing: true` only until a whole import has finished since the Inbox started or Plans was turned on; the quick pickups after it say nothing, so a window that reads again while `importing` stops. An import that fails is not tried again on every read: the next pickup waits 4 s, twice as long after each failure in a row, at most 5 min; the error is logged once per distinct message; the list says `import_error` (the message, null when the last import went through), and `GET /api/plans?retry=1` (the window's Try again) runs it now. There is no file watch. The import yields after each chain, snapshot and feedback file, every 10 versions and 25 feedback lines, and after each plan while it repairs the index and rebuilds the map, so a first import of a long history does not hold the Inbox.
- Not yet: `index.jsonl` only grows (one line per change); compacting it (written whole when it holds many more lines than plans) is a follow-up.

### The capability seam (`packages/server/inbox-capability.ts`)

`InboxCapability` (`key`, `on`, `save`, `prefix`, `route`, `settingsWire`, `started`) and `InboxCore` (only `dataDir` and `changed` for now). `inbox.ts` routes (`routeInboxCapabilities`), answers the settings (`capabilitiesWire`, `checkInboxCapabilities`, `answerInboxCapabilities`) and starts (`startInboxCapabilities`, after listen) through the list, and never imports Plans. The route guard is Shape's: off, or reached any way but the owner's window on this computer (the tailnet, a phone's door, a linked machine), `404`; another site `403`; a POST with another page's `serverSession` `409`. Plans is not on any door route. The same windows the routes refuse are never told of Plans: the settings answer and the `event: capabilities` frame carry the capability keys only for a window on this computer that came in by no door (`capabilitiesWire(list, local)`, `capabilitiesFrame(list, changed, local)`), so a phone or a linked window shows no Plans row. Plans is the only capability on the seam; Shape, Routines, the Board and code review stay wired by hand. A capability's agent tool and the window's capability rows come with the first capability that has them.

### The command (`apps/hook/server/plans-command.ts`)

- `plannotator plans`: on, then the Inbox started detached or found (`ensureInboxRunning`), and its Plans page (`<url>#plans`) shown and printed: in the window the person used last when one is open (`POST /api/inbox/control/show` `{ page: "plans" }`, `event: show { page, window }`, as `plannotator inbox --open <thread>` shows a thread), else in a tab opened as `plannotator inbox --open` opens one.
- `plannotator plans off`: off.
- Both save the switch through a running Inbox (`POST /api/inbox/settings` `{ plans: { on } }`, as the window does), so its open windows hear `event: capabilities` and follow without a reload; with no Inbox running, or one that refuses (older than Plans) or does not answer within 5 s, the command writes config.json itself.
- `plannotator plans list`: one line per plan (id, last change, project, head version, decision, "changed, you saw vN", name) from the running Inbox (waiting out its import), else read from the library on disk. Never starts the Inbox, never writes.

### The Plans page (`packages/inbox/plans/`)

The window's page, self-contained like Routines (`client.ts`, `store.ts`, the route and the nav row). Styles in `plans.css`, imported by `apps/inbox/index.css` with its `@source`.

- **Gating.** `usePlansOn(settings, toast)` (the toast is where a failed pin says so) is true only while the settings answer has `plans: { on: true }`. Off, nothing of Plans is drawn: App passes no `onPlans` to the sidebar, `drawnSidebarItems` leaves `plans` out of the sidebar, its menu and Customize, and `#plans` goes back to the Inbox. There is no Settings row and no `--help` entry. Turned on or off while a window is open, the window follows at once: `event: capabilities` names `plans: { on: true }` while on and `{ on: false }` on the change that turned it off (`capabilitiesFrame` in `packages/server/inbox-capability.ts`), the window merges it into its settings (`capabilities.ts`), the row comes or goes, and a window on `#plans` goes back to the Inbox. A `404` from `/api/plans` (an Inbox that could not tell the window) shows "Plans is off" with a link back to the Inbox. Off, `plans` is never saved either: the window keeps it out of the layout cookie (`setSidebarUnsaved` in `sidebarLayout.ts`, set by `setPlansOn`) but sends the layout whole, so a window that never hears Plans is on (a phone, a linked window) keeps the Plans row's place and hidden state; the server stores a layout without the item of any capability that is off (`saveInboxSidebar` in `packages/server/inbox-sidebar-save.ts`: the lenient read puts back every item a layout does not name, so the read-back check compares that read form), so an off Plans leaves nothing in what the window draws or saves.
- **Sidebar.** Core `INBOX_SIDEBAR_ITEMS` has `plans` (top stack, second under Inbox, hideable; labelled "Spaces"). `PlansNav` ("Spaces") counts the plans `changed` since the person looked. Under it, the person's pinned spaces in their order (`pinnedPlans`, from `pins` in `GET /api/plans`): the pinned threads' row (`ib-pinrow`/`ib-pin`, `PinnedRow.tsx`'s look) with the plan's name, its unread dot, and a tooltip with its project and fact; a click opens the plan (the row of the plan on screen is lit); its ⋯, or a right-click, holds Unpin, Move up and Move down (`POST /api/plans/pins`; no drag, no Copy link, no shortcut). While the home is scoped to a project, that project's sidebar row is the lit one and Spaces is not.
- **Hash.** `#plans` (home), `#plans&all` (All plans), `#plans&project=<id>` (the home scoped to one of the sidebar's projects, `route.project`; a sidebar project clicked while on Spaces goes there, `onProject` in `App.tsx`), `#plans&new` (the get-started screen once there are plans), `#plans=<pln_id>` (a plan at its newest version), `&v=N` (a version), `&from=A&to=B` (a diff), `&doc=<doc_id>` (another page of the plan, with its own `&v`/`&from&to`), `&file=<asset_path>` (an artifact; it wins over `doc`). The main page keeps the plain plan address. Parsed in `app/route.ts`, written in `app/writeRoute.ts`; switching versions replaces the history entry.
- **Home** (`PlansHome.tsx`, `SpacesHome.tsx`, approval "plans-home", `home-5.html`). While the list is read, "Loading plans…"; with no plans, or from Start a plan (`#plans&new`), the get-started screen (`PlansGetStarted.tsx`): "What do you want to plan?" over a dither (`dither.ts`: an 8x8 Bayer field that settles in ten steps at 12 fps, then stays still; reduced motion or a hidden window draws only the still frame; its ink is `--muted-foreground`, redrawn when the theme changes). Its "Start a plan" shows how a plan arrives (plan in the agent as usual; each review is kept here, on this computer). An import that failed (`import_error`) is a quiet line on either screen, "Could not read your earlier plans." with Try again (`?retry=1`). Otherwise the home (`SpacesHome.tsx`):
  - **Head.** "What do you want to plan?" and Start a plan over home-5's own still field (`startStillField` in `dither.ts`, ported as written: six soft blobs over the 8x8 Bayer matrix in 3 px dots, `k` 0.34, alpha 0.22 light and 0.26 dark, about 37% covered and every tenth of the width above 0.2, `stillFieldCells`; drawn once and again on a resize or a theme change, never moving; masked to fade from 20% down), and at the top right "On this computer" (a laptop mark), Search plans and the cards/list switch (two buttons named Cards and List). The view is the person's: config.json `inboxSpacesView` through `POST /api/plans/view` (`spacesView`/`setSpacesView` in `packages/shared/plans/switch.ts`), read with the list (`view`), so every window opens on it; a failed save holds for that window. An earlier build's own "compact" choice (localStorage `plannotator-inbox-plans-view`) is carried over once, as List, on the first list read, and the key removed (`carryOldView`).
  - **Sections.** "Now" (`isNow`, one predicate in `spacesModel.ts`, switched by `NOW_RULE`): a plan a live session is known to be on, or one whose newest main-page version came in the last 3 days (`head_at` in the index line: the version's own time, so a plan imported from old history counts by its history, not the import) and holds no decision of the person's or is unread; older plans sit in Recent, keeping "Your move" and the unread dot (a library of old imported plans never opened does not fill Now) (`NOW_RULE = 'waiting'` is the other answer: every plan that waits). Never cut: one row of large cards at most (as many as the page's width holds at 280 px, so 3 at 1440), the rest of it as rows (the list's row, with the project; Recent's rows say it too) under them in the same section, so no card is left alone on a row and Recent's first card is on the first screen (rows in the list). "Recent": the rest, newest first, one row of cards (as many as the page's width holds at 230 px) or 8 rows, then "All plans" (`#plans&all`): every plan not in Now by project (projects by their newest plan, "No project" for none), the newest 5 rows or one row of cards each, then "Show N more" (open for this visit). A project's name is a fold button; folded it says "N plans"; the folds are kept in this browser (`plannotator-inbox-spaces-folded`). A sidebar project scopes the page (`#plans&project=<id>`): its plans only (by `project_id`, else the project's name or folder name, also those of the projects the sidebar combined into it, `inProject`), Now first, then "Earlier"; "Home" in the crumbs goes back. Search looks through every title, in a scope too (each word, any case; no folds, nothing cut); in a scope the search box holds the project as a chip whose × ("Remove <name>, show every project") goes Home, and that project's matches come first; none: "No plans match “…”." Lists are `role="list"` with `listitem`s. The rules are pure in `spacesModel.ts`.
  - **The card and the row** are the frame's (`@plannotator/ui/components/frame`: `Card`, `CardRow`, `CardRows`, `CardGrid`, `CardUpdatesPill`, `settleBatch`, `arrive`; its README is the contract). The card grids are `CardGrid`, each given its row gap (28 px for Now's large cards, 44 for the rest, never the default); the rows are `CardRows` with `actionAtRest="never"`: a row's pin shows on hover or keyboard focus only, never at rest on a touch screen, where a row is pinned from its long-press menu (Base UI's context menu, 500 ms: Pin to sidebar, Unpin); a pinned row keeps the card's pin after its title. The home's card and row links set `-webkit-touch-callout: none` so that iOS opens that menu, not its own link preview; the long-press has been checked in Chromium's touch emulation only, not yet on a real iPhone. Each face is laid out at `CARD_FACE_WIDTH` (the home sets it as `--ib-spc-face-w`). A date fact keeps the home's words ("Today", "Yesterday", "Nov 15") and passes `updated_at` as `time` for the tooltip; a working plan passes `working`. A row gets a `thumb` only when `SpaceThumb` draws (`useThumbDraws`): never for an HTML page, a picture once its face has one, a diagram once read, not cut, and not a Mermaid source that could load something; otherwise the card draws its kind's glyph. The settle runs `settleBatch` on each grid and on the rows (nested, one mutate), and a newcomer in Now also fades in (opacity only, so there is no second movement). A changed document face calls `arrive` on the block where the change landed (`data-face-landed`); any other face cross-fades. The pill is always drawn by the first heading (count 0 while nothing waits), so its polite live region stays. Faces mount 240 px before they come into view and unmount 1200 px away (the card's margins); the HTML face's `srcdoc` stays cached. A card is one link (the title and the fact; the face is inert, hidden from screen readers, and outside the link, so no frame is inside a link), with the pin ("Pin <name> to sidebar", "Unpin <name>") as a sibling of the link at the top right of its well (on hover and focus, always on touch and while pinned; keyboard order: the link, then the pin); its right-click menu holds Pin to sidebar or Unpin. The kind is read from the main page alone (`spaceKind`): HTML a page; a picture, Mermaid or Graphviz an image; CSV or TSV data; else a document. A document is paper with one sheet behind; a page a window with its 16 px bar of three dots; an image or data flat on a panel; the well's ground is the kind's tint. Paper, its edge and the shadow are the card's: in dark the paper is lighter than its ground; the app's dark is the root without `.light` (`:root:not(.light)`), never a `.dark` class. The caption is 11/14/13 with a 2 px gap; "Your move" is weight 400, in the accent through the card's `factTone: 'action'` (every other fact is `'default'`, grey). The title takes two lines (a row's one). A row is 44 px (52 on a phone) with a 36x27 thumbnail of the card's own face (`SpaceThumb`), static and cheap: a document's lede and first lines as plain words at the sheet's scale (no renderer), data as a few cells, a picture or a drawn diagram as the same still drawing; a page keeps its kind's shape (no frame in a row): the window with its bar of three dots and a few lines. In dark, what the plan brought (its picture, its HTML page) is dimmed on the home (`filter: brightness(0.78)`, never recoloured); a drawn diagram is drawn in the theme's colours; the plan's own page shows each as it is.
  - **The face** (`SpaceFace.tsx`), made with no AI and nothing reordered, from the main page's kind. A document: its newest version from its first paragraph (`faceParts` in `spacesModel.ts`), past front matter and a first heading equal to the title, never starting on a list; the paragraph's first sentence is the lede (18/27, weight 500, full foreground), the rest in the sheet's type (home-5's `.dd`, scoped to `.ib-spc-face`: padding 34/36, body 15/24 at 82% foreground with 10 px after, headings 15/22 weight 600 with 18/8 around, lists 15/24 with muted markers and 2 px between items); a generic heading (Context, Overview, Summary, Background, Problem, Goal(s), Introduction) is left out wherever it is, its words kept; a specific first heading ("Session layout") is the top line, above the lede, at body size. - **Diff** (`PlanDiffView.tsx`). `GET /:id/diff` through `computePlanDiff` and `PlanCleanDiffView` with no annotation handler, so it is view-only, inside `PlanContentRules` (`PlanCleanDiffView`'s own inline renderer reads the same image and link contexts; with no provider it renders as before); `plans.css` turns its left bars into fills.
- **Not yet.** An agent's open turn on a plan as "working" (only its last submit counts), a way for an agent to submit a picture or data main page (the store takes them; nothing writes one but a sandbox seed and tests), the agent tool, starting a plan from the window (it needs agent text and a launch), "Start from Markdown" (it needs a write route), a plan being written, version summaries, a way for an agent to add a page or an artifact.

### Share this space

Approval "share-this-space" (`.product/approved/share-this-space/`: `approval.md`, `FLOW.md` with every state and string, `shots/`). A plan's page can put a copy of the plan into a hosted space and get a link back. This is slice 1: the engine and the Share control on a plan's page in the Inbox. The plan review and annotate windows come later; until then their "Share" and "Copy Share Link" stay as they are.

**The switch.** config.json `inboxSpaceShare: true` (`spaceShareOn` in `packages/shared/spaces/url.ts`), and Plans on, and sharing not disabled (`PLANNOTATOR_SHARE=disabled` or `share: "disabled"`). Config only: no Settings row, no command, no agent text. Off (the default): `/api/plans/:id/share…` is the `404` of any unknown plan path, the settings answer is what it was (`plans: { on: true }`; on, `plans: { on: true, share: true }`), the page draws no button and reads nothing (`usePlanShareOn`), and no call leaves the computer. The Spaces address is `PLANNOTATOR_SPACES_URL`, else config.json `spacesUrl`, else a placeholder that resolves nowhere (`https://spaces.invalid`): an owner who turns the switch on sets the address too. `https`, or `http` on this computer only.

**What goes up, in order** (`planSpaceShare`):

1. The space, with the main page's first version in the same call. Its id is made here (`ws_<ulid>`), so the create tried twice is one space; the call is kept as first made (`record.name`, `record.seed` with its share time) and sent again exactly so. Signed in, it carries the plan's id as `external_key` (never without an account: the service refuses a key with none); a Share as new sends a key of its own, `<id>:<the new space's id without ws_>` (the record's `as_new`), so it really is a new space and no key is ever used twice. A key the person already has answers that space under its own id (`200`, the id sent is not used): the share takes that id for every later call (`record.space_id`), so a share whose record was lost goes on in its old space. Its main page is the page at its path, else the one page holding one of its versions from here (a path worked out again may differ; not a page at another page's or file's path, not the empty page, and only when exactly one matches); a space with pages and none of them its main page is not added to, and is the `gone` state (Share as new). A page there that holds any version of it from here is taken as up to that version, and what is newer goes up; one holding anything else is a page changed in the space, left alone. Comments on older versions of such a space are neither sent nor counted (a known limit). `409 external_key_conflict` (the key names a space of another team) and an answered id this share cannot keep are the `gone` state, so the way on is Share as new.
2. Each page: "All versions" sends every version oldest first, each a save on top of the one before (`If-Match` names the version the space is expected to hold); "Newest" sends the newest of each page. A save is the JSON `PATCH …/documents/{doc}` with the page's text as `body` and the actor, never a path (the service refuses an actor with a path change); a file sent as a page (below), and a page whose bytes are not UTF-8, still save with the raw `PUT` and no actor. A call's wait before it counts as not answered grows with its body, JSON or raw. Only Markdown, HTML, Mermaid and Graphviz are pages there. A picture page or a table page goes up as a file (`lane: "file"`); an artifact whose extension is a page's (`.html`, `.md`, …) goes up as a page, since the file door refuses it. A page has a path there: its `doc_path` when the space takes it for its kind, else its title with the kind's extension, never one already taken (`spacePagePath`); the path is kept in the record.
3. Each file (artifact), its bytes as they are. Unchanged bytes (the recorded SHA-256) are not sent again. A name the space does not take (`#`, `%`, `?`) is written with `-` on the way up (`spaceFilePath`, kept as `remote_path`); the file keeps its name here, and the library's own path rule is unchanged.
4. Each comment not yet sent to the agent, on a version that is up, with the store's `anno_` id as its `Idempotency-Key` and an allow-list of the annotation as its anchor (`spaceCommentAnchor`: what the space's parsers need to place it: its id, type, words and selected text, the block and offset fields, an answer to a question block, and the own position fields of the diagram, HTML, picture, math and diff anchors and their extra targets; a picture's reference only when it is a web address or relative inside the plan, `spaceImageSrc`). Its pictures, commenter's name, the people it names, the tool that made it, page, PR and artifact addresses, an element's description, local paths and its time stay here: a space nobody kept is open to every holder of its link. A reply (`inReplyTo`) goes through the reply call, and only under a comment that is in the space too. Comments the agent already has, and every decision's notes ("Changes asked"), never go.
5. The person's approval of the main page's newest version goes up only with Keep this space, on the space's sign-in page (below): a run never sends it, since the space refuses a tool's own approval call (`PUT …/approval`, approve or take back, is `403 approval_human_only` for a tool's token), and no step is planned for an approval that is not up. Details lists the approval only while it is up there: recorded with Keep, of the version the space holds, the page not saved since (a save clears it there) nor changed there. Old records may carry `approval_refused` (from the call once made): read, never written, and it locks nothing out.

What stays, counted in Details under "Not shared": comments already sent to the agent, pictures inside comments, the original dates and authors of versions (each version is dated at the push), a file over 100 MB, a page over 1,572,864 bytes (HTML 16,000,000), a comment over 8 KiB (anchor 16 KiB, or a call over 32 KiB once its words are written as JSON), approvals on older versions. A comment on a version that is not up (an older version under "Newest") stays too, and is not counted.

**The record** (`SpaceShareRecord`, `<dataDir>/plan-library/<pln_id>/share.json`): `host`, `space_id` (the id made here, or the one a known key's space answered with), `seed` (the create as first made: its page, version and share time `at`), `as_new` (made by Share as new: its key is its own), `share_url` (shown exactly as returned), `mode`, `kept`, `refused`, per document id `pages` (`lane`, the hosted id, `doc_path`, `pushed`: pairs of local version number, hosted version and content hash, and `stopped` once the page changed in the space), per artifact path `files` (hosted id, content hash), per comment id `comments` (the hosted id, or why it stayed), `approval`, `keep_approval` (the approval sent with the last Keep and what the sign-in page did with it: `recorded`, `moved` or `none`; for a later panel, not shown), `shared_at`, and `job` (a run not finished: steps done, total, how it ended). Later calls go to the host the record names, whatever the setting says now.

**The run** (`runSpaceShare`). The steps are planned again from the record before each call, so a run that failed, was stopped or died with the Inbox goes on from the step after the last one kept, and its count goes on ("13 of 40" after "12 of 40").

- A call whose answer was lost is not made twice: the create replays by its id; a page add finds the page by its path; a save is refused by its own `If-Match` and the version the space names is the one sent (a leading byte-order mark is dropped before hashing, as the space does); a file is the same bytes at the same path; a comment carries its key.
- `429`: waited out for as long as `Retry-After` says (10 s when it does not say); the status says `waiting` with the seconds left. A `503 workspace_seed_timeout` or a `500` is sent again, three times at most.
- `412 version_conflict` on a save: the page changed in the space. It is marked `stopped`, named on the panel ("<title> changed"), and left alone from then on; the rest goes up.
- Only a claim says "Someone else kept this space" (`spaceKeptByAnother`: `409 claim_conflict`). A page save or file upload the space does not allow (`403`), to a space made here and not known to be the person's own, only means it has an owner now, perhaps this person from the browser or another computer: the run ends as `keep` (`job.keep`), nothing more is sent, the panel is the result with Keep this space and the changes still counted (Update waits), and Keep asks the claim: theirs (the Update goes on) or refused. The same when the claim a signed-in create makes loses. A comment counts the same: it carries the imported actor, which a space with an owner takes from its owner only (`403 imported_owner_only`).
- A space that is not there for this caller (`spaceNotAvailable`: with no account `401 login_required`, which an expired or removed space answers and a space made private answers; signed in `404 workspace_not_found`; never `410`) is the `gone` state (`job.gone`): one line, "This space is gone", and Share as new. No link, no Copy link, no Try again; nothing is made again by itself, and no sign-in is started or suggested.
- Any other "no" is a run that did not finish. The space's `413 quota_exceeded`: for a space nobody kept, the over-the-limit state with Sign in; for the person's own space (or a share started signed in), one line, "Over the limit", with the link when there is one and Try again, which sends once more (room may have been made in the space) and comes back to the same line when it is still over; nothing tries by itself. Once what it holds here changes (`job.bytes`) it is an Update again, or, never finished, the first share again. The 100 MB count before anything is sent applies only to a space nobody owns: not to a kept space, nor to a share started signed in until a claim has said the space is someone else's.
- A share started signed in whose space was made but never confirmed as the person's own (the claim after the create got no answer) is taken as private meanwhile, and the next run makes that claim before it sends anything.
- Whose the space is, is what the space answers: `kept` is set from the create's answer (`access: "owner"`), and a signed-in create that comes back with no owner (made before the sign-in, its answer lost) is claimed then and there. It is never assumed from being signed in.
- More file bytes than a space nobody kept may hold (100 MB, counted before anything is sent, or the space's `413 quota_exceeded`): `over_limit`; the one way on is Sign in.
- The token is forgotten only when the space refuses the credential itself (`401 unauthorized`), never for another 401 (a sign-in asked for, a proxy's page). A share started signed in (`signed`), or a kept space, with no token now is never gone on with, or made, without a sign-in: Keep this space takes the place of Try again, the pending changes stay counted, and an Update never opens a browser. For a space that is the person's own (kept, or started signed in), Keep sits on the access line itself, with no "Make it yours" beside "Only you"; where a stopped page's row takes the access line's place, Keep has its own row.
- The Inbox going down is not the person's Stop: the run's record is left as a run not finished (`ended: null`), which Try again goes on from.
- Every call ends after a minute with no answer (longer for many bytes), as a call that was not answered.

**Keep this space** (`signin.ts`, `share-job.ts`). A listener of the sign-in's own on `127.0.0.1` (a random port, `/callback`, answering only to the `state` it made, closed after one use, a Cancel or 10 minutes), the browser opened at `<spaces>/cli/login` with `redirect_uri`, `state`, the PKCE challenge, `code_challenge_method=S256` and always `client_name=Plannotator` (the space sends a Cancel back only when it was sent; a name it does not know is `400`). For a space that is up and not refused it adds `space=<space id>` (the page claims it), and, when the person approved the main page's newest version and that is the version the space holds (the last pushed, the page not stopped: `spaceKeepApproval`), `approve_document` (the hosted page id) and `approve_version` (its hosted version). The way back is a `code` (with `approval=recorded|moved|none` only when an approval was sent; absent is `none`), `error=access_denied` (Cancel: back to where it was before Keep, nothing changed, no error; the tab reads "You can close this tab.") or `error=claim_conflict` with no code (the space was free when the page was drawn and someone else kept it before the press: `refused`, as a lost claim; no token). A space someone else owns when the page is drawn gets the plain connect page: a code only, which is a sign-in, not a Keep. `kept` is set only from this computer's own claim call (`POST …/claim`, always made after a sign-in); there it answers `409 claim_conflict` and the share is `refused`. The outcome is kept as `keep_approval` on the record (not shown yet); `recorded` also sets `approval` (it is up, and Details lists it); `moved` and `none` leave it not up, with nothing sent for it later. A Keep made while already signed in opens no page, so it sends no approval. The code that comes back (120 seconds, single use) is traded once at `POST /cli/token` as a form (`application/x-www-form-urlencoded`; JSON is refused `415`) with `grant_type=authorization_code`, `code`, `code_verifier` and the same `redirect_uri` string the login page got, byte for byte (`http://127.0.0.1:<port>/callback`; the service refuses `localhost`); no Origin, cookie or Authorization rides on it. It is never tried again: the service spends a code on its first lookup, and a second load of the callback is not found. The answer is `access_token` (`expires_at: null`) with no name; the name is `name` on `GET /v1/me` with the token, read and kept alone (never the email or an id), and a null or unreadable name still finishes the sign-in, with no name. Errors from `/cli/token` are `{"error": "<words>"}`. The token is kept in the credential file and put only in the `Authorization` header of calls to that origin: never logged, never in a URL, never in an answer to the page (which learns `signed_in` and a name). Then the space is claimed (`POST …/claim`, the token as Bearer, no body; a `200` alone says it is the person's now; after the page claimed it, the same answer again), and what waits is sent (a run not finished, or something new; never an approval). One claim per plan at a time: a second Keep joins the first (`busy` in the status, Keep disabled), a run going without the sign-in is stopped first, and no run starts while a claim is going. A claim that lost (`409 claim_conflict`) means someone else kept it first; a `401` forgets the token; anything else (`404 workspace_not_found`: not available) changes nothing. Claiming a space that is already the person's own answers the same again. When the Inbox goes down, its runs are stopped and its sign-in listeners closed (`stopped()` on the capability). Where the Inbox runs on another machine than the browser (`isRemoteSession`), a loopback sign-in cannot come back: the panel says "Sign in from your own computer." There is no sign-out on screen (the design shows none). **Stop sharing** (Details, a kept space only) deletes the space and the record; a space nobody kept cannot be deleted, by anyone.

**The screen** (`PlanShare.tsx`). The button is at the right end of the top bar (the frame's page actions; on a phone the bar's end slot, so it stays on the first row). It reads Share, Sharing, Shared or Update, with a mark when it needs a look (a stopped page, a space someone else kept, a run that did not finish). The panel is Base UI's Popover under it, a sheet from the bottom on a phone (the Inbox's `ib-oq-pos` and scrim). No keyboard shortcut is added. Each state shows the approved words only (`SHARE_WORDS`; one addition: "Copy link" reads "Copied" for a moment). The page reads `GET /share` when it opens, after its own writes, when the window comes back, and every 600 ms only while an upload, a sign-in or a claim is going, panel open or not (the Inbox reads the plan once for those, not on every ask). The link's "Open in Spaces" and "Invite" are plain links to `share_url` in a new tab (the service names no address for a space's people page); a stopped page's "Open in Spaces" opens `share_url`, the space itself. Only an http(s) link is ever drawn. Details holds its 20 words: when more rows apply than fit, the rows about what stays give way, the dates first; a file or a page too big to go is always said (`detailsRows`).

**Not yet.** The plan review and annotate windows (and replacing their older share), the helper that finishes an upload after a window closes, a Pi twin (none is needed while only the Inbox shares), a sign-in by code for a remote window, "Share opened files only". `scripts/spaces-share-e2e.ts` is the manual check against a real Spaces server (skipped unless `SPACES_E2E_URL` is set; never part of the test suite). Its `read back` line says, for the main page's newest version and one comment as the server reads them, whether `imported` is there and `author` is null. Run on 2026-11-19 against a test copy with no account (before the imported shape): the create with an id made here, all versions and newest by `If-Match`, pages, files, a file with a page's extension as a page, a comment and a reply replayed by their `Idempotency-Key`, an Update and a run with nothing new all answered as the engine expects; a raw Mermaid save takes `text/vnd.mermaid`. Not run there, because that copy has no sign-in yet: Keep, the claim, the approval, Stop sharing, and what a write to a space someone else kept answers. Its rate limit could not be drawn, so the 429 wait is proven against the stand-in only.

**Who wrote it, and when.** Share this space needs a Spaces server with the imported shape. Every version and comment the engine sends goes through `spaceImportedFields` (`packages/core/space-share.ts`), which makes it the service's "imported" `actor`: `{ "kind": "imported", "at": "<the time of this share run>" }`, one time for the whole run, on the create (beside its first page), every page add and save, every comment and every reply. No author's name, no agent fields and not the version's or comment's own time go, until the owner decides they do; the function already gets its origin (`SpaceImported`: the author's display name, the agent's host, session and name, its own time), so sending them is a change there alone. A file upload carries no actor (its call does not take one), nor does a file here that goes up as a page. A server without the shape refuses the actor (`422 validation_error`, its schemas refuse unknown fields): nothing checks for that, and none is needed, since the switch is off by default with a placeholder address and stays off until the production Spaces server has the shape. Nothing on the panel shows it.

Open on the Spaces side (each changes a line above when it lands): an approve-only visit after an Update (`GET /cli/approve`), a settled answer for a write to a space someone else kept, the people page's address for Invite. Open with the owner: whether the original authors and times go up. The access line says what is true of the space (`access` in the status, from the `visibility` the space answers): "Anyone with the link can edit" while nobody kept it; "Anyone with the link can comment" once it was kept after being shared (the claim leaves its link open to read and comment); "Only you", with the lock, only for a space made signed in, which the space itself calls private. That line stays on one line beside Invite. (The owner's change to the approved panel, which said "Only you" for every kept space.)

### A local space and the hosted one

A later copy of a space kept by a hosted service must be able to take this library as it is. The rules, and where this store does not keep them yet (checked 2026-11-16; "Share this space" above now pushes, and says how it meets each one meanwhile):

- **Versions are matched by content hash, with an ordered list per page.** Kept: a version is its git blob SHA-1 (`gitBlobSha`) and each page's versions are numbered 1, 2, 3 with no gap. Not kept: a page's list may hold one hash twice (a Restore writes the older bytes again, and plan review may submit the same text twice), so a hash alone does not name one place in the list.
- **The server mints ids on push and returns a mapping; local ids keep the same prefix and shape.** Kept: `pln_`, `doc_`, `actev_`, `anno_` and ULIDs. The mapping a push returns is kept in the plan's `share.json` ("Share this space"); the local records themselves hold no remote id.
- **Approvals are stored as page + version + who + when, and imported as history only.** Kept: a decision holds `document_id`, `version_number` and `version`, `at`, and its event's actor. Not kept: the person is the role word `person` (`PLAN_PERSON`), not a display name; and an approval imported from plan review's history on the newest version reads as the current approval (`planApprovalState`), not as history only.
- **Authors and commenters are display or agent names.** Kept for versions (`author_label`, `agent_name`; never an email or a user id). Not kept: a comment carries no commenter name of its own (`author_via: "person"`; the viewer's annotation inside it holds the Tater identity as `author`).
- **Comments are anchored by the quote plus 32 characters on each side.** Not kept: a comment's anchor is the viewer's whole annotation (block id, offsets and `originalText`), with no 32 characters before and after.
- **Page kinds markdown, html, mermaid and graphviz are stored explicitly per page; extensions md, markdown, mdx / html, htm / mmd, mermaid / dot, gv; the extension must match strictly only for the two diagram kinds.** Kept: `kind` on each document, and each version file has its kind's extension (`md`, `html`, `mmd`, `dot`). Not kept: a document's `doc_path` is not checked against its kind (a Mermaid page may name `x.md`), and the other extensions (`markdown`, `mdx`, `htm`, `mermaid`, `gv`) are never read as a kind.
- **Page text: at most 1,572,864 bytes for markdown, mermaid and graphviz; 16,000,000 for html.** Not kept: the person's edit takes up to 2 MiB (`PLAN_TEXT_MAX`, more than 1,572,864), and `addVersion` (plan review's import, an agent's version) has no limit at all.
- **A file: at most 104,857,600 bytes.** Not kept: `addArtifact` has no limit.
- **A path is a page or a file, never both.** Not kept: `addArtifact` does not check the pages' `doc_path`, and `addDocument` does not check the artifacts' paths.
- **The store is exportable as one bundle.** Not kept: the library is plain files under `plan-library/`, but nothing writes it out as one bundle.
