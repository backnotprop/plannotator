## Inbox: Plans

Plans keeps every plan plan review handled, with its versions and decisions, in one library on the person's computer. It lives in the Inbox (the same server and window); there is no separate Plans window. This guide covers the records, the library on disk, the import from today's stores, the switch, the routes, the command and the Plans page in the window. Comments on a plan's Markdown pages, Send to the plan's agent (its own Inbox thread once the first Send made one), editing, Restore and Approve are on the plan page (editing and approvals: approval "plans-editing", `.product/approved/plans-editing/approval.md`); an agent tool comes later.

On screen and in every word an agent may read, it is "Plans", one item "a plan". The words Space, Spaces, Groups and Loops are never used.

### The switch

- config.json `inboxPlans` (`true` / `false`, unset is off): `plansOn()` / `setPlansSwitch()` in `packages/shared/plans/switch.ts`, read on every request.
- On only by the person: `plannotator plans` (no gate: running it is the opt-in, from any shell), or `POST /api/inbox/settings` `{ plans: { on } }` from the window. No agent tool, agent text, skill or `--help` names it (the subcommand is in `HIDDEN_SUBCOMMANDS`; its help is the usage line only).
- `plannotator plans off` (or the settings switch) turns it off and keeps `plan-library/`.

### Off costs nothing

`packages/server/plans-capability.test.ts` holds all of it:

- Every `/api/plans` path is the Inbox's unknown-route `404`, as if absent (as Shape's).
- The library is not opened, read or imported; no file appears under the data dir.
- `GET /api/inbox/settings` has no `plans` key (it is present only while on, as `plans: { on: true }`; the window draws Plans only when it reads that key, see The Plans page).
- Plan review writes exactly what it wrote before (it does not know Plans: `history/` stays the source).
- The Inbox's agent tools, their text and the served tool list are unchanged; only the capability seam and the command reach Plans' modules (a source scan in the same test).
- `plannotator plans …` other than `plans` and `plans off` prints `PLANS_OFF_TEXT` (one line naming `plannotator plans`) and exits 1, starting nothing.

### The records (`packages/core/plans.ts`)

Browser-safe types, id prefixes, pure checks and the version id; no I/O. Field names are snake_case, as stored.

| Record | Id | Notes |
| --- | --- | --- |
| Plan | `pln_<ulid>` | `name` (the primary document's first heading), `project_name` (the `history/{project}` folder), `project_id` / `project_root` (an Inbox project, later), `primary_doc_id`, `status`, `thread_id` (its Inbox thread: the one the first Send from the plan page started), `created_by`, `legacy` (the chains and snapshots it was built from), `last_approval_cleared` (`{ document_id, cleared_at, version_number, from_version_number, approver_names }`: the last new version that cleared approvals) and `last_approval_moved` (`{ document_id, moved_at, version_number, from_version_number, name }`), both absent until the first, and `agent_told` (per page id, the newest of the person's versions a Direct Edits section carried to the agent) |
| Document | `doc_<ulid>` | `kind` (markdown, html, mermaid, graphviz), `title`, `head_version` |
| Version | the git blob SHA-1 (`gitBlobSha`) | `version_number` 1, 2, 3… with no gaps, `file` (`docs/<doc>/<n>.md`), `committed_at`, `source` (`person` for the person's own edit or Restore), author fields, `legacy` (the file it came from), `restored_from` (a Restore only: the version whose bytes it took) |
| Decision | (inside a `decision` event) | `decision` (approved, approved-with-notes, denied, feedback), `version_number`, `feedback`, `feedback_record`, `snapshot`, `moved_from` (an approval the person's own edit carried from that version); who gave it is the event's actor (`author_label`, else the person on this computer, `PLAN_PERSON`) |
| Event | `actev_<ulid>` | the plan's activity; `legacy` names the line or file an imported one came from |
| Look | (looks.json) | per plan `looked_at`, per document the newest version seen |
| Artifact | (its `asset_path`) | a file kept with the plan as it is, no versions: `asset_path` (relative, `isPlanAssetPath`: plain `/`-separated names every disk can hold, so no `.`/`..`, leading dot, trailing dot or space, `\`, control character, `<>:"|?*` or Windows device name such as `CON` or `com1.txt`), `content_hash` (sha256 hex), `content_type`, `size`, `title`, `created_at`. Read and shown; written only by the store's `addArtifact` (tests and a sandbox seed): no agent or command adds one yet. `addArtifact` refuses a path that differs from a recorded one (or its folders) only by case or Unicode form, since the Mac's and Windows' disks hold them as one file; serving (`artifactPath`) answers only when the file's real path is exactly the recorded one under the plan's `files/` (a symlink anywhere below it, or a name the disk folds, is refused) |
| Comment `anno_` | | the person's comment on a version (`comments.jsonl`): `anchor` the annotation, `sent` (`{ at, message_id, to }`) once a Send carried it |
| Reply `reply_` | | type only: not written yet |

Rules the records keep, so a later copy kept elsewhere stays possible (nothing leaves the computer today):

- A version's author is a display name only (`author_label`, with `author_via` and the agent fields): never an email or a user id. The import writes none.
- Events and Looks are local-only: they never go with a plan; a copy kept elsewhere writes its own.
- Of the decisions, only "approved" (and "approved-with-notes") maps to a document approval at a version. "denied" and "feedback", with the person's notes, stay local-only.
- An approval belongs to the version it was given on, the current one only (approval "plans-editing"; `planApprovalsOn`, `planApprovalState` in `packages/core/plans.ts`, one rule for the store, the index and the window). The store's `addVersion` decides as it writes the version, from the new version's authors: the approvals the version before holds clear (nothing to write: approvals are read on the newest version; `last_approval_cleared` in the plan line it writes says whose), except that the person's own edit (`source: "person"`, `author_via: "person"`, no Restore, no agent field) carries the person's own approval to the new version (a decision event on it with `moved_from`, then `last_approval_moved` in the plan line). Those are separate appends after the version lines, not one write: a crash between them reads as cleared, the safe way, since no approval ever survives a change it was not given on. A Restore, an agent's version or any version with an agent in it clears. Past approvals stay on their own versions (history); an imported decision whose version was never found counts as on the first version (`planDecisionVersion`), so an old approval is history there rather than lost. The index line carries `approval` (`planApprovalState` of the main page), so the list never shows an older version's approval as current.

### The library on disk (`packages/shared/plans/store.ts`)

```
<dataDir>/plan-library/
  index.jsonl              one line per plan change (the last line per id wins), for a fast list
  looks.json               the person's looks (written whole)
  legacy-map.json          what the import took from where (written whole)
  <pln_id>/
    plan.jsonl             the plan record, one snapshot per change (a new version that clears or moves approvals adds one)
    docs.jsonl             documents and versions ({ kind: "document" | "version", record })
    docs/<doc_id>/<n>.md   each version as a plain file, readable without Plannotator
    events.jsonl           decisions and activity
    artifacts.jsonl        artifact records (the last line per asset_path wins)
    files/<asset_path>     each artifact's bytes (written before its line)
    comments.jsonl         the person's comments ({ kind: "comment", record } with the annotation in `anchor`, the last line per
                           annotation id wins; { kind: "removed", annotation_id, at } takes one away)
```

Not under `plans/`, which holds decision snapshots (and may be a person's custom folder). The Inbox store's rules (`packages/shared/inbox/store-log/jsonl-log.ts`): one writer (the Inbox server; `plans list` only reads), one line per change in one append-mode write, a torn line skipped on read and never glued to the next one, whole files through a temp file and a rename, folders 0700 and files 0600. A version's file is written before the line naming it; the head is the newest version line, so a crash between lines never reuses a number; `repairIndex()` writes again an index line a crash left behind. Opening the store reads and writes nothing.

### The import (`packages/shared/plans/import.ts`)

Read-only: it reads `history/`, `plans/` and `feedback/` and writes only under `plan-library/`; it calls no writer of those stores (`getPlanDir` creates its folder). It runs as often as asked and never takes anything twice: each record it writes names its source (`legacy`), checked before every add; `legacy-map.json` only makes a second run fast and is rebuilt from the records when lost. The odd cases:

- A `history/{project}/{slug}/` folder with `NNN.md` files is one plan: its files in number order are versions 1, 2, 3…, dated by each file's modified time; the plan's name is the newest version's first heading.
- Chains are never joined. A heading change (a new slug) or the same heading after two quiet days (a new dated slug) is a second plan; two projects with the same slug are two plans. Joining is the person's later merge.
- Missing numbers (001, 002, 004): imported in order and numbered without a gap; each keeps its file name; the chain is listed in the report's `gaps`.
- A file plan review may still be writing (it truncates, then writes: modified less than `PLAN_IMPORT_SETTLE_MS`, 2 s, ago, or a different size or time after the read than before) is not read yet: its chain stops there (`unsettled`), is not marked read, and a later run takes the whole file. The same for a snapshot. An empty `NNN.md` is no version (`empty_files`). The newest file empty: its chain waits there and is not marked read (plan review fills a truncated file in place, which does not change the folder's time, so a mark would skip it for good). An empty file with later files after it: that write is over, the later files are imported. `legacy-map.json` is written only when a chain's entry changed, so a chain waiting on an empty file writes nothing on each pickup.
- Version order is file order, never arrival: a version is never placed before one already imported. A file whose number is below the newest one imported (an empty `002.md` filled after `003.md` was taken) is not imported: it is listed in `late_files`.
- An unreadable file stops its chain there (`unreadable`); the next run goes on from it, in order.
- A folder with no `NNN.md` is no plan yet; annotate's chains (`annotate-…-<8 hex>`), `submissions/` and other files are left out.
- A feedback line of plan review (`surface: "plan"`) is a decision on the version it names (`target.slug`, `target.planVersion`), with the person's notes. A line with nothing to land on yet (its chain is not in the library, or the version it names is on disk but not imported yet) waits, counted in `orphan_feedback`; the map keeps the file's size, the offset after its last whole line read and the waiting lines' byte ranges, so the file is not read again until it grows (then only its new lines), and the waiting lines are tried again only after a run that added versions. A line still being appended (no newline yet) waits for the next run. Other surfaces and torn lines are skipped.
- A decision snapshot is matched by its text (the version's text, or it followed by `\n\n---\n\n` and the notes) to a version of a chain with the same heading. If a feedback line already gave that decision on that version, it is not kept twice (`duplicate_snapshots`); otherwise it is a decision. A snapshot written over by a later decision is a new decision. Feedback lines are read before snapshots; plan review writes the snapshot a moment before its line, so a pickup landing exactly between the two would keep both.
- A snapshot with no matching history (a decision without history) is a plan of its own: the snapshot file as its one version (the plan text and the notes cannot be told apart), its decision, no project. The plan's `legacy.snapshots` names the snapshot (`plans/<file>#<blob sha>`) from its first record, and it counts as done only once it holds its decision: a run after a crash between its steps finishes that plan rather than making a second one.
- Snapshots saved to a custom folder (a browser setting the server never keeps) are not found.
- New versions plan review writes while Plans is on are picked up by the same function: the Inbox runs it in the background once it is up and when the switch turns on, and a request to `/api/plans` runs it again at most every 2 seconds (`packages/server/plans-capability.ts`). The list says `importing: true` only until a whole import has finished since the Inbox started or Plans was turned on; the quick pickups after it say nothing, so a window that reads again while `importing` stops. An import that fails is not tried again on every read: the next pickup waits 4 s, twice as long after each failure in a row, at most 5 min; the error is logged once per distinct message; the list says `import_error` (the message, null when the last import went through), and `GET /api/plans?retry=1` (the window's Try again) runs it now. There is no file watch. The import yields after each chain, snapshot and feedback file, every 10 versions and 25 feedback lines, and after each plan while it repairs the index and rebuilds the map, so a first import of a long history does not hold the Inbox.
- Not yet: `index.jsonl` only grows (one line per change); compacting it (written whole when it holds many more lines than plans) is a follow-up.

### The capability seam (`packages/server/inbox-capability.ts`)

`InboxCapability` (`key`, `on`, `save`, `prefix`, `route`, `settingsWire`, `started`) and `InboxCore` (only `dataDir` and `changed` for now). `inbox.ts` routes (`routeInboxCapabilities`), answers the settings (`capabilitiesWire`, `checkInboxCapabilities`, `answerInboxCapabilities`) and starts (`startInboxCapabilities`, after listen) through the list, and never imports Plans. The route guard is Shape's: off, or reached any way but the owner's window on this computer (the tailnet, a phone's door, a linked machine), `404`; another site `403`; a POST with another page's `serverSession` `409`. Plans is not on any door route. The same windows the routes refuse are never told of Plans: the settings answer and the `event: capabilities` frame carry the capability keys only for a window on this computer that came in by no door (`capabilitiesWire(list, local)`, `capabilitiesFrame(list, changed, local)`), so a phone or a linked window shows no Plans row. Plans is the only capability on the seam; Shape, Routines, the Board and code review stay wired by hand. A capability's agent tool and the window's capability rows come with the first capability that has them.

### The command (`apps/hook/server/plans-command.ts`)

- `plannotator plans`: on, then the Inbox started detached or found (`ensureInboxRunning`), and its Plans page (`<url>#plans`) shown and printed: in the window the person used last when one is open (`POST /api/inbox/control/show` `{ page: "plans" }`, `event: show { page, window }`, as `plannotator inbox --open <thread>` shows a thread), else in a tab opened as `plannotator inbox --open` opens one.
- `plannotator plans off`: off.
- Both save the switch through a running Inbox (`POST /api/inbox/settings` `{ plans: { on } }`, as the window does), so its open windows hear `event: capabilities` and follow without a reload; with no Inbox running, or one that refuses (older than Plans) or does not answer within 5 s, the command writes config.json itself.
- `plannotator plans list`: one line per plan (id, last change, project, head version, decision, "changed, you saw vN", name) from the running Inbox (waiting out its import), else read from the library on disk. Never starts the Inbox, never writes.

### The Plans page (`packages/inbox/plans/`)

The window's page, self-contained like Routines (`client.ts`, `store.ts`, the route and the nav row). Styles in `plans.css`, imported by `apps/inbox/index.css` with its `@source`.

- **Gating.** `usePlansOn(settings)` is true only while the settings answer has `plans: { on: true }`. Off, nothing of Plans is drawn: App passes no `onPlans` to the sidebar, `drawnSidebarItems` leaves `plans` out of the sidebar, its menu and Customize, and `#plans` goes back to the Inbox. There is no Settings row and no `--help` entry. Turned on or off while a window is open, the window follows at once: `event: capabilities` names `plans: { on: true }` while on and `{ on: false }` on the change that turned it off (`capabilitiesFrame` in `packages/server/inbox-capability.ts`), the window merges it into its settings (`capabilities.ts`), the row comes or goes, and a window on `#plans` goes back to the Inbox. A `404` from `/api/plans` (an Inbox that could not tell the window) shows "Plans is off" with a link back to the Inbox. Off, `plans` is never saved either: the window keeps it out of the layout cookie (`setSidebarUnsaved` in `sidebarLayout.ts`, set by `setPlansOn`) but sends the layout whole, so a window that never hears Plans is on (a phone, a linked window) keeps the Plans row's place and hidden state; the server stores a layout without the item of any capability that is off (`saveInboxSidebar` in `packages/server/inbox-sidebar-save.ts`: the lenient read puts back every item a layout does not name, so the read-back check compares that read form), so an off Plans leaves nothing in what the window draws or saves.
- **Sidebar.** Core `INBOX_SIDEBAR_ITEMS` has `plans` (top stack, second under Inbox, hideable). `PlansNav` counts the plans `changed` since the person looked.
- **Hash.** `#plans` (home), `#plans&new` (the get-started screen over a list), `#plans=<pln_id>` (a plan at its newest version), `&v=N` (a version), `&from=A&to=B` (a diff), `&doc=<doc_id>` (another page of the plan, with its own `&v`/`&from&to`), `&file=<asset_path>` (an artifact; it wins over `doc`). The main page keeps the plain plan address. Parsed in `app/route.ts`, written in `app/writeRoute.ts`; switching versions replaces the history entry.
- **Home** (`PlansHome.tsx`). With no plans, or from New plan, the get-started screen (`PlansGetStarted.tsx`): "What do you want to plan?" over a dither (`dither.ts`: an 8x8 Bayer field that settles in ten steps at 12 fps, then stays still; reduced motion or a hidden window draws only the still frame; its ink is `--muted-foreground`, redrawn when the theme changes). Its "Start a plan" shows how a plan arrives (plan in the agent as usual; each review is kept here). An import that failed (`import_error`) is a quiet line on either screen, "Could not read your earlier plans." with Try again (`?retry=1`). Otherwise the list from `GET /api/plans`: search, a project filter when there is more than one, "Since you looked" first, then by project. Each row: name, project, last change, version count, decision, "N new" when `changed`. The decision is the newest version's only (approval "plans-editing", `summaryApproval` and `approvalWords` in `words.ts`, from the index line's `approval`): "Approved" ("Approved with notes"), "Changes asked", "v4 is new and not approved" when an older version was approved, "No decision on v4" when an older one was only sent back, else "No decision"; its mark's tone follows (an older approval is no green mark). A view switch beside the search (the Inbox's `.ib-seg`, two marks named "Rows with previews" and "Compact list", no shortcut) shows the same plans as a compact list instead (`PlansCompact.tsx`): a table, one line per plan (name, project, version, decision, last change, "N new"), each name a link to the plan stretched over its line; "Since you looked" first, then every other plan newest first in one list (`compactGroups`: not by project, as the list has a Project column). Lines show hover and focus by fill. On a phone the table keeps name, decision mark and date, with project and version on a quiet second line. The choice is kept in this browser's `localStorage` (`plannotator-inbox-plans-view`, as the Artifacts wall keeps its size); the rows are the default. Search, the project menu and the empty search are the same in both. A plan never opened shows no marker, so a first import does not mark every plan.
- **Plan page** (`PlanPage.tsx`), drawn from the shared frame, `@plannotator/ui/components/frame` (the Space page screen, PR backnotprop/plannotator#3540; read its README before changing the page, and change nothing inside `components/frame/` from here: a needed change goes to that PR). `apps/inbox/index.css` imports `frame.css` after the theme, with `@source` lines for the folder. The page sits on the frame's ground (`FrameGround as="div" colors="theme"`, filling the Inbox's main column, whose padding is removed). The frame's top bar (`AppRail` dense, `PageHeader`, `Breadcrumbs`; the Inbox's sidebar toggle first) sits outside the cards: on the main page Plans / the project / the plan (Plans / the plan with no project), elsewhere Plans / the plan / the file (the frame's crumbs have three places, so the project is not there). The project crumb is words, not a link: the Plans list's project filter is its own state, with no address. From 768 px each part of the row is a card (`FrameBox`): the frame's rail (`DocumentRailShell`, the Files panel below), the frame's `PageCard` whose top is the frame's `ReadingLine` (its `start` holds Edit and Approve, or Done and Cancel while editing, and its `approved` slot the newest version's approval line, both from `PlanEditing.tsx`, below; at its end the version words, "v4 · newest" or "v2 of 4" with the frame's Back to version 4, "Comparing v1 with v3" during a diff, `comparing`, and the toggle with the number of versions, `count`; the toggle opens and closes the versions), and the frame's `VersionsPanel` docked through `DockedPanelClip` (288 px). The versions are open on first use, closed by the panel's Close (`plannotator-inbox-plan-rail-hidden`, kept) and opened again from the reading line. Short of room (the document keeps 480 px) the rail gives way first, to the frame's `RailSheet` (`docked={false}` from the rail's `onFitChange`, its trigger on the top bar), then the versions, to the frame's `VersionsSheet`; on a phone the frame's `RailSheet` and `VersionsSheet`. The frame's selected, hover and subtle border follow the theme: `colors="theme"` on the ground, and `apps/inbox/index.html` puts `data-frame-colors="theme"` on `<html>` too (the root, so the frame's sheets, which portal out, get it); nothing here sets a `--frame-*` value. A Markdown page is the Inbox's own file pane (`PlanAnnotate.tsx` renders `components/AttachmentPane.tsx`, the very component a Markdown file opens in beside a thread; not a look-alike): its header (the file's name, "from <agent> in <project>", Download, the comments button where the panel folds, Side by side / Full screen, ×), the annotation toolstrip (Select, Pinpoint, Markup, Comment, Redline), the Viewer's own Copy file and Global comment, the comments panel, the contents rail, the typed comment kept as the file's draft (`fileCommentDrafts.ts`), and Full screen with its ⋯ (Download). Each version is one synthetic attachment (`planAttachment`: `plan-<doc>-v<n>`, kind `markdown`, version `current`), served through the file-source seam (`fileSource.tsx`, as the tour does): the text from `/versions/:n`, Download the version's bytes, a comment saved to and removed from the plan library (`POST /:id/comments`, `/comments/:annotation/remove`; `comments.jsonl`, one line per change, the last per annotation id wins; a removal is a line too), and the seam's three optional rules for a plan's own words (`markdownImage`, `markdownLink`, `textBlocks`: the same rules as below). No Open in (a version is not a file in a project) and no pin or reuse. × goes back to the Plans list, as the Plans crumb and the rail head's back do; an Escape never does: the plan page is not a file beside a thread, so the pane's "Escape closes the file" is held at the host (`useCloseNotOnEscape` in `PlanAnnotate.tsx`: an Escape seen in the window's capture phase holds the pane's close until that key is over; the pane is unchanged). Under the pane, Send (`deliver.ts`): the comments on the version on screen exported as plan feedback (`exportAnnotations`, "# Plan Feedback"). Whom it goes to (`planAgentOf`, read again as Send is pressed, `planAgentNow`): the plan's thread once it has one; else an agent live in the plan's project, from the Inbox's live sessions (`GET /api/inbox/sessions`, the list New message picks from; `useComposeSessions`; a session whose project id, folder or folder name is the plan's `project_id`, `project_root` or `project_name`), the session that wrote the plan first when it is one of them (`agent_session`; plan review's history records none, so today the live one), else the one agent matched by the project's id or folder. An agent matched by the folder's name only (an imported plan knows no more; two folders may share the name) is never chosen for the person: New message opens on its own To list, as it does when several are live and none is the plan's. To keeps the parent folder whole for two folders of the same name (`FolderPath`'s `names`, `compose/ToPicker.tsx`: "…/work/trailhead-api", "…/oss/trailhead-api"), so the rows tell them apart where the path is cut. Before the plan has a thread, Send opens New message (`compose/openComposer.ts`, its `onSent`, which `ComposeDialog` calls after the window's own, and with `{ held }` when it was held for another machine) to that agent; the person presses Send there, and then `POST /:id/sent` marks those comments sent (with the message) and records the thread it started as the plan's `thread_id` (the first one stays). Once the plan has its thread, Send is a reply in it at once (`inboxApi.reply` on the thread's id; its idempotency key is the plan, the thread, the comment ids it carries, the version it tells of and its words: the same Send tried again is one reply, and a new Send is never taken for an old one), then the same `POST /:id/sent`. That record is tried again quietly (four tries over about 20 s) and never reported as a failure: the reply went. One that never lands waits in the browser's localStorage (`plannotator-inbox-plan-sent-queue`, at most 50; not Plannotator's cookie `storage`, which holds about ten and rides on every request; a queue an older build kept in the cookie is moved once and the cookie cleared) and is recorded when a plan page opens (`flushQueuedPlanSent`; a 400 or 404 drops it, anything else keeps it for the next page, a 409 too: an Inbox that restarted under the tab). A Send held for another machine is recorded once its outbox entry leaves the waiting list with no notice (`whenHeldDelivered`, `GET /api/inbox/outbox` every 5 s for up to a day; a held New message's thread is that machine's, so it records no thread). A sent comment is an earlier comment in the pane (`earlierRecords`), no longer counted, edited or taken away. With no thread and no agent live in the project, Send is disabled and its line says the Inbox's "No agent is running in <project>" (pressed after the last read changed: "No agent is running in <project> now."); with one, the pane's own chip words ("2 annotations ride your next Send to Claude Code."). After any write of its own (a Send, a version, an approval) the page reads the plan again in place (`usePlan`'s `fresh`). A diagram or HTML page stays read-only in `PlanDocument.tsx`. The frame around it is the frame's. A plan is an agent's text, so what it may do is set once in `planContent.tsx` (`PlanContentRules`) for the document and the diff alike: a picture is drawn only from a `data:image/` URL, any other (`https:`, a path) is a placeholder with its alt text and is never fetched; an http(s) link opens in a new tab; a relative path or any other scheme (`mailto:`, an editor's) is inert text with its target as a tooltip, in Markdown and in raw HTML; an `#anchor` still scrolls the plan; an email autolink (`<a@b.com>`) is inert too. A Mermaid fence that could reach another host is shown as its source, not drawn (`mermaidMayLoad`, `planBlocks`). The rule refuses classes, not Mermaid features (`mermaidMayReachAnotherHost`), with tabs and line breaks removed first (a URL parser drops them): `http:`/`https:` in any case, with or without `//` (`https:host/x` resolves to `host`); `//`; a backslash (YAML, JSON and CSS escapes; a URL reads `\` as `/`); an HTML character reference (`&#` anywhere, or `&` and a letter, with or without `;`: an HTML parser decodes `&#58` too); Mermaid's `#…;` when it can decode to ASCII (a number below 128 or a name not only hex digits, so colours like `#fff;` draw), except `#quot;`; and HTML in a label (`<` and a letter, `/`, `!` or `?`), except `<br>`, `<br/>`, `<br />` and a class diagram's `<<interface>>`. On top: an `img`/`src`/`href` key (then `:` or `=`), `url(`, `@import` and `click` lines. `A & B` (Mermaid's join) draws; `A&B` without spaces shows as source.
