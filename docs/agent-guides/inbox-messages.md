## Inbox: replies and thread actions

**Reply drafts and the Draft label** (approval "inbox-reply-drafts", variant Label, 2026-10-20; record in `.product/approved/inbox-reply-drafts/`, not in this repo). The owner: "I need a way of knowing that I typed a message and haven't sent... 'not sent' is helpful but 1. looks bad. 2. doesn't help me when I'm no longer in the thread".
- **The words are kept per thread as a server draft** (`packages/shared/inbox/reply-drafts.ts`, `inbox/reply-drafts/<thread id>.json`, 0600 in a 0700 folder, written whole; the store reads them at open, `InboxStore.replyDraft` / `saveReplyDraft` / `deleteReplyDraft`). Outside the event log, like compose drafts: no line, no seq, nothing an agent, the MCP, search or the phone's event stream sees. A save is a compare-and-set on `updated_at` (`base`; `409 draft_conflict` with the newer draft); an empty body with no files deletes it (a draft keeps the box's files beside the words, `files`: every attached file, a long paste with its place; see the reply box's files in `inbox-window.md`); a deleted thread or project takes its drafts with it. Routes (`packages/server/inbox-reply-drafts.ts`): `GET /api/inbox/threads/:id/draft`, `POST` the same `{ body, base, base_body?, files_add?, files_remove?, files_place? }` (or `files?`, `base_files?`, `all_files?`, below), `POST …/draft/delete`; same-origin and `serverSession` for the POSTs, another site's read refused. This window's save names its box's file changes since it last held the draft's files: `files_add` (files attached, a long paste with its place), `files_remove` (ids taken out), `files_place` (its long pastes' places now). The store applies them to the draft's files as they are then (`applyReplyDraftFileOps`): a file the save does not name stays, a change applied twice is the same as once, an added file whose upload is gone (sent or swept) is left out without refusing the save (an entry that names no upload id is a `422`), and when the words change, a long paste the save does not add or place (another window's) moves with them (`mapAnchor`, clamped to the new words). With changes the compare-and-set is on the words alone: `409` only when `base` is behind and the draft's words are not the save's `base_body` (another window changed the words). Such a save a step behind (its own words, `base_body`) adds no file the draft lost after the version its `base` names: the store remembers, per draft, each file it dropped with the `updated_at` that dropped it (in memory; a file back in the draft, or the draft gone, forgets it), so a page sending again an add whose answer it lost never brings back a file another window removed since. A save with a list instead (`files`): with `all_files: true` the list is the draft's; without it (an Inbox page of 0.28.46 or earlier, which knew long pastes only, with `base_files`) it replaces only the draft's long pastes, so an older writer never drops a file it does not know (`replyDraftFilesAfterSave`). Going back to an older Inbox (0.28.46 or earlier) after drafts held other files keeps the words but not those files: its reader drops every file that is not a long paste, its next save of the draft writes it without them, and its 24 h sweep deletes their uploads (they were pending, and it sees no draft naming them). The reply route's `clear_draft: "<updated_at>"` (the window puts it on every reply that carries the draft, naming the `updated_at` it was saved as, `''` when it knows none) settles the draft with the Send (`settleReplyDraftAfterSend` in `@plannotator/core/inbox-reply-draft`, `InboxStore.clearSentReplyDraft`): still that draft, its words and the files the reply carried go, and a file the reply did not carry (a phone or an older page that sent the words alone) stays as a draft of files only; an older `updated_at` deletes it only while it holds exactly the reply's `words`, trimmed, and only files among the reply's `uploads` (another window's newer, different draft stays, one with a file the Send did not carry too; the match covers a save whose answer the window never read, a file alone with empty words included); a Send without it (the phone app's) leaves it. The files any reply carried leave every reply draft (`dropSentUploadsFromReplyDrafts`). A save may name `base_body`, the words that window saved last: a draft still holding them is accepted as the window's own even when `base` is a step behind (a save whose answer the window never read, or the page's last save as it goes). A change sends `event: drafts` `{ thread_id }` on every window's stream (windows only, and `InboxStore.onReplyDraftChange` in-process, which search uses to drop the thread's cached facts so its status filter follows), and the window reads the list and the Drafts again, and the open thread its own draft. A row's comment count is kept per thread as annotations change (`unsentAnnotations`), never scanned.
- **The window** (`packages/inbox/replyDraft.ts`, `useReplyDraft`; `components/DraftLabel.tsx`): typing saves after a 500 ms pause (`REPLY_DRAFT_SAVE_MS`), leaving the thread saves what waits at once, and a page going away sends it with `keepalive` (`pagehide`). Opening the thread puts the words back in the box, open but without focus (the thread's keys and the page keep working). Cancel and Escape keep the words; Discard (the link beside "Saved 4:43 PM" under the box) drops them; the Send that carries them clears them. Each save uses the `updated_at` this window last knew for that thread (kept per thread, also for the save made on leaving a thread). When `event: drafts` says the thread's draft changed (another window, or a Send from the phone), the window reads it (`reload` with the box's words): unchanged since its base, nothing moves; changed, and the box has no edits since its last save or read (or is closed), the window takes the new draft and the box shows its words, or closes when the draft is gone ("This reply changed / was sent or discarded in another window", said in the thread's live region); changed while the box HAS edits, the base does not move, so the window's save (made at once) is refused. A refused save (`409 draft_conflict`) is never written over: the window adopts the draft as the server holds it. When both windows hold words (this box is not empty and differs from the server's), its words stay in the box, not saved, and one line above the box says "Not saved: this reply changed in another window." (or "…was sent or discarded…"), with **Keep mine** (saved over it) and **Discard mine** (only this window's words go: the box takes the other window's words, or empties); the line is not a live region but is said once in the thread's live region when it appears, the textarea names it in `aria-describedby`, focus goes back to the textarea after either button, and the two buttons stay on one line 20 px apart (24 px on a phone), wider than their hit areas reach. An empty box (a delete) or the same words refused shows nothing and never deletes the other window's draft. A Send claims the thread when it starts (`claim`): what waits is saved, every save in flight is answered, the thread's generation is raised (a save queued earlier does nothing) and no save of it runs until the Send ends (`sent`) or fails (`release`); the box is read-only meanwhile (`readOnly`, and its changes are ignored). A Send that fails without a clear refusal (no answer, or a 5xx) after the reply carrying the words went out is read back: the thread is read for a reply with that idempotency key. Found, it went: the Send is finished as if its answer had come (the box closes, the files it carried leave it, the draft is done with, "Your reply went." in the live region). Not there: the words are saved again and the next Send is an ordinary new Send. Not known (the read failed too, e.g. the Inbox is down): the draft stays as it is on the server, the box keeps the words, and the key, the words and what the Send carried (uploads, comments, picks) are kept for that thread (`unconfirmed`). It holds only while the box keeps exactly those words: it is forgotten when any thread read shows the reply landed (and, the box still holding those words, the Send is finished then: the box closes, "Your reply went."), when the words change or the box empties, when the person leaves the thread, and after 10 minutes. The next Send of those words first reads the thread for that key: found, the words' Send is finished and nothing goes again, and anything added since (a comment, a pick, a file it did not carry) stays and is named ("Your reply went. Not sent yet: 1 pick. Press Send to send it."), for an ordinary Send; not there, an ordinary new Send; still unreadable, nothing is sent; the thread deleted (404), "This thread was deleted, so nothing was sent." When the words change or empty, or the box closes, while such a Send is remembered, the thread is read for it and the line says where it is ("Your earlier reply went; Send sends your edited words as another reply.", or "may have gone"; a closed box's draft copy is read again, so no stale "Draft · Your reply" foot stays), and the draft this window's own Send may have cleared is expected (`expectOwnClear`): a save refused for that reason saves the edited words as the new draft, never a conflict line about "another window". Nothing is ever replayed from memory: a later Send always carries what is in the box and the thread now, to the message it answers now. Words a conflict left unsaved are kept per thread at module level (`conflictWords`), so closing or switching the thread never loses them: they come back in the box, with the line, when it reopens. The Send names the draft its words were saved as in `clear_draft` (`''` after a conflict, so the other window's different draft stays and the foot shows it after the Send). A drafts read (`reload`) applies only the newest answer, reads again (after the window's queued saves and Discard) when this window's own save, Send or Discard answered while it was out, and gives up after three reads, judges the box's words as the answer comes, and never writes back words a Send claimed or sent (a read answered after the Send would otherwise bring the sent words back as a draft). A save with no answer (a dropped connection, a suspended page) is read back, and the keepalive save on `pageshow` from the back/forward cache: the draft holding those words becomes this window's base. Who sends `base_body`: every save the window makes names the words of its last save sent for that thread, answered or not (forgotten after a Send or Discard, and a refused save does not count); the page's save as it goes names the words of the last save queued. The foot's Send (box closed) reads the draft again and carries it as it is now. The page's save as it goes is sent with `keepalive`, and none while a Send holds the thread or after a conflict. A browser refuses a `keepalive` body over 64 KiB, so `keepaliveBody` keeps it under 60 KiB (`KEEPALIVE_BODY_MAX`): when the words and `base_body` together are larger, the save leaves `base_body` out and stands on `base` alone (a save whose answer had not come back yet then makes it a conflict, and that last edit is lost); words alone over 60 KiB go as a plain request, which a browser may cancel as the page goes. The restart guard (`unsentReply`, `unsent.ts`) and a `beforeunload` question ask while a file the draft does not hold yet (still uploading, waiting for its save, another machine's thread), a file landing in a closed box's draft, a save on its way, a conflict's words, or words a refused save left (`refusedThreads`: a `validation_error` not about the length, or a save with no answer not found when read back that carried words or an added file, until a save lands, Discard or Send) would be lost (`replyDraftUnsaved`); a restart the person already confirmed is not asked again. The `beforeunload` listener is registered only while something would be lost (a page with one runs it before every navigation, and some browsers keep it out of the back/forward cache). Files in the reply box are kept in the draft, as pending uploads the upload sweep keeps at any age.
- **"Draft" replaces "Not sent" everywhere**: the question card's tag "Draft" and footer "Picked 4:35 PM · in your draft"; the folded line's "1 pick in your draft"; the thread's foot "Draft · 2 picks" (or "Draft · Your reply, 1 comment") before Send and Edit draft (the foot's Send carries kept words too); with the box open, on a phone, "Draft", "Saved 4:43 PM" and Discard on a line above the box, at the right (a 44 px hit area); a computer saves without a word, shows only "Not saved …" (on its own line over the box's row) and its Discard is the bin at the row's far right (approval "inbox-reply-box", T6; after a conflict the bin is "Discard mine" and never deletes the other window's draft). Whom it goes to is the recipient pill's, see `inbox-compose.md`. A save that did not land (refused, or no answer and not found when read back) reads "Not saved. It tries again when you type." in place of the last good time (`failed`, `data-draft-failed`), until a later save lands, a Send carries the words or Discard drops them. A replaced question's pick keeps "Not sent": it is never sent, not a draft.
- **The list row** carries the additive `unsent: { reply_at, picks, comments } | null` (`InboxRowUnsent`, `inboxHasUnsent` in `@plannotator/core/inbox-types`): the count slot reads "Draft · Your reply" / "Draft · 2 picks" / "Draft · Your reply, 1 comment" on a wide row in a list of 1150 px or more ("Draft" in the accent colour, the rest muted; the owner's call of 2026-10-29, full words in full-width mode), and "Draft" alone on narrower wide rows, three-line and phone rows (the short form, approval "inbox-row-byline", option A), with the full words in its tooltip and the row's accessible name; the Drafts page keeps the full label; an older Inbox's row keeps "Answered, not sent". The section rule is the list's rule 9 above. Mark read on a thread holding words or comments keeps it in New, and its toast says "Your draft keeps it in New".
- **Drafts**: the sidebar's Drafts row counts message drafts plus open threads holding unsent work; `GET /api/inbox/drafts` adds `replies` (those rows, each with `reply_preview`, the words' first 160 characters), and the Drafts page lists them under "Replies not sent" above the messages; a row opens its thread.
- **Phones**: the Inbox window on a phone is the same window: its reply box shows the draft's words and file tiles and its Send carries them. The iPhone app's door reads a draft (`GET threads/:id/draft`, contract 7.62, now with every file in `files`) and writes none in v1 (the app composes its own reply); a Send of its words with `clear_draft` leaves the files it did not carry as a draft of files only.
- **Linked machines**: a draft for another machine's thread is not saved (its door takes none), words or files; unchanged.

**Floating reply drafts** (approval "inbox-reply-floaters", 2026-11-07, take "A. One corner" with separate windows; record in `.product/approved/inbox-reply-floaters/`, not in this repo). The owner: when they leave a thread with a draft, it floats bottom right like a mail app's draft windows. `packages/inbox/floaters/`: `model.ts` (the rules, plain functions), `useReplyFloaters.tsx` (App.tsx's one seam: the corner and the windows), `FloaterBox.tsx` (a draft's window), `floaters.css`.
- **Off by default** (the owner, 2026-11-08, 0.28.55; it shipped on in 0.28.54). The switch is Settings → Capabilities → Experimental → "Float reply drafts" ("Keep an unsent reply in a small window in the corner when you leave its thread."; row `data-settings-float-drafts`), config.json `inboxFloatDrafts` through `POST /api/inbox/settings` `{ float_drafts: { on } }`; the settings read carries `float_drafts: { on }`, and every window hears a change in `event: capabilities` (named only while on or when it was the change). `useReplyFloaters` takes it as `floatDrafts` (null until the settings are read). Off: nothing below floats: leaving a thread or closing the box with the down arrow or Escape leaves the draft in Drafts, as before 0.28.54; no draft row in the corner and no draft window. Once read as off, the threads already floating (an upgrade from 0.28.54) are forgotten from `plannotator-reply-floaters` and stay drafts, and an open draft window closes. Ask's window works the same either way; Ask has no row in the corner, so with no draft floating there is no corner.
- **When a draft floats.** Its box closes with words the person typed on this visit: T6's down arrow or Escape in the box (Thread.tsx calls `replyBoxSetAside`), or leaving the thread. "Typed on this visit" is the draft's `updated_at` moving since the thread opened (read from the drafts list's `reply_at`, no request of its own); the closed box's draft is read once its save lands (its `drafts` event), for 5 s. It needs 8 characters or a file (`floatWorthy`). It shows once the person is in another thread (or on no thread): in its own thread the thread's box has it. Sent or discarded anywhere (its row has no words), a day untouched (from when it floated or was last edited), or × ("Stop floating", toast "Stays in Drafts"), it stops floating and stays a draft (`staleFloats`). Picks or comments alone never float.
- **What is kept.** The words only in the reply draft (`replyDraft.ts`, the server's draft): no second store. Which threads float, and since when, in this browser's localStorage (`plannotator-reply-floaters`), shared by the browser's windows.
- **The corner.** One button, level with Send at the thread foot's right end (the foot gives it a 56 px column, `data-rf-room`, as long as there is something for it, so the row never jumps), or 16 px from the window's corner with no thread open. Hovering spreads a list (14 ms stagger): one row per floating draft (the agent's mark, the thread's name, a pencil; × on hover). Ask has no row here (the owner, 2026-11-09: "I don't want that button at all right now"): a minimized chat comes back through Side. A badge counts the drafts. A finger or a key spreads first, then opens. Past 6 rows, "N more in Drafts". With Ask's window open the button sits just left of it; with a draft's window open on a computer it steps aside. It shows only while drafts float, and hides in full screen and while a phone's keyboard is up. It is measured by observers (the page's changes, the foot's size, the window's), never a timer. A phone: a round button in the foot's row (gone while the thread's box is open); a press opens the one draft, or a sheet ("Drafts") with "All drafts".
- **Separate windows.** A draft's window shows only that draft; Ask's only the chat, and Ask's menu never lists drafts. A draft's window is Ask's `ChatFrame` with its own `ChatWindowStore` (drag by the header, the corner grip, full screen, minimize; × stops floating): header "Reply to <thread name>" with the reply arrow and Open the thread (↗), a one-line peek at the agent's last words (a dot when a new one came), then T6's box and row (Send, paperclip, Skills, mic, bin). A computer shows no "Draft · Saved · Discard" line: the box saves quietly, "Not saved …" alone shows over the row, and the bin discards (toast "Reply discarded", Undo). A phone fills the screen and keeps T6's Draft line above the box. ⌘↵ sends; no Escape (Ask's window takes none) and no new shortcut. The window keeps its row while the person empties the words to rewrite them (the draft is gone from the list for a moment); it closes only on Send, Discard, ×, minimize, or a send or discard elsewhere. Discard stops uploads in flight (nothing lands after the bin), the bin is off mid-send, and Undo restores the words and the files (a refused Undo shows a toast). It opens left of Ask's window when that is open, and moves there when Ask opens over it. A phone shows one window at a time.
- **Send.** Words and files to the message the words answer (`wordsMessage`), with the skills block and `clear_draft`, after `claim`, as the thread's Send does for the plain case. Anything the thread's Send decides first goes to the thread: picks, comments or action items waiting, a recipient chosen in the pill, several agents, a hand-off or a taken-over reply ("Open to send"), and an agent found ended at the press (`sendsHere`). Sent: the toast "Sent to <agent> in <project>" with Open.

**Reply with a quote** (approval `.product/approved/inbox-reply-quote/`, option A, 2026-11-11; issue #3109; the window side is "Reply with a quote" in `inbox-compose.md`). The person tells the agent which message, or which words, a reply answers.
- **The route.** `POST /api/inbox/messages/:id/reply` takes an optional `quote: { of, words?, time? }`. `of` is a message in the same thread (not one of the Inbox's own notes). `words` are non-empty and at most `INBOX_MESSAGE_COMMENT_QUOTE_MAX`. `time` is a label the store checks (`inboxReplyQuoteTime`). A bad quote is a `422 validation_error` with field `quote`, `quote.of` or `quote.words`, and nothing is written. A quote with no words in the reply is a `422` on `words`. Without `quote` a reply is exactly as before: an older window sends none, and an older linked machine ignores the field.
- **What the store writes** (`InboxStore.sendReply`, `planQuote`). The reply keeps `quote: { of, words? }`. A lead goes in front of the person's words, after the store's first line ("Answered 1 question.", "Did 1 action item."), so every way an agent reads a reply (a wake, `read_thread`, a Codex queue) carries it. `reply_to`, who gets the reply and what settles it do not change. The lead (`inboxReplyQuoteLead` in `@plannotator/core/inbox-reply-quote`; the words are `INBOX_REPLY_QUOTE_LEAD`, not yet approved word for word):
  - `Replying to your message from 10:04 AM (<id>):` then the message's first words (about 280 characters, `inboxReplyQuoteExcerpt`) as `> ` lines.
  - `Replying to these words in your message from 10:04 AM (<id>):` then the selected words as `> ` lines (a blank line is a bare `>`; cut at 2000 characters with "…").
  - Whose: `your message` (the recipient session wrote it), `my message` (the person's), `<Host>'s message` (another agent, named from `INBOX_HOST_NAMES` only, never an agent's own name). With no time the `from …` part is left out; with nothing to quote the line ends with a period.
- **The wake.** `wakeContext` sets no `replying_to` when the quote names the message the reply answers, so the agent does not read "Replying to" twice. A quote of another message keeps the wake's own `[Replying to …]` line. "Feedback on your messages" is unchanged and comes after the words, as before.
- **The person's words.** `replyWords` (`inbox-folding.ts`) and `withoutInboxReplyQuoteLead` strip the lead, so snippets, the list's preview and the excerpt of a quoted reply show the person's words. The window strips it from a drawn reply only when that message has `quote`. Copy message copies the body as stored, lead included.
- Tests: `packages/core/inbox-reply-quote.test.ts`, `packages/shared/inbox/store-reply-quote.test.ts`, the wake case in `packages/server/inbox-wake-context.test.ts`.

**Saving an answer** (`packages/inbox/pickQueue.ts`; the owner's debug log, 2026-11-02: a dictated "Other" answer queued 81 saves on a phone over a tailnet, and a Send waited 7.2 s behind them). A question card calls `commit` on every change (`QuestionBlock`: each key, each step of a dictation). The window saves a click at once, and typed words after a pause:
- **Typed words wait for a pause** (`packages/inbox/typedAnswers.ts`, 2026-11-10: every key used to save a full copy of the question, 212 MB of `questions.jsonl` for one person, and each save redrew the thread and read the list and drafts). A change that only edits the words of "Other…", a free-text answer or a note (`isTypedChange`) waits `TYPED_ANSWER_SAVE_MS` (the reply box's 500 ms) after the last key. The field draws every key at once from `pending`. The words waiting go at once on: a click or pick anywhere on the cards (a choice, Skip, Accept recommended, the suggested answer's row), the field losing focus, every wait of the line (`settled()`, each Send round and the line closing, Re-ask, Mod+Enter, the stale page's Reload), the pane moving to another thread or closing, and the page hiding or going (`pagehide`, `visibilitychange`: sent with `keepalive`, through the line when no save of that question is out, else on its own at the next revision). The first words on an unanswered question, a choice, Skip and a cleared answer change the question's state, so they save at once. A save that fails with words waiting puts them in the line at once, and they decide.
- **One save at a time, the newest answer next.** A thread's saves run one by one: a save answers its message's questions whole, and each save's revision comes from the one before. While one runs, each question keeps only its newest answer waiting, in the place in the line it first took, so answers to other questions all save, each once.
- **A Send saves what the field shows before its reply leaves** (`forSend()`). A reply names its questions by revision and the server sends what is saved, so the final answer must land first. It waits in rounds (`SEND_ROUNDS`, 3), each the saves running and waiting as it starts, so a change made after the press is saved too. Dictation that never stops cannot hold it: the line closes as the third round starts, those saves land, and the reply goes. No save runs beside a reply: a change after that point waits for the reply to leave, then saves. Re-ask waits the same way. Mod+Enter, with the Send not drawn yet, waits for one round (`settled()`) and then presses it.
- **The rule: no answer the person typed is lost or sent stale.** A question's newest answer not saved stays on the card (it stays in `pending`), the error shows, and it stays owed: the next press (Send, Re-ask, Mod+Enter) saves it first, one try per press, never on its own. While it is not saved nothing goes, so the older saved answer can never go in its place. A revision conflict (another window's answer landed first) follows one rule, `PICK_CONFLICT_RULE` in `packages/inbox/pickConflict.ts`: built as "the later click wins" (the refused save goes again at the revision the refusal names, `current_revision`; after `PICK_CONFLICT_RETRIES` it draws the Inbox's answer), flippable to "first save wins" (the refused window draws the Inbox's answer). Either way quietly: the refusal's own words ("Question q-… changed since you read it") never show. An Inbox that names no revision gets the old path: the words stay and the next Send saves them. A failed save with a newer answer of that question waiting shows no error: whoever waited on it waits for the newer save, which decides, and a wait that ends unsaved always shows an error. A held pick (`InboxHeldError`) counts as saved and the next one goes with the next revision (`inbox-machines.md`).
- **When the words have nowhere to go, a notice says so** (the window's toast, `onToast`, which outlives the pane). A question replaced under an answer: "Pick not saved. That question was replaced, so this answer won't be sent.", and a Send stops for the stale guard, even with no answer saved on it (until a read shows the question replaced, no guard can draw, so the error says why). A save that lands after its question went (the thread saves with `unsent_only`, so it can never reopen what the agent has): "Pick not saved. That question was already sent, so your last change did not go." An answer not saved when the pane closes, or refused after: `Pick not saved. Your answer in "<subject>" did not reach the Inbox.`
- **One read for a run of saves.** Each save's answer already brings the message's questions (`onQuestions`), so the reads wait for the last save (`onPickSaves` in `App.tsx`, which names the questions saving): then the list, the decisions and the drafts (a save that lands after its pane closed: the list). A run whose saves kept every question's state (only typed words changed: `stateKept` on `onQuestions`) reads none of them, since no row, count or draft label moved; on the Drafts page or in decision mode it reads as before. Then and a `question` record of one of those questions that came meanwhile owes one read, at once: for the echo of the window's own save (`ownSaves.ts`), the list, the decisions and the drafts, never the thread or its files, which the pane drew from each save's answer; for anything newer, the usual read (list, decisions, thread, drafts). The echo that comes after the run's read started reads nothing more ("A change costs what it changed" in `inbox-window.md`). Only those records wait, and only while the pane is open: any other record is read as it comes, so a save that never answers holds back nothing but its own question's records, and closing the pane ends that too. A close reads no list of its own, so the rows still wait out the settle (`settle.ts`). A linked machine's `machine` frames are not held. The files are read again only by a real read of the thread, not when a saved pick patches its questions (`onlyQuestionsChanged`).
- **A late read never takes an answer back** (`keepSavedQuestions`; the owner, 2026-11-08: typing in a question's "Other…" field "felt like it was backspacing on me"). A read of the thread the server answered before the last keys were saved can arrive after their saves; taken whole, it put the older answer back in the field, and the next key built on it, so the letters typed since were lost. The pane keeps the questions its own saves brought back and draws the thread read with each question never older than those (a question's revision only grows; a read with the same or a newer revision wins). This covers the "Other…" field, a free-text answer and the Add note box, which all save through the same line.
- Decision mode has its own chain of saves and no backlog: its fields stay on the card until Answer, so a save is one press.

**Replaced questions** (design record, not in this repo; direction A "Quiet"; model agreed with Workspaces).
- An agent supersedes an earlier question of the SAME thread: `supersedes: ["<message id>"]` (every open question of that message) or `["<message id>/<key>"]` on `send_message` (and `submit_guide`, through `SEND_ROUTING_FIELDS`), or a `Replaces: <message id>/<key>` line in a newer block. **Tidy** (owner-approved design, 2026-10-28, the ⋮ variant; the Board's added the same day: "We need a tidy for the board app as well"; simplified the same day: "all I want is just the prompt being sent to agents", quiet, no banner). - Entry: the ⋮ menu (`TidyMenu` in `packages/inbox/components/Tidy.tsx`, Base UI `Menu`) at the far right of the list's header (after Search and New message) and of the Board's header: "Tidy N" (disabled with nothing to ask once read; the plan is read when the menu opens or the pointer reaches ⋮, not after every list read: "Only what changed" in `inbox-window.md`) and "Refresh"; the list's menu then has its four look checkboxes (see "List options" in `inbox-window.md`). No shortcut, no schedule. Tidy opens a popover anchored to the ⋮ (a bottom sheet on a phone): "Tidy · N threads", one checkbox per agent with its count, one Tidy button; nothing else. Progress lives only in that popover (no banner): while a run is shown (24 h) the popover lists each asked agent's state, with the picker under it when there is something new to ask (an agent left unticked, or one the cool-down offers again): Waiting, At its next Inbox call, Delivered, "N threads updated" (only threads that run sent it a note in), Nothing to change (it went idle after delivery and wrote nothing; its last idle transition is kept through later turns and after it ends, `lastIdleOf` in `packages/server/inbox-sessions.ts`, never the per-poll `idleAt`), Session ended (it ended before delivery, or after it without writing or going idle; counted as done). A session that cannot be reached (no wake connection, no MCP call in the last hour) is not offered. A session asked in the last 30 min is left out until the person writes to it again, and one whose last wake is still undelivered is left out whatever happened since (never two prompts queued). A question the person picked and did not send is theirs: never listed, and Tidy never sends anything in the person's name. The list's scope is its project filter (`?project=`); the Board's is the agents that own live cards in view (with the cards' linked threads), honoring the Board's project filter (`#board&project=prj_…`, sent as `?project=`; every project without one).

**The person's own text keeps its line breaks** (owner, 2026-11-02: a reply typed with Shift+Enter read back as one line).
