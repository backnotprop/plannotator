## Inbox: search, notifications, and agent connections

**Search** (design record "inbox-search", not in this repo; owner approval 2026-10-13, "Approve it as mocked, with your recommendations"). The person searches everything the Inbox holds; agents get a read-only search over messages (the `search` MCP tool, below; approval "inbox-agent-search", 2026-10-19, which superseded the earlier "agents get no search tool"). Server: `packages/shared/inbox/search.ts` (the index, pure over the store), `packages/server/inbox-search.ts` (the routes), the text rules both sides share in `@plannotator/core/inbox-search`.
- What is indexed, one document each: a thread (its current subject, following a replaced question's subject, and its thread name as title fields; its project's name); an agent message (its body as text: question blocks, images and link targets dropped, code kept; each question's prompt, context, choice labels and the person's answer; the agent's name); the person's own reply words (`inboxSearchReplyText`: not the "Answered N questions." line, not the answers section); an attachment's name and the last two path segments; a guided review's title; a project's name and root. Not indexed: attachment contents, guide section text, annotation text, image alt text, the Inbox's own set-aside and reopened notes.
- Text rules (`@plannotator/core/inbox-search`, browser-safe, so the window highlights with the same ones): NFKC, default-ignorable code points dropped, case folded, Latin/Greek/Cyrillic accents dropped (U+0300 to U+036F; Japanese voicing marks stay), for matching only. Tokens: maximal letter and digit runs (an ASCII chunk by a char-code scan; any other chunk as word runs of letters, digits and marks, through `Intl.Segmenter` only when it holds a script written without spaces: Han, Hiragana, Katakana, Hangul, Thai, Lao, Khmer, Myanmar). A token under 2 characters is dropped unless CJK. A query is at most 200 characters and 8 terms; every term must match, the last as a prefix. Snippets cut about 40 characters before the first match at a word start, on grapheme boundaries, with an unbroken run over 48 characters (a URL) shortened unless it holds a match; CJK, Arabic and Hebrew runs are never shortened; a long source is windowed first. Marks are `[start, length]` in UTF-16.
- Ranking inside a group: the match tier (the terms as a phrase, then every term as a whole word, then the last as a prefix; inside a tier, every term in the title fields first), then open before archived, then the project open in the list (`current`, ties only, never a filter), then newest. Groups and first-answer caps: Threads 5, Messages 8, Files 5 (attachments and guided reviews), Projects 3; `group=` with `offset=` and `limit` (at most 50) is "Show all". A thread is listed under Threads only when its own title fields (or project name) match; a message is listed once, with the snippet from the field that holds every term (the body, else a question: then `question: { key, replaced }`, the "Question" chip). Archived means resolved and not come back (`inboxRowArchived`); archived rows say so.
- Filters (`project`, `status`, `from`) apply on the server and the totals follow. `status=waiting` is Stopped, Holding and Waiting; `new`, `sent`, `quiet` are those sections of open threads; `archived` the archived. Any status or From hides Projects. `from=me` keeps the person's replies (Files are agents', so hidden); a thread counts for a side that wrote in it. Filters with no words list the matching threads, newest first (20). An empty query with no filters answers `recent` (the 6 threads with the highest `person_seen_seq`: no new storage) and `recent_searches`.
- The index: an inverted index over numbered documents; each document's token ids as varints (0 separates fields, so a phrase never spans two; one pass finds a phrase with a bit run, no look-ahead). The vocabulary and postings (`packages/shared/inbox/search-vocabulary.ts`) are sized for text full of one-off tokens, since a distinct word costs memory however rarely it occurs: word text in one byte pool (ASCII words; others as strings), an FNV-1a open-addressing table that reads ASCII tokens straight from the text and grows incrementally (the old table stays readable while each new word moves 8 of its slots, so no insert pays for a million words), one Int32 of postings per id (a single document inline, more as delta varints in blocks of one shared arena), the last term's prefix through lists keyed by a word's first two characters, and the arrays trimmed when the build ends. About 40 bytes per distinct word. **Identifier-like tokens are not words** (`isIdLikeToken`): 8+ hex characters with digits and letters (commit hashes, UUID parts), more than 8 digits (timestamps), or 16+ letters and digits with 3+ digits switching between letters and digits 3+ times (ULIDs, base32 and base64 ids). Each is posted once under one of 65,536 shared bucket ids, made as first used: an id with a letter by the hash of its first 7 characters, a number by the hash of its whole value (timestamps share their first digits). Beside the bucket id, the document's token stream keeps the id's tail: a number's remaining 16 hash bits, or an id's first 12 characters (whole when it is no longer, else with 21 bits of its whole hash). A query confirms an id from those bytes, so an id query costs about what a word query does however many ids the store holds: an id of up to 12 characters is compared whole, and the text is read only for a number or a longer id whose kept bits all match, to confirm the exact token (`textHasToken`; rare unless the id is there, since a different id must share 32 hash bits, or 12 characters and 21 hash bits). An id with a letter is also found by any start of 7 characters or more (git's short SHA: `9fceb02` and `9fceb02d0ae5` find `9fceb02d0ae598e9…`), compared with the 12 characters kept; a start longer than 12 that is not the whole id is confirmed by reading the text of only the documents whose ids start with those 12 (`textHasPrefix`). Numbers are found by their whole value only, and nothing shorter than 7 characters finds an id. A row is drawn from at most about 8 KB of a long message: the lines around the first token a term matches, case-insensitive (the last term as a token's start, so `re` centres on `retry`, not `there`; `nearFirstHit`, for bodies over 64 KB; the whole body when a term is not plain ASCII). Built lazily on the first search (start stays as fast as before), in slices of 5 ms that yield (`setImmediate`) between messages, so health, the list, the event stream and the bridge keep answering. `store.subscribe` marks what a line touches (a message, its thread's document and facts, a project); a 50 ms timer, and every search, re-index it. A deletion re-reads the store (`store.reloadCount()` changes), and the next search rebuilds; a build that a deletion interrupts is void. Thread facts (section, archived, last time, who wrote) come from `store.listRow`, cached until a line touches the thread.
- `GET /api/inbox/search` while the index is still building waits up to 250 ms, then answers `indexing: true` with the thread count and no groups; the window asks again. `POST /api/inbox/search/recent` writes the last 6 recent searches to `inbox/recent-searches.json` (0600), only when the window opens a result (`{ q }`) or clears them (`{ clear: true }`).
- Access: the loopback window and the owner over the tailnet listener, like every read route (the listener's identity, Host and `Sec-Fetch-Site` checks first). Both routes refuse another site first (`403 cross_origin`, before anything is searched): `Sec-Fetch-Site: cross-site` or `same-site` (a page on another localhost port is the same site), and an Origin that does not name this server (`isSameOriginOrNoOrigin`), because a page that cannot read the answer could still pick the query and time it (a hit takes longer than a miss); the window's own page and a client without browser headers are answered. The recent-searches POST also takes the `serverSession` guard. The phone's door carries `GET search` (contract 7.42; it sends no Origin and forwards no fetch metadata), never the recent searches.
- Measured with `bun scripts/inbox-search-bench.ts` (4,000 threads, 30,000 messages, about 65 M characters, 40 projects, written straight into a scratch store, the client in the same process; Apple M-series laptop): first build about 1.1 to 1.4 s (target 1.5 s; 1.5 to 1.9 s with 1% to 15% of words one-off, on a machine at a load average of about 7), longest slice under 8 ms (at most one of about 250 past it), query server time p95 about 21 to 25 ms over a mix that includes queries of only common words (target 25 ms; `the an` alone is about 28 to 30 ms, because every document holding both words is read for the phrase; most queries take under 10 ms). Index memory (JSC live heap plus typed-array memory after full collections, the store loaded first) against the text it covers: 1.0x with no one-off tokens, 1.2x / 1.4x / 2.1x with 1% / 3% / 15% of words replaced by identifiers, paths and timestamps seen once (`--unique N`), 1.1x / 1.3x / 2.4x with random one-off words instead (`--unique N --unique-words`, 1.5 million distinct words at 15%, the case no identifier rule can tell from words). The memory grows with distinct words and ids, not text, so these mixes are the numbers to watch. Id-dense logs (40 MB of lines each holding a timestamp and a 12-character hash, as 200 messages of 0.2 MB or 20 of 2 MB): an id query, a short SHA, a number or an id in no document takes 1 to 5 ms (0.2 MB messages) or 7 to 14 ms (2 MB messages); one 2 MB message is tokenized in one slice of about 25 ms, since slices end between messages. `--keep DIR` keeps the seeded store, for a look in the window.
- The window (`packages/inbox/search/`): a field-shaped **Search** entry at the top of the sidebar, under the Tater mark and above Inbox (`.ib-sp-entry`, 32 px, `aria-haspopup="dialog"`, the ⌘K / Ctrl K hint at its end), and on a phone a search icon in the list header (`.ib-lhead-search`, shown only under `PHONE_QUERY`; decision D3; the desktop header has none, D2). **⌘K on macOS, Ctrl+K elsewhere, opens search**: the Inbox's one new keyboard shortcut, an owner exception (approval amendment 2026-10-14) to the rule of no Inbox shortcuts until the centralized shortcut system exists, where ⌘K is its first binding. `search/searchShortcut.ts` defines it as a registry scope (`inboxSearchShortcuts`, `Mod+K`) and holds the window's one capture-phase keydown handler (`onOpenSearchKey`, installed by `App.tsx`): only the platform's own modifier counts (`isModKeyHeld`; on macOS Ctrl+K stays the text fields' delete-to-end-of-line), never with Shift or Alt or while an IME composes; it works from the reply box or any field (a chord eats no typing) and prevents the browser's own Ctrl+K; with the palette open it goes back to its input, the words selected; another modal dialog (`dialog[open]`, `aria-modal`) keeps the keys; keys inside an attached HTML page's frame never reach the window. The Search entry shows the keycaps from the registry's formatter (`⌘K` / `Ctrl K`, `aria-hidden`, hidden on a phone) and names the chord in `aria-keyshortcuts`. No other key opens search. The palette (`search/SearchPalette.tsx`) is lazy: `components/SearchHost.tsx` is its one `lazy(() => import('#search-palette'))`, mounted on the first open with no fallback and kept mounted after (`tests/entry-assets.test.ts` keeps every other import out). It is a native modal `<dialog role="dialog">` pinned at `top: max(16px, 12vh)`, `min(680px, 100vw - 32px)` wide, a full-screen sheet with **Cancel** on a phone (`data-phone`). The input is a `role="combobox"` (`aria-expanded`, `aria-autocomplete="list"`, `aria-controls`, `aria-activedescendant`) over one `role="listbox"` ("Search results") of `role="group"`s labelled by their headings; focus stays in the input (a mouse press on a row, a heading or Show all is `preventDefault`ed, and Show all puts focus back in the input, so the arrows go on). Results announce through one live region only (the No matches and error blocks in the list carry no `role="status"`), and an option carries no `title` repeating its own text. Keys are the open palette's own, and its `keydown` never reaches the window's shortcuts (it stops propagation): ↓ ↑ move a highlight that wraps, Enter opens (never while an IME composes; an Enter while a newer query settles opens that query's first row once it lands), ⌘Enter / Ctrl+Enter (or a modified click) opens the hash in a new tab and keeps the palette open, Escape closes a chip's menu, then the palette, Tab walks the input and the chips. The highlight snaps to the first row when an answer lands, never while arrowing; `pointermove` moves it. Typing debounces 120 ms, one request in flight (`AbortController`), stale answers dropped, the last results dimmed (`data-dim`) until the next land; an `indexing` answer shows skeletons and "Indexing N threads…" and is asked again after 350 ms; a failed request shows "Search isn't answering." with **Try again**, the text kept. A visually hidden `role="status"` says "N results in M groups" (or "No matches for …") once per settled answer. Filter chips **Project** (starting on the project open in the list, removable), **Status**, **From** open `role="menu"` lists of `menuitemradio`; a set chip is primary-tinted with a ×, and **Clear filters** appears. "Show all N messages" asks for that group (`group`, `limit=50`) and expands it in place, then "Show 50 more". Rows (`search/model.ts` for groups, labels and hashes): two lines, the matched words semibold, the primary line `dir="auto"` with its full text in a tooltip while cut, the secondary line's user-written parts in `<bdi>` that truncate by themselves (46%), chips Stopped / Archived / Question / Replaced / the file kind; file names cut in the middle keeping the extension and date (`middleCutInboxName`). Every result that belongs to a thread draws the list's thread chip (`.ib-key` / `.ib-keyt`, owner request 2026-10-16: "the chip form, what I'm used to everywhere else in the app"; `MetaLine` / `ThreadChip` in `SearchPalette.tsx`, `rowThreadChip` in `search/model.ts`), first on its second line, where a phone's list row draws it: `[chip] what it is · project · section · time`. A thread row follows the list's rule (`threadChipName`, `packages/inbox/threadChip.ts`, shared with the list: its name, none when the subject starts with the name or there is no name). A message, file or guided review always shows one chip: the thread's name, or with no name the thread's subject in the chip (the row's face; names keep the list's monospace face, except right-to-left ones, `:dir(rtl)`, which the mono face would draw unjoined); the subject chip is left out only when the first line is the subject, begins with it, or is a start of it at least 12 characters long, never for a word met inside the text. The chip's tooltip and visually hidden words carry the whole thread ("Thread: name: subject"; always for a named chip, a subject chip only while cut), and ", " stands for each drawn "·". One flex line: the project and the chip give way together (chip at least 4.5em, at most `min(55%, 24em)`; project at least 2.5em); the lead, section and time keep their place, so nothing leaves the row. The answer carries it additively: `thread_name` on message, file and guide rows, so the phone door gets it too. Opening a result closes the palette and opens it as a row click does (`openSearchResult` in `App.tsx`): searched from a project's list, the list stays on that project, and the route is a new history entry, so Back returns to where the search started (on a phone `‹ Inbox` is the browser's Back to that list, D7); a result in the thread already open (nothing beside it) replaces the entry instead, since once `msg=` drops a new one would equal the last. A `msg=` with no thread is dropped from the address (`stripStrayMsg`). ↓ ↑ and Escape belong to an IME while it composes (the palette's `cancel` too); dismissing returns focus to what opened it. Opening a result with words posts it to recent searches.
- Landing (`Thread.tsx`'s `landing` prop, `search/highlight.ts`): `#thread=…&msg=…` opens the thread, unfolds the message (or its middle fold), scrolls it to the centre, focuses and rings it (`.ib-q-target`; on a phone, where a message has no padding of its own, the ringed message takes 8 px of inline padding inside an equal negative margin, so the ring clears the text and nothing moves; a question's card when the match was in a question, kept in memory by the window), and paints the query's words in that message with the CSS Custom Highlight API (`::highlight(ib-search-hit)`, no DOM change, the header skipped); the first click or key in the thread clears it. Then `msg=` is dropped with `replaceState`, so a reload does not jump again. A reload of a `msg=` link (no query in memory) lands without words.

**The count on the tab** (`packages/inbox/tabCount.ts`; approval "inbox-tab-count", 2026-10-20, not in this repo). The tab shows how many threads hold agent messages the person has not looked at: the rows of the window's latest list read (`GET /api/inbox/threads?archived=exclude`, every project whatever the sidebar's filter) with `unseen > 0`, an archived thread only when it came back (`back_from_archive`). Never the sidebar's waiting-on-you count: an open question the person already saw does not count. The look (opening the thread, seen on sight) clears it. The title reads "(N) Plannotator Inbox" (the title the page loaded with, no prefix at zero; the accessible signal, nothing said in a live region), and the favicon link gets the page's own icon (`/favicon.png`, so the person's favicon style holds) with a badge in the bottom-right corner (white, near-black `#18181B` digits and a 4 px dark ring, one pixel at 16 px: the owner's pick over red, which sat too close to Tater's orange), the number up to nine and "9+" above: drawn once per count on a 64 px canvas as a PNG data URL, an SVG data URL where there is no 2D canvas (happy-dom) or the canvas draw throws (`roundRect` is missing before Safari 16 and Firefox 112), and `/favicon.png` again at zero. It follows the list reads the window already does (the event stream, every look); no new polling, no server change. Tests: `packages/inbox/tabCount.test.ts`, the DOM test `packages/inbox/tabCountWindow.test.tsx`.

**Notifications** (`packages/inbox/notify.ts`; the open page first, no Web Push, no service worker; approval "inbox-notify-every-thread", 2026-10-15, not in this repo).
- What notifies: every new thread an agent starts, the tab in front or not (`isNewAgentThread`: the root's FIRST line, which the event stream marks with the additive `first: true` on message records (`store.messageCursor(id) === line.seq`); a later line of a root (a look, an archive, an Unarchive, even of a thread archived before the page loaded) is never "new", nor is a thread a list read already showed this page); and each new question the event stream brings in, also in front, unless it is in the thread open and visible (ThreadPane's `onScreenChange`: the pane mounted and nothing over it, `covered` or a file over the thread, and the tab in front; `notifiableItems`). Plain news in an existing thread never notifies. Every notification carries one tag (`plannotator-inbox`) and `renotify: true` (`inboxNotificationOptions`), so a new one replaces the last and still alerts; without `renotify` Chrome replaces a notice still holding the tag silently.
- One thread: "<project>: <agent> stopped on you", "is waiting on you", or "started a thread" for a new thread that asks nothing, with the subject as the body. A click opens the thread.
- A burst becomes one notice, "3 waiting in 2 projects" ("3 new in …" when a thread in it asks nothing). A click opens the list. Away, a burst lasts until the tab is back in front; in front, notices within 30 s (`FRONT_BURST_MS`) are one burst; a change between the two starts a new one (`startsNewBurst`).
- **Nothing fails silently.** Every way a notification can fail to reach the person is detected and shown (`askKind` in `notify.ts`, the words in `notifyStatus.ts`):
  - One origin. The browser's permission is per scheme+host+port, so the Inbox has one address, `http://localhost:<port>/` (`inboxCanonicalBaseUrl`, `packages/server/inbox-canonical.ts`; the address it opens and advertises, the thread links agents get, and the spelling plan review shares its cookies on). A browser's top-level navigation of `/` at another loopback spelling of THIS port (`127.x.y.z`, `[::1]`: `Sec-Fetch-Mode: navigate` + `Sec-Fetch-Dest: document`, GET only) answers `307` to it with the query (the browser keeps the `#thread=` fragment), `no-store`. Never for an API, the device door, MCP, a connection route, a frame, a client without fetch metadata, the tailnet listener (`via: "tailnet"`), another port's spelling or any non-literal name (`inbox.plannotator.localhost`, a `PLANNOTATOR_ALLOWED_HOSTS` name). The fixed-address prototype (#1945) removes port drift entirely; it can make its name the one address when it lands.
  - The line above the list (`components/NotificationAsk.tsx`) stays on every load until it is resolved: `moved` (allowed at another address of this computer, `allowedOrigin`, and none here: the Inbox changed port or was opened at 127.0.0.1) shows at once, prominently, with **Allow**; `ask` (the browser has not been asked) once the Inbox holds a thread; `blocked` (the browser blocked this address) a quiet line with **How to allow** (Settings → General) and **Hide**, also only once there is a thread. On the first-run screen ("No agent has written yet") the same line sits under "Try it" (`EmptyState`'s `ask`, `NotificationAsk` with `firstRun`: "Get a desktop notice when the first question arrives."), from `notifications.firstRunAsk`, which is `askKind` without the wait for a thread, so the first question can notify (owner approval 2026-10-24, the onboarding audit's finding 3). So `ask` and `blocked` ("…no notice when an agent asks you its first question") show on the first-run screen at once, without a thread; dismissed, off, per origin and moved are the same as above the list. Not on a page opened over the tailnet (another device; the first run is set up on this computer). Both lines (and "tab slept") wait until this load's one-time dialogs are decided: the sound claim settled and the agent-note dialog shown or not (`askLinesFree`: `soundSettled`, `agentNoteSettled`), so a dialog never opens over a line the person may be pressing; they stand down while one is open, come back on the same load after the note dialog closes, and wait for the next load after the sound dialog. "Not now" / Hide (`dismissed`), turning notifications off, or a Block in the browser's own prompt ends it; closing the prompt without an answer does not. A grant made in the browser's site settings while the page is open records `allowedOrigin` (once per page), so a later port change reads as `moved`.
  - The permission is read live: the Permissions API's `change` event, plus a fresh read on every `focus` and `visibilitychange`.
  - Settings → General: the status (`On for this address`, `Off`, `Not allowed in <browser> for this address` with **Allow**, `Blocked in <browser> for this address` with the browser's own steps for this address), **Send a test notification** while on (its own tag, `plannotator-inbox-test`, so it never replaces a real notice; "Didn't see it? Check System Settings → Notifications → Google Chrome, and Focus." on macOS, since a browser reports `granted` while macOS or Focus hides it), and "Notifications reach you" (below).
  - Which windows can notify (`packages/server/inbox-windows.ts`): notifications come only from an open Inbox tab. Each window opens its event stream with `window=<id>&permission=…&origin=…` and reports a change with `POST /api/inbox/window`; the server counts windows holding a stream (or served by one: see "One event stream per browser" below) and those whose browser said `granted` (a record outlives its last stream by 15 s, `WINDOW_GRACE_MS`; the URL's `permission=` is what the page had when it first connected, so the page reports again on every `hello`, i.e. every reconnect, past the grace and across an Inbox restart: `reportWindow` via `subscribeInboxEvents`' `onConnect`), in memory only. `notify_reach: { enabled, windows, allowed, allowed_origins }` rides `GET /api/inbox/health`, `GET /api/inbox/settings` and an `event: reach` frame on every window's stream (only streams with a `window=` id; never the phone's door, contract 7.9) when it changes, so "Notifications reach you: yes, through this tab / another Inbox tab (localhost:61000) / no: no open Inbox tab may notify / no Inbox tab is open" is live. Nothing notifies with no tab open; the options for that are a design note for the owner (not built).
  - A tab the browser put to sleep: Chrome's Memory Saver discards a background tab (`document.wasDiscarded` on the reload) and Energy Saver can freeze one (`freeze` / `resume`, 60 s or more: `FROZEN_NOTICE_MS`); the page then says once, under the list, that it could not notify meanwhile, and how to keep `localhost` always active in Chrome. A frozen tab's queued events arrive on `resume` and raise their notices then; an EventSource reconnect resumes from its `Last-Event-ID` (a usable one, a non-negative whole number, now wins over the `cursor` its URL was opened with; an empty or malformed header falls back to that cursor), so a tab whose connection dropped catches up and raises what it missed, once. Background timer throttling does not delay a notice beyond a second: the work after an event is one unchained timer.
  - A tab that may not notify (another origin with no permission, a blocked one) claims nothing (`claimNotices` runs only after `Notification.permission === 'granted'`), so it never swallows an item a tab that may notify would show; claims are per origin (localStorage) anyway.
- State lives in config.json as `inboxNotifications` (`{ enabled, dismissed, allowedOrigin }`), through `GET` and `POST /api/inbox/settings`.
- A notice is raised with `silent: true` only when the bell owns its sound: it is about a question, this tab is away, and the sound is on, armed and no other Inbox tab is in front (`bellCovers`), so Windows and Linux do not chime a second time. Every other notice (a new thread that asks nothing, anything raised in front, the sound off) keeps the system's sound.
- Several Inbox tabs raise each item once: a tab away stays quiet while another Inbox tab is in front (the sound's channel, `otherTabInFront`), and otherwise the first tab to claim the item raises it (`claimNotices`: claims in localStorage `plannotator-inbox-notified`, kept 10 minutes, under one Web Lock). In front, a thread the person opened leaves the burst.

**One event stream per browser** (`packages/inbox/sharedEvents.ts`; owner-approved). Every Inbox tab used to hold its own EventSource, one HTTP/1.1 connection for the tab's life; Chrome allows six per host, so a seventh tab (and everything else on that origin) stalled (proved against the build before this change: the seventh tab never loads until one closes). Now the tabs of one origin share ONE stream:
- **Leader and followers.** `subscribeInboxEvents` (api.ts) is unchanged for its callers. With Web Locks and BroadcastChannel (and a window id), each tab queues for the Web Lock `plannotator-inbox-events`; the tab holding it (the leader) opens the EventSource (with its own `window=`) and posts every frame (`hello`, `record`, `status`, `reach`, `deliveries`, `drafts`, unparsed) on `BroadcastChannel('plannotator-inbox-events')` (messages `{ v: 1, type: 'frame' | 'leader' | 'join' | 'ping' | 'pong' }`, anything else ignored), and handles it itself; followers only listen. Every tab still runs its own handlers (list reads, notifications with their claims, the sound with its lock), so nothing above it changed. Locks and channels are per origin: `localhost:<port>`, a tab left on an old port and the tailnet address never share. Where Web Locks or BroadcastChannel is missing, or there is no window id, the tab opens its own stream exactly as before. The surface (`packages/inbox/surface`) does not use it.
- **No record missed or twice.** Each tab drops a record whose seq it already passed (its subscribe cursor, its list read's, counts as passed). A new leader opens its stream after the highest seq IT has seen. A tab that learns of a new leader (a handover, or its own join) first fetches what it may lack, `GET /api/inbox/events?cursor=<its last seq>&once=1` (the hello and the replay, then the response ends; not counted as a stream), holding the leader's frames until then, so a tab that slept or whose list read was older than the new leader's start loses nothing. A catch-up that fails (the Inbox restarting) keeps holding: the frames that arrive meanwhile wait (past 5,000 the oldest records go, which the catch-up fetches again), and it is tried again on a timer (1 s, doubling to 30 s) and at the next `hello`, from the same seq, so the gap is never skipped. A replay holds each record's latest line only (`changesSince`), exactly as an EventSource reconnect always did. `prepareInboxEvents()` opens the channel before the first list read, so a frame passed on between that read and the subscription is kept.
- **Handover.** Close, reload, navigation and a crash free the leader's lock; the next tab in the lock's queue leads (measured 1 to 8 ms after the old leader went, 217 ms in the simulated freeze). `freeze` and a `pagehide` into the back/forward cache step down and leave the queue; `resume` / `pageshow` (persisted) join again, as a follower, with a catch-up. A frozen tab is never a candidate.
- **A leader that stops without freezing** (a debugger, a long script in an attached HTML page's frame, which shares the tab's main thread, a phone's browser suspending a background tab) keeps its lock and passes nothing on. So every follower asks: `ping` on the channel every 3 s while the person can see it (`LEADER_PING_EVERY_MS`; at once when it becomes visible or gets focus), every 15 s while hidden (`LEADER_HIDDEN_PING_EVERY_MS`: a notification may still be owed); the leader answers `pong` from its message handler, so the answer proves its main thread runs, and any frame or announcement from a leader counts as an answer. No answer in 2 s (`LEADER_PONG_TIMEOUT_MS`): the follower takes the lock (`navigator.locks.request(..., { steal: true })`) and leads, opening its stream from its own last seq. The old leader learns it when it runs again (its lock request rejects): it closes its stream, steps down, joins, queues again and catches up, as a follower. Until then the server holds two streams (the stopped one and the new); records the two pass on are told apart by seq. A follower takes a leader only from its announcement (or, knowing none, from a frame), so the old leader's last frames never take the tabs back. Measured: Chromium with the leader held by the debugger for 8 s, the tab in front had the stream 3.4 s in, its longest gap without a record 3.2 s, two streams at most, every tab every record once; WebKit with a looping script in an attached page, 3.8 s and 3.7 s. A leader busy for more than 2 s for an ordinary reason is taken over the same way; nothing is lost.
- **Presence (`notify_reach`).** A follower holds no stream, so its `POST /api/inbox/window` reports `served_by` (the leader's window id, `inboxEventsServedBy()`), again whenever its leader changes and on every relayed `hello` (an Inbox restart); the server counts it while that leader holds its own stream, or held one less than the 15 s grace ago (a handover). Only a leader's own stream counts, never one link further: two tabs naming each other are never counted. Each tab holds the Web Lock `plannotator-inbox-window:<its id>` for its life; the leader queues for each follower's (on its `join`), and when the browser grants it the tab is gone (closed or crashed): the leader posts `{ window, gone: true }`. A tab also sends that itself at `pagehide` (a beacon). A gone tab stops counting at once; the followers it served keep counting through the grace. Worst case (the whole browser killed): followers stop counting 15 s after the leader's stream drops (one grace, and the pages hear it then).
- **Health** carries `event_streams` (additive): the event streams open now, windows' and the phone door's.
- **Another site** is refused on `GET /api/inbox/events` (`Sec-Fetch-Site` cross-site or same-site, or an Origin naming another server: `403 cross_origin`), as on the other read routes; the window, the tailnet page (same-origin), the phone's door and agents (no fetch metadata) are answered.
- **With every tab hidden**, a stalled leader is taken over in about 16 s (the next hidden check, up to 15 s, plus the 2 s wait), longer where the browser throttles a hidden tab's timers (Chrome: at most once a minute in a tab hidden for more than 5 minutes; Safari suspends background tabs).
- **A crashed tab** frees its locks when the browser notices the renderer died: at once on macOS (2-3 ms measured), about 3 s on GitHub's Linux runners (CI: the next tab in line led 3.0 s after the leader's crash, and a crashed follower stopped counting 3.3 s after). Should that take longer than a check, the tab in front takes the lock first (the check every 3 s, no answer in 2 s).
- **A catch-up that fails while the tab has come to lead** owes nothing: its own stream replays every line after its last seq, so it clears what it held back and handles its stream (a leader never holds frames for a catch-up retry).
- **Not covered:** Chrome's Energy Saver is believed not to freeze a tab holding a Web Lock other tabs wait for; if it does, `freeze` hands over first. Headless Chrome cannot really freeze a page (`Page.setWebLifecycleState` is a no-op on a visible page), so the freeze proof plays `freeze`, a debugger hold and `resume`.
- **Proofs:** `packages/inbox/sharedEvents.test.ts` (fakes for Web Locks with `steal`, BroadcastChannel and the server's stream, and a paused tab whose main thread runs nothing; closes, crashes, freezes, a stopped leader taken over by a visible and by hidden followers and following when it runs again, a leader that answers never taken over, a failed catch-up keeping its gap, the back/forward cache, a follower behind a new leader, and seeded random lives of up to 12 tabs, with and without stopped leaders), `packages/server/inbox-shared-windows.test.ts` (`served_by`, `gone`, the grace through a handover, two tabs naming each other, the whole browser gone, `event_streams`, the cross-site refusal), `tests/e2e/inbox-shared-events.spec.ts` (Chromium, real tabs in one context, the compiled binary, the server's stream count in every case: 1, 3, 8 and 12 tabs; the old build's seventh-tab stall with `PLANNOTATOR_E2E_BASELINE_BINARY`; the leader closing, reloading, crashing (`Page.crash`), frozen and stalled (debugger-held, no freeze) while an agent writes, with a tab in front; notifications and the sound once; `notify_reach`; an Inbox restart; two origins; no Web Locks; a soak with `PLANNOTATOR_E2E_SOAK_MS`, which also brings tabs to the front and stalls leaders) and `tests/e2e/inbox-shared-events-webkit.spec.ts` (WebKit, with the leader stalled by a looping script in an attached page). **The question sound** (`packages/inbox/sound.ts`; design record `.product/approved/inbox-sound/`, not in this repo). A soft two-tone doorbell ("Ding-dong", the owner's pick of twelve), synthesized live with Web Audio (`DING_DONG`, no audio files).
- When it rings: for a new question in an agent's message (never a plain message, nor a new thread that asks nothing), and only while no Inbox tab is in front (`pageInFront`). It does not depend on notifications being on, allowed or blocked. `notify.ts` calls `onQuestions` after the list read, before any notification rule.
- Once per burst (`decideRing`, pure): the first question rings, a question within 30 s (`RING_BURST_MS`) of the last one stays silent and extends the burst, and a tab coming to the front ends it.
- Several tabs ring once: they share `BroadcastChannel('plannotator-inbox-sound')` (who is in front, repeated every 5 s and trusted for 15 s; who rang, which puts the others in that burst), and a tab rings only while it holds the Web Lock `plannotator-inbox-sound` (`ifAvailable`, held 3 s or until a tab comes to the front; a localStorage timestamp without Web Locks). Another port is another origin, so a tab left on an old port can ring once more.
- Chrome plays sound only after a user activation in the tab. The first pointer, click, touch or key event that the browser counts as one (`navigator.userActivation`; Escape or a modifier alone does not count, and the page keeps listening) makes and resumes the AudioContext ("armed"); before it a ring is skipped. Until then, with the sound on, Settings shows "Click once in this tab to allow sound." under the row; the sidebar says nothing (the "Click to turn on sound" row was removed, approval "inbox-notify-every-thread"): the first click arms it silently.
- Settings: one row under the notifications switch, "Play a sound · when an agent asks you", the volume (10 to 100 in steps of 10, disabled while off; letting go plays it once at that level), Play (always plays, even in front) and the switch.
- The one-time dialog (`components/SoundIntro.tsx`, on the `Modal` shell of `components/Updates.tsx`): "The Inbox can ring now" with Play, one sentence, a notification line only when something needs fixing (not allowed: Allow; off: Turn on; blocked: where to fix it), and Turn it off · Keep it on. Keep it on has the first focus; Escape and the backdrop keep it on; Tab stays inside; Turn it off saves off and toasts "Sound off". No entrance motion.
- It shows once per machine, for someone who used an earlier Inbox. The server decides at start from evidence that predates that start (`inboxUsedBefore`, read before the store, the update state and the registry are written): a recorded `inboxVersion`, `inbox/inbox.json`, a project under `inbox/projects/`, or `inboxNotifications` / `inboxTool` in config.json. Builds 0.28.7 to 0.28.11 recorded no version, so the version alone is not enough. With such evidence, on a release version other than the one recorded, it writes `inboxSound.dialogDueFor`, which waits in config.json until a page claims it, so a `--background` start that ends before any window opens does not lose it; settings answer `sound.dialog_due`. With none (a fresh install) it writes `dialogShownFor`, so the dialog never shows, and the notification ask line ends with "Sound is on." The page asks `POST /api/inbox/sound/dialog`, a compare-and-set from `dialogDueFor` to `dialogShownFor`: only the first ask ever gets `show: true` (other tabs and reloads get false). It waits for the list, for a reply being typed and for an update dialog; the notification ask line does not show on that load. A page that came through the tailnet is always answered false and leaves it for a page on this computer.
- State lives in config.json as `inboxSound` (`{ enabled, volume, dialogDueFor, dialogShownFor }`), through `GET` and `POST /api/inbox/settings` (`sound: { enabled?, volume? }`); one volume for every device.

- Each host checks the knob and the registry once: the Claude Code mod at the process's first `session.start` (so a change applies when Claude Code restarts; it registers the tool from a bundled list even with no `inbox/inbox.json`, see the mod section), Pi when the extension instance loads (each session and `/reload`) and OpenCode at plugin setup (each OpenCode start), where the tool exists only when `inbox/inbox.json` existed then and the knob allowed it. The tool list never changes during a session.
- The session-start reminder (`INBOX_REMINDER_TEXT`, config-only `inboxReminder`, on by default wherever the tool is, once the Inbox has run here): one fixed line, decided with the tool, in each host's cache-safe place: the mod's `prompt.context` block (the tool's full name; under `cc-plugin-sec-default`, the first prompt's `prompt.submit` context, and after each compaction a `SessionStart` `compact` command hook's line), Pi's hidden `before_agent_start` message (`plannotator-inbox-reminder`, once per session, ignored by the Ask-this-session bridge), OpenCode 2's composed system part on requests that offer the tool (primary agents; no-wake wording without `session.prompt`), the end of OpenCode 1's last system part for agents with the tool (no-wake wording). Details in the `inboxReminder` entry under Config-only settings.
- The knob: `PLANNOTATOR_INBOX_TOOL` (`1`, `true`, `on` / `0`, `false`, `off`, `disabled`), then config `inboxTool` (one boolean, or `{ "claude-code", "pi", "opencode" }`, written by Settings), then `INBOX_TOOL_DEFAULTS` (on for Claude Code, off on Pi and OpenCode, which send every tool's full definition with each request) (`packages/shared/config.ts`, `resolveInboxTool`).
- **Claude Code** (the mod, `apps/hook/hooks/mod/inbox.ts`; details in "The Plannotator Inbox" in the mod section):
  - `InboxLink` long-polls on a 1 s tick and submits the wake once the session has been idle for two ticks; a Send now reply (`now`) goes in at once, into a running turn as a user row (`$.session.append`).
  - It claims each reply once (mkdir) and holds a per-session lease, `watcher.json`: the person's last process wins, and the lease goes stale after 20 s.
  - It needs the mod (Claude Code 2.1.287+, not `claude -p`, not Windows).
- **Pi and OpenCode** (`packages/shared/inbox/agent-link.ts`, vendored into Pi as `generated/inbox/`):
  - `InboxAgentConnection` starts a stopped Inbox with `plannotator inbox --background`, through `PLANNOTATOR_BIN`, `plannotator` on PATH, or `~/.local/bin/plannotator`. With no binary, the first result says to install Plannotator.
  - `InboxWake` long-polls, delivers after two idle ticks, checks the reply once more, and claims it with a mkdir of `inbox/claims/<reply id>`. It never interrupts a turn. A Send now reply (`now`) goes in at once: through the target's optional `steer` while the session is busy (its presence is what makes the poll say `send_now`), else `deliver`.
  - Two processes on one session (`pi -c` or `--session` twice; two `opencode2` servers on one database): only the holder of the session's lease, `inbox/leases/<host>-<session>.json` (`{ owner, at, touchedAt }`, `inboxLeaseFileOf` in `agent-link.ts`), polls and delivers. It is the Claude Code mod's rule ported: the process the person used last holds it, renewed every 5 s (`INBOX_LEASE_EVERY_MS`), taken over about 20 s after the holder dies (`INBOX_LEASE_STALE_MS`; released at once on a clean exit), and re-read right before the claim. The claim still keeps a delivery once whatever the lease says.
  - What moves the lease: on Pi, the person typing (an `input` whose source is not `extension`) and a `plannotator_inbox` call, plus a session start. On OpenCode 2 (checked on 2.0.19) typing does NOT move it, only a `plannotator_inbox` tool call does, because the plugin gets no typing events: its event subscription yielded none there. The code would also touch on a user `session.inbox.enqueued` item or a `session.execution.started`, should an OpenCode deliver them. So on OpenCode 2 a process the person only typed into, whose agent never called the tool, has no wake, and the other process still delivers.
  - Pi (`apps/pi-extension/inbox.ts`): the tool is inactive in print and JSON mode. Delivery is `pi.sendUserMessage(text, { deliverAs: "followUp" })` (Send now while a run goes: `deliverAs: "steer"`), confirmed by its `message_start`, and the thread reads "Delivered to Pi".
  - OpenCode 2 (`apps/opencode-plugin/inbox.ts`): the wake is per root session, made on its first tool call or run in the process. Delivery is `session.prompt({ delivery: "queue" })`, never steer except Send now while the session runs (`delivery: "steer"`), and the thread reads "Delivered to OpenCode".
  - OpenCode 1: the tool only, with no wake.
  - Neither package ships `inbox.html`.

**MCP for other agents** (`packages/server/inbox-mcp.ts`, `@modelcontextprotocol/server` 2.2.0, stateless).
- Tools: `send_message`, `read_thread`, `search`, `resolve_message`, `wait_for_reply`, `get_guide_brief`, `submit_guide`; `card` once the Board ships (held back by `INBOX_CARD_ACTION_ON`, see "The Board: cards"). (`list_decisions` and `record_decision` were removed with Decisions, 2026-10; a connection's `plannotator_inbox` never offers them, even against an older Inbox that still lists them.)
- Transports: stdio through `plannotator inbox mcp` (the harness picker's commands use it), or Streamable HTTP at `http://127.0.0.1:<port>/mcp`. The window says to prefer the command, because the port can change.
- Character limits: server instructions stay under Claude Code's 2,048 characters. The question guide rides `send_message`'s description, and `inbox.test.ts` pins that Claude Code's 2,048-character description cut keeps the guide's working part.
- Answers: success is `structuredContent` plus one line. A refusal is `isError` with `<snake_code>: <message>`.
- `wait_for_reply` returns a reply as soon as it lands, or `{ status: "waiting", cursor }` after 50 s.
- Result size, step 1 (the findings are not in this repo). The connections (the mod, Pi, OpenCode) hand the model the result's text plus `structuredContent` as COMPACT JSON (`inboxToolResultText`, no indentation; indented, a long thread read was about 1.5 times the bytes). `wait_for_reply`'s `questions` are the replied-to message's questions as `{ key, state, answer, sent_reply_id? }` (`replyQuestions`), not the window's full records: the prompts and choices are the agent's own block and the body words every answer; `status` and `reply.body` are unchanged (the phone proofs read them through `scripts/inbox-sim.ts`). `read_thread`'s list mode returns one short row per thread (`agentThreadRow`: `thread_id`, `subject`, `thread_name`, `section`, `message_count`, `questions: { open, picked, prompt }`, `last_author`, `last_at`, `last_person_at`, `last_person_message_id`, `unread`, and `resolved_at` on a resolved thread, listed with `include_resolved` or because an agent wrote after the archive), not the window's list row. `last_person_*` and `unread` read past the Inbox's own notes (`isInboxNote`: the set-aside, reopened and 👍 notes). `unread` is the caller's: a person message after the thread's agent-read mark (any agent's read_thread or wait_for_reply), or one addressed to that session (`to`) not yet delivered; the addressed session's own read_thread does not deliver it (only its wake or its own wait_for_reply does), so such a row stays unread until then. (A thread read was then still the whole thread; step 2 below made it a window.) send_message and submit_guide refuse a `thread` shaped like a message id (`msg_` + 26 ULID characters, any case; `refuseIdShapedThread`, checked in `sendProject` before a project is resolved) with `validation_error: thread: "<id>" is a message id, and thread takes a name. To write in an existing thread, pass reply_to <id> instead.`; beside `reply_to` it is refused too (there `thread` may name a person-started thread, and an id is never a name), worded "You passed reply_to, which already places this message: leave thread out". Before, it started a new thread named after the id. Old hosts on a new Inbox get the smaller payloads indented; new hosts on an old Inbox get its full payloads compact. Measured on a seeded 59-message thread (`tests/helpers/inbox-long-thread.ts`, as the hosts render it, before → after): read_thread 154,348 → 99,115 bytes; the list of 17 threads 18,932 → 5,425; wait_for_reply 3,594 → 1,446. Pinned by `packages/server/inbox-mcp-size.test.ts`.
- Result size, step 2: windowed thread reads, text transcripts and agent search (owner's choices: newest 6 in full, the same window on every read, `after` as an option). **Windowed read_thread** (`packages/server/inbox-mcp-read.ts`, `windowedThread`): the header (subject, name, project, participants with message counts, and `open_questions`: every open or picked question of the thread with `message_id`, `key`, `q` (its number as the reply's answers section numbers it), `state`, `prompt`, `choices`, a picked one's `answer`); then the newest `limit` messages in full (`INBOX_THREAD_WINDOW`, 6); the person's earlier messages in full, newest first, while their bodies total `INBOX_EARLIER_PERSON_BYTES` (12 KB: the person's words in the longest thread measured, 17 replies in 46 messages, and what agents re-read most; older ones become one line), each without its "Answers to your questions" section (`withoutAnswersSection`: the answers are on their questions; a reply in the window or expanded is as sent); every other message in range as one line in `thread.earlier` (`id`, `author`, `created_at`, `reply_to`, `words` (the first 120 characters, the person's own words for a reply, a question-only message's first prompt), `bytes`, `questions` as `{ key, q, state, prompt (clipped to 120), answer?, superseded_by? }`, attachment names, guide title, `ack`, `to`). A body over `INBOX_BODY_CUT_BYTES` (16 KB) is cut with a marker naming the `expand` call (`body_bytes` gives the size); the person's newest message (not an Inbox note) is always whole. The 12 KB budget skips a reply that does not fit and goes on with older ones. `withoutAnswersSection` cuts only the section, by the grammar `formatQuestionAnswersSection` writes (heading, the "N of M answered" line, `###` blocks of answer lines), so feedback and a skills block after it stay byte for byte; text that does not parse is not cut. Answers in the text are quoted whole as JSON strings (up to 4,000 characters, line breaks kept). A person's message with `to` carries `to: { host, session, you }` and reads `to you` / `to another session (…)`. A read builds the window first and only then marks read: up to `before` (`readThrough`), and seen only the acks of messages it showed, so a refused or `before` read never swallows an undelivered reply. `message_id` with `thread_id` must be in that thread. `expand: [ids]` and `message_id` show messages whole (as sent); `before` / `after` take a message id or a cursor (number, or digits) and bound the range; a message `before` / `after` left out keeps its questions in `thread.questions` (not open or picked ones, which the header has; for a message older than `after`, only those whose state changed since, `questionLineSeq` or the archive line), so no question's state is ever lost and a read of what is new stays the same size however long the thread (a property test over random windows, `inbox-mcp-window.test.ts`). `format: "full"` returns the old `{ thread: agentThread }` records, unmarked. Messages in full keep the record field names (`id`, `author.kind` (+ `name` for agents), `created_at`, `reply_to`, `body`, `questions[].key/kind/prompt/state/answer`, `attachments[].name/kind/size/path`, `ack { label, at }`, `guide.title`) and drop the bookkeeping (sha256s, mtimes, revisions, idempotency keys, per-message project and thread ids, pickers, inline-image records, `delivery`, `to`, `wakes`); answers drop their copies of key, kind and prompt. The result adds `window` (`limit`, `full`, `lines`, `left_out`, the bounds) and `cursor` (the store's). expand / before / after without a thread id are refused. **Text-complete results**: read_thread (both modes), search and every wait_for_reply answer carry `_meta["ai.plannotator/text-complete"]: true` (`INBOX_TEXT_COMPLETE_META_KEY` in the connection contract) and a text that holds everything their JSON does: the windowed transcript (`windowedThreadText`: a summary line kept from before, the header, the messages oldest first, full or one line, the date printed only when it changes and `reply to` only when it is not the message above, `Cursor N` last), one line per list row (`threadRowText`), one line per search result, and for wait_for_reply a closing `[reply <id> · to <id> · <time> · questions of <id>: Q1 q-… sent: "…" · cursor N · <url>]`. `inboxToolResultText` (contract, so the mod's copy too; Pi vendors it) then hands the model the text alone; send_message, submit_guide, resolve_message and `format: "full"` stay unmarked and keep the appended JSON. An older connection ignores the mark and appends the (now trimmed) JSON after the text; an older Inbox sends no mark, so a new connection appends its JSON as before. **Agent search** (`packages/server/inbox-mcp-search.ts`, MCP tool `search`, in `INBOX_MCP_TOOLS` and the contract's `INBOX_TOOL_ACTIONS`): `query`, `project_path` (filled; the caller's project plus an older worktree project, `threadReadScope`), `all_projects`, `limit` (default 10, at most 50; a larger one answers 50). The project is looked up, never made (`findProjects` on the MCP context: resolveProject's lookup without creation): a folder the Inbox has never seen answers no results with a note, and one whose git did not answer in time (no existing project holds it) answers no results saying so, never `project_unresolved`. It runs the window's own ⌘K index (`searchIndex` on the MCP context, `group: "messages"`), waiting up to 10 s for a first build (`search_indexing` after that), and answers rows `{ thread_id, message_id, author ("person" or the agent's name), at, subject, snippet, question?, project? (all_projects) }` plus `total`. It writes nothing: no store line, no recent search, no agent-read mark. Measured on seeded threads (`tests/helpers/inbox-long-thread.ts`, as the hosts render them, step 1 → step 2, bytes / o200k tokens): a 60-message thread 99,971 / 34,689 → 18,848 / 6,658; 46 messages 76,535 / 26,319 → 14,969 / 5,172; 3 messages 6,065 / 2,032 → 2,652 / 877; the list of 17 threads 5,719 / 1,959 → 2,759 / 1,217; wait_for_reply 1,446 / 523 → 705 / 281. Pinned by `packages/server/inbox-mcp-window.test.ts` (a size budget and a per-message growth bound, the window semantics, the property test, both renderings, search) and `inbox-mcp-size.test.ts`.
- `supersedes` (send_message, submit_guide) is described in its own field (`SUPERSEDES_DESCRIPTION`), which reaches the model whole; send_message's description is cut at 2,048 characters and stays the question guide. `plannotator inbox --help` documents it and the `Replaces:` line ("Only in the Inbox", `INBOX_REPLACES_EXAMPLE`).
- The Inbox-only `Stopped:` / `Holds up:` lines (with the bare-negative rule and an example, `INBOX_STOP_EXAMPLE`) are taught in send_message's `body` field (`SEND_BODY_DESCRIPTION`), which reaches the model whole and rides the `plannotator_inbox` tool's `body`; never in `QUESTION_AUTHORING_GUIDE`, which plan review shares and the skill copies byte for byte.
- The optional question contract lines (`Stakes:`, `Shows:`, `Why:`, `Reversible: no — …`) and picture choices are taught in the same `body` description, after `INBOX_STOP_EXAMPLE`: one paragraph, one example (`INBOX_CONTRACT_EXAMPLE`) and "Most questions need none of these"; never in `QUESTION_AUTHORING_GUIDE`.
