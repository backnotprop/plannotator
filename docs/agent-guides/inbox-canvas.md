## A thread's canvas

Every thread of this computer's Inbox can hold one canvas: a real Excalidraw scene that the person draws on and an agent reads and changes. A linked computer's threads too ("Linked computers" below), no phone relay, no approval record yet.

### The switch

A capability, off by default: Settings → Capabilities → Canvas, last in the main card (`canvas/SettingsRow.tsx`, config.json `inboxCanvas`, `POST /api/inbox/settings` `{ canvas: { on } }`, answered as `canvas: { on }` and sent to every window in `event: capabilities`; `packages/server/inbox-canvas-switch.ts`). Read on every request. One of the one set across linked computers (`INBOX_CAPABILITY_SET_KEYS`, "One set of capabilities" in `inbox-machines.md`): a flip on any of them applies on all, and `plannotator inbox capability canvas on|off` turns it. Off:

- no pen in a thread's header or reply box, and the window loads nothing of the canvas (`canvas/useThreadCanvas.tsx` renders nothing; the pens and the layer are the lazy `canvas/CanvasParts.tsx`, the editor the lazy `#canvas-board`);
- every canvas route answers `409 canvas_off`, `plannotator inbox canvas`'s too (it prints `canvas_off: …` and exits 1); no `event: canvas` or `canvas-job` frame is sent; a reply's `sketch` is dropped (the reply goes);
- `plannotator inbox --help` says nothing of it (on, one line under "Commands and flags", `INBOX_CANVAS_COMMAND_LINE`);
- stored canvases stay as they are: a deleted thread's canvas is not moved aside and nothing is swept.

The agent tool never has a canvas action, on or off (the owner, 2026-11-24: no new action and no new description on the tool; `inbox-tool-budget.test.ts` guards it). A flip takes effect at once for agents too: the command asks the Inbox each time.

### The window

- **Sketch** opens it, from the thread's header and from the reply box's row (`packages/inbox/canvas/CanvasParts.tsx`). The canvas takes the whole window, as Excalidraw does on its own site: tools across the top, the style panel at the left edge beside the drawing. A Thread button at its top left goes back. On a phone Excalidraw uses its own compact layout.
- The layer is a `<dialog open>` put on `document.body`. Every Inbox key handler leaves a dialog's keys alone (`shortcuts/guards.ts`), so a letter pressed while drawing is Excalidraw's tool and never the thread's Reply or Archive. Escape belongs to the drawing. The editor takes the focus as it mounts (`autoFocus`), so a tool key works before any click. No keyboard shortcut was added: the bar's field sends on Enter with Cmd or Ctrl, the reply box's own Send key, and Enter alone is a new line as it is there.
- **Mark.** A thread whose canvas holds something carries a dot on its header's pen button, in the accent colour when an agent changed the canvas since the person last had it on screen (`GET /api/inbox/canvases`, read only by a window that shows a thread's header; `canvasApi.ts` marks; opening the canvas reads with `look=1`). A list row carries no canvas mark (the owner's call): it is as tall and as quiet as without the feature.
- The editor is `@excalidraw/excalidraw`, in the lazy `#canvas-board` chunk (`CanvasBoard.tsx`, `lazyParts.tsx` `CanvasBoardPart`), never warmed with the window's other parts. Its stylesheet is imported as text and put in the page when the chunk mounts; the layer's own few styles are inline, so the window's stylesheet does not grow.
- `build/excalidraw-local.ts` makes Excalidraw run from the Inbox alone: its drawing fonts are packed under `/assets/excalidraw/fonts/` (all but Xiaolai, 12 MB), its CDN fallback address is replaced by that folder, its font subsetter and its picture resizer's WebAssembly are taken out (the window ships none).
- **The bar** under the canvas sends it with a reply. It starts from the words the reply box held (its saved draft), and words left in it go back to the reply box when the canvas closes. Nothing selected: the whole canvas (`canvas.png`, `canvas.excalidraw`, and one picture per freehand sketch). Something selected: only that. The reply goes through the thread's own Send (`Thread.tsx`, the reply part's `files`, `sketch`, `send`, `replace`).
- **After Send** a chip says "Sent" for a few seconds. Once the thread's own delivery mark says a running session has the reply (`ThreadSlot.tsx` `canvasReceived`, the last message's `delivery`), the chip is the agent's icon with three dots; with no session it shows nothing more. When a change lands, each changed thing gets a wash and a pill says who changed what, with Show and **Undo**. Undo takes back that one change (`POST …/canvas/undo`): each thing that still looks as the change left it goes back, what the agent added goes if nobody touched it, and anything the person moved, rewrote or deleted since stays theirs and is named. A second press does nothing. The bar then says "Undone" or "Undone. Yours kept: N". A shape and its label are one thing: an added note the person moved keeps its words.
- A drag that starts on a frame's empty inside draws a selection box. Excalidraw would drag the frame; for the length of the press the frame under the pointer is locked and then put back, with no version change (`CanvasBoard.tsx` `overFrame`).
- Export and import of `.excalidraw` files are Excalidraw's own menu items.
- **Words are never changed.** The Inbox stores an agent's words whole in `text` and `originalText`, with a guessed size. The window wraps and measures them with Excalidraw's own rule (`restoreElements` with `refreshDimensions`, from `originalText`) once the drawing faces have loaded (`facesReady`, `settleText`; the drawing is hidden for that moment), and whenever it takes elements from the Inbox (`restored`, always with the rest of the scene as context, so a label and its shape stay tied). Line breaks exist only in the editor's `text`; reading, names and Undo go by `originalText` (`scene.ts` `wordsOf`).
- **A press that never lifts** (the tab left mid-press, a release outside the page) stops holding an agent's change back: on `pointerup` or `pointercancel` anywhere, on blur, when the tab is hidden, and after 4 seconds without movement (`pressOver`).
- **What a file or a paste brings in is put right once** (`tidy`, `fitPictures`): a place that is not a number is made one, a thing farther than 250,000 from the rest (`scene.ts` `farElements`, `tameFar`) is brought beside the drawing, and a picture three or more times longer than wide gets a readable short side (its own, up to 70% of the view) instead of Excalidraw's few pixels. A file that is not a picture says "Not a picture" for at least 6 seconds; the resizer's uncaught error is taken.
- **The state line** holds one thing: "Thread deleted", something said once (an Undo's outcome, "<agent>'s change failed", "Not a picture"), "Saving…" while a failed save is tried again (4 times, 4 seconds apart), "Not saved" after that (it keeps trying every 15 seconds and when the network returns).
- **Send's label**: "Send selection", "Send all" after the selection was removed by someone else (the chip says "Selection gone"), "Send sketch" for freehand only, else "Send canvas".
- Xiaolai's faces are kept out of the page's font list (`leaveOutUnshippedFaces`): Excalidraw adds them again on every load and export, and each asked for a file this build does not ship.
- On a phone the pill is one 44 px row above the bar, clear of Excalidraw's own top row; the agent is its icon there, and its name beside the icon from 520 px up. The Thread button is 44 px tall.

### What the agent reads

- A selection reply also lists, under "Connected, not selected:", the arrows that touch the picked things and the things at their other ends (one step); they are shown to the session with the rest. Both kinds end with one line, `INBOX_CANVAS_REPLY_HOW` (`packages/shared/inbox/uploads.ts`): "(To read or change the canvas: plannotator inbox canvas --help)". That line and the reply's head are all an agent is handed; the rule "change it only when the person asks; a selection asks you to work on it" is in the command's help.
- A reply sent from the canvas stores `sketch` on the message (`InboxReplySketch`: `kind`, `rev`, `things`, `reading`), written by the server from the stored scene (`inbox-canvas.ts` `replySketch`), never by the window. `inboxSketchBlock` (`packages/shared/inbox/uploads.ts`) puts it under the person's words for the wake, the CLI and `read_thread`; the body stays the person's words.
- The reading is one line per thing, each opening with an id (`packages/shared/inbox/canvas/reading.ts`). A thing is what a person would point at: a box with its label is one thing, and freehand strokes within 32 px of each other are one `sketch`, described in words (closed loops, lines, which way a curve opens, where in the sketch) and sent as one picture. A sketch of up to 40 strokes that makes a common drawing opens with a guess, said as one (`reading.ts` `compositeOf`: a face and its mouth, a crown-like zigzag on top, an arrow, a check mark, a cross, an underline, a circle around a thing). A sketch of more than 12 strokes is said as counts by kind, the typical stroke size, where the strokes gather, and the three largest.
- A thing's words are cut at 90 characters in a reading, which then ends with the call that gives them whole; `things: [ids]` gives all of each thing's words. A thing far from the rest says so and is left out of the size.

### `plannotator inbox canvas`

A command, not an action of the agent tool (`apps/hook/server/inbox-canvas-command.ts`, its `--help` is `INBOX_CANVAS_USAGE`; the route `POST /api/inbox/canvas/agent`, `packages/server/inbox-canvas-agent.ts`; the work, `packages/server/inbox-canvas.ts` `agent`). It reaches the Inbox as `plannotator inbox capability` does: this computer's listener, or a paired cloud agent's agent door (`route`, `inbox-agent-routes.ts`, which names the agent). Who asks is `inbox call`'s caller (`inboxCallerOf`: the shell's session, or `--session`), so the canvas remembers what it showed that session. stdout is the answer's text; a change that did not land is `canvas_unchanged: <the answer>` on stderr, exit 1. Every "next" command an answer offers (`canvasReadCommand`, `packages/shared/inbox/canvas/command.ts`) is one the command takes (`inbox-canvas-command.test.ts`).

- `<thread>` reads; `--in` one frame; `--after` the next page of a cut reading; `--things a,b` exactly those, all their words.
- `--picture [<thing>]` (repeat for more) writes a PNG and answers its path. A paired cloud agent gets a path on the person's computer (no fetch yet). A part three or more times longer than wide and over 2,400 px (`scene.ts` `pictureTiles`) is drawn in up to 8 pieces along its length and all paths are answered, in order; a reply sent from the canvas attaches up to 6 such pieces beside `canvas.png`. A window draws it (`event: canvas-job`); with no window open the last stored picture is cut to the part and the answer says which revision it shows.
- `--do '<json list>'` (or `--do -`, stdin) with `--base <rev>` changes the canvas, all or nothing (`packages/shared/inbox/canvas/apply.ts`): `add` (box, ellipse, diamond, note, text, frame, mermaid), `connect`, `set`, `move`, `remove`, `frame`, `replace`. A thing's whole words name it first, then its whole id (8 characters, as the reading prints it; never the start of one); a name that fits two things is refused with both. Invisible characters are taken out of words (`apply.ts` `seenWords`), except the joiner inside an emoji and the joiner or non-joiner between letters of a script that joins; names are compared the same way. Words with marks that stack on letters are drawn in the plain face (font 2), which carries them. A frame's title is at most 120 characters. An arrow's label is wrapped by the editor to at least 220 px; when that would lie on a thing, the arrow bows through the nearest free spot that holds the label (`routeLabelled`). Mermaid flowcharts and sequence diagrams are converted by an open window with Excalidraw's own `mermaid-to-excalidraw`; other kinds (class, state, ER) come out of that converter as one flat picture and are refused. With no window open the change is refused.
- A loose name (part of a thing's words, any order, a kind word) is taken only when one thing fits and the answer says how it was read; `set`, `remove` and `replace` take only an id or whole words. New things never land on another thing or on a connector's line, and the answer says what the board decided (which side `near` chose, a frame that grew). A thing placed by another (`near`, `rightOf`, `leftOf`, `above`, `below`; also written "next to", `beside`, `under` and the like, `apply.ts` `PLACE_WORDS`; `move` takes the same places) stands 40 px from its edge: a taken spot gives way by sliding along that side first, then by stepping out, inside the thing's frame before outside it. Farther than 120 px, the answer names what is in the way and an arrow ties the new thing to it. `add note` is answered as "added note"; a frame added and filled in one call is answered with what it holds at the end.
- **An agent never replaces the person's change unseen, by construction.** What each session was shown is kept per thing (`told.json`: element id → the look the element had, `scene.ts` `lookOf`, when an answer to that session held the thing's line). A change may overwrite, move, remove, replace or frame a thing only while it still looks as the session was shown it. The comparison is with the element itself, so the log's length protects nothing and unprotects nothing; the log only names who changed it. What shows a thing: a reading that prints its line, the opening list of changes, a refusal that lists it, the session's own change, and the person's reply from the canvas, once it is stored, to the session it went to (so "work on this" lands on the first try). What does not: a read that is refused, a list that was cut, the `base` sent, `picture`. A refusal shows up to 30 things as they are now and gives the call that reads exactly the rest (`things`: ids); the same change then goes through. Session keys such as `__proto__` or `*` name no session.
- A call that names no session is remembered by nothing and shares nothing with another such call: its `base` must be the current rev, and it is shown what changed since the base it sent.
- Every answer (errors too) opens with what others changed since that session's last answer, edits and removals before additions; a list too long is cut at a whole revision and ends with the call for the rest. A change is told with what it was and what it is ("renamed "A" → "B"", "moved from x,y to x,y"), and the list's head says why the revision jumped ("rev 1; now rev 4: 3 changes by the person"). A change refused because a name fits nothing lists the closest things as they are now, and that shows them (`RefError.things`, `ApplyResult.listed`). Several revisions of one thing are told as one change, from what it was at the first to what it is at the last (`CanvasChange.was` and `now`, `whatChanged`); a change that went back is not told, and a text's re-measured size is no change. The person's Undo of the session's change is said in one line that names what went back, what was removed, what went partly back and what was not undone (`changes.ts` `undoneLine`, the log entry's `undone`). An answer to a change is at most 40 lines.
- `packages/server/inbox-canvas.test.ts` holds one test per way this rule was once broken.

### Storage

`inbox/canvas/<thread id>/`: `scene.excalidraw` (Excalidraw's JSON without pictures' bytes), `files/<file id>.json` (each picture once, kept for as long as the canvas lives, so a save rewrites kilobytes and a picture deleted and brought back still has its file), `told.json`, `meta.json` (revision, each session's last look, the stored picture's place), `log.jsonl` (one line per revision: who changed which things), `picture.png`, `pictures/` (cut for agents; each kept a day, the folder at most 200 MB), `undo/<rev>.json` (what each agent revision replaced). Files, not the event log (`packages/shared/inbox/canvas/store.ts`). A save that changes nothing a reader would see is not a revision.

The window's save is merged element by element (`changes.ts` `mergeSave`): the higher version wins, the person wins a tie, and an element the window does not name is one it never had.

A deleted thread's canvas folder is moved to `inbox/canvas/.gone/<thread>-<time>` (`retireCanvas`, on the store's deletion signal), where nothing reads it, and removed 30 days later (`sweepGoneCanvases`, at start and on each deletion).

### Linked computers

A thread's canvas lives with the thread, on its own computer; a window on a linked computer draws on it as on its own (one set of rules: the same routes and merge, `canvasApi.ts` routing every call by `machineOf` through the forward `/api/inbox/m/<machine>/…`).
- The pen: on a linked computer's thread when its list carries the mark `canvas` (`INBOX_LINKED_MARKS`, `linkedMachinesWith('canvas')` in `useThreadCanvas.tsx`); an older computer has none, and its threads get no pen. The marks list reads each such computer's `canvases` too.
- The door (`machineOnly`, so a phone gets its 404; `inbox-canvas-door.test.ts`): `GET threads/:id/canvas` (with `look` and `since`), `GET threads/:id/canvas/files/:id`, `GET canvases`; `POST threads/:id/canvas` and `/undo` (rule 8 `set`: held in the outbox in order while that computer is away; a copy puts the same state again, elements merging by version and a second Undo answering `already`; a delivered one reads that computer's list no further, since a canvas write changes no list); `POST threads/:id/canvas/files`, `/picture` and `canvas/jobs/:id` (raw bodies, rule 8 `file`: sent now or not at all, each with the page's `serverSession` in its query, checked here as an upload's is and dropped by the forward).
- A save to a linked computer is a command, not a draft: it names only what changed since what that computer holds (`partial`, mergeSave keeps the stored order and the version rule), its pictures' files go first (`/files`, now), so the outbox holds small JSON and no bytes (`canvas/farSave.ts`).
- **One held save per thread.** Each save goes to the outbox at once and names only what no save waiting for that computer carries. The forward folds a canvas save into the newest save of the same thread that waits and never left, when nothing of that thread (an Undo, a delete) is queued behind it (`inbox-canvas-fold.ts`, `InboxOutbox.amend`): each element at its higher version, what either removes, the older `have`, under the first save's key. So minutes of drawing while that computer is away are one entry, from any window, tab or reload, and nothing waits only in the editor. The 202 names that entry's key; the board joins what both carry (`joinHeld`). A save larger than the outbox holds (256 KB) goes in parts under it; one thing larger than that alone (a long stroke) is sent at once by the forward while that computer is online, and while it is away waits in the board (`503`) until it is back. A save refused for what it is (`400`, `413`, `422`) is not tried again by itself; the next change tries again.
- **How a held one ended** is its outbox entry (`event: outbox`, the window's outbox handed to the board), never that computer's frame alone, so it also ends when the merge changed nothing there (no frame): delivered, the board takes its answer and clears "Waiting for MacBook: …"; refused, its link removed, or given up, the bar says the outbox's words as an error ("Not delivered: …", "May have been delivered. Check on MacBook.") and what it carried is saved again with the next change. One the window's outbox listed and no longer lists (it is read again whole after a reconnect: only what waits and what did not land) has ended too, how is not known there: the held words go and what it carried is saved again, which changes nothing for what landed. A held Undo ends the same way: its answer's words ("Undone", "Undone. Yours kept: 2", "Already undone"), or the outbox's.
- **A new picture while that computer is away**: its file cannot go yet (`/files` answers `503 machine_offline`), so that picture waits in the board and every other change is saved (held) as ever; the bar says the held words, never "Saving…" or "Not saved". It goes once that computer is back (its state turning online, or a retry every 15 s). One drawn as the page closes then is not sent.
- Live: the far computer sends its `event: canvas` and `event: canvas-job` to a linked computer that asks (`canvas=1`, inbox-peer-link.ts); this Inbox hands them to its windows with `machine`, so the board reads that computer and a window here answers its agent's picture or mermaid job through the forward. The stream asks `canvas=1` only while the canvas is on here (`canvasOn`, asked again at a flip: `canvasChanged`). A drawing job that no window here can draw (the canvas off here, or no window open) is answered at once with `?none=1`: that computer counts the streams it sent the job to (`Job.left`), and once each has said `none` the agent hears at once, without waiting out the job's 8 s (mermaid's 12 s): a picture falls back to the stored one, as with no window open there. A window open on that computer still draws it: `none` is not an answer, only one stream fewer.
- A paired agent on another computer (the agent door, `by.away`) gets no picture path on the person's computer: "No picture: …", with the canvas as text.
- Tests: `inbox-canvas-machines.test.ts` (two Inboxes both ways: reads, partial saves, files, frames, a drawing job answered from the other computer and answered at once with no window open, a save too large to hold, a save and an Undo held while one is away and their outbox ends), `inbox-canvas-forward.test.ts` (the forward against a stand-in door: the large save, no list read per save, saves folded into one while that computer is away, jobs no window here can draw), `canvas/farSave.test.ts` (what a far save names, its parts, how a held one ended), `tests/e2e/inbox-canvas-machines.spec.ts` (two compiled Inboxes in a browser: a picture, an Undo and boxes held as one save while one is away; proof shots in `canvas-machines/`).
