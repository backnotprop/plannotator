## Guides in VS Code

Approved spec: `.product/approved/vscode-guided-review/SPEC.md` (not in this repo; phase 1). The extension's **Guided Reviews** activity-bar view (container title and command category "Guided Reviews"; command ids and settings keep their `plannotator.guides.*` names) writes and reads Guided Reviews with VS Code's own parts. Its code is a second bundle, `dist/guides.cjs`, that `src/guides-loader.ts` loads the first time the view or a `plannotator.guides.*` command is used; the main bundle only registers a proxy tree view and command stubs.

- **Dashboard.** Showing the view from the activity bar opens the "Guided Reviews" dashboard tab once per session (`guides-loader.ts`'s `onDidChangeVisibility`; not when VS Code restores the view at startup, and not when a dashboard, guide or run tab is already open: `openHome({ auto: true })`); the view title bar's home button is "Open Dashboard". With a folder open it leads with this repo (pull request and local-changes cards), recent guides, then PRs waiting on you; with no folder open it shows "Open a repository" and "Guide a pull request by link", then Waiting on you (every repository) and recent guides of every repository on this machine (`listRecentEverywhere`, every shelf under `guides/`). The tree's no-folder rows are the same two actions. Clicking a PR row anywhere (tree or dashboard; `plannotator.guides.openPullRequest`) never opens the browser: it shows the run when one is building that PR, opens the newest saved guide of that PR made at its current head (`guideForPullRequest`; the head from the dashboard's PR list or `gh pr view --json headRefOid`), else starts the Guide flow for it; "Open on GitHub" stays a secondary button. A PR of a repository that is not open (a waiting row of another repo, a pasted link) is guided from a blobless, no-checkout clone of that repository in the extension's storage (`ensureRepoClone`: `gh repo clone <repo> <storage>/repos/<repo-key> -- --filter=blob:none --no-checkout`, made once and reused; its shelf key is the same a local checkout gets), then the usual per-PR worktree; `gh pr view` names `--repo` so a fork's `upstream` remote cannot redirect it. A clone is made in `<path>.cloning-<pid>-<ts>` and renamed into place only when complete (one clone per path at a time in a window; a window that loses the race to another uses the winner's; `*.cloning-*` folders older than an hour are swept), and gets gh as its credential helper in its own config only (`credential.https://<host>.helper` = `!'<gh>' auth git-credential`, the path in POSIX single quotes (`'` as `'\''`, `shellQuoteForGit`) because git runs a `!` helper with `sh -c`, Git for Windows included; the same shape `gh auth setup-git` writes), because `gh repo clone` lends git its credentials for the clone command alone (gh's `AuthenticatedCommand`) and the later fetches of a private repository over HTTPS need them. Whether a PR belongs to the open repository is `isOpenRepository`: owner and repo compare case-insensitively and the host loosely (`ssh.github.com` and SSH host aliases such as `git@github-work:org/repo` are github.com), so the open repository's own PRs never go to a clone; rows of its own PR list pass only the number. When that cannot work (no gh, not signed in, no access) one line says why, with "Open a folder…" and "Open on GitHub". The reader of such a guide reads the open repository only when it is the guide's own, else the clone (made then if missing).

- **Agents.** Any ACP agent can write a guide. `packages/acp-client/agents.ts` holds a small bundled registry (no runtime fetch of the ACP registry, never `npx`): Claude Code (`claude-agent-acp`), Codex (`codex-acp`), OpenCode (`opencode acp`), GitHub Copilot CLI (`copilot --acp --stdio`), Cursor (`cursor-agent acp`, else `agent acp` only when that `agent` is Cursor's own CLI: `altCommandsSignature`, checked by `packages/acp-client/same-program.ts`, which accepts a real path through a `cursor-agent` file or folder without running anything, else a `--version` line shaped like Cursor's dated build `2026.07.08-0c04a8a`, read once per file; another `agent` on PATH, such as Grok Build's `~/.grok/bin/agent`, leaves Cursor not installed, with its install command), Kiro CLI (`kiro-cli acp`), Kilo Code (`kilo acp`, else `kilocode acp`) and Pi (`pi-acp`). Each entry links its source and carries its install command, cheap model/effort defaults, an optional `note` (a capability gap shown in the picker, never a block: Pi's is that pi-acp does not pass MCP servers on to Pi, so it cannot reach the builder tools) and optional `permissiveModes` (used only with automatic approval; the first is the target, and a session already in any listed mode is never downgraded: Claude Code `acceptEdits`, `auto`, `bypassPermissions`; Codex `agent`, `agent-full-access`). No agent is ever refused or disabled, for local changes or pull requests alike. The picker lists installed agents first; a missing one shows its install command. Overrides: `plannotator.guides.agentCommands` (`{ "<id>": { command, args } }`; `plannotator.guides.claudeCode.command` / `.args` still apply to Claude Code), and `plannotator.guides.customAgent.command` / `.args` / `.label` for any other ACP agent. All command settings, `plannotator.guides.autoApprove` and `plannotator.guides.ghPath` are `"scope": "machine"`, so a workspace cannot set them. Model and effort are read per agent and cached per agent (`plannotator.guides.agentOptions.<id>`); effort is the `thought_level` category, else an option id `thinking`, `thinking_effort`, `reasoning_effort`, `effort` or `effortLevel`; the mode is category `mode`, else id `mode`. Saved guides record the agent as `generator.engine` (`claude`, `codex`, `opencode`, …).
- **Your agent, your config (owner decision 2026-10-23: never block an agent; the user's harness config is their responsibility).** Guides runs the agent with the user's own configuration and permissions: no `_meta` on `session/new`, no forced or reset mode, no tool allow/deny lists, no narrowed setting sources, no injected config or env (one exception, below: the path of the user's own CLI). It adds only its builder MCP server, the chosen model and effort, and the prompt (which says a review needs no edits). The client advertises no `fs` and no `terminal` (every listed agent brings its own tools); an agent that calls `fs/read_text_file` anyway is served (regular files up to 10 MB, `MAX_CLIENT_READ_BYTES`), and the unadvertised write and terminal methods answer "method not found" (left out, the SDK would answer `fs/write_text_file` with an empty success). **Permissions:** every `session/request_permission` is shown with all the agent's options (allow once or always, reject once or always) in the generating view (`pendingPermissions`, "Waiting for your approval: …", `webview/approvals.ts`) and in a non-modal notification; the first answer goes back as it is (`GuideGeneration.answerPermission`). The builder's own `guide_*` tools, matched by exact programmatic name or whole title and kind `other` or none, are allowed once without a prompt (`acp/permission-policy.ts`). **Automatic approval (opt-in):** `plannotator.guides.autoApprove` (`off` | `allow-all`), a toggle in the start flow's effort step, or at the first request ("Approve all for this run", "Always approve during guides", which sets the setting); then every request is answered with the agent's allow option (once, else always; a request with no allow option stays with the user, since `cancelled` would abort the agent's tool; "Approve all" from a notification whose request was already answered still turns it on while the run is live; the start flow's toggle, seeded from the setting, decides for that run: `autoApproveChoice`) and the session switches to the agent's first offered `permissiveModes` entry, shown in the run's Approvals stat; a mode that cannot be set is a note. **Bottlenecks** (`state.bottlenecks`, never a stop): a request the user turned down (action "Approve automatically for this run"), a failed tool whose output is Claude Code's deny-rule wording "Permission to use … has been denied" (`blockedCause`; one notice per cause, updated with each tool; generic errors such as `Permission denied`, EACCES or `Operation not permitted` are never read as config, and codex-acp reports declined or sandbox-failed commands only as status `failed`, so they are not guessed at), the agent never reaching the builder's MCP server, and a run that ended after the user turned requests down (action "Resume with automatic approval"; deny-rule blocks are not counted, since automatic approval does not lift a deny rule). There is no tripwire and no mode watcher.
- **Generating.** A Quick Pick picks what (this branch's PR, local changes since the merge base, uncommitted only, another PR by number or link), the agent, and the agent's model and effort, read from the agent's ACP `configOptions` (cached per agent; Claude Code defaults to Sonnet at low effort). The extension is an ACP v1 client (`@agentclientprotocol/sdk`, `packages/acp-client/client.ts`; the agent table, spawn plan, ensure-launch and same-program check are there too, `src/guides/acp/` keeps the adapters and the builder permission policy) that starts the chosen agent with the user's own environment. Resolution order (`resolveAgentLaunch`): the command in `plannotator.guides.agentCommands` (or `customAgent`), the agent on PATH, the npm ACP adapter the extension installed, then install it now. Claude Code, Codex and Pi have an `adapter` in the agent table (`packages/acp-client/agents.ts`), pinned to an exact npm version published at least 7 days before it was pinned (claude-agent-acp 0.91.0, codex-acp 2.2.2, pi-acp 0.0.34); when it is missing and `plannotator.guides.installAdapters` is on (default), `src/guides/acp/adapters.ts` runs `npm install --prefix <globalStorage>/adapters/<agent>/<copy> --ignore-scripts --before=2026-10-16 --save-exact <pkg>@<version>` under a progress notification (`--before`, `ADAPTER_PIN_BEFORE`, holds every transitive dependency to the 7-day release-age rule too: codex-acp's `@openai/codex ^0.160.1` resolves to 0.160.1, not the newest), then points `<agent>/current.json` at the new copy. Every install and "Update Agent Adapters" writes a new copy and switches the pointer, so a run using the old copy (any window) keeps it; a copy that stopped being current is removed 6 hours after it stopped (the switch stamps `.plannotator-replaced.json` into it, so a long run in another window keeps its copy), and unfinished installs and the first layout's `<agent>.installing-*` folders 6 hours after they were made; when `current.json` exists but cannot be read, nothing is removed. Each launch picks the runtime again: `node` on PATH when its version satisfies the package's `engines.node` (`satisfiesNodeRange`: `>=`, `<`, `^`, `~`, `x`, hyphen and `||` forms; an unreadable range counts as unsatisfied), else VS Code's own runtime (`ELECTRON_RUN_AS_NODE=1`). No global install, no `npx`, no sudo. A failure is one line (npm's reason and the manual `npm install -g <pkg>@<version>`) with Retry (`packages/acp-client/ensure-launch.ts`); "Guided Reviews: Update Agent Adapters" (`plannotator.guides.updateAdapters`) reinstalls the copies it made. Pi also needs `pi` itself (`requires`). **The user's own CLI (Guides only: `src/guides/acp/agent-cli.ts`, not the shared package):** claude-agent-acp runs the Agent SDK's bundled Claude unless `CLAUDE_CODE_EXECUTABLE` is set (0.91.0 `dist/acp-agent.js`, `claudeCliPath` and each session's `pathToClaudeCodeExecutable`), and codex-acp runs its `@openai/codex` dependency unless `CODEX_PATH` is set (2.2.2 `dist/index.js`, `startAcpServer`). `withAgentCli` (called by `resolveGuidesLaunch`, the controller's wrapper around the shared `resolveAgentLaunch`, so every Guides launch and the adapter's terminal sign-in get it; the CLIs are `AGENT_CLIS`, keyed by agent id) sets that variable to `findExecutable("claude")` / `findExecutable("codex")` (PATH plus the usual install folders, as Ask AI's `Bun.which`). A value already in the environment is left alone. The adapter keeps its bundled copy when the CLI is not found (someone who uses only the Claude Code VS Code extension has no `claude` on PATH; their guides kept working before), when `plannotator.guides.useInstalledCli` (machine scope, default on) is off, and on Windows when the CLI found is not an `.exe`: an npm `claude.cmd` / `codex.cmd` cannot be started by claude-agent-acp, which spawns the path without a shell (SDK spawn, `--cli` sign-in, `auth status`), and codex-acp's `cli` subcommand uses `shell: true` with the path unquoted. Every launch logs which copy runs (`cliLog`, output channel only, never a notification). When Guides set the variable, the launch carries a `startHint` ("Guided Reviews ran your claude at <path>; it may be older than … Update it, or turn off plannotator.guides.useInstalledCli …"), which the shared `AcpClient` adds (any caller may set `AgentLaunch.startHint`) to a failure before the first session is ready (`initialize`, `session/new`, `session/load`, and `describeFailure`), never to a sign-in error or a stop or time limit (`AcpStartAbortedError`). There is no `--version` floor check. The sign-in terminal is planned in `acp/sign-in.ts` (`planSignIn`): an adapter-listed sign-in gets the launch's env. Tested against the fake agent (`acp/agent-cli.test.ts`; the fake logs `cliEnv` in `initialize`). Agents that are their own program (OpenCode, Copilot CLI, Cursor, Kiro, Kilo) are never installed: "Install <agent>" opens a terminal with the official install command typed in, not run (on Windows the documented PowerShell command, `installCommandWindows`, or the same npm command; Kiro documents none, so there the button is not offered and the message points at its docs). The client offers no client tools but terminal sign-in (`auth.terminal`, so the agent lists its own login commands for the "Sign in" button, which opens a VS Code terminal running them), and refuses an agent whose `initialize` answers another ACP protocol version (it could not speak to it). Permission requests and automatic approval are described above. Windows: an npm `.cmd` adapter is started through its JavaScript entry (`packages/acp-client/spawn-plan.ts`, never through `cmd.exe`); untested on Windows. The builder tools reach the agent through a stdio MCP server, `dist/guide-mcp.cjs` (`src/guides/mcp/relay-script.ts`, run by VS Code's runtime with `ELECTRON_RUN_AS_NODE=1`), which relays each line over a private local socket with a per-run token to `src/guides/mcp/relay-host.ts`; the draft (core's `GuideDraft`) stays in the extension and is written after every call. `src/guides/generation.ts` runs one guide: activity stream, cost from `usage_update`, cancel (`session/cancel`), resume and Save as is. The agent runs as the leader of its own process group: when a run ends, or the agent exits or crashes by itself, the group gets SIGTERM, then SIGKILL 3 s later whether or not the agent itself exited (Windows: `taskkill /T /F`); closing VS Code kills it at once, along with every group still inside that grace (`killPendingProcessGroups`); an empty group is never signalled (its id may be reused), and an exit hook kills the live and pending groups when the extension host exits. A PR is checked out in a detached worktree of its own head, `worktrees/<repo-key>/pr-<n>-<sha7>` under the extension's global storage, so a worktree is never moved under a live run or another guide. Fetches use `--refmap=` (no ref of the user's moves: the PR head from `refs/pull/<n>/head`, the base by its sha, else into a private ref deleted once read); `git worktree prune` never runs (a re-add uses `worktree add --force`); nothing outside the storage folder is created or removed. Deleting a guide, or discarding a PR draft, removes its worktree only when no other guide, draft, run or open reader uses it (`src/guides/worktrees.ts`); deleting a guide also removes a share link from its host first (`src/guides/share.ts` over the shared `unshareGuide`; when that fails the person is warned and decides). The overview diagram is render-checked in a Guided Reviews webview; with none open (a background run whose tab was closed) the guide is saved with `diagramCheck: "unchecked"`, the run and the agent are told, and the reader checks it when the Guide tab opens.
- **Storage.** Finished guides go in Plannotator's guide store (`guides/{repo-key}/{id}.json` + `.patch`, the overview inside `guide`), so the web app lists them and `plannotator guide export` exports them. VS Code-only state (file ticks, `focus` hints, the source and base commit) is a sidecar at `guides/{repo-key}/vscode/{id}.json`; unfinished drafts at `guides/{repo-key}/vscode/drafts/`. The shared store never reads `vscode/`. Plannotator's guide-history switch is honored: with `PLANNOTATOR_GUIDE_HISTORY=0` or `{ "guideHistory": false }` (read at each run) nothing is written, neither drafts nor the guide, its patch or sidecar; the guide stays in memory for the VS Code session (listed as "not saved (this session only)") and the generating view, the dashboard and the finish message say so.
- **Reading: the Guide tab** (approved 2026-10-24, `.product/approved/vscode-guide-reader/`, direction A, "Don't rebuild the reader; host it"; not in this repo). A guide is read in ONE editor tab, a `WebviewPanel` of view type `plannotator.guides.guide` (`vscode/reader-panel.ts`), that runs Plannotator's own guide reader: the guide-viewer chain (`GuideView` → `GuideSectionCard` → `GuideFileCard` → `GuideViewportManager`) over review-editor's `AllFilesCodeView` and Pierre diffs, the same components the review app and guides.show render. Its React app is `src/guides/reader/` (`main.tsx`, `App.tsx`, `bridge.ts`, `ChapterStrip.tsx`, `HoverCard.tsx`, `ChapterAsk.tsx`, `OverviewDiagram.tsx`, `theme.ts`, `reader.css`), built by Vite (`vite.reader.config.ts`, run from `scripts/build.ts`) into `dist/reader/`: `reader.js` and `reader.css` by name, Shiki's grammars as lazy chunks, the highlight worker started as a blob worker through guides.show's `PortableWorkerPool` (the webview's CSP has `worker-src blob:`); `@viz-js/viz` is stubbed (overviews are Mermaid only), the Oniguruma WASM aliased away as in the other builds, and the shared CSS's web fonts (Inter, Geist Mono) dropped (`dropWebFonts`: the tab uses VS Code's fonts). A second entry, `dist/reader/diagram.js` (`src/guides/webview/diagram.ts`), shares the reader's Mermaid and ELK chunks with the other Guides webviews: they import it lazily from the URL the host puts on the body (`data-pn-diagram`, `webview/diagram-loader.ts`), so `guides-webview.js` carries no Mermaid. Both CSPs (`webview-csp.ts` outside the answer tab, `readerCsp`) have `script-src 'nonce-…' 'strict-dynamic'` and no host: only the nonced script and what it imports itself run (the reader's lazy chunks, `diagram.js`), so markup past the sanitizer cannot load even one of the extension's own scripts (checked in a real `serve-web` webview). A render check whose engine did not load (`diagram.js` missing, a chunk that fails) answers `unavailable`; the host reads that as not checked (`null`: the controller asks another webview, else `checked: false`), and only Mermaid's own errors refuse the agent's diagram. The Guide tab's own recheck of an `unchecked` guide retries only while the tab is still loading and stops at once once it answers `unavailable` (`diagramEngineUnavailable`). `scripts/watch.ts` runs the reader's Vite build in watch mode too. The generation tab has its own view type, `plannotator.guides.run` (`RUN_VIEW_TYPE`). `.vscodeignore` leaves out source maps and build configs; the vsix is about 4.2 MB. The extension is the reader's `GuideHost`: it sends `init` (`ReaderInit` in `reader-protocol.ts`: the guide snapshot from the store, ticks, chapter colors, the files changed on disk since the guide (`changedPatchFiles` against a fresh `git diff <base>` for local guides, with the user's own `diff.renames` as the guide's patch had, renamed files' old paths in the pathspec too: `changedSinceDiffArgs`, so a pure `git mv` does not read as changed; at most 500 paths per run, a rename's two paths in one run, so a large guide is batched, never skipped), the answering agent, the chapter to start at) and answers the reader's messages; every message from the reader passes `parseReaderMessage` (strict shapes: repo-relative paths with no `..`, absolute or drive part; integer positions; capped, non-blank questions), and the reader takes messages only through `fromWebviewHost` (the page's own origin). The controller then accepts a file path only when it is one of the guide's files (`ReaderModel.isGuideFile`: hover, references, navigate, openFile, openDiff, toggleFileReviewed, ask); file ticks are kept for guide files only; a place opened outside them (the hover card's Open in editor, a run's activity location) must be a regular file inside the repository once symlinks are followed (`realFileInside`, `src/guides/safe-path.ts`), and so must a guide file's head on disk wherever it is opened, hovered, diffed or linked (`headLeavesRepo`: `resolvePosition` for hover, definition, references and open; `openDiffBeside`; `code:` and `symbol:` links in `locateLink`, for any file of the repository, a `symbol:` link's own path refused before any language server is asked or the file read; the editor's Ask; the text search for a symbol's definition, `searchDefinitions`, and the builder's `resolveFile` hook, `resolveHeadFile`, read a file only through `realFileInside`; a refusal says "is not on disk" when nothing is at the path, `headRefusal`), so a symlink the change adds out of the repository (`notes.md -> ~/.aws/credentials`) is never opened, hovered or asked about. Seams added to the shared chain for it, all optional: `GuideHost.renderFileActions` (Open in editor / Diff), `renderSectionFooter` (the chapter's ask box and answers), `renderLink` (`symbol:` / `code:` links in chapter text), `TokenHoverCard`'s `content`, and `askOnly` on `AllFilesCodeView` / `ToolbarHost` / `AnnotationToolbar` (the selection toolbar is the Ask box only and closes once asked; no comments in the Guide tab). They change guides.show's viewer bytes, so its manifest was regenerated. **Layout:** one scrolling page, the overview then every chapter (prose column `minmax(240px, 320px)` beside unified diffs at the tab's width), under a sticky strip (`ChapterStrip.tsx`: title, "N of M reviewed", Back, Overview, chapter pills with the chapter colors and a check when reviewed, Export, outline = focus the tree); narrow tabs drop the count, Export's label and then Overview. Theme: the reader's palette is picked from VS Code's theme name (`vscodeThemeOf`, else dark-plus), its mode from the body's `vscode-light`/`vscode-dark` class, and `reader.css` maps the UI tokens onto `--vscode-*` variables (fonts too). **Hover and navigation** (the spike, `.product/drafts/vscode-guide-ux/HOVER-SPIKE.md`: warm round trip median 7 ms): the review app's `useTokenHover` with a `resolve` seam posts `{ path, side, line, character, token }`; `reader-intel.ts` opens the real document (head: the working-tree file or the PR worktree file; base: the `plannotator-guide:` document), finds the token there (`locateToken` in `reader-mapping.ts`: exact, else the same line, else within 40 lines, marked stale), and calls `vscode.executeHoverProvider` + `executeDefinitionProvider` together; while TypeScript still loads the project ("(loading...)") it asks again every 300 ms for up to 5 s, and a definition that lands on an import or re-export line is followed up to two hops (`realDefinition`). The card (`HoverCard.tsx`: code blocks, sanitized markdown with `command:` links dropped (`splitHoverMarkdown`), "Changed in Chapter N", the definition's place, Go to definition F12, Find references (N) ⇧F12 (the count arrives in a second request), Open in editor). ⌘-click (Ctrl elsewhere) or F12 on a token: a definition in a changed file of the guide scrolls the reader to that line on its side (`reveal` with `line` and `side`, `scrollToDiffLine` / `findDiffLine` in `reader/lines.ts`: an unchanged row's numbers are read per row, `data-line` the old number inside the split view's `[data-deletions]` column and the new one elsewhere, `data-alt-line` the other; only the latest jump lands, a later jump, a chapter jump, Overview or Back cancels one still waiting for its row, and so does the reader scrolling, pressing a key or clicking meanwhile (a jump that arrives first also skips the opening scroll to the first chapter not reviewed); it shows **Back**); anywhere else its own document opens beside at the definition, the base revision's for a definition found from a removed line (`docSideOf`, `guideFileAt`: a `plannotator-guide:` base document is never read as the head), with a status-bar message; Shift+F12 opens the references view. `code:path#L24` links land on their line too. Tree rows (chapters, files), `openChapter` / `openFile` and in-guide `code:` / `chapter:` links reveal in the Guide tab; **Diff** opens VS Code's own diff beside (`openDiffBeside`), where the context menu's Ask still works. Kept from 0.17.0: the tree as the outline (with checkboxes; chapter ticks are the format's `reviewed[]`), the status-bar item ("Guide · Chapter N of M · X/M reviewed", the chapter in view), the gutter marks, focus-range highlight and the one hover line on guide files opened in an editor. Not built: comments on the diff (the toolbar is Ask only); HTML overview diagrams (not drawn, as before); base-side hovers answer only what a language server gives on a virtual document.
- **Ask the agent** (approved 2026-10-23, `.product/approved/vscode-guides-ask/`, not in this repo; the owner's answers override its brief). Entry points: selected lines in the Guide tab's diff (the selection toolbar opens as the Ask box, `askOnly`, which keeps its outside-click and Escape dismissal on touch screens and narrow tabs too; the question posts `ask` with the path, the side (`askLines`: removed lines are base lines, added and unchanged lines head lines; with the file's patch the patch rows between the two ends decide, since the unified view reports an unchanged row as a new line: removed lines with unchanged ones are the old version's lines, so two unchanged ends around a removed line ask the old side; a selection holding both removed and added lines is refused with a note; otherwise the new side) and the lines, `GuideAsks.askAboutLines`, whose code is the guide patch's own lines on that side (`patchExcerpt`), never read from disk, so a symlink in the change cannot leak what it points at; lines the patch does not show go without code; the old side of a renamed file is named by its old path, `oldPath`), the chapter's box under its text (**Ask about this chapter…**, `ChapterAsk.tsx`: typed text is asked about the chapter, `askChapter`), and the editor context menu **Ask the Agent About This…** (`plannotator.guides.askAboutSelection`, shown when `plannotator.guides.editorInGuide`, set from the active editor by `guideSideOf` in `vscode/uris.ts`, and text is selected: a Quick Pick question box, `vscode/ask-box.ts`). No keyboard shortcut. The answer tab opens beside the Guide tab as soon as a question is asked (`preserveFocus`) and shows the agent's work (time, cost, tool calls, streamed text, Stop); answers are marked on their lines in the Guide tab (`ask-markers.ts`: the review app's AI markers; a click opens the answer) and listed under the chapter. Follow-ups are asked at the foot of the answer tab (the same ACP session). Closing or switching the guide while a question runs stops it. Who answers: the reader's pick, else the sidecar's `agent`, else the agent whose `engine` wrote the guide. `vscode/asks.ts` (`GuideAsks`) runs it; `ask/session.ts` (`GuideAskSession`, no `vscode`) is one ACP session per guide kept while the window is open: the first question loads a saved session when the agent's `initialize` advertises `agentCapabilities.loadSession` (`sessionsToLoad`: the sidecar's `askSession` for the same agent first, then the guide's own `acpSessionId`), replayed updates ignored; a failed or unsupported load starts `session/new`; follow-ups reuse the session; the agent stops after `ASK_IDLE_MS` (10 min) and the next question loads the conversation again where it can (the session id is saved as `askSession { id, agent }` in the sidecar). One question at a time per guide. Same user config and permissions as a guide run (agent policy): permission requests with every option in the answer tab (`renderPermissions`) and a notification, opt-in automatic approval, the agent's own `permissiveModes` only then. The prompt (`ask/prompt.ts`, modes `fresh` with the guide's title, intent and chapters / `loaded` / `next` / `followUp`) carries where the change is, the selected lines numbered, and the file's (or the chapter's files') diff from the guide's patch, capped. ## Plan Review Flow

```
Claude calls ExitPlanMode
        ↓
PermissionRequest hook fires
        ↓
Bun server reads plan from stdin JSON (tool_input.plan)
        ↓
Server starts on random port, opens browser
        ↓
User reviews plan, optionally adds annotations
        ↓
Approve → stdout: {"hookSpecificOutput":{"decision":{"behavior":"allow"}}}
Deny    → stdout: {"hookSpecificOutput":{"decision":{"behavior":"deny","message":"..."}}}
```

### Qwen Code plan review

Qwen Code runs the `plannotator` Qwen extension (`apps/qwen-code/extension/`): a `PermissionRequest` hook on `exit_plan_mode` that runs `plannotator` (timeout 345600000: Qwen reads a command-hook timeout of 1000 or more as milliseconds) and a `PreToolUse` hook on `enter_plan_mode` that runs `plannotator improve-context` (timeout 5000: 5 s both on Qwen before 2026-09-12, which read every timeout as milliseconds, and after). Both set `PLANNOTATOR_ORIGIN=qwen-code` through the hook's `env` field (no shell prefix, so it works on Windows). The plan arrives inline (`tool_input.plan`), as Claude Code's does.

- **Detection.** The plan hook knows Qwen from its payload alone (`isQwenPlanPermissionRequest` in `apps/hook/server/qwen-plan.ts`: `PermissionRequest` + `exit_plan_mode`, a pair no other host sends), so an older Qwen without the hook `env` field still gets the Qwen badge and tool name. Elsewhere `detectedOrigin` reads `QWEN_CODE_SESSION_ID` (Qwen sets it for its hooks and its shell tool) or `QWEN_CODE=1` (shell tool only), after `GEMINI_CLI` and before `OMPCODE`. Qwen also sets `CLAUDE_PROJECT_DIR` for hooks, as an alias; the plan hook uses `QWEN_PROJECT_DIR` for the history root instead.
- **Decision.** `qwenPlanHookOutput`: deny is `{hookSpecificOutput:{hookEventName:"PermissionRequest",decision:{behavior:"deny",message}}}`, and Qwen hands `message` to the model as the tool's error, so the agent revises at once and stays in plan mode. Approve is a bare `{behavior:"allow"}`: no `updatedInput` and no Claude-only `updatedPermissions`.
- **The second confirmation.** Qwen never lets a hook approve a tool that needs the person (`requiresUserInteraction`; `exit_plan_mode` is one), so after an approve in the browser Qwen still shows its own plan confirmation in the terminal (Restore previous / Proceed once / Proceed always / Cancel), and the person approves there too. That is Qwen's rule, not a Plannotator bug. For the same reason approval notes cannot reach the model: `approvalNotesSupported` stays false. The NonoElRobot fork reports that a PreToolUse hook does not fire on `exit_plan_mode`, so it cannot hold the turn instead (not checked here).
- **Skills.** Qwen reads `~/.agents/skills` (the shared core skills) and `$QWEN_HOME/skills`, and the second wins on a name clash, so `apps/qwen-code/skills/` (review, annotate, last) replace the shared copies for Qwen without a second name. They tell the model to use the shell tool's `is_background: true`: a foreground command is stopped after 2 minutes by default (10 at most), which would end the review. The extension carries no skills: Qwen names extension skills `plannotator:<name>`, which would list each one twice.
- **Install.** The three installers install the extension and the skills when they detect Qwen Code 0.13.0 or newer; see `PLANNOTATOR_SKIP_QWEN_INSTALL` in [environment.md](environment.md) for detection, the stable source path and the update rules. Tests: the `Qwen Code integration (install.sh, fake qwen)` and `Windows installers' Qwen Code steps` blocks in `scripts/install.test.ts` (fake: `scripts/fixtures/fake-qwen.ts`; the `qwen-installers-windows` CI job runs them on Windows with a `qwen.cmd`), and the `Qwen Code` block in `packages/server/uninstall.test.ts`.
- **Annotate last.** `apps/hook/server/qwen-session.ts` (ported from the NonoElRobot fork, commit c6a02a0): `QWEN_CODE_PROJECT_DIR` + `QWEN_CODE_SESSION_ID` name `<project dir>/chats/<id>.jsonl`; otherwise the newest chat of `<$QWEN_RUNTIME_DIR | $QWEN_HOME | ~/.qwen>/projects/<sanitized cwd>/chats/`. Messages are read along the active `parentUuid` chain, so a `/rewind` never offers a reply that was rewound away. The fallback skips Ask AI chats (ids starting `a5ca1000`, see the Qwen Code transport note in code-review.md).
- **Ask AI.** The `qwen-sdk` provider answers Ask AI with the installed `qwen`, and is the default for the `qwen-code` origin; see the Qwen Code transport note in [code-review.md](code-review.md#ask-ai-provider-defaults).
- **Tests.** `apps/hook/server/qwen-hook.test.ts` (the real CLI: payload-only detection, both decision shapes, Claude's payload unchanged, `last` from the session variables), `apps/hook/server/qwen-session.test.ts`, `apps/qwen-code/qwen-code.test.ts` (hook timeout and origin, no extension skills, background runs).

### Plan review header decision control (#1057)

Approved design: "plan-review-decision-control" (owner approval 2026-10-21, design record not in this repo; built as the proposal shows). Plan review's header uses the same `DecisionControl` annotate and code review use, from the pure `buildDecisionSpec({ app: 'plan', plan: { answers, directEdits, answersOnly, agentName, approveTarget } })` (`packages/ui/utils/decisionSpec.ts`), with no ghost Close (a plan review ends with a decision). It replaced the old pair (an outlined Send Feedback beside a green Approve, OpenCode's `ApproveDropdown`), the "Add Feedback First" dialog (the empty Send Feedback path is now **Request changes…** in the caret) and the Claude Code "Feedback Won't Be Sent" dialog with its faded Approve and hover note (#1457).

- **States.** Nothing to send: **Approve** (OpenCode: `Approve → <agent>`, the agent switch target, cut at 24 characters), caret: "Approve with a note…" (only where notes on approval are delivered) and "Request changes…". Something to send: **Send Feedback**, or **Send answers** when the only feedback is question answers (`isAnswersOnlyFeedback`); caret: "Send with a note…" ("Send answers with a note…"), "Approve with notes" (only where delivered; `→ <agent>` on OpenCode), and always "Approve, discard N annotations…" (the noun follows the feedback: answers, annotations, direct edits) with one confirm, "Discard & approve". Where notes would be lost, that row's subtitle and confirm name the agent ("Claude Code can't take notes on approval").
- **Which hosts take notes on approval is a server advert, not the agent's name.** Both plan servers advertise `approvalNotesSupported` on `/api/plan` (Bun `ServerOptions.approvalNotesSupported`, Pi `startPlanReviewServer`'s option; absent or false reads as false in the tab, so an older server offers no approve-with-notes row). Set true by: the Claude Code mod's `claude-mod-plan` (`planHostResult` composes approved-with-notes), the OpenCode CLI bridge (`opencode-plan`) and the embedded OpenCode plan server (the `submit_plan` executor), the DeepSeek Harness bridge (`dsh-plan`; `@plannotator/dsh` approves, then steers the composed notes into the agent), and Pi's `startPlanReviewBrowserSession` (`deliverPlanDecision`; the event API's result carries `feedback`). Left false: the classic Claude Code PermissionRequest hook (its allow carries no message), Gemini CLI (a `systemMessage` is shown to the person, not the model), Qwen Code (it ignores a hook's allow on `exit_plan_mode`), Codex, Copilot CLI, Mistral Vibe, and archive.
- **Transports are unchanged.** Primary and Mod+Enter are one `submitPrimaryDecision` (`submitPrimaryDecisionRef`): Approve posts `/api/approve` (with `permissionMode` for Claude Code, `agentSwitch`, `planSave`, the notes integrations, `serverSession`, `planRevision`), Send Feedback / Send answers post `/api/deny` (`answersOnly: true` only for answers alone). Routing is pure in `packages/editor/planDecision.ts` (`resolvePlanDecisionAction`): a note becomes a `GLOBAL_COMMENT` and is posted one render later (annotate's #1436 mechanism, `queueNoteDecision`), on `/api/deny` for Request changes / Send with a note and on `/api/approve` for Approve with a note; "Approve with notes" posts the approval with the session's feedback (what plan Approve always sent); the confirmed discard posts a bare approval (`handleApprove({ discardFeedback: true })`, no `feedback`). Every approval goes through `requestPlanApprove`, so the unsaved-file-edit warning and OpenCode's "Agent Not Found" check run on every approve path, and that dialog's "Approve Anyway" runs the captured continuation (a confirmed discard stays bare). A note on Send answers makes the deny mixed (the note is a comment), so it carries the denied prompt, as any mix does. Unlike annotate's L3 retry, a queued plan note decision is never left armed: after any refusal (409 `plan_revised`), cancelled warning (Agent Not Found, unsaved file edits) or failed POST it is dropped, the note stays as an ordinary general comment, and the primary means what its label says (Send Feedback posts the deny); the reviewer decides again from scratch. A plan revision waits while the decision note is open (`[data-decision-note-input]` and the compact `[data-decision-note-composer]` are in `PLAN_REVISION_COMPOSER_SELECTOR`, `packages/editor/hooks/usePlanRevisions.ts`). When the only feedback is saved file changes (a host that grants source save), the approve-away row reads "Approve without telling the agent…" and its confirm says the changes are already on disk (`plan.savedFilesOnly`); plan review's own servers grant no source save, so this does not arise there today.
- **Menu rows that are not decisions** go through `DecisionControl`'s `menuFooter` (`packages/ui/components/PlanDecisionMenuExtras.tsx`): OpenCode's agent picker as an "After approval, switch to" radio section (`role="menuitemradio"`, the arrow keys reach it; a pick writes the `agentSwitch` setting and keeps the menu open; shown in both states), and for Claude Code one read-only line, "After approval, Claude Code runs in <mode>", with **Change** (closes the menu, opens Settings). ### Linked documents in plan review (#1545)

A plan's draft (`/api/draft`) is keyed by the plan's text and holds the PLAN's comments. Comments on the documents the plan links are saved per document, under each file's path, by the same machinery annotate uses (#1710, "Annotate drafts follow the file" in `annotate.md`): both plan servers create a `createDocumentDraftStore` (`packages/shared/annotate-draft.ts`, vendored to Pi), serve `/api/draft/document`, and advertise `documentDrafts: true` on `/api/plan` (not in archive mode). The client is unchanged from annotate: `useDocumentDrafts` writes each linked document's copy, and `composeSessionDraft` keeps the plan's draft on the plan's comments even while a linked document is open, so opening a linked document with no comments never empties (and so deletes) the plan's draft. Before this, the draft held only the open document: opening an empty linked document deleted it, and a reload with a linked document open offered that document's comments as the plan's.

- **Draft Recovered offers every document.** The store also keeps a durable index of the copies the review wrote or read, beside the plan's draft (`documentDraftIndexKey(<plan draft key>)`). GET `/api/draft` adds `documents: [{ path, annotations, globalAttachments }]` for every listed copy (`loadSessionDraftWithDocuments`); with only those, it answers a draft with no plan comments, so the banner still shows. `useAnnotationDraft` counts them (the banner says "including comments on N linked documents", or "on N linked documents" when the plan itself has none) and returns them from `restoreDraft()`; App puts each on its own document with `useLinkedDoc.restoreStoredDocuments` (a cache entry for a document not opened yet, so the comments count, list and reach the feedback at once) and marks the copies as read (`adoptRestoredCopies`), so opening the document does not merge them twice. Dismiss returns them from `dismissDraft()` and App clears their copies (`discardCopies`). A single-document plan's draft is served byte for byte as before.
- **Allowed paths** are what `/api/doc` serves: inside the project, and on Bun also a document the plan links beside its own plan file (`isPlanLinkedDocPath`, `packages/shared/doc-resolve.ts`). Any other path is refused (`403`) and its comments ride the plan's draft, as before.
- **Clearing.** Approve and deny clear the plan's draft (unchanged) and every copy the review wrote, read or lists, and drop those entries from the index; later document writes get `409`. The index key comes from the plan's text alone, so the same plan reviewed in two folders (worktrees) shares one index: an entry this server cannot serve (not an existing file, outside its allowed paths) is never offered, counted or cleared, and stays in the index; the index file is deleted only when no entries remain. GET `/api/draft/document` lists the copy it reads, so it has the writes' cross-site guard (`isSameOriginOrNoOrigin`, `403`). Pi's session close keeps them, as it keeps the plan's draft; the host status `unsentAnnotations` counts them. Copies follow the file (#1710): an abandoned review's comments on `docs/design.md` also come back when that file is opened in another session.
- Tests: `packages/server/linked-document-drafts.scenarios.ts` (both runtimes: `packages/server/linked-document-drafts.test.ts`, `apps/pi-extension/server/linked-document-drafts.test.ts`), `packages/ui/hooks/useAnnotationDraft.documents.test.tsx`, the DOM test `packages/editor/App.planLinkedDrafts.test.tsx`, and the browser proof `tests/e2e/plan-linked-doc-drafts.spec.ts`.

### Pi plan review does not block

On Pi, `plannotator_submit_plan` returns as soon as the review server is up
("submitted for review … end your turn and wait", `terminate: true`) instead of
holding the tool call until the reviewer decides, so the session stays usable
during review and "Ask this session" works there. The decision is delivered
later by `deliverPlanDecision` (`apps/pi-extension/index.ts`) as a
`pi.sendUserMessage(..., { deliverAs: "followUp" })`, the same delivery review
and annotate feedback use (Oh My Pi only queues a message that names
`deliverAs`, even when idle, so there an idle session gets it without one:
`resolveIdleDeliveryOptions` in `current-pi-session.ts`): approval switches to the executing phase first
(tools, model, `plannotator-execute` entry) and sends the approved /
approved-with-notes prompt, which starts the execution turn and its framing;
deny and answers-only send `composePlanDeniedMessage`; external execution mode
hands off and records a non-triggering `plannotator-handoff` message. Nothing
is implemented before approval because the phase stays `planning` while the
review is open, so the planning write gate still holds. The open review is
closed (and its decision dropped) when plan mode is left, when a `/tree` path is
not planning, and on `session_shutdown`; a plan decision is never re-targeted to
a replacement session. The Esc-aborts-the-review behavior of the old blocking
tool is gone: leaving plan mode is how to abandon a review. Closing it first
calls the plan server's in-process `closeKeepingDraft()` (never reachable over
HTTP, where a plan review stays unclosable): open tabs get the `session-closed`
event with `by: "session"` (the tab shows "Review Closed", not "Closed by the
Agent", which stays for `by: "agent"` host closes), and a late approve/deny
answers `409`. The saved draft survives the close, but the server stops right
after, so the last unsaved keystrokes (the draft autosave's debounce window)
may be lost. The same close runs when planning ended while a review was still
starting. Reviews opened through the `plannotator:request` event API
(`plannotator-events.ts`) deliberately do NOT close on `session_shutdown`: the
README promises `review-status` lets a caller recover across session restarts,
so a decision made in that tab after `/reload` is recorded for `review-status`
and never emitted (the replaced runtime's bus is gone). That status file is
written atomically (temp file + rename), and one that cannot be parsed is left
untouched (logged, the write skipped) rather than restarted from `{}`.
Decision listeners run on a microtask (`publishDecision` in `serverPlan.ts`),
because a replaced runtime's `pi.events.emit` throws Pi's stale-ctx error
synchronously and an escape inside the HTTP handler ends the Pi process
(#1864). In `plannotator-events.ts` the review-result emit, `request.respond`
and the status writes are each wrapped in try/catch; `index.ts`'s
`handoffApprovedPlan` emit is not wrapped itself: it runs either inside the
submit tool call (auto-approve, a live session) or behind
`deliverPlanDecision`'s liveness check inside a caught promise chain.

**Revisions while a review is open update the same tab**: a resubmission while a review is pending calls the Pi plan
server's `updatePlan`, which saves a new history version (slug from the revised
heading, `previousPlan` from that slug's prior version) and bumps a revision
counter. `/api/plan` carries `planRevision`; the plan editor polls
`/api/plan/revision` every 2s only when that field is present
(`packages/editor/hooks/usePlanRevisions.ts`) and loads the revision in place
through `applyEditedDocument` (annotations re-anchor by text, the diff base
re-seeds through `usePlanDiff`'s docKey). It waits while Edit Mode is open or
holds direct edits, or a linked document is open. Approve/deny bodies echo
`planRevision`, and the server answers `409 { code: "plan_revised" }` to a stale
one, so a reviewer cannot approve text the agent replaced; the tab then loads
the revision and the reviewer decides again. Both plan servers implement it (`updatePlan` on the
server result, `/api/plan/revision`, the 409) but advertise `planRevision` only
when the caller passes `planRevisions: true`; today only Pi's
`plannotator_submit_plan` and the Claude Code mod's `claude-mod-plan` do, so
classic Claude Code, OpenCode and the Pi event-API `plan-review` action keep a
tab that never polls and sends unchanged bodies.
A decision claims the review right after the revision check (before the note
integrations are awaited), so `updatePlan` refuses from then on; a Pi
resubmission that hits that refusal tells the agent to wait for the decision
instead of opening a second review. The tab also holds a revision while a
comment composer or annotation popover is open.

**Execution works from the approved text, not the file.** The Pi plan
server's approve decision carries `plan`, the exact text on screen when the
reviewer approved. `deliverPlanDecision` appends it to the approval message
under "## Approved plan", records it on the `plannotator-execute` entry
(`approvedPlan`), and executes from it: the checklist, the per-turn framing
and resume (`resyncPhaseFromSession`) read the snapshot instead of re-reading
the plan file, and checkmarks are written back to the file only while its
checklist still matches the approved one. If the file differs from the
approved text at approval, the message says so and tells the agent not to
execute the unreviewed edits (to keep them, the user returns to plan mode and
the agent resubmits). Auto-approved plans (no UI) keep the file as their
source.

### Pi: the `plannotator` tool

The extension registers the shared tool contract
(`packages/shared/plannotator-tool.ts`, vendored as
`generated/plannotator-tool.ts`) with `pi.registerTool`: name, description,
validation (`parsePlannotatorToolInput`), argument mapping and result text all
come from it, and `parameters` is `PLANNOTATOR_TOOL_INPUT_SCHEMA` itself
(plain JSON Schema, which Pi validates without a TypeBox Kind since 0.79.1,
the peer floor; `plannotator-tool.test.ts` runs the installed Pi's
`validateToolArguments` against it). `executionMode: "sequential"` (#1622: an
"edit, then open" batch opens the edited file).

**Registration and activation are decided once per session.** The tool is
OFF by default on Pi and registered only when the agent tool switch turns it on
(`PLANNOTATOR_AGENT_TOOL=1` / `{ "agentTool": true }`, `resolveAgentTool(...,
host)` read once when the extension instance loads; Pi builds a new instance
per session and per `/reload`). Inside Oh My Pi (`detectPiHost(pi)` in
`pi-host.ts` answers `oh-my-pi`) the host is `oh-my-pi` and the tool is ON by
default, because OMP lists an extension tool as one short `xd://plannotator`
line instead of sending its definition; `PLANNOTATOR_AGENT_TOOL=0` /
`{ "agentTool": false }` keep it out there. `setPiHost` records the host for
the extension's review servers, whose `serverConfig` then advertises
`agentToolHost: "oh-my-pi"`. `omp.test.ts` (opt-in, the real `omp`) proves the
default on, the one line and no tool-list entry. Off, nothing is registered and the slash
commands are unchanged. It is registered with
`defaultActive: false` (Pi 0.99+ then leaves it inactive; older Pi ignores the
key and activates every registered tool), and the first `session_start`
(`settleAgentToolActivation`) makes it active when `ctx.hasUI`, inactive in
print/JSON mode, before the session's first request, and never touches it
again. Plan mode's `setActiveTools` calls add and release only the tools they
own, so `plannotator` stays in the tool list (and the prompt prefix) through
planning, execution, completion, leaving plan mode, `/tree` and `/reload`:
`agent-tool-stability.test.ts` drives that whole lifecycle over a fake Pi that
models both activation rules and fails on any request without the tool or any
`setActiveTools` that flips it after the start; it also pins the registered
description/parameters to the shared constants, no `promptSnippet` /
`promptGuidelines` on any Plannotator tool, and no `systemPrompt` from
`before_agent_start`.

**The bundled knowledge skill is user-invoked only.** `vendor.sh` adds
`disable-model-invocation: true` to the vendored copy's frontmatter (the
source `apps/skills/core/plannotator` stays model-invocable for the installers
that ask, #1377), so an npm-only Pi install keeps the #842 promise of no
Plannotator skill in Pi's system prompt; `/skill:plannotator` still loads it,
and the model learns the tool from the tool's own description. A CLI install's
`~/.agents/skills` copy still wins when present (#1642) and carries the
installer's model-invocation choice.

**One launch path.** `/plannotator-review`, `/plannotator-annotate`,
`/plannotator-last` and the tool share `launchCodeReview` / `launchAnnotate` /
`launchLastMessage` in `apps/pi-extension/index.ts` (in-process server,
"Ask this session" bridge, decision as a `followUp` message). The commands
notify a launch error; the tool throws it, which Pi reports as an error
result. Tool differences: the annotate target is ONE argument, so the #1182
tolerant word split never runs on it (`tolerant: false`); an opened review
returns `plannotatorToolOpenedText` with `terminate: true`, so the turn ends
and the session is idle for Ask; a gated session the tool opened delivers a
bare Approve as a message (`deliverApproval`, the mod's rule). The tool's
`last` skips the assistant entry holding the calling tool call
(`isAssistantEntryForToolCall` in `assistant-message.ts`): Pi saves an
assistant message at message_end, before its tools run, so otherwise the
agent's own "opening it now" message would open, and would head the picker.
On one fixed port (remote mode or a single `PLANNOTATOR_PORT`, read from
`getServerPorts`) a second open is refused while any review is open
(`fixedPortBusyText` names it), because the new server would otherwise
self-preempt the open one silently. A list target opens ONE `annotate-bundle`
review through the same `launchAnnotate` the slash command uses: the list goes
to the shared `selectAnnotateTokenTarget` as pre-split tokens (paths with
spaces survive), only the `bundle` selection opens (a missing entry answers
`buildMissingAnnotateFilesMessage`; a folder, URL or bare name refuses, so the
tool never opens fewer files than named), `resolveAnnotateBundleFiles` checks
types and size, and the subject is `plannotatorBundleSubject` (`2 files:
spec.md, notes.md`) in the result, list, close and decision heading; feedback
names every file (`Files:` + `annotateBundleTargetText`). A session without
UI (print/JSON mode) never has the tool active (see above), and a call that
reaches it anyway is refused, since nothing could deliver the decision later.

**Sessions, list and close.** Every review the extension opens (tool,
commands, `plannotator_submit_plan`) is recorded in ONE process-wide registry
(`getProcessPiReviewRegistry` in `apps/pi-extension/plannotator-tool-host.ts`,
on `globalThis`) with a `pn-` id until its decision settles. Process-wide
because Pi builds a new extension instance on `/reload` and `/resume`, and a
per-instance map would forget the open reviews of a session that merely
reloaded. `list` and `close` see only entries whose owner is the calling ctx's
`sessionManager.getSessionId()`, so another session's reviews (including the
previous one after `/new`) are never in reach; the global `sessions/` registry
is never read. `unsent` and `decided` come from the server's
in-process `hostControl.status()`; `close` calls `hostControl.close()` (the
reviewer's Close marked `closedBy: "agent"`, draft kept, tab told), so it
works in remote mode too, where the HTTP endpoints are off. A review the agent
closed delivers nothing: its decision handler notifies "the agent closed …"
instead (user-facing notices name a last-message review "the agent's last
message"; agent-facing texts say "your last message"). Plan reviews are listed
as `Plan vN` (the history version, read from `updatePlan`'s no-op answer for
the same text, and from each revision) and never closed.
Review, annotate and last decisions (commands included) now start with
`plannotatorDecisionHeading` (`Plannotator: notes.md (pn-3f2a9c) — Feedback ·
2 comments.`); outcomes follow the mod: a code review that is not an approval
is `Changes requested` (` · N comments` when it carries annotations), and the
PR-platform status post, which the review server marks `platform: true`
(#1719, `classifyReviewOutcome` in `apps/pi-extension/review-outcome.ts`), is
`Review posted` (`PLANNOTATOR_OUTCOME_REVIEW_POSTED`, shared with OpenCode 2) and delivered verbatim, without the verification
suffix. Every review decision whose feedback has content is delivered,
zero annotations included (PR description, PR comment and editor notes ride
only in the feedback text); nothing is inferred from the annotation count.
Plan decisions are unchanged. Pi cannot take over an agent's
shell `plannotator` command: its `tool_call` event can only block a call, which
the model reads as an error, so the skill's "use the tool" line is what steers
it.

### Pi: session events and the checklist window

**`plannotator:session-opened` / `plannotator:session-closed` (#1589).** One
pair per Pi review, whatever opened it (`apps/pi-extension/session-events.ts`):
the `/plannotator-*` commands and the `plannotator` tool (`trackReview` in
`index.ts`, at the registry's add and its decision or failure), plan review
(the submit tool, closed by its decision, by `stopPendingPlanReview` or by its
server stopping), and `plannotator:request` code-review / annotate /
annotate-last / plan-review (`plannotator-events.ts`, which now starts the
session and waits on it itself so the URL is known before the decision).
Opened: `{ id, action, url, openedAt, piSessionId?, reviewId?, requestId? }`,
`id` the registry's `pn-` id (a fresh `pn-` id for `plannotator:request`
reviews, which are not in the registry; unique among the open reviews both
ways: `newSessionEventId` skips ids the registry or an announced review holds,
and the process registry skips ids an announced review holds,
`isSessionEventIdOpen`), `action` one of `plan-review`,
`code-review`, `annotate`, `annotate-last`. Closed: the same plus `outcome`
(`approved`, `submitted`, or `closed` with `closedBy` `reviewer` | `agent` |
`stopped` | `error`) and `closedAt` (`sessionEndOf` / `sessionEndOfError`).
The handle emits closed at most once; an event with no live bus is dropped. Archive emits neither. **Cache safety:** they go
on `pi.events` only, never a message, entry, system prompt or tool list.
**Stale runtimes (#1864):** every emit runs on a microtask inside try/catch;
it goes through the opener's `pi` when the opener's session was live at the
moment of the open or close, else (or when that throws) through the instance
that last claimed a process-wide slot (`claimSessionEventBus` at
`session_start`, released at `session_shutdown`, on `globalThis` under a
versioned key; a holder that throws, torn down without releasing it, is
forgotten quietly), else nowhere, silently. So a review that ends after `/reload`
reaches the replacement's bus and never throws out of a handler.
`session_shutdown` now calls `stopPendingPlanReview()` first, so a plan review
the session ends closes on its own bus. `plannotator:request` reviews use the
listener's own `sessionLive`, so after a replacement their close goes to the
live instance's bus or nowhere (never the dead one; `plannotator-events.test.ts`
pins that nothing is logged). Proofs: `apps/pi-extension/session-events.test.ts`
(over a fake Pi whose instances share one bus and whose replaced instance
throws Pi's stale-ctx error: every model request, the active tools with their
definitions, `before_agent_start`'s results and every message, is
byte-identical while reviews open, close and outlive `/reload`, and identical
again with a bus that throws; the pair per entry point and outcome) and the
session-event cases in `plannotator-events.test.ts`.

**An update while a review is open keeps the decision.** The extension's lazy
imports go through `importFresh`, which refuses an import once the package on
disk is a different version than the one Pi loaded. The prompts a decision is
written with (`generated/prompts.ts`) therefore load when a review opens
(`preloadDecisionPrompts()` in `trackReview` and the plan review path), not
when the decision arrives: loaded late, an update under an open review lost
the reviewer's feedback ("could not be sent: Plannotator was updated…", 5 of 5
times on a real Pi 0.84.4 with `pi update --extensions`). A new lazy import on
a decision path needs the same preload. Proof:
`apps/pi-extension/review-survives-update.test.ts` (annotate and code review
over a copy of the extension whose `package.json` changes mid-review).

**The checklist widget scrolls (#1412).** Pi draws at most 10 lines of a
widget (`InteractiveMode.MAX_WIDGET_LINES`), so `updateWidget` sends
`checklistWindow(checklistItems)` (`apps/pi-extension/checklist-window.ts`):
all items when there are 10 or fewer, else 10 items ending on the first open
one (the first 10 until it is past them), and the last 10 once everything is
done. `setWidget` only; the status line keeps the full count.
