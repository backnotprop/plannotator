# Pele: a second engine for Mermaid fences (not on)

[Pele](https://pele.run) (MIT, pinned 1.3.0) draws Mermaid syntax without Mermaid. It is in the package but **draws nothing today and is in no build**: every Mermaid fence is drawn by Mermaid, as before, and no built file carries any of Pele's code. There is no setting and nothing a person can see.

One constant decides: `DIAGRAM_ENGINE_MODE` in `utils/diagram-engine.ts`.

- `'mermaid'` (shipped): Mermaid draws every fence; Pele is in no build (below).
- `'pele-where-safe'`: Pele draws a fence unless `diagramEngineFor` keeps it on Mermaid: it is a type where Plannotator offers comments on single parts under Mermaid and not under Pele (none today: `PELE_CAPABILITIES` gives Pele part comments on every type Mermaid has them). A `$$` math label no longer keeps a fence on Mermaid (below). A fence Pele cannot draw (its type is unsupported, or it throws) is drawn by Mermaid.
- `'pele'`: Pele draws every fence; its errors are shown.

What Pele keeps and loses, per type and per feature, is data in `PELE_CAPABILITIES` and `DIAGRAM_FEATURES` (same file), checked through the real `DiagramBlock` in `components/DiagramBlock.engine.test.tsx`. In short: part comments under Pele work on flowchart, sequence, state, class, ER and requirement diagrams, the six types Mermaid has them on (`utils/diagram-anchor-pele.ts`); Pele has 8 series colours. Math labels, styled label text, an author's typed colours and the Diagram Shadow setting are drawn around Pele by Plannotator (below). Comments, the popout, the Source pane, export, print and Ask AI work the same with either engine.

Part comments: for the same source, a click on a part makes the same anchor (kind, id or ends, label, source line) under either engine, so a comment made under one restores on the same part under the other. Checked per type against Mermaid svgs captured in Chromium (`test-setup/fixtures/diagrams/2x-*.svg`, each with its `.mmd` source) in `utils/diagramAnchorPele.test.ts`, and through the real `DiagramBlock` in `components/DiagramBlock.engine.test.tsx`. Per type:

- sequence: an actor by name (a stick-figure `actor` too), a message `msg-<n>` with its ends read from where its line starts and stops (at a lifeline, the edge of an activation bar however deep, or the box of an actor the message creates; a point two actors could claim names neither), a note `note-<n>`, a frame `frame-<n>`, numbered as both engines draw them (a frame nested in another first).
- state: a state or composite state by id (as a node, as Mermaid does), a transition `edge<n>`, a note; no start or end pseudo-state.
- class: a class by name (its label is the name, not an `«interface»` annotation), a relation by its ends; a note is not a part.
- ER: an entity by name, a relationship by its ends.
- requirement: a requirement or element by name (its label is the name, not the `<<Element>>` type line), a relationship by `{a}-{b}`, its label `<<satisfies>>` under both engines.

Two relations with the same ends (`User --> Order` twice) restore by their label. Two that are the same in ends and label cannot be told apart after a reload: Pele offers neither (a click there is a whole-diagram comment), as it does for a repeated flowchart edge. Labels Mermaid loses are not copied: when one message wraps over two lines Mermaid labels every message `''`, and a wrapped note by its first line; Pele keeps the words, and the restore, which goes by the ordinal when a label does not match, finds the same part either way.

Colours: `utils/peleTheme.ts` hands Pele the colours the Mermaid mapping already guards (`buildMermaidThemeVariables`) and re-fits the few pairs Pele draws differently; `utils/peleTheme.test.ts` checks every pair in every palette and mode. Labels wrap at `MERMAID_LABEL_WRAP_WIDTH` and use the app's fonts.

## Labels, an author's colours and the shadow

Pele by itself prints `$$…$$` as text, keeps no HTML in labels beyond bold, italic and `<br>`, ignores `%%{init}%%` and draws no shadow. `utils/pele-labels.ts` and `utils/peleAuthorTheme.ts` add these around it, in `renderPele` (`utils/diagram-render.ts`):

- **Math labels** (`$$…$$`, Mermaid's own syntax): before Pele runs, each formula is typeset with KaTeX through the math slot (`getMathRenderer`, else `loadMathRenderer`), with Mermaid's options (display mode, MathML output), and measured once in a hidden probe. The label gets private-use placeholder characters in its place: one token beside words when the formula is one line tall, or as many lines as it is tall on lines of its own. Pele lays out the placeholders, so a node is sized for its formula. After Pele, each placeholder becomes a `foreignObject.pele-math` holding the MathML, sanitized with the rest of the svg (DOMPurify's MathML profile). The formula takes the label's colour and anchor, and is scaled down only where Pele keeps a label on one line (class members, gantt tasks). Every label position works: flowchart nodes, edges and subgraph titles; sequence messages, notes and frame labels; state, class, ER, mindmap, gantt and timeline. Under happy-dom, or wherever no layout is measured, sizes come from an estimate. KaTeX's CSS gives `.katex` `position: relative`, which makes WebKit paint a transformed foreignObject at the svg's origin, so the wrapper is set to `position: static`. Cost: 0.4–3 ms per diagram warm in Chromium, 1–4 ms in WebKit and Firefox (10 diagram types, measured on the static harness, 2026-11-21).
- **A part comment on a math label** carries the TeX: the anchor's label reads `$$x^2$$` where Mermaid's reads the MathML text. Both restore by id, ends or ordinal, so a comment made under one engine still finds its part under the other.
- **Styled text**: `<span style="color:…">`, `<font color>`, `<u>`/`<ins>`, `<s>`/`<del>`/`<strike>` and `<code>`/`<kbd>` become tspans with a fill, a `text-decoration` or the mono font. A colour is kept only when it matches a strict pattern (`SAFE_LABEL_COLOR`: a hex, `rgb()`/`hsl()` of numbers, or one bare word such as a colour name), so nothing that can fetch or reach a variable gets in. Pictures (`<img>`) and Font Awesome icons (`fa:fa-…`) are dropped without a message.
- **An author's colours**: only the colours a source spells out (`themeVariables` in a `%%{init: …}%%` directive or front matter `config:`, with or without `theme: base`) reach the drawing, each replacing its own over the person's palette (`peleAuthorColors`). The mapping: `primaryTextColor`/`textColor` → text, `titleColor` → muted text, `lineColor` → lines, `primaryColor`/`mainBkg` → node fill, `tertiaryColor`/`clusterBkg` → group and note fill, `primaryBorderColor`/`nodeBorder` → borders, `taskBkgColor`, `critBkgColor` and `cScale0..7` → accent, critical and series colours. A theme **name** (forest, dark, neutral, default, base, any other) is ignored: the diagram draws in the person's theme exactly as with no directive (the owner's decision, 2026-11-21). An author's `background` is never painted, and no panel is drawn behind a diagram. Every value must pass the safe colour pattern; unknown keys and **`themeCSS`** (arbitrary CSS) are ignored. The rule for readability, with the floors the person's own palette is held to (`PELE_TEXT_MIN` 4.6:1 for text, `PELE_LINE_MIN` 3.1:1 for lines):
  - Drawn on the person's page (edge lines and arrowheads, sequence lifelines, and text outside a filled shape such as edge and message labels): an author colour below the floor against the person's page ground gives way to the person's colour for that element.
  - Text inside a filled shape (a node, a sequence actor, a note): the author's text colour when they give one and it reaches 4.6:1 on that fill, else whichever of the person's text and ground colours reads better on it.

  Plannotator's Mermaid draws less of an author's colours today (its complete `themeVariables` override wins over most of them).
- **Diagram Shadow**: the setting gives Pele the same `drop-shadow` Mermaid's neo look draws (`buildMermaidShadow`, the same amount), as one CSS rule scoped to the svg (`peleShadowCss`), built from numbers only after the sanitizer. Nodes, clusters, sequence actors and notes get it; mindmap and gantt get none, as under Mermaid.

- **Limits on what a source can cost**: every pattern that reads an author's text has one way to match (a colour over 64 characters is refused before it is tested; directives and front matter are read by `indexOf`, not by a rescanning pattern). A formula KaTeX throws on (a `RangeError` from deep nesting) stays its TeX text, and any failure in the label step is the fence's error, so `'pele-where-safe'` falls back to Mermaid. KaTeX runs with `maxExpand` 200 (`PELE_MATH_MAX_EXPAND`), one diagram's formulas add at most 250,000 characters of MathML (`PELE_MATH_TOTAL_LIMIT`), and `PELE_OUTPUT_LIMIT` is checked again after the MathML is in. The placeholder block avoids every character an entity in the source (`#57600;`, `&#xE100;`) stands for. An author's `stroke-dasharray`, `stroke-width`, `font-size`, `rx`/`ry` and letter and word spacing are held to sane ranges in the drawn svg (`utils/peleStyleClamp.ts`; a dash at least 1 px, a stroke at most 16 px, text 6 to 64 px). Covered by `utils/pele-hostile.test.ts`.

The browser proof is `tests/e2e/pele-labels.spec.ts` (Chromium and WebKit). It bundles `diagram-render.ts` with the switch forced to Pele and checks that every formula is MathML inside its box and its shape, and that styled runs are drawn.

Loading: through `pele/lazy`, so Pele's core and each diagram type are their own chunks, fetched on the first fence Pele draws.

## Out of every build while the switch is `'mermaid'`

`utils/pele.ts` is the only file that imports Pele's library (`tests/entry-assets.test.ts` checks every source file), and its `import('pele/lazy')` is behind `PELE_IN_BUILD`, a constant derived from `DIAGRAM_ENGINE_MODE`. The engine switch in `utils/diagram-render.ts` (the Pele renderer, the Pele finders, `peleTheme`) is behind the same constant. Rollup folds it, so a shipped build drops all of it, and the builds that inline every dynamic import (the Inbox surface, the Shape page, code review's diagram engine) have nothing of Pele to inline. A new build config needs nothing for this. What is left is two selector strings Plannotator's own Mermaid finder reads (`pele-edge`, the `pele` root class), about 250 bytes.

The guards read the artifacts: `tests/entry-assets.test.ts` checks every built page and `diagram-engine/engine.js` for class names only Pele's svg writer prints (CI's build job runs it right after the build), and `apps/review/diagram-engine/build.ts`'s `guardBundle` fails the build when a Pele module is rendered into `engine.js`. Tests draw with Pele through `test-setup/pele.ts` (`setPeleInBuildForTests`), which puts the library and the engine switch back the way a build with Pele in it has them.

## Turning Pele on

The one change: set `DIAGRAM_ENGINE_MODE` in `utils/diagram-engine.ts` to `'pele-where-safe'` (or `'pele'`). `PELE_IN_BUILD` follows it; no build config, alias or guard needs an edit (the artifact checks above skip, and the Inbox window's check then requires Pele to be lazy). What it brings back, measured with Pele 1.3.0 on 2026-11-21:

- **Packed apps** (plan review `index.html`, which OpenCode and Pi copy; the Inbox window `inbox.html`): Pele's core and diagram types are lazy chunks in the pack, about +684 KB in all (24.39 MB to 25.08 MB), none loaded up front; a page fetches the core and one type's chunk on the first fence Pele draws.
- **The Inbox surface** (`surface.html`, the phone's single-file page): it inlines every dynamic import, so all of Pele is in the page, about +690 KB (20.42 MB to 21.11 MB). An inlined module is parsed and run when the page starts, so this is load-time work too, not only bytes.
- **Code review's diagram engine** (`diagram-engine/engine.js`): it also inlines, about 240 KB to 913 KB. The review page itself carries none of it: it imports `engine.js` only when a Markdown preview or a guide overview holds a diagram fence. `guardBundle` allows Pele once the switch is on. To keep Pele out of `engine.js` too, serve it as a fourth runtime file the way `mermaid.js` is served.
- The Shape page draws no diagrams and does not change.
- The VS Code extension's Guide reader and the guides-show viewer are their own Vite builds: the same constant keeps Pele out of them while the switch is `'mermaid'`; what they gain when it is on was not measured.
